后端分层架构与数据模型规范（实用主义DDD）

后端分层架构与数据模型规范（实用主义DDD）

实用主义 DDD = 用 DDD 的思想解决复杂度，而不是照搬 DDD 的全部理论

一、 核心执行层职责说明

在后端架构中，Controller、Service 和 Repository 是处理业务逻辑和数据流转的核心“器官”，它们各司其职，有着严格的边界。

组件所在层级核心作用处理的数据模型核心原则与特点
Controller接口层 (Web 层)交通警察：负责路由转发与输入输出控制接收外部 Request，转换为 Command 传给底层；接收底层 DTO/BO，封装为 Response/VO 返回。处理 HTTP 请求、参数基础校验、身份解析。绝对不包含业务逻辑，不关心底层数据库。
Service业务层 (Domain 层)业务大脑：执行核心业务逻辑与规则处理 BO，调用 Repository 或其他 Service负责事务控制、业务规则校验、状态流转。不关心外部协议（无视 HTTP/JSON），是系统最核心的层级。
Repository持久层 (Data 层)数据搬运工：与数据库进行交互操作 Entity，查询返回 Projection只负责数据的 CRUD 和 SQL 组装。不包含业务逻辑，只关心“怎么查/存”，不关心“为什么查/存”。

二、 核心领域层（业务的基石）

在融入了领域驱动思想（DDD）的架构中，Model 是剥离了技术细节后，最纯粹的业务表达。

对象所在层级核心作用特点示例
Model核心领域层业务概念与规则的具象化纯净对象，无框架依赖（无 Spring/JPA 注解）。包含核心枚举、值对象、核心业务实体。UserAuthType (枚举) UserStatus (状态机)

💡 Model 层的核心价值：

核心业务逻辑只依赖纯净的 Model，不依赖底层的数据库结构（Entity），实现了真正的“业务与技术解耦”。

三、 数据模型职责说明（输入与输出的统一）

数据模型是系统中流淌的“血液”，为了保证各层之间的解耦和安全，针对不同的场景需要使用特定的数据载体。

对象类别具体命名层级作用特点示例
输入模型Request / Command接口层（入参）接收外部（前端/第三方）请求参数可校验（Validation）、可缺省、与接口强绑定CreateUserRequest AssignRoleCommand
输出模型Response / VO接口层（出参）封装并返回给前端的数据载体控制字段暴露、结构稳定、可包含脱敏逻辑UserProfileResponse UserDetailVO
传输模型DTO跨层 / RPC调用内部服务间或跨进程的数据传输解耦内部结构、无业务逻辑、适配远程调用WechatUserInfoDTO
业务模型BO业务层承载业务流转过程中的中间状态与规则聚合、充血/贫血模型、状态机载体UserPermissionBO
持久模型Entity持久层数据库表结构的一一映射全字段、与 ORM 框架（JPA/MyBatis）强绑定User
查询切面Projection持久层（只读）数据库查询结果的精简或聚合视图绝对只读、字段子集、与 SQL 强绑定UserPermissionProjection

🔍 命名风格约定（解决团队分歧）

针对输入和输出，团队需统一选择其中一种命名风格，切勿混用：

  1. RESTful 标准风格（最常见）
    • 输入统一叫 xxxRequest（例如 CreateUserRequest）。
    • 输出统一叫 xxxResponse（例如 UserDetailResponse）。
    • (注：Form 通常属于遗留的 MVC 时代结合页面模板的叫法，现代前后端分离架构中建议淘汰。)
  2. CQRS / DDD 风格（适合复杂业务）
    • 输入 (写) 叫 xxxCommand（例如 CreateUserCommand，代表一个改变状态的命令）。
    • 输入 (读) 叫 xxxQuery（例如 UserDetailQuery，代表一个查询参数）。
    • 输出 叫 xxxDTO 或保留 xxxResponse。

💡 核心红线规范：

  • Entity 绝不能越界进入 Controller。
  • Projection 绝不能进入 save 或 update 的写操作流程。
  • 接口的返回值必须是 Response 或 VO，绝对不能直接返回底层 Entity 或 BO。
  • 不要用 DTO 作为 Controller 的入参（Request）或出参（Response），DTO 专职于 RPC 或服务间内部流转。

DTO核心理解

隔离两个“不同模型体系”、“隔离变化”、“这两个对象是不是属于两个不同系统/边界？”

DTO = 用在“跨边界”的地方，而不是“所有地方”

1️⃣ 调第三方接口

WechatUserInfoDTO

👉 微信返回的数据结构 ≠ 你系统的结构

所以需要：

第三方数据 → DTO → 转换 → 你的 BO / Model

2️⃣ 微服务 / RPC / Feign（非常常见）

UserServiceClient.getUser() → UserDTO

👉 服务 A ≠ 服务 B

必须：

  • 用 DTO 作为契约
  • 防止内部模型泄漏

正确的架构

Controller → Request / Response
Service → BO / Model
Repository → Entity / Projection
外部 → DTO

👉 结果：

  • 每层职责清晰
  • DTO 不再滥用
  • 结构稳定

另一种说法：Request 是 DTO

👉 接收 Controller 传进来的数据（HTTP / JSON）

前端 JSON  →  CodeLoginRequest → 应用层

这就是典型的：

✅ 跨边界的数据传输对象（DTO）

类型是否 DTO用途
CodeLoginRequest✅ 是Controller 入参
CodeLoginResponse✅ 是Controller 出参
WechatApiRequest✅ 是调外部接口
User❌ 不是领域模型
UserProfileBO❌（一般不算）业务聚合

但再实用主义 DDD中，命名依然只在第三方接口中才体现

类型命名用途
前端入参xxxRequestController 输入
前端出参xxxResponseController 输出
第三方xxxDTO外部接口
RPCxxxDTO服务间调用

四、 数据流转全景视图

为了清晰表达，以下采用 Request / Response 风格作为示例：

1. 正向数据流（查询 / 读）

前端 → 发起 QueryRequest → Controller → Service → 指挥 Repository → 查出 Entity / Projection → 映射为 BO / DTO → Controller 封装为 Response / VO → 前端渲染

2. 反向数据流（提交 / 写）

前端 → 提交 Request → Controller (协议解析/基础校验) → 转化为 Command → Service (业务编排/执行动作) → 转化为/操作 BO 或 Entity (核心规则/状态变更) → Repository → 数据库持久化

👉 优先用：

Request → Service（拆字段传）

👉 参数变得复杂再引入Command：

Request → Command → Service

关键差异总结

为了让你更直观地理解为什么要多这一层，我们可以对比一下它们的职责：

环节对象名称主要职责在你代码中的体现
入口Request适配 HTTP 协议。处理序列化、Swagger 注解、基础非空校验。CodeLoginRequest
指令Command封装意图。它是 Service 方法的唯一参数，代表一个明确的业务动作。WechatMiniAppLoginCommand
模型BO / Entity处理规则。比如 UserBO.updateLoginInfo()。Command 里的数据会填充到 BO 中进行运算。UserService 操作的对象

为什么要把 Command 和 BO 分开？

  1. 动作 vs. 状态：LoginCommand 只需要 code；但 UserBO 可能包含 userId、status、registerTime 等几十个字段。如果你用 UserBO 来做登录参数，方法签名会变得极度模糊——调用者不知道该填哪几个字段。
  2. 幂等与溯源：在高级架构（如事件驱动）中，Command 是可以被记录和重放的。你可以记录“用户在 A 时间点发出了一个 LoginCommand”，但你很难记录“用户在 A 时间点发出了一个 UserBO”（因为 BO 只是个数据集合，不代表动作）。
  3. 多来源支持：你的 AuthService.loginByWechatMiniAppCode(command) 现在只依赖 Command。如果明天要加一个 MQ 消费者来触发登录，它只需构建 Command 即可，完全不需要碰 Request。

五、 易混淆概念辨析

1. Request vs DTO（最易踩坑）

维度Request / Command (输入)DTO (传输)
方向纯输入（Input）双向传输（内部/跨进程）
面向对象外部调用方（前端 / OpenAPI 客户端）内部微服务 / 第三方 API 适配
参数校验✅ 必须严格校验（@NotNull, @Size 等）❌ 通常不负责基础校验（信任内部流转）
复用性❌ 极低（与特定接口强绑定）✅ 较高（可在多个内部方法间复用）

🚨 红线警告：

坚决抵制“一个 DTO 走天下”！不要用 xxxDTO 接收前端请求，也不要用 xxxDTO 直接作为接口响应返回给前端。输入输出的语义必须明确。

2. Response vs VO（输出视角的细微差异）

  • Response：更侧重于 “接口级别的回应”。例如 ApiResponse<UserProfileResponse>，它往往包含了状态码、提示信息等外壳。
  • VO (View Object)：更侧重于 “视图层的数据聚合”。如果你们是纯粹的 BFF 层或后端只为特定 UI 服务，VO 的结构会严格贴合前端的 UI 组件树。
  • 结论：在绝大多数前后端分离项目中，Response 的 payload（数据体）本质上就是 VO，两者选其一作为包名统一即可（推荐统一使用 Response 降低认知负担）。

七、 一句话总纲总结

  • Controller 负责把守边界，Service 负责核心大脑，Repository 负责搬运底层数据。
  • Request/Command 负责“接收世界不可信的输入”。
  • Response/VO 负责“提供安全、脱敏、贴合场景的输出”。
  • Model 负责“定义系统最纯粹的业务基石”。
  • BO 负责“承载系统真实运转的业务逻辑”。
  • DTO 负责“跨越服务边界的数据搬运”。
  • Projection 负责“还原 SQL 世界的精简形态”。

Java 圈最流行的对象转换工具

既然分层这么清晰，必然会面临大量的对象属性拷贝（比如把 CreateUserForm 转换成 BO，再转成 Entity）。

在 Java 领域，目前最推荐、性能最高且最优雅的工具非 MapStruct 莫属。

为什么选择 MapStruct？

  1. 性能巅峰：它在编译期生成原生的 Java 代码（类似你手写的 set/get），运行期零反射，性能等同于手写。
  2. 类型安全：如果字段名对不上或类型不兼容，编译时就会报错，而不是等到运行时才抛异常。
  3. 代码洁癖友好：你的业务代码里不再有成堆的转换逻辑，只需要定义一个接口。

实战演示：从 CreateUserForm 到 UserEntity

假设我们要将前端传来的 CreateUserForm 转换成业务层的 UserBO，最后持久化为 UserEntity。

1. 引入依赖 (Maven)

除了 lombok，你需要加入 mapstruct 的核心库和注解处理器。

<properties>
    <org.mapstruct.version>1.5.5.Final</org.mapstruct.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.mapstruct</groupId>
        <artifactId>mapstruct</artifactId>
        <version>${org.mapstruct.version}</version>
    </dependency>
</dependencies>

2. 定义转换器接口 (Mapper)

这是 MapStruct 的灵魂。你只需要定义规则，具体的实现类由 MapStruct 在编译阶段自动生成。

package com.xiaodingtie.passup.modules.user.converter;

import com.xiaodingtie.passup.modules.user.controller.app.form.CreateUserForm;
import com.xiaodingtie.passup.modules.user.repository.entity.UserEntity;
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.factory.Mappers;

@Mapper(componentModel = "spring") // 交给 Spring 管理，可以在 Service 中 @Autowired
public interface UserConverter {

    UserConverter INSTANCE = Mappers.getMapper(UserConverter.class);

    // 1. 如果字段名完全一致，MapStruct 会自动映射
    // 2. 如果字段名不一致（例如 Form 里叫 username，Entity 里叫 account），使用 @Mapping 指定
    @Mapping(target = "account", source = "username")
    UserEntity formToEntity(CreateUserForm form);

    // 也可以方便地定义反向映射或 BO 转换
    // UserBO entityToBO(UserEntity entity);
}

3. 在 Service 中优雅使用

有了转换器，你的 Service 代码会变得异常干净：

@Service
public class UserServiceImpl implements UserService {

    @Autowired
    private UserConverter userConverter;

    @Autowired
    private UserRepository userRepository;

    @Override
    public void createUser(CreateUserForm form) {
        // 一行代码完成转换，无需关心内部细节
        UserEntity entity = userConverter.formToEntity(form);
        
        // 执行业务逻辑...
        userRepository.save(entity);
    }
}

MapStruct 的“企业级”高级技巧

为了配合你笔记中的职责划分，MapStruct 还能处理更复杂的场景：

  • 默认值与常量：@Mapping(target = "status", constant = "1")，创建用户时强制状态为正常。
  • 格式转换：自动处理 String 转 Date，或数字转枚举。
  • 多对一合并：可以将 CreateUserForm 和另一个 OperatorDTO（操作人信息）合并转换成一个 UserEntity。
  • 更新现有对象：使用 @MappingTarget，可以将 UpdateUserForm 的值覆盖到现有的 UserEntity 对象上，非常适合更新操作。
