    Java 线程池

    Java 线程池

    Executors 常用工厂方法对比

    这三种方式代表了 Java 线程池处理任务的三种不同“性格”。理解它们的关键在于核心线程数、最大线程数以及阻塞队列的配合。

    1. 三者对比概览

    特性newCachedThreadPoolnewSingleThreadExecutor自定义 ThreadPoolExecutor (示例配置)
    核心线程数0110
    最大线程数$Integer.MAX_VALUE$1200
    阻塞队列SynchronousQueue (不存任务)LinkedBlockingQueue (无界)SynchronousQueue
    空闲存活时间60秒0 (永久)60秒
    适用场景短时间内大量短异步任务需要任务按顺序执行高并发、压力可控的生产环境

    2. 深入原理分析

    newCachedThreadPool (缓存型)

    • 行为：来一个任务就开一个新线程，直到线程数达到惊人的 21 亿。如果线程空闲超过 60 秒则销毁。
    • 优点：响应速度极快，不会阻塞任务。
    • 风险：极易导致 OOM (内存溢出)。如果瞬间涌入几万个请求，它会尝试创建几万个线程，直接榨干 CPU 和内存。

    newSingleThreadExecutor (单线程型)

    • 行为：始终只有一个干活的线程。如果这个线程挂了，会换一个新的继续干。多余的任务都在队列里排队。
    • 优点：保证任务按顺序执行，且不用担心并发安全问题。
    • 风险：由于队列是无界的，如果生产任务太快，队列会无限膨胀，最终导致 OOM。

    自定义 ThreadPoolExecutor (生产环境推荐)

    • 配置解析：10 个常驻线程，最高扩容到 200 个，配合 SynchronousQueue。
    • 行为：由于使用了 SynchronousQueue（不存储任务），当 10 个核心线程都在忙时，新任务会立刻触发开启新线程，直到达到 200 个。
    • 优点：可控性高。配合拒绝策略（RejectedExecutionHandler），你可以明确知道系统在过载时该怎么处理（是丢弃任务还是报错）。

    3. 选择建议

    • 本地小工具/脚本：追求省事，用 newCachedThreadPool。
    • 后台串行任务（如写日志到同一文件）：用 newSingleThreadExecutor。
    • 高并发生产系统：必须使用手动 new ThreadPoolExecutor。这能强迫开发者根据机器性能设置合理的阈值，避免系统崩溃。

    容错处理：四种拒绝策略与 CallerRunsPolicy 的妙用

    在 Java 线程池中，当线程数达到最大值且队列也满了时，拒绝策略（RejectedExecutionHandler） 就是你的最后一道防线。

    如果不手动设置，默认使用的是 AbortPolicy（直接抛异常），这在生产环境可能会导致整站崩溃。以下是四种标准策略的对比：

    1. 四种拒绝策略对比

    策略名称行为描述形象比喻适用场景
    AbortPolicy (默认)直接抛出 RejectedExecutionException 异常。“我不干了，你自己看着办！”关键业务，需要立刻知道处理失败了。
    CallerRunsPolicy哪来的回哪去。让提交任务的线程（通常是主线程）亲自执行该任务。“老板，我忙不过来了，这活你自己干吧。”不允许任务丢失，且希望能通过这种方式让提交速度降下来。
    DiscardPolicy静默丢弃任务，不予任何处理，也不报错。“假装没看到，直接扔进垃圾桶。”对数据丢失不敏感的业务（如日志采集、无关紧要的统计）。
    DiscardOldestPolicy丢弃队列中最老的一个任务（排在队头的），然后尝试再次提交当前任务。“喜新厌旧，把排队最久的踢走给新任务腾位子。”追求数据实时性的场景（如最新的价格推送）。

    2. 深度建议：如何选择？

    • 追求系统稳定性：首选 CallerRunsPolicy。
      • 理由：它不仅保证了任务一定会被执行，还会因为主线程在干活而暂时无法提交新任务，从而产生一种天然的背压（Back-pressure）机制，保护系统不被冲垮。
    • 追求快速响应且数据可补发：使用 AbortPolicy。
      • 理由：配合日志记录和告警，你可以事后通过消息队列（MQ）或其他机制补偿处理这些失败的任务。
    • 极端高并发丢弃：如果任务确实不重要，DiscardPolicy 性能最高，因为它没有任何逻辑开销。

    3. 自定义策略

    你甚至可以实现 RejectedExecutionHandler 接口，在里面写自己的逻辑。例如：将任务临时持久化到数据库或者发送一条钉钉告警通知研发。

    new ThreadPoolExecutor(..., (r, executor) -> {
    // 1. 打印日志
    // 2. 存入 Redis 备用
    // 3. 统计丢弃次数
});

    进阶配置：ThreadPoolExecutor 核心参数详解

    这正是理解 SynchronousQueue（同步移交队列）与 CallerRunsPolicy（调用者运行策略）配合的最佳场景。

    由于 SynchronousQueue 的容量为 0，它不存储任务，而是直接在线程间传递。一旦核心线程满且达到最大线程数，新任务会立刻触发拒绝策略。

    1. 代码模拟演示

    这段代码模拟了“疯狂提交任务”的场景：

    import java.util.concurrent.*;

public class ThreadPoolDemo {
    public static void main(String[] args) {
        // 配置：1个核心，2个最大，使用 SynchronousQueue
        // 拒绝策略：CallerRunsPolicy (让提交任务的 main 线程自己干)
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
                1, 
                2, 
                60L, TimeUnit.SECONDS, 
                new SynchronousQueue<>(),
                new ThreadPoolExecutor.CallerRunsPolicy() 
        );

        for (int i = 1; i <= 5; i++) {
            final int taskId = i;
            executor.execute(() -> {
                System.out.println("任务 " + taskId + " 开始执行，执行线程: " + Thread.currentThread().getName());
                try { Thread.sleep(1000); } catch (InterruptedException e) {}
            });
        }
        executor.shutdown();
    }
}

    2. 执行结果预测与解析

    你会看到类似这样的输出：

    1. 任务 1：由 pool-1-thread-1（核心线程）执行。
    2. 任务 2：由于核心线程在忙且队列不存任务，立即开启新线程，由 pool-1-thread-2（达到最大线程）执行。
    3. 任务 3：线程池已满（2个线程都在忙），触发拒绝策略。由于是 CallerRunsPolicy，任务 3 会由 main 线程直接执行。
    4. 连锁反应：当 main 线程在执行任务 3 时，它无法继续提交任务 4 和 5，这就形成了一种“天然降压”。

    3. 为什么这个组合在生产中很流行？

    这种 SynchronousQueue + CallerRunsPolicy 的组合非常适合“高吞吐、低延迟”的系统：

    • 实时性高：任务要么立即被线程接走，要么主线程自己干，绝不在队列里发霉。
    • 自适应过载控制：当系统撑不住时，提交任务的入口线程（比如处理 HTTP 请求的 Tomcat 线程）会被拉去打工，这迫使它慢下来，不再接收新的前端请求，从而给后台线程池喘息的时间。

    生产实战：基于 $N$ (CPU核数) 的参数调优公式

    这绝对是面试中绕不开的“压轴题”，也是性能调优的精髓。设置核心线程数 $corePoolSize$ 并非拍脑袋，而是要看你的任务属于计算密集型还是 I/O 密集型。

    1. 科学计算公式

    我们需要根据 CPU 的核心数（用 $N$ 表示）来分情况讨论：

    A. 计算密集型 (CPU-bound)

    • 特征：任务在做复杂的逻辑运算、加密、视频解码等，CPU 几乎没有闲着的时候。
    • 公式：$N + 1$
    • 原理：线程数等于 CPU 核数能最大限度利用多核性能。多出来的那个 $1$ 是为了防止某个线程偶尔因意外（如页缺失）暂停时，CPU 不至于闲着。

    B. I/O 密集型 (I/O-bound)

    • 特征：任务大量时间在等数据库返回、调 HTTP 接口、读写文件。此时 CPU 是闲置的。
    • 公式：$2N$ （经验法则） 或 更精确的：$N \times \text{CPU 利用率} \times (1 + \frac{\text{等待时间}}{\text{计算时间}})$
    • 原理：因为线程大部分时间在“等”，所以多开一些线程，让 CPU 在 A 线程等待时去处理 B 线程的任务，压榨出极致性能。

    2. 如何在 Java 中获取 CPU 核数？

    不要硬编码数字，因为不同的服务器核数不同。你应该动态获取：

    int n = Runtime.getRuntime().availableProcessors();
// 如果是计算密集型：
int corePoolSize = n + 1;
// 如果是 I/O 密集型：
int corePoolSize = n * 2;

    3. 线程池配置的“避坑指南”

    在实际整理笔记时，请记住这三条金律：

    1. 不要用无界队列：new LinkedBlockingQueue() 如果不传大小，默认是 $Integer.MAX_VALUE$。任务堆积会直接撑爆 JVM 内存。
    2. 一定要给线程起名字：默认的线程名叫 pool-1-thread-1，出生产事故看堆栈（Dump）时，你根本分不清是哪个业务模块。建议自定义 ThreadFactory。
    3. 核心线程数不是越多越好：线程切换是有成本的（上下文切换）。如果线程太多，CPU 忙着切来切去，反而比单线程还慢。

    线程池队列对比：LinkedBlockingQueue vs SynchronousQueue

    要对比的代码：

    new ThreadPoolExecutor(10,50,60L,TimeUnit.SECONDS,new LinkedBlockingQueue<>(200));
new ThreadPoolExecutor(10, 50, 60L, TimeUnit.SECONDS, new SynchronousQueue<>());

    我的总结：

    LinkedBlockingQueue(200) ：只有当队列满了后，才会增加线程，线程和队列都满了后，会触发拒绝策略

    SynchronousQueue() ：没有队列，线程满后触发拒绝策略

    核心参数对比

    参数配置 A (LinkedBlockingQueue)配置 B (SynchronousQueue)
    核心线程数1010
    最大线程数5050
    等待队列有界队列 (容量 200)零容量移交队列
    扩容触发时机队列满了以后（即第 211 个任务时）核心线程都在忙时（即第 11 个任务时）

    1. 行为逻辑深度解析

    配置 A：LinkedBlockingQueue(200) —— “缓冲优先”

    这种配置比较保守，强调资源节约。

    1. 1-10 个任务：直接由核心线程处理。
    2. 11-210 个任务：核心线程满了，任务进入队列排队。
    3. 211-250 个任务：队列也满了，线程池开始创建新线程（增加到 50 个）。
    4. > 250 个任务：触发拒绝策略（RejectedExecutionException）。

    特点： 只有在队列堆满的情况下才会增加线程。这意味着如果你的任务执行较慢，任务会在队列里积压，导致整体响应时间变长。

    配置 B：SynchronousQueue() —— “立即执行”

    这种配置比较激进，强调低延迟。

    1. 1-10 个任务：由核心线程处理。
    2. 11-50 个任务：核心线程在忙，且 SynchronousQueue 不存储任务，它会立即尝试将任务移交给新线程。因此，线程数会迅速从 10 增加到 50。
    3. > 50 个任务：因为没有地方排队，直接触发拒绝策略。

    特点： 它更像是一个“传球手”。如果没有空闲线程接收任务，它会立刻要求开辟新线程。它的吞吐量通常更高，但对 CPU 和内存的消耗也更快。

    2. 适用场景建议

    • 选择 LinkedBlockingQueue (配置 A) 当：
      • 你希望平滑 CPU 峰值，不希望瞬时创建大量线程。
      • 任务之间没有依赖关系。
      • 你可以容忍任务在队列中等待一段时间。
    • 选择 SynchronousQueue (配置 B) 当：
      • 你需要极高的响应速度（任务来了立刻跑，不排队）。
      • 任务之间存在依赖（比如 A 任务等待 B 任务），排队可能会导致死锁。
      • 你有足够的硬件资源来支撑较多活跃线程的开销。

    3. 优化建议

    在配置 A 中，由于队列长度是 200，在任务量达到 211 之前，你的线程数永远固定在 10。如果你设置了 maximumPoolSize = 50，但在绝大多数情况下任务排队都不超过 200，那么那 40 个额外的线程位置实际上是被浪费的，永远不会被创建。

    以下是三个维度的优化方案：

    1. 动态平衡：根据任务性质调整参数

    你需要根据任务是 CPU 密集型 还是 IO 密集型 来重新审视这三个数字：

    任务类型核心线程 (Core)队列长度 (Queue)最大线程 (Max)理由
    CPU 密集型N + 1较大 (如 500)较小 (如 $N+1$)线程多了反而增加上下文切换开销。
    IO 密集型2N较小 (如 50)较大 (如 100+)任务常在等待，多开线程可以提高利用率。

    注：N 为 CPU 核心数。

    2. 让“最大线程数”真正发挥作用

    如果你发现即使在高负载下，线程数也始终停留在 10 个，且响应变慢，可以尝试：

    • 减小队列容量：将 200 改为 50。这样当第 61 个任务进来时，就会触发扩容到第 11 个线程，响应更快。
    • 调高核心线程数：如果系统资源充足，直接将 corePoolSize 设为 20 或 30，减少任务进入队列排队的概率。

    3. 生产环境的“三件套”优化建议

    A. 必须自定义拒绝策略 (RejectedExecutionHandler)

    默认的 AbortPolicy 会直接抛出异常，这在生产中很危险。

    new ThreadPoolExecutor(..., 
    new ThreadPoolExecutor.CallerRunsPolicy() // 队列满了，让提交任务的线程自己执行，实现“降速”
);
    B. 设置合理的线程回收时间

    配置 A 中 60L 的回收时间对于非核心线程是合理的。但如果你的任务执行极其频繁，可以稍微加长（如 5 分钟），避免线程频繁销毁和创建。

    C. 监控是最好的优化

    不要凭感觉猜。你可以通过以下代码定期打印线程池状态：

    • executor.getQueue().size() (查看队列积压情况)
    • executor.getActiveCount() (查看活跃线程是否触及最大值)
    • executor.getCompletedTaskCount() (查看总吞吐)

    4. 进阶方案：VariableLinkedBlockingQueue

    如果你觉得队列长度定死太僵硬，可以参考某些开源框架（如 Dubbo）的实现，自定义一个可以动态修改容量的队列，这样你就可以在不重启应用的情况下，根据监控数据在线调整队列大小。
