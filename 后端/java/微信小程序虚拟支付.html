微信小程序虚拟支付

微信小程序虚拟支付（xpay / 米大师）

小程序内售卖虚拟商品（虚拟货币、解锁功能、订阅内容、付费功能、打赏、虚拟礼物等），购买和支付必须接入虚拟支付，不能再用普通 JSAPI 支付。

与 是两套完全不同的体系：商户主体、下单方式、签名算法、回调协议、退款接口全部不同。那篇笔记里的「三把钥匙 + 两次签名 + APIv3 回调解密」在这里一个都用不上。

项目背景：PassUp 面试助手（卖面试时长礼包 = 虚拟商品）。改造思路：新增 VirtualPayService（签名 + /xpay/* 服务端接口 + 回调分派），保留 WechatPayService 走双轨，业务层抽象 PaymentChannel，订单 / 快照 / 幂等发放 / 补偿任务全部复用。

一、为什么必须改

在 iOS 上用普通 JSAPI 收虚拟商品的钱属于违规，微信有明确的处罚路径（见错误码 -15017 商家违规收款被限制、-15019 商户受限）。只要业务在 iOS 端合规收款，就必须切虚拟支付。

强制范围包括：虚拟货币、解锁功能、订阅内容、付费功能、打赏、购买虚拟礼物等——面试时长、积分、会员、课程这些都在范围内。

二、JSAPI vs 虚拟支付 对照

环节JSAPI 普通支付虚拟支付

三、开通与配置

1. 开通条件与入口

  • 条件：已认证小程序，主体为企业 / 事业单位 / 个体工商户，主体信息完备。
  • 入口：MP 左侧栏【虚拟支付】→ 提交营业执照、提现账户、支付管理员 → 账户验证 → 扫码签约。审核约 1–7 个工作日，签约后再等 1–2 个工作日。
  • 开通后拿到的是新的二级商户号，与原微信支付商户号是两套资金账户。

2. 基础配置（拿三样东西）

MP → 虚拟支付 → 基础配置：

项说明
appid小程序 AppID
offerId商户号（signData 里必须传字符串，传数字会验签失败）
AppKey沙箱 AppKey 和现网 AppKey 各一套，按 env 取值
发货订阅配置消息推送地址（见第七节）

3. 道具 / 代币配置

MP → 虚拟支付 → 道具管理 / 代币配置：

  • 道具：上传到「开发版本」，测试通过后「发布至现网版本」。名称需符合法规要求，发布后约 10 分钟才生效（未生效下单报 -15014）。
  • 代币：配置代币名称 + 兑换比例，一旦发布不可修改。

4. 选型：道具直购 还是 代币充值

模式mode适用说明
道具直购short_series_goods固定金额买固定权益（面试时长礼包推荐这个）一个礼包 = 一个 productId，goodsPrice（分）做价格校验
代币充值short_series_coin先充成余额，再按次扣减充值后业务侧用 /xpay/currency_pay 扣币
会员订阅见独立文档连续包月安卓/鸿蒙 与 iOS 各有单独文档

判断依据：用户付一次钱拿到「一个确定的东西」用道具直购；用户先把钱充进账户、后续按用量慢慢扣，用代币。 组合方案与业务建模（问答次数 / 语音时长、自定义时长充值、双账本设计、表结构）见 。

四、整体流程

1. 道具直购（推荐）

① 小程序端选择礼包 → POST /api/recharge-orders 创建订单
   ↓
② 后端：校验礼包 → 生成 outTradeNo（8-32 位规则）→ 查 session_key
   ↓
③ 后端：构造 signData（字典序）→ 算 paySig + signature
   ↓
④ 返回 { signData, paySig, signature, mode } 给小程序端
   ↓
⑤ 小程序端 wx.requestVirtualPayment(...)  ← 内部完成下单 + 拉起收银台
   ↓
⑥ 用户支付成功
   ├─ 分支 A：微信 MP 消息推送 xpay_goods_deliver_notify → 后端发货
   └─ 分支 B：后端定时 /xpay/query_order 轮询补单（**必须做**，success 回调可能丢失）
   ↓
⑦ 发货：解析 Attach → 发放资产（幂等）→ 响应 {"ErrCode":0}

2. 代币充值

比道具直购多一步消费：用户先买代币（short_series_coin），业务侧实际消费时调 /xpay/currency_pay 扣减，扣减成功后触发 xpay_coin_pay_notify。

3. 关键差异：下单不在后端

普通支付是「后端下单 → 前端拉起」，虚拟支付是「后端只出签名 → 前端内部完成下单和拉起」。所以后端没有 prepay_id，也无法感知「用户是否已打开收银台」——只能靠推送或轮询确认结果。

五、后端：签名与出参

1. signData 构造（最容易踩坑）

signData 是一个 JSON 字符串，字段必须按 key 字典序排列：

// 顺序：attach < buyQuantity < currencyType < env < goodsPrice < offerId < outTradeNo < productId
String signData = "{"
        + "\"attach\":\""      + jsonEscape(attach)      + "\","
        + "\"buyQuantity\":"   + quantity                + ","
        + "\"currencyType\":\"CNY\","
        + "\"env\":"           + env                     + ","
        + "\"goodsPrice\":"    + goodsPriceFen           + ","
        + "\"offerId\":\""     + offerId                 + "\","   // 字符串！
        + "\"outTradeNo\":\""  + outTradeNo              + "\","
        + "\"productId\":\""   + productId               + "\""
        + "}";
字段必填说明
offerId✅MP 基础配置中的 offerId，字符串类型
buyQuantity✅购买数量
currencyType✅币种，目前只能填 CNY
env❌0 现网（默认）、1 沙箱。现网版本只能填 0（-15011）
productId道具直购必填道具 ID，必须已发布到现网
goodsPrice道具直购必填道具单价（分），用于校验与后台价格一致，不一致报 -15013
activitySellingPrice❌优惠价（分），需与 goodsPrice 一起传，传了即为实际下单价
outTradeNo✅业务订单号，8–32 字符，仅数字/大小写字母/`_-
attach✅透传数据，发货通知时原样回传（放订单号 / 礼包 ID）

⚠️ 逐字节一致原则：微信会按字典序重组 signData 后验签。签名用的字符串和最终传给 wx.requestVirtualPayment 的 signData 必须完全一致，前端绝不能 JSON.parse 后再 stringify（字段顺序/空格变了就报 -15006）。后端直接返回签名用的那个原始字符串最安全。

2. 两个签名

// 支付签名：uri 固定为 "requestVirtualPayment"（基础库调用场景）
String paySig = hmacSha256Hex(appKey, "requestVirtualPayment" + "&" + signData);

// 用户态签名：用 code2Session 拿到的 session_key
String signature = hmacSha256Hex(sessionKey, signData);

HMAC-SHA256 实现：

private static String hmacSha256Hex(String key, String data) {
    try {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(key.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        byte[] raw = mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        StringBuilder sb = new StringBuilder(raw.length * 2);
        for (byte b : raw) {
            sb.append(Character.forDigit((b >> 4) & 0xF, 16))
              .append(Character.forDigit(b & 0xF, 16));
        }
        return sb.toString();   // 小写 hex
    } catch (Exception e) {
        throw new IllegalStateException("HMAC-SHA256 计算失败", e);
    }
}

private static String jsonEscape(String s) {
    if (s == null) return "";
    return s.replace("\\", "\\\\").replace("\"", "\\\"")
            .replace("\n", "\\n").replace("\r", "\\r").replace("\t", "\\t");
}

3. Service 实现

@Service
public class VirtualPayService {

    private final WechatVirtualPayProperties props;   // offerId / appKey / env
    private final SessionKeyStore sessionKeyStore;    // 自己维护的 openid → session_key

    public VirtualPayParams createGoodsOrder(RechargeOrder order, String openId) {
        int env = props.getEnv();                          // 0 现网 / 1 沙箱
        String appKey = env == 0 ? props.getAppKeyProd() : props.getAppKeySandbox();

        // 1. session_key（过期会导致 -15007，需重新 code2Session 刷新）
        String sessionKey = sessionKeyStore.get(openId)
                .orElseThrow(() -> new BusinessException("登录态已失效，请重新进入小程序"));

        // 2. 价格（分），必须与 MP 后台该道具的发布价一致
        int goodsPriceFen = order.getAmount().multiply(BigDecimal.valueOf(100)).intValue();

        // 3. signData（字典序，见上）
        String signData = buildSignData(order, goodsPriceFen, env);

        // 4. 两个签名
        String paySig    = hmacSha256Hex(appKey, "requestVirtualPayment" + "&" + signData);
        String signature = hmacSha256Hex(sessionKey, signData);

        return VirtualPayParams.builder()
                .signData(signData)                    // 原样返回，前端不要二次序列化
                .paySig(paySig)
                .signature(signature)
                .mode("short_series_goods")
                .env(env)
                .build();
    }
}

4. 订单号规则

R + 时间戳 + 4 位随机（沿用 JSAPI 笔记的 generateOrderNo()）需要校验：

// outTradeNo：8-32 字符，[0-9A-Za-z_\-|*@]，且不能以 _ 开头
if (!orderNo.matches("[0-9A-Za-z|*@][0-9A-Za-z_\\-|*@]{7,31}")) {
    throw new IllegalStateException("订单号不符合虚拟支付规则: " + orderNo);
}

outTradeNo 重复使用会报 -15002，且官方说明「极端情况不保证唯一，不建议业务强依赖唯一性」——幂等仍要靠自己的 markAssetGranted。

六、小程序端调用

// 基础库 >= 2.19.2（Android / 鸿蒙 / Windows）
const res = await createVirtualOrder(packageId);   // 后端返回 signData/paySig/signature/mode

  signData: res.signData,      // 字符串，原样传，勿 JSON.parse
  paySig: res.paySig,
  signature: res.signature,
  mode: res.mode,              // 'short_series_goods' | 'short_series_coin'
  success: () => { /* 仅表示收银台流程结束，不代表发货成功 */ },
  fail: ({ errMsg, errCode }) => { /* 见错误码表 */ },

if (compareVersion(SDKVersion, '2.19.2') >= 0 || wx.canIUse('requestVirtualPayment')) {

七、回调：MP 消息推送

1. 事件类型

Event触发时机
xpay_goods_deliver_notify现金购买道具并支付成功（主要处理这个）
xpay_coin_pay_notify代币支付推送，用户代币扣减成功后（报文含 WeChatPayInfo + CoinInfo）
xpay_refund_notify退款完成
xpay_complaint_notify用户发起投诉
xpay_wxpay_callback_notify风控事件（尽职调查 / 管控流水）
xpay_subscribe_ios_refund_query_notifyiOS 退款问询（见第九节）

2. 回调真实性校验（没有 APIv3 那样的验签）

虚拟支付的消息推送走小程序消息推送通道，不存在 APIv3 那套 RSA 请求头验签 + AES-GCM 解密。可用的防护手段：

  1. 校验 ToUserName 等于自己的小程序原始 ID；
  2. 校验 FromUserName——道具发货场景固定为微信官方 openid；
  3. 校验 Env：沙箱（1）的推送不得发放到现网业务库；
  4. 最可靠：收到推送后主动调 /xpay/query_order 反向确认订单真实存在且已支付，再发货。这一步同时兜住了伪造回调与数据不一致。

不要照搬 JSAPI 那篇的 Wechatpay-Signature 头验签逻辑，这里根本没有这些请求头。

4. 响应格式（写错会被重推）

三种都算成功，推荐第一种：

{"ErrCode":0,"ErrMsg":"success"}
<xml><ErrCode>0</ErrCode><ErrMsg><![CDATA[success]]></ErrMsg></xml>

响应格式不对会重推，最多 15 次（间隔 2、4、8、16… 秒）。XML 推送就用 XML 响应，JSON 推送就用 JSON 响应。

5. Controller 实现

@RestController
@RequestMapping("/api/callback/wechat-virtual-pay")
public class VirtualPayCallbackController {

    @PostMapping
    public Map<String, Object> handle(@RequestBody Map<String, Object> msg) {
        String event = (String) msg.get("Event");
        try {
            switch (event) {
                case "xpay_goods_deliver_notify" -> handleDeliver(msg);
                case "xpay_coin_pay_notify"      -> handleCoinPay(msg);
                case "xpay_refund_notify"        -> handleRefund(msg);
                case "xpay_subscribe_ios_refund_query_notify" -> handleIosRefundQuery(msg);
                default -> log.info("忽略的虚拟支付事件: {}", event);
            }
            return Map.of("ErrCode", 0, "ErrMsg", "success");
        } catch (Exception e) {
            log.error("处理虚拟支付回调失败 event={}", event, e);
            return Map.of("ErrCode", 1, "ErrMsg", "处理失败");  // 触发微信重推
        }
    }

    private void handleDeliver(Map<String, Object> msg) {
        if (!Integer.valueOf(0).equals(msg.get("Env"))) {
            log.info("沙箱推送，跳过发货");
            return;
        }
        String outTradeNo = (String) msg.get("OutTradeNo");
        String transactionId = (String) ((Map<?, ?>) msg.get("WeChatPayInfo")).get("TransactionId");

        rechargeOrderService.handlePaymentSuccess(outTradeNo, "WECHAT_VIRTUAL", transactionId);

        try {
            RechargeOrder order = rechargeOrderService.getOrderByOrderNo(outTradeNo);
            rechargeAssetGrantService.grantAssets(order.getId());   // 内部 markAssetGranted 幂等
        } catch (Exception e) {
            log.error("发放资产失败，等待补偿任务", e);
        }
    }
}

正常通过推送返回成功即可不需要再调 /xpay/notify_provide_goods——那个接口是推送处理失败后的补救手段。

6. 幂等与补偿（比 JSAPI 更重要）

官方文档明确：「发货推送分支」与「发货轮询分支」至少实现一个，两者结合使用体验更可靠。原因是 wx.requestVirtualPayment 的 success 回调可能丢失（微信异常退出），推送也可能失败。

所以在 JSAPI 笔记的补偿任务之外，还要加一条主动查单通道：

// 定时扫描「已发起支付但未确认」的订单，主动向微信确认
public void confirmPendingOrders() {
    List<RechargeOrder> orders = rechargeOrderRepository.findUnconfirmedOrders();
    for (RechargeOrder order : orders) {
        VirtualOrderQueryResult r = virtualPayService.queryOrder(order.getOrderNo());
        if (r.isPaid()) {
            rechargeOrderService.handlePaymentSuccess(
                    order.getOrderNo(), "WECHAT_VIRTUAL", r.getTransactionId());
            rechargeAssetGrantService.grantAssets(order.getId());  // 幂等
        } else if (order.isExpired()) {
            rechargeOrderService.markExpired(order.getOrderNo());
        }
    }
}

原有的 markAssetGranted 原子更新 + 补偿任务完全保留，这两条路径共用同一套幂等保护。

八、服务端 API 清单

网关：https://api.weixin.qq.com，接口路径均为 /xpay/*。

签名与鉴权

// uri：不含 query string，如 "/xpay/query_order"
// postBody：本次请求的 POST body（逐字节一致）
String paySig    = hmacSha256Hex(appKey,     uri + "&" + postBody);   // 支付签名
String signature = hmacSha256Hex(sessionKey, postBody);               // 用户态签名

三个凭证都通过 query 参数传递：

POST https://api.weixin.qq.com/xpay/query_order
     ?access_token=ACCESS_TOKEN&signature=SIGNATURE&pay_sig=PAY_SIG
  • access_token 用 stable_token 接口获取并缓存（提前 300 秒刷新），需要在微信侧配置 IP 白名单（否则报 40164）。
  • signature 依赖 session_key，过期会报 268490009，与前端 wx.requestVirtualPayment 的 -15007 同理。
  • 注意：客户端调用时 uri 固定为 requestVirtualPayment，服务端接口则用各自的路径。
  • 具体每个接口的参数以官方服务端 API 文档为准。

常用接口

查订单/xpay/query_orderorder_id（商户单号）或 wx_order_id 二选一；退款也靠它轮询结果

通知已发货/xpay/notify_provide_goods仅现金单；推送已返回成功时不必调

九、iOS 端差异（新增工作量）

wx.requestVirtualPayment 会按设备类型自动路由：

设备对接支付系统
Android / 鸿蒙 / Windows微信支付
iOSApple 支付

1. 门槛

  • 用户：iPhone/iPad + iOS 15+，微信 8.0.68+，最低支付 1 元，仅中国大陆 App Store 账户。
  • 小程序：需先配置小程序简称（Apple 要求展示 display name）。
  • Apple 支付不支持沙箱环境，只能现网测（现网会产生技术服务费，注意成本）。
  • 道具 / 代币是双端互通的，已配置的无需重复配。

2. 开发者不能主动退款

Apple 支付下，用户需到 App Store 自行申请退款。苹果会向开发者发起最多 3 次退款问询，后端需应答 xpay_subscribe_ios_refund_query_notify：

{
  "Event": "xpay_subscribe_ios_refund_query_notify",
  "refund_time": "1756000000",
  "order_time": "1755000000",
  "channel_bill": "Apple 支付票据号",
  "bundleid": "应用的 Apple bundleid",
  "product_id": "道具 id",
  "p_count": "数量",
  "refund_request_reason": "用户请求退款的原因",
  "provide_status": "0 未发货 / 1 已发货 / 2 发货中",
  "pay_order_id": "退款对应支付订单号"
}

应答：

{
  "result_code": 0,          // 0 = 放过，建议退款；1 = 拦截，拒绝退款
  "result_info": "结果描述",
  "evidence": "决策凭据（必填），本次判断的依据，用于退款审计"
}

⚠️ 若连续 3 次、3 秒内均未应答，微信会向 Apple 返回「不确定」，退款决定权完全交给苹果。所以这个接口要同步快速返回，不能走耗时业务。 策略建议：查订单发货状态 → 已消费/已发货用 result_code=1 拦截（附消费凭据），未发货则用 0 放过。

3. 结算与费率

  • 结算：iOS 订单由苹果结算，自然月结束后 45～60 天汇款给腾讯，再划转到你的虚拟支付账户。
  • 费率（iOS 端）：

  • Android 端结算为 T+3，费率参见官方「技术服务费」文档。

application.yml

wechat:

  pay:
    mch-id: your-mch-id
    api-v3-key: your-api-v3-key
    serial-number: your-serial-number
    private-key-path: /secrets/apiclient_key.pem
    public-key-path: /secrets/pub_key.pem
    notify-url: https://your-domain.com/api/callback/wechat-pay
  # 新增：虚拟支付
  virtual-pay:
    app-id: wxXXXXXXXX
    app-secret: your-app-secret        # 用于换取 access_token
    offer-id: "12345678"               # 字符串！
    app-key-sandbox: sandbox-appkey
    app-key-prod: prod-appkey
    env: 0                             # 0 现网 / 1 沙箱，按环境注入
    callback-path: /api/callback/wechat-virtual-pay

密钥用途对比

凭证JSAPI虚拟支付
商户私钥 / 平台公钥 / APIv3 密钥签名 + 验签 + 解密❌ 完全不用
offerId—商户标识，进 signData
AppKey（沙箱/现网两套）—算 paySig、pay_sig
session_key（code2Session）—算 signature（会过期）
access_token（stable_token）—调 /xpay/* 服务端接口

session_key 维护

signature 依赖 session_key，而它会过期（-15007）。需要：

  1. 登录时 code2Session 拿 session_key 存起来（Redis，key 为 openid，过期时间与微信侧对齐）。
  2. 前端遇到 -15007 → 重新 wx.login → 后端刷新 session_key → 前端重试下单。

十三、易错点总结

  1. signData 逐字节一致：字段按字典序、不重排、不重新序列化，否则 -15006。
  2. offerId 必须是字符串，传数字验签失败。
  3. env 与 AppKey 必须配套：env=0 用现网 AppKey，env=1 用沙箱 AppKey。
  4. 后端没有 prepay_id：下单在客户端完成，后端只能靠推送或轮询确认。
  5. 回调响应是 ErrCode/ErrMsg，不是 APIv3 的 code/message。
  6. success 回调会丢失：必须做轮询补单，不能只靠前端回调。
  7. outTradeNo 规则：8–32 位、限定字符集、不能以 _ 开头。
  8. session_key 会过期：-15007 时刷新后重试。
  9. Apple 支付不支持沙箱，现网测试会产生技术服务费。
  10. iOS 退款问询 3 秒内必须应答，否则退款决定权交给苹果。
