怎么用 · 2 分钟

1 一页纸核心

先把这张图刻进脑子。后面所有问题，答到最后都要能回到这张图上——Skill 不是孤立名词，是 Agent 这一层的一个部件。

大语言模型（LLM）　　理解 · 推理 · 生成
        │
        ▼
Agent　　　　　　　　任务理解 → 决策 → 编排
        │
        ├── Rules　　　　　遵守什么（常驻约束）
        ├── Skills　　　　怎么做（按需加载的能力）
        ├── RAG　　　　　　需要什么知识（检索事实）
        ├── Tools　　　　 能做什么（read / write / exec）
        ├── MCP　　　　　 怎么连外部能力（标准协议）
        ├── Subagents　　 谁来做子任务（独立上下文）
        └── Hooks　　　　 什么时候自动执行（事件触发）
                 │
                 ▼
            执行 → 验证 → 交付

三个根本问题（答题时的落点）

Agent 怎么知道做什么？
LLM 推理 + 任务规划 + 上下文。
Agent 怎么知道怎么做？
Rules（约束）+ Skills（方法）+ RAG（事实）。
Agent 怎么真正完成？
Tools + MCP + Subagents + Hooks + 执行环境。

三句话口诀：做什么靠推理，怎么做靠知识与方法，做成靠工具和执行。讲任何概念前先定位它在这张图的哪一层——定位错了，答案一定绕。

六种组件的分工

组件解决什么类比
Rules / AGENTS.md应遵守什么公司制度
Skills某项工作怎么做专业操作手册
Tools能执行什么工具箱
MCP怎么连接外部工具和数据标准化接口
Hooks什么时候自动执行自动化触发器
Subagents谁负责某个子任务专业岗位
Workflows步骤怎么串成流程流水线

Workflows 不一定是独立软件——Agent 提示、Skill、工作流引擎或代码都能承担。它的作用是编排，不是替代上面的能力。

2 六组对比速查

最容易混的就是这几组。记法：先说对方解决什么，再说 Skill 解决什么，最后给一句区分——三句话答完，不展开。

对比对方负责Skill 负责一句话区分
vs RAG知识从哪来：检索文档，给事实依据任务怎么做：给流程和判断标准一个喂事实，一个给动作
vs MCP怎么连接外部工具和数据：标准协议拿到数据后按什么规则办事协议 vs 说明书
vs Tools / FC真正执行操作：read_file、execute_command该调什么、调完怎么验能力 vs 使用说明
vs Rules项目长期通用约束：架构、编码规范特定任务的作业流程，按需加载常驻制度 vs 按需手册
vs Hooks事件触发时自动跑检查，不需 LLM 决策告诉 AI 应该检查什么自动执行 vs 提醒
vs Subagent独立承担子任务，有自己的上下文和权限可被主 Agent 或子 Agent 加载复用谁干 vs 怎么干

最容易答偏的一句：别把 Skill 说成「一种工具」或「一段自动执行的代码」。它是给 Agent 看的指令与资料；真正执行的是 Tools / 运行环境。能带脚本，但脚本靠工具调用。

3 十二道口播题自测

点题目翻面，先看自己的回答够不够 30 秒讲完，再对照要点。答完在题底打分——这是本遍唯一需要动脑的动作。

本遍自评 0 / 12 · 打分只记在本机

30 秒口播

Skill 是可复用的专业能力封装：结构化指令 + 参考资料 + 可选脚本。它让「这件事该怎么做」不靠每次重新交代，而是按需加载。传统提示词是一次性的，Skill 把经验沉淀下来，跨任务复用。

落点回第一张图：它是 Agent 的一个部件，不是模型参数，也不是可执行程序。

本遍自评

30 秒口播

三段。发现：Agent 读 name / description 元数据，判断任务是否匹配。加载：命中后读 SKILL.md 的具体指令。执行：LLM 按指引结合当前任务和工具干活。为省上下文，详细资料放 references、脚本放 scripts，需要时才读或跑。

收尾加一句「具体机制看平台」，别答成某一家的实现细节。

本遍自评

30 秒口播

全塞进去有三个代价：token 按量线性涨；无关规则互相干扰；长上下文中间部分容易被忽略。渐进式加载分三层——元数据 → SKILL.md → references / scripts，只在本任务真正需要时才深入。

关键词是「按需」，目的既是省钱也是降噪——两个字：省、准。

本遍自评

30 秒口播

RAG 解决知识从哪来：检索文档，给事实依据。Skill 解决任务怎么做：给流程和判断标准。两者能组合——Skill 定流程，流程里某一步让 RAG 喂资料，LLM 综合后调工具执行。

一个喂事实，一个给动作。可加例子：Skill 说「事务要检查边界」，RAG 找出项目里事务设计文档。

本遍自评

30 秒口播

Skill 是能力与方法的封装，回答「怎么做」；MCP 是连接 AI 应用与外部工具、数据的开放协议，回答「怎么连、怎么调」。比如退款 Skill 讲业务规则，MCP Server 暴露查订单、查退款记录这些工具。

协议 vs 说明书。补一句：MCP 不是唯一的工具调用方式，宿主原生工具也算。

本遍自评

30 秒口播

Tool 提供具体操作能力：读写文件、执行命令、查数据库。Skill 提供使用这些能力的指引：改完先编译、再跑相关测试、失败要分析原因。LLM 决定调不调，Agent 管理执行过程。

Skill 是说明，Tool 是能力。SKILL.md 自己不会执行，要靠工具跑脚本。

本遍自评

30 秒口播

AGENTS.md 放长期通用约束：架构、编码规范、技术选型，常驻。Skill 放特定任务的知识与流程，按需加载。全堆进去会文件膨胀、上下文冗余、不同任务的规则互相混杂。

通用常驻 + 专业按需，分层管理。别答成「AGENTS.md 不好」——它只是职责不同。

本遍自评

30 秒口播

SKILL.md 本身不会执行，它是指令。带 scripts/ 时，Agent 通过宿主的执行工具去调脚本——真正执行的是工具或运行环境。所以写「我跑过测试」之前，得确认真跑了。

这条对应你自己的规矩：不接受「已改完但没验证」。

本遍自评

30 秒口播

五点：职责明确、场景清晰；description 准确便于发现；步骤具体可操作；复杂资料按需加载不撑爆上下文；带验证与异常处理，能判断任务是否真的完成。

description 写太宽会乱触发，写太窄该用时找不到——这一句最容易被追问。

本遍自评

30 秒口播

先靠清晰的 description 和职责边界减少重叠；一个任务涉及多领域就编排组合——需求分析 → 开发 → 代码审查；执行顺序由 Agent 或显式 workflow 决定。

关键词是「组合」而不是「合并」——不要做一个包罗万象的大 Skill。

本遍自评

30 秒口播

会过期。流程、技术栈、业务规则随代码变化而失效，所以要版本管理、定期审查，尽量引用项目里的权威规范而不是复制。不能替代微调：Skill 在推理期注入指令与知识，不改模型参数；微调改参数、改固有行为。

工作流程和项目规范优先用 Skill；要改模型固有行为才考虑微调。

本遍自评

30 秒口播

不能只看文档写得全不全，要看实际任务效果。用同一组测试任务对比使用前后：需求遗漏率、缺陷数、测试通过情况、返工次数、耗时、规则遵循度。建固定评测集持续回归。

跟你做 RAG 一个思路——没有数字，所有优化都是猜。

4 综合架构题

「如果让你设计一套企业级 AI Coding 系统，你会怎么设计？」——先自己画一遍，再展开对照。这题把前面 12 题串成一张图。

展开参考答案（先别点，画完再说） 
用户需求
   │
   ▼
Agent / LLM　　理解需求 · 推理决策 · 任务编排
   │
   ├── Skills　　　 专业知识与执行方法
   ├── Rules　　　　长期规则与约束
   ├── Tools / MCP　外部操作能力
   ├── Subagents　　专业任务分工
   └── 执行与验证　 Hooks · 测试 · CI/CD · 代码审查
   │
   ▼
交付结果

强调各司其职：Agent 是任务组织者与决策者，LLM 提供推理；Skill 给专业知识与方法；Tool / MCP 提供实际操作；Subagent 做任务分工；Hooks / CI 提供自动化质量保障。

别把 Skill 说成系统的核心——它是被 Agent 调用的一层能力。这句话最能暴露有没有真懂。

5 每遍怎么过

场合动作
第一遍看完核心图和对比表，再逐题自测，允许翻面。目的是搭骨架。
第二遍起只自测，不回看核心图。卡壳的题打 1，说清了打 2，能扛追问打 3。
每周日把打 1 / 2 的题挑出来重过；连对三次的题才敢算「会了」。
阶段验收后想长期留的整理进 cqlql-notes/docs/ai/；本手册和卡片是练习态，不进笔记站。

边界要说清：这里的打分只做本机自评，不排复习日期；真正按 1 / 2 / 3 排「明天 / 3 天后 / 7 天后」的是抽题系统 dist/index.html。另外别把学习手册直接塞进笔记站——notes-rag 拿笔记站当语料，练习材料混进去会让评估集 recall 虚高。
