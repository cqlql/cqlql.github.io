AI Agent Skills 学习与面试指南

原文完整版 · 8 章阅读讲义复习抽题用 导航页 里的《AI Agent Skills 复习手册》。

这份指南的目标不是简单罗列 Skill 的概念和工具名称，而是建立三层能力：

  1. 理解原理：知道 Skill 是什么、为什么需要、如何工作。
  2. 掌握应用：知道如何编写 Skill，如何与 Agent、MCP、RAG、Hooks 等配合。
  3. 应对面试：能够解释底层机制、设计方案、结合实际项目回答问题。

建议学习方式：先理解概念，再看执行过程，最后自己动手实现。

学习路线

  1. Skill 基础概念
  2. Skill 的发现、加载与执行机制
  3. Skill 与其他 Agent 技术的区别
  4. Skills、MCP、Hooks、Subagents 协作
  5. 实际开发：自己编写 Skill
  6. AI Coding 工作流与工程实践
  7. 面试题与项目实战

第一章：为什么需要 Skill？

1.1 先理解一个问题

假设你让 AI 开发一个 Spring Boot 接口：

帮我新增一个用户充值接口。

普通 AI 可能会：

  1. 阅读相关代码。
  2. 编写 Controller。
  3. 编写 Service。
  4. 编写 Repository。
  5. 编写 SQL。
  6. 完成接口。

看起来没问题，但实际可能出现：

  • 不遵循项目现有架构。
  • 不知道项目的异常处理规范。
  • 不知道数据库 Migration 的命名规则。
  • 没有考虑幂等性。
  • 测试只覆盖正常情况。
  • 不了解项目已有的资产账户设计，重复实现。

问题在哪里？

AI 具备通用编程能力，但不一定具备当前项目的专业知识和操作经验。

即使你把所有要求写进 AGENTS.md，也有问题：

  • 文件越来越长。
  • 每次任务都需要携带大量无关规则。
  • 不同任务需要的知识不同。
  • 某些操作需要详细步骤，而不是简单的规则。

这就引出了 Skill。

1.2 Skill 是什么？

Skill 可以理解为：

给 AI Agent 使用的、可复用的专业能力说明书。

它通常包含：

  • 适用场景。
  • 任务执行步骤。
  • 专业知识。
  • 操作规范。
  • 示例。
  • 相关脚本或参考资料。

例如，一个 Spring Boot 开发 Skill：

springboot-feature/
├── SKILL.md
├── references/
│   ├── architecture.md
│   ├── database.md
│   └── exception-handling.md
└── scripts/
    └── check-migration.sh

其中：

  • SKILL.md：告诉 AI 什么时候使用、具体怎么做。
  • references/：提供需要时再阅读的专业资料。
  • scripts/：提供可以实际执行的辅助工具。

注意：Skill 不等于可执行程序。它的核心通常是结构化指令和资料，也可以附带脚本。

1.3 Skill 解决了什么问题？

问题Skill 的作用
AI 不知道什么时候应该采用某种方法提供触发描述
AI 不知道具体执行步骤提供工作流程
AI 缺乏项目专业知识提供参考资料
每次都要重复告诉 AI 怎么做实现能力复用
项目规则过于庞大按任务加载相关知识

关键理解：Skill 不是让模型变得更聪明，而是让模型在特定任务中能够使用更合适的知识和方法。

1.4 Skill 的核心价值：把经验变成可复用能力

可以把它理解成传统软件开发中的设计模式、开发规范和操作手册的结合，但它是为 Agent 执行任务而组织的。

例如：

你已经掌握了 PassUp 的充值业务规则：

  • 充值订单有不同类型。
  • 资产采用批次管理。
  • 资产扣减遵循 FIFO。
  • 支付成功后才能发放资产。
  • 支付通知必须幂等。

这些知识不应该每次都靠你重新告诉 AI。

可以把它们整理成充值业务 Skill。

下次 AI 处理充值相关需求时，就可以先发现并加载这个 Skill。

思考题： 为什么不直接把所有知识都写进 AGENTS.md？

参考答案

因为不同任务需要的知识不同。Skill 可以按需发现和加载，减少无关上下文，同时让专业流程具备复用性。

第二章：Skill 是如何工作的？

这是面试中非常值得深入的问题。

2.1 Skill 并不是模型自身的能力

首先区分两个概念：

  • 大语言模型：负责理解、推理、生成内容。
  • Skill：为 Agent 提供额外的专业指令和知识。

例如，模型本身知道 Java 怎么写，但不一定知道你的项目采用什么异常处理方式。

加载 Skill 后，Agent 就能获得这些额外信息。

可以用这个模型理解：

用户提出需求        新增 Spring Boot 充值接口
      ↓
Agent 分析任务      判断需要哪些专业能力
      ↓
发现并加载 Skill    读取 Skill 描述、执行指引和必要参考资料
      ↓
LLM 根据上下文推理  结合需求、项目代码、Skill 指令制定实现方案
      ↓
执行开发任务        必要时调用工具、运行脚本、执行测试

注意：这是概念模型，不是所有 Agent 产品完全一致的内部实现。不同平台的 Skill 发现、加载和触发机制可能不同。

2.2 Skill 如何被发现？

一个典型的 Skill 会有一个 SKILL.md 文件。

例如：

skills/
├── springboot-feature/
│   └── SKILL.md
├── database-migration/
│   └── SKILL.md
└── code-review/
    └── SKILL.md

Skill 通常通过元数据告诉 Agent 自己叫什么、适合做什么。

示例：

---
name: springboot-feature
description: >
  用于 Spring Boot 业务功能开发。
  当需要新增或修改 Controller、
  Service、Repository、数据库业务逻辑时使用。
---

这里最重要的是 description。

它不仅是介绍，还可能参与 Agent 的 Skill 匹配和选择。

如果描述写得太宽泛，可能导致：

  • 不该使用时也被触发。
  • 应该使用时却没有被发现。
  • 多个 Skill 之间发生选择冲突。

所以 Skill 的适用范围应该清晰。

2.3 什么是渐进式加载（Progressive Disclosure）？

这是 Skill 设计中一个很重要的思想。

假设你有一个非常庞大的 Java 开发 Skill，里面有：

  • 数据库设计规范。
  • Spring Security 使用方法。
  • Redis 缓存策略。
  • WebSocket 开发规范。
  • 单元测试方法。
  • 异常处理规则。

如果每次开发一个简单接口，都把这些内容全部交给模型，会浪费上下文。

渐进式加载可以理解成三层：

第一层 · 发现阶段：元数据

Agent 先知道有哪些 Skill，以及每个 Skill 的用途。

主要依赖名称和描述，成本较低。

第二层 · 加载阶段：SKILL.md

选中 Skill 后，读取具体工作流程和执行指引。

第三层 · 深入阶段：References / Scripts

需要数据库规范时才阅读数据库资料，需要自动检查时才运行对应脚本。

例如：

用户：增加一个充值接口
       ↓
发现 springboot-feature
       ↓
读取 SKILL.md
       ↓
发现涉及数据库变更
       ↓
进一步读取 database.md
       ↓
执行 migration 检查脚本

这样可以避免每次把所有知识塞进上下文。

面试重点：Skill 不等于一次性把整个目录加载到模型中。合理设计应尽量按需加载。

2.4 Skill 是如何执行的？

这里需要特别注意一个误区：

Skill 本身通常不是 Agent，也不是一个独立运行的程序。

例如 Skill 里写着：

## 开发步骤

1. 阅读相关业务模块。
2. 确认现有数据结构。
3. 设计接口。
4. 实现 Service。
5. 编写单元测试。
6. 执行测试。

它只是给 Agent 提供执行指引。

真正的执行者仍然是 Agent：

  • LLM 负责理解和决策。
  • Skill 提供知识和操作流程。
  • Tools 提供实际执行能力。
  • Agent 负责组织这些步骤。

例如，AI 要执行测试，就需要有终端工具；Skill 只是告诉它应该执行什么测试、如何判断结果。

第三章：Skill 与其他技术有什么区别？

这部分是面试高频考察方向，也是最容易混淆的地方。

3.1 Skill vs RAG

两者都可能向模型提供额外知识，但解决的问题不同。

对比SkillRAG
核心目标提供专业工作方法检索外部知识
主要内容指令、流程、示例文档、数据、知识
触发方式根据任务选择能力根据问题检索相关内容
典型场景如何开发退款功能退款业务历史资料是什么
输出价值指导 Agent 怎么做为回答提供事实依据

举个例子：

你有 100 份 Java 开发文档。

RAG 可以根据问题检索出与 Spring 事务相关的资料。

Skill 则可以告诉 Agent：

当开发涉及事务的业务时：

1. 检查事务边界。
2. 确认异常回滚规则。
3. 检查是否存在自调用导致事务失效。
4. 检查外部调用是否处于事务内。
5. 编写事务相关测试。

两者可以组合：

Skill：告诉 Agent 如何处理事务
             ↓
RAG：检索项目事务设计资料
             ↓
LLM：结合资料制定实现方案
             ↓
Tools：修改代码并执行测试

一句话：RAG 主要解决知识从哪里来，Skill 主要解决任务应该怎么做。

3.2 Skill vs MCP

这是另一个特别容易被问到的问题。

MCP（Model Context Protocol）是一种连接 AI 应用与外部工具、数据源的开放协议。

例如：

你需要让 AI 查询 PostgreSQL。

没有 MCP 时，可能需要针对数据库编写专门的工具接口。

使用 MCP，可以通过标准化协议暴露数据库工具，让支持 MCP 的客户端发现和调用它们。

例如：

AI Agent
   ↓
MCP Client
   ↓
MCP Server
   ↓
PostgreSQL

Skill 和 MCP 的区别：

对比SkillMCP
本质专业指令与知识通信协议
解决问题怎么做如何连接和调用
是否负责执行通常提供执行指引提供工具调用能力
典型内容开发流程、检查规范数据库查询、API 调用
是否互补是是

举个实际例子：

你要让 AI 开发一个充值退款功能。

  • Skill：告诉 AI 退款业务应该遵循哪些规则。
  • MCP：让 AI 查询数据库、读取 Issue 或调用外部系统。
  • LLM：理解需求并决定下一步操作。
  • Agent：组织整个执行流程。

注意：MCP 不是唯一的工具调用方式。Agent 也可以直接使用宿主提供的原生工具。

3.3 Skill vs Tools / Function Calling

Tools 是 Agent 实际使用的工具。

例如：

read_file()
write_file()
execute_command()
run_test()
query_database()

它们提供具体的操作能力。

Skill 可以告诉 Agent：

修改代码后：

1. 执行编译。
2. 执行相关单元测试。
3. 检查测试结果。
4. 如果失败，分析原因并修复。

而 Tools 负责真正执行：

execute_command("./mvnw test")

区别：

  • Skill 是操作说明。
  • Tool 是操作能力。
  • LLM 决定是否调用。
  • Agent 管理执行过程。

3.4 Skill vs AGENTS.md / Rules

对比AGENTS.md / RulesSkill
主要用途项目通用约束特定任务的专业能力
作用范围项目或目录范围特定任务场景
内容项目架构、编码约定执行步骤、专业方法
加载特点依平台机制加载通常按需发现和加载

例如：

AGENTS.md：

- 使用实用主义 DDD。
- 业务模块放在 modules。
- 基础设施实现放在 infrastructure。
- 数据库使用 PostgreSQL。
- 数据库变更必须使用 Flyway。

database-migration/SKILL.md：

当需要修改数据库时：

1. 检查现有表结构。
2. 检查历史 Migration。
3. 创建新的版本迁移文件。
4. 避免修改已经执行的历史 Migration。
5. 检查索引和约束。
6. 执行 Migration 验证。

项目规则是长期约束，Skill 是按场景调用的操作能力。

3.5 Skill vs Hooks

Hooks 是事件触发机制。

例如：

AI 修改文件
    ↓
触发 Hook
    ↓
执行代码格式检查
    ↓
返回检查结果

Skill 更像告诉 AI 应该检查什么。

Hook 则可以在指定事件发生时自动执行检查。

两者的区别：

  • Skill：指导 AI。
  • Hook：自动触发程序。
  • Hook 的执行不一定需要 LLM 决策。

这点很重要：不能只依赖 Skill 提醒 AI 遵守规范，关键质量约束应尽可能自动化。

3.6 Skill vs Subagent

Subagent 是独立承担特定子任务的 Agent。

例如：

主 Agent
   │
   ├── 架构分析 Subagent
   │
   ├── 开发 Subagent
   │
   └── 代码审查 Subagent

每个 Subagent 可以有自己的指令、上下文、工具权限，具体取决于平台。

Skill 则可以被主 Agent 或子 Agent 使用。

举例：

  • 架构分析 Subagent 加载架构分析 Skill。
  • 开发 Subagent 加载 Spring Boot 开发 Skill。
  • Review Subagent 加载代码审查 Skill。

所以两者并不冲突。

第四章：如何设计一个好的 Skill？

理解概念之后，需要掌握实际编写能力。

4.1 Skill 的目录结构

一个比较完整的 Skill 可以这样组织：

springboot-feature/
├── SKILL.md
├── references/
│   ├── architecture.md
│   ├── database-conventions.md
│   └── testing-guide.md
├── scripts/
│   ├── check-migration.sh
│   └── verify-tests.sh
└── assets/
    └── example-template.java

各目录的职责：

文件职责
SKILL.md技能说明、适用范围、执行步骤
references专业知识、参考资料
scripts可执行的辅助脚本
assets模板、示例等资源

不是每个 Skill 都需要这些目录。简单 Skill 只有一个 SKILL.md 就足够。

4.2 SKILL.md 应该怎么写？

下面是一个实际示例：

示例：Spring Boot 业务功能开发 Skill

---
name: springboot-feature
description: >
  用于 Spring Boot 项目的业务功能开发。
  当需要新增或修改业务接口、Service、
  Repository 或业务流程时使用。
---

# Spring Boot 业务功能开发

## 目标

在遵循现有项目架构的前提下，
完成业务功能开发和验证。

## 执行流程

### 1. 现状调查

- 阅读 AGENTS.md。
- 检查相关业务模块。
- 理解现有调用链。
- 检查相关数据库表结构。
- 优先复用现有实现。

### 2. 方案设计

- 明确业务流程。
- 确定需要修改的模块。
- 确认接口和数据结构。
- 分析异常和边界情况。
- 评估对现有功能的影响。

### 3. 功能实现

- 遵循项目现有分层。
- 避免重复实现。
- 避免不必要的抽象。
- 控制单次修改范围。

### 4. 测试验证

- 执行编译。
- 编写或更新单元测试。
- 覆盖正常、异常和边界场景。
- 执行相关测试。

### 5. 完成检查

- 对照需求检查完整性。
- 检查代码变更范围。
- 检查文档是否需要更新。
- 报告实际验证结果。

## 注意事项

- 不要在不了解现有架构时直接新增模块。
- 不要为了遵循某种模式而过度设计。
- 不要声称执行过未实际运行的测试。
- 遇到需求不明确的情况，先澄清。

这个示例最值得学习的不是内容本身，而是组织方式：

  1. 用 description 告诉 Agent 什么时候使用。
  2. 用 目标 说明希望达到什么结果。
  3. 用 执行流程 告诉 Agent 如何完成任务。
  4. 用 注意事项 约束容易出错的行为。

4.3 Skill 应该拆多细？

这是实际设计时经常遇到的问题。

例如，有两种方案。

方案 A：一个大 Skill。

java-development/
└── SKILL.md

包含：

  • Java 编码。
  • Spring Boot。
  • 数据库。
  • Redis。
  • 安全。
  • 测试。
  • 性能优化。

方案 B：多个专业 Skill。

skills/
├── springboot-feature/
├── database-migration/
├── redis-development/
├── security-review/
├── performance-analysis/
└── code-review/

我更推荐方案 B，但不要拆得过细。

判断标准：

  • 是否有独立的适用场景？
  • 是否有相对独立的执行流程？
  • 是否会被多个项目或任务复用？
  • 是否需要单独维护和迭代？

如果答案基本都是肯定的，可以考虑独立 Skill。

例如，数据库 Migration 和性能分析虽然都涉及数据库，但执行目标和验证方法完全不同，拆开比较合理。

4.4 Skill 设计最容易犯的错误

错误改进方式
description 过于宽泛明确触发条件
一个 Skill 包含所有知识按职责拆分
SKILL.md 过长将详细资料放入 references
只有原则没有操作步骤增加可执行流程
只有操作步骤没有验证增加结果检查
假设 AI 一定会遵守关键约束配合自动化工具
不考虑平台差异检查目标 Agent 的 Skill 规范

第五章：Skill 生态与辅助开发工具

Skill 只是整个 AI Coding 工具体系的一部分。

5.1 六种重要组件

组件解决的问题类比
Rules / AGENTS.md应遵守什么公司制度
Skills某项工作怎么做专业操作手册
Tools能够执行什么工具箱
MCP如何连接外部工具和数据标准化连接协议
Hooks什么时候自动执行自动化触发器
Subagents谁负责某个子任务专业岗位

另外还有 Workflows：

Workflows 负责把多个步骤组织起来，形成一套完整任务流程。

例如：

开发一个业务功能
      │
      ▼
需求分析
      │
      ▼
加载需求分析 Skill
      │
      ▼
调用代码搜索 Tool
      │
      ▼
加载开发 Skill
      │
      ▼
执行代码修改
      │
      ▼
Hook 自动检查
      │
      ▼
调用测试 Subagent
      │
      ▼
完成验收

这里的 Workflows 可以由 Agent 的提示指令、Skill、专用工作流引擎或程序代码实现，并不一定需要独立的软件。

5.2 三个值得研究的开源项目

Superpowers（优先学习）· obra/superpowers

学习重点：

  • Brainstorming
  • Writing Plans
  • Test-Driven Development
  • Subagent-Driven Development
  • Code Review

价值：学习如何把软件工程方法封装成 Skill。

OpenSpec · Fission-AI/OpenSpec

学习重点：

  • Proposal
  • Design
  • Tasks
  • Apply
  • Archive

价值：学习如何让 AI 管理已有项目中的需求变更。

GitHub Spec Kit · github/spec-kit

学习重点：

  • Specify
  • Plan
  • Tasks
  • Analyze
  • Implement

价值：学习完整的规格驱动开发方法。

5.3 它们之间应该如何选择？

你的目标优先研究
学会编写和使用 SkillsSuperpowers
管理中大型需求变更OpenSpec
建立完整规格驱动开发流程Spec Kit
自动执行代码检查Hooks + CI
分工完成复杂任务Subagents

不要同时把 Superpowers、OpenSpec、Spec Kit 全部设置成强制流程。

它们解决的问题有重叠，尤其是规划、任务拆分和实施管理。

5.4 其他值得认识的概念

  • LSP（Language Server Protocol）：提供代码定义跳转、引用查找、诊断等语义能力，帮助 Agent 更准确地理解代码。
  • MCP Server：向 MCP Client 暴露工具和资源的服务端。
  • CI/CD：自动构建、测试、检查和部署。
  • Git Worktree：让多个开发任务在不同工作目录中并行推进。
  • TDD：先写测试，再实现功能，通过测试结果指导开发。

这些技术不都是 Skill，但可以与 Skill 组合，形成更完整的 Agent 开发体系。

第六章：实际动手——自己设计一套开发 Skill

我建议使用你的 PassUp 项目作为学习案例。

不要一开始就设计几十个 Skill，先做三个。

6.1 第一个：需求分析 Skill

目标：让 AI 接到需求后，先理解问题，而不是立即修改代码。

执行步骤：

  1. 明确业务目标。
  2. 梳理用户场景。
  3. 确定验收条件。
  4. 找出边界条件。
  5. 判断任务复杂度。
  6. 输出需求分析结果。

验收：给 AI 一个模糊的业务需求，观察它是否能发现缺失信息和潜在风险。

6.2 第二个：Spring Boot 开发 Skill

目标：让 AI 按照项目现有架构开发。

执行步骤：

  1. 阅读项目规则。
  2. 调查相关模块。
  3. 分析现有实现。
  4. 设计修改方案。
  5. 分步实现。
  6. 执行测试。

验收：让 AI 新增一个简单业务接口，检查它是否遵循项目约定。

6.3 第三个：代码审查 Skill

目标：让 AI 从独立审查者的角度检查代码。

重点检查：

  • 业务逻辑错误。
  • 并发安全。
  • 事务边界。
  • 数据一致性。
  • N+1 查询。
  • 不必要的 SELECT *。
  • 异常处理。
  • 测试覆盖。
  • 架构依赖。
  • 安全风险。

注意：不要简单地把所有问题列为违规。比如 N+1 和 SELECT * 并非在所有场景都错误，应该结合实际 SQL、数据规模和性能测量判断。

6.4 实战：充值退款功能

可以将这三个 Skill 组合起来：

需求：实现充值退款
       │
       ▼
需求分析 Skill
       │
       ├── 明确退款规则
       ├── 确定订单状态
       ├── 确定资产回退规则
       └── 形成验收条件
       │
       ▼
Spring Boot 开发 Skill
       │
       ├── 调查现有代码
       ├── 设计技术方案
       ├── 编写 Migration
       ├── 实现业务逻辑
       └── 编写测试
       │
       ▼
代码审查 Skill
       │
       ├── 检查幂等性
       ├── 检查并发安全
       ├── 检查事务边界
       └── 检查测试有效性
       │
       ▼
自动化验证
       │
       ▼
完成

这里可以进一步让代码审查 Skill 使用独立 Subagent 执行，减少开发者自我审查带来的盲区。

第七章：面试必备知识点

这一章建议反复阅读，直到能够脱离文档，自己讲清楚。

7.1 高频面试题

Q1：什么是 Agent Skill？为什么需要 Skill？

参考回答：

Skill 是一种可复用的专业能力封装，通常由结构化指令、参考资料和可选脚本组成。

它可以让 Agent 在执行特定任务时，按预先定义的方法和规范工作。

传统提示词通常针对单次任务，而 Skill 可以沉淀专业经验，并在不同任务中重复使用。

例如，在 Spring Boot 项目中，可以把数据库 Migration、接口开发、代码审查等流程封装成不同 Skill。

Q2：Skill 是如何被 Agent 发现和加载的？

参考回答：

通常分为三个阶段：

  1. 发现：Agent 通过 Skill 的名称、描述等元数据了解可用技能。
  2. 加载：判断任务匹配后，读取 Skill 的具体指令。
  3. 执行：LLM 根据 Skill 提供的指引，结合当前任务和可用工具完成工作。

为了减少上下文开销，通常采用渐进式加载，需要详细资料时再读取 references 或运行脚本。

具体机制取决于 Agent 平台。

Q3：Skill 和 RAG 有什么区别？

参考回答：

RAG 主要解决知识检索问题，通过检索相关文档，将知识提供给模型。

Skill 主要解决任务执行方法问题，告诉 Agent 在特定场景下应该如何完成任务。

两者可以结合：Skill 指导执行流程，RAG 提供所需的专业知识。

Q4：Skill 和 MCP 有什么区别？

参考回答：

Skill 是专业指令和工作方法的封装，MCP 是连接 AI 应用与外部工具、数据源的开放协议。

例如，退款 Skill 告诉 Agent 退款应该遵循哪些业务规则；MCP Server 可以向 Agent 提供查询订单、查询退款记录等工具。

两者解决不同问题，可以配合使用。

Q5：Skill 和 Tool 有什么区别？

参考回答：

Tool 提供具体操作能力，例如读取文件、执行命令、查询数据库。

Skill 提供使用这些能力的专业指引。

Skill 告诉 Agent 应该做什么、如何做，Tool 负责真正执行操作。

Q6：为什么不直接把所有规则写进 AGENTS.md？

参考回答：

AGENTS.md 更适合存放项目长期通用的约束，例如架构、编码规范、技术选型。

Skill 更适合存放特定任务的专业知识和执行流程。

如果所有内容都放在 AGENTS.md，容易导致文件膨胀、上下文冗余，以及不同任务之间的规则混杂。

所以通常采用通用规则与按需加载的 Skill 相结合。

Q7：Skill 能否自动执行代码？

参考回答：

Skill 本身通常不是独立执行程序，而是为 Agent 提供指令和资源。

如果 Skill 附带脚本，Agent 可以通过宿主提供的执行工具调用脚本。

真正执行代码的是工具或运行环境，而不是 SKILL.md 本身。

Q8：如何设计一个好的 Skill？

参考回答：

主要考虑五个方面：

  1. 职责明确，适用场景清晰。
  2. 描述准确，便于 Agent 发现。
  3. 执行步骤具体，具有可操作性。
  4. 复杂资料按需加载，避免上下文膨胀。
  5. 包含验证和异常处理，能够判断任务是否完成。

Q9：多个 Skill 同时适用怎么办？

参考回答：

应该尽量明确每个 Skill 的职责和触发条件。

如果一个任务涉及多个领域，可以组合多个 Skill，例如先使用需求分析 Skill，再使用开发 Skill，最后使用代码审查 Skill。

具体选择由 Agent 根据任务和平台机制决定，必要时也可以通过工作流明确执行顺序。

Q10：Skill 会不会存在过期问题？

参考回答：

会。

Skill 中的流程、技术知识和项目约束可能随着代码架构、技术栈和业务规则变化而过期。

因此需要版本管理、定期审查，并结合实际执行结果持续改进。

特别是项目相关 Skill，应尽量引用项目中的权威规范，而不是复制大量可能过期的内容。

Q11：Skill 能否替代 Fine-tuning？

参考回答：

不能。

Skill 是在推理阶段向 Agent 提供额外的指令和知识，不改变模型自身的参数。

Fine-tuning 则通过训练调整模型参数，使模型在特定任务上形成更稳定的行为模式。

一般而言，工作流程和项目规范优先考虑 Skill；需要改变模型固有行为或提升特定任务能力时，再考虑 Fine-tuning。

Q12：如何判断一个 Skill 是否有效？

参考回答：

不能只看 Skill 写得是否完整，而要看实际任务效果。

可以设计一组相同的测试任务，对比使用 Skill 前后的：

  • 需求遗漏率。
  • 代码缺陷数量。
  • 测试通过情况。
  • 返工次数。
  • 完成时间。
  • 规则遵循情况。

还可以建立固定评测集，持续验证 Skill 修改后的效果。

7.3 面试时最重要的一个综合题

问题：如果让你设计一套企业级 AI Coding 系统，你会怎么设计？

可以这样回答：

整体架构

用户需求
   │
   ▼
Agent / LLM          理解需求、推理决策、任务编排
   │
   ├── Skills        专业知识和执行方法
   ├── Rules         长期规则和约束
   ├── Tools / MCP   外部操作能力
   └── Subagents     专业任务分工
   │
   ▼
执行与验证           Hooks、测试、CI/CD、代码审查
   │
   ▼
交付结果

回答时强调：

  • Agent 是任务的组织者和决策者。
  • LLM 提供推理能力。
  • Skill 提供专业知识和工作方法。
  • Tool/MCP 提供实际操作能力。
  • Subagent 提供任务分工。
  • Hooks/CI 提供自动化质量保障。

这就是一个比较完整的 AI Coding 系统设计思路。

8.2 最终自测：你是否真正理解了 Skill？

下面这些问题，如果不看资料也能讲清楚，就说明已经掌握了核心内容。

1. Skill 本质上是什么？

参考答案

为 Agent 提供可复用的专业指令、知识和执行方法。它不是模型参数，也不一定是可执行程序。

2. Skill 如何被发现和加载？

参考答案

通常通过名称、描述等元数据发现，匹配后加载具体指令，需要时再读取参考资料或运行脚本。具体依赖平台。

3. 为什么要渐进式加载？

参考答案

降低无关上下文和 Token 开销，让 Agent 只获取当前任务需要的知识。

4. Skill 和 RAG 的核心区别？

参考答案

RAG 侧重检索知识，Skill 侧重指导任务执行方法，两者可以结合。

5. Skill 和 MCP 的核心区别？

参考答案

Skill 是专业能力说明和流程，MCP 是连接外部工具和数据的协议。

6. Skill 和 Tool 的关系？

参考答案

Skill 指导如何使用工具，Tool 提供实际操作能力。

7. 什么时候使用 Subagent？

参考答案

复杂任务需要独立职责、上下文隔离或并行执行时。

8. 如何保证 Skill 真正有效？

参考答案

建立实际任务评测集，对比使用前后的质量、耗时、缺陷和返工情况。

9. 为什么不能所有规则都写入 AGENTS.md？

参考答案

通用约束与专业任务流程不同，分层管理可以减少上下文冗余和规则混乱。

10. 如何设计企业级 AI Coding 系统？

参考答案

以 Agent 为编排中心，组合 Rules、Skills、Tools/MCP、Subagents，并通过 Hooks、测试和 CI 保证质量。

大语言模型（LLM）

       │

我认为面试时最重要的是能够讲清楚三个问题：

  1. Agent 如何知道自己应该做什么？ —— LLM 推理、任务规划、上下文。

  3. Agent 如何真正完成任务？ —— Tools、MCP、Subagents、Hooks 和执行环境。

当你能够把这三个问题讲清楚，就不再只是记住了 Skill 的定义，而是真正理解了 Agent 的工作体系。
