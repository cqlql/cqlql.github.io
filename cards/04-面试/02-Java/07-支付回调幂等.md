# 支付回调重复通知怎么办

## 30 秒版

微信回调会重试，必须幂等。做法是条件更新抢占：`UPDATE ... WHERE status = '待处理'`，影响行数为 0 说明已经被处理过，直接返回成功。加分点是用唯一索引兜底，以及用状态机而不是布尔标记。

## 展开

- 为什么用条件更新而不是先查再改：查和改之间有时间窗，两条并发请求会同时查到「待处理」
- 为什么用状态机而不是布尔：布尔只能表达「处理过没有」，无法表达「处理到哪一步」，退款这类多段流程必须能表达中间态
- 唯一索引兜底：同一笔业务号的记录只允许一条，写不进去就说明重复

## 我的数字

- 条件更新是主路径，唯一索引是兜底
- 677 个单测里专门覆盖了「重复回调」这一组

## 追问预演

- **Q**：两条请求同时到会怎样？
  **A**：数据库行锁保证只有一个 `WHERE status='待处理'` 能命中，另一条影响行数为 0，当作已处理返回成功。
- **Q**：返回成功但实际没处理完怎么办？
  **A**：状态已经落了，后续由补偿任务推进。回调只负责把事实记下来，不负责把所有事做完。
