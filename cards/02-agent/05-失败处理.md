# 工具报错、重复调用、死循环怎么防

## 30 秒版

> 关键词桩，不是成稿。合上卡，用这几根桩自己连成 5 句话。

- 三类故障：工具报错、空结果反复调、跑飞（死循环 / 发散）
- 报错回「发生了什么 + 可能原因 + 建议怎么办」，别回堆栈
- 防护分四层：最大轮次、总超时、重试上限、成本上限
- 到上限不抛错，降级给「部分答案 + 缺什么」

## 展开

**报错分三类，处理方式不同**

| 类型 | 例子 | 处理 |
|---|---|---|
| 可重试 | 超时、429、网络抖动 | 退避重试 2~3 次，仍失败再回给模型 |
| 不可重试 | 参数错、权限不足、404 | 直接包装回给模型，让它改参数 |
| 致命 | 下游服务挂了 | 终止，告知用户「暂时不可用」，别让模型瞎编 |

**错误信息的写法对比**

```
差： Traceback (most recent call last): ... KeyError: 'start_date'
好： {"ok": false, "error_type": "missing_param",
     "message": "缺少必填参数 start_date",
     "suggestion": "请提供日期范围，格式 YYYY-MM-DD，例如 start_date=2026-03-01"}
```

模型看不懂堆栈，但看得懂「缺什么、怎么补」。原始异常同时写进日志给自己排查——**给模型的和给自己的，是两份不同的东西**。

**重复调用的三层防护**

1. 上下文层：空结果显式标注「已查询，该条件无记录，不要重复查询」
2. 代码层：幂等缓存 + 调用计数，同一 `(tool, args)` 超过 N 次直接返回「已尝试 N 次，请换方法」
3. 提示层：system 里写明「不要用相同参数重复调用」

**跑飞的两种表现**

- 无限循环：一直调同一个工具，或 A→B→A→B 打转
- 任务发散：越调越偏，用户问面试记录，它去查题库又去查简历

检测方法：算当前 Action 和原始 user query 的相关性，偏离到一定程度就拉回；或者统计「连续 N 轮没有产生新信息」。

**四层硬约束**：最大轮次（硬）→ 总超时（硬）→ 单工具重试上限 → 单任务成本上限。**这些必须是代码里的硬约束，不能写进 prompt 指望模型遵守**。

**兜底策略**：到上限时组装「已知信息 + 缺什么 + 建议用户怎么做」，而不是 500。用户能接受「我查到了 A 但没查到 B，你能补充 C 吗」，不能接受「系统错误」。

## 追问预演

- **Q**：工具抛异常，你原样回给模型还是包装一下？举个实际写法。
  **A**：**要点**：包装。catch 之后构造 `{"ok": false, "error_type": "...", "message": "缺少 start_date", "suggestion": "请提供 YYYY-MM-DD 格式的日期"}` 作为 tool 消息 content 回填，原始异常写日志。原则：模型看不懂堆栈，但看得懂「缺什么、怎么补」。

- **Q**：模型反复调同一个工具，怎么破？
  **A**：**要点**：三层——上下文层把空结果显式标注「已查询，无记录」；代码层幂等缓存 + 计数，超限直接返回「已尝试 N 次，请换方法」；提示层在 system 里写明不要重复调。**核心是让「重复」在代码层被拦住，而不是靠提示**。

- **Q**：最大轮次设 5 的依据是什么？设 3 会怎样？
  **A**：**要点**：不能拍。先统计正常任务的轮次分布，取 P95 再留 1~2 轮余量。设 3 的问题：正常的多步任务（查记录 → 查题库 → 打分）正好被截断，用户拿到半成品。设太高（20）则兜底失效，成本和延迟失控。

- **Q**：达到最大轮次时直接报错，用户体验如何？你会怎么处理？
  **A**：**要点**：很差——用户看到「系统错误」，前面几轮的工作全废。改成降级返回：把已收集到的信息整理成答案 + 明确说明「以下信息不完整，缺少 X」。**部分成功优于完全失败**，这也是产品感和工程感的区别。
