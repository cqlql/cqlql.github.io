# 工具描述怎么写模型才调得对

## 30 秒版

> 关键词桩，不是成稿。合上卡，用这几根桩自己连成 5 句话。

- 模型选工具只看 name + description，所以 description 就是给模型看的 API 文档
- 四样必写：什么时候用、什么时候不用、参数含义和取值、一个调用示例
- 相邻工具必须在描述里划清边界，否则模型按字面相似度随机选
- 关键约束放第一句，模型对长文本中间部分注意力弱

## 展开

**反例 → 正例**

```jsonc
// 反例：模型不知道查什么，要么不调，要么乱调
{"name": "search", "description": "查询信息"}

// 正例：触发条件 + 不适用场景 + 参数示例
{"name": "get_interview_record",
 "description": "查询某位候选人**已完成**的面试记录。当用户问「上次面试怎么样」「面试表现如何」时使用。若用户问的是题库里的题目，用 list_questions，不要用本工具。",
 "parameters": {"type": "object",
   "properties": {
     "candidate_id": {"type": "string", "description": "候选人 ID，形如 c_01"},
     "round": {"type": "integer", "enum": [1, 2, 3],
               "description": "第几轮面试；不传则返回全部轮次"}},
   "required": ["candidate_id"]}}
```

**四条设计原则**

| 原则 | 做法 | 不做的后果 |
|---|---|---|
| 边界显式 | 描述里写「X 用于…；Y 用于…，不要混用」 | 两个相似工具被随机选 |
| 参数给例子 | 枚举值 + 格式示例 + 单位，比给 `type` 重要 | 模型传 `"3月1日"` 而不是 `2026-03-01` |
| 命名动宾结构 | `get_interview_record` / `score_answer` | `interview`、`data` 这种泛词无法区分 |
| 关键信息前置 | 触发条件写第一句 | 长描述里真正的约束被淹没 |

**工具数量是隐藏成本**：工具越多，描述之间互相干扰越严重，选错率上升、token 成本上升、延迟上升。超过 10~15 个就该考虑分组：先让模型选「领域」，再只挂该领域的工具子集（两阶段路由）。

**description 不是越长越好**：3~5 句能说清「何时用 / 何时不用 / 参数含义」就够。太长有两个副作用——每次请求都带全量工具定义（token 贵），且关键约束被稀释。

## 追问预演

- **Q**：举一个「改了一句话，模型就从乱调变正确」的具体例子。
  **A**：**要点**：必须真实。模板：原来写「查询面试信息」→ 用户问「题库里有没有这道题」时也调它 → 改成「查询**候选人已完成**的面试记录，用户问'上次面试怎么样'时用；题库用 list_questions」→ 选对率从 a/b 到 c/d。关键是讲清**歧义在哪、怎么消除的**，不是背结论。

- **Q**：两个工具功能很像，怎么让模型选对？
  **A**：**要点**：三招——描述里显式互斥（「如果…用 A，如果…用 B」）；参数上做区分（A 必填 `interview_id`，B 必填 `question_id`，模型看到不同必填项会多想一步）；实在分不清就合并成一个工具加 `mode` 参数（工程上最稳，模型只需选 mode）。

- **Q**：工具数量多了（比如 20 个）会有什么问题？
  **A**：**要点**：选错率上升（描述互相干扰）、token 成本上升、延迟上升。做法：工具分组 + 两阶段路由、按场景只挂当前需要的工具、把低频工具合并成「通用查询 + 参数」。

- **Q**：description 写多长合适？写太长有什么副作用？
  **A**：**要点**：3~5 句，能覆盖「何时用 / 何时不用 / 参数含义」就停。副作用有两个：每次请求都带全量工具定义（token 按调用次数放大）；关键约束被长文本稀释（模型对中间内容注意力弱）。所以把触发条件放第一句。
