# 什么场景不该用 Agent

> 这张卡是**加分卡**。答得出「不该用的场景」，说明你想过成本，不是拿着锤子找钉子。

> 关键词桩，不是成稿。合上卡，用这几根桩自己连成 5 句话。

- 判断标准：步骤能不能画成确定的流程图
- 能画 → workflow：确定性、可测试、延迟低、成本可预测
- 不能画（下一步取决于上一步结果）→ 才值得上 Agent
- 最实用的是混合：外层 workflow 固定骨架，局部用 Agent

## 展开

**对照表**

| | workflow | Agent |
|---|---|---|
| 确定性 | 同样输入同样输出 | 每次可能不同 |
| 可测试 | 能写单测、断言 | 只能做 eval、看统计 |
| 延迟 | 固定（1 次调用） | 随轮次线性涨 |
| 成本 | 可预测 | 波动大 |
| 出错定位 | 看日志哪一步挂 | 要复盘整条轨迹 |
| 灵活性 | 低 | 高 |

**Agent 值得上的三个信号**

1. 路径不固定：要先查 A 才知道该查 B
2. 输入形态多变：自由文本、多模态、格式不统一
3. 需要多轮澄清：信息不全时要主动追问

**不该用的信号**（占一个就别上）：步骤能画成流程图；有明确的 if-else 分支；结果要求 100% 可复现；延迟敏感（<1s）；成本敏感。

**混合方案是最实用的答案**：外层固定骨架（校验 → 检索 → 生成 → 落库），只在「意图识别」或「检索策略选择」这一个环节用 LLM/Agent。这样拿到 90% 的确定性和 10% 的灵活性，而且那 10% 出问题也只影响一个节点。

**反例**：把「查数据库 → 拼模板 → 返回」做成 Agent，等于用 3 次 LLM 调用换一个 SQL 查询——慢 10 倍、贵 20 倍，还可能查错表。**判断标准很简单：如果这件事一个 if-else 能写完，就别让模型决定。**

## 追问预演

- **Q**：你怎么判断一个需求该用 Agent 还是 workflow？
  **A**：**要点**：画流程图。每个节点的下一步是否固定——固定就是 workflow；某个节点的下一步「看返回内容再定」，那个节点才需要 Agent。第二个判断更实用：**能不能写出确定的输入输出对做单测**，能写就说明该用 workflow。

- **Q**：Agent 的成本和延迟比 workflow 高多少？能接受吗？
  **A**：**要点**：按实测答。量级上：workflow 一次调用；Agent 每步一次调用且每步都带全量上下文，所以 3 步就是 3 倍 token 和 3 倍延迟起步。有数字就报数字，没有就说「我测过同一个任务：workflow 800ms / 0.002 元，Agent 平均 3.2 轮 4.1 秒 / 0.03 元」。

- **Q**：如果业务方坚持要「智能体」，但需求其实是固定流程，你怎么处理？
  **A**：**要点**：别正面反驳「智能体」这个词（它现在是个营销词）。做法：先按需求用 workflow 实现，对外仍叫「智能助手」，能演示、能用；同时留出 Agent 的接口（意图识别那一层）。如果对方明确要求「能自己决定调什么工具」，就上混合方案，把可控的部分固定住。

- **Q**：你的项目里哪部分用了 Agent，哪部分是固定流程？为什么这么切？
  **A**：**要点**：按实际项目答。PassUp Agent：意图识别和工具选择用 LLM（路径不固定，用户可能问记录、问题、评分）；数据校验、打分计算、落库是固定代码（要求可复现、可审计）。切分原则一句话：**需要理解模糊输入的用模型，需要保证正确结果的用代码。**
