> 关键词桩，不是成稿。合上卡，用这几根桩自己连成 5 句话。

- size 管「一块装多少信息」，overlap 管「切断处别丢上下文」
- 我的依据：语料是 md 笔记，按 `##` 标题切 = 作者给的语义边界，超长块再二次切
- 太碎 → 答案被切成两半，命中但内容不全
- 太大 → 一块混多个主题，向量被稀释，相似度上不去
- overlap 只解决边界问题，不是越大越好

## 展开

**四种切法，各自适合什么语料**

| 切法 | 适合 | 坏在哪 |
|---|---|---|
| 固定长度（字符/token） | 无结构文本：日志、聊天记录、OCR 出来的纯文本 | 会在句子中间切断，语义不完整 |
| 按段落 / 空行 | 段落边界清晰的文档 | 段落长度方差极大，有的 20 字有的一屏 |
| 按标题层级 | md 的 `##`、HTML 的 `h2/h3`、Confluence 页面树 | 标题下面可能很长，仍需二次切 |
| 父子块（small-to-big） | 检索粒度和阅读粒度不一致时 | 实现复杂，父块太长会吃 token |

**父子块解决的是「粒度冲突」**：小块建索引，向量只承载一个意思，检索准；命中后不返回小块，而是按 `parent_id` 取回父块，喂给模型的内容完整。两件事分开调——检索要小，阅读要大。

**语义切分 vs 字符切分**：语义切分算相邻句子的向量相似度，跌破阈值才切，边界更贴合语义；代价是入库前要先算一遍 embedding（慢）、块数不可控、短文本上噪声大。字符切分快、可预测、可复现，工程上默认选它。**先上字符切分，切不动了再考虑语义。**

**overlap 的作用被高估了**。它只解决一种情况：一句话正好横跨切点。代价是索引冗余（体积 +10%，检索时同一段内容在多个块里出现，会挤占 top-k 名额）。所以别指望靠调大 overlap 补语义完整性——那是父子块的活。

**为什么按标题切在这个项目里是对的**：笔记站是 md，`##` 就是作者亲手划的主题边界，比任何算法猜得都准。注意 `###` 层级的块要合并进上级 `##`，否则「原因」和「解法」会被切开，命中一个答不完整。

## 追问预演

- **Q**：overlap 为什么要设成 size 的 10% 左右？设 0 会怎样？
  **A**：**要点**：10% 是经验起点不是定理，它约等于 1~2 句话，刚好接住跨边界的句子。设 0 时，横跨切点的答案会前半句在 A 块、后半句在 B 块，检索命中 A 块但喂给模型的是断句。代价只是索引体积涨 10%。别背 10% 这个数，要说「我用 0 / 10% / 20% 在同一批 query 上比过」。

- **Q**：什么时候该用「按标题层级切」而不是固定长度？
  **A**：**要点**：语料本身有稳定结构时——md 的 `##`、HTML 的标题、Confluence 的页面树。因为标题就是作者给的语义边界。反例：纯文本、OCR 的 PDF、聊天记录，没有可靠标题，只能退回固定长度。判断标准一句话：**标题是否由人来划**。

- **Q**：父子块具体怎么实现？检索命中的是子块，喂给模型的是父块，那引用出处怎么写？
  **A**：**要点**：入库时子块存 `parent_id`；命中子块 → 按 id 取父块文本喂模型。出处记在子块上（子块有标题路径 + 字符偏移），引用时回填父块标题 + 子块位置。坑：父块要设上限（如 2000 字），超了就用「父块摘要 + 命中子块」的组合，否则 token 爆掉。

- **Q**：切太碎会出现什么具体问题？举一个你遇到的例子。
  **A**：**要点**：要举真实例子。典型形态是 `### 原因` 和 `### 解决` 被切成两块，top-1 命中「原因」块，模型只看到原因没看到解法，答成「可能是 X 导致的」——明明资料里有答案。修法：`###` 合并到上级 `##`，或上父子块。
