- IVFFlat：聚类，建得快、省内存，召回看数据分布，必须先有数据才能建

## 展开

**三种相似度**：余弦 = 内积 / (模长乘积)。向量归一化到单位长度后，余弦和内积排序完全等价；欧氏距离在归一化后也单调相关（L2² = 2 − 2cos）。所以「用哪个」在归一化之后不是精度问题，是实现成本问题。

**为什么需要 ANN**：精确检索是 O(n·d)，5000 块没问题，百万级 × 1024 维就是每次查询几百 ms 到秒级。ANN 用一点召回率换数量级的延迟下降。

**HNSW（图）**

- 多层图：上层稀疏做长跳，下层稠密做精搜，查询时从顶层往下贪心走
- 三个参数：`m`（每层连接数，默认 16）、`ef_construction`（建图时候选集，默认 64）、`ef_search`（查询时候选集）
- 建得慢（要反复插边、维护邻居）、吃内存（图结构常驻）；查询快、召回高
- **支持增量插入**，这对「笔记天天更新」的场景很关键

**IVFFlat（聚类）**

- k-means 把向量聚成 `nlist` 个簇，查询时只扫最近的 `nprobes` 个簇
- 建得快、省内存；`lists` 经验值是 `rows/1000`（或 `sqrt(rows)`）
- **必须先有数据才能建**（聚类要样本），数据分布变了要重建；`nprobes` 越大越准越慢
- 增量写入后新向量可能落在错误的簇，召回慢慢劣化

**pgvector 实操要点**

```sql
-- HNSW
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;   -- 查询时调，越大越准越慢

-- IVFFlat（先灌数据，再建索引）
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);
SET ivfflat.probes = 10;
```

**top-k 的正确推法**：不是「试到好为止」，而是两头夹——上限是 token 预算（5 块 × 500 字 ≈ 2500 token 可接受），下限是 rerank 的池子大小（池子外的东西 rerank 捞不回来）。有 rerank 时 k 取 20；没 rerank 时 k 取 5。

## 追问预演

- **Q**：你的数据量多大？这个量级需要上 ANN 吗？
  **A**：**要点**：诚实答。5000 块 / 1024 维，精确检索 10ms 级，**不需要** ANN。上 pgvector 的 HNSW 是为了把生产路径走通（真实业务是百万级），并且拿到建索引耗时和召回曲线这组数字。这种「我知道我的量级不需要，但我测过」比硬吹有说服力。

- **Q**：HNSW 的 ef_search 调大，代价是什么？
  **A**：**要点**：查询时候选集变大 → 图遍历步数变多 → 延迟近似线性上升、内存带宽压力上升。召回收益递减：40→100 提升明显，100→200 提升很小。所以选**拐点**（比如 100）而不是最大值。

- **Q**：余弦相似度和内积什么时候可以互换？
  **A**：**要点**：向量都归一化到单位长度时等价。实际影响：归一化后能用内积索引（省一次归一化，略快）；不归一化时内积偏好大模长向量，排序会偏。纪律是「要么全归一化，要么统一用 cosine 算子」，别混着用。

- **Q**：top-k 取 5 还是 20？为什么不是 50？
  **A**：**要点**：看下游。接 rerank 就取 20（等于池子大小，池子外的捞不回来）；直接喂模型就取 5（受 token 预算约束）。50 的问题是噪声多、贵，而且模型对长上下文中间部分注意力弱（lost in the middle），塞进去不等于用上。正确做法：测 recall@k 曲线，看 k 到多少饱和。
