# recall@k、MRR、nDCG 分别衡量什么

> 边界：这张卡讲**指标本身的含义和适用场景**。怎么建 eval 集、怎么用 judge，看 `03-eval/` 下的卡。

> 关键词桩，不是成稿。合上卡，用这几根桩自己连成 5 句话。

- recall@k 答「有没有捞到」，MRR 答「第一条对的排多前」，nDCG 答「多条相关的整体排序」
- RAG 检索层首选 recall：后面还有 rerank 和模型兜底，先保证不遗漏
- 一个 query 一个答案用 MRR，多个相关文档用 nDCG
- precision 在 RAG 里意义有限，捞多了 rerank 会筛

## 展开

**三个指标的定义与适用场景**

| 指标 | 公式 | 回答什么 | 什么时候用 |
|---|---|---|---|
| recall@k | `|top-k ∩ 相关集| / |相关集|` | 该捞的有没有捞到（不管排第几） | RAG 检索层首选 |
| MRR | `mean(1 / rank_first_relevant)` | 第一条对的排在第几 | 「只要一条就对」：事实查询、问答 |
| nDCG@k | `DCG@k / IDCG@k`，`DCG = Σ (2^rel−1)/log₂(i+1)` | 多条相关的整体排序质量（含分级 + 位置衰减） | 一个 query 对应多个相关文档，且相关性有强弱 |

**为什么 RAG 优先看 recall**：架构决定的。后面还有 rerank 和 LLM 两层过滤，多捞几条不相关的代价很小（几 ms + 一点 token）；漏掉的代价很大——模型只能编，或者答「资料里没有」。**precision 在「检索结果直接给用户看」的场景才重要**（搜索框、推荐），在 RAG 里不是。

**MRR 和 nDCG 的分工**：MRR 只看第一条，且假设相关是二值的；nDCG 看全部结果、支持 0/1/2/3 分级、有位置衰减。所以——「一个 query 只该命中一篇」用 MRR，「一个 query 该命中好几篇且重要程度不同」用 nDCG。只用 MRR 会把「其余几篇全排错」掩盖掉。

**三个指标会互相打架**：nDCG 高但 recall 低，意思是「把少数相关文档排得很漂亮，但漏了一半」。所以 RAG 里要 recall + nDCG 一起看，不能只看一个。

**指标要说清口径**：recall@5 的分母是「标注的相关文档总数」。标 3 篇、命中 2 篇 = 2/3；只标 1 篇就退化成 0 或 1（hit rate）。口径不说清，两个人算出来的数能差一倍。

## 追问预演

- **Q**：为什么 RAG 更看 recall 而不是 precision？
  **A**：**要点**：因为后面有 rerank 和 LLM 两层过滤。多捞几条不相关的，代价是几 ms 和一点 token；漏掉的代价是模型只能编。precision 在「检索结果直接呈现给用户」时才是主指标，RAG 里它是下游问题。

- **Q**：MRR 和 nDCG 的区别是什么？什么时候必须用 nDCG？
  **A**：**要点**：MRR 只看第一条、二值相关；nDCG 看全部、支持分级、有位置衰减。必须用 nDCG 的场景：一个 query 对应多个相关文档且强弱不同（比如「RAG 怎么做」命中 5 篇，2 篇核心 3 篇边缘）——只用 MRR 会掩盖「其余 4 篇全排错」。

- **Q**：一个 query 有多个正确文档时，recall@5 怎么算？
  **A**：**要点**：分母是相关文档总数。标了 3 篇、top-5 命中 2 篇 → 2/3。只标 1 篇就退化成 0/1（hit rate）。所以**标注时必须说清这个 query 的相关文档集合**，否则不同人算出来的数不一样，跨版本也没法比。

- **Q**：recall@5 从 0.6 提升到 0.8，业务上意味着什么？
  **A**：**要点**：每 5 个问题里，「检索没捞到正确答案」的从 2 个降到 1 个。对 RAG 来说没捞到 ≈ 必然幻觉或答「资料里没有」。要换算成用户侧指标——答对率、追问率、转人工率。只报 recall 不换算，显得只会跑指标。
