## 展开

**主流候选的取舍**

| 模型 | 维度 | 输入长度 | 适合 | 代价 |
|---|---|---|---|---|
| bge-m3 | 1024 | 8192 | 中文/多语言、要本地、要长文本 | 显存 ~2.2G，比小模型慢 |
| bge-large-zh-v1.5 | 1024 | 512 | 纯中文短文本，追求速度 | 长文档会被截断 |
| text-embedding-3-small | 1536（可裁） | 8191 | 原型阶段、省事、便宜 | 数据出网，按量计费 |
| text-embedding-3-large | 3072（可裁） | 8191 | 效果优先 | 更贵，存储翻倍 |

**bge-m3 真正的优势不是「效果好」，是「一个模型出三种表示」**：dense（语义）+ sparse（词权重，可直接当 BM25 的替代）+ colbert（多向量，细粒度匹配）。意味着混合检索的两路可以共用一个部署，不用再单独搭一套 BM25 服务。

**query 侧 instruction 是最容易踩的坑**。bge 系列训练时 query 前面带了指令（「为这个句子生成表示以用于检索相关文章：」），document 侧不带。推理时不还原这个形态，会掉几个点，而且掉得不明显——你不测就发现不了。判断方法：看模型卡有没有写，别猜。

**换模型的代价是「向量空间不兼容」**：不同模型输出的向量不在同一个空间里，距离没有可比性，旧索引直接作废。所以要全量重算 + 重建。工程上提前做两件事：索引里存 `embedding_model` 版本字段；把向量化封装成一个接口，换模型只改一处。

## 追问预演

- **Q**：query 和 document 为什么要区别处理？
  **A**：**要点**：这是非对称检索——query 是短问句，document 是长段落，两者分布不同。模型训练时就是按「query + instruction」配「document」学的，推理时要还原这个形态，否则输入分布偏移。验证方法：同一批 query 加/不加 instruction 各跑一次 recall，差多少一目了然。

- **Q**：向量要不要归一化？不归一化会怎样？
  **A**：**要点**：归一化到单位长度后，余弦相似度就等于内积，可以省一次计算、也能直接用内积索引。不归一化时模长会污染排序——长文本的向量模往往更大，导致「长块天然排前面」。pgvector 的 cosine 算子 `<=>` 内部会归一化，但自己写内积就要手动做。

- **Q**：什么时候必须用本地模型，不能用 API？
  **A**：**要点**：四种情况——数据不能出网（内部制度、代码、医疗金融）；量大到 API 成本受不了（百万块 × 每次全量重建）；要求低延迟（本地 GPU 几 ms vs 网络往返）；要离线/内网部署。反过来，量小、原型期、只追效果上限，用 API 更省事。

- **Q**：已经上线跑了一年，想换更好的 embedding 模型，要付出什么代价？
  **A**：**要点**：全量重算 + 重建索引，且不能新旧混用（距离不可比）。做法：索引带模型版本字段 → 新旧索引并行双写 → 用 eval 集验证新的更好 → 影子流量/灰度切换。成本主要是重算的 GPU 时间和重建索引的窗口期，不是钱。
