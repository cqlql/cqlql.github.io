设计决策更新（2026-07-23）：经复盘，对 PassUp 当前阶段（用户本人跨设备继续操作）而言，原文的 ROLE_INTERVIEW_HELPER + 独立 Cookie + scope 方案偏重。当前推荐采用更简单的「Magic Login Ticket」（直接以用户身份登录）方案 → 。

本文保留作为备选方案，适用于未来出现第三方授权、多角色（ROLE_INTERVIEWER / ROLE_COMPANY_ADMIN / ROLE_GUEST）等场景参考。

背景与问题

辅助面试页面只能在 PC 端打开，移动端需要提供一个 URL 链接，复制后粘贴到 PC 浏览器打开。

场景本质是：

手机端已经登录 → 点击"辅助面试" → 生成一个临时链接 → 复制到 PC 浏览器 → PC 直接进入辅助面试页面

这类场景不建议做传统账号登录，而应设计成一次性访问凭证（One-Time Access Token）。

不要直接暴露：

https://passup.com/interview/helper?interviewId=123&userId=456

因为没有安全性，任何人拿到链接即可访问。

推荐方案：短期免密登录链接（Magic Link）

核心思路不变：跨端无缝授权 + 一次性凭证 + 最小权限 + 身份隔离。

关键设计原则：GET 只渲染页面，POST 才消费凭证（用于防社交软件预抓取，见下文）。

手机端
  |
  | 点击辅助面试
  ↓
后端生成 ticket（Redis，TTL 10min）
  |
  ↓
https://passup.ai/helper?t=abc123xyz
  |
  | 复制
  ↓
PC浏览器打开
  |
  | 前端 SPA 加载 /helper 路由（GET 不消费 token）
  ↓
前端点击/自动调用 POST /api/helper/exchange
  |
  | 后端 Lua GET+DEL 校验并销毁 token
  ↓
创建独立受限 Cookie（PASSUP_HELPER_SESSION，ROLE_INTERVIEW_HELPER）
  |
  ↓
前端 replaceState 擦除 ?t=   → SPA 路由进入辅助面试

身份隔离是这套方案最关键的改进点：辅助面试身份使用独立的 PASSUP_HELPER_SESSION Cookie，与主账号的 PASSUP_SESSION 完全隔离，互不覆盖、互不干扰。

是否免密？

是，但不是永久免密，而是：

短期 + 单次 + 限定资源

这是很多产品使用的方式（飞书文档分享、腾讯会议入会链接、Notion share link、Stripe checkout）。

生成链接

手机端请求：

POST /api/interview/{id}/helper-ticket

后端直接用 Redis 存储临时凭证，不建表（Ticket 生命周期仅 10 分钟，属典型 ephemeral credential，Redis 天生适合；建表 + 定时清理属于过度设计）：

String token = SecureRandomUtil.randomString(32); // 62^32 已远超需求，无需 48

String json = JsonUtil.toJson(
    new Ticket(userId, interviewId, AccessTicketType.INTERVIEW_HELPER)
);
redis.set(
    "interview:helper:ticket:" + token,
    json,
    Duration.ofMinutes(10)
);

return "https://passup.ai/helper?t=" + token;

生成：

https://passup.ai/helper?t=8fK39s9aKdj29...

token 长度说明：原方案用 48 字符，实际 32 字符（SecureRandom 62 字符空间，62^32）已极其安全，缩短后可减少传输/日志体积，MVP 阶段足够。

PC 打开（防预抓取 + 防泄露）

致命陷阱：社交软件会预抓取链接导致 Ticket 提前失效

微信 / QQ / 飞书 / 钉钉在用户点击或发送链接时，后台会自动发起 HEAD 或 GET 请求（抓取网页标题、生成 OG 预览图、做安全域名检测）。

如果后端在 GET 阶段就"校验通过即销毁 Ticket"，那么：

社交软件的爬虫一刷，Redis 里的 Ticket 就被销毁了；等用户在 PC 浏览器真正打开时，页面直接报"链接已失效"。

解法原则：GET 只负责渲染页面，POST 才消费凭证。

1. GET /helper?t=xxxx —— 只渲染，不消费

前后端分离下，/helper 是前端（SPA）路由，后端不做模板渲染。后端只需提供一个轻量校验接口供前端判断 UI 状态，且绝不消费 ticket：

// 仅校验"是否存在 / 是否过期 / 是否已使用"，不删除、不建登录态
@GetMapping("/api/helper/ticket/validate")
@ResponseBody
public Result<TicketStatusVO> validate(@RequestParam("t") String token) {
    TicketStatus status = ticketService.status(token); // EXISTS / EXPIRED / USED / NOT_FOUND
    return Result.ok(new TicketStatusVO(status));
}

前端 SPA 路由组件读取 location.search 中的 t，调上述接口决定展示"进入辅助面试"按钮还是"链接已失效"。

注意：GET 阶段任何请求（包括微信 / 飞书的预览爬虫）都只命中 validate，不会触碰兑换逻辑，Ticket 不会被提前销毁。

页面只渲染 UI，真正的兑换由前端在用户点击（或页面加载后）时发起 POST。

2. POST /api/helper/exchange —— 真正消费凭证

@PostMapping("/api/helper/exchange")
@ResponseBody
public Result<HelperTokenVO> exchange(@RequestBody @Valid ExchangeReq req,
                                       HttpServletResponse response) {

    // 1. 校验 ticket（存在 / 未过期），并一次性消费（见 Redis 消费逻辑 Lua GET+DEL）
    Ticket ticket = ticketService.consume(req.getToken());

    // 2. 按最小权限颁发专用角色凭证（独立 Helper Cookie，不绑定具体面试，详见下文"Helper 身份生命周期"）
    String jwt = jwtService.issueHelper(
        ticket.getUserId()
    );

    ResponseCookie cookie = ResponseCookie.from("PASSUP_HELPER_SESSION", jwt)
        .httpOnly(true).secure(true).sameSite("Lax")
        .path("/helper")                  // 仅辅助面试路由携带，普通请求不会带上它，隔离更彻底
        .maxAge(Duration.ofHours(8))      // 初始 8 小时；每次辅助面试接口请求滑动续期，绝对上限 24 小时（见下文）
        .build();
    response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());

    return Result.ok(new HelperTokenVO(ticket.getInterviewId()));
}

注意：这里写的是 PASSUP_HELPER_SESSION，不是 PASSUP_SESSION。两个 Cookie 完全隔离，PC 即使已登录主账号 A，打开账号 B 的辅助面试链接也只会新增一个独立 Helper 身份，不会把主账号 A 踢下线。

3. 前端兑换后擦除 ?t= 并跳转（防历史记录 / 日志泄露）

兑换成功后，前端必须擦除 ?t=，再进入面试页：

const token = new URLSearchParams(location.search).get('t');

const res = await fetch('/api/helper/exchange', {
  method: 'POST',
  credentials: 'include', // 跨域带 Cookie 时需开启
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ token })
});
const data = await res.json();

// 1. 先擦除地址栏中的 ?t=，避免残留浏览器历史 / Referer 泄露
history.replaceState(null, '', '/helper/login');

// 2. 再进入 SPA 面试页（前端路由跳转，读取已下发的 Cookie）
router.push('/helper/interview/' + data.interviewId);

这样 t=xxxx 不会残留在浏览器历史、也不会通过 Referer 泄露给第三方 CDN/图片。 跨域场景（Web 与 API 不同源）需在后端为 /api/helper/exchange 配置 CORS 并允许凭据（Allow-Credentials）；同源则可省略。 注意：最初的 GET /helper?t=... 仍会短暂出现在 Nginx Access Log 中，但因为 GET 不消费 token，可重试，且 token 本身只用于兑换、兑换后即失效，泄露风险可控。

安全增强建议

1. token 不要可预测

不要用 uuid。虽然 UUID 看似随机，但建议用 256bit random（如 SecureRandom）生成随机串。MVP 阶段 32 字符（62^32）已足够安全，无需 48~64 字符。

2. 设置过期时间

  • Ticket（链接本身）：建议 10 分钟。用户流程：手机打开 → 复制 → 切电脑 → 打开，10 分钟足够。
  • Helper Session（兑换后的身份）：建议 8 小时（滑动过期，绝对上限 24 小时）。辅助面试是"工作模式身份"而非单场面试授权，类比管理后台 / SaaS 工作台登录，应覆盖一整天的连续面试（上午开 A、下午开 B 无需重新授权）。采用滑动过期：每次辅助面试接口请求都把过期时间顺延 8 小时，但设绝对上限 24 小时（从首次兑换起算），不会无限续期。权限极低（仅 ROLE_INTERVIEW_HELPER + 每接口按 interviewId 校验归属），泄露风险可控，8 小时体验最好。实现上：在 TokenAuthenticationFilter 放行辅助请求后，若距首次兑换未超过 24 小时，则重新签发一个 exp 顺延 8 小时的新 JWT 并刷新 PASSUP_HELPER_SESSION 的 maxAge；超过 24 小时则强制失效、需重新走 Ticket 兑换。

3. 单次使用（一次性消费）

兑换时用 Lua GET + DEL 一次性销毁。不必标记 USED 并保留宽限期——POST /exchange 不是浏览器预加载场景，"重复点击"由前端 loading=true 拦截，弱网环境用户重新打开链接即可重新生成 Ticket。MVP 阶段 一次性消费 + 10 分钟 TTL 已足够（见下方 Redis 消费逻辑）。

4. 防社交软件预抓取

GET 阶段绝不消费 token，只渲染页面；真正的兑换放在 POST /api/helper/exchange。否则微信 / 飞书 / 钉钉的预览爬虫会把 Ticket 提前销毁。

5. 防 URL / 日志泄露

  • 兑换后前端用 history.replaceState 擦除 ?t=。
  • 不在页面里把 t 拼进任何外链、图片 src、第三方资源，避免 Referer 泄露。
  • 如 nginx 日志敏感，可对 /helper 路径关闭 query_string 记录或做脱敏。

6. 身份隔离（独立 Helper Cookie，取代"会话冲突处理"）

PC 浏览器可能已经登录了主账号 A，打开辅助面试链接（可能对应账号 B）时，不要覆盖 PASSUP_SESSION，否则会把主账号踢下线。改用独立的 PASSUP_HELPER_SESSION Cookie 承载辅助面试身份，两者完全隔离（详见下文"身份隔离"小节）。这样初期无需做复杂的会话冲突检测与二次确认弹窗。

7. 绑定浏览器（初期可不做）

第一次打开可记录 user-agent 与 ip，后续请求检查。PassUp 初期不建议做，增加复杂度。

Redis 方案（推荐，无需建表）

项目已使用 Redis，可以直接用，不必建表。

key:   interview:helper:ticket:{token}
value: { userId:1001, resourceId:2001, type:"INTERVIEW_HELPER" }
TTL:   600s

> `type` 字段便于后续扩展（如 `RESUME_SHARE` 分享简历、`INTERVIEWER_INVITE` 面试官邀请），避免未来为不同场景重新设计 Ticket 结构：
>
> ```java
> enum AccessTicketType {
>     INTERVIEW_HELPER,    // 辅助面试
>     RESUME_SHARE,        // 分享简历
>     INTERVIEWER_INVITE   // 面试官邀请
> }
> ```

生成：

String token = SecureRandomUtil.randomString(32);

redis.set(
    "interview:helper:ticket:" + token,
    json,
    Duration.ofMinutes(10)
);

消费（Lua 原子操作，GET + DEL 一次性消费）：

public Ticket consume(String token) {
    String key = HELPER_TICKET + token;

    // 用 Lua 脚本保证"读取 + 删除"在 Redis 单线程内原子执行，
    // 避免 Read-Then-Write 并发下（用户连点 / 前端并发两次 /exchange）同一 Ticket 被兑换两次。
    DefaultRedisScript<String> script = new DefaultRedisScript<>(
        "local json = redis.call('GET', KEYS[1])\n" +
        "if not json then return '-1' end\n" +            -- 不存在 / 已过期
        "redis.call('DEL', KEYS[1])\n" +                  -- 一次性消费，直接删除
        "return json",                                     -- 返回原 JSON 供后端继续处理
        String.class
    );

    String result = redis.execute(script, List.of(key));
    if ("-1".equals(result)) {
        throw new BizException("链接不存在或已失效");
    }
    return JsonUtil.toObj(result, Ticket.class);
}

并发场景下，Lua 在 Redis 单线程内串行执行：只有第一个请求拿到 JSON 并 DEL，后续请求 GET 返回 nil 直接报"已失效"，不会出现重复兑换 / 建立两个临时会话。 相比"标记 USED + 保留 2 分钟宽限期"的方案，GET+DEL 更简单：POST /exchange 不是浏览器预加载场景，重复点击由前端 loading 拦截，弱网则重新生成链接即可，无需为宽限期增加复杂度。 可选增强：若需排查"链接已失效"类工单，可在兑换成功后异步打一条业务日志（INTERVIEW_HELPER_EXCHANGE：userId / interviewId / time / ip / ua），进业务日志即可，无需建表。MVP 阶段可暂不做。

推荐方案（GET 渲染 / POST 兑换）：

  |
  | POST /interview/{id}/helper-ticket
  ↓
Redis（TTL 10 分钟）
  |
  | 返回 URL
  ↓
PC 打开

  ↓

  • Redis Key 管理
  • JWT
  • Cookie refresh token

Redis Key 设计：

public interface InterviewRedisKey {

    String HELPER_TICKET = "interview:helper:ticket:";

    Duration HELPER_TICKET_TTL = Duration.ofMinutes(10);
}

关键细节：PC 不应获得完整用户权限

这一点很重要。链接登录后不要生成普通登录 JWT，应生成专用角色：

ROLE_INTERVIEW_HELPER

权限：

  • 允许：GET /api/interview/current、POST /api/answer/analyze、GET /api/resume/context
  • 禁止：修改账号、充值、删除简历

否则链接泄露风险很大。

JWT / Cookie 方案下的实现

生成凭证时，不要把普通用户的 ROLE_USER 放进去，仅放入 ROLE_INTERVIEW_HELPER 与 scope（interviewId 不写入 JWT，详见下文"Helper 身份生命周期"）：

String jwt = Jwts.builder()
    .subject(String.valueOf(ticket.getUserId()))
    .claim("type", "HELPER")                                   // 身份类型，统一 Filter 据此区分 USER / HELPER
    .claim("authorities", List.of("ROLE_INTERVIEW_HELPER"))
    .claim("scope", List.of("INTERVIEW_READ", "AI_ANALYZE"))    // 用 scope 数组，便于未来细分权限
    .expiration(new Date(System.currentTimeMillis() + 8 * 60 * 60 * 1000)) // Helper Session 8 小时，滑动过期，绝对上限 24 小时，无 Refresh Token
    .signWith(secret)
    .compact();

关键修正：JWT 不绑定 interviewId。Helper Session 代表"当前浏览器处于辅助面试模式"这一身份，而非"某一场面试"。interviewId 由业务 URL 在请求时携带、经后端动态校验（见下文"Helper 身份生命周期"）。若把 interviewId 写进 JWT，同一浏览器先后/同时辅助多场面试时，新 Ticket 兑换出的 JWT 会覆盖旧 JWT，导致先前的面试页因 interviewId 不匹配而整体失效。

用 authorities + scope 数组而非单值字符串，未来扩展更舒服：例如面试官模式 ROLE_INTERVIEWER、候选人模式 ROLE_CANDIDATE，或新增 INTERVIEW_WRITE 等细粒度 scope，都无需改 JWT 结构。

统一 Token Filter（不拆两个 JWT Filter）

不要为 Helper 单独写 HelperJwtAuthenticationFilter，否则以后 JwtAuthenticationFilter 与 HelperJwtAuthenticationFilter 会越来越多、越来越乱。只保留一个 TokenAuthenticationFilter，同时识别两种身份：

String token = request.getHeader("Authorization");
if (token == null) token = cookie("PASSUP_SESSION");        // 普通用户身份
if (token == null) token = cookie("PASSUP_HELPER_SESSION");  // 辅助面试身份

Authentication auth = jwtService.parse(token);               // 同一套 JWT 解析逻辑
// auth 的 principal 携带 AuthenticationContext

AuthenticationContext 区分身份类型，便于后续扩展：

class AuthenticationContext {
    Long userId;
    String sessionType;     // "USER" | "HELPER"
    List<String> authorities;
    // 注意：HELPER 不再携带 interviewId，interviewId 由请求 URL 动态提供、由业务层校验
}
  • 普通：{ userId:100, type:"USER", authority:"ROLE_USER" }
  • 辅助：{ userId:100, type:"HELPER", authority:"ROLE_INTERVIEW_HELPER" }（无 interviewId）

Spring Security 接口隔离 + 不轻信 JWT scope

在 SecurityFilterChain 中用 hasAuthority 做接口隔离，拒绝辅助面试凭证访问全局接口：

http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/helper/interview/**", "/api/answer/analyze").hasAuthority("ROLE_INTERVIEW_HELPER")
    .requestMatchers("/api/user/**", "/api/payment/**").hasAuthority("ROLE_USER") // 拒绝 HELPER 角色访问
    // 其他业务接口默认需 USER，HELPER 无法命中
);

不要认为 JWT 里有 INTERVIEW_READ 就直接放行：JWT 生命周期 8 小时（滑动过期，绝对上限 24 小时），期间用户可能删除面试、面试已结束或权限变化。接口层在通过 authority 校验后，还要再查一次业务状态：

if (!authentication.hasAuthority("ROLE_INTERVIEW_HELPER")) {
    deny();
}

// interviewId 来自 URL 路径（如 /api/helper/interview/{id}），而非 JWT
Long interviewId = (Long) request.getAttribute("interviewId");
Interview interview = interviewRepository.findById(interviewId);
if (interview == null || interview.isExpired() || interview.isEnded()) {
    deny(); // 即使 JWT 有效，资源已不可访问
}
// 关键：校验该面试是否属于当前 Helper 用户（本人即授权），越权访问者被拦截
if (!interview.getUserId().equals(authentication.getUserId())) {
    deny(); // Helper Token 泄露也只能访问自己的面试，无法访问他人
}

这样即使 ROLE_INTERVIEW_HELPER 的 JWT 泄露，持证者也只能访问受限接口；且一旦资源状态变化，越权访问会被业务层拦截。

Helper 身份生命周期：Session 与 Interview 分层

上述"在 JWT 里绑定 interviewId"有一个隐含前提：一个浏览器同一时刻只服务一场辅助面试。但 PassUp 真实场景可能是：

上午：手机生成面试 A → PC 打开 → 辅助完成
下午：手机生成面试 B → PC 再打开

甚至同一浏览器同时开两个窗口，分别辅助面试 A、面试 B。此时若 Helper JWT 绑定了 interviewId，第二次兑换出的新 JWT 会覆盖第一次的 JWT：

第一个面试页 /helper/interview/888
请求携带 PASSUP_HELPER_SESSION(interviewId=999)   ← 被第二次兑换覆盖
后端校验：❌ 无权访问 888

第一个面试页直接失效。

根因：当前设计把 Helper Session（辅助身份）与 Interview Session（某一场面试）耦合在了一起。正确做法是分层：

普通登录：   USER TOKEN  ──┐
                          ├─ 多个业务页面
辅助登录：   HELPER TOKEN ─┘（多场 Interview 共用同一 Helper 身份）

即：HELPER TOKEN（身份）  +  Interview Context（来自 URL + DB 校验）

分层后的模型

Helper Ticket（仍绑定 interviewId）：负责"手机授权 PC 打开哪一个面试"，因此 Redis 中的 Ticket 仍保留 interviewId：

interview:helper:ticket:xxxx  →  { userId:1001, interviewId:888 }

Helper Token（不绑定 interviewId）：兑换时生成，只表达"该浏览器处于辅助面试模式"，代表用户身份而非某场面试：

{
  "userId": 1001,
  "type": "HELPER",
  "authorities": ["ROLE_INTERVIEW_HELPER"],
  "scope": ["INTERVIEW_READ", "AI_ANALYZE"]
}

Interview 权限在请求时动态判断：访问 GET /api/helper/interview/888 时，interviewId 由 URL 路径提供，后端再查库校验当前 Helper 用户是否拥有该面试的辅助权限：

// 辅助面试即本人，直接校验归属即可；若需更灵活可建 interview_helper_access 表
if (!interview.getUserId().equals(helper.getUserId())) {
    forbidden();
}

这样：

第一次：PASSUP_HELPER_SESSION(user=1001)  打开 /helper/interview/888   → OK
第二次：PASSUP_HELPER_SESSION(user=1001)  打开 /helper/interview/999   → OK（仍是同一 Cookie）

两个页面可以同时存在，互不影响。

安全性并没有下降

Helper Token 泄露后，攻击者拿到的仅是 user=1001 这一身份，只能访问 user=1001 自己的面试，访问 user=2000 的面试会被后端 interview.userId != authentication.userId 拦截。这与 Google Session 不绑定"某一个 Gmail 页面"、而是绑定"用户身份 + 页面资源动态鉴权"的设计一致。

因此 Helper Token 的 TTL 语义也更清晰：它代表"当前浏览器处于辅助面试模式"这一工作身份，而非"某一场面试的有效期"。建议采用 8 小时滑动过期、绝对上限 24 小时（类比管理后台 / SaaS 工作台登录，覆盖一整天连续面试），而非固定 2 小时——因为单场面试模型已解耦，Helper Session 不应按单场面试生命周期设计。这个生命周期解耦，比 Cookie 的 Path 设置更关键——它直接决定了能否支持多场面试、多标签页、同时辅助多个候选人，以及后续面试官模式的扩展。

身份隔离：独立 Helper Cookie（取代"会话冲突处理"）

原方案假设 PC 打开时是未登录状态，并设计了"检测已有会话 → 弹窗确认 → 退出重兑"的冲突流程。在 PassUp 初期，这套流程偏重，且与"辅助面试是临时场景"的定位不符。

更好的方式是从 Cookie 层做身份隔离，让主账号与辅助面试身份并存：

                        浏览器

           ┌───────────────────────────────┐
           │                               │
  PASSUP_SESSION              PASSUP_HELPER_SESSION

   普通用户身份                  辅助面试身份

   ROLE_USER                    ROLE_INTERVIEW_HELPER

    全功能              多场面试共用同一 Helper 身份（interviewId 由 URL 动态提供）
  • 普通接口：TokenAuthenticationFilter 读取 PASSUP_SESSION，按 ROLE_USER 鉴权（sessionType=USER）。
  • 辅助接口：同一 Filter 读取 PASSUP_HELPER_SESSION，按 ROLE_INTERVIEW_HELPER 鉴权（sessionType=HELPER），interviewId 来自 URL 并由业务层按归属校验。
  • 由于 Helper Cookie 的 Path=/helper，普通请求（/api/user/** 等）根本不会带上它，隔离更彻底；同一 Helper 身份可同时服务多场面试（见"Helper 身份生命周期"）。

两个 Cookie 完全独立：

  • PC 已登录账号 A（PASSUP_SESSION=A），打开账号 B 的辅助面试链接 → 仅新增 PASSUP_HELPER_SESSION=B，主账号 A 不受影响。
  • 辅助面试结束后 PASSUP_HELPER_SESSION 过期 / 登出，主账号 A 仍在。

这正是很多 SaaS 系统偏好"多身份并存"而非"覆盖原会话"的原因：复杂度更低、体验更顺、初期无需二次确认弹窗。等 PassUp 后期确实需要"同一浏览器唯一辅助身份"等约束时，再在此基础上加会话冲突检测即可。

最终建议

Redis + Lua 原子 GET+DEL 的一次性 ticket（10 分钟过期、绑定 interviewId、带 type 便于扩展）+ GET 渲染 / POST 兑换消费 + 兑换后前端 replaceState 擦除 ?t= + 独立 PASSUP_HELPER_SESSION Cookie（Path=/helper，8 小时滑动过期、绝对上限 24 小时，无 Refresh，JWT 不绑定 interviewId）+ 统一 TokenAuthenticationFilter 识别双身份 + 专用辅助面试权限（ROLE_INTERVIEW_HELPER，interviewId 由 URL 提供、接口层按归属与业务状态校验）+ Helper Session 8 小时滑动过期（绝对上限 24 小时）有效期。

核心方向（Magic Link + Redis 极简存储 + 最小权限 + 身份隔离）保持不变，相对早期版本的关键调整：

  1. 防社交软件预抓取：GET 不消费，POST 才兑换。
  2. 防 URL / 日志泄露：兑换后 history.replaceState 擦除 t。
  3. 身份隔离（取代会话冲突）：独立 PASSUP_HELPER_SESSION Cookie（Path=/helper），不覆盖主账号 PASSUP_SESSION，普通请求不携带它；初期无需冲突弹窗。
  4. 并发安全：consume 用 Lua 脚本 GET+DEL 原子执行，杜绝重复兑换（简化掉"USED 标记 + 2 分钟宽限期"）。
  5. 统一 Filter：只有一个 TokenAuthenticationFilter 同时识别 PASSUP_SESSION 与 PASSUP_HELPER_SESSION，用 AuthenticationContext.sessionType 区分身份，不拆两个 JWT Filter。
  6. 权限不轻信 JWT（且 JWT 不绑定 interviewId）：ROLE_INTERVIEW_HELPER + scope 只做粗粒度拦截；interviewId 不写入 JWT，由请求 URL 提供，接口层先按用户归属、再按业务状态（是否已删除 / 过期 / 结束）校验，从而支持同一浏览器多场面试 / 多标签页并存。
  7. 极简存储 + 可扩展：Ticket 直接存 Redis（不再建表），value 增加 type 字段（INTERVIEW_HELPER / RESUME_SHARE / INTERVIEWER_INVITE）；token 32 字符；Helper Session 8 小时滑动过期（绝对上限 24 小时）且无 Refresh Token，结束重新生成即可。
  8. Helper 身份生命周期解耦：Helper JWT 只承载 userId + ROLE_INTERVIEW_HELPER + scope，不绑定 interviewId；interviewId 来自业务 URL + DB 归属校验。这样同一浏览器可先后/同时辅助多场面试、多标签页并存，且后续面试官模式扩展无需改 JWT 结构（详见"Helper 身份生命周期"）。

该方案与 PassUp 现有的 Spring Security + Redis 架构衔接最好，也是复杂度、安全性、未来扩展性之间最平衡的选择，可直接进入开发。
