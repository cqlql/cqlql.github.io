实时面试会话重构-领域事件解耦

实时面试会话重构：领域事件解耦

针对 AudioStreamSession 承担职责过多（计费、持久化等横切关注点侵入实时链路）的问题，进行的一次结构化重构。

1. 问题诊断

AudioStreamSession 是一个「上帝类」（约 730 行），混杂了 6 类职责：

AudioStreamSession
│
├── WebSocket 收发
├── 音频队列
├── ASR 生命周期
├── LLM 调用
├── Prompt 构建
├── 消息持久化
├── 面试生命周期
└── 计费

其中 billingService.startBilling / pauseBilling / stopBilling 与 conversationService 是典型的横向关注点，被硬编码进会话生命周期，导致：

  • 每加一个业务（评估、分析）就要往里塞依赖
  • 无法单独测试 ASR/LLM 链路
  • 计费逻辑散落在 onAsrReady、onClose 等多处

更深层的结构性问题

WebSocket 断开
      ↓
AudioStreamSession.onClose()
      ↓
结束 ASR
      ↓
停止计费
      ↓
结束面试

这意味着：物理连接生命周期 = 面试生命周期。

而这正是后续要支持「暂停 / 断线重连 / 切后台 / 多次继续面试」时最大的结构障碍。

2. 设计决策：为什么选「领域事件」而非 Listener / Facade

2.1 否决方案 A：List<SessionLifecycleListener> 手动遍历

private final List<SessionLifecycleListener> lifecycleListeners;

for (var listener : lifecycleListeners) {
    listener.onReady(...);
}

问题：生命周期一旦复杂，接口会膨胀成「另一个上帝接口」：

onReady() onStarted() onPaused() onResumed() onDisconnected()
onReconnected() onClosed() onExpired() onLlmStarted() onLlmCompleted() ...

2.2 否决方案 B：大 Facade（InterviewSessionLifecycleHandler）

AudioStreamSession → LifecycleHandler → BillingService / ConversationService

本质上只是把依赖搬家，没有真正的扩展性。

2.3 采纳方案：领域事件 + @EventListener 独立处理器

                    ┌──────────────────────┐
                    │  InterviewSession    │
                    │  interviewId / userId │
                    │  status / context     │
                    │  billing state        │
                    └──────────┬───────────┘
                               │ Session Lifecycle
                               ▼
                    ┌──────────────────────┐
                    │   Domain Events      │
                    │ SessionStarted       │
                    │ SessionPaused        │
                    │ SessionResumed       │
                    │ SessionEnded         │
                    └──────────┬───────────┘
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        BillingHandler   PersistenceHandler  AnalyticsHandler

新增一个功能（如面试质量分析），只需新增一个处理器类，无需改动 AudioStreamSession、InterviewBillingService 等任何现有类。

3. 核心边界原则（最重要）

不是所有逻辑都事件化。

类别处理方式示例
实时流处理链路直接调用receiveAudio → ASR → LLM → 推送、saveUserMessage
业务生命周期领域事件Started / Paused / Resumed / Ended / Expired

原因：实时链路（音频、ASR token、LLM token）一旦事件化会变得极难调试，且属于高频热路径，不应引入事件广播的开销与间接性。

4. 最终结构

modules/realtime/
├── session/
│   ├── InterviewSessionState.java   # 逻辑会话状态（跨暂停/重连存活）
│   ├── AudioStreamSession.java      # 物理流连接：收音频/ASR/LLM/推送
│   └── ...
├── lifecycle/                        # 领域事件（纯 record，语义明确）
│   ├── InterviewSessionEvent.java    # 基接口
│   ├── InterviewStartedEvent.java
│   ├── InterviewPausedEvent.java
│   ├── InterviewResumedEvent.java
│   ├── InterviewEndedEvent.java      # 携带 EndReason
│   └── InterviewEndReason.java       # USER_ENDED / SESSION_EXPIRED / BILLING_EXHAUSTED / SYSTEM_ERROR
├── billing/
│   └── InterviewBillingEventHandler.java      # @EventListener 监听 4 个事件
└── conversation/
    └── InterviewConversationEventHandler.java # 监听 Paused/Resumed/Ended

事件定义为业务化语义（而非模糊的 onReady）：

public record InterviewEndedEvent(
    Long userId,
    Long interviewId,
    String sessionId,
    InterviewEndReason reason
) implements InterviewSessionEvent {}

结束原因一开始就枚举化，后续业务判断会简单很多：

public enum InterviewEndReason {
    USER_ENDED,        // 用户正常结束
    SESSION_EXPIRED,   // 暂停超时回收
    BILLING_EXHAUSTED, // 余额耗尽
    SYSTEM_ERROR
}

5. 事件发布关键点

AudioStreamSession 注入 ApplicationEventPublisher（通过依赖聚合对象 AudioStreamSessionDependencies 传递）：

eventPublisher.publishEvent(new InterviewStartedEvent(
    userId, interviewContext.getInterviewId(), state.getSessionId()));
  • Started 必须在 startConversation 同步回填 interviewId 之后发布（否则事件的 interviewId 为空）。
  • 发布时统一用 state.getSessionId()（逻辑会话 ID），而非 this.sessionId（物理连接 ID）。

6. 遗留的同步调用（有意保留）

位置调用保留原因
AudioStreamSession.startConversationconversationService.startConversation必须同步回填 interviewId，否则后续消息保存拿不到 ID
AudioStreamSession.saveUserMessage/AssistantMessageconversationService.save*Message实时链路热路径，直接调用
AudioStreamingService.onOpenbillingService.forceTerminateActiveSession同步强踢，需返回 oldSessionId 去断开旧连接（请求-响应语义，非通知）

7. 后续演进方向

  1. 计费状态快照：进一步彻底实现「物理连接生命周期 ≠ 面试生命周期」，可将计费状态与逻辑会话状态机统一快照管理。详见 第 8 节。
  2. forceTerminateActiveSession 事件化：需同步返回 oldSessionId，属请求-响应而非通知，需引入同步事件/回调机制后再评估。
  3. 新增横切能力零侵入：后续「面试质量分析」「埋点统计」只需新增 @EventListener 处理器监听 InterviewEndedEvent。

8. 计费状态与逻辑会话状态机统一快照管理

本节针对第 7 节第 1 点「计费状态快照」展开，是领域事件解耦之后的再收敛：把「计费状态写入」从事件回调收回到状态机调用链，同时保留 Redis 持久化容灾。

8.1 问题的本质：两套账 + 双写

当前「暂停」这一个业务事实，被拆成三个互不知情的动作，靠事件桥接：

位置现状问题
InterviewSessionState.markPaused()只设 State.PAUSED + 解绑连接状态机无计费意识
InterviewBillingService.pauseBilling()sessionInfo.setPaused(true)独立维护第二份 paused
InterviewBillingEventHandler.handlePaused靠 userId 回查 Redis状态源在 Redis 而非状态机

即存在两份独立状态：

状态载体存储状态机
逻辑会话状态InterviewSessionStateJVM 内存ACTIVE → PAUSED → ACTIVE → ENDED
计费状态InterviewSessionInfoRedis（interview:session:user:{userId}）paused 布尔 + 心跳基准

关键洞察：这两份「账」恰恰提供了进程崩溃后的 Redis 兜底能力。因此「统一」的目标不是把计费状态迁进 JVM 内存（那样反而弱化容灾），而是让状态机成为写状态的唯一入口，Redis 计费快照作为它的持久化投影。

8.2 目标架构

            InterviewSessionState（唯一事实源）
                 │  markPaused / markActive / markClosed
                 │  （状态迁移 + 内联触发计费投影）
                 ▼
         BillingStateProjection（realtime 层接口）
                 │
                 ▼
      InterviewBillingService（billing 模块实现）
                 │
                 ▼
      Redis InterviewSessionInfo（持久化投影，容灾兜底）

     （旁路，不改状态）领域事件 InterviewPausedEvent 等 → 分析/埋点 handler

核心变化：状态机 → 投影 → Redis 是一条「写」的直线；领域事件退化为「只读通知」旁路，不再承载写状态职责。

8.3 改造步骤（每步可独立提交）

  1. 新增投影接口 modules/realtime/billing/BillingStateProjection.java（放 realtime 层，避免 realtime.session 反向依赖 billing 模块）：

    public interface BillingStateProjection {
    void onStarted(Long userId, String logicalSessionId, Long interviewId);
    void onPaused(Long userId, String logicalSessionId);
    void onResumed(Long userId, String logicalSessionId);
    void onEnded(Long userId, String logicalSessionId);
}

    签名带 userId，因为 InterviewBillingService 的 Redis Key 依赖 userId；InterviewSessionState 本就持有 userId 可直接透传。

  2. InterviewSessionState 持有投影，三处状态迁移内联触发：markPaused → onPaused、markActive → onResumed、markClosed（在 compareAndSet 成功分支内）→ onEnded。

  3. InterviewBillingService 实现投影：投影方法仅为现有 startBilling/pauseBilling/resumeBilling/stopBilling 的薄封装，计费逻辑一行不动。

  4. 调整 InterviewBillingEventHandler（⚠️ 唯一正确性风险点）：状态机内联触发与 @EventListener 并存会重复扣费，必须二选一——

    • 方案 A（推荐）：handler 只保留旁路职责（日志/埋点/未来分析），删除计费写状态调用。
    • 方案 B（过渡）：保留监听但加幂等保护（Redis Key 已删除/已 paused 时早退）。

  5. 装配投影：经 AudioStreamSessionDependencies 传入，在 AudioStreamSession 构造 InterviewSessionState 时注入；重连复用 resumeState 时投影随之复用，无需重建。

8.4 风险与对策

风险对策
状态机内联 + 事件监听并存导致重复扣费二选一（见 8.3 步骤 4），加幂等保护
markClosed 重复触发保持 closed.compareAndSet 幂等，投影调用放成功分支内
forceTerminateActiveSession 是同步请求-响应语义保持现状不动，本方案不覆盖（另见第 7 节第 2 点）
暂停超时回收（evictExpiredPausedSessions）走 markClosed → onEnded → 结算，天然收敛

8.5 收益

  • 消除 State.PAUSED 与 sessionInfo.paused 的双写，状态机成为唯一事实源。
  • 暂停/重连/结束的计费动作，全部收敛到 markPaused/markActive/markClosed 一条链。
  • 保留 Redis 持久化，进程重启容灾不退化。
  • 领域事件保留，未来「面试质量分析」「埋点」仍可零侵入扩展。

工作量参考：约 5 个类、净增不到 100 行，无计费业务逻辑改动，每个 commit 独立可测、可回滚。
