实时会话链路复杂度评估与拆解清单

实时会话链路：复杂度评估与拆解清单

文档定位：现状评估（不评价历史决策）+ 可执行的拆解清单。状态：已定稿（2026-09-22，两轮评审）—— 可按 §7 的顺序开始实施，不再扩展架构。

这是本目录关于实时会话的第三篇，三篇分工如下：

文档处理的事
用领域事件把计费 / 持久化从实时链路摘出去（✅ 已落地）；其 §8「计费投影」仍是提案（代码里没有 BillingStateProjection）
独立心跳、死连接检测、暂停恢复、跨进程重建、参数配置化（✅ 全部闭环），并定了三条健壮性原则
本文前两篇之后仍然留在这两个类里的复杂度：量化 → 病根 → 拆解清单 → 验收方式

本文不推翻前两篇的结论，恰恰相反：其中一条原则（统一 cleanup）已经在文档里定死， 但代码结构上尚未收敛 —— 这会是本文要处理的重点之一（§4.4）。

相关：后端方案 —— 本文 §6 的 P0 三项即它的「步骤零」。

1. 结论

  1. 复杂度是真的，但不是「写坏了」，而是「新能力持续落在同两个类上」。 领域事件解耦时 AudioStreamSession 约 730 行，现在是 812 行 —— 拆过一次又长回来了。 暂停恢复、独立心跳、ASR 自愈、错误归一这些后续能力，全都默认落在它身上。
  2. 「容易出错」的准确口径：单点改动有测试兜着（本模块约 62 个用例）， 长尾组合场景没有防线（暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出 + 顶号并发）。
  3. 病根不是行数，而是三类可复现的东西：职责叠加、隐式不变量、跨模块隐式耦合。
  4. 处方：先补测试接缝（P0-0）→ 三次抽取（ASR 运行期 / 回合编排 / 连接判据接口）→ ID 语义区分 → cleanup 收敛与不变量结构化。全部是行为等价的机械重构，不新增能力。 V2 的 input=text 与 /ws/asr 应该在这些之后加（见 §7）。

    测试不是最后一步，而是第一步：P0-0 是 P0-1 / P0-2 的前置条件（§4.5 的三个盲区正好是要动的块）。

  5. 完成标准不是"行数下降"，而是变化边界：AudioStreamSession 不再认识 ASR 运行机制、 LLM 客户端与上下文裁剪；且满足 §8 的四条约束（新增输入源不改 runner、新增通道不复制 runner、 新增回合输入不复制 turn runner、新增退出路径只能进统一 cleanup）。

3. 职责清单：这两个类现在到底在干什么

3.1 AudioStreamSession（10 个角色）

WebSocket 持有者（含发送队列 + sendLoop）｜ASR 运行器（consumeLoop、重连退避、pumpAudio、残留帧丢弃、lastAsrId 轮换、asrUnavailable）｜上行协议适配（binary / text / heartbeat / PAUSE）｜回合编排（triggerLlmReply、triggerInitialQuestion）｜对话上下文管理（context、trimContext、buildMessages、MAX_CONTEXT）｜落库协调（conversationService）｜领域事件发布（Started / Paused / Resumed / Ended）｜连接存活状态（两套时间戳 + heartbeatCapable + isAlive）｜暂停与结束语义（paused、markPaused、onClose 分支）｜ASR 消息 id 轮换与去重语义

3.2 AudioStreamingService（8 个角色）

握手准备与失败回滚｜两张注册表的所有者（streamSessions / logicalSessions）｜恢复与跨进程重建协调｜心跳扫描与踢出｜三种回收（暂停 / 悬挂 / pending）｜连接存活的唯一判据来源｜顶号与强制关闭｜主动 / 被动关闭的仲裁

这不是"作者没拆"，而是新能力没有落脚点：加一个"文字作答"要动它、加一个"识别通道"也要动它。 上一轮讨论 V2 时"专门写一套会不会更好"的直觉，正是被这个类逼出来的（结论见 V2 方案 §10.2：新写一套更贵）。

4. 真正的病根

4.1 隐式不变量只能靠注释维持

编译器管不了、只能靠人记住的规则：

#不变量出处忘了会怎样
1构造器有副作用（markActive + bindConnection + 起 2 个线程 + 发事件），失败必须调用方手工回滚AudioStreamingService#onOpen 的 catch (RuntimeException) 里手工 resumeState.markPaused() / endInterview()留下"无物理连接的 ACTIVE"僵尸，两条回收路径都扫不到（历史上真实发生过，见前一篇 P0.1）
2顶号时只请求关闭，不能抢先摘注册表onOpen 内注释心跳扫描再也扫不到该连接，逻辑会话永久残留
3streamSessions.remove() 的返回值同时承担「移除」与「幂等守卫」前一篇 §4 原则一"移除"与"清理"变成两件事，静默出错
4ASR 重连前必须 dropStaleAudio() + 轮换 lastAsrIdconsumeLoop旧帧喂给新连接（过期转写）、新旧句子在前端串成一条
5不要无脑 forceClose()DoubaoAsrClient 注释abort + shutdownNow 以异常回调，日志出现误导性故障栈
6计费起算必须由 startedPublished 守卫onAsrReady重连重复 startBilling，覆盖起算点、已用时长归零
7ASR 故障必须走 onAsrSessionError 而非 onAsrSessionEndconsumeLoop finally + asrUnavailable结束原因误记为 USER_ENDED，统计与客诉都失真

前一篇（心跳与暂停恢复）已经修过一批同类问题，但新写法仍在重复同一模式： 横向关注点默认寄生在业务回调里 —— 这次 V2 要拆的 ASR→LLM 耦合，就是它的第二次发作。

4.2 跨模块的隐式耦合：谁在依赖注册表

4 处「按物理连接定位会话」的调用点直接依赖 AudioStreamingService 的 streamSessions：

// InterviewBillingScheduler#validateSessionState（每 10 秒跑一次）
String activeConnectionId = streamingService.resolveActiveConnectionId(sessionId);
if (activeConnectionId == null || !streamingService.hasActiveStreamSession(activeConnectionId)) {
    billingService.stopBilling(userId, sessionId);   // ← 找不到就视为孤儿，停计费
    return false;
}
调用点依赖漏改后果
InterviewBillingScheduler#validateSessionStateisConnectionLost / resolveActiveConnectionId / hasActiveStreamSession新链路的会话若不在注册表里 → 静默停止扣费，TIME_UPDATE 停发
InterviewBillingScheduler#terminateSession同上 + forceCloseSession余额耗尽时关不掉会话
WsHeartbeatScheduler → evictDeadSessions只遍历 streamSessions死连接不回收
AudioStreamingService#onOpen（顶号）forceTerminateActiveSession → resolveActiveConnectionId → streamSessions.get顶号失效，同用户两条会话并行计费

这就是 V2「识别通道」方案里建议不碰注册表的原因，也是 §6 P0-3 要接口化的动机。

4.3 命名与语义漂移

漂移具体表现危害
两个 sessionIdInterviewContext#sessionId 是物理连接 ID，InterviewSessionState#sessionId 是逻辑会话 ID，后者靠 getLogicalSessionId() 别名纠偏InterviewAsyncService#runSafely 的告警日志打的是 context.getSessionId()（物理 ID），排查时极易看错
stopBilling 参数名与注释不符形参 currentSessionId，javadoc 写"当前正在关闭的 WebSocket 会话 ID"；但三处调用方全部传逻辑会话 ID，内部也是拿它比 sessionInfo.getSessionId()（startBilling 用逻辑 ID 写入）按注释传物理连接 ID，会静默走"跳过清理"分支 → 计费不结算、Redis key 残留
Audio* 前缀AudioStreamSession / AudioWebSocketHandler 现在还要承载文本（V2 之后更明显）误导阅读者以为只处理音频
文档与代码相反AGENTS.md §6.5.4 末尾称 PausedMessage 经 sendQueue 异步入队"若需强一致可改为同步发送"，代码早已是 sendMessageNow；§8.6 把"补实时会话单测"列为待做，实际已有约 62 个用例下一个人按文档改代码

4.4 已定原则与代码结构的落差

前一篇 §4 定了三条原则，其中原则一（任何物理连接退出路径最终都必须进入统一 cleanup）在结构上还没收敛：

状态：这条已在 P1-1 收敛（连接退出的「通知/关闭」与「收尾」各成一个入口，见 §6 P1-1 进度）。 下面保留问题描述作为改造动机；未进 cleanup 的两条逻辑终结路径（暂停超时 / DB 兜底）见 P1-1 说明。

  • 触发收尾的入口有 7 处：Spring afterConnectionClosed（间接承接 handleAsrSessionEnd / handleAsrSessionError / handlePauseRequested / handleTransportError / forceCloseSession 五个主动 close() 路径） + 心跳踢出 evictDeadSessions 里自己拼的「发 ERROR → onError → 虚拟线程 sleep 1500ms → onClose」。 后者的时序（发错误通知 + 宽限 1.5 秒）是心跳踢出独有的，与其他路径不一致。
  • 「发结束事件」没有单一入口：AudioStreamSession#onClose 发 InterviewEndedEvent； evictExpiredPausedSessions 自己 logicalSessions.remove() + 发事件； evictExpiredPausedInterviews（DB 兜底）刻意不发事件（有理由，但正是"每个路径各自决定"的体现）。
  • 登记与移除不对称：逻辑会话登记有 3 个分支（新会话/重建态/不登记），移除有 2 处，各有条件。

结论：原则写在文档里，代码里仍是"每条退出路径各自拼一遍收尾"。新增输入源或新端点时，这里最容易漏。

4.5 测试覆盖的不对称（最需要正视的一点）

本模块测试其实是全仓最厚的：AudioStreamingServiceTest（32 个用例）、LogicalSessionRebuilderTest（14）、 AudioStreamSessionHeartbeatTest（6）、AudioStreamingWebSocketIntegrationTest（6）、RealtimePropertiesTest（4），合计约 62 个。

但盲区恰好落在最常改、最该动的地方：

块覆盖
注册表 / 恢复 / 心跳判据 / 暂停回收✅ 覆盖较好
ASR 消费循环与重连预算❌ 无（依赖豆包客户端）
回合流水线（LLM 交互、上下文裁剪、落库顺序）❌ 无
计费调度器的三条判据❌ 无

→ 含义：§6 的 P0-1 / P0-2 正好落进盲区，所以 P0-0（测试接缝与行为基线）是它们的前置条件 —— 先给 DoubaoAsrClient 与 LLM 客户端做注入点 + fake，把两组不变量测试按现状跑绿，再开始抽取； 否则拆完只是"看起来没坏"。

6. 拆解清单

原则：每项都是行为等价的机械重构，独立提交、独立可回滚、不夹带新功能。

完成定义（每项都适用）：代码抽取完成 + 行为基线测试通过 + 原链路集成测试通过。 没有测试就不算完成 —— 机械抽取不等于低风险：ASR 回调 → 会话状态 → 回合 → 计费 → WebSocket 推送 之间存在隐式时序，只有测试能证明它没变。

P0-0 测试接缝与行为基线（先做，是 P0-1 / P0-2 的前置条件）

进度：已落地（2026-09-22）。 注入点用两个工厂接口实现（AsrClientFactory / LlmClientFactory， 默认走豆包实现，放在 AudioStreamSessionDependencies 上），测试脚手架为 AudioStreamSessionTestHarness，两组基线共 7 个用例（AudioStreamSessionAsrBaselineTest 3 个、 AudioStreamSessionTurnBaselineTest 4 个）。

验证结果：71 个测试全绿 = realtime 单元测试 63（含新增 7）+ WebSocket 端到端集成 5 + 计费集成 3。 端到端集成测试需要本地存在 pass_up_test 库（application-test.yml 指向它；库不存在会以 「上下文加载失败」的形式报错，表现为 5 个 Error，与本类改动无关）： docker exec postgres psql -U postgres -c "CREATE DATABASE pass_up_test ENCODING 'UTF8' TEMPLATE template0"。

不是"补覆盖率"，而是先把现状钉住：

  1. 注入点：DoubaoAsrClient（工厂或接口）、LLM 客户端（现在每轮 new DoubaoLlmClient，加一个 LlmClientFactory 即可 fake）。

  2. 不变量测试（两组，分别对应 P0-1 / P0-2 的抽取对象）：

    ASR     ready × reconnect → startBilling 只能一次
        reconnect         → 残留音频 = 0
        new ASR           → asrId != 旧 asrId

回合     final text → 恰好一轮 LLM
        非 final   → 零轮
        空 final   → 零轮

  3. 这两组测试先在现有实现上跑绿（即把现状钉住），再开始抽取。

cleanup 的基线不在这一步：它对应 P1-1 的收敛对象，放在 P1-1 一起做（见该节「行为基线」）。 这样划分是为了让"测试接缝"只服务于它真正要保护的那两次抽取，不提前把 P1 的对象拉进来。

P0-1 抽 AsrStreamRunner：ASR Runtime

进度：已落地（2026-09-22）。 产出 AsrStreamRunner + AsrEvent（sealed：Ready / Transcript / Ended / Unavailable）

  • AsrEventHandler；会话侧改为 onAsrEvent(...) 消费事件，stop() 由 markPaused() / onClose() 显式调用 （不再让运行期去读会话的 paused / WebSocket 状态）。 判据已核验：会话里不再出现重连 / 退避 / asrId / 残留帧（812 → 676 行）； 验收 = P0-0 的 7 个基线 + 64 个既有单元/集成测试，共 71 个全绿。

  • 职责一句话：从「收到音频字节」到「产出 ASR 事件」，含连接重建。

  • 对外只有三个动作 + 一个事件入口：

    interface AsrEventHandler { void onEvent(AsrEvent event); }
// AsrReady / AsrFinalText / AsrSessionEnded / AsrSessionError

class AsrStreamRunner {
    void start();
    void submitAudio(byte[] chunk);
    void stop();
}

    修订（原方案留了 onReady / onText / onEnd / onError 四个回调）：统一成一个事件入口。 四个回调在第二个使用点（/ws/asr）就会立刻分叉 —— 换 API 比换一个 handler 实现贵得多。

  • 判据：抽取完成后，AudioStreamSession 不应再出现重连、退避、asrId、残留帧这些概念。

  • 搬走：consumeLoop、pumpAudio、AsrRun、reconnectBackoffMillis、dropStaleAudio、shouldStopRetrying、lastAsrId 轮换、asrUnavailable。

  • 附带收益：V2 的 /ws/asr 识别通道复用同一个 runner（V2 方案 §4.2.1 的依赖项）。

  • 验收：P0-0 的 ASR 组 + 集成测试 + 手工弱网回归（断网 / 杀连接后自动恢复）。

P0-2 抽 ConversationTurnRunner：一个输入 = 一个回合

进度：已落地（2026-09-22）。 产出 ConversationTurnRunner（submit(UserTurnInput) / submitOpening() / cancel() + TurnOutbound 输出口）；会话侧只剩「输入源适配 + 下发」，context / MAX_CONTEXT / 上下文裁剪 / LLM 客户端 / 持久化调用全部移出（LogicalSessionRebuilder 的窗口引用同步改到 ConversationTurnRunner#MAX_CONTEXT）。 判据已核验：会话里不再出现 buildMessages / trimContext / MAX_CONTEXT / streamChat / saveUserMessage（812 → 550 行）；71 个单元 / 集成测试全绿，并通过真实端到端冒烟 11/11。

  • 职责一句话：一个输入，执行一个完整回合。

P1-1 关闭路径收敛：cleanup(reason) 的边界

进度：已落地（2026-09-22）。 落法不是"抽一个新类"，而是把收尾抽成两个函数：

入口职责调用方
cleanup(session, reason)唯一收尾入口（幂等）：摘除物理连接（幂等的锚点）→ AudioStreamSession#onClose() → 已结束则摘除逻辑会话Spring 关闭回调；心跳踢出 / 主动关闭后的兜底
requestClose(session, reason, status, notice)唯一退出出口：按需同步发通知 → 关闭传输层。不做收尾（收尾统一走回调）7 条路径全部改调它

7 条路径改写后各自只剩一行：顶号 / 传输层错误 / 计费终止 / 心跳踢出 / ASR 自然结束 / ASR 不可用 / 用户暂停。 新退出路径只需给出 CleanupReason + 关闭码 +（可选）通知。新增 CleanupReason（lifecycle 包）， 与 InterviewEndReason 刻意分开：连接退出 ≠ 面试结束（暂停、顶号、心跳踢出都只退出连接）。

幂等的锚点是「注册表摘除成功者唯一」：cleanup 里 removeConnection 返回 null 即直接返回， 于是 session.onClose() 至多执行一次 → InterviewEndedEvent 至多一条 → 停计费至多一次（§10 第 8 条）。 心跳踢出的「兜底补一刀」因此天然安全，不必再自己防重。

刻意保持现状项（累计，都已写进代码注释）：

  1. 心跳踢出的宽限期仍是「先关连接、等 1.5 秒再兜底收尾」—— 于是"给前端留时间把残存数据发完"这个初衷 其实没落到实处（连接那时已经关了）。改成「先等宽限、再关闭」是行为变更，需单独决策。
  2. 通知的发送方式按路径区分：ASR 不可用走同步写（保证"先收到原因、再收到关闭帧"，与握手错误一致）； 心跳踢出走会话发送队列（扫描线程与发送线程并发写同一 socket 会交错）。
  3. 结束原因的映射口径（P1-2）：现在只有 ASR 故障记 ASR_ERROR，心跳超时 / 计费终止 / 顶号都记 USER_ENDED。 ✅ 已收口（2026-09-23）：新增 DISCONNECTED（心跳超时·顶号·传输错误），并把 BILLING_TERMINATED 拆成 BILLING_EXHAUSTED / BILLING_ERROR （后者映射到此前空置的 SYSTEM_ERROR）—— 拆而非改名，因为 InterviewBillingScheduler#terminateSession 本来就有"余额耗尽"与"计费异常"两个调用点。 映射表见《模拟面试第二版》§8 P0-2，单测 AudioStreamSessionEndReasonTest 钉住。 历史数据不回溯，报表按发布日分界。

测试（§10 第 8 条基线落地）：

  • cleanup：重复调用只收尾一次；逻辑会话未结束 → 保留（暂停可重连）、已结束 → 摘除；未知连接静默跳过。
  • 心跳踢出 3 个用例：失联 → 通知（走队列）+ 请求关闭 + 宽限后兜底收尾（用 Mockito timeout(3000) 等异步结果）； 存活不踢；已标记踢出不重复踢。这条路径冒烟脚本覆盖不到（脚本一直发心跳、永远不会被判失联），只能靠单测锁住。
  • 合计 89 个用例全绿（82 → 89），真实端到端冒烟仍 11/11（本次主代码改动后未复跑的必要性见 §10）。

本阶段只收敛「物理连接退出」：evictExpiredPausedSessions（暂停超时 → 终结逻辑会话）与 evictExpiredPausedInterviews（DB 兜底）刻意不进 cleanup —— 它们没有物理连接要收， 属于"面试为什么结束"的判定（各有其既有理由，见 §4.4）。 这正是上面那句"定义收窄"的含义：cleanup 不被拉成万能方法。

定义收窄为：物理连接退出的唯一收尾入口，而不是"所有会话结束都要调它"。

7 个物理连接退出入口
        ↓
cleanup(connection, reason)     ← 连接资源收敛 + 注册表移除（幂等）
        ↓
   逻辑会话是否结束？
     ├─ 否 → pause（保留 TTL 待重连）
     └─ 是 → ended（发 Ended 事件）

  • cleanup 不做"面试是否结束"的判断 —— 那是逻辑生命周期（pause / resume / end）的事。 两者一旦混在一起，cleanup 就会变成万能方法，把"连接关闭"和"面试结束"再次搅在一起。

  • 心跳踢出的"发错误 + 宽限期"变成 cleanup 的参数（如 gracefulNotice(code, message, graceMillis)）， 而不是每条退出路径各写一遍 —— 这正是 §4.4 里 7 个入口时序不一致的根因。

  • 验收：前一篇原则一在结构上成立；新增一条退出路径不再复制收尾代码。

  • 行为基线（本阶段落地为测试）：

    cleanup() × N    → remove 只一次
                 → Ended 事件只一次
                 → 停计费只一次

非当前连接的事件  → 不影响活跃连接与逻辑会话（见 P1-3 的"迟到事件"场景）

    这组基线归 P1-1 而不归 P0-0：P0-0 只保护 P0-1 / P0-2 那两次抽取， 而 cleanup 是本阶段才收敛的对象，测试与重构同批交付更清晰。

P1-2 生命周期不变量结构化

进度：已落地（2026-09-22）。 四项逐条：

项落地
① 构造器无副作用new AudioStreamSession(...) 只赋字段 + 建两个 runner；不再 markActive / bindConnection / submit(sendLoop) / asrRunner.start() / publishResumed()
② start() 是启动事务边界start()：重连 → markActive + bindConnection → submit(sendLoop) → asrRunner.start() → publishResumed()；任一步失败 → rollbackStart() → 继续抛
③ 退出原因统一删掉 asrUnavailable 布尔，改为会话上的 exitReason（CleanupReason）：requestClose 时记录、收尾时由 onClose(reason) 消费
④ 两类原因不混用CleanupReason（连接为什么退出）经 toEndReason(reason) 唯一一次映射为 InterviewEndReason（面试为什么结束）

③ 的关键点：退出原因必须在请求关闭时记到会话上。因为收尾走的是容器关闭回调， 回调只带"连接断了"（CONNECTION_CLOSED），真实原因（ASR 故障 / 暂停 / 顶号 / 计费终止）会丢 —— 原先那个 asrUnavailable 布尔正是为了跨过这次回调。现在换成通用的 exitReason，任何退出路径都能带上原因。

③ 与 ④ 的口径冲突（已按 ④ 处理）：任务描述里"InterviewEndReason 扩展为 CleanupReason"与 "两类原因不混用"互相矛盾。落地为两个枚举都保留：CleanupReason 是入参（连接维度）， InterviewEndReason 是出参（面试维度），中间只在一处映射。 映射现状刻意不变：只有 ASR 故障记 ASR_ERROR，心跳超时 / 计费终止 / 顶号仍记 USER_ENDED （改它会动到已落库的统计口径）—— 见待确认项。

回滚责任转移：rollbackStart() 就地把逻辑会话恢复成"未启动"的样子（重连 → PAUSED 并解绑连接； 新会话 → 标记 ENDED），因为不这么做就会留下「无物理连接的 ACTIVE」僵尸（心跳扫描扫不到、暂停回收又不认它）。 AudioStreamingService 因此不再手工 resumeState.markPaused()，只保留新会话失败时的 endInterview（DB 不归会话管）。 另外「面试开始」事件仍在 ASR 就绪时发（handleAsrReady），本次没动 —— 计费起算点必须与"识别真的可用"对齐。

  • AudioStreamingServiceTest：原「重连失败退回 PAUSED」用例改为断言服务侧剩余责任（不登记连接、不结束 DB 记录）； 新增「新会话启动失败 → 结束 DB 记录」。

P1-3 组合场景测试（长尾）

进度：已落地（2026-09-22），并且这一步抓到了真 bug。

场景 2（旧连接迟到事件）不是"补个测试就好" —— 写出来立刻暴露出： AudioStreamSession#onClose 对共享的逻辑会话是无条件写状态的，于是 「A 掉线（无 PAUSE）→ 客户端带 resume 重连成 B → A 的收尾才到达」这条时序下， A 的收尾会把 B 正在进行的面试结束掉：状态标记 ENDED → 发 InterviewEndedEvent （→ 停计费 + 结束面试记录），上层随后还把逻辑会话摘出注册表 —— 计费扫描从此找不到它，表现为"面试还在跑、时长却不扣了"。这是既有 bug，与本次重构无关。

防护（已落地）：onClose(reason) 先 releaseResources()（只收敛本连接资源），然后两道早退：

  1. 逻辑会话已 ENDED → 直接返回（不重复发结束事件，§10.8 的第二道防线）；
  2. state.getCurrentConnectionId() 非空且 ≠ 本连接 → 迟到收尾，只清自己的资源，绝不碰逻辑会话。 （暂停态 currentConnectionId 为 null，因此正常暂停收尾不会被误判成迟到 ✓ 冒烟已实测。）

测试（新增 AudioStreamSessionLongTailTest，真实会话 + fake ASR）：

  • 重复收尾_Ended事件只发一次：端点重复回调 / 兜底补刀也不能重复发事件（否则重复停计费、重复结束记录）；
  • 迟到收尾_已被新连接接替_不影响逻辑会话：不得结束面试、不得改暂停、不得解绑新连接、不得发结束事件；
  • 暂停收尾_保留逻辑会话并发暂停事件：暂停的正例（反向保证第 2 条不会误伤暂停路径）。

合计 97 个用例全绿（94 → 97），真实端到端冒烟 11/11。

尚未覆盖（留作后续）：

  • 场景 1 的"真并发"（暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出同刻发生）目前只覆盖了确定性交错 （迟到收尾 / 重复收尾），没有多线程随机交错压测 —— 随机交错容易产出偶发红灯，价值不如确定性用例； 如需补，建议用 AudioStreamSessionTestHarness#blockAsrClientClose 构造确定性窗口，而不是加 sleep。
  • 场景 3（异步落库丢失窗口）未做：InterviewAsyncService 的 @PreDestroy 有 30 秒排空等待， 可以补一条"shutdown 会等待在途落库任务"的用例，但那是"进程优雅退出"的语义，与本次长尾关系较远。

P0-0 / P1-1 锁的是单点不变量，这里补组合：

  1. 暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出并发。

  2. 旧连接迟到事件不得影响新连接（前一篇 §4 原则三的强化版，比"旧 onClose 晚于新连接建立"更具体）：

    旧连接 A 断开 → 新连接 B 建立并成为 active → A 的 onClose / ASR error / cleanup 才到达
     ↓
允许：只清理 A 自身（A 的资源、A 在注册表中的条目）
禁止：移除 B / 结束逻辑会话 / 停掉 B 的计费 / 清掉 B 的注册表条目

    这是最容易"看起来修好了、实际偶发踩中"的一类竞态，必须用测试钉住。

  3. 异步落库丢失窗口（前一篇 §7 假设 5）。

P2-1 命名与文档对齐

Audio* → Interview*（路径 /ws/audio 不动，两个前端都写死了）；AGENTS.md §3.6 / §6.5.4 / §8.6 与代码同步； 两端错误码白名单补齐（protocol.ts、ws.ts）。

归属前一篇、尚未落地的提案

§8 的 BillingStateProjection（状态机成为写计费的唯一入口）： 代码里没有这个类，属"提案未落地"。是否做、何时做由计费侧决定；若做，与本文 P1-2 有交集 （都指向"状态迁移成为唯一写入口"）。

7. 与 V2 的关系（顺序）

按 ①~⑨ 串行实施（⑤~⑧ 可与 V2 并行）：

① P0-0  测试接缝 + 行为基线（ASR fake / LLM fake）
② P0-1  AsrStreamRunner
③ P0-2  ConversationTurnRunner
④ P0-4  connectionId / logicalSessionId
        ★ V2 门槛到此满足（+ 原链路集成测试通过）→ 可以开始 V2，不必等 ⑤~⑧
⑤ P0-3  SessionRegistry（只做查询 / 判据）
⑥ P1-1  物理连接 cleanup 收敛
⑦ P1-2  生命周期不变量结构化
⑧ P1-3  长尾组合场景
⑨ V2    input=text → /ws/asr（可与 ⑤~⑧ 并行）

  • V2 要加的两个入口正好是这次抽象的验收用例：

    ASR final ──┐
            ├─→ ConversationTurnRunner
TEXT answer ┘

/ws/audio ──┐
            ├─→ AsrStreamRunner
/ws/asr   ──┘

    如果这两个入口接不进去，说明抽象不对 —— 这也是"先拆后加"的真正价值。

  • 不需要等所有 P1 才做 V2：门槛是 —— P0-0 基线绿 + P0-1 / P0-2 抽取完成且原链路集成测试通过 + P0-4 合并。 达到这个门槛，V2 就已不会继续污染 AudioStreamSession。

    • P0-3 尚未合并不阻塞 V2 步骤一（文本作答不碰注册表），但 V2 步骤二（新增 /ws/asr）之前建议完成。
    • P1-1 / P1-2 / P1-3 可与 V2 并行或排在其后。

  • 反过来先加分支的后果：if (audio) { … } else if (text) { … } 会继续落在最脆的地方， V2 之后这个类会到 900 行以上且无人敢动。

8. 拆解完成的结构性验收（不看行数）

AudioStreamSession 的目标形态

  • 只应出现：WebSocket 输入输出、连接生命周期协调、InterviewSessionState 引用、少量编排。

    措辞用「协调」而不是「连接生命周期」：P1-1 之后真正的 close / cleanup / 注册表移除应收敛到统一入口， 会话本身只负责"触发并协调"，不负责自己再实现一遍收尾。

  • 不应出现：DoubaoAsrClient、重连 / 退避 / 残留帧、LLM 客户端、上下文裁剪、计费调度、清理细节。

AudioStreamingService 的目标形态

  • 只应出现：连接建立、连接注册、恢复协调、生命周期协调。
  • 不应出现：ASR runtime、回合执行、心跳判据细节。

拆解的目标是「变化边界」，不是「代码变短」

这份方案的核心不是把 812 行拆成几个小类，而是把实时链路后续演进的变化方向固定下来：

拆解不是为了减少代码行数，而是为了建立稳定的变化边界：

变化约束
输入源变化（新增一种"用户输入"）不修改 AsrStreamRunner
识别通道变化（/ws/audio ↔ /ws/asr）不复制 AsrStreamRunner
回合输入变化（ASR final / TEXT answer / 首问 / 未来的"重新生成"）不复制 ConversationTurnRunner
连接退出路径变化（新增一种断开原因）只能进入统一 cleanup，不再新增收尾入口

落到日常开发，就是一句可操作的对照：

新输入      → 找输入适配点
新识别通道  → 复用 ASR Runner
新回合输入  → 复用 Turn Runner
新退出路径  → 进入统一 cleanup
新连接状态  → 不直接碰外围注册表

行数只是副产品（预计 AudioStreamSession 回落到 300~400 行），不是目标本身。

9. 明确不做的事

  • 不重写实时链路、不引入 Actor / 响应式框架：现有约 62 个用例是资产，重写等于清零。
  • 不把实时热路径事件化：沿用前一篇 §3 的边界 —— 实时流处理（音频 / ASR token / LLM token）直接调用， 只有业务生命周期（Started / Paused / Resumed / Ended）才走领域事件。本次不扩大领域事件的范围。
  • 不为 V2 新写一套会话实现（代价见 V2 方案 §10.2）。
  • 不做一次性大重构：每项独立提交、独立回滚，P0 与 P1 之间不留长分支。
  • 不在这些类上继续叠"顺手写的"新能力：新能力先找落脚点（runner / handler），找不到就先设计。
  • 不再新增 Runner / Manager / Context / Projection 这类抽象：本清单写明的抽取对象就是全部， 实施过程中不得临时"顺手再抽一个" —— 这是本次重构最大的风险（换文件名 ≠ 降复杂度）。

本次实施要守住的一句话：先把已经存在的变化边界拆出来，而不是提前为未来所有可能的变化设计架构。 与项目整体"实用主义 DDD、不过度设计"的方向一致。

10. 拆解完成的行为基线

真实验证入口：pass-up.backend/tools/realtime-session-smoke.mjs（零依赖 Node 脚本）—— 登录 → 取 WS 凭证 → /ws/audio 建连(MOCK) → 心跳 + 静音音频上行 → 面试官首问 → 跨 70 秒验证「音频不是心跳」的严格判据 → PAUSE → resume 重连（校验不重复首问）→ 结束，共 11 条断言。 P0-2 落地后实测 11/11 通过；P0-4 后复测同样 11/11 通过（含 resume 重连与计费恢复）。 P0-3 后复测仍 11/11 通过 —— 注册表抽取对上面这些行为是等价的。 P1-1 后复测仍 11/11 通过；第 8 条（清理幂等）由 7 个新单测锁住， 其中「心跳踢出」这条冒烟够不到的路径（脚本一直发心跳）也一并覆盖。 P1-2 后复测仍 11/11 通过（启动路径改成"构造 + start() 事务"后，首问 / 恢复 / 计费起算全在）。 DB 侧 interview 记录为 ended、首问消息已落库。

⚠️ 跑冒烟前先看测试账号余额：脚本每轮会真实消耗 admin(user 1) 约 85 秒「面试时长」， 连跑几轮就会扣到 0，表现为跑到一半收到 BALANCE_EXHAUSTED 并以 1008 关闭 —— 那不是回归。 充值（dev 库在 docker 里）：

docker exec -e PGPASSWORD=123456 -i postgres psql -U postgres -d pass_up_dev \
  -c "UPDATE user_asset SET balance = 3600, updated_at = now()
      WHERE user_id = 1 AND asset_type = 'INTERVIEW_SECONDS';"

这些基线会分批落成测试（不留在文档里）：第 1~3 条随 P0-0，第 4~7 条由既有测试与集成测试覆盖，第 8 条随 P1-1。

  1. ASR final → 一次 LLM 回合；非 final 与空文本不触发。
  2. MOCK 首问只发一次；计费起算只发一次（重连、暂停恢复都不重复）。
  3. ASR 中断自动重建：退避 500ms → 1s → 2s、最多 3 次、单连接存活 ≥30s 重置预算；重连前丢弃残留音频并轮换 asrId。
  4. 暂停 → 保留逻辑会话 15 分钟；恢复时复用 systemPrompt / 上下文 / interviewId，不重复开场。
  5. 心跳判据：发过心跳的客户端 60 秒，老客户端音频 5 分钟；计费与心跳共用同一判据来源。
  6. 余额耗尽 → 下发 BALANCE_EXHAUSTED + 停计费 + 关连接；顶号 → 旧连接以 POLICY_VIOLATION 关闭。
  7. 端到端：PC 正式面试（会议音频）与小程序模拟面试各跑通一次完整流程（含暂停 / 继续）。
  8. 清理幂等：同一次会话的 remove / Ended 事件 / 停计费各只发生一次。

工作量参考：P0 四项以「移动 + 新接口」为主、净增代码少，但风险不在代码量（隐式时序）， 主要成本在 P0-0 的测试接缝与 P1-1 的幂等验证。没有测试就不算完成。
