面试体验模板-预置场景与快照固化方案

面试体验模板：预置场景与快照固化方案

定稿方案（2026-09-16）。目的：让新用户零上传、零等待直接进入一场有质量的 AI 模拟面试。

1. 要解决的问题

新用户进入模拟面试的现状链路是：

上传简历 → MinIO → Python AI 解析（10~30s）→ resume_parse_result

而模拟面试能否"有质量"，取决于建连时后端能取到多少上下文——只有两个输入：

输入来源缺失后果
简历 JSONresume_parse_result.raw_json面试官无料可问，只能泛泛提问
岗位 JDapp_user.current_target_position_id → target_position提问方向与用户预期不匹配

所以冷启动有三个硬伤：慢（10~30s）、贵（每次调用 AI）、不稳（依赖外部解析服务）。

结论：模板的本质不是"一份简历样本"，而是一条绕过 AI 解析、直接产出面试上下文的种子数据通道。

2. 核心原则（定死）

体验模板不属于用户、不进入 resume、不参与 onboarding、不产生用户简历数据；它只是 PassUp 内置的 AI 面试输入。开始面试时把模板内容固化为 Interview 快照，之后整个面试生命周期只依赖快照。

三条由此推出的硬约束：

  1. 模板是"可变配置"，快照是"不可变事实"。 这是整个方案的基石。
  2. 前端只能传 templateUid，绝不能传 resumeJson / jobContextJson。 与「角色由后端配置、前端只传枚举」的反提示词注入原则一致。
  3. 模板只作用于面试链路（/ws/audio）。QnaService#buildSystemPrompt 同样读取默认简历，但模板不落库，因此 QnA 场景下用户仍是"无简历"状态——这是有意为之，不是缺陷。

4. 关键设计决策

决策采纳理由
模板不落 resume 表✅面试链路对简历的唯一消费点是两个字符串；interview 表不引用简历任何字段；面试历史不展示简历
模板存储用 DB✅需后台可编辑
Registry 接口隔离来源✅后台化只换实现，主链路不动
prepare 阶段固化快照✅消灭 30 秒竞态窗口，职责更干净
握手阶段不再读模板✅握手只认 Interview，不再依赖可变配置
所有面试统一经 prepare 创建 PENDING✅模板与真实简历共用一条创建路径与生命周期；顺带修复"HTTP 侧选简历、WS 侧取默认简历"的不一致
重连走独立的轻量 ticket✅重连必须复用原 Interview 与快照，不能再创建 PENDING
允许 handshake 报 TEMPLATE_UNAVAILABLE❌该错误场景本身被 prepare 固化消灭，不需要
模板版本表 / 变更日志❌快照已解决"历史可重现"，无需为追溯建版本体系
物理删除模板❌改为归档，避免历史引用悬空
模板缓存（Redis/TTL）❌模板数量 5~20，每次查一次主键即可，缓存只会引入一致性问题
审计做到 created_by/updated_by✅第一阶段够用，完整审计待运营需求明确后再加

4.1 关于"快照与版本管理"的精确表述

快照不是模板版本管理的替代品，而是"面试历史可重现"的解决方案。

机制回答的问题
Snapshot这场面试当时 AI 到底看到了什么？
Template Version / Audit这个模板历史上改过什么？谁改的？能不能回滚？

当前阶段前者明显更重要。快照的作用是让"是否需要版本管理"不再紧急，而不是取代它。后台运营将来真的需要回滚时，再加 experience_template_change_log 即可。

5. 数据模型

5.1 experience_template（新建）

CREATE TABLE experience_template (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uid              VARCHAR(64)  NOT NULL UNIQUE,   -- ULID，对外标识（与项目其他业务对象一致）
    name             VARCHAR(100) NOT NULL,
    tag              VARCHAR(50),
    direction        VARCHAR(50),                    -- BACKEND / FRONTEND / ALGORITHM ...
    experience_years INTEGER,
    description      VARCHAR(500),                   -- 前台卡片展示文案
    resume_json      JSONB        NOT NULL,          -- 与 ResumeInfo 同构
    job_context_json JSONB        NOT NULL,          -- 与 InterviewContext.jobContextJson 同构
    status           VARCHAR(20)  NOT NULL,          -- DRAFT / PUBLISHED / ARCHIVED
    sort_order       INTEGER      NOT NULL DEFAULT 0,
    created_by       BIGINT,
    updated_by       BIGINT,
    created_at       TIMESTAMPTZ  NOT NULL,
    updated_at       TIMESTAMPTZ  NOT NULL,

    CONSTRAINT chk_experience_template_status
        CHECK (status IN ('DRAFT', 'PUBLISHED', 'ARCHIVED'))
);

CREATE INDEX idx_experience_template_status_sort
    ON experience_template (status, sort_order);

为什么用 job_context_json 而不是 position_title + position_jd 两列：

  • 与 InterviewContext.jobContextJson 结构统一，避免"表结构"和"上下文结构"两套；
  • 岗位未来若扩展 company / requirements / responsibilities，不需要改表。

5.2 interview（扩展）

-- 快照（本次核心）
ALTER TABLE interview ADD COLUMN resume_snapshot_json JSONB;
ALTER TABLE interview ADD COLUMN job_snapshot_json    JSONB;
ALTER TABLE interview ADD COLUMN created_at           TIMESTAMPTZ;

-- 面试参数（原为 WebSocket query 参数，统一到 prepare 后必须随 Interview 落库）
ALTER TABLE interview ADD COLUMN language        VARCHAR(10);
ALTER TABLE interview ADD COLUMN detail_level    VARCHAR(20);
ALTER TABLE interview ADD COLUMN interview_style VARCHAR(20);

COMMENT ON COLUMN interview.resume_snapshot_json
    IS '面试创建时固化的简历上下文（裁剪后，即 AI 实际看到的输入）';
COMMENT ON COLUMN interview.job_snapshot_json
    IS '面试创建时固化的岗位上下文';
COMMENT ON COLUMN interview.created_at
    IS '创建（prepare）时间，用于清理超时未建连的 pending 记录';
COMMENT ON COLUMN interview.language
    IS '面试语言：zh / en';
COMMENT ON COLUMN interview.detail_level
    IS '提问详细程度：short / medium / detailed';
COMMENT ON COLUMN interview.interview_style
    IS '面试风格，与 InterviewStyle 枚举对齐（STANDARD / PRESSURE）';

ALTER TABLE interview DROP CONSTRAINT IF EXISTS chk_interview_status;
ALTER TABLE interview ADD CONSTRAINT chk_interview_status
    CHECK (status IN ('pending', 'active', 'paused', 'ended'));

COMMENT ON COLUMN interview.status
    IS '会话状态 (pending/active/paused/ended)';

三个必须注意的点：

  1. created_at 是必需的，不是锦上添花。 V5 建表时 interview 只有 start_time / end_time，而 prepare 创建的 PENDING 记录 start_time 为空，没有 created_at 就无法按时间清理孤儿记录。
  2. chk_interview_status 必须 DROP 后重建。 V15 已定义 ('active','paused','ended')，直接插入 pending 会被约束拒绝。
  3. language / detail_level / interview_style 三列是统一到 prepare 后新暴露的缺口。 这三项原本从 WebSocket query 参数读取，interview 表里没有对应列。一旦 Interview 在 prepare 时创建、握手时只认 Interview，这三项就必须落库——否则握手（以及重连）无源可取。

5.3 快照存"裁剪后的内容"而非解析原文

InterviewContext.resumeJson 存放的不是 resume_parse_result.raw_json，而是已经过裁剪管线的内容：

rawResumeJson ──→ ResumeContextBuilder#buildBoundedJson ──→ InterviewContext.resumeJson
                   （按 realtime.resume-context.* 裁剪）

所以快照必须固化裁剪后的内容，理由：

  • AI 从未看到过完整原文，它看到的就是裁剪后的有限上下文——这才符合"事实快照"的语义；
  • 天然有界（受 ResumeContextPolicy 约束），不会让 interview 表无界膨胀；
  • 完整性不丢：真实简历的 rawJson 本身就在 resume_parse_result 里；
  • job_snapshot_json 的 JD 来自 target_position.description（TEXT，无长度约束），写入时需做一次长度兜底截断。

6. 接口设计

6.1 prepare 承担"创建面试"职责

POST /api/interviews/prepare
{
    "templateUid": "01j...",        // 可选：不传则走用户真实简历
    "resumeId": 12,                 // 可选（真实简历路径）：不传则用默认简历
    "targetPositionUid": "01j...",  // 可选：不传则用 current_target_position_id
    "mode": "MOCK",                 // ASSIST / MOCK
    "language": "zh",
    "detailLevel": "medium",
    "interviewStyle": "STANDARD"
}

内部流程：

1. 解析上下文来源
   ├── templateUid 存在? → Registry.getPublished(uid)
   │                       ├── 不存在 / 非 PUBLISHED → TEMPLATE_NOT_FOUND
   │                       └── 命中 → resumeJson / jobContextJson
   └── 无 templateUid   → 真实简历路径
                          ├── resumeId 指定? 否则 resolveDefaultResume(userId)
                          ├── targetPositionUid 指定? 否则 current_target_position_id
                          └── 简历与岗位皆空 → EMPTY_CONTEXT

2. ResumeContextBuilder 统一裁剪（模板也必须过同一条管线）
3. 计费预检 billingService.canConsume(INTERVIEW_SECONDS) → 否则 INSUFFICIENT_BALANCE
4. 创建 Interview(status = pending, start_time = null, created_at = now())
   mode / language / detailLevel / interviewStyle 一并落库
5. 写入 resume_snapshot_json / job_snapshot_json
6. 生成 ticket，payload = { userId, interviewId }

6.1.1 统一后顺带修掉的一个既有缺陷

现有链路里，「用哪份简历」被决定了两次，且两处互不知情：

GET /api/resumes/interview-prepare    ← 前端据此让用户选择简历（BOUND / DEFAULT / candidates）
        ↓ 用户选 A 简历
WebSocket 建连
        ↓
AudioStreamingService#onOpen
        ↓
resumeService.getDefaultResumeJson(userId)   ← 又独立取了一次「默认简历」

也就是说，HTTP 侧用户选的简历与 WebSocket 实际使用的简历可能不是同一份。

统一到 prepare 后，简历在 prepare 时一次性确定（resumeId 传入或按默认解析）并与快照一起固化，该缺陷自然消除。原 GET /api/resumes/interview-prepare 的推荐能力（BOUND / DEFAULT / candidates）可以作为 prepare 的前置查询保留，但决策必须落在 prepare 的入参上。

返回：

{
  "ticket": "xxx",
  "interviewId": 88,
  "source": "TEMPLATE",
  "context": { "templateName": "Java 后端 3 年经验", "positionTitle": "Java 后端开发工程师" }
}

6.2 ticket payload

新建面试（由 POST /interviews/prepare 签发）：

{ "userId": 1001, "interviewId": 88 }

ticket 的职责收敛为：

证明"这个用户已经准备好进入这场面试"。

而不是"告诉 WebSocket 去重新寻找一次面试配置"。

同时不存 resumeJson：ticket 是凭证，不是数据通道；内容已在 interview 表里，握手时读库即可。

⚠️ 实现细节：RedisTemplate<String, Object> 的 value serializer 会把 DTO 反序列化成 LinkedHashMap。ticket value 必须显式用 JSON 字符串写入（复用 Jsons），消费侧显式解析，不可直接按 Long 强转。

6.2.1 重连不走 prepare（重要）

重连必须复用原 Interview 与快照，不能再创建 PENDING。 因此重连路径不经过 prepare，而是保留现有的轻量 ticket 接口：

新建：POST /api/interviews/prepare        → ticket { userId, interviewId }
重连：GET  /api/ws/ticket（保留）          → ticket { userId }   ← 仅凭证，不含 interviewId
      然后 /ws/audio?ticket=xxx&resume=<logicalSessionId>

握手侧因此必须新增一条校验：

必须满足「interviewId 存在」XOR「resume 参数存在」
├── 两者都有 → 拒绝（语义冲突）
└── 两者都无 → 拒绝（不知道该进入哪场面试）

这样 GET /api/ws/ticket 有了明确定位：重连专用凭证签发，而不是"另一个创建面试的入口"。

已知限制（既有，非本次引入）：logicalSessions 是 JVM 内存注册表，重连需落到同一实例。统一到 prepare 后，InterviewContext 已可从 interview 表（快照 + 参数列）完整重建，为将来做无粘性重连留下了空间，但本次不改。

6.3 前台 / 后台接口

侧接口说明
前台GET /api/experience-templates仅返回 PUBLISHED，卡片列表（不含完整正文）
前台POST /api/interviews/prepare唯一的新建面试入口：解析上下文 + 固化快照 + 签发 ticket
前台GET /api/ws/ticket保留，定位收窄为「重连专用凭证签发」（payload 仅 userId）
前台GET /api/resumes/interview-prepare保留为「简历推荐」查询，其结果作为 prepare 的入参来源；不再由它决定最终用哪份简历
后台GET/POST/PUT /api/admin/experience-templatesCRUD
后台POST /api/admin/experience-templates/{uid}/publish发布
后台POST /api/admin/experience-templates/{uid}/archive归档（不提供物理删除）
后台GET /api/admin/experience-templates/{uid}/preview返回裁剪后内容，供运营确认"AI 实际会看到什么"

        ↓ 生成

8. 错误码分层

prepare 阶段（HTTP）

TEMPLATE_NOT_FOUND       模板不存在
TEMPLATE_NOT_PUBLISHED   模板存在但非 PUBLISHED
EMPTY_CONTEXT            既无模板，也无真实简历/岗位
INSUFFICIENT_BALANCE     时长不足

handshake 阶段

只处理面试本身的问题：

MISSING_TICKET / INVALID_TICKET   已有
INSUFFICIENT_BALANCE              兜底（prepare 已预检）
INTERVIEW_NOT_FOUND               记录不存在
INTERVIEW_FORBIDDEN               interview.userId != ticket.userId
INTERVIEW_EXPIRED                 PENDING 超时已被回收
INTERVIEW_NOT_PENDING             新建场景下 Interview 已不是 pending（已被消费/已结束）
INVALID_HANDSHAKE_PARAMS          interviewId 与 resume 参数同时存在或同时缺失

不再关心：模板现在是否存在、是否还是 PUBLISHED。 那不是握手阶段该关心的事。

9. Interview 生命周期（本次调整的核心影响）

9.1 已定：所有面试统一经 prepare 创建 PENDING

模板与真实简历一律走 POST /interviews/prepare，Interview 只保留一条创建路径、一套生命周期语义。

pending ──(WebSocket 建连)──→ active ──→ paused ──→ active
   │                             │                    │
   │ 超时未建连                   │                    │
   ▼                             ▼                    ▼
删除                          ended                ended
时机状态迁移同时写入
prepare— → pendingcreated_at、快照、mode/language/detailLevel/interviewStyle
WebSocket onOpen（新建）pending → activestart_time、session_id（物理连接 ID）
暂停active → paused—
重连paused → activesession_id 刷新为新连接 ID
结束 / 暂停超时→ endedend_time

9.2 生命周期前移派生的 5 个问题

#问题对策
1孤儿 PENDING：用户 prepare 后从未建连① 补 created_at 列；② 复用 WsHeartbeatScheduler 定时清理超时 PENDING
2start_time 语义错位（列注释是"面试开始时间"，历史按它排序）prepare 时留空，转 active 时回填
3握手时 session_id 还不存在prepare 时为空，建连后回填物理连接 ID
4用户连点两次产生两条 PENDING新 prepare 时直接删除该用户所有 pending 记录（无消息、无副作用，与现有 endInterview 的"空会话即删"同构），旧 ticket 指向已删除记录 → 握手返回 INTERVIEW_NOT_FOUND，天然失效
5参数列缺失导致握手/重连无源可取V24 补齐 language / detail_level / interview_style（见 5.2）

好消息： 孤儿 PENDING 不会污染历史列表——findNonEmptyByUserIdOrderByStartTimeDesc 用 exists(interview_message) 过滤，无消息的 PENDING 天然不出现在前端。

9.3 附带收益：上下文可从 DB 完整重建

统一后，InterviewContext 的全部输入（快照 + 参数列 + mode）都在 interview 表中。这意味着逻辑会话的上下文不再唯一依赖 JVM 内存，为将来做无粘性重连、多实例水平扩展留出了空间（本次不改，logicalSessions 仍是内存注册表）。

10. 模板内容规范

模板是面试官提问的燃料，不是占位符。

  1. 结构必须填满：basic（含 jobTitle / experienceYears）、summary、skills、workExperiences、projectExperiences、educations 全非空。
  2. 每个项目要有"可追问的抓手"：具体技术选型 + 量化成果 + 个人职责（如"QPS 从 800 提升到 5000，P99 从 320ms 降到 90ms"），面试官才有得追。
  3. 按 ResumeContextPolicy 上限内书写：单条描述 ≤300 字、项目描述 ≤500 字、技能 ≤30 项。写到上限外会被静默截断，不如一开始就写紧凑。
  4. 规模控制：2 段工作经历 + 2~3 个项目 + 8~12 项技能，撑起 15~20 分钟面试，再长只增 token 成本。
  5. 严禁真实隐私与真实公司：虚构姓名、示例邮箱（*.example.com）、"某电商平台"式公司名。
  6. 简历技能栈必须与 JD 呼应：形成"JD 要求 X → 简历有 X → 面试官深挖 X"的正循环。
  7. 一个模板 = 一份简历 + 配套 JD 的完整场景：不要让前端自由组合简历与岗位——"Java 后端简历 × 算法岗 JD"会让提问非常怪异。
  8. 数量控制在 3~6 份：按方向 × 经验层级（java-backend-3y / frontend-2y / software-fresh）。
  9. 不要用模板区分"压力程度"或"语言"：二者已由 interviewStyle（STANDARD/PRESSURE）和 language 控制。模板管内容，风格管打法。

11. 校验与安全

11.1 保存期校验（后台化后的新安全边界）

模板在 classpath 时可以启动期校验、写错就启动失败。改为后台可编辑后，校验必须前移到 Admin 保存时，否则脏数据会直接流进正在等待的用户面试。

校验项说明
反序列化必须能解析为 ResumeInfo
必填结构basic.name 非空、至少 1 段工作经历、至少 1 个项目、job_context.title / jd 非空
长度上限与 ResumeContextPolicy 对齐
发布门槛未通过校验不允许 PUBLISHED

11.2 PII 检测（定位为"检测"，不是"保证"）

⚠️ 不要承诺"保证模板不含真实个人信息"。正则能拦 138xxxx8888 / x@example.com，拦不住"某某互联网公司 张经理"。

做法：

  • 服务端做常见 PII 模式检测，命中即告警/阻断；
  • 后台 UI 明确提示：模板仅允许使用虚构人物、虚构公司及脱敏数据；
  • 二者结合，比单纯依赖正则可靠。

11.3 反提示词注入

  • prepare 只接受 templateUid，绝不接受 resumeJson / jobContextJson；
  • 模板内容由后端受控数据源提供，前端无法注入任意 system prompt。

12. Seeder：classpath → DB

classpath JSON ──→ Seeder ──→ DB ──→ Registry ──→ InterviewContext

不是：

classpath JSON ──┐
                 ├──→ Registry     ← ❌ 会出现"到底谁是真相"
DB ──────────────┘

规则：

  1. Flyway 只建表；模板 JSON 留在 classpath 仅作为 seed 数据源；
  2. Seeder 只插不覆盖（按 uid 判存在）——否则发版会冲掉运营修改，且极难排查；
  3. 上线后 classpath JSON 不再参与运行时读取，这一点必须写进代码注释；
  4. 多实例并发执行 Seeder 由 UNIQUE(uid) 兜底，第一期不做分布式锁。

13. 风险与对策

风险对策
孤儿 PENDING 记录堆积created_at + 定时清理（复用 WsHeartbeatScheduler）
chk_interview_status 未更新导致插入失败V24 中 DROP 后重建，加入 pending
参数列缺失导致握手/重连无源可取V24 补齐 language / detail_level / interview_style
ticket value 反序列化成 LinkedHashMap显式 JSON 字符串读写，不依赖 RedisTemplate 对象序列化
ticket 被伪造指向他人 Interview握手校验 interview.userId == ticket.userId
重复 prepare 产生多条 PENDING新 prepare 先删除该用户所有 pending 记录，旧 ticket 自然失效
重连误走 prepare 导致重复创建面试重连不经过 prepare（见 6.2.1）；握手校验 interviewId 与 resume 互斥
握手时 Interview 已被消费（并发建连）INTERVIEW_NOT_PENDING
用户 prepare 后超过 30 秒才建连（ticket TTL）ticket 过期 → 前端重新 prepare；旧 PENDING 由定时清理回收
模板内容写坏直接影响新用户保存期强校验 + DRAFT 草稿态 + 预览接口
运营误传真实隐私数据PII 检测 + UI 提示 + 明确"仅虚构数据"
发版覆盖运营修改Seeder 只插不覆盖

14. 明确不做的事

  • 不建 resume / resume_parse_result / resume_parse_task 任何数据
  • 不碰 resume.source，不抽 ResumeMaterializer
  • 不改 completeOnboarding（体验路径独立于引导）
  • 不落 app_user.default_resume_id
  • 不做模板缓存
  • 不做模板版本表 / 完整变更审计
  • 不做 TEMPLATE_UNAVAILABLE 握手错误
  • 不保留第二条 Interview 创建路径（onOpen 不再新建面试记录）
  • 不改重连机制（仍走 resume + 内存逻辑会话，只是入口 ticket 收窄）
