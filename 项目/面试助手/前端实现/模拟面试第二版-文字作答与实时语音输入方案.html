1. 背景与目标

1.1 要解决的问题

V1 的整场音频上行（/ws/audio 二进制 PCM 帧）有三个连带成本：

问题说明
网络与稳定性每分钟约 60KB/s 的持续上行，网络抖动直接表现为卡顿、断连
用户表达成本必须「说完」才能被识别，思考型用户（面试做题思路）被迫在语音里组织语言
环境限制开会、办公室、图书馆等场景无法开口说话

V2 的目标：默认用文字作答，让「不愿/不便开口」的用户能完成整场模拟面试；语音只作为想偷懒时的快捷输入。

1.2 目标形态

  • 交互形态对齐 pages/ai-qa：气泡对话 + 底部输入区，用户发一条、AI 面试官回一条（流式）。
  • 输入框右侧一个话筒按钮：点击开始实时语音识别，识别文本实时写入输入框。
  • V1 的会话语义（一场面试、时长计费、面试记录、暂停恢复）不因形态变化而消失，接入时需继续满足（见 6.3）。

4. 页面设计

4.1 路由与入口

面试助手首页「步骤一：模拟面试」
  └─ /pages/mock-interview-setting/index            → 开始面试 → /pages/mock-interview/index     （V1，默认，行为不变）
  └─ /pages/mock-interview-setting/index?mode=text  → 开始面试 → /pages/mock-interview-v2/index  （V2）
  • 设置页用 useRouter().params.mode 判定形态，不传即 V1，因此现有入口完全不受影响。
  • V2 下不校验麦克风授权、也不显示「请先授权麦克风权限」的拦截提示：文字作答不需要麦克风，语音输入是可选项，权限在点话筒时才申请。
  • 入口是否切到 V2（甚至砍掉 V1）属产品决策，留待接口接入后再定，见第 9 节。

⚠️ ?mode=text 不是后端的 input=text —— 两者不能互相透传（接线时最容易踩的一处）：

含义取值归属
页面参数 ?mode=text（设置页 → 页面）选页面形态（V1 语音版 / V2 文字版）text / 不传前端路由
WS 建连参数 input=text选作答方式（起不起 ASR、收不收 ANSWER）audio / text后端会话
WS 建连参数 mode=mock选面试模式（AI 是面试官还是求职者）assist / mock后端会话

V2 建连是 mode=mock + input=text。若把页面的 mode=text 直接透传： 后端 InterviewMode.from('text') 会静默回退成 ASSIST，随后被 assist + text 组合校验拒掉 —— 表现为"建连就失败"，但根因是页面参数被当成了会话参数。

4.3 交互

操作行为
输入后点发送（或键盘回车）追加用户气泡 → 清空输入框 → 上传 ANSWER，AI 追问以 loading 气泡占位并逐字填充
发送后（AI 未回复完）输入框与发送按钮禁用（这是 TURN_BUSY 的语义要求，见 §6.1）；收到 LLM_REPLY.final 或 ERROR 后恢复
点话筒（空闲）申请麦克风权限 → 开始识别 → 按钮变红并出现状态条
点话筒（识别中）结束识别（stop），保留已识别文本；识别连接由 transport 在空闲 ~8 秒后自动释放
点发送（识别中）先停识别再发送（useSpeechInput 的 stop()）：输入框马上要清空，识别结果再写回来会变成"幽灵文字"（用户没说的话出现在空输入框里）
录音达到单次上限（180 秒，MAX_RECORDING_MS）录音由微信自动停止，明确提示「已到单次语音上限，可再点话筒继续说」，不能静默停止（否则用户会以为识别坏了）。界面上不显示已用时长（2026-09-24 决定：提示条只写"正在聆听…"，不拿数字分散注意力）
输入为空发送按钮置灰不可点；同时前端做长度拦截（上限 2000 字，后端会拒）
点「暂停」（进行中时出现在头部）先弹确认（暂停会取消在途回复、超 15 分钟面试就结束，值得挡一下）→ 同时立即停止语音输入（只停录音与推帧；识别通道由 transport 在空闲 ~8 秒后自行释放）→ 发 PAUSE → 收 PAUSED 后进入暂停态：输入区禁用、底部出现暂停条 + 「继续面试」，头部同一位置也由「暂停」变为「继续」；暂停不往对话流里补记录（暂停是状态，不是对话内容，状态栏已有提示）
点「继续面试」/ 头部「继续」（暂停态）两处等价，都是 handleResume；用 resume=<逻辑会话ID> 重连：复用原上下文与计费，不重发首问；超时或记录不可恢复 → RESUME_EXPIRED / RESUME_FORBIDDEN → 提示"暂停会话已失效，请重新开始面试"
点头部「结束」（红胶囊，与「暂停 / 继续」并列）断开连接 → 提示「面试已结束」→ 600ms 后跳转：用了通用模板进「体验完成」引导页，否则返回上一页（细节见 §6.3.3）；语音输入通道随之释放（terminated → dispose()，页面不手工调用）

5. 实时语音识别方案

5.1 分层

页面（mock-interview-v2）
  └─ useSpeechInput（features/speech/hooks）      ← 权限申请、识别文本与输入框的合并规则、卸载释放
       └─ SpeechRecognizer（features/speech）      ← 平台判定、录音采集、生命周期收尾、错误归一
            └─ AsrTransport（features/speech）     ← 【唯一待接入点】把 PCM 帧送出去、把文本收回来

接入识别服务只需要实现 AsrTransport 并在 createAsrTransport() 里换掉返回值，页面与 Hook 无需改动。

5.2 路线取舍（方案 A 已定稿，B 仅作历史备选）

维度方案 A：服务端流式 ASR（推荐）方案 B：微信同声传译插件 WechatSI
文本来源后端 ASR，前端推 PCM 帧、收识别文本插件内置识别，零后端
前端改动实现 AsrTransport（新通道，如 /ws/asr）页面配置声明插件 + 换 Hook 内部实现，AsrTransport 不再需要
跨端采集能力本来就仅微信端，与 A 相同仅微信端
额外成本后端需提供识别通道需在小程序后台添加插件、需用户授权该插件
与面试链路通道独立、资格挂靠：不产生面试计费、不触发 AI 回复；但必须有进行中的面试才能建连（后端方案 §4.2.5）完全独立
风险需要后端配合插件不可用/未授权时无法自愈，构建与运行都依赖后台配置

已定稿：正式方案是 A（服务端流式 ASR）。 方案 B（微信同声传译插件）不进入实现范围，仅作为历史备选保留上表： 它引入的是插件声明 + 后台配置 + 用户授权三层外部依赖，且会与既有 ASR 能力形成两套语音输入链路； 而后端方案 §3 已经做了同样的取舍（A / B / C 三选一，结论 A），并明确"识别不依赖任何第三方插件"。

A 的落地节奏：前端已经把通道抽象出来（AsrTransport 留桩）；后端 /ws/asr 也已交付 （2026-09-22，后端 Step 2：路由 + 轻量鉴权 + 并发/时长上限，复用 AsrStreamRunner）。 因此现在唯一缺的就是前端把 AsrTransport 的占位实现换成真实传输（协议见 §6.2）。

还有一条不推荐的取巧路线：复用现有 /ws/audio 的音频上行，只取回包的 ASR_RESULT 而忽略 LLM_REPLY。它会让每次语音输入都额外产生一场面试会话与时长消耗，且 AI 会同时抢答，仅在「后端支持纯识别模式」时才值得考虑。

5.3 识别文本写入输入框的规则

以「基准 + 草稿」两段式合并，保证边说边改不覆盖用户已输入的文字：

点话筒那一刻：base = 输入框当前内容，draft = ''
收到 final=false（流式中间态）：draft = 该片段        → 输入框 = base + draft
收到 final=true （定稿）      ：base = base + 片段，draft = '' → 输入框 = base
  • 中间态是覆盖而非追加，否则会出现「我我我想想」这类叠字。
  • 定稿后 base 才前进，因此连续说多句会依次追加，标点随服务端结果带回。
  • 用户手动输入的内容作为 base 起点保留，不会被识别结果清空。
  • value/onChange/onError 通过 ref 读取最新值，避免识别过程中每次结果触发重渲染而拿到旧闭包。

边界：识别过程中用户手动改字（补一条，否则会覆盖用户刚改的内容）

ASR 识别中 → 用户手动改了输入框 → 后续 ASR 中间结果到达
  • 规则：用户一旦手动编辑，就视为"用户接管输入" —— 把 base 重置为"用户编辑后的输入框内容"、 draft 清空；之后 ASR 结果继续按"中间态覆盖 draft / 定稿追加 base"处理， 不再回滚用户改过的内容。
  • 实现：onChange 里区分"程序写入"与"用户输入"（程序写入时置一次性标记）， 非程序触发的 onChange ⇒ base = 最新值; draft = ''。
  • 为什么必须定义：两段式只解决"边说边改"，没解决"人机同时改" —— 用户把 Redis 改成 Redis Cluster，下一个中间态会把改动吃掉。

5.4 跨端与降级

  • 实时帧回调（RecorderManager.onFrameRecorded）是小程序专属能力，H5/其他端无等价实现。
  • 识别器构造时即判定 process.env.TARO_ENV === 'weapp'，非微信端点话筒直接返回 UNSUPPORTED_PLATFORM，页面提示「当前端暂不支持实时语音识别，请手动输入」——输入框与发送链路不受影响。
  • 因此 V2 页面在 H5 端可用（只是不能语音输入），不违反跨端规范。

到达单次上限✅ 已实现（2026-09-23）：由 SpeechHandlers.onTimeout 给显式提示（「本次语音输入已结束，可再次点话筒继续」）：静默停止会被当成"识别坏了"

录音参数的官方依据（2026-09-24 核对微信开放文档 RecorderManager.start）：

  • duration 官方默认 60000、上限 600000（10 分钟） —— 原来的 60000 就是"官方默认值"， 现在的 180000 是产品口径（= 官方额度的 3/10），两者都不是"规则上限"；
  • frameSize（单位 KB）官方注明传入才会有帧回调，且暂仅支持 mp3 / pcm —— 所以 format: 'PCM' + frameSize: 4 不是可选优化，而是"实时识别"这条链路的硬前提；
  • sampleRate: 16000 配 encodeBitRate: 48000 落在官方「采样率 × 编码码率」合法区间 （16000 → 24000~96000）内；官方原文明确不合法的组合会导致录音失败 —— 改参数前先对表；
  • 两处端/版本限制留意：sampleRate PC 不支持（微信 PC 版跑小程序时录音参数未必完整支持）； 官方另有 audioMode: 'voiceRecognition'（基础库 3.17.3+，噪声抑制 + 自动增益）尚未启用， 若嘈杂环境识别率不理想可作为候选（需真机对比后再定）。

停止识别时不立即释放通道：流式识别常在停止后才吐出最后一段定稿文本，因此留一个约 8 秒的空闲窗口 （WsAsrTransport#stop() 的 IDLE_RELEASE_DELAY_MS）再断开，避免最后一句丢失。 但不能无限期保留（2026-09-24 更正）：后端 DoubaoAsrClient 有静音保活，挂着的豆包会话会继续按 音频时长计费 —— 原注释里"这条通道不计费、多留一会儿没有成本"是错的；后端另有 25 秒上游空闲兜底 （见后端方案 §4.2.4）。

Hook 对外是 { listening, toggle, stop }：toggle 给话筒按钮做"开 / 关"， stop 给「发送作答」这类必须停的场景调用 —— 它不做状态反转， 免得在竞态（刚点话筒、还在建连）时反而把识别开起来。

入参 enabled / terminated 是资源生命周期的唯一开关（2026-09-24 加，见 §6.2 的「生命周期收口」）： 页面只回答"现在还能不能录音"，不直接操作 WebSocket —— "什么时候真的断开连接"只由 hook 决定。

    四道闸门顺序：凭证 → 资格 → 并发 → 日配额（后端已写死）。三者的引导各不相同： 资格是"去开始面试"、并发是"先关掉旧连接"（可即时自救）、配额是"改用打字"（重试无用）—— 别合成一句提示。 4007 已进 transport.ts 的白名单与关闭码映射 —— 不登记的话它会落进"未知码 → ASR_UNAVAILABLE" 兜底，把「去开始面试」说成「改用打字」（同一份代码里那个兜底是从第一版就有的）。

  • 上行只发音频：这条通道没有心跳、没有控制指令（后端收到文本只记日志）； 连接存活由后端物理连接绝对上限兜底（session-max-duration-ms，300 秒，绝对墙钟、不重置）。 ⚠️ 两个概念别混（2026-09-24 明确）：单次回答允许说多久 = 前端录音上限（duration: MAX_RECORDING_MS，180 秒）； 连接能活多久 = 后端那个 300 秒（关系固定为「后端 = 前端 + 120 秒余量」）。后者只兜"客户端该关没关 / 连接悬挂"，正常路径由前端的 8 秒空闲释放先收掉。

后端侧对这条通道的禁区是硬约束（后端方案 §4.2.1）：/ws/asr 不接 SessionRegistry、 不走 requestClose / cleanup、不创建/修改 Interview、不计费、不落库、不触发 LLM； 自检句是「识别失败时会不会有人想动面试状态？」—— 答案是"不会"才没跑偏。 前端侧同构的一条：识别失败只提示"改用打字"，不要因此去动面试连接。

6.3 会话生命周期（接入时必须一起解决，不能只接"发消息"）

V2 只是把上行从音频换成文本，产品语义仍是一场有时长的面试。 下表区分"后端已实现（直接消费）"与"仍待产品定"：

机制状态与做法
建会话与结束✅ 已实现（后端 + 前端）：建连成功即起算（text 模式不再等 ASR 就绪），MOCK 首问由后端立刻下发；结束时生成面试记录。前端收尾见 §6.3.3：头部「结束」→ 用通用模板进「体验完成」，否则返回上一页
计时与计费✅ 后端已实现：文本模式同样按会话时长计费（思考时间算面试时间），且不做"无操作自动暂停"（已定稿）。「文本模式单价是否与语音一致」仍属商业决策（见 §9-3）
心跳⚠️ 硬要求：建连后立即发一次 {"type":"heartbeat"}，之后每 25 秒一次，随连接启停。文本模式下「思考 1 分钟再回」是常态，心跳比语音模式更关键（小程序 V1 的 InterviewSocket 已内置，V2 复用它即可，页面不要自己 setInterval）。失联阈值：语音 60 秒 / 文字作答 180 秒（realtime.text-heartbeat-timeout-ms，见 §6.3.1）
暂停 / 恢复✅ 后端已实现：显式 PAUSE → PAUSED，用 resume=<逻辑会话ID> 重连，重连后仍是 text（input_mode 已落库还原）。
✅ 前端入口已实现（2026-09-23）：头部「暂停」（带确认弹窗）→ 暂停条 + 「继续面试」，头部同一位置也变为「继续」（两处等价，都是 handleResume）；时序与守卫见 §6.3.2
多端顶号✅ 沿用 V1：同一用户新建连接会踢掉旧连接
计费活跃度判据✅ 不沿用"无音频即静默"：只看心跳。后端不做「收到 ANSWER 就当心跳」的特例（那样"正在思考"与"已掉线"无法区分）—— 这正是心跳是硬要求的原因
失联 vs 暂停⚠️ 失联 = 结束，显式 PAUSE = 暂停 —— 见 §6.3.1，这条最容易被当成 bug

6.3.1 两条状态机（分开写，别合并）+ 三条容易混的语义

① 后端权威的会话状态（前端只消费，不定义）：

pending ──(WebSocket 建连)──→ active ──(显式 PAUSE)──→ paused ──(resume=逻辑会话ID)──→ active
                                │                        │
                                └──── 结束 / 失联 / 余额耗尽 / 暂停超时 ────→ ended

（这是 interview.status 的取值；内存里的逻辑会话只有 ACTIVE / PAUSED / ENDED 三态， pending 只存在于"准备好了但还没建连"这个短暂窗口。）

② 前端回答气泡的 UI 状态（与上面的会话状态无关）：

sending ──→ thinking ──→ streaming ──→ done
                 │             │
                 └─────────────┴──→ error（还原输入框 / 提示）
  • 由后端事件驱动：THINKING → thinking；LLM_REPLY(final=false) → streaming 并追加文本； LLM_REPLY(final=true) → done（末分片带最后一段正文，仍按追加处理）；ERROR 或本地失败 → error。
  • 不要把 thinking / streaming 画进会话状态机 —— 它们只是"这一个气泡"的状态， 期间会话一直是 active（回合执行状态由后端 ConversationTurnRunner 自持，前端不参与）。

三条容易混的语义（写死）：

事件会话状态说明
用户在思考，长时间不发 ANSWER仍 active思考 ≠ 暂停；思考时间算面试时间（按整场时长计费）
发 {"type":"heartbeat"}仍 active心跳只证明连接活着，不代表"用户正在操作"，也不刷新计费活跃度
超过失联阈值没收到心跳（语音 60 秒 / 文字作答 180 秒）ended失联 = 结束，不是暂停（后端踢出 + 停计费 + 落库收尾）；只有显式 PAUSE 才进 paused。文字模式阈值放宽的理由见下
显式 PAUSE 后paused保留 15 分钟等 resume 重连，超时 SESSION_EXPIRED 结束

已定稿（2026-09-22，产品方向）：失联仍沿用「结束」，不改「暂停」；但文字作答的失联阈值放宽到 180 秒。 这样两套语义都保持干净：

事件含义处置
显式 PAUSE用户明确表示"我暂时不面了"paused，15 分钟内可 resume
失联（心跳丢失）系统无法确认用户还在短暂等待后仍然 ended（停计费 + 落库收尾）

为什么不能把失联也映射成 paused：那样 paused 会同时表示"用户主动暂停 / 锁屏 / 断网 / 杀进程 / 故意断网"五种情况，而「用户主动暂停」这条最有产品价值的信号会被冲掉 —— 一旦 paused 变成万能状态，它就不再能回答"用户是不是自己要停"。

180 秒这个数的边界：失联判定期间会话仍是 active、仍在计时计费（心跳丢失 ≠ 暂停， 见 §6.3 表格），所以阈值 = "真的一去不回时最多多扣多少秒余额"；上限由它约束，不能随意放大。

为什么不新增 DISCONNECTED 状态 / "短暂重连窗口"：小程序切后台时TCP 连接通常还在 （被挂起的是 JS，心跳随之停），因此只放宽阈值就能让用户回来自动续上，零前端改动； 而连接真的断了（进程被杀 / 网络断开）时，前端没有自动重连（当前唯一的恢复路径是 "显式 PAUSE → 手动 resume"），后端留多久都不会有人来接 —— 要做真正的"失联可恢复"， 得引入新状态 + DB 语义 + 前端自动 resume，属独立议题，收益远小于成本。 结论：本轮只放宽阈值，不新增状态。

联调提醒仍适用：若用户切后台超过 180 秒，回来时面试已经结束（不是暂停）， 这是既定行为，不要当 bug 报。

已定稿（2026-09-23，后端已落地）：失联结束不再记 USER_ENDED —— 新增 InterviewEndReason.DISCONNECTED（心跳超时 / 顶号 / 传输错误），埋点 end_reason 从此能区分 「用户主动结束」与「连接层失联」；历史数据不回溯，报表按发布日分界。 映射与理由见后端方案 §8 P0-2 与 §8.1。

6.3.2 暂停 / 恢复的时序与守卫（实现里最容易写错的一处）

点「暂停」
   ├─ 确认弹窗（取消则什么都不做）
   ├─ pausing = true  ←── 先立标志，再发指令
   └─ 上行 PAUSE
        ↓
   服务端：回 PAUSED{sessionId}  → 页面：paused = true、存 sessionId、进入暂停态
        ↓
   服务端：**正常关闭**物理连接（1000）→ onClose 一样会触发
        ↓
   点「继续面试」（或头部「继续」，两处等价）→ connect({ ...原建连参数, resume: sessionId })
        ↓
   恢复成功（onOpen）→ pausing / paused 复位 → 回到进行中（**不重发首问**）

三条"不这么写就会出 bug"的实现要点：

  1. 必须用 pausing / paused 标志区分「预期的关闭」与掉线：服务端确认暂停后会正常关闭连接， onClose 照样触发。没有标志，页面会立刻弹"连接已断开"，用户以为暂停失败了。
    • 已确认暂停（paused）→ 连接关闭静默处理；
    • 发过 PAUSE 但没等到 PAUSED → 拿不到逻辑会话 ID，恢复不了 → 按「暂停失败，请重新进入」收尾（不假装成功，否则用户点"继续"必然失败）。
  2. 恢复要用同一套建连参数（模式 / 作答方式 / 模板 / 语言…）+ 多一个 resume： 少任何一项，恢复出来的都是"另一场面试"（例如 input 丢了就退回 audio 会话）。 实现里存了一份建连参数（wsConfigRef）供恢复复用。
  3. 暂停要 5 秒兜底：PAUSED 没来（发送时连接已关 / 网络断）时回滚标志并提示， 否则页面会永久停在"正在暂停…"。

暂停会取消在途回复：如果在"刚发完作答、AI 正在生成"时暂停，那一轮回答会被服务端取消且不落库。 当前实现不阻止这种暂停（用户可能正是因为来电话才急着暂停），但没有把它做成"无损暂停" —— 真要无损，需要后端先把已生成的部分落库，属独立议题。

参数名陷阱：恢复用的 query 参数是 resume（= 逻辑会话 ID）；协议里另有一个 resumeId 是简历 ID。两者只差两个字母，混用会得到"用错简历（或直接失败）的一场面试"。

为什么从底部移到头部：底部只留输入区，操作入口集中在一处（V1 的底部按钮是当时的形态， 上移后与「暂停 / 继续」同一视线高度，不会在长对话里被滑走的输入区挤走）。 跳转规则、usedTemplateRef 定格、无二次确认这些都不随位置变化。

本场面试跳转为什么
用了通用模板redirectTo('/pages/experience-complete/index')体验用户还没填自己的岗位/简历，收尾正是引导补齐的最佳时机
没用模板有上一页 → navigateBack()；否则 → redirectTo('/pages/index/index')回到设置页 / 首页即可

三条要点：

  1. 模板分支用 redirectTo 而不是 navigateBack：面试页要被顶掉 —— 返回它只会看到一张过期的对话。
  2. 「是否用了模板」在建连成功时定格（usedTemplateRef）：面试结束后用户可能已经清掉选中态， 那时再读 storage 就判断不出这场面试到底用的什么（V1 同款处理）。
  3. 不做二次确认、也不依赖网络往返：断连即结束，离线也点得动（与 V1 一致）。

暂停态也能结束，但这条路径靠后端兜底：暂停时没有物理连接可断，服务端无从立刻得知"用户结束了"， 该记录由暂停保留时长（默认 15 分钟）到期后自动收尾 —— 也就是说这条路径的 end_reason 会是超时口径，而不是 USER_ENDED。要做到"暂停态结束也立即落库、归因准确"，需要一个显式的结束指令 （控制消息或 REST 接口），属独立议题（当前把它当已知限制）。

8. 验证方式

  1. 微信开发者工具打开 demo 页（开发环境下自动登录）→ 点「模拟面试V2（文字作答）」，或走「模拟面试设置（V2 入口）」→ 自动建连。
  2. 首问：建连成功后无需任何操作，AI 面试官主动发出第一题（先出现打字指示器气泡，再逐字填充）。 不应出现前端写的固定开场白（GREETING 已删）。
  3. 作答：输入文字 → 发送 → 用户气泡立刻出现、输入框清空并禁用（话筒按钮同时禁用）→ AI 追问逐字填充 → 收到结束信号后输入框恢复。
  4. 发送前拦截：空文本时发送按钮置灰；超过 2000 字被输入框 maxLength 拦住（后端仍会兜底拒绝）。
  5. 重复发送：AI 生成期间输入框是禁用的（这是 TURN_BUSY 的语义要求）。若通过看门狗恢复后提前发送而被后端拒绝， 应看到「AI 正在回复中」提示，且刚才那段文字回到输入框（不会被丢掉）。
  6. 语音输入：点话筒 → 首次弹麦克风授权 → 授权后话筒变红 + 出现「正在聆听」提示条 → 说话内容实时填入输入框 （中间态覆盖草稿、定稿追加）→ 再点一次结束。识别不会触发 AI 回答（这是本方案的核心解耦）。 识别中点发送：识别随发送一起停止（话筒恢复蓝色、状态条消失），发送后不应再有识别文字写回刚被清空的输入框。

  8. 暂停 / 继续：点头部「暂停」→ 确认 → 输入区禁用、底部出现「面试已暂停，15 分钟内可继续」+「继续面试」， 且头部同一位置的按钮由「暂停」变为「继续」（两处都能恢复）； 不应出现"连接已断开"之类的提示（服务端此时会正常关闭连接，页面已按预期关闭处理）， 也不应在对话流里多出一条"面试已暂停"的消息（暂停是状态，不是对话内容）。 点「继续面试」或头部「继续」→ 回到进行中，对话不丢、且不会重发首问。 暂停期间剩余时长停表（数字不再变化），恢复后接着走。

  18. 资格闸门（2026-09-24 可测）：未开始 / 已结束 / 暂停中的页面上点话筒 → 提示「请先开始面试」， 且不会打开麦克风、不会自动重连；面试结束（含掉线 / 余额耗尽）时服务端会回收识别连接， 前端不应对这次关闭弹任何错误（此时本就在结束态）。
  19. 停止后的空闲释放（2026-09-24 新增）：
    • 说一段话 → 点话筒停止 → 之后什么也不做：约 8 秒后连接自动关闭（开发者工具 Network 能看到 WS 关闭）， 再次点话筒能正常建立新连接；
    • 「发送」后再点话筒仍然正常（发送那次 stop() 起的定时器不能把新连接关掉）；
    • 把前端窗口临时调大（或用老版本客户端）以触发后端兜底：应看到 [识别通道] 上游输入空闲已达上限 与指标 end="input_idle"，且页面不弹任何错误。
  20. 单次上限 180 秒（2026-09-24 新增，配合上限 60 → 120 → 180 秒）：
    • 说到 180 秒 → 微信自动停录音 + toast「已到单次语音上限，可再点话筒继续说」， 已识别的文字留在输入框里（不能因为自动停止而丢掉）；
    • 随后再点话筒 → 能正常开始新的一次（新连接、新的 180 秒窗口）；
    • 界面不显示已用时长（2026-09-24 决定，见 §5.6 的权限/边界表）。
