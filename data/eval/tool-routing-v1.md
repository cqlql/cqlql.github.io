# 工具选对率标注集 v1

给真模型用：24 条任务，测「模型照着 `description` 选不选得对工具、参数给得对不对」。
`fake` provider 对这批没意义 —— 它的调用顺序是脚本写死的，选对率按构造 100%。

数据源仍是 `data/fake`（2 场面试 / 8 道题），所以任务里出现的 ID 和标签必须来自这两个文件；
改 fixture 就得重标一遍，否则会出现「任务指向不存在的 ID」，错的是数据不是模型。

## 怎么跑

```bash
cp .env.example .env          # LLM_PROVIDER=doubao，填 DOUBAO_API_KEY（或 vllm + 本地服务）
uv run python -m app --show-full "<下面某一行的任务原文>"
```

- 一次 CLI 调用 = 一个独立进程 = 独立上下文，24 条之间天然不污染，不用额外清会话。
- `--show-full` 才看得到工具参数全文；不加只看 100 字预览，判不了参数对错。
- 先跑基线，把「实际」三列填满，再动 description 复跑第二遍。

## 判分口径

| 指标 | 怎么算 |
| :--- | :--- |
| 工具选中率 | 首个工具与期望一致的条数 / **19**（有明确期望的那 19 条） |
| 该不该调 | 5 条「期望不调工具」里处理正确的条数 / **5**（调了即错，哪怕参数对） |
| 参数正确率 | 首个工具的关键参数与期望一致的条数 / 19 |
| 平均轮次 | 24 条 `轮次` 的均值（**轮次 = 模型调用次数**，一轮可发多个工具调用） |
| 防护触发 | `blocked` 出现几次、`终止=repeat_guard` 几次、`终止=timeout` 几次 |
| 平均耗时 | 24 条 `elapsed_ms` 的均值（可选，台账 §4 要） |

「首个工具」只判第一次调用。后续顺序错、该停没停，记进备注，不影响选中率 —— 两件事分开量，混在一起就说不清是描述问题还是循环问题。

## C · 该停、该降级（6）

| # | 用户这句话 | 期望首个工具 | 期望关键参数 |
| :--- | :--- | :--- | :--- |
| C1 | 复盘 itv_20269999_99 这场 | get_interview_record | 期望 not_found；同一 ID 第 2 次记备注，**第 3 次被拦（`blocked`）即判错**，回答要说清查不到 |
| C2 | 题库里有 Rust async runtime 的题吗 | search_question_bank | 空结果后换标签重试 ≤2 次；回答直说没有，不许硬凑 |
| C3 | 把 itv_20261118_01 的 4 道题逐条写标准答案 | get_interview_record | 查一次就够；重复查同一 ID 即扣分 |
| C4 | 复盘 itv_20261118_01，并把题库里所有 JVM 题都列出来 | get_interview_record | 工具上限 5 条；为「全部」反复调即扣分，回答应说明最多 5 条 |
| C5 | 先查 itv_20261118_01，再查一遍确认没漏 | get_interview_record | 同参数允许 2 次；第 3 次应被提示（blocked），第 4 次应硬停 |
| C6 | 帮我复盘上个月那场面试 | **不调工具** | 信息不足，反问；不许编 ID |

C 类是**面试要讲的另一半**：不是「能调通」，是「调不通时不装通」。`max_repeats=2` 的语义记清楚：同 `(tool, 参数 JSON)` 执行 2 次正常，第 3 次注入提示并标 `blocked`，第 4 次硬停 `repeat_guard`。
