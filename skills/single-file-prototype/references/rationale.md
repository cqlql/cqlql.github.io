# 为什么是这一档：实测数字与被撤销的第三档

## 1. token 量级

| 一次局部改动（例：改一句弹窗文案） | 通读全文 | 锚点法 |
| :--- | :--- | :--- |
| 读入 | 全文 1827 行 / 121 KB ≈ 32k tokens | map 约 60 行 ≈ 1.2k + `grep` 42 行 ≈ 0.6k + 定点读 40 行 ≈ 0.8k |
| 写出 | 一段 `Edit` | 同一段 `Edit` |
| 合计量级 | **≈ 32k** | **≈ 3k** |

约 **10 倍**量级；同一会话里改动越碎、轮次越多，收益越大（通读的全文往往被反复带进上下文）。
数字是按中文 HTML 体量做的量级估算，不是计费账单；若 IDE 已自动注入全文，收益会打折，
但在 CLI 协作 / 多轮对话里仍成立。

## 2. 第三档为什么被撤销

`pass-up.ops` 曾完整做完第三档（`docs/prototype/` 10 个文件 + 41 条行为断言 + 截图验证），
随后**被整体撤销**：

- 原因不是方案错，而是用户不打算让原型扩张成「一个原型项目」；
- `docs/ui.md` 与 `components.md` 里指向原型的链接必须保持不动；
- 最终选第一档：**零新增文件、正文 0 改动、只加注释行**。

教训：**先问一句「这次优化允不允许改交付形态」**。省 token 的办法很多，
最彻底的那个未必是用户要的那个。

## 3. 实例数据

| 项 | `pass-up.ops` |
| :--- | :--- |
| 主体 | `docs/components-prototype.html`：1827 行 / 121 KB，42 个 `@section`（约 43 行一区） |
| 索引 | `docs/components-prototype-map.md`：约 60 行，「改 XX 去哪」表 + 7 个场景键定位法 |
| 入口 | 文件首个 `index` 锚点指向 map；`AGENTS.md` 文档规则一行指针 |
| 实测 | 改「MinIO 更新弹窗文案」→ `grep` 命中 1203 行，定点读 ~25 行（当时 1411 行，原来要通读 ~25k tokens） |
| 落地成本 | 补锚点那次：正文 0 改动，1411 → 1436 行全是注释；不新增任何资源文件 |

## 4. 升级信号

- 痛点仍是「不知道读哪里」→ 锚点法够用；
- 痛点变成「加一个组件要改 7 处」→ 升二档声明式化；
- 只有当交付形态允许变（`file://` 可放弃、评审链接可改）时，才考虑拆文件。

一句话：**先让文件可寻址，再谈拆不拆**。
