# 单文件原型分区锚点

给「被交付形态绑死的长文件」加一层语义索引：改文案时只读 40 行，不通读 1800 行。

## 0. 它省什么、不省什么

省的是**读进来**的 token，不是把文件变小，也不是让改动面变少。

| 一次局部改动 | 通读全文 | 锚点法 |
| :--- | :--- | :--- |
| 读入 | 1827 行 / 121 KB ≈ 32k tokens | map ≈ 1.2k + grep ≈ 0.6k + 定点读 ≈ 0.8k |
| 合计量级 | **≈ 32k** | **≈ 3k** |

约 10 倍量级；同一会话里改动越碎、轮次越多，收益越大。

**真正起作用的三件事，缺一不可**：

1. **语义 → 位置的翻译表**（map）。AI 拿到的是「改 MinIO 更新弹窗文案」，不是行号。
2. **行号不写死**。map 只写 slug，行号每次由 `grep -n` 现场取。
3. **slug 稳定**。锚点名定下不改，map、AGENTS、历史对话里的引用都不漂移。

**不省的边界**：不降改动面、不省全局理解（跨区重构仍要通读）、不省输出，且有长期维护成本。

## 1. 适用判据（三条全满足才用）

1. **必须单文件交付**：`file://` 双击可开、不能引入目录 / 多资源文件。能拆就先拆。
2. **大到读一次肉疼**：经验阈值 > 500 行 / > 20k tokens，且一次会话里会反复改。
3. **改动以局部为主**：改文案、加一区、调样式，按语义能说清「改哪儿」。

🔴 **生产代码不要用**：函数 / 模块 / 组件边界本来就可寻址，再加锚点是重复建设。
这套只给单文件原型、演示稿、长配置、长 SQL、单篇长文档。

## 2. 三档选型：别默认就拆文件

| 档 | 做法 | 解决什么 | 代价 |
| :--- | :--- | :--- | :--- |
| 一档 · 可寻址（本文） | 单文件 + `@section` 锚点 + map | 只降**读**的成本 | 改动面不变；多一份 map 要维护 |
| 二档 · 声明式化 | 注册表 / 数据驱动，删掉 `id === "xxx"` 特判 | 降**改动面** | 要重构渲染器，回归面大 |
| 三档 · 拆文件 | 入口变目录 + 多个 js/css | 两者都降 | 交付形态变了：`file://` 相对路径、脚本加载顺序、评审链接全要改 |

🔴 **先问一句「这次优化允不允许改交付形态」**，没确认就别往下做。
实战里第三档做完整套后被整体撤销——不是方案错，是用户不打算让原型扩张成「一个原型项目」。
最终选第一档：零新增文件、正文 0 改动、只加注释行。

当痛点从「不知道读哪里」变成「加一个组件要改 7 处」时，按上表升档。

## 3. 源文件侧：埋锚点

格式固定 `==== @section <slug> ==== <人话说明>`，按所在语言的注释语法包起来：

```html
<!-- ==== @section index ==== 分区索引入口；改本页前先查 docs/<主体>-map.md -->
```
```css
/* ==== @section css-base ==== 变量 / 全局 / 导航 / 工具条 / 场景条 */
```
```js
// ==== @section fn-modal ==== 弹窗提交门 / 代理校验 / 至少勾一个 / 任务回写
```

| 项 | 约定 |
| :--- | :--- |
| 区边界 | **一个区的终点就是下一个锚点**，不写 `@endsection`，不嵌套 |
| slug | 唯一、小写、连字符；前缀标类别：`css-` / `html-` / `card-` / `data-` / `fn-`；**定下后不改** |
| 子锚点 | 热点区里的可定位单元单独起锚点，如 `confirm-<组件>-<动词>` |
| 密度 | 一区 30~80 行为宜（实例：42 锚点 / 1827 行 ≈ 43 行一区） |
| `index` | 文件第一个锚点，只写一句「改本页前先查 `<主体>-map.md`」 |
| 说明文字 | 写「这一区装什么」，不写「怎么改」；改动方法归 map |

🔴 **锚点只能是注释**：补锚点那次提交用 `git diff --unified=0` 验证「除注释行外无任何内容变更」；改完内联脚本再跑一次 `node --check`。

## 4. 索引侧：写 map

命名强制 **`<主体文件名去扩展名>-map.md`**，与主体同目录，**一个文件一份 map**。
不要用 `prototype-map.md` 这类泛名——第二个原型出现时它立刻会被误读成「所有原型的地图」。

直接用 `assets/prototype-map.md` 当骨架。写表的两条要点：

- **按「人话任务 → slug」写，不按文件顺序复述目录**——后者是 `grep -n` 的活。
- 一任务一行；跨多区的任务写 `fn-plan` + `fn-render` 这样并列，别合并成一个含糊的大区。

## 5. 改动时的标准动作

1. **先读 map**（不到 100 行），不读 HTML。
2. 在「改 XX 去哪」表里按人话任务找到 slug。
3. `grep -n "@section <slug>" <主体>` 取**实时**行号。
4. `Read offset=<行号> limit=40~80` 读完这一区；确实跨区再读下一个，一次最多 2~3 区。
5. `Edit` 定点改，只回传锚点下那一段。
6. 若新增 / 拆了区块：补锚点 → 更新 map 表 → 跑 §6 自检。
7. 项目 `AGENTS.md` 里留**一行**指针（「改原型前先 grep 锚点定点读」），不要为它新建索引。

🔴 **不要「保险起见把全文读一遍」**。不确定就再 grep 一个锚点，而不是通读。这条要写进项目 AGENTS，否则下一次会话会默认通读。

## 6. 验收与防漂移

跑 `scripts/verify-anchors.sh <主体> <map>`，它做三件事：

1. 锚点总数与 map 状态行对账，并检查 slug 唯一；
2. map「改 XX 去哪」表引用的 slug 与源文件逐个对账；
3. 纯补锚点那次，`git diff --unified=0` 只允许注释行变化。

> ⚠️ ② 只取表格第二列。对全文所有反引号做全量匹配必然误报：实例里
> `image-copy`（CLI 动词）、`absent` / `healthy`（场景键）都不是锚点。

🔴 **最大的失败模式是漂移**：新增区块忘了补锚点 → map 变旧 → AI 按旧表定点读，读到错的区、改错地方，而且因为「只看了 40 行」还看不出来。所以「新增区块同步补锚点」必须是项目 AGENTS 里的硬规则。

## 7. 反模式

| 反模式 | 后果 |
| :--- | :--- |
| map 里写死行号 | 文件一长，整张表失效 |
| 用泛名 `prototype-map.md` | 第二个原型出现就串味 |
| 把 map 当能力索引 | 两个索引必然漂移 |
| 锚点名随功能改名 | map / AGENTS / 历史对话里的引用全失效 |
| 想靠锚点解决「加组件要改 7 处」 | 越改越累，该升二档声明式化 |
| 给 200 行的一次性原型上这套 | 维护成本 > 收益 |
| 锚点里塞逻辑或可执行标记 | 破坏「注释零改动」，也可能改变行为 |
