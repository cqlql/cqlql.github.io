# 给仓库落地 AGENTS、文档、代码规范、验证规范、目录

**判据优先于模板**：模板可以照抄，判断不能。**分阶段落地**：只补「有真实改动会用到」的那一份，
其余留着不建 —— 建了但没被用过，里面的工具和命令只能编。

## 0. 落地分阶段：不确定的先别写

> 判据：**规范只在「有真实改动会用到它」时落地**。没被用过的规范，里面的工具、命令、专项场景只能编 ——
> 而编出来的命令比不填更坏（AI 会照着跑失败，再把「已验证」写成结论）。
>
> 每条规则的成熟度见 `references/evidence.md`：标 ❓ 的是推演，**不强制**；标 ⚠️ 的注明边界。

### 阶段 0 · 第一天（新仓第一次提交前）

1. **`AGENTS.md`**：只放红线 + 指针，目标 ≤220 行 / **≤13KB**（实测口径，见 §1.1）；超了说明该拆到 `docs/`。
   **必须含一张「任务路由」表**（≤8 行 / ≤1.5KB：改动类型 → 读哪几节 → 验到 L几 → 报告篇幅），
   否则专项规范只有「全读」和「全不读」两条路（见 §1.4）。
2. **`docs/`**：第一个功能落地时就定下「契约 / 口径 / 实现」三分，别等到有 20 份再回头分。
3. **每份文档第一行写状态**，并在 AGENTS 那张表里给它一行。
4. **实例化文档约定**：通用条款复制成 `docs/doc-conventions.md`，顶部写明母本路径；
   把母本「新开仓六件事」一节换成「本仓落地现状」，**不复制文档表**（AGENTS 已是唯一索引，见 §2.4）。

### 阶段 1 · 第一个功能落地后（有代码可看）

5. **实例化代码设计规范**：`references/code-design.md` 全文复制成 `docs/code-design.md`，
   **按 §0.5 的标记删掉与本栈不符的节**（不逐个读着判断）；「本仓现状」节此时才填（最大的类、状态字段、模块调用方向）——
   没代码时填出来的阈值比不写更坏（见 §2.6）。

### 阶段 2 · 第一次 L3 改动前（要动资金 / 权益 / 状态机 / 事务）

6. **实例化代码验证规范**：`references/code-validation.md` 全文复制成 `docs/code-validation.md`，
   **按 §0.5 的标记裁剪**；工具映射表（9.1 右两列）**先留空**，跑通一次再填。
   理由：没有它就没人规定「什么算验完」，第一批改动会默认以「编译过」作为交付标准。
7. **集成测试基建**：没有它，L3 的「真组件集成」永远只能写「受阻」——
   而一旦允许写「受阻」，就等于允许把单测冒充一致性验证。

### 阶段 3 · 第一次真实 SQL 改动（要改查询 / 索引 / 分页 / 批量）

8. **实例化 SQL / ORM 规范（仅后端仓，且有数据访问层）**：`references/sql-orm.md` 全文复制成 `docs/sql-orm.md`，
   **按 §0.5 的标记裁剪**（非 Java 仓删掉 `〔Java〕` 节）。查询形态、金额/时间字段类型、迁移工具是定形项。

> **为什么不是「第一天七件事」**：原版把 1~8 全压在第一天。实测（`evidence.md` #13）：
> 没有真实 SQL 改动时，「本仓查询次数怎么统计、`EXPLAIN` 在哪跑」只能编。
> ⚠️ pass-up.backend 按阶段落地，但它的**阶段 3 早已触发**（64 个 Flyway 迁移 + 游标分页 + 秒级扣减），
> `sql-orm.md` 拖到 2026-11-23 才补 —— 中间那段时间的缺口是**欠账**，不是「可以不建」的例证
> （2026-11-23 更正，见 `evidence.md` #13）。

## 0.5 按栈选装：只装这个仓用得到的部分

> 一个 Java 后端仓里出现 `nav.ts`、`hooks/`、`Taro switchTab`，读者会开始怀疑其余条款是不是也抄错了仓；
> 而且每多一段不相干内容，就多一处要跟着母本同步的漂移点。**裁剪不是精简，是让剩下的每一句都可信。**

### 第一步：探测栈，不要问人

按仓库根目录（含一级子目录）出现的文件判断：

| 证据 | 结论 |
| :--- | :--- |
| `pom.xml` / `build.gradle(.kts)` | Java 后端 |
| `go.mod` | Go 后端 |
| `pyproject.toml` / `requirements.txt`（且依赖里有 fastapi / django / flask） | Python 后端 |
| `*.csproj` / `*.sln` | .NET 后端 |
| `package.json` 且依赖含 `vue` / `react` / `next` / `nuxt` / `svelte` / `@tarojs/taro` | 前端 |
| `package.json` 但只是文档站 / 静态站 / CLI | 只装 AGENTS + `doc-conventions.md` |

两栈证据同时存在（后端 + 内置前端）→ **两栈都留**，但在节内补一句「本节只适用 `<子目录>/`」。
证据不足（空仓、第一天）→ 只装阶段 0 的两份，**不要先猜一个栈**。

### 第二步：文件级取舍

| 文件 | 前端仓 | 后端仓 | 无数据访问层 |
| :--- | :--- | :--- | :--- |
| `references/doc-conventions.md` | 装（阶段 0） | 装（阶段 0） | 装（阶段 0） |
| `references/code-design.md` | 装（阶段 1），按标记裁剪 | 装（阶段 1） | 装（阶段 1） |
| `references/code-validation.md` | 装（阶段 2） | 装（阶段 2） | 装（阶段 2） |
| `references/sql-orm.md` | 🔴 **不装** | 有数据访问层才装（阶段 3） | 🔴 **不装** |
| `references/directory.md` | 只读，结论写进 AGENTS「目录与边界」 | 只读，同上 | 只读 |
| `assets/AGENTS-template.md` | 骨架，删掉不相干行 | 骨架，同上 | 骨架，同上 |

### 第三步：节级裁剪（照标记删，不靠判断）

四份 `references/` 的节标题带栈标记，**标记就是裁剪指令**：

- **无标记** = 全栈通用，留；
- `〔前端〕` / `〔后端〕` = 只留与目标仓匹配的；
- `〔Java〕` = 只留 Java 仓（Go / Python / .NET 删掉，按本栈框架另写，**不要在这里编等价物**）；
- 表格里有「适用」列的，删掉不属于本仓的行。

本文件（`SKILL.md`）自己的节也带同样标记，最明显是 §3 目录结构：**一个 Java 后端仓读到 §3.3/§3.4
（`features/`、`nav.ts`）应当跳过，不要照着给本仓定目录**。这类「读时跳过」不在脚本检查范围内，
只有复制进仓的实例才查得到。

**第四步：裁完把脚手架说明删掉。** 实例里那几行 `> 节标题后的 … 是裁剪标记` 是复制时带过去的说明书，
裁剪完成后没有意义，`check-agents.sh` 会提示残留。

🔴 **裁完没剩下什么的，就别建这份。** 一份只剩三行的 `code-design.md` 不会被任何人读，
下次改代码也不会有指针指向它 —— 这跟 §0「不确定的先别写」是同一条判据：宁缺勿假。
遇到这种仓，先把 AGENTS + `doc-conventions.md` 做实，等真有了需要约束的代码再回来建。

裁完要能自证：`scripts/check-agents.sh` 按探测到的栈报出**残留的不适用标记**与**未删的说明块**。

## 1. `AGENTS.md`

### 1.1 先记住那条实测数据

某仓的 AGENTS.md 曾写到 **1117 行 / 106KB**，结果**只有前 17% 进得了上下文** —— 后面 83% 的红线写得再好，AI 也读不到。

| 指标 | 上限 | 超了怎么办 |
| :--- | :--- | :--- |
| 行数 | **≤ 220 行** | 拆到 `docs/`，AGENTS 只留一句结论 + 指针 |
| 体积 | **≤ 13KB**（实测截断点，不是估的） | 同上；**先把「查表用」的模块索引搬到 `docs/index.md`** |

### 1.2 每条内容先过三问

**三条缺一条就别写进 AGENTS**：

1. **每次动代码都要遵守吗？** —— 只对某个功能成立 → 进 `docs/`。
2. **不知道会不会写错 / 搞坏？** —— 显然不会踩的常识 → 删掉。
3. **能一句话说清吗？** —— 要三段话解释的判据、实测数据、决策历史 → 进 `docs/`。

留下来的形态统一是：**一句结论 + 一个指针**。

⚠️ **骨架里的「模块索引」不在三条之内** —— 它过不了第 1 问（查表用，不是每次动代码都要遵守）。
它曾经靠「索引只有一处」赖在 AGENTS 里，实测代价是**占掉全文 44%、把整节红线推出窗口**。
现在放 `docs/index.md`，判据见 §1.3 第 1 条与 §1.4 末尾。

### 1.3 写法规矩

1. **每件事只有一张表，位置可以不在 AGENTS**。模块索引放 `docs/index.md`、AGENTS 只留指针；
   但不许**同一件事有两处可写**（不额外建 `README.md` 当第二索引）。判据见 §1.4 末尾。
2. **红线和指针必须成对出现**。只写「见 `docs/xxx.md`」等于没写。
3. **用 🔴 标「不知道就会搞坏」的条目**，一个仓控制在 10~20 条。满屏红点 = 没有红点。
4. **不写「项目简介」「如何安装」**。AI 需要判据，不是产品介绍。
5. **改完代码先改 AGENTS，再改 docs**。顺序反了会出现「文档说 A、红线说 B」。
6. **一份 AGENTS 只服务一个仓**。跨仓契约放生产方，消费方只放指针。

骨架直接用 `assets/AGENTS-template.md`。

### 1.4 任务路由表（骨架里唯一一张表）

**解决的是检索成本，不是规则数量。** 六份规范每份都写了「本文不管什么 → 指针」，但没有正向的「改 X 读哪节」。
缺了它，AI 只有两条路：全读（上下文膨胀）或全不读（红线失效）。这张表是第三条路。

**它不是「第二份索引」**：`文档约定` §四 禁的是「同一件事两张表」（两份必然漂移）；
这张表按**改动类型**索引，与「模块 → 文档」正交（前者答「改这个读哪节」，后者答「这模块有没有文档」），
所以可以并存 —— 但**位置不同**：路由表必须在 AGENTS，模块表在 `docs/index.md`。

🔴 **搬出去后 AGENTS 里不得再留第二份模块表**（哪怕缩成 5 行）。判据不是「在不在 AGENTS」，
是**同一件事有几处可写**。

🔴 **索引只收已成立的事实**：提案 / 设计留痕 / 规划中的能力**不进索引**（实测：两条「🗄 提案未实施」
的行在表里躺了几个月，每次读表都要重新判断它算不算现状）。落地了再加行。

填法：

1. **只填章节号，不填标题** —— 标题会改名，章节号相对稳定；章节重排时顺手核对本表。
2. **本仓没实例化的规范，删掉对应行**（无 `docs/sql-orm.md` 就删 SQL 两行）。删 = 明确不存在；指向空文件比删掉更坏。
3. **上限 8 行 / 约 1.5KB** —— 每行约 180B，10 行就要占掉 AGENTS 体积预算的 11%。
   超了说明分类太细，合并相邻行。这是「四档决策表」，不是「改动类型词典」；
   AGENTS 已接近 13KB 时压到 **5 行**（实测够用，见 `references/evidence.md` #4）。

🔴 **等级是下限**（同 `references/code-validation.md` §2.2）：命中资金 / 权益 / 并发 / 状态机任一项，
不许以「表里写 L2」为由降级；反过来 L1 改动也不许照着 L3 那行做。

## 2. 文档

### 2.1 四个问题（有一个答不上就别新建）

| 类型 | 放哪 | 判据 |
| :--- | :--- | :--- |
| 契约（表 / 接口 / 消息帧 / 错误码） | **生产方那一仓**；跨端功能收敛到一份「施工图」 | 谁定义谁维护，消费方只放指针 |
| 产品口径（文案 / 交互 / 三态 / 期别） | 需求方那一仓 `<功能>-v<N>.md` | 会随产品决策变 |
| 实现判据（页面 / 踩坑 / 冒烟） | 实现方那一仓 `<功能>-frontend.md` / `<主题>.md` | 换个实现就失效 |
| 「为什么这么设计、哪些方案被否」 | **并进对应实现文档的决策节，不单独开一份** | 单开一份必然烂尾 |

**能不能塞进已有文档的一节？** 能就不新建。**每多一份文件，就多一处要同步的地方。**

🔴 **跨仓 / 跨端两边都不复制字段 / 接口副本，只放指针。**
典型烂法：方案文档里抄了一份表结构，三个月后字段改名，四份文档还在指着旧名。

### 2.2 命名

| 类型 | 命名 | 例 |
| :--- | :--- | :--- |
| 实现口径 | `<功能>-frontend.md` | `mock-interview-chat-frontend.md` |
| 产品口径 | `<功能>-v<N>.md` | `ai-interview-v1.md` |
| 后端主题方案 | `<主题>.md`（**不加 frontend 后缀**） | `ai-interview-report-ticket.md` |
| 设计稿 | `<功能>-v<版本>-<模块>.html`；基准稿 `*-redesign.html` | `me-page-v2-hero.html` |
| 跨仓引用 | 按相对仓名写 | `pass-up.backend/docs/xxx.md` |

### 2.3 每份文档第一行必须是状态

```md
> 状态：**现行**（2026-10-30）
> 状态：**已完结**（阶段 0~4 全部合入，改代码请转 full-checklist）
> 状态：**已归档**（2026-10-30，被 xxx 取代，只作历史留痕）
```

判据：**读者打开第一眼就该知道「这份还算不算数」**。没有状态行 = 默认为「现行」，那就必须一直维护它 —— 大多数烂尾文档都是这么来的。

### 2.4 索引：每件事只有一张表

- 按**改动类型**索引（改什么 → 读哪节）→ `AGENTS.md` 的任务路由表，**必须在 AGENTS 里**。
- 按**模块**索引（这模块有没有文档、最硬那条是什么）→ `docs/index.md`，AGENTS 只留一条指针。
- 🔴 **同一件事不许有两处可写**：漂移的根因是「一件事两张表」，不是「表不在 AGENTS 里」。
- 🔴 **索引只收已成立的事实**：提案 / 设计留痕 / 规划中的能力不进索引，放 `docs/roadmap.md`。
  已归档文档可以留一行标 🗄（它是既成事实，只是被取代了）。

### 2.5 母本 / 实例：双写边界

「同一件事两个地方写」是漂移的起点，但有一处**无法避免的双写**：AI 只加载当前仓的上下文，读不到别的仓。所以把双写范围钉死：

| 内容 | 母本 | 实例（项目仓） |
| :--- | :--- | :--- |
| 四问、命名、状态行、索引分工（§2.4） | ✅ 唯一权威 | 照抄，**不许自行改** |
| 本仓文档表 / 本仓路径 / 专有样例 | ❌ 不写 | ✅ 只写这些 |

### 2.6 代码设计规范在「阶段 1」落地，不是第一天

[文档四问](#21-四个问题有一个答不上就别新建)管「要不要新建这份文档」，代码设计规范管「代码写出来长什么样」（职责边界、状态机、事务幂等、抽象时机）。

原版要求第一天就复制全文，理由是「定晚了第一批代码就在无规范状态下写」。**实测后改成阶段 1**：
新仓第一天往往连目录都还没长出来，此时复制的「本仓现状」只能编；
而代码设计规范真正起作用的时机是**第一个功能要落地的当口**，那时既有代码可看，也正好要决策「放哪个类」。

但它的两步不在同一个时间点，别混：

| 时机 | 动作 | 为什么 |
| :--- | :--- | :--- |
| **阶段 1 前半**（有第一个真实功能要做） | 全文复制成 `docs/code-design.md`；状态行改 `实例 · 现行（母本：…）`；删掉与本栈不符的章节 | 仓内读不到母本，规范只存在别的仓 = 等于没写 |
| **阶段 1 后半**（该功能合入后） | 补「本仓现状」：最大的 3~5 个类及行数、状态字段在哪、哪些模块互相调用 | 没有代码时这一节只能编，编出来的阈值比不写更坏 |

> ⚠️ 这条是 ⚠️ 部分实测（`evidence.md` #14）：pass-up.backend 的 `code-design.md` 是先有代码才建的，
> 「第一天建 vs 有代码后建」没有对照数据。如果某仓第一行代码就要写复杂设计，提前到阶段 0 也合理。

🔴 **实例必须留全文，不许改成「指针 + 差异」**。这跟 §2.5 是同一个理由：AI 不跨仓读文件。

AGENTS 里只留 3~5 条最反直觉的指针（如「状态转换只许走 `XxxStateMachine`」），正文不进 AGENTS。

## 3. 目录结构

### 3.1 一句话

**按业务能力组织代码，而不是按技术类型堆代码。**

- `features/order/`（业务优先）✅
- `api/` + `services/` + `store/` 各堆几十个文件（技术类型优先）❌

### 3.2 切分判据（三个问题）

| 问题 | 答案 | 放哪 |
| :--- | :--- | :--- |
| 只服务**一个**业务能力？ | 是 | 该 `features/<能力>/` 内部 |
| **两个以上**业务都要用？ | 是 | 下沉到 `shared/`（无业务耦合才行） |
| 这个职责**现在不存在**？ | 是 | 🔴 **不建空目录、不建空文件** |

> 判据：**目录是长出来的，不是规划出来的。** 需要第二个文件时才建目录。

### 3.3 依赖方向（只许单向）〔前端〕

```text
pages / routes  →  features  →  shared（api / ui / domain / utils）
```

| 层 | 可以依赖 | 🔴 禁止 |
| :--- | :--- | :--- |
| `pages` | 本页私有组件、`features`、`shared` | 页面之间互相 import；直接写请求 |
| `features` | `shared`、**其他 feature 的 `index.ts`** | 跨 feature 读对方内部文件（含 store） |
| `shared` | 无（最底层） | 反向引用 `features` / `pages` |

跨 feature 通信的三条正路：**走共享 store（明确归属）**、**走对方 `index` 暴露的接口**、**在页面层编排**。

### 3.4 feature 内部〔前端〕

```text
features/<能力>/
  api.ts        # 只发请求，一个函数一个接口
  types.ts      # DTO / 枚举
  service.ts    # 多接口编排、重试、数据转换
  store.ts      # 只放跨组件/跨页面状态
  nav.ts        # 只放「跳转意图」
  components/   # 只被本 feature 用的组件
  index.ts      # 对外出口（需要时才建）
```

**单接口直接用 `api.ts`；只有「多接口 + 状态变更 + 重试」才值得加 `service.ts`。**

### 3.5 后端：竖切有阈值〔后端〕

前端那条原则换个名字：**按领域切包，不按 controller/service/mapper 横切**。但**收益随业务数线性增长，成本固定**：

| 条件（任一不满足就先别竖切） | 判据 |
| :--- | :--- |
| 领域 ≥ 10 个，或接口 ≥ 30 个 | 少于此数，三个包一眼看得完 |
| 有 ≥ 2 人同时改后端 | 单人开发的成本只是多按两次 `Ctrl+P` |
| 表数 ≥ 10，存在跨聚合的一致性边界 | 6 张表没有聚合边界问题 |
| 将来要换库 / 并行多存储 | 换库压力落在 store 层，不在包的形状 |

反例是「照抄 DDD 分层」：6 张表的单人项目切成四层，加一个字段改 5 个文件。

### 3.6 反例速查

| 反例 | 为什么错 | 改法 | 适用 |
| :--- | :--- | :--- | :--- |
| 为「结构完整」建 5 个空目录 | 半年后分不清空的和废弃的 | 需要第二个文件时再建 | 通用 |
| `utils/` 里塞业务逻辑 | 最底层反向依赖业务 | 挪回对应 feature | 通用 |
| 页面直接 `fetch` | 绕过鉴权与错误处理 | 走 feature 的 `api` | 前端 |
| Feature A import Feature B 的 store | 状态归属不清，改 B 坏 A | 下沉共享状态或走对方出口 | 前端 |
| 用 URL query 传长文本 | 超长静默截断，用户数据被改 | 走 `nav.ts` 的一次性意图 | 前端 |

## 6. 写回协议（这套东西怎么长大）

每次用完之后，**只做下面三件事之一**，不要临场发明新做法：

| 遇到的情况 | 写回哪里 | 怎么做 |
| :--- | :--- | :--- |
| 规则在真实仓**行不通** | 先改母本（cqlql-notes `docs/工程/`），再同步 `references/` 与各仓实例 | 只改某个仓的实例 = 制造第四份副本 |
| 发现了**新判据**（原规范没写） | `references/evidence.md` 记为 ❓ 推演 | 写清「在什么改动上发现的」，**不要直接写成规则** |
| 某条 ❓ **被真实改动验证了** | `references/evidence.md` 升 ✅ / ⚠️ 并补证据 | 证据要能复核：哪个仓、什么改动、什么数字 |

🔴 **三条硬约束**

1. **没在真实仓跑过的规则，不许写「必须」。** 写成「默认如此，理由待验证」。
2. **一个判据只有一个源头。** 母本 → `references/`（可移植副本）→ 实例（落地副本），三份都要改，但源头唯一。
3. **改完母本必须回来更新台账状态。** 台账过期 = 下一轮又按老假设办事。

> **反模式**：把「这次踩的坑」直接塞进 SKILL.md 正文。SKILL.md 是**流程**，踩坑是**证据**——
> 混在一起，三个月后没人分得清哪条被验证过。证据进 `evidence.md`，流程才进正文。
