# 新仓第一天：AGENTS、文档、代码规范、目录

四样东西一次定下来，后面才不会越加越乱。**判据优先于模板**：模板可以照抄，判断不能。

## 0. 第一天五件事

1. **`AGENTS.md`**：只放红线 + 指针，目标 ≤220 行 / 16.5KB；超了说明该拆到 `docs/`。
2. **`docs/`**：第一个功能落地时就定下「契约 / 口径 / 实现」三分，别等到有 20 份再回头分。
3. **每份文档第一行写状态**，并在 AGENTS 那张表里给它一行。
4. **实例化文档约定**：把通用条款复制成该仓 `docs/doc-conventions.md`，顶部写明母本路径，只追加本仓特有的文档表。
5. **实例化代码设计规范**：把 `references/code-design.md` 全文复制成 `docs/code-design.md`，删掉与本栈不符的章节；「本仓现状」节先留空，第一个功能落地后补（见 §2.6）。

## 1. `AGENTS.md`

### 1.1 先记住那条实测数据

某仓的 AGENTS.md 曾写到 **1117 行 / 106KB**，结果**只有前 17% 进得了上下文** —— 后面 83% 的红线写得再好，AI 也读不到。

| 指标 | 上限 | 超了怎么办 |
| :--- | :--- | :--- |
| 行数 | **≤ 220 行** | 拆到 `docs/`，AGENTS 只留一句结论 + 指针 |
| 体积 | **≤ 16.5KB** | 同上 |

### 1.2 每条内容先过三问

**三条缺一条就别写进 AGENTS**：

1. **每次动代码都要遵守吗？** —— 只对某个功能成立 → 进 `docs/`。
2. **不知道会不会写错 / 搞坏？** —— 显然不会踩的常识 → 删掉。
3. **能一句话说清吗？** —— 要三段话解释的判据、实测数据、决策历史 → 进 `docs/`。

留下来的形态统一是：**一句结论 + 一个指针**。

### 1.3 写法规矩

1. **索引只有一张表，就在 AGENTS 里**。不额外建 `README.md` 当第二索引。
2. **红线和指针必须成对出现**。只写「见 `docs/xxx.md`」等于没写。
3. **用 🔴 标「不知道就会搞坏」的条目**，一个仓控制在 10~20 条。满屏红点 = 没有红点。
4. **不写「项目简介」「如何安装」**。AI 需要判据，不是产品介绍。
5. **改完代码先改 AGENTS，再改 docs**。顺序反了会出现「文档说 A、红线说 B」。
6. **一份 AGENTS 只服务一个仓**。跨仓契约放生产方，消费方只放指针。

骨架直接用 `assets/AGENTS-template.md`。

## 2. 文档

### 2.1 四个问题（有一个答不上就别新建）

| 类型 | 放哪 | 判据 |
| :--- | :--- | :--- |
| 契约（表 / 接口 / 消息帧 / 错误码） | **生产方那一仓**；跨端功能收敛到一份「施工图」 | 谁定义谁维护，消费方只放指针 |
| 产品口径（文案 / 交互 / 三态 / 期别） | 需求方那一仓 `<功能>-v<N>.md` | 会随产品决策变 |
| 实现判据（页面 / 踩坑 / 冒烟） | 实现方那一仓 `<功能>-frontend.md` / `<主题>.md` | 换个实现就失效 |
| 「为什么这么设计、哪些方案被否」 | **并进对应实现文档的决策节，不单独开一份** | 单开一份必然烂尾 |

**能不能塞进已有文档的一节？** 能就不新建。**每多一份文件，就多一处要同步的地方。**

🔴 **跨仓 / 跨端两边都不复制字段 / 接口副本，只放指针。**
典型烂法：方案文档里抄了一份表结构，三个月后字段改名，四份文档还在指着旧名。

### 2.2 命名

| 类型 | 命名 | 例 |
| :--- | :--- | :--- |
| 实现口径 | `<功能>-frontend.md` | `mock-interview-chat-frontend.md` |
| 产品口径 | `<功能>-v<N>.md` | `ai-interview-v1.md` |
| 后端主题方案 | `<主题>.md`（**不加 frontend 后缀**） | `ai-interview-report-ticket.md` |
| 设计稿 | `<功能>-v<版本>-<模块>.html`；基准稿 `*-redesign.html` | `me-page-v2-hero.html` |
| 跨仓引用 | 按相对仓名写 | `pass-up.backend/docs/xxx.md` |

### 2.3 每份文档第一行必须是状态

```md
> 状态：**现行**（2026-10-30）
> 状态：**已完结**（阶段 0~4 全部合入，改代码请转 full-checklist）
> 状态：**已归档**（2026-10-30，被 xxx 取代，只作历史留痕）
```

判据：**读者打开第一眼就该知道「这份还算不算数」**。没有状态行 = 默认为「现行」，那就必须一直维护它 —— 大多数烂尾文档都是这么来的。

### 2.4 索引只有一个

- 唯一入口是各仓 `AGENTS.md` 的文档表（**一行 = 一个功能 / 模块**）。
- 🔴 **不新增 README 类索引**：两个索引必然漂移。
- 归档文档在入口表里标 🗄。

### 2.5 母本 / 实例：双写边界

「同一件事两个地方写」是漂移的起点，但有一处**无法避免的双写**：AI 只加载当前仓的上下文，读不到别的仓。所以把双写范围钉死：

| 内容 | 母本 | 实例（项目仓） |
| :--- | :--- | :--- |
| 四问、命名、状态行、索引唯一 | ✅ 唯一权威 | 照抄，**不许自行改** |
| 本仓文档表 / 本仓路径 / 专有样例 | ❌ 不写 | ✅ 只写这些 |

### 2.6 代码设计规范也要第一天落地，但只落地一半

[文档四问](#21-四个问题有一个答不上就别新建)管「要不要新建这份文档」，代码设计规范管「代码写出来长什么样」（职责边界、状态机、事务幂等、抽象时机）。它跟目录结构一样属于**第一天定形**的东西 —— 定晚了，第一批代码就是在无规范状态下写的。

但它的两步不在同一个时间点，别混：

| 阶段 | 动作 | 为什么 |
| :--- | :--- | :--- |
| **第一天** | 全文复制成 `docs/code-design.md`；状态行改 `实例 · 现行（母本：…）`；删掉与本栈不符的章节 | 仓内读不到母本，规范只存在别的仓 = 等于没写 |
| **第一个功能落地后** | 补「本仓现状」：最大的 3~5 个类及行数、状态字段在哪、哪些模块互相调用 | 没有代码时这一节只能编，编出来的阈值比不写更坏 |

🔴 **实例必须留全文，不许改成「指针 + 差异」**。这跟 §2.5 是同一个理由：AI 不跨仓读文件。

AGENTS 里只留 3~5 条最反直觉的指针（如「状态转换只许走 `XxxStateMachine`」），正文不进 AGENTS。

## 3. 目录结构

### 3.1 一句话

**按业务能力组织代码，而不是按技术类型堆代码。**

- `features/order/`（业务优先）✅
- `api/` + `services/` + `store/` 各堆几十个文件（技术类型优先）❌

### 3.2 切分判据（三个问题）

| 问题 | 答案 | 放哪 |
| :--- | :--- | :--- |
| 只服务**一个**业务能力？ | 是 | 该 `features/<能力>/` 内部 |
| **两个以上**业务都要用？ | 是 | 下沉到 `shared/`（无业务耦合才行） |
| 这个职责**现在不存在**？ | 是 | 🔴 **不建空目录、不建空文件** |

> 判据：**目录是长出来的，不是规划出来的。** 需要第二个文件时才建目录。

### 3.3 依赖方向（只许单向）

```text
pages / routes  →  features  →  shared（api / ui / domain / utils）
```

| 层 | 可以依赖 | 🔴 禁止 |
| :--- | :--- | :--- |
| `pages` | 本页私有组件、`features`、`shared` | 页面之间互相 import；直接写请求 |
| `features` | `shared`、**其他 feature 的 `index.ts`** | 跨 feature 读对方内部文件（含 store） |
| `shared` | 无（最底层） | 反向引用 `features` / `pages` |

跨 feature 通信的三条正路：**走共享 store（明确归属）**、**走对方 `index` 暴露的接口**、**在页面层编排**。

### 3.4 feature 内部

```text
features/<能力>/
  api.ts        # 只发请求，一个函数一个接口
  types.ts      # DTO / 枚举
  service.ts    # 多接口编排、重试、数据转换
  store.ts      # 只放跨组件/跨页面状态
  nav.ts        # 只放「跳转意图」
  components/   # 只被本 feature 用的组件
  index.ts      # 对外出口（需要时才建）
```

**单接口直接用 `api.ts`；只有「多接口 + 状态变更 + 重试」才值得加 `service.ts`。**

### 3.5 后端：竖切有阈值

前端那条原则换个名字：**按领域切包，不按 controller/service/mapper 横切**。但**收益随业务数线性增长，成本固定**：

| 条件（任一不满足就先别竖切） | 判据 |
| :--- | :--- |
| 领域 ≥ 10 个，或接口 ≥ 30 个 | 少于此数，三个包一眼看得完 |
| 有 ≥ 2 人同时改后端 | 单人开发的成本只是多按两次 `Ctrl+P` |
| 表数 ≥ 10，存在跨聚合的一致性边界 | 6 张表没有聚合边界问题 |
| 将来要换库 / 并行多存储 | 换库压力落在 store 层，不在包的形状 |

反例是「照抄 DDD 分层」：6 张表的单人项目切成四层，加一个字段改 5 个文件。

### 3.6 反例速查

| 反例 | 为什么错 | 改法 |
| :--- | :--- | :--- |
| 为「结构完整」建 5 个空目录 | 半年后分不清空的和废弃的 | 需要第二个文件时再建 |
| 页面直接 `fetch` | 绕过鉴权与错误处理 | 走 feature 的 `api` |
| Feature A import Feature B 的 store | 状态归属不清，改 B 坏 A | 下沉共享状态或走对方出口 |
| 用 URL query 传长文本 | 超长静默截断，用户数据被改 | 走 `nav.ts` 的一次性意图 |
| `utils/` 里塞业务逻辑 | 最底层反向依赖业务 | 挪回对应 feature |

## 4. 验收

- [ ] `AGENTS.md` ≤220 行 / 16.5KB，只有结论 + 指针，🔴 10~20 条；
- [ ] 每份文档第一行有状态，且在 AGENTS 表里有一行；
- [ ] 没有第二份索引（README 类）；
- [ ] 没有空目录 / 空文件；`shared/` 不 import `features/`；
- [ ] 跨仓契约只在一处，另一处是指针；
- [ ] `docs/doc-conventions.md` 顶部写明母本，且只追加了本仓内容；
- [ ] `docs/code-design.md` 存在、状态行是「实例 · 现行（母本：…）」、不适用章节已删；「本仓现状」可留空但不得编造。

## 5. 附件

- `assets/AGENTS-template.md` —— 可直接复制的骨架。
- `references/doc-conventions.md` —— 文档治理全文（四问、命名、状态、索引、母本实例）。
- `references/code-design.md` —— 代码设计全文（职责边界、状态机、事务幂等、抽象时机、交付自检）。
- `references/directory.md` —— 目录判据全文（依赖、feature 职责、后端阈值、各栈指针）。

母本在 cqlql-notes 仓 `docs/工程/`：`AGENTS模板.md`、`文档约定.md`、`代码设计规范.md`、`目录结构规范.md`。目标仓读不到时，以本 skill 为准。
