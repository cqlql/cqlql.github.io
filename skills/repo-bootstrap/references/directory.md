# 目录结构判据（通用全文）

本文只写**跨栈通用判据**。各栈的具体目录树不在这里重复，见文末指针表。

> 节标题后的 `〔前端〕` / `〔后端〕` 是**裁剪标记**：实例化时只留与目标仓栈匹配的节，无标记 = 全栈通用。
> 规则见 `SKILL.md` §0.5；本文是只读参考（结论写进 AGENTS 的「目录与边界」节），不整份复制。

## 一、一句话

**按业务能力组织代码，而不是按技术类型堆代码。**

- `features/order/`（业务优先）✅
- `api/` + `services/` + `store/` 各堆几十个文件（技术类型优先）❌

技术类型优先在小项目里很顺手，一旦过 20 个模块就开始出问题：改一个功能要在四个目录之间跳，删一个功能要在四个目录里翻残留。

## 二、切分判据（三个问题）

| 问题 | 答案 | 放哪 |
| :--- | :--- | :--- |
| 只服务**一个**业务能力？ | 是 | 该 `features/<能力>/` 内部 |
| **两个以上**业务都要用？ | 是 | 下沉到 `shared/`（无业务耦合才行） |
| 这个职责**现在不存在**？ | 是 | 🔴 **不建空目录、不建空文件** |

第三条最常被违反：为了「结构完整」先建出 `hooks/`、`service/`、`types/` 五个空目录，结果半年后没人知道哪个是空的、哪个是废弃的。

> 判据：**目录是长出来的，不是规划出来的。** 需要第二个文件时才建目录。

### 为什么是单一 `shared/`，不是三个顶层〔前端〕

三个平级顶层目录正是「全局目录爆炸」：它们各自会长到几十个文件，而**「谁能依赖谁」在目录上一眼看不出来**。

```text
shared/
  api/      # 请求封装（鉴权、错误、mock 开关）
  ui/       # 跨 feature 的展示组件
  domain/   # 枚举、标签映射等无状态的业务词汇
  utils/    # 纯函数
```

规则只有一条：**`shared/` 不得 import 任何 `features/`**。

## 三、依赖方向（只许单向）〔前端〕

```text
pages / routes  →  features  →  shared（api / ui / domain / utils）
       ↓              ↓
   shared/ui ←────────┘   （只允许 features 引用通用组件）
```

| 层 | 可以依赖 | 🔴 禁止 |
| :--- | :--- | :--- |
| `pages`（路由页） | 本页私有组件、`features`、`shared` | 页面之间互相 import；直接写请求 |
| `features` | `shared`、**其他 feature 的 `index.ts`** | **跨 feature 读对方内部文件**（含 store） |
| `shared` | 无（最底层） | 反向引用 `features` / `pages` |

跨 feature 通信的三条正路：**走共享 store（明确归属）**、**走对方 `index` 暴露的接口**、**在页面层编排**。没有第四条「直接 import 对方内部文件」。

### 页面放哪：顶层 `pages/` 还是 feature 内？

| 布局 | 适用 | 例子 |
| :--- | :--- | :--- |
| 顶层 `pages/`，`features/` 只存业务逻辑 | 页面彼此共享布局、页面本身就是全局路由的一部分 | Vue / React 后台管理、官网 |
| `features/<能力>/pages/` | 页面按业务归属明确，且要能**整块删除** | Taro 小程序、Next App Router |

判据是**「删掉一个业务，能不能只删一个目录」**。无论哪种，**路由表只有一份**，只登记路径、不写逻辑。

## 四、feature 内部〔前端〕

```text
features/<能力>/
  pages/<page>/index.tsx  # 路由页：取数 + 拼装，不写业务细节
  api.ts        # 只发请求，一个函数一个接口
  types.ts      # 该 feature 的 DTO / 枚举
  service.ts    # 多接口编排、重试、数据转换
  store.ts      # 只放跨组件/跨页面状态
  components/   # 只被本 feature 用的组件
  hooks/        # 只被本 feature 用的 hook
  nav.ts        # 只放「跳转意图」
  index.ts      # 对外出口（可选）
```

| 文件 | 职责边界 | 常见越界 |
| :--- | :--- | :--- |
| `api.ts` | 拼参数、调统一请求封装、返回类型化结果 | 写业务判断、弹 toast |
| `service.ts` | 多接口编排、状态更新、失败重试 | 变成第二个 `api.ts`（只是转发） |
| `store.ts` | 跨页面/跨组件共享 | 只在一个组件用的状态也塞进去 |
| `nav.ts` | 跳转意图的一次性传递 | 写取数、写业务判断 |
| 页面 | 生命周期、布局、路由参数 | 把业务逻辑写进页面 |

**单接口直接用 `api.ts`；只有「多接口 + 状态变更 + 重试」才值得加 `service.ts`。**

### `api.ts` 还是 `api/<resource>.ts`？

一个 feature 只打一个资源时用单文件；**出现第二个资源才升级成目录**。

### 页面之间怎么传参（`nav.ts`）

小程序 / Taro 有硬限制：**`switchTab` 不吃 query**，`navigateTo` 的 query 超长会静默截断。

所以「跨页传长 / 复杂数据」走进程内的一次性意图：

```text
features/<能力>/nav.ts     # set 一份 → 目标页 take 一次并清空
```

三条不变量：**写入即覆盖**、**取走即清空**、**不落 storage**。

短参数（`?id=`、`?type=`）仍走 URL。

## 五、页面层的三条禁令〔前端〕

1. 🔴 **页面之间不许互相 import**。复用业务代码归 feature，复用展示组件归 `shared/ui`。
2. 🔴 **页面不直接发请求**。一律经 feature 的 `api` / `service`。
3. **一次性私有组件放页面目录下**，不要为「以后可能复用」提前上提。

## 六、后端：竖切有前提〔后端〕

**按领域切包，不按 `controller/service/mapper` 横切。**

| 前端 | 后端 | 判据 |
| :--- | :--- | :--- |
| `features/<能力>/api.ts` | `<domain>/controller` | 一个能力一个包 |
| `service.ts` | `<domain>/service` | 编排、事务边界 |
| `types.ts` | `<domain>/dto` | 出入参 |
| `shared/utils` | `common/` / `infra/` | 无业务耦合 |

🔴 不要「所有 controller 一个包、所有 service 一个包」——加一个业务要改三个包。

### Java / Go 不能互抄

| | Go | Java |
| :--- | :--- | :--- |
| 包/目录有编译期约束吗 | 有（`internal/` 由编译器挡） | **没有** |
| 竖切靠什么强制 | 目录名 | Maven/Gradle **多模块**，或 ArchUnit |
| 资源与代码同根吗 | 是 | **否**（`src/main/java` 与 `resources` 两棵树） |

### 先看阈值

竖切的收益是「删一个业务只清一个包」，成本是每个业务多建 3–4 个包。
**收益随业务数线性增长，成本固定**：

| 条件（任一不满足就先别竖切） | 判据 |
| :--- | :--- |
| 领域 ≥ 10 个，或接口 ≥ 30 个 | 少于此数，`internal/{api,store,domain}` 三个包一眼看得完 |
| 有 ≥ 2 人同时改后端 | 单人开发只是多按两次 `Ctrl+P` |
| 表数 ≥ 10，存在跨聚合一致性边界 | 6 张表没有聚合边界问题 |
| 将来要换库 / 并行多存储 | 换库压力落在 store 层 |

> 前后端不对称是**允许**的。前端的痛点是「删不干净」，后端的痛点是「找不到」。

## 七、反例清单

| 反例 | 为什么错 | 改法 | 适用 |
| :--- | :--- | :--- | :--- |
| 为「结构完整」建 5 个空目录 | 分不清空的和废弃的 | 需要第二个文件时再建 | 通用 |
| `utils/` 里塞业务逻辑 | 最底层反向依赖业务 | 挪回对应 feature | 通用 |
| 页面直接 `fetch` / `Taro.request` | 绕过鉴权与错误处理 | 走 feature 的 `api` | 前端 |
| Feature A import Feature B 的 store | 状态归属不清 | 下沉共享状态或走对方出口 | 前端 |
| 页面里手拼路由路径 | 改路由时漏改一处，白屏 | 从 feature `index.ts` 取常量 | 前端 |
| 用 URL query 传长文本 | 超长静默截断 | 走 `nav.ts` 的一次性意图 | 前端 |
| 所有组件丢 `components/` | 全局目录爆炸 | 只放跨两个业务复用的 | 前端 |
| 6 张表照抄四层 DDD | 加一个字段改 5 个文件 | 看 §六 阈值 | 后端 |

> 实例里删掉「适用」不是本仓的行；本仓两栈都有就全留，并在表头补一句各行的适用范围。
