# 代码设计规范（通用全文）

本文只管**代码写出来之后长什么样** —— 职责是否混杂、状态是否可控、事务是否安全、抽象是否值得。

一句话边界：本文只回答「**怎样设计代码，才能在满足当前需求的同时保持合理的职责边界、复杂度和可维护性**」。
性能是否达标、测试是否充分、SQL 是否高效，都不是本文的判断标准。

**本文不管的四件事：**

- 目录怎么切、依赖往哪指 → `references/directory.md`
- DDD 四层各放什么、跨层数据怎么转换 → 各栈自己的 DDD 文档（有则指向，无则别提前建层）
- SQL / ORM 怎么写、索引与分页怎么选、并发更新与加锁顺序 → `references/sql-orm.md`
  （本文第四节只管**事务代码**怎么写，数据库侧的原子更新、加锁顺序、死锁重试在那边 §5.7）
- 怎么验证（测试、性能、静态分析）→ 本仓 `AGENTS.md` 的验证命令 + 交付说明

代码规范进 `AGENTS.md` 的方式见第十一节，**正文一律不进**（AGENTS 有体积上限）。

> 节标题后的 `〔后端〕` / `〔Java〕` 是**裁剪标记**：复制成实例时只留与目标仓栈匹配的节，
> 无标记 = 全栈通用。规则见 `SKILL.md` §0.5。

## 零、四条元规则（优先级高于下面所有条款）

1. **先读再改**：改任何类之前先看现有实现和调用方。不要因为「看起来能更优雅」就推倒重写。
2. **最小必要拆分**：拆分的依据是**变化原因不同**，不是行数。同一个变化原因的逻辑留在同一个类里。
3. **抽象必须能说出它解决了什么实际问题**：说不出来就是过度设计，不写。
4. **规则是判断依据，不是机械执行清单**：下面的条款描述的是「什么情况下该警觉」，
   不是「命中就必须改」。判断标准是**当前实现有没有实际代价**，以及**改动能不能带来明确收益**。

### 规则适用性（第 4 条元规则的展开）

1. 条款默认适用，但**允许基于具体场景做例外**。
2. 例外必须有业务或技术理由，**不能只是为了省事**。
3. 不要为了满足某条规则，引入比原问题更复杂的设计（拆出来的东西比原来更难读 = 失败）。
4. 性能、资源、并发这类问题以**实际运行数据和验证结果**为依据，不凭主观猜测。
5. 发现存量代码违反规范时，**不顺手扩大修改范围**：先判断它与本次任务是否相关，不相关就报告、不动手。

**几个典型的不构成违规的情形**（写在这里是为了避免被机械套用）：

| 现象 | 什么时候可以保留 |
| :--- | :--- |
| 方法 200 行 | 都是同一件事的协议分支 / 步骤串联，且顺序就是业务顺序 |
| 类注入 7+ 依赖 | 它本来就是编排类，依赖分属同一变化原因（不是七件事各沾一点） |
| 两处相似代码 | 差异在**行为**且未来会分叉，强行抽象反而要传一堆开关参数 |
| `interface + Impl` 只有一个实现 | 它是**外部依赖的适配边界**（要 mock 第三方 SDK），不是为了「解耦」 |
| 一个 Service 直接查两张表 | 同一模块内的聚合查询，没有跨模块数据归属问题 |

### 必须警惕的反模式（AI 尤其容易犯）

```text
发现某个 Service 有 1400 行
  → 机械拆成 5 个 Service
  → 每个配 1 个接口
  → 加 Factory / Strategy / Facade
```

这不是重构，是把「一个难读的类」换成「六个互相调用、需要来回跳的类」。
正确路径：**找出不同的变化原因 → 判断是否真的独立 → 选最小拆分 → 验证行为未变**。

**代码质量不由类的数量和方法行数衡量。** 现存 1400 行的类往往不需要现在拆，
需要的是**别再往里加新职责**。

## 二、职责边界

### 规则

- **模块边界 = 数据归属边界**：跨模块协作走对方的 **Service 方法**，不许直接注入别的模块的
  Repository，也不许在别人的 entity 上做写操作。
  - 反例：在 A 模块里直接 `bRepository.save(...)` 改 B 的数据。
  - 正例：调 B 的语义化方法（它负责校验、记账、发事件）。
- **Controller 不写业务规则**：只做参数绑定、权限注解、调 Service、包统一响应。
  出现 `if (order.getStatus().equals("PENDING"))` 就是规则漏到了错误层。
- **不要让一个模块承担别人的职责**：实时会话模块不负责计费，编排层不负责持久化细节。
  判断方法：问「这段逻辑的变化原因，跟着谁的需求走」，跟着谁就放谁那儿。

### 边界 ≠ 层层转发

模块边界解决的是**数据归属**，不是「每个业务动作都必须穿过 N 层」：

- 不要为了形式上的隔离加**纯转发层**：`Controller → XxxFacade → XxxService → XxxManager`
  四层都在做同一件事，只是把一次调用拉长了。转发层自身没有逻辑就是负债。
- 模块**内部**按实际复杂度组织：一次简单查询、一次单表写入，一个 Service 方法直接做完即可，
  不需要先拆 Manager / Helper / Support。
- 跨模块调用要走对方**语义化的业务方法**，但**不要求把每个方法都抽成接口**：
  只有一个实现、只被一个模块调用时，直接用类；接口留给「真的会有第二实现」或「要 mock 外部依赖」的地方（第七节）。
- 不要为了「看起来像 DDD」批量生成接口、Facade、Adapter —— 抽象的成本由后面维护的人付。

### 新增代码往哪放（决策顺序）

1. 属于已有模块的已有职责 → 加进该模块的 Service；
2. 是该模块的**新变化原因**（例如订单模块里新增「发票」）→ 新建 Service，不加进主流程服务；
3. 跨模块复用 → 先看 `shared/` / `common/` 有没有，没有再考虑下沉，**不要提前下沉**。

### 不要把文档塞进源码目录

不要用 `modules/<模块>/AGENTS.md` 这种布局：`.md` 混进源码目录会被资源处理/扫描规则误伤。
模块约束写进 `docs/` 对应文档，`AGENTS.md` 只放指针。

## 三、状态与状态机

### 规则

- **状态用枚举，不用裸字符串/数字**。判断依据：这个值会不会被 `switch`、会不会有非法取值、
  会不会出现在多个 `if` 里 —— 有一个「会」就该是枚举。
- **状态转换必须集中**：允许的路径写在一个地方（枚举方法 / 专门的 `XxxStateMachine` /
  实体的 `canXxx()`），**不要**在 5 个 Service 里各写一遍 `if (status == ...)`。
- **非法转换必须显式失败**，不是静默忽略。
- **不要用条件更新代替状态机**（见下表）：`UPDATE ... WHERE status='PENDING'` 只能防并发，
  它不会告诉你「这个转换本来就不该存在」。
- 枚举值的**影响面要写在枚举的注释里**（新增一个值必须同步哪几处），
  否则下一个人加值就会漏。

### 状态机、条件更新、数据库约束：三者是叠加关系〔后端〕

| 机制 | 回答的问题 | 不能替代什么 |
| :--- | :--- | :--- |
| **状态机**（枚举 / 转换表 / `canXxx()`） | 哪些转换在业务上**合法** | 防不住并发：两个请求同时读到 `PENDING`，都能通过校验 |
| **条件 UPDATE**（`WHERE status='PENDING'`，判断影响行数） | 并发下**谁能原子地抢到**这次推进 | 表达不了业务规则：它不知道哪些转换本来就不该存在 |
| **数据库约束**（CHECK / 唯一索引 / 外键） | 非法数据**落不了库**（最后一道兜底） | 表达不了流程：它只保证数据形状，不保证业务顺序 |

```sql
UPDATE recharge_order
SET status = 'SUCCESS'
WHERE id = :id
  AND status = 'PENDING';   -- 只有一个并发请求的影响行数为 1
```

这条 SQL 能保证「只有一个请求推进成功」，但它本身**不是一个状态机**：
如果业务上不允许 `PENDING → SUCCESS`（必须先 `PAID`），它照样会成功。

反过来，代码里写了完整状态机，也**不能省掉并发保护** —— 校验通过和真正写入之间还有窗口。

**结论**：状态机管「该不该」、条件更新管「谁抢到」、约束管「兜底」。
三者都在各自的位置上做一件事，不要指望其中一个把另外两个的活干完，
也不要为了「三者齐全」再套一层 StateMachine 框架 —— 一个枚举方法加一条带条件的 UPDATE 就够了。

### 实例必须补

本仓有哪些生命周期（订单、会话、任务、批次），各自的状态取值和允许的转换路径。

## 四、事务与幂等（钱 / 权益类最高优先级）〔后端〕

### 事务边界

- **一个事务 = 一个原子业务事实**，范围尽量短：事务里只做数据库写。
  网络请求、文件 IO、模型调用一律移到事务外 —— 外部调用慢、会超时，事务持有连接期间锁着行。
- 涉及「资金事实」与「资产收口」两类记录时，**分两段事务**：先记事实，再收口资产，
  中间失败靠补偿而不是靠一锅大事务。
- **数据库提交与外部系统调用无法构成一个原子事务**。需要可靠投递时按业务要求选机制：
  Outbox / 本地消息表 / 对账补偿，**不要**用「提交后立刻发 MQ，发失败就抛异常回滚」假装原子。

### 自调用导致注解失效：按这个顺序处理〔Java〕

`this.xxx()` 不走代理 → `@Transactional` / 切面类注解全部静默失效。发现自调用后：

1. **优先重新划分事务职责**：把需要独立事务的那一段提取成另一个 Service 的方法。
   最干净，而且通常顺带修正了一个职责问题。
2. **只是要一个明确的事务边界、暂时不想动结构** → 用 `TransactionTemplate` 显式包住那一段：
   事务边界写在代码里看得见，不依赖代理，也不会引出自我注入。
3. **确实必须保留当前类结构** → 才用 self 自引用代理，并在字段注释里写清「为什么不能提取」：

   ```java
   /** 自引用代理：用于突破 @Transactional 自调用失效，通过代理触发事务边界。
    *  未提取独立 Service 的原因：<具体原因>。 */
   @Lazy
   @Autowired
   private XxxService self;
   ```

**不要把 `@Lazy self` 当成默认方案。** 它是最后手段，不是首选写法；
它**只解决自调用**，不是循环依赖的解法（见第五节）。

### 幂等

- **支付回调、外部通知、订阅消息、定时任务**必须幂等：重复到达不能产生第二份权益。
- **重试必须幂等**：框架重试、MQ 重投、网关超时重发、人工补单，都属于「同一件事来了第二次」。
  没有幂等保证的重试是把小故障放大成资损。
- 实现优先「唯一约束 + 抢占式更新」（`UPDATE ... WHERE 状态=预期`，判断影响行数），
  不要「先查后写」（并发下必漏）。
- **幂等不能只靠 Java 层判断**：内存标记、`if (已经处理过) return` 在多实例 / 重启 / 重放场景下不可信。
  关键业务事实要有数据库唯一约束或原子条件更新兜底（见第三节表）。
- **抢占失败必须抛**，不能静默返回 `false` / `null` 让调用方以为成功了。
- 资产扣减类操作**先冻结再确认**，不要「先发后用」。

## 五、依赖

> 依赖**方向**（谁可以 import 谁、跨模块怎么通信）见 `references/directory.md` 的依赖方向一节。
> 本节只管**注入关系**（谁持有谁的实例、循环依赖怎么办）。

### `@Lazy` 只许用于 self 自引用，不许用于掩盖循环依赖〔Java〕

两者在代码里长得一样、后果完全不同：

| 用法 | 是否允许 | 说明 |
| :--- | :--- | :--- |
| `@Lazy @Autowired private XxxService self;`（指向自己） | ⚠️ 最后手段 | 为了让 `@Transactional` 经代理生效，优先按第四节顺序处理 |
| `@Lazy` 注入**另一个** Service 来打破 A↔B 循环 | ❌ | 把「启动期报错」推迟成「运行期调用时序问题」 |

发现模块间循环依赖时**不要加 `@Lazy` 绕过**，按顺序判断：
① 是否有一方的职责放错了模块（多数情况是这个）；
② 能否用接口收窄依赖；
③ 是否为「A 完成后要通知 B」—— 那应该是**领域事件**，不是 B 反过来依赖 A。

### 依赖数量是信号，不是判据

- 一个类注入 **7 个以上**依赖时，先问「这些依赖是不是分属不同变化原因」。
  - 是 → 说明这个类在承担多件事，考虑按变化原因拆；
  - 不是（编排类、门面类本来就要协调多方）→ **保留，不拆**。
- 新增依赖时不要顺手引入整条链路：为了用一个工具方法去注入一个重服务，
  等于把它的所有依赖传染进来。

## 六、数据建模

- **持久化模型不出模块**（Java 的 Entity、前端直接映射后端响应的那层对象）：
  Controller 不返回 Entity、不被别的模块当参数接收。
  不是因为「DTO 更规范」，而是 Entity 带持久化注解与懒加载语义：一旦作为响应，
  加字段就成了对外契约变更，且会把不该暴露的列（内部状态、风控标记、软删除位）发出去。
- **数据库存真实数据，展示默认值由 UI / DTO 决定**：不要为了前端好看在 entity 里写默认值或拼文案。
- **避免基本类型偏执**：金额、状态、角色、类型这类有业务含义的概念用枚举或值对象表达，
  别用 `String` / `int` / `boolean` 裸传。**`boolean` 参数不要超过一个** ——
  `execute(true, false, true)` 的调用点无法阅读。
  - 反过来的例外：纯技术性的开关（`retryable`、`dryRun`）用 `boolean` 没问题，
    不要为了「不裸传」给它造一个只有两个值的值对象。
- **数据泥团**：一组参数总是同时出现（`(userId, orderNo, amount, channel)`）→ 收成一个参数对象，
  但**只在真的每次都一起出现时才收**，不要为了一次调用造对象。

## 七、抽象的时机

**允许抽象**（满足其一即可）：

- 同一段业务规则已经在**两处以上**真实重复，且未来还会增加第三处；
- 已经出现第二个实现（第二个支付渠道、第二种存储），且差异在**行为**而非参数；
- 外部依赖需要隔离以便测试（适配器包住第三方 SDK 是合理的）。

**禁止抽象**：

- 「以后可能要支持多种…」—— 没有第二种实现就不建接口；
- 只有一个实现、且只被注入一次的 `interface + Impl` 对；
- 为了「解耦」而加的中间层，中间层自身没有任何逻辑（纯转发）；
- 把简单 `if/else` 换成 `Strategy` + `Factory` + 注册表三件套。

**判断标准**：抽象后的调用方代码是否**变短、变清晰**。如果调用方需要先理解工厂和注册表，
就是抽象失败。

## 八、可观测性与异常处理

### 失败要分类表达（不要一律抛，也不要一律吞）

| 类型 | 表达方式 |
| :--- | :--- |
| **预期业务拒绝**（余额不足、订单已过期、无权限、重复提交） | 明确的业务结果（`Result.rejected(...)` / 业务错误码），调用方能区分，**不打 error 日志**、不抛未知异常 |
| **系统异常**（DB 连不上、第三方超时、NPE） | 记录必要上下文后**传播或按策略处理**，禁止吞掉 |
| **违反业务不变量**（出现了不该存在的状态组合） | **立即显式失败**，不降级、不「尽力而为」地继续执行 |
| **可恢复异常**（限流、瞬时超时、锁冲突） | 按业务策略重试 / 降级 / 补偿，且**必须幂等**（第四节） |

```java
// 这是明确的业务拒绝，不是静默失败
if (order.isExpired()) {
    return RefundResult.rejected("订单已过期");
}
```

**唯一的硬要求：调用方必须能区分成功与失败。**
「静默失败」指的是调用方**无法感知失败**，不是「没有抛异常」——
把预期业务分支包装成异常抛出去，同样是设计问题（调用方被迫用 `try` 做流程控制）。

### 日志

- **关键分支必有日志，且带可关联 ID**（业务单号、逻辑会话 ID、traceId）。
- **禁止打印密码、Token、密钥、完整手机号、身份证**；请求体日志在过滤器层统一处理，
  不要在业务里重复打。
- 钱 / 权益类操作**手工打点**，不依赖切面注解（自调用会失效，见第四节）。

## 九、坏味道速查（按优先级）

> 这张表是**检查信号**，不是违规清单。命中只代表「值得看一眼」，
> 是否要改取决于它有没有造成实际代价（难改、易错、查不出问题）。见第零节第 4 条。

| # | 坏味道 | 典型形态 | 处置 |
| :-- | :--- | :--- | :--- |
| 1 | **散弹式修改** | 改一条规则要同时改多个 Service + 状态常量 + 前端公式 | 规则集中到一处 |
| 2 | **状态机缺失** | 状态是裸字符串，转换散落 | 见第三节 |
| 3 | **幂等缺失** | 回调 / 通知 / job 重复执行发两份权益 | 见第四节 |
| 4 | **事务边界错误** | 事务里调外部 HTTP / 模型 | 见第四节 |
| 5 | **隐式依赖** | 依赖某个 Service 的副作用（它顺带改了状态） | 显式返回值 + 显式调用 |
| 6 | **循环依赖** | A↔B 互注，用 `@Lazy` 压住 | 见第五节，**不许绕过** |
| 7 | **过长方法** | 单方法 200+ 行 | 若是协议分支/顺序步骤 → 抽私有方法即可；若混杂多个变化原因 → 才拆 Service |
| 8 | **过深嵌套** | 5 层 `if` | 卫语句前置返回 |
| 9 | **魔法值** | `if (status == 3)`、裸 `"SUCCESS"` | 常量 / 枚举 |
| 10 | **重复代码** | 同一段公式前后端各写一份 | 至少写清「两处必须同步」+ 文档 |
| 11 | **Feature Envy** | A 反复取 B 的字段来算 B 自己的事 | 把行为移回 B |
| 12 | **过度抽象** | 单实现接口、纯转发层、预埋扩展点 | 删 |
| 13 | **注释与代码不一致** | 注释说「不落库」实际已落库 | 改代码时同步注释，注释是契约 |
| 14 | **长事务锁竞争** | 事务持有行锁等外部 IO | 缩短事务，异步化 |

## 十、交付前自检（只看设计）

改完代码逐条过（不适用写「不涉及」，**不要静默跳过**）：

- [ ] 是否让某个类的职责变多？新增逻辑是否放错了模块（第二节）？
- [ ] 是否直接读写别的模块的 Repository / Entity？
- [ ] 有没有为了形式上的隔离加纯转发层 / 单实现接口（第二节、第七节）？
- [ ] 状态是否有新的非法转换路径？转换是否集中？有没有用条件更新代替状态机（第三节）？
- [ ] 新流程会不会被重复请求触发两次？抢占失败是否抛？幂等有没有数据库层兜底（第四节）？
- [ ] 事务里有没有外部 IO？有没有自调用导致注解失效（第四节）？
- [ ] 新增 `@Lazy` 吗？如果是用来打破循环依赖 → 改设计（第五节）。
- [ ] 失败分支的表达方式对不对：业务拒绝 vs 系统异常 vs 不变量违反（第八节）？
- [ ] 有没有静默 `catch`、`return null` 当错误用？日志里有没有敏感信息？
- [ ] 改动是否超出本次需求范围？超出的部分**报告，不擅自改**。

**验证不在本文范围**：测试、性能、静态分析按本仓 `AGENTS.md` 的验证命令执行，
结果和未解决问题写进交付说明。不要用「已优化」这类模糊说法掩盖。
