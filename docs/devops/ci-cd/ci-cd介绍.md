在软件开发领域，**CI/CD** 是实现“自动化”的核心概念，旨在通过频繁、可靠的代码发布，缩短开发周期。

简单来说，CI/CD 就像工厂里的**自动化流水线**：原料（代码）进入流水线，经过自动加工（构建）、自动检测（测试），最后变成成品（软件）交付给用户。

------

## 1. CI：持续集成（Continuous Integration）

**CI** 关注的是开发者的代码**合并过程**。当多个开发者在同一个项目中工作时，频繁地将代码合并到主分支是关键。

- **核心动作**：开发者每提交一次代码，系统就会**自动**触发构建和测试。
- **目的**：尽早发现错误。如果新代码破坏了原有的功能（即“挂了”），CI 会立即报错，防止问题累积。
- **流程示例**：
  1. 代码上传（Push）。
  2. **自动构建**：将源码编译成可执行文件。
  3. **单元测试**：运行自动化测试脚本，确保逻辑正确。

------

## 2. CD：持续交付 / 持续部署（Continuous Delivery / Deployment）

CD 是 CI 的延伸，关注的是如何将代码**发布到环境**中。它通常包含两个层面：

### 持续交付 (Continuous Delivery)

- **定义**：代码通过 CI 后，会自动部署到**测试环境**或**预发布环境**。
- **关键点**：它确保代码随时处于“可发布状态”，但最终发布到**生产环境**通常需要人工点击“确认”按钮。

### 持续部署 (Continuous Deployment)

- **定义**：比持续交付更进一步。
- **关键点**：完全自动化。只要代码通过了所有测试，流水线会自动将其发布到**生产环境**，无需人工干预。

------

## 3. 为什么要用 CI/CD？

| **传统模式**                              | **CI/CD 模式**                         |
| ----------------------------------------- | -------------------------------------- |
| **手动打包**：耗时且易出错。              | **自动流水线**：秒级启动，标准统一。   |
| **合并地狱**：几周合并一次代码，冲突多。  | **频繁集成**：每天多次合并，冲突小。   |
| **上线恐慌**：发布前由于未知Bug感到压力。 | **信心十足**：每步都有自动化测试把关。 |

**一句话总结**： **CI** 是保证代码质量的自动检测员，**CD** 是负责把代码平稳送到用户手里的搬运工。
