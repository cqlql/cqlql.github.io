## useRef 用法

### A. 访问 DOM 元素（最常见）

在 React 中我们通常不直接操作 DOM，但有时你必须得动它（比如：让输入框自动聚焦、获取滚动位置、初始化第三方插件）。

```javascript
const inputRef = useRef(null);

const handleClick = () => {
  // 直接操作原生 DOM 节点
  inputRef.current.focus(); 
};

return <input ref={inputRef} />;
```

### B. 存储“跨渲染”的变量

如果你在组件里定义一个普通变量（如 `let x = 1`），每次组件重新渲染时，这个变量都会被重置。

- `useState`：变量变了，页面跟着变（重新渲染）。
- `useRef`：变量变了，**页面不动**，但它的值会一直保留。

## useEffect

```typescript
useEffect(() => { stopProcessingRef.current = stopProcessing }, [stopProcessing])
```

React 依赖数组比较的是：

```
Object.is(旧值, 新值)
```

函数比较的是引用地址。

### 只加载一次 useEffect

```jsx
function App() {
    const loadVideos = () => {
        setLoading(true)
        fetchVideos()
            .then((data) => {
            setVideos(data)
            setError(null)
        })
            .catch((e) => setError(e.message))
            .finally(() => setLoading(false))
    }

    useEffect(() => {
        loadVideos()
    }, [])
}
```

#### 更规范的写法

如果你以后打算把它放进依赖数组，建议这样写：

```jsx
const loadVideos = useCallback(() => {
  setLoading(true)
  fetchVideos()
    .then((data) => {
      setVideos(data)
      setError(null)
    })
    .catch((e) => setError(e.message))
    .finally(() => setLoading(false))
}, [])
```

然后：

```
useEffect(() => {
  loadVideos()
}, [loadVideos])
```

这样：

- 函数引用稳定
- 不会死循环
- 代码更规范
- ESLint 不会警告

## 初始化 State 方式

### 方案一：直接初始化 State（推荐）

如果你在组件挂载时就已经知道初始数据是什么，**直接将它传递给 `useState`**。这是最简单、性能最好的方式，因为它避免了多余的渲染周期。

TypeScript

```
export const VoicePanel = () => {
  const { start } = useRealtimeVoice();
  const [messageApi, contextHolder] = message.useMessage();

  // 直接在 useState 中初始化，不需要 useEffect
  const [list, setList] = useState<string[]>([text]); 

  // ... 剩余逻辑
};
```

### 方案二：使用函数式初始化（针对复杂计算）

如果你的初始数据需要经过复杂的逻辑计算，可以将函数传递给 `useState`，该函数只会在组件**初次挂载时执行一次**。

TypeScript

```
const [list, setList] = useState<string[]>(() => {
  const initialState = prepareInitialData(text); // 仅执行一次
  return [initialState];
});
```

## useCallback  缓存函数引用

### useCallback 的作用

```
const fn = useCallback(() => {
  console.log("hello")
}, [])
```

React 会：

- 第一次 render 创建函数
- 以后只要依赖不变
- 就复用之前那个函数引用

于是：

```
fn === 上一次的 fn   // true
```

👉 **引用稳定性**
 👉 **减少不必要的子组件渲染**（需是 React.memo 子组件）

### ❌ 不使用 useCallback

```
function Parent() {
  const [count, setCount] = useState(0)

  const handleClick = () => {
    console.log("clicked")
  }

  return <Child onClick={handleClick} />
}
```

每次 count 改变：

- Parent 重新 render
- handleClick 新建
- Child 认为 props 变了
- Child 重新渲染

即使 Child 用了 `React.memo` 也没用。

### 用一句话理解 React

> React 性能优化的核心是 —— 减少不必要的重新渲染。

useCallback 只是这个体系里的一个工具。

### 通俗比喻

不使用 useCallback：

每次 render 都给子组件一张“新的名片”

使用 useCallback：

只要信息没变，就一直给同一张名片

React 只认“是不是同一张名片”。



## setCount什么时候用函数式

### 为什么现在很多人“几乎默认用函数式”？

因为：

#### 1️⃣ 在 useCallback 里特别安全

```
const onClick = useCallback(() => {
  setCount(prev => prev + 1);
}, []);
```

不需要依赖 count。

------

#### 2️⃣ 自动批量更新下更安全

React 18 以后会自动 batch：

```
setCount(count + 1);
setCount(count + 1);
```

结果可能只 +1。

但函数式：

```
setCount(p => p + 1);
setCount(p => p + 1);
```

一定 +2。

------

#### 3️⃣ 并发模式下不会出问题

函数式更新永远拿的是“最新确认值”。

### 清晰判断表

| 场景      | 推荐写法                  |
| --------- | ------------------------- |
| +1 / -1   | `prev => prev + 1`        |
| toggle    | `prev => !prev`           |
| push 数组 | `prev => [...prev, item]` |
| reset     | 直接 `setX(0)`            |
| 覆盖赋值  | 直接 `setX(newValue)`     |

### 工程实践建议（偏主流写法）

在实际项目里

> 👍 只要是“计算型更新”，默认写函数式

这是目前 React 社区更主流、更稳的习惯。

## 很多时候不需要手动 memo

1. **函数调用 vs DOM 更新**
   - React 18 可以快速 diff 并跳过真实 DOM 改变
   - 小组件渲染很轻量，不会有性能瓶颈
2. **自动批量更新**
   - 避免了多次 setState 导致的多次渲染
3. **现代 React DevTools 统计**
   - 实测很多组件即使不 memo，性能也足够好
4. **手动 memo 的成本**
   - 不必要的 `React.memo` / `useCallback` 会增加代码复杂度
   - 浅比较本身也有一定开销

所以官方推荐：

> 先写清晰、直观的代码
>  **只在性能瓶颈明显时**才用 memo 或 useCallback

### 什么时候仍然要用 memo

1. 子组件很重，渲染耗时长
2. 父组件更新非常频繁
3. 子组件数量非常多（列表、表格等）
4. props 是稳定的对象或函数（搭配 useCallback / useMemo）

## 常见问答（FAQ）

### loadVideos 总是重复定义会有影响吗？

> [!NOTE]
>
> 使用 useCallback 可避免重新定义，但并不是为了解决这个问题，因为重复定义没有影响。
>
> useCallback 主要优化： **引用稳定性**，**减少不必要的子组件渲染**

> **一般情况下，没有任何实际影响。**
>
> `loadVideos` 每次 render 都被重新定义，是 React 的正常行为。

#### 会不会有性能问题？

99% 情况下：**完全没影响。**

原因：

- JS 创建函数成本极低
- 这只是创建一个函数对象
- 不会产生额外渲染
- 不会触发 useEffect（你依赖是 []）

现代 React 应用中，这种写法是完全正常的。

## 副作用（Side Effect）

一句话定义：

> **副作用 = 代码执行时，影响了函数外部世界的行为**

也就是说：

如果一个函数不只是“计算并返回结果”，
 而是 **改变了外部状态、环境、数据、网络、DOM 等东西** —— 那它就有副作用。

在 React 里这些都算副作用：

- 修改 ref.current
- setTimeout
- setInterval
- fetch
- WebSocket
- 操作 DOM
- 添加事件监听
- 订阅
- console.log（严格来说也算）

## React 是函数式 UI 框架

函数式编程强调：

> 尽量减少副作用
>  让数据流可预测

副作用越多：

- 越难调试
- 越难测试
- 越难维护

## React 的执行顺序

```
render 阶段（纯函数阶段）
↓
commit 阶段（DOM 更新）
↓
effect 阶段（useEffect 执行）
```

在 render 阶段：

- 不允许有副作用
- 不允许修改外部可变对象（ref 属于可变对象）

否则在并发模式下可能会出现状态错乱。

## React 组件本质

```typescript
UI = f(state)
```

## React 希望：render 阶段是纯函数

也就是：

- 只根据 state/props 计算 UI
- 不做任何“影响外部世界”的事

因为在 React 18：

- render 可能执行多次
- render 可能被丢弃
- render 可能被中断
- render 可能是并发执行

如果 render 里有副作用：

🔥 结果就会乱掉

## React 把逻辑分成两类

| 类型   | 放哪里    |
| ------ | --------- |
| 纯计算 | render    |
| 副作用 | useEffect |

### ✅ 属于纯计算（放在 Render 中）

这类逻辑只涉及数据的转换、过滤或格式化。

```javascript
function Receipt({ items }) {
  // 1. 这里的 logic 是纯计算：根据 items 算出总价
  // 只要 items 不变，total 永远不变
  const total = items.reduce((sum, item) => sum + item.price, 0);

  // 2. 这里的格式化也是纯计算
  const formattedTotal = `$${total.toFixed(2)}`;

  return <div>Total: {formattedTotal}</div>;
}
```

### ❌ 不属于纯计算（必须放在 useEffect 或事件处理函数中）

这些行为统称为**副作用（Side Effects）**，因为它们会改变“外部世界”。

- **修改全局变量：** `window.title = 'Hello'`
- **网络请求：** `fetch('/api/data')`
- **操作 DOM：** `document.getElementById('my-id').focus()`
- **定时器：** `setTimeout(...)`

## 🚀 其实 React 很“简单”

React 核心模型只有一句话：

```
render 是纯函数
副作用放 effect
```

就这么简单。

你现在遇到的问题，都是在：

> “我在 render 外面注册了一个长期存在的副作用”

那就必须考虑闭包。


这是性能问题，不是正确性问题。

你只需要记住三条：

#### ① render 里不要做副作用

不要：

- 改 ref
- 发请求
- 注册事件

------

#### ② 长期存在的回调 → 用 ref 或 useEvent

WebSocket / interval / 事件监听。

------

#### ③ 如果函数不依赖 state，就不用紧张

像你那个 stopProcessing：

完全没问题。
