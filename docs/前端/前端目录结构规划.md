# Vue / React 目录结构规范

> 状态：**子篇 · 现行**（2026-10-31 由「目录结构规划」升级）
>
> 跨栈判据（切分三问、依赖方向、`shared/` 分层、页面放哪、反例清单）在
> [目录结构规范](../工程/目录结构规范.md)（母本），**本文只写 Vue / React 这一栈**。
> 两处冲突时以母本判据为准。

## 一、Vue

```text
src/
  main.ts
  App.vue

  router/
    index.ts

  store/
    index.ts
    user.ts

  layout/
    MainLayout.vue

  features/
    realtime-voice/
      components/        # 只被本 feature 用
      hooks/
      pages/             # 需要整块删除的业务页才放这里
      api.ts             # 只发请求
      service.ts         # 多接口编排 / WebSocket 连接
      types.ts
      store.ts           # 只放跨组件、跨页面状态
      utils/             # pcm.ts、downsample.ts 这类本 feature 专用纯函数
      index.ts           # 对外出口

  shared/
    api/                 # 请求封装（鉴权、错误拦截、mock 开关）
    ui/                  # 跨 feature 的展示组件
    hooks/               # 跨 feature 的 hook
    domain/              # 枚举、标签映射等无业务耦合的词汇
    utils/               # 纯函数

  styles/
```

`shared/` 下按需建子目录，不预先铺满 —— 母本第二节那条「目录是长出来的」同样适用。

## 二、React

```text
src/
├── router/
│   └── index.tsx                    # 全局路由表，只登记路径、不写逻辑
├── pages/                           # 共享布局的页面
│   ├── HomePage.tsx
│   └── AboutPage.tsx
│
├── features/
│   ├── auth/                        # 认证：一个能力一个目录
│   │   ├── api.ts                   # 只发请求
│   │   ├── service.ts               # 编排（登录 + 拉用户信息 + 存 token）
│   │   ├── types.ts
│   │   └── index.ts                 # 只导出外部要用的东西
│   │
│   └── realtime-voice/
│       ├── pages/                   # 要能整块删除，所以页面放 feature 内
│       │   ├── VoicePage.tsx
│       │   ├── VoiceSettingsPage.tsx
│       │   └── VoiceHistoryPage.tsx
│       ├── components/
│       │   ├── VoicePanel.tsx
│       │   ├── VoiceControls.tsx
│       │   └── TranscriptView.tsx
│       ├── hooks/
│       │   ├── useDisplayAudio.ts
│       │   ├── usePCMProcessor.ts
│       │   ├── useVoiceWebSocket.ts
│       │   └── useRealtimeVoice.ts
│       ├── api.ts                   # HTTP：历史记录、配置读写
│       ├── service.ts               # 编排：WebSocket 建连、断线重连、PCM 管线
│       ├── utils/
│       │   ├── pcm.ts
│       │   └── downsample.ts
│       ├── types.ts
│       ├── router.tsx               # 本 feature 的子路由
│       └── index.ts
│
├── shared/
│   ├── api/
│   │   └── http.ts                  # axios 实例（Token、错误拦截）
│   ├── ui/
│   ├── domain/
│   └── utils/
│
└── App.tsx
```

### 两处容易走偏的地方

**1. `api/`、`services/` 不要留在 `src/` 顶层。** 那是技术类型优先的结构：加一个业务要改两个顶层目录，删一个业务要在两个目录里翻残留。请求归到 `features/<能力>/api.ts`，跨 feature 的底座才放 `shared/api/`。

**2. `src/lib/` 不要和 `shared/api/` 并存。** 两者都是「系统能力」的容器，并存的结果是有人把 `http.ts` 放 `lib/`、有人放 `shared/api/`，同一个东西两个位置。统一收敛到 `shared/api/`。

> `src/utils/` 与 `shared/utils/` 同理：只留一个。业务无关的纯函数放 `shared/utils/`，业务相关的放对应 feature 的 `utils/`。

## 三、路由与 pages 的边界

### 路由懒加载

顶层 `router/index.tsx` 与 `features/*/router.tsx` 并存时，顶层要用懒加载引入 feature 路由，否则所有 feature 会打进首屏包。

```tsx
// src/router/index.tsx
const VoiceRoutes = lazy(() => import('../features/realtime-voice/router'));

// 路由定义中
{
  path: 'voice/*',        // 注意这个 *，交给子路由接管
  element: <VoiceRoutes />
}
```

### feature 内的 pages 归谁引用

`src/pages/` 和 `src/features/*/pages/` 并存时，规则只有一条：

**feature 内部的 `pages` 只能被该 feature 自己的 `router.tsx` 引用。** 外部要访问 `VoicePage.tsx`，走 feature 的 `router` 或 `index.ts`，不要直接 import 那个文件。

判断某个页面该放顶层还是 feature 内，用母本第三节那条判据：**删掉一个业务，能不能只删一个目录**。

## 四、`index.ts` 出口写法

feature 的 `index.ts` 是**对外契约**，不是文件清单。

```typescript
// src/features/realtime-voice/index.ts

// 1. 导出该 feature 的路由入口（最常用）
//    主路由只加载 VoiceRoutes，不需要知道内部有 VoicePage、SettingsPage
export { default as VoiceRoutes } from './router';

// 2. 导出可能跨模块使用的组件（比如放在顶部导航栏的麦克风图标）
//    只导出需要跨模块用的，不要导出内部专用子组件
export { default as VoiceIndicator } from './components/VoicePanel';

// 3. 导出类型定义
export type { VoiceConfig, VoiceStatus } from './types';

// 4. 【重要】不要导出内部实现细节
//    外部不需要知道你用了 WebSocket 还是 WebRTC，也不需要知道你怎么处理 PCM。
//    所以不要导出 service、utils、或内部 hooks（如 usePCMProcessor）。
```

这种写法带来三个好处：

1. **重构自由**：把 `VoicePanel.tsx` 改名或移位，只需改 `index.ts` 里的引用，`App.tsx` 完全不动 —— 它只认 `VoiceIndicator` 这个名字。
2. **认知负担更低**：看 `index.ts` 一眼就知道「这个模块对外只提供这三样东西」，不用翻十几个文件猜入口。
3. **避免循环依赖**：严格限制导出内容，能防止 Feature A 和 Feature B 之间长成蜘蛛网。

## 五、`features/api` vs `api/`

两种组织逻辑的取舍，母本第八节指派给本文展开。

### 方案 A：`features/<能力>/api`（业务优先，推荐）

API 是功能的一部分。

```text
src/
└── features/
    ├── user/                # 业务模块：用户
    │   ├── api/             # 仅与用户相关的 API
    │   ├── components/      # 仅用户模块使用的 UI
    │   ├── hooks/
    │   ├── service/         # 业务编排
    │   └── types/
    └── order/               # 业务模块：订单
        ├── api/
        └── ...
```

- **适用**：大型复杂项目、领域驱动设计（DDD-Lite）
- **特点**：想看「订单是怎么保存的」，进 `order/` 就有从 UI 到 API 的完整链路

### 方案 B：顶层 `api/`（技术角色优先）

API 是一个集中的技术设施。

```text
src/
├── api/                     # 全局 API
│   ├── userApi.ts
│   ├── orderApi.ts
│   └── authApi.ts
├── components/
├── hooks/
└── types/
```

- **适用**：中小型项目、API 逻辑简单且复用率极高
- **特点**：符合传统直觉，但项目一大 `api/` 就臃肿，且难以分辨某个 API 被哪些业务引用

### 对比

| **维度**     | **features/xxx/api（分层）**      | **api/（集中）**                     |
| ------------ | --------------------------------- | ------------------------------------ |
| **关注点**   | 业务领域（Domain）                | 技术类型（Type）                     |
| **依赖关系** | 明确，模块间尽量不交叉引用        | 模糊，任何地方都能调任何 API         |
| **代码搜索** | 快速（按功能搜）                  | 较慢（长列表里找文件）               |
| **团队协作** | 冲突少（不同人负责不同 feature）  | 冲突多（大家都要改同一个 api 目录）  |
| **重构难度** | 低（局部重构）                    | 高（全局牵一发动全身）               |

### 建议

1. **优先用 `features/` 结构**，API 放各自 feature 下
2. **提取 `shared/api`**：全平台通用的接口（字典表、文件上传、当前登录用户）放全局共享
3. **统一拦截器**：无论 `api` 文件放哪，底层 `axios` / `fetch` 实例（Token 处理、错误拦截）只放一个全局单例，供各层调用
