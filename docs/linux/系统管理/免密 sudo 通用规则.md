# 免密 sudo（NOPASSWD）通用规则

> 状态：**现行**（2026-11-05）
>
> **定位**：跨项目、跨环境的通用母本。不含任何项目名、主机名、IP、端口、真实用户名。
> **用法**：把本文件整份丢给 AI，作为实现 / 评审 / 排查的依据。项目仓只需补 §5 的「本仓怎么拿到 root」
> 和自己的接口、授权名、任务状态机，**不要复制本文规则全文**。
> **适用**：任何需要无人值守 `sudo -n` 的 Linux —— 物理机、VM、容器、WSL 发行版、集群节点。
> **AI 读法**：§1 / §3 / §4 是必须遵守的规则；§5 是唯一需要按目标环境补的一节；§8 是交付前自检。

---

## 0. 什么时候才该配

唯一正当理由：**有非交互脚本硬编码 `sudo -n`，而现场没有人能回答密码提示**。
典型症状是 `sudo: a password is required`，或任务永远停在「正在执行…」、日志停在上一行。

- 不配的理由不成立时（只是想少输一次密码、只是交互式操作嫌麻烦）→ **不要配**。
- 密码**永不**进配置文件、命令行参数、环境变量、CI 变量、日志、接口请求体。
  这些地方都会留副本，而 `sudo -n` 的价值正是「失败要快，而不是卡在交互提示上」。
- 不用 `sudo -S` 加管道 / here-string 喂密码，不做「密码输入框」，不做 `-sudo-password` 之类的参数。

## 1. 唯一落地形式

```
/etc/sudoers.d/90-<user>-nopasswd
<user> ALL=(ALL) NOPASSWD:ALL
```

| 项 | 值 |
| :--- | :--- |
| 文件 | `/etc/sudoers.d/90-<user>-nopasswd`（编号 + 用户名 + 固定后缀） |
| 内容 | 上面那**一行**，不多不少 |
| 权限 / 属主 | `0440 root:root` |
| 不动的东西 | `/etc/sudoers` 本体、别人的 drop-in |

- **不写任何 `Defaults` 行**：`Defaults` 是全局语义，写错一条会影响这台机器上所有人的 sudo。
- **不写通配、不写多用户**：只给那个确实要跑脚本的默认用户。
- **绝不把 `NOPASSWD` 给可逃逸的命令**（`bash`、`sh`、`vi`、`less`、`find`、`cp` 等）——等于直接给 root。
- 文件名固定，是为了人肉对照和「收回就是删掉这一个文件」。

## 2. 安全影响面：先说清楚再动手

- 在**本来就有 root 通道**的环境（本机 root、VM 控制台、容器 `docker exec -u root`、WSL `wsl.exe -d <distro> -u root`），
  能操作的人本来就能拿 root，所以这一步**不是提权**。
- 但影响是真实的：**此后任何以该用户身份运行的代码都能静默变成 root** ——
  被污染的 npm / pip 包、一个写错的脚本、一次误粘贴，都不会再被密码拦一下。
- 由此推出四条设计约束：
  1. **单独一个写开关**，不随「配 SSH」「初始化」「换源」等别的动作一起放行；
     副作用不能藏在别的动作里，点「配 SSH」的人预期不是「以后谁跑 sudo 都不用密码」；
  2. 界面与任务日志里如实写明「它不增加权限，但它让 sudo 静默可用」；
  3. **不提供任意用户名输入框** —— 多一处注入面，而它写的是 sudoers；
  4. 收回也是一个独立写操作，不与配置共用同一个开关。

## 3. 七条硬约束（每条对应一个会咬人的事实）

**1. 用户名从目标机器读，不从请求 / 参数 / 前端来。**
用默认用户的 `id -un` 之类的方式实时读，再过白名单 `^[a-z_][a-z0-9_-]{0,31}$`；
`root`、空值、非法字符一律拒，一条命令都不许跑就返回错误。
原因：这个值会同时写进 sudoers 文件和 `runuser -u <user>` 的命令行 —— **白名单式校验比「过滤危险字符」可靠**。

**2. 先自检、再落地。**
顺序固定：写临时文件 → `visudo -cf <临时文件>` → 通过了才 `install -m 0440 -o root -g root <临时文件> <目标>`。
- 顺序反了：**语法错会让 sudo 整体拒绝工作**，而修它还得靠 sudo（自锁）。
- 权限 / 属主不对时，**sudo 会直接忽略这个片段**，只在日志里留一句很难懂的话 ——
  症状是「我明明配了，为什么还要密码」。

**3. 复查必须切到那个用户的身份。**
`runuser -u <user> -- sudo -n true`。
最容易写错的一条：整个流程常以 root 跑，而 **root 自己的 `sudo -n true` 永远成功**，
拿它当验证等于没验 —— 症状是「工具说配好了，部署脚本还是 `sudo: a password is required`」。
没有 `runuser` 时退 `su - <user> -c 'sudo -n true'`；两条都做不到 → 报**未验证**，不许报 `ok` / `changed`。

**4. 幂等 = 终态一致，不是每次重写。**
先按第 3 条的身份探一次 `sudo -n true`：通了就不新建文件，并如实说明
「已生效，没有改动文件（可能由别处的 drop-in 生效）」。

**5. 「文件在」与「真的生效」是两件事，反过来也一样。**
生效了不代表文件是我们写的那一份。两者都要分开报，来源至少区分 `ours` / `other` / `none`。
只看文件存在就报成功，会把「权限不对被 sudo 忽略」漏掉。

**6. 没有 sudo 的环境是 `skip`，不是 `error`。**
Alpine 之类用 `doas`。判据是 `command -v sudo`，不要猜、也不要在这时尝试写 sudoers。

**7. 没跑 ≠ 通过了。**
探测读不到、`visudo` 缺失、没有可用的复查工具 → `error` / `未验证`，
**不许降级成 `ok`**。任务日志里「没做成」和「做成了」必须是两个状态。

## 4. 四态：探测结果该怎么报

| 探测到的现状 | 只读查看 | 执行后 |
| :--- | :--- | :--- |
| `sudo -n true` 通过，文件是**我们的** | `ok` 已生效（文件在） | 不动 |
| `sudo -n true` 通过，文件**不在** / 不是我们的 | `ok` 已生效（**别处的规则**） | **不新建** |
| 不通，我们的文件在 | `warn` 文件在但不生效（多半权限 / 语法不对） | 重写 + 复查 → `changed` / `error` |
| 不通，没有文件 | `warn` 未配置 | `changed`（复查通过才算） |
| 没有 `sudo` | `skip` + 原因 | `skip` |
| 读不到 / `visudo` 缺失 | `error` | `error` |

## 5. 唯一的平台变量：「怎么进到 root」

**把通用规则接到具体项目时，只有这一节需要自己补**，也是最容易把别的项目经验套错的地方。
文件内容、§3 的七条约束与进入方式**完全无关**。

| | 有 root 通道（本机 / VM 控制台 / 容器 / WSL `wsl.exe -u root`） | 只有 SSH 用户（远程节点 / 集群） |
| :--- | :--- | :--- |
| 拿 root | 直接拿到 | 拿不到，只能靠 sudo 提权 |
| 密码通道 | **不需要** | 需要一次交互（人在终端输，**不落盘**） |
| TTY | **不需要** | 需要；`--apply` 应拒绝非 TTY |
| 脚本怎么送 | 直接 stdin / `sh -c` | **scp 文件**，不要 `ssh -t … bash -s`：`-t` 之后 stdin 是 TTY，要留给密码 |
| ssh 选项 | — | 必须带 `-o BatchMode=yes`：否则公钥认证失败会退回 password，在控制终端弹提示并**永远等下去**；`ConnectTimeout` 只管 TCP 那一段，管不了这个 |

两个方向的典型错：

- 把「不需要 TTY / 不需要密码」抄到 SSH 场景 → 脚本卡死或直接失败；
- 把「必须 TTY / 走 scp / 密码通道」抄到已有 root 通道的场景 → 白造一整套用不上的管道。

**§3 的第 2 条（`visudo -cf` 自检）、第 1 条里的 `install -m 0440`、第 3 条（`runuser -u` 复查）
在两条路上一条都不能省。**

## 6. 最小正确骨架

以 root 运行；不含远程传输 / TTY / 密码通道（那部分按 §5 由调用方补）。

```bash
#!/usr/bin/env bash
# 前置：user 是「从目标机器读出的默认用户名」，且已过 §3.1 的白名单校验。
set -euo pipefail

user='<user>'
dest="/etc/sudoers.d/90-${user}-nopasswd"
line="${user} ALL=(ALL) NOPASSWD:ALL"

command -v sudo   >/dev/null 2>&1 || { echo 'skip: 未安装 sudo'; exit 0; }
command -v visudo >/dev/null 2>&1 || { echo 'error: visudo 缺失'; exit 1; }

probe() {                     # 0=通过 1=不通过 2=没有可用的复查工具
  if command -v runuser >/dev/null 2>&1; then
    runuser -u "$user" -- sudo -n true && return 0
    return 1
  fi
  if command -v su >/dev/null 2>&1; then
    su - "$user" -c 'sudo -n true' && return 0
    return 1
  fi
  return 2
}

probe && rc=0 || rc=$?
if [ "$rc" -eq 0 ]; then
  echo 'ok: 已生效，未改动任何文件（可能由别处规则生效）'
  exit 0
fi

tmp="$(mktemp)"
trap 'rm -f "$tmp"' EXIT
printf '%s\n' "$line" > "$tmp"
visudo -cf "$tmp" >/dev/null                          # 先自检
install -m 0440 -o root -g root "$tmp" "$dest"        # 再落地

probe && rc=0 || rc=$?
case "$rc" in
  0) echo 'changed: 已写入且复查通过' ;;
  1) echo 'error: 写入后复查仍不通过'; exit 1 ;;
  2) echo 'warn: 已写入，但无法验证（没有 runuser / su），状态=未验证'; exit 2 ;;
esac
```

## 7. 收回

```bash
sudo rm /etc/sudoers.d/90-<user>-nopasswd
```

- 收回是另一个写操作，单独授权；删完按 §3.3 切身份复查，`sudo -n true` 应当失败。
- **节点重装 / 镜像重建后这一步会丢**，症状就是 `sudo: a password is required`。
  把它列进部署前置检查，而不是等脚本失败再查。

## 8. 交付前核对清单（给 AI 逐条对照）

- [ ] 是否真的存在 `sudo -n` 的无人值守需求？没有就不配。
- [ ] 用户名是否从目标机器读 + 过白名单？有没有从请求 / 参数直接拼进 sudoers 或命令行？
- [ ] 是否只写 `sudoers.d` 下自己那一个文件，没动 `/etc/sudoers`、没写 `Defaults`、没给可逃逸命令？
- [ ] 是否 `visudo -cf` 在 `install` **之前**，且 `install` 是 `0440 root:root`？
- [ ] 复查是否 `runuser -u <user>`（而不是 root 下裸 `sudo -n true`）？
- [ ] 没有 `runuser` / `su` 时是否报「未验证」，而不是 `ok` / `changed`？
- [ ] 已生效时是否不重写，并区分 `ours` / `other` / `none`？
- [ ] 没有 `sudo` 时是否 `skip` 且不尝试写文件？
- [ ] 密码是否以任何形式进入配置 / 命令行 / 日志 / 变量？
- [ ] 「进到 root」的方式是否匹配目标环境（§5），有没有把另一种环境的 TTY / 密码假设抄过来？
- [ ] 免密是否是**单独一个开关**，没被藏进「配 SSH」等别的动作？
- [ ] 收回命令是否可直接粘贴，且单独授权？

## 9. 明确不做什么

- 不做密码输入框 / `sudo -S` / 任何形式的密码参数。
- 不给任意用户配，只给确实跑脚本的那个默认用户。
- 不动 `/etc/sudoers` 本体。
- 不把配置藏进别的动作：两者授权面不同，合并会让人「改了 A，B 却变了」。
- 不在状态卡里混半份 `sudo -l` 权限审计 —— 审计是另一件事。
