# 代码设计规范（母本）

> 状态：**母本 · 现行**（2026-11-13 从 `pass-up.backend` 的 `docs/code-design.md` 提炼）
>
> 本文件是**通用条款的母本**。各仓的 `docs/code-design.md` 是**实例**：通用条款以本文件为准，
> 实例只允许**追加**本仓特有的现状（类名、行数、状态字段、阈值）。
> 改通用条款 → 改这里 → 再逐仓同步实例。**不要反向：先改某个仓、再指望别的仓知道。**

> **本文不管的两件事**（各有专文，别在这里重复）：
> - 目录怎么切、依赖往哪指 → [目录结构规范](./目录结构规范.md)
> - DDD 四层各放什么、跨层数据怎么转换 → [DDD 落地规范](../后端/架构设计/分层与建模/DDD落地规范.md)
>
> 本文只管：**代码写出来之后长什么样** —— 职责是否混杂、状态是否可控、事务是否安全、抽象是否值得。
> 代码规范进 `AGENTS.md` 的方式见 [AGENTS.md 模板](./AGENTS模板.md)，**正文一律不进**（有体积上限）。

## 零、三条元规则（优先级高于下面所有条款）

1. **先读再改**：改任何类之前先看现有实现和调用方。不要因为「看起来能更优雅」就推倒重写。
2. **最小必要拆分**：拆分的依据是**变化原因不同**，不是行数。同一个变化原因的逻辑留在同一个类里。
3. **抽象必须能说出它解决了什么实际问题**：说不出来就是过度设计，不写。

**必须警惕的反模式**（AI 尤其容易犯）：

```
发现某个 Service 有 1400 行
  → 机械拆成 5 个 Service
  → 每个配 1 个接口
  → 加 Factory / Strategy / Facade
```

这不是重构，是把「一个难读的类」换成「六个互相调用、需要来回跳的类」。
正确路径：**找出不同的变化原因 → 判断是否真的独立 → 选最小拆分 → 验证行为未变**。

**代码质量不由类的数量和方法行数衡量。** 现存 1400 行的类往往不需要现在拆，
需要的是**别再往里加新职责**。

## 一、新仓怎么用这份母本

1. **复制本文全文**到本仓 `docs/code-design.md`，把状态行改成 `实例 · 现行（母本：<本文件路径>）`。
   🔴 **必须留全文，不要改成「只放指针 + 差异」**：AI 在仓内工作时不会跨仓读文件，
   规范一旦只存在于别的仓，等于没写。母本与实例之间的重复是**有意的受控重复**，
   靠「改母本 → 按下方清单逐仓同步」来控制漂移，不靠删正文。
2. **删掉与本仓技术栈不符的章节**（无外部支付就没有退款两段事务；无前端就没有跨端公式同步）。
3. **填本仓现状**（这一节是母本唯一要求实例必须补的）：
   - 最大的 3~5 个类及行数，判断是「协议分支多」还是「职责混杂」；
   - 状态字段在哪、是什么类型、有没有枚举约束；
   - 哪些模块会互相调用（画出方向，找循环）。
4. `AGENTS.md` 只留 **3~5 条最反直觉的指针**，不复制正文。

## 二、职责边界

### 规则

- **模块边界 = 数据归属边界**：跨模块协作走对方的 **Service 方法**，不许直接注入别的模块的
  Repository，也不许在别人的 entity 上做写操作。
  - 反例：在 A 模块里直接 `bRepository.save(...)` 改 B 的数据。
  - 正例：调 B 的语义化方法（它负责校验、记账、发事件）。
- **Controller 不写业务规则**：只做参数绑定、权限注解、调 Service、包统一响应。
  出现 `if (order.getStatus().equals("PENDING"))` 就是规则漏到了错误层。
- **不要让一个模块承担别人的职责**：实时会话模块不负责计费，编排层不负责持久化细节。
  判断方法：问「这段逻辑的变化原因，跟着谁的需求走」，跟着谁就放谁那儿。

### 新增代码往哪放（决策顺序）

1. 属于已有模块的已有职责 → 加进该模块的 Service；
2. 是该模块的**新变化原因**（例如订单模块里新增「发票」）→ 新建 Service，不加进主流程服务；
3. 跨模块复用 → 先看 `shared/` / `common/` 有没有，没有再考虑下沉，**不要提前下沉**。

### 不要把文档塞进源码目录

不要用 `modules/<模块>/AGENTS.md` 这种布局：`.md` 混进源码目录会被资源处理/扫描规则误伤。
模块约束写进 `docs/` 对应文档，`AGENTS.md` 只放指针。

## 三、状态与状态机

### 规则

- **状态用枚举，不用裸字符串/数字**。判断依据：这个值会不会被 `switch`、会不会有非法取值、
  会不会出现在多个 `if` 里 —— 有一个「会」就该是枚举。
- **状态转换必须集中**：允许的路径写在一个地方（枚举方法 / 专门的 `XxxStateMachine` /
  实体的 `canXxx()`），**不要**在 5 个 Service 里各写一遍 `if (status == ...)`。
- **非法转换必须显式失败**，不是静默忽略。
- **禁止用更新语句兜底**：`UPDATE ... WHERE status='PENDING'` 只能防并发，
  不能替代状态机 —— 它不会告诉你「这个转换本来就不该存在」。
- 枚举值的**影响面要写在枚举的注释里**（新增一个值必须同步哪几处），
  否则下一个人加值就会漏。

### 实例必须补

本仓有哪些生命周期（订单、会话、任务、批次），各自的状态取值和允许的转换路径。

## 四、事务与幂等（钱 / 权益类最高优先级）

### 事务边界

- **一个事务 = 一个原子业务事实**。不要把「外部调用 + 落库」塞进同一个事务：
  外部调用慢、会超时，事务持有连接期间锁着行。
- 涉及「资金事实」与「资产收口」两类记录时，**分两段事务**：先记事实，再收口资产，
  中间失败靠补偿而不是靠一锅大事务。
- **事务方法不要自调用**：`this.xxx()` 不走代理 → `@Transactional` / 切面类注解全部静默失效。
  合法解法是 self 自引用代理：

  ```java
  /** 自引用代理：用于突破 @Transactional 自调用失效，通过代理触发事务边界。 */
  @Lazy
  @Autowired
  private XxxService self;
  ```

  注意：这**只解决自调用**，不是循环依赖的解法（见 §五）。

### 幂等

- **支付回调、外部通知、订阅消息、定时任务**必须幂等：重复到达不能产生第二份权益。
- 实现优先「唯一约束 + 抢占式更新」（`UPDATE ... WHERE 状态=预期`，判断影响行数），
  不要「先查后写」（并发下必漏）。
- **抢占失败必须抛**，不能静默返回 `false` / `null` 让调用方以为成功了。
- 资产扣减类操作**先冻结再确认**，不要「先发后用」。

## 五、依赖

> 依赖**方向**（谁可以 import 谁、跨模块怎么通信）见 [目录结构规范](./目录结构规范.md) 第三节。
> 本节只管**注入关系**（谁持有谁的实例、循环依赖怎么办）。

### `@Lazy` 只许用于 self 自引用，不许用于掩盖循环依赖

两者在代码里长得一样、后果完全不同：

| 用法 | 是否允许 | 说明 |
| :--- | :--- | :--- |
| `@Lazy @Autowired private XxxService self;`（指向自己） | ✅ | 为了让 `@Transactional` 经代理生效（§四） |
| `@Lazy` 注入**另一个** Service 来打破 A↔B 循环 | ❌ | 把「启动期报错」推迟成「运行期调用时序问题」 |

发现模块间循环依赖时**不要加 `@Lazy` 绕过**，按顺序判断：
① 是否有一方的职责放错了模块（多数情况是这个）；
② 能否用接口收窄依赖；
③ 是否为「A 完成后要通知 B」—— 那应该是**领域事件**，不是 B 反过来依赖 A。

### 依赖数量是职责信号

- 一个类注入 **7 个以上**依赖时，先问「这些依赖是不是分属不同变化原因」。
- 新增依赖时不要顺手引入整条链路：为了用一个工具方法去注入一个重服务，
  等于把它的所有依赖传染进来。

## 六、数据建模

- **Entity 不出模块**：Controller 不返回 Entity、不被别的模块当参数接收。
  不是因为「DTO 更规范」，而是 Entity 带持久化注解与懒加载语义：一旦作为响应，
  加字段就成了对外契约变更，且会把不该暴露的列（内部状态、风控标记、软删除位）发出去。
- **数据库存真实数据，展示默认值由 UI / DTO 决定**：不要为了前端好看在 entity 里写默认值或拼文案。
- **避免基本类型偏执**：金额、状态、角色、类型这类有业务含义的概念用枚举或值对象表达，
  别用 `String` / `int` / `boolean` 裸传。**`boolean` 参数不要超过一个** ——
  `execute(true, false, true)` 的调用点无法阅读。
- **数据泥团**：一组参数总是同时出现（`(userId, orderNo, amount, channel)`）→ 收成一个参数对象，
  但**只在真的每次都一起出现时才收**，不要为了一次调用造对象。

## 七、抽象的时机

**允许抽象**（满足其一即可）：

- 同一段业务规则已经在**两处以上**真实重复，且未来还会增加第三处；
- 已经出现第二个实现（第二个支付渠道、第二种存储），且差异在**行为**而非参数；
- 外部依赖需要隔离以便测试（适配器包住第三方 SDK 是合理的）。

**禁止抽象**：

- 「以后可能要支持多种…」—— 没有第二种实现就不建接口；
- 只有一个实现、且只被注入一次的 `interface + Impl` 对；
- 为了「解耦」而加的中间层，中间层自身没有任何逻辑（纯转发）；
- 把简单 `if/else` 换成 `Strategy` + `Factory` + 注册表三件套。

**判断标准**：抽象后的调用方代码是否**变短、变清晰**。如果调用方需要先理解工厂和注册表，
就是抽象失败。

## 八、可观测性

- **关键分支必有日志，且带可关联 ID**（业务单号、逻辑会话 ID、traceId）。
- **静默失败是最贵的 bug**：`catch` 后不处理、`if` 分支什么都不做、`return null` 当错误用 —— 全部禁止。
  宁可抛出去，也不要让调用方以为成功了。
- **禁止打印密码、Token、密钥、完整手机号、身份证**；请求体日志在过滤器层统一处理，
  不要在业务里重复打。
- 钱 / 权益类操作**手工打点**，不依赖切面注解（自调用会失效，见 §四）。

## 九、坏味道速查（按优先级）

| # | 坏味道 | 典型形态 | 处置 |
| :-- | :--- | :--- | :--- |
| 1 | **散弹式修改** | 改一条规则要同时改多个 Service + 状态常量 + 前端公式 | 规则集中到一处 |
| 2 | **状态机缺失** | 状态是裸字符串，转换散落 | 见 §三 |
| 3 | **幂等缺失** | 回调 / 通知 / job 重复执行发两份权益 | 见 §四 |
| 4 | **事务边界错误** | 事务里调外部 HTTP / 模型 | 见 §四 |
| 5 | **隐式依赖** | 依赖某个 Service 的副作用（它顺带改了状态） | 显式返回值 + 显式调用 |
| 6 | **循环依赖** | A↔B 互注，用 `@Lazy` 压住 | 见 §五，**不许绕过** |
| 7 | **过长方法** | 单方法 200+ 行（多为协议分支） | 按「阶段」抽私有方法，别抽 Service |
| 8 | **过深嵌套** | 5 层 `if` | 卫语句前置返回 |
| 9 | **魔法值** | `if (status == 3)`、裸 `"SUCCESS"` | 常量 / 枚举 |
| 10 | **重复代码** | 同一段公式前后端各写一份 | 至少写清「两处必须同步」+ 文档 |
| 11 | **Feature Envy** | A 反复取 B 的字段来算 B 自己的事 | 把行为移回 B |
| 12 | **过度抽象** | 单实现接口、纯转发层、预埋扩展点 | 删 |
| 13 | **注释与代码不一致** | 注释说「不落库」实际已落库 | 改代码时同步注释，注释是契约 |
| 14 | **长事务锁竞争** | 事务持有行锁等外部 IO | 缩短事务，异步化 |

## 十、交付前自检

改完代码逐条过（不适用写「不涉及」，**不要静默跳过**）：

- [ ] 是否让某个类的职责变多？新增逻辑是否放错了模块（§二）？
- [ ] 是否直接读写别的模块的 Repository / Entity？
- [ ] 状态是否有新的非法转换路径？转换是否集中（§三）？
- [ ] 新流程会不会被重复请求触发两次？抢占失败是否抛（§四）？
- [ ] 事务里有没有外部 IO？有没有自调用导致注解失效（§四）？
- [ ] 新增 `@Lazy` 吗？如果是用来打破循环依赖 → 改设计（§五）。
- [ ] 是否新增了只有一个实现的接口 / 纯转发层（§七）？
- [ ] 关键失败分支有日志吗？有没有静默 `catch`？
- [ ] 涉及的测试是否同步改？核心路径 + 异常路径是否覆盖？
- [ ] 改动是否超出本次需求范围？超出的部分**报告，不擅自改**。

**无法解决的问题写进交付说明**，不要用「已优化」这类模糊说法掩盖。

## 十一、和 `AGENTS.md` 的分工

| 文件 | 放什么 | 体积 |
| :--- | :--- | :--- |
| `AGENTS.md` | **只放「不读就会写错代码」的 3~5 条指针** + 本仓特有红线 | ≤220 行 / ≤16.5KB |
| `docs/code-design.md` | 本文的实例：全文规则 + 本仓现状 | 不限 |
| 本文（母本） | 通用条款 | 不限 |

**红线与指针必须成对**：只写「见 `docs/code-design.md`」AI 不一定会点；只写结论不写指针，
以后判据变了没人知道去哪改。
