# 目录结构规范（按能力切，不按类型切）

> 状态：**母本 · 现行**（2026-10-30 起草；同日修订：引入 `shared/`、补页面间传参、
> 给后端竖切补阈值）
>
> 本文只写**跨栈通用判据**。各栈的具体目录树不在这里重复，见第八节的指针表 ——
> 一份树抄两遍，改一次就漂一次。

---

## 一、一句话

**按业务能力组织代码，而不是按技术类型堆代码。**

- `features/order/`（业务优先）✅
- `api/` + `services/` + `store/` 各堆几十个文件（技术类型优先）❌

技术类型优先的结构在小项目里很顺手，一旦过 20 个模块就开始出问题：改一个功能要在四个目录之间跳，删一个功能要在四个目录里翻残留。

---

## 二、切分判据（三个问题）

| 问题 | 答案 | 放哪 |
| :--- | :--- | :--- |
| 只服务**一个**业务能力？ | 是 | 该 `features/<能力>/` 内部 |
| **两个以上**业务都要用？ | 是 | 下沉到 `shared/`（无业务耦合才行） |
| 这个职责**现在不存在**？ | 是 | 🔴 **不建空目录、不建空文件** |

第三条最常被违反：为了「结构完整」先建出 `hooks/`、`service/`、`types/` 五个空目录，结果半年后没人知道哪个是空的、哪个是废弃的。

> 判据：**目录是长出来的，不是规划出来的。** 需要第二个文件时才建目录。

### 为什么是单一 `shared/`，不是 `components/` + `utils/` + `hooks/` 三个顶层

三个平级顶层目录正是第七条反例里那种「全局目录爆炸」：它们各自会长到几十个文件，
而**「谁能依赖谁」在目录上一眼看不出来**。

`shared/` 用一个命名空间表达一条依赖方向：

```text
shared/
  api/      # 请求封装（鉴权、错误、mock 开关）
  ui/       # 跨 feature 的展示组件
  domain/   # 枚举、标签映射等无状态的业务词汇
  utils/    # 纯函数
```

规则只有一条：**`shared/` 不得 import 任何 `features/`**。反过来的依赖一旦出现，
`shared` 就变成「什么都装」的杂物间，删 feature 时永远删不干净。

---

## 三、依赖方向（只许单向）

```text
pages / routes  →  features  →  shared（api / ui / domain / utils）
       ↓              ↓
   shared/ui ←────────┘   （只允许 features 引用通用组件）
```

| 层 | 可以依赖 | 🔴 禁止 |
| :--- | :--- | :--- |
| `pages`（路由页） | 本页私有组件、`features`、`shared` | 页面之间互相 `import`；直接写请求 |
| `features` | `shared`、**其他 feature 的 `index.ts`** | **跨 feature 读对方内部文件**（含对方的 `store`） |
| `shared` | 无（最底层） | 反向引用 `features` / `pages` |

跨 feature 通信的三条正路：**走共享 store（明确归属）**、**走对方 `index` 暴露的接口**、**在页面层编排**。
没有第四条「直接 import 对方内部文件」—— 那是最容易变成蜘蛛网的一条。

### 页面放哪：顶层 `pages/` 还是 feature 内？

| 布局 | 适用 | 例子 |
| :--- | :--- | :--- |
| 顶层 `pages/`，`features/` 只存业务逻辑 | 页面彼此共享布局、页面本身就是全局路由的一部分 | Vue / React 后台管理、官网 |
| `features/<能力>/pages/` | 页面按业务归属明确，且要能**整块删除** | Taro 小程序、Next App Router |

判据是**「删掉一个业务，能不能只删一个目录」**。能，就放 feature 内；
不能（页面强耦合、共享一套布局壳），就留顶层。

无论哪种，**路由表只有一份**（`app.config.ts` / `router.ts`），只登记路径、不写逻辑。
页面文件只在路由表里出现一次，其余地方引用 feature `index.ts` 导出的路径常量。

## 四、feature 内部：按需建，各管一段

```text
features/<能力>/
  pages/<page>/index.tsx  # 路由页：取数 + 拼装，不写业务细节
  api.ts        # 只发请求，一个函数一个接口
  types.ts      # 该 feature 的 DTO / 枚举（跨 feature 的契约放顶层 types/）
  service.ts    # 多接口编排、重试、数据转换
  store.ts      # 只放跨组件/跨页面状态
  components/   # 只被本 feature 用的组件
  hooks/        # 只被本 feature 用的 hook
  nav.ts        # 只放「跳转意图」，见下
  index.ts      # 对外出口（可选，需要时才建）
```

| 文件 | 职责边界 | 常见越界 |
| :--- | :--- | :--- |
| `api.ts` | 拼参数、调统一请求封装、返回类型化结果 | 在里面写业务判断、弹 toast |
| `service.ts` | 多接口编排、状态更新、失败重试 | 变成第二个 `api.ts`（只是转发一次） |
| `store.ts` | 跨页面/跨组件共享 | 只在一个组件用的状态也塞进去 |
| `nav.ts` | 跳转意图的一次性传递 | 在里面写取数、写业务判断 |
| 页面 | 生命周期、布局、路由参数、调用 feature | 把业务逻辑写进页面 |

**单接口直接用 `api.ts`；只有「多接口 + 状态变更 + 重试」才值得加 `service.ts`。**

### `api.ts` 还是 `api/<resource>.ts`？

一个 feature 只打一个资源时用单文件；**出现第二个资源才升级成目录**——和「目录是长出来的」同一条判据。

```text
features/order/api.ts             # 只有 /api/orders 一个资源
features/stats/api/home.ts        # /api/home 与 /api/stats 是两个资源
features/stats/api/stats.ts       # → 升级成目录
```

### 页面之间怎么传参（`nav.ts`）

小程序 / Taro 有一条硬限制：**`switchTab` 不吃 query**（tabBar 页之间跳转，带上也被丢掉），
而 **`navigateTo` 的 query 超长会静默截断** —— 备注 200 字、备忘 2000 字都能顶到上限，
目标页拿到半条内容原样写回去，等于悄悄改了用户的数据。

所以「跨页传一段长 / 复杂的数据」不走 URL，走进程内的一次性意图：

```text
features/<能力>/nav.ts     # set 一份 → 目标页 take 一次并清空
```

三条不变量：

1. **写入即覆盖** —— 用户不可能同时有两个待处理的意图；
2. **取走即清空** —— 否则下一次「新建」会拿到上一条的内容；
3. **不落 storage** —— 落盘会让上一次的意图在冷启动时复活，用户点开页面莫名变成上次的状态。

同一份机制出现第三个调用方时，抽成 `shared/utils/oneShot.ts` 的泛型工厂，
别让「读完即清空」在三个文件里各实现一遍——哪天只改一处就是 bug。

> 短参数（`?id=`、`?type=`）仍然走 URL。意图只用于「长 / 复杂 / 不可序列化」的那一类。

## 五、页面层的三条禁令

1. 🔴 **页面之间不许互相 `import`。** 复用的业务代码归 `feature`，复用的展示组件归 `shared/ui`。
2. 🔴 **页面不直接发请求。** 一律经 feature 的 `api` / `service` 调统一请求封装（鉴权、401 刷新、错误提示都在那一层）。
3. **一次性私有组件放页面目录下**（`pages/<page>/components/`，或与页面同级），
   不要为了「以后可能复用」提前上提到 `shared/ui`。

## 六、后端怎么落（有前提，不是无条件）

前端那条原则换个名字：**按领域切包，不按 `controller/service/mapper` 横切**。

| 前端 | 后端 | 判据 |
| :--- | :--- | :--- |
| `features/<能力>/api.ts` | `<domain>/controller` | 一个能力一个包 |
| `service.ts` | `<domain>/service` | 编排、事务边界 |
| `types.ts` | `<domain>/dto` | 出入参 |
| `shared/utils` | `common/` / `infra/` | 无业务耦合 |

🔴 不要出现「所有 controller 一个包、所有 service 一个包」的横切结构 —— 加一个业务要改三个包，删一个业务要清三个包的残留。

### 但先看阈值

竖切的收益是「删一个业务只清一个包」，成本是**每个业务都要多建 3–4 个包**，
而事务、鉴权、分页这些跨业务的共用逻辑要么下沉、要么重复一遍。
**收益随业务数线性增长，成本是固定的**，所以在业务少的时候横切反而更好找、更好改。

| 条件（任一不满足就先别竖切） | 判据 |
| :--- | :--- |
| 领域 ≥ 10 个，或接口 ≥ 30 个 | 少于此数，`internal/{api,store,domain}` 三个包一眼看得完 |
| 有 ≥ 2 人同时改后端 | 单人开发时「跳四个包」的成本只是多按两次 `Ctrl+P` |
| 表数 ≥ 10，存在跨聚合的一致性边界 | 6 张表的系统没有聚合边界问题，切了只是把 handler 和 store 各拆一份 |
| 将来要换库 / 并行多存储 | 换库压力落在 store 层，不在包的形状 |

**升级触发条件出现任一项才重新评估**：领域过 10、接口过 30、后端 ≥2 人、
出现真正的聚合一致性边界、并行接第二种存储。

反例是「照抄 DDD 分层」：一个 6 张表的单人项目被切成
`domain / application / infrastructure / interface` 四层，每个实体再配一套 mapper，
加一个字段要改 5 个文件，而它从来没有过跨聚合事务。

> 前后端不对称是**允许**的，不是疏漏。前端的痛点是「删不干净」（页面、组件、请求散落四处），
> 后端的痛点是「找不到」（一个 handler 牵动三张表）。两个痛点不同，结构就不该一样。

## 七、反例清单

| 反例 | 为什么错 | 改法 |
| :--- | :--- | :--- |
| 为「结构完整」建 5 个空目录 | 半年后分不清空的和废弃的 | 需要第二个文件时再建 |
| 页面直接 `fetch` / `Taro.request` | 绕过鉴权与错误处理 | 走 feature 的 `api` |
| Feature A `import` Feature B 的 `store` | 状态归属不清，改 B 坏 A | 下沉共享状态或走对方出口 |
| 页面里手拼 `/features/x/pages/y/index` | 改路由时漏改一处，表现是白屏 | 从 feature `index.ts` 取路径常量 |
| 用 URL query 传长文本 | 超长静默截断，用户数据被改 | 走 `nav.ts` 的一次性意图 |
| `utils/` 里塞业务逻辑 | 最底层反向依赖业务 | 挪回对应 feature |
| 所有组件丢 `components/` | 全局目录爆炸，删除困难 | 只放跨两个业务复用的 |
| 6 张表的后端照抄四层 DDD | 加一个字段改 5 个文件 | 看第六节的阈值 |
