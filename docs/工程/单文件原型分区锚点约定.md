# 单文件原型分区锚点约定

> 状态：**母本 · 现行**（2026-11-08，从 `pass-up.ops/docs/components-prototype.html` 一次实战提炼）
>
> **这份文档的用法**：新项目要写「双击就能开的单文件 HTML 原型」时，把这一篇丢给 AI，
> 让它按 §3 埋锚点、按 §4 写 map、按 §6 验收；改原型时按 §5 的 SOP，**不要通读全文**。
>
> 本文只写**通用判据与可复制骨架**。文档治理仍以 [文档约定](文档约定.md) 为母本，
> 本约定不是第二个索引。实例：`pass-up.ops/docs/components-prototype.html` + `components-prototype-map.md`。

---

## 0. 结论：省不省 token

**省，但省的是「读进来」的 token —— 不是把文件变小，也不是让改动面变少。**

| 一次局部改动（例：改一句弹窗文案） | 通读全文 | 锚点法 |
| :--- | :--- | :--- |
| 读入 | 全文 1827 行 / 121 KB ≈ 32k tokens | map 约 60 行 ≈ 1.2k + `grep` 42 行 ≈ 0.6k + 定点读 40 行 ≈ 0.8k |
| 写出 | 一段 `Edit` | 同一段 `Edit` |
| 合计量级 | **≈ 32k** | **≈ 3k** |

约 **10 倍**量级；同一会话里改动越碎、轮次越多，收益越大（通读的全文往往被反复带进上下文）。
数字是按中文 HTML 体量做的量级估算，不是计费账单；若 IDE 已自动注入全文，收益会打折，
但在 CLI 协作 / 多轮对话里仍成立。

**真正起作用的是三件事，缺一不可：**

1. **语义 → 位置的翻译表**。AI 拿到的是「改 MinIO 更新弹窗文案」，不是「改第 1203 行」。
   光有锚点只是多了些注释，没有 map 就不知道该 grep 哪个 slug。
2. **行号不写死**。map 只写 slug，行号每次由 `grep -n` 现场取；文件从 1411 行长到 1827 行，
   map 里**没有任何一行行号需要跟着改**（功能变了当然要加表项，但不必为「行号漂了 400 行」返工）。
3. **slug 稳定**。锚点名定下不改，map、AGENTS、历史对话里的引用都不漂移。

**不省的边界（别拿它当万能药）：**

- 不降**改动面**：加一个组件仍要动 7 处（数据 / 派生 / 计划 / 渲染 / 弹窗…），那是「声明式化」的事。
- 不省**全局理解**：跨区重构、改数据流、第一次接手要看全貌时，该通读还是通读。
- 不省**输出**：`Edit` 本来只回传一小段。
- 有**长期维护成本**：锚点 + map 必须与源文件同步，见 §6。

## 1. 适用判据（三条全满足才用）

1. **必须单文件交付**：`file://` 双击可开、不能引入目录 / 多资源文件。能拆就先拆。
2. **大到读一次肉疼**：经验阈值 > 500 行 / > 20k tokens，且一次会话里会反复改。
3. **改动以局部为主**：改文案、加一区、调样式，按语义能说清「改哪儿」。

🔴 **生产代码不要用**：函数 / 模块 / 组件边界本来就可寻址，再加锚点是重复建设。
这套是给「被交付形态绑死的长文件」用的：单文件原型、演示稿、长配置、长 SQL、单篇长文档。

---

## 2. 三档选型：别默认就拆文件

| 档 | 做法 | 解决什么 | 代价 |
| :--- | :--- | :--- | :--- |
| 一档 · 可寻址（**本约定**） | 单文件 + `@section` 锚点 + map | 只降**读**的成本 | 改动面不变；多一份 map 要维护 |
| 二档 · 声明式化 | 注册表 / 数据驱动，删掉 `id === "xxx"` 特判 | 降**改动面** | 要重构渲染器，回归面大 |
| 三档 · 拆文件 | 入口变目录 + 多个 js/css | 两者都降 | 交付形态变了：`file://` 相对路径、脚本加载顺序、评审链接全要改 |

**实战教训**：`pass-up.ops` 曾完整做完第三档（`docs/prototype/` 10 个文件 + 41 条行为断言 + 截图验证），
随后**被整体撤销** —— 原因不是方案错，而是用户不打算让原型扩张成「一个原型项目」，`docs/ui.md` 与
`components.md` 里指向原型的链接必须保持不动。最终选第一档：**零新增文件、正文 0 改动、只加注释行**。

> 🔴 先问一句「这次优化允不允许改交付形态」，没确认就别往下做。
> 省 token 的办法很多，最彻底的那个未必是用户要的那个。

当痛点从「不知道读哪里」变成「加一个组件要改 7 处」时，按上表升档，别继续往 map 里堆补丁。

## 3. 源文件侧：埋锚点

格式固定 `==== @section <slug> ==== <人话说明>`，按所在语言的注释语法包起来：

```html
<!-- ==== @section index ==== 分区索引入口；改本页前先查 docs/<主体>-map.md -->
```
```css
/* ==== @section css-base ==== 变量 / 全局 / 导航 / 工具条 / 场景条 */
```
```js
// ==== @section fn-modal ==== 弹窗提交门 / 代理校验 / 至少勾一个 / 任务回写
```

规则：

| 项 | 约定 |
| :--- | :--- |
| 区边界 | **一个区的终点就是下一个锚点**，不写 `@endsection`，不嵌套 |
| slug | 唯一、小写、连字符；前缀标类别：`css-` / `html-` / `card-` / `data-` / `fn-`；**定下后不改** |
| 子锚点 | 热点区里的可定位单元单独起锚点，如 `confirm-<组件>-<动词>`（10 个弹窗各自可达） |
| 密度 | 一区 30~80 行为宜（实例：42 锚点 / 1827 行 ≈ 43 行一区）；太稀等于没分区，太密 map 会膨胀 |
| `index` | 文件第一个锚点，只写一句「改本页前先查 `<主体>-map.md`」，让直接打开 HTML 的人也能找到索引 |
| 说明文字 | 写「这一区装什么」，不写「怎么改」；改动方法归 map |

🔴 **锚点只能是注释**：补锚点那次提交用 `git diff --unified=0` 验证「除注释行外无任何内容变更」；
改完内联脚本再跑一次 `node --check`。锚点不是运行时标记，不参与任何逻辑。

## 4. 索引侧：写 map（可直接复制的骨架）

命名强制 **`<主体文件名去扩展名>-map.md`**，与主体同目录，**一个文件一份 map**。
不要用 `prototype-map.md` 这类泛名 —— 第二个原型出现时它立刻会被误读成「所有原型的地图」。

````md
> 状态：**现行**（YYYY-MM-DD；N 个 `@section` 锚点）

# <主体文件名> 分区索引

单文件原型（约 X 行 / 约 Xk tokens；行数会漂移，以 `wc -l` 为准）。改动前**不要通读全文**：

    grep -n "@section" docs/<主体>.html     # 一次拿到全部锚点 + 当前行号

按命中行号定点 `Read offset=<行号> limit=40`，再用 `Edit` 改锚点下的那一段。
锚点格式 `==== @section <slug> ==== 说明`；**一个区的终点就是下一个锚点**。本文不写死行号。
HTML 段用 `<!-- -->`、CSS 段用 `/* */`、JS 段用 `//`。

## 改 XX 去哪

| 要改的东西 | 锚点 |
| :--- | :--- |
| 配色 / 变量 / 导航 | `css-base` |
| 确认弹窗 DOM / 勾选 / 目标镜像 | `html-modal` |
| 改某个弹窗文案 | `confirm-<组件>-<动词>` |

（大静态数据区补一句键定位法，例：`grep -n "  <键>: {"` 直接定位，不必读整个 `data-scenes` 区。）

## 维护约定

- 新增或拆分区块 → 同步补一个 `@section` 锚点 + 本表加一行；slug 定下不改，**行号不写进文档**。
- 本文只索引**单个文件内部**；能力索引仍是 `AGENTS.md` 的「文档速查」表。
- 母本见 `cqlql-notes/docs/工程/单文件原型分区锚点约定.md`。
````

写表的两条要点：

- **按「人话任务 → slug」写，不按文件顺序复述目录** —— 后者是 `grep -n` 的活，抄一遍只会多一处可漂移的副本。
- 一任务一行；跨多区的任务写 `fn-plan` + `fn-render` 这样并列两个 slug，别合并成一个含糊的大区。

---

## 5. 改动时的标准动作（给 AI 的 SOP）

1. **先读 map**（不到 100 行），不读 HTML。
2. 在「改 XX 去哪」表里按人话任务找到 slug。
3. `grep -n "@section <slug>" <主体>` 取**实时**行号。
4. `Read offset=<行号> limit=40~80` 读完这一区；确实跨区再读下一个，一次最多 2~3 区。
5. `Edit` 定点改，只回传锚点下那一段。
6. 若新增 / 拆了区块：补锚点 → 更新 map 表 → 跑 §6 自检。
7. 项目 `AGENTS.md` 的文档规则里留**一行**指针（「改原型前先 grep 锚点定点读」），不要为它新建索引。

> 🔴 红线：不要「保险起见把全文读一遍」。不确定就再 grep 一个锚点，而不是通读。
> 这条要写进项目 AGENTS，否则下一次会话的 AI 会默认通读，前面全白做。

## 6. 验收与防漂移

```bash
# ① 锚点总数（与 map 状态行对账）/ slug 唯一（应无输出）
grep -c "@section" docs/<主体>.html
grep -n "@section" docs/<主体>.html | sed 's/.*@section \([^ ]*\).*/\1/' | sort | uniq -d

# ② map「改 XX 去哪」表引用的 slug 逐个对账（应无输出）
grep -o '@section [a-z0-9-]*' docs/<主体>.html | awk '{print $2}' | sort -u > /tmp/slugs
grep '^| ' docs/<主体>-map.md | sed 's/^|[^|]*|//' \
  | grep -o '`[a-z][a-z0-9-]*`' | tr -d '`' | sort -u > /tmp/refs
comm -23 /tmp/refs /tmp/slugs

# ③ 纯补锚点那次：只允许注释行变化
git diff --unified=0 docs/<主体>.html
```

> ⚠️ ② **只取表格第二列**。对全文所有反引号做全量匹配必然误报：实例里
> `image-copy`（CLI 动词）、`absent` / `healthy` / `failed`（场景键）、`planned`（状态标签）
> 都不是锚点，机械对账会报 5 个「缺失」，真正的漏补反而被淹在噪声里。
> 实测取第二列后差异为 0。

- 注释配对检查：HTML `<!-- -->` / CSS `/* */` / JS `//`；内联脚本 `node --check`。
- 每次改完原型做一次，成本几秒。

🔴 **最大的失败模式是漂移**：新增区块忘了补锚点 → map 变旧 → AI 按旧表定点读，读到错的区、
改错地方，而且因为「只看了 40 行」还看不出来。所以「新增区块同步补锚点 + 表加一行」
必须是项目 AGENTS 里的硬规则，不是建议。

## 7. 反模式速查

| 反模式 | 后果 |
| :--- | :--- |
| map 里写死行号 | 文件一长，整张表失效 |
| 用泛名 `prototype-map.md` | 第二个原型出现就串味（实例里已因此改过一次名） |
| 把 map 当能力索引 | 两个索引必然漂移，违反 [文档约定](文档约定.md) §4 |
| 锚点名随功能改名 | map / AGENTS / 历史对话里的引用全失效 |
| 想靠锚点解决「加组件要改 7 处」 | 越改越累，该升二档声明式化 |
| 给 200 行的一次性原型上这套 | 维护成本 > 收益 |
| 锚点里塞逻辑或可执行标记 | 破坏「注释零改动」，也可能改变行为 |

## 8. 实例（可对照抄）

| 项 | `pass-up.ops` |
| :--- | :--- |
| 主体 | `docs/components-prototype.html`：1827 行 / 121 KB，42 个 `@section`（约 43 行一区） |
| 索引 | `docs/components-prototype-map.md`：约 60 行，「改 XX 去哪」表 + 7 个场景键定位法 + 维护约定 |
| 入口 | 文件首个 `index` 锚点指向 map；`AGENTS.md` 文档规则一行指针 |
| 实测 | 改「MinIO 更新弹窗文案」→ `grep` 命中 1203 行，定点读 ~25 行（当时 1411 行，原来要通读 ~25k tokens） |
| 落地成本 | 补锚点那次：正文 0 改动，1411 → 1436 行全是注释；不新增任何资源文件 |

> 一句话：**先让文件可寻址，再谈拆不拆**。
> 锚点是「零交付形态变化」的第一档，不是终点；当痛点从「读哪里」变成「改动面」时按 §2 升档。
