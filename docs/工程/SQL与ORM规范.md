## 零、核心工程原则（这段进 AGENTS.md）

这 25 行是**所有条款的上位规则**。条款冲突时以本节为准；本节与某条 MUST 冲突时，  
说明那条 MUST 写错了，去改它，而不是绕过本节。

### 1. 结果导向

- 以**实际运行结果**作为判断依据，不以「代码形式是否符合某种惯例」作为判断依据。
- 规范是指导，不是目的。理论分析不能替代必要的实际验证。
- 不因为某种写法看起来不优雅，就认定它有问题。
- 不因为某种写法符合最佳实践，就认定它一定正确。

### 2. 合理决策

- 优先选择**简单、清晰、可靠、可维护**的实现。
- SHOULD 遵循成熟实践，但不机械套用；技术规范允许根据业务场景合理例外。
- 偏离 MUST 必须先解决约束冲突，**不得自行忽略**。
- 偏离 SHOULD 且存在明显风险时，说明原因。
- 不得为了满足单项规范而引入更严重的问题（更多代码、更难维护、更慢）。
- 不要对没有实际瓶颈的代码做过度优化。

### 3. 实现验证

- 代码写完不代表任务完成，应按改动类型做必要验证（见 §六）。
- 优先跑已有自动化测试；关键业务逻辑补必要测试。
- 性能敏感实现必须实测；优化必须有明确问题依据，并在优化后重新测。
- **不得将未经执行的测试描述为「已通过」**。
- 无法验证的部分必须明确说明，不得假定其正确。
- 不要求所有简单 CRUD 都压测或做复杂性能分析。

## 一、约束等级与「例外」怎么写

规范的价值不在「禁止了什么」，而在**让人知道哪条不能碰、哪条可以商量**。

| 等级         | 含义                 | 违反时                           | 典型内容                                   |
| :--------- | :----------------- | :---------------------------- | :------------------------------------- |
| **MUST**   | 安全、数据完整性、业务正确性的硬要求 | 不许自行偏离。确有冲突 → 停下来说明冲突，改设计或改规范 | 参数绑定、金额不用浮点、扣减用原子更新、结构变更走 Flyway       |
| **SHOULD** | 通常有明确收益，允许合理例外     | 可以偏离，但**存在实际风险时要说明原因**        | 避免不合理 N+1、DTO 投影、控制事务范围、EXPLAIN 验证     |
| **MAY**    | 按场景选型              | 选哪个都行，但要能说出为什么                | JPA / 原生 SQL、OFFSET / Keyset、乐观锁 / 悲观锁 |

**例外的写法**（三句话，不要写成报告）：

```md
偏离：SHOULD「避免 N+1」。
原因：该列表最多 5 条，日调用量 < 100，批量查询会让权限过滤逻辑多绕一层。
依据：已用 Hibernate Statistics 确认单次请求 6 次 SQL，P95 12ms。
```

**反向要求同样成立**：对每个简单 CRUD 都写一份技术决策报告，本身就是过度设计。  
只有「偏离 SHOULD 且存在实际风险」时才需要这三句。

## 二、先破除五个「看着像错、其实不一定」的判断

这一节比后面所有条款都重要 —— 大部分误伤都发生在这里。

| 现象             | 什么时候是问题                                                       | 什么时候不是问题                                                  |
| :------------- | :------------------------------------------------------------ | :-------------------------------------------------------- |
| **N+1**        | 列表条数随业务增长（分页 20 条 × 每条 3 次 = 60 次往返）；接口在高频路径上；数据量已到万级         | 结果集只有 2~3 条；低频后台/定时任务；关联是条件性的（只有展开详情才查）；批量查询会引入明显更复杂的过滤逻辑 |
| **`SELECT *`** | 高频列表接口；表里有大字段（`text` / `jsonb` / `bytea`）；只需要 2 个字段的报表；破坏覆盖索引 | 确实需要完整实体；小型配置表（几十行）；后台低频管理操作；临时排查数据                       |
| **EAGER**      | 该实体被大量查询复用，EAGER 会传染到每个查询                                     | 一对一且必然一起用（如 `order -> order_snapshot`），且只有一个查询入口          |
| **OFFSET 分页**  | 深翻页（`OFFSET 100000`）；无限滚动；导出全量                                | 后台管理列表（最多几百页且不常翻到底）；总量小；必须显示「第 N 页 / 共 M 页」               |
| **逐条操作**       | 十万级数据写入；循环里发 SQL 且循环次数由业务数据决定                                 | 一次只处理几条；每条都要独立事务与独立结果（部分成功要分别报错）                          |

**判断方法统一是三个数**：**查询次数 × 单次数据量 × 调用频率**。  
三个数都小 → 不是问题；任一个随业务增长 → 是问题。**不看代码形态，看这三个数。**

## 三、问题总表（按风险排序，不是按代码写法）

| 分类     | 问题                  | 主要风险                          | 等级       |
| :----- | :------------------ | :---------------------------- | :------- |
| SQL 安全 | 字符串拼接用户输入           | 注入、数据泄露/破坏                    | **MUST** |
| 数据类型   | 金额用 float / double  | 精度错误、对账不平                     | **MUST** |
| 并发     | 先查后改做扣减             | 丢失更新、超卖                       | **MUST** |
| 数据完整性  | 只靠应用校验，库里无约束        | 脏数据、并发窗口                      | **MUST** |
| 事务     | 事务内调外部 IO           | 长事务、连接与行锁被占                   | **MUST** |
| 迁移     | 手工改生产表结构            | 环境不一致、不可追踪                    | **MUST** |
| 软删除    | 软删除与唯一约束冲突          | 无法重建同名记录                      | **MUST** |
| 查询性能   | 深分页（大 OFFSET）       | 扫过再丢弃，越翻越慢                    | SHOULD   |
| 查询性能   | N+1                 | 往返次数放大                        | SHOULD   |
| 查询性能   | 只查需要很少字段却取全表        | 多余 IO、内存                      | SHOULD   |
| 查询性能   | 索引缺失 / 用不上（函数、隐式转换） | 全表扫描                          | SHOULD   |
| ORM    | JOIN FETCH + 集合分页   | 重复行 + 内存分页                    | SHOULD   |
| ORM    | 脏检查隐式 UPDATE        | 意外的全列更新、审计失真                  | SHOULD   |
| ORM    | 批量操作后持久化上下文不一致      | 读到旧值、覆盖他人修改                   | SHOULD   |

| 资源     | 连接池耗尽               | 请求堆积雪崩                        | SHOULD   |
| 性能     | 无依据的「优化」            | 更慢、更难维护                       | SHOULD   |

## 四、技术选型：五种方式并存，不强制统一

「全用 ORM」和「全用原生 SQL」都是错的。**按查询的复杂度与可控性需求选**。

| 方式                                                               | 适合                               | 不适合                            |
| :--------------------------------------------------------------- | :------------------------------- | :----------------------------- |
| Spring Data JPA（派生查询 / `findById`）                               | 常规 CRUD、按主键或单条件取实体、实体生命周期管理      | 多表复杂条件、报表聚合                    |
| JPQL / Criteria                                                  | 面向实体的中等复杂查询、需要动态拼条件但仍是实体语义       | 需要窗口函数、CTE、`ON CONFLICT` 等方言能力 |
| MyBatis                                                          | 复杂 SQL、动态查询、需要精确控制 SQL 形态        | 简单 CRUD（多一层 XML/注解维护成本）        |
| `JdbcTemplate`                                                   | 批量写、精确控制 SQL、无实体语义的数据搬运          | 需要实体关系与懒加载的场景                  |
| 原生 SQL（`@Query(nativeQuery` / `EntityManager.createNativeQuery`） | 原子更新、`FOR UPDATE`、复杂统计、批量 upsert | 需要跨库移植（放弃方言能力就得改回来）            |

**MAY**：同一模块里混用是正常的。判据是「这段 SQL 的复杂度是否已经超出 ORM 表达能力」——  
超出了就用原生 SQL，不要用 Criteria 拼一个 80 行、没人看得懂的等价物。

**MUST**：无论用哪种，**参数绑定、事务边界、结果映射的显式性**三条要求不变。

## 五、具体规范

标注约定：🔴 = MUST，无标注 = SHOULD，`MAY` = 按需。

### 5.1 查询与字段

- 🔴 **列表/分页查询必须有确定性排序**，且排序键包含唯一列：  
  `ORDER BY created_at DESC, id DESC`。只按 `created_at` 排序时，同一毫秒的多行顺序不定，  
  翻页会重复或漏数据。PostgreSQL 不保证无 `ORDER BY` 时的返回顺序。
- 🔴 **禁止把用户输入拼进 `ORDER BY` / 表名 / 列名**（参数绑定对标识符无效），走白名单映射。
- **只取业务实际需要的字段**：判据是「返回行数 × 行宽 × 频率」。列表接口、含大字段的表、  
  报表、导出，一律 DTO / 投影查询。
- **避免在 `WHERE` 里对列做运算**：`WHERE date(created_at) = :d`、`WHERE lower(name) = :n`  
  会让普通索引失效。改成范围条件（`>= :d AND < :d + 1`），或建表达式索引。
- **注意隐式类型转换**：`varchar` 列传数字、`bigint` 列传字符串，都可能让索引失效  
  （PostgreSQL 里表现取决于操作符与类型，用 `EXPLAIN` 确认，不要凭直觉）。

### 5.2 关联与加载

- 🔴 **集合关联默认 `LAZY`**。`EAGER` 只在「一对一且唯一查询入口」时使用。
- 🔴 **JOIN FETCH 不与集合分页同用**：Hibernate 会在内存里分页，且返回行数被放大。  
  需要时拆两步 —— 先分页查主表 ID，再按 ID 批量取关联。
- 🔴 **Entity 不出模块**（Controller 不返回、不被别的模块当参数），用 DTO。  
  理由不是「更规范」，而是 Entity 带懒加载语义与持久化注解：一旦作为响应，  
  加字段就是契约变更，还会把内部列（风控标记、软删除位）发出去。
- **显式关闭 `spring.jpa.open-in-view`**（默认 `true`）：它把 Session 拖到视图渲染结束，  
  让「事务外懒加载」看似能用，实际把连接持有时间拉长，问题被推迟到压测才暴露。
- **不要在事务外触发懒加载**。`LazyInitializationException` 是设计信号（该查的没查），  
  不要用 `Hibernate.initialize()` 到处打补丁。

### 5.3 分页

`MAY` 两种方式并存，判据如下：

| 场景                 | 选型                                                                    | 理由            |
| :----------------- | :-------------------------------------------------------------------- | :------------ |
| 后台列表、总量小、需要「共 M 页」 | `OFFSET / LIMIT`                                                      | 实现简单，能算总数     |
| 深翻页、无限滚动、导出、时间线    | **Keyset**（`WHERE (created_at, id) < (:t, :id) ORDER BY ... LIMIT n`） | 恒定成本，不随页码退化   |
| 只需要「有没有下一页」        | Keyset + `LIMIT n+1`                                                  | 省掉 `COUNT(*)` |

- **单独评估 `COUNT(*)` 的成本**：多表 JOIN + 大表 count 常常比数据查询本身还慢。  
  前端不需要总数就不要查；需要时考虑近似值或缓存。
- PostgreSQL 的 `OFFSET` 是**扫过再丢弃**，不是跳过 —— `OFFSET 100000` 会真的读 10 万行。

### 5.4 索引

- 🔴 **索引依据真实查询条件建**（`WHERE` + `JOIN` + `ORDER BY` 的组合），不是「给常用字段各建一个」。
- **复合索引顺序**：等值条件列在前，范围/排序列在后；遵循最左前缀。  
  建之前先看现有索引能否复用（调整顺序往往比新建更划算）。
- **唯一性靠唯一索引/约束表达**，不要靠应用层「先查再插」（并发下必漏）。
- **低区分度列单独建索引通常无用**（`status`、`gender`、`deleted`）：优化器多半不会用，  
  还要付写入成本。这类列应作为复合索引的后缀列。
- **索引有写放大**：每加一个索引，每次写入多一次维护。给「可能要查」的字段预建索引是负收益。
- 🔴 **索引变更必须在接近生产规模的数据上验证执行计划**（见 §六），空表上的 `EXPLAIN` 全是 `Seq Scan`，没有参考价值。

### 5.5 SQL 安全

- 🔴 **所有值参数必须绑定**（`?` / `:name` / `#{}`）。禁止任何形式的字符串拼接用户输入。
- 🔴 **动态标识符（排序字段、表名、列名）走枚举白名单映射**，不能靠转义。
- **`LIKE` 的用户输入要处理 `%` `_` 转义**（否则用户输入 `%` 就变成全表匹配，既是语义错误也是性能事故）。
- **数据库账号最小权限**：应用账号不给 DDL、不给超级用户；迁移用独立账号。

### 5.6 数据完整性与类型

- 🔴 **金额用 `NUMERIC(19,4)` + `BigDecimal`**。禁止 `float` / `double` / `REAL`（二进制浮点无法精确表示 0.1）。  
  统一小数位与舍入规则（`HALF_UP`），并写进字段注释。
- 🔴 **绝对时间点用 `Instant` ↔ `TIMESTAMPTZ`**。不要用 `LocalDateTime` 存「何时发生」——  
  它没有时区，跨时区/夏令时/服务器时区变更都会偏。`DATE` 只用于「日历日」这类无时刻语义的值。
- 🔴 **约束尽量下沉到数据库**：`NOT NULL`、`UNIQUE`、`CHECK`、`FOREIGN KEY`。  
  应用校验有并发窗口和绕过路径（脚本、其他服务、手工修数据），数据库约束是最后一道。
- **状态字段用可读值 + `CHECK` 约束**（或枚举映射到 `smallint` + 注释写清取值），  
  不要裸魔法数字；新增取值要同步约束与注释。
- **外键是否建**：按团队约定统一。不建就必须在应用层保证引用完整性，并写清这一点 —— 不要一半建一半不建。

### 5.7 事务与并发（数据库视角）

> 代码层怎么写（代理失效、自调用、`rollbackFor`、幂等实现）见 [代码设计规范](./代码设计规范.md) §四。  
> 本节只讲**数据库这一侧**的约束，不重复上面的内容。

- 🔴 **事务内不做外部 IO**（HTTP、同步发 MQ、读文件、调模型）：外部调用慢且会超时，  
  期间连接与行锁一直被占。要「落库 + 通知」，就落库提交后异步发（Outbox 或本地消息表）。
- 🔴 **扣减/占用类操作禁止「先查后改」**，用原子 SQL 判断影响行数：
  ```sql
  UPDATE account
     SET balance = balance - :amount
   WHERE id = :id AND balance >= :amount;
  -- 影响行数 = 0 → 余额不足，抛业务异常，不要静默返回 false
  ```
- 🔴 **多行加锁保持统一顺序**（如按主键升序），否则两个事务交叉加锁必然死锁。
- 🔴 **死锁按「可重试异常」处理**：有限次重试 + 退避，并记录日志。吞掉死锁异常等于丢业务。
- `MAY` **乐观锁 vs 悲观锁**：
  - 冲突概率低、可以重试 → 乐观锁（`@Version` / `version` 列，`UPDATE ... WHERE version = :v`）。
  - 冲突概率高、业务必须成功、持有时间短 → 悲观锁（`SELECT ... FOR UPDATE`，注意锁范围与超时）。
  - 乐观锁重试要设上限，并保证重试块内无副作用（不发消息、不写日志表）。
- **只读查询标 `readOnly = true`**：跳过脏检查、避免误触发 flush。
- **隔离级别保持数据库默认**（PostgreSQL 是 `READ COMMITTED`）。不要用提升隔离级别来「保证正确」——  
  它带来序列化失败与重试，正确性应该由原子更新/锁/唯一约束保证。

### 5.8 批量操作

- 🔴 **大批量必须分批**（每批 500~1000，按实测调），不要一次 `IN` 十万个 ID（SQL 长度、执行计划、内存三重风险）。
- 🔴 **JPA 的 `saveAll` 不等于批量插入**：`IDENTITY` 主键会禁用 JDBC batch（Hibernate 需要立即拿到 ID）。  
  要真批量：改用 `SEQUENCE` 生成器 + `hibernate.jdbc.batch_size`，或直接 `JdbcTemplate.batchUpdate`。
- 🔴 **JPQL bulk `update` / `delete` 后要 `flush()` + `clear()`**：它绕过持久化上下文，  
  内存里的实体仍是旧值，后续读会拿到脏数据。
- **批量前先实测**：逐条 vs 批量在目标数据规模下的耗时对比。批量不一定更快  
  （大批量单事务会放大锁持有时间与 undo/WAL 体积）。

### 5.9 软删除

- 🔴 **软删除列全库统一**（建议 `deleted_at TIMESTAMPTZ NULL`），不要一张表一个花样。
- 🔴 **软删除与唯一约束共存，用部分唯一索引**：
  ```sql
  CREATE UNIQUE INDEX uk_user_email_alive
      ON app_user (email)
   WHERE deleted_at IS NULL;
  ```
  普通 `UNIQUE(email)` 会导致「删掉的记录占着邮箱，同名无法重建」。
- 🔴 **过滤软删除必须统一**（`@SQLRestriction` / 统一基类 / 视图），不要指望每个查询都记得加 `WHERE deleted_at IS NULL`。  
  漏一处就是数据泄露或统计错误。
- **高频表慎用软删除**：数据只增不减会稀释索引效率、拖慢统计。量大时考虑归档表或分区。

### 5.10 数据库迁移

- 🔴 **结构变更一律走 Flyway**，禁止手工改任何环境的表结构（手工改 = 环境不一致 + 不可追踪）。
- 🔴 **已执行过的迁移脚本不再修改**（checksum 校验会失败）。改结构就发新版本脚本。
- 🔴 **破坏性变更分两步发布**：先加列/双写并兼容旧代码，等全量发布后再删旧列/改名。  
  一个脚本里「删列 + 改代码」= 发布期间必然报错。
- **大表变更注意锁**：加索引用 `CREATE INDEX CONCURRENTLY`（不能放在事务块里）；  
  加非空列要给默认值（PG 11+ 加常量默认值不重写表，但仍要确认版本行为）；大表回填分批做。
- **迁移必须在「有历史数据的库」上跑过**，空库跑通不代表能跑 —— 约束冲突、脏数据、超长值都只在真实数据上暴露。
- 迁移脚本命名与目录遵循仓内既有约定；脚本里写清「为什么改」，不要只写 DDL。

## 六、验证闭环：怎么证明它是对的

**代码符合规范，不代表运行效果就好。** 这一节是本文档的落点。

```
编写实现 → 自测验证（正确性 / 性能 / 资源） → 发现问题 → 优化 → 重新测试对比
```

### 6.1 按改动类型定验证力度（不要一律压测）

| 改动类型           | 最低验证                      |
| :------------- | :------------------------ |
| 普通 CRUD        | 单元测试 + 集成测试（含异常路径、空结果）    |
| SQL 查询逻辑改动     | 结果正确性 + 查询次数              |
| 复杂关联 / 多表 JOIN | 查询次数 + `EXPLAIN` 执行计划     |
| 高频接口（首页、列表、详情） | 接口压测：P95 / P99 / 吞吐 / 错误率 |
| 批量操作           | 小 / 中 / 大三档数据规模的耗时对比      |
| 余额、资产、库存、额度扣减  | **并发测试（必须）** + 事务边界检查     |
| 索引变更           | 执行计划对比 + 优化前后耗时           |
| 数据库迁移          | 空库 + 历史数据 + 预发环境各跑一次      |
| 软删除 / 唯一约束改动   | 重复插入、删除后重建同键、并发插入         |

### 6.2 SQL 执行计划

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, amount
  FROM recharge_order
 WHERE user_id = 100
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

看这六项，别只看总耗时：

| 项                            | 要看什么                                   |
| :--------------------------- | :------------------------------------- |
| `Execution Time`             | 绝对值，以及优化前后对比                           |
| `Seq Scan` / `Index Scan`    | 大表上的 `Seq Scan` 是否合理（小表全扫是对的）          |
| `Actual Rows` vs 估算 `rows`   | 差 10 倍以上 → 统计信息过期或索引选择错误（考虑 `ANALYZE`） |
| `Rows Removed by Filter`     | 扫了很多又丢掉 → 索引没覆盖过滤条件                    |
| `Buffers`（shared hit / read） | `read` 高 → 缓存未命中，磁盘 IO                 |
| `Sort`（尤其 `external merge`）  | 外部排序 → `work_mem` 不够或索引未覆盖排序           |

- 🔴 **`EXPLAIN ANALYZE` 会真正执行语句**。`UPDATE` / `DELETE` 必须在事务里跑完 `ROLLBACK`，  
  或改写成等价的 `SELECT`。禁止在生产库直接跑。
- 对比优化前后，**必须同一份数据、同一台机器、同一条 SQL**，否则数字没有意义。


### 6.3 查询次数

工具任选：**Hibernate Statistics**（`hibernate.generate_statistics=true`）、
**datasource-proxy**、**P6Spy**（日志友好，适合定位具体语句）。

看四件事：

1. 单次请求 SQL 总次数；
2. 按类型分布（SELECT / INSERT / UPDATE / DELETE）；
3. 是否有**参数不同、形态相同的重复语句**（N+1 的指纹）；
4. 关联查询是否被拆成了 N 次（而不是 1 次 JOIN 或 1 次 `IN`）。

### 6.4 接口性能

工具：**k6**（脚本化、易进 CI）或 **JMeter**（图形化、团队通用）。

| 指标 | 意义 |
| :--- | :--- |
| 平均响应时间 | 参考值，**不要用它下结论**（长尾被平均掉） |
| **P95 / P99** | 真实用户体验；优化看这两个 |
| 吞吐量（RPS） | 容量规划依据 |
| 错误率 | 超时、连接池耗尽、死锁都会体现为错误率上升 |

同时看 **CPU、内存、连接池活跃/等待数、数据库连接数与慢查询**。
接口变慢但 CPU 不高 → 大概率在等 IO 或等锁，不是「代码不够快」。

### 6.5 并发测试（钱 / 权益类必须）

场景写清楚，断言要能失败：

```
初始余额 1000
请求 A 扣 700，请求 B 扣 500，同时到达
预期：恰好一个成功、一个失败（余额不足）；最终余额 300；不允许出现负数或 800
```

实现：JUnit + `CountDownLatch`（统一放行）+ 线程池，循环多轮（并发 bug 单轮跑不出来）。
断言三件事：**成功数符合预期、最终余额正确、没有中间态被读到**。
用 `@Version` 的实现，还要验证「重试后仍不超卖」。

### 6.6 数据规模

| 环境 | 规模 | 用途 |
| :--- | :--- | :--- |
| 单元/集成测试 | 几条 | 逻辑正确性 |
| 功能自测 | 几百~几千 | 分页、排序、边界 |
| 性能验证 | **10 万~百万级，分布接近生产** | 索引、执行计划、深分页 |

「分布接近生产」比「数量够大」更重要：如果 100 万订单全属于同一个用户，
索引测试结果全是错的。构造数据时按真实基数造（用户数、每用户订单数、状态分布）。

### 6.7 报告纪律（🔴 MUST）

- **不得把没跑过的测试写成「已通过」**。
- 没验证的部分写「**未验证 + 原因**」（如「无生产规模数据，未做深分页压测」）。
- 优化的结论必须带数字：**优化前 P95 180ms / 6 次 SQL → 优化后 40ms / 2 次 SQL**。
  「已优化」「性能提升」不算结论。
- 写清测试条件：环境、数据量、并发数、是否冷缓存。

## 七、AI 机械执行的六种表现（自查用）

规范写歪了，AI 会这样执行 —— 见到就停：

1. 看到 `SELECT *` 就改，不看它是不是在查完整实体。
2. 见到循环里查库就拆成批量 `IN`，哪怕列表只有 3 条、且批量后逻辑复杂一倍。
3. 给每个方法都套 `@Transactional(readOnly = true)` + DTO + 接口，哪怕是个内部私有方法。
4. 把两分支 `if` 改成 Strategy + Factory + 注册表。
5. 声称「已消除 N+1」，但没跑过任何查询次数统计。
6. 两个极端：要么偏离规范一声不响；要么给每个 CRUD 附一份技术决策报告。

**正确姿势**：先对照 §二 判断是否命中「不是问题」，再决定改不改；改了要给前后数字；
不改要说一句为什么。**规范用来做决策，不用来刷改动量。**

## 八、交付前自检

改完数据访问层代码逐条过（不适用写「不涉及」，不要静默跳过）：

- [ ] 分页/列表有确定性排序，且排序键含唯一列？
- [ ] 有没有把用户输入拼进 SQL 或标识符？动态排序走白名单了吗？
- [ ] 新增查询是否带上了软删除过滤？唯一约束是否与软删除冲突？
- [ ] 关联是 `LAZY` 吗？有没有 `EAGER` 或 `JOIN FETCH` + 集合分页？
- [ ] 返回给前端的是 DTO 还是 Entity？
- [ ] 金额字段是 `NUMERIC` + `BigDecimal`？时间是 `Instant` + `TIMESTAMPTZ`？
- [ ] 扣减/占用是原子 SQL 或行锁，还是「先查后改」？影响行数为 0 时抛了吗？
- [ ] 事务里有没有外部 IO？多行加锁顺序是否一致？
- [ ] 批量操作分批了吗？`saveAll` 是否误当成了批量插入？bulk 后 `flush` + `clear` 了吗？
- [ ] 新增/修改的索引，在接近生产规模的数据上看过执行计划吗？
- [ ] 结构变更是否通过 Flyway？脚本是否可重入、是否在历史数据上跑过？
- [ ] 按 §6.1 的力度做了对应验证吗？验证结果有数字吗？
- [ ] 未验证的部分，是否在交付说明里写清了原因？

**`AGENTS.md` 里推荐的指针写法**（一句结论 + 一个指针，不要复制正文）：

```md
- 🔴 扣减/占用禁止「先查后改」，用原子 UPDATE 判断影响行数（影响行数 0 要抛）。

- 🔴 软删除表的唯一约束必须用部分唯一索引（`WHERE deleted_at IS NULL`），否则删掉的记录占着键。
  见 `docs/sql-orm.md` §5.9。
- 性能相关结论必须带前后数字，禁止「已优化」。见 `docs/sql-orm.md` §6.7。
```
