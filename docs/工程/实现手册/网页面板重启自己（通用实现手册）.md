## 0. 一页速用

目标形态，五段交接，**顺序不能换**：

```text
页面「重启」按钮 → POST /api/restart（confirm + rebuild）
  → [1] 服务端可选重建，产物落到 <tool>.next.exe（失败就地停，服务照旧在跑）
  → [2] 先回 200（显式 Content-Length）→ 拉起 __restart 接手进程（detached，输出进日志）
  → [3] 旧进程 shutdown（让出端口）→ exit 0（原守护随之结束）
  → [4] 接手：等端口空 → 把 next.exe 换到正式 exe → __takeover 同端口同 token 起服务
  → [5] 前端轮询 /api/health，boot_id 变了才 location.reload()
```

四句红线，先记住：

1. 🔴 **重建失败就地停**。构建可能产出一个起不来的二进制，而交接之后没有回头路。
2. 🔴 **不换 token**。前端 token 通常只在内存 + 地址栏；换掉之后轮询 health 会一直 401，
   `boot_id` 永远拿不到，界面会把一次**成功**的重启误报成失败。
3. 🔴 **判据只有 `boot_id`**。交接失败时旧进程会刻意原地活着，那时「服务还在」与
   「重启成功」在界面上完全一样；传输层失败也不是失败。
4. 🔴 **重建过就从产物 `next.exe` 拉起接手进程**。从正式 exe 拉，接手进程自己锁住它，
   接下来的换身永远 `Access is denied`，日志却只写「换不上」。

## 1. 适用与不适用

### 1.1 适用

- 本机**单二进制**工具（Go / Rust / Node 打包均可），已有或想要一个 `127.0.0.1` 的 Web 面板。
- 开发时反复改代码，需要「重建 → 重启」这条循环不再靠手工四步。
- 平台是 Windows（本文的交接机制是 Windows 专属，见 §3）。

### 1.2 不适用（别硬套）

| 场景 | 为什么 | 该怎么做 |
| :--- | :--- | :--- |
| 服务端 / 多实例 / 有负载均衡 | 没有「单个本机进程」可换 | 走正常的滚动发布 |
| 前端产物由别的进程托管（独立 dev server） | 二进制里没有需要重建的嵌入产物 | 只重启后端，构建交给前端工具链 |
| 无法写本机日志文件 | detached 进程没有控制台，启动失败原因会静默丢掉 | 先补日志落点，见 §1.3 |
| Linux / macOS | 那边有 `syscall.Exec`，同 PID 换映像更干净 | 用 exec，不要照抄本文的接手进程 |

### 1.3 🔴 开工前必须满足的四个前提

**缺任何一个，就别做**，照母本 §8 保留「不做自重建」并在文档里写明理由。

| 前提 | 缺了会怎样 |
| :--- | :--- |
| 构建输出能同时**回 HTTP 响应**并**落日志** | 重建失败在隐藏进程里无人看见 —— 这正是母本当初否决它的正当理由 |
| 有一个本机日志文件作为 detached 进程的输出落点 | 新进程启动失败时只剩「连不上」，原因查不到 |
| 单实例凭据可复用（端口 + token 落盘，如 `ui.json` 0600） | 页面回来后 401，或新进程绑到别的端口 |
| 前端能读到「进程实例标识」（`boot_id`） | 只能按「服务还在」判，交接失败会被报成成功 |

## 2. 三条硬约定：当初「不做」的理由怎么被解决

| 母本 §8 的顾虑 | 本文的对策 | 不做会怎样 |
| :--- | :--- | :--- |
| 重建链路长、失败面大 | **先重建、成功才交接**；失败回 500 + 构建输出进响应 | 构建出一个起不来的二进制，服务彻底没了 |
| 失败发生在隐藏进程、无人看见 | 新进程 stdout/stderr **重定向到日志**；确认弹窗显示日志路径 | 启动失败原因静默丢掉，人只能对着「连不上」猜 |
| 链路长，人会懒得点、干脆不重启 | **过期检测自动勾「先重建」**；前端产物新鲜时跳过耗时的前端构建 | 忘了勾 = 用旧二进制起来，症状是「我明明改了，界面怎么没变」 |

> 这三条互为前提：只做第一条（失败就地停）而不做第二条（日志落点），
> 等于把「失败得看得见」换成了「失败得见得着、但成功失败都查不到」。

## 3. 机制选型：Windows 上没有 exec

| 机制 | 平台 | 评价 |
| :--- | :--- | :--- |
| `syscall.Exec`（同 PID 换映像） | Linux / macOS | 同终端、同 cwd/env，失败原因就在原终端里；**但 Windows 没有** |
| 退出码 75 + `exe.new` 换身 + 启动器循环重拉 | Windows | 复用守护；代价是要改启动器（CRLF / ASCII 注释 / 隐藏窗口 `pause` 规则），多一处状态机 |
| **detached 接手进程 + 内部子命令**（本文选它） | Windows | 启动器**一行不改**；失败面收敛到「旧进程 / 接手进程」两处，日志同一份 |

**为什么不用守护循环**：启动器是这类工具里最脆的一层（批处理解析、代码页、隐藏窗口），
让它承担「退出码 → 换文件 → 重拉」的状态机会把风险放到最不该放的地方。
独立接手进程只认三个参数，行为可单测。

**但已有退出码 75 方案时先评估，不要为了统一而重写**：只要满足 §1.3 四个前提，
可以在原机制上补齐 `boot_id`、确认视图与六道门；`ReplaceBinary` 的同路径拒绝与
`boot_id` 唯一判据这两条必须补。没有旧方案时，再按本文落地。

**Windows 上必须显式补 exec 免费给的两件事**：

| 缺什么 | 判据 / 做法 | 漏了的症状 |
| :--- | :--- | :--- |
| 监听地址要先被让出来 | `WaitPortFree(addr, 60s)`：反复尝试 `net.Listen(addr)`，**能绑上**就是「可以接手」；不查 PID（会复用、会因权限查不到） | 新进程绑不上端口，界面「重启完连不上了」 |
| 新进程不能共享原控制台 | `DETACHED_PROCESS` + `CREATE_NEW_PROCESS_GROUP`；stdout/stderr 接日志文件 | 关掉原窗口会把新服务一起带走；或输出静默丢掉 |

## 4. 施工骨架

详细步骤、接口字段、12 个实测坑与测试矩阵都在
[`skills/web-panel-restart/`](https://github.com/cqlql/cqlql-notes/tree/note/skills/web-panel-restart)。
下面只留施工顺序，避免站点读者在文档里找不到全局。

```text
1. 前置自检        四个前提（§1.3）；缺一个就停，写清「为什么不做」
2. 机制层           WaitPortFree / ReplaceBinary / NormalizeExePath / TargetExe
                    / Spawn / Rebuild / Check，全项目只有这一份实现
3. 三个接口 + 六道门  health / 确认视图 / 执行；校验、拒绝、闸门都在服务端
4. 接手进程         __restart（等端口→换二进制→起服务）+ __takeover（复用 port+token）
5. 前端             判定纯函数 + 确认弹窗 + 全局顶部工具栏 + 轮询 boot_id
6. 测试             自动用例 → 覆盖变量下真跑 → Windows 真机逐条打勾
7. 文档             把结论与红线写进 AGENTS，删掉「点了就会生效」的错误暗示
```

依赖只许单向：`main → ui → restart → shared`。`restart` 不反向 import `ui`；
接手入口放根包，就是为了不成环。非 Windows 明确报错，不假装能用。

## 5. 决策与备选

| 决策 | 备选 | 为什么选这个 |
| :--- | :--- | :--- |
| **修订母本 §8/§15，做自重建** | 继续「不做，手动 build」 | 当初的顾虑（失败无人看见）被 §2 三条硬约定解决；链路长的问题由自动勾重建 + 前端新鲜跳过 npm 解决。**前提不满足时仍不做** |
| detached 接手进程 | 退出码 75 + `.new` 换身 + 启动器循环 | 启动器是最脆的一层（批处理解析 / 代码页 / 隐藏窗口 pause），不该再塞一个换身状态机；`.cmd` 一行不改 |
| 复用 `ui.json` 的 token | 每次进程生成新 token | 前端 token 没落盘，换了就 401，成功会被误报成失败 |
| 令牌从 0600 文件读，不进命令行 | 当 argv 传给子进程 | 命令行参数在任务管理器里看得见 |
| 单例互斥体带重试 | 拿不到就判「已有实例」 | 关监听在 `exit` 之前，锁晚几毫秒释放；误判会只开浏览器、服务却没起来 |
| `boot_id` 作唯一判据 | 按「服务还在」/「请求成功」 | 交接失败时前者同样成立；后者在响应丢失时必然误报 |
| 传输层失败不算失败 | 任何异常都报失败 | 服务端先回 200 再退出，连接切断是预期形态 |
| 重建失败就地停 | 失败也重启 / 带旧二进制重启 | 后者会把「构建坏了」变成「服务没了」 |
| 备份类长任务在跑时 409 拒绝 | 只提示「会中断」 | 远端/数据库正在写，截断会留半状态 |
| 过期检测只有一份实现 | 重启一份、手工构建一份 | 两份会漂移成「重启说要重建、手工说不用」 |
| 自动勾「先重建」 | 默认勾 / 默认不勾 | 默认勾每次白等；默认不勾会用旧二进制起来 |
| 二次确认但**不输 `yes`** | 沿用远端写操作的 `yes` | 重启是本机动作；多一次输入只会让人更少用它 |
| `next.exe` + 旧进程退出后改名 | 直接 `build -o <tool>.exe` | 正在运行的 exe 被 Windows 锁着，覆盖只会拿到 sharing violation |
| 非 Windows 明确报错 | 用 POSIX detach 假装能用 | 没验证过的「看起来能用」比明确失败更坏 |
| 全局顶部工具栏 | 某个页面的头部 | 对服务本身的动作，与当前页无关；不随页面卸载，轮询不中断 |

### 7.1 已定稿、不再作为待确认项

- Windows 用 detached 接手进程，不用退出码 75 / 启动器循环。
- 非 Windows 明确报错，不做 POSIX 等价物。
- 界面重启不输 `yes`，但必须显式点击 + 二次确认 + 服务端确认令牌。

- 启动器（`.cmd` / `.lnk`）不改动。
- 重建过必须从 `next.exe` 拉起接手进程（2026-11-18 验证补充）。
