## 1. 问题与目标

### 1.1 真实痛点

给自己的笔记站（632 篇 md / 约 300 万字）做问答。关键词检索在这里会失效：
搜「rerank 为什么要对 top-20 做」搜不到，因为笔记里写的是「精排只处理粗排的前 N 条」——
**字面不重合，但语义相同**。向量召回是唯一能救回这一类的手段。

这不是 demo，是天天要用的东西，所以「能不能用」比「指标多好看」优先；
同时它是学习项目，所以「能不能讲清为什么」和「有没有可对比的数字」同样优先。

### 1.2 目标与非目标

量化目标（recall@5 ≥ 0.80、rerank 增益 ≥ +10pp、端到端 < 5s、50 条人工标注评估集）
与简历口径见 [`evaluation.md`](evaluation.md) §3 —— 🔴 那里是**待填模板，不是成果**。

| | 内容 |
| :--- | :--- |
| **要做** | 切分 → 向量化 → 召回 → rerank → 生成全链路；numpy 与 pgvector 双后端对比；检索层评测 + 生成层评测；把 `Retriever.search()` 包成 MCP Server |
| **不做** | Agent 编排（另开 PassUp Agent）；生产级 SLA / 多租户 / 权限；追 SOTA 指标；把实测数字写进本仓文档 |

> 一句话取舍：**宁可每个环节都留着可对比的笨版本，也不要一个说不清来路的「最优」实现。**

## 2. 总体架构

### 2.1 三条链路

```
【离线 · 建索引】
note/docs/  (632 篇 md，由 CORPUS_DIR 指定，只读)
   │  chunk_file()：去 front matter → 切分（baseline 固定长度 / 目标 标题感知）
   ▼
Chunk { id, text, source, heading }          ← 字段定义权威在 src/notes_rag/chunker.py
   │  Embedder(bge-m3)：float32、已 L2 归一化
   ▼
   ├── numpy 后端：vectors.npy + meta.jsonl + manifest.json
   └── pg    后端：chunks 表 + HNSW / IVFFlat 索引
                    ▲
                    └── 建索引 / 写入耗时在这里计时（对比实验的观测项）

【在线 · 问答】
query → Embedder → store.search(top_k)
      → [目标形态] 两段式：召回 top-20 → cross-encoder 精排 → top-5
      → generator.answer(max_hits=3，SYSTEM_PROMPT 约束「没找到就说没找到」)
      → 回答 + 可点回原文的来源编号

【旁路 · 评测】
queries.jsonl（50 条人工标注）→ evaluate.py → Retriever  ← 🔴 不经过生成层
      → recall@k / MRR / 检索 P95 → learning/实验台账.md
```

三条链路共享同一份索引与同一个 `Retriever`，**评测旁路刻意绕开生成层**：
这样才能把「召回没召回」与「模型有没有编」分开归因。代价是 recall@5 不能当答案正确率，见 §5.4。

### 2.2 阶段契约（架构视角）

| 阶段 | 输入 | 输出 | 可替换实现 |
| :--- | :--- | :--- | :--- |
| 切分 | 一篇 md | `Chunk[]`（`source` = 相对语料根的路径） | 固定长度 / 标题感知 / 语义切分 |
| 向量化 | 文本数组 | `(n, dim)` 归一化矩阵 | bge-m3 / 本地 Qwen embedding |
| 存储检索 | query 向量 | `[{score, text, source, heading, id}]` | numpy 暴力 / pgvector HNSW / IVFFlat / BM25 混合 |
| 重排 | 粗召回结果 | 精排后的 top-5 | cross-encoder / 无（baseline） |
| 生成 | hits + question | 带引用编号的回答 | 豆包 API / 本地 vLLM |

🔴 **`search()` 的返回形状是两种后端的共同契约**：`store.py` 与 `store_pg.py` 接口必须一致，
上层 `Retriever` / `evaluate.py` 才不用分叉。字段清单不在这里复制，权威见 `src/notes_rag/store.py`。

### 2.3 为什么双后端并列，而不是二选一

numpy 是**基准与对照组**，pgvector 是**被考察对象**。二者跑同一份评估集、同一套 score 口径
（numpy 归一化点积 ≡ pg 的 `1 - (embedding <=> vec)`），差异才归因得到「索引结构」而不是「数据不同」。
详细判据见 [`rag-pipeline.md`](rag-pipeline.md) §4。

## 3. 关键设计决策（含被否方案）

> **决策的唯一权威是本节**。改选型只改这里；`rag-pipeline.md` 只保留实现结论与判据，不复制本表。
> 面试要的答法是「我先用了什么，因为什么，什么情况下会换」，不是背结论。

| 选择 | 为什么 | 什么时候该换 |
| :--- | :--- | :--- |
| **两种后端都做**：numpy 暴力 vs pgvector | 不是二选一，是**对比实验**。numpy 五分钟跑通，当基准和对照组；pgvector 用来学 HNSW / IVFFlat，这是 JD 硬要求 | 生产环境按数据量选；学习场景两个都要 |
| **bge-m3** 本地 | 多语言、8192 上下文、数据不出网、免费；8G 显存 fp16 够跑 | 需要多模态，或显存不够 |
| **bge-reranker-v2-m3** | cross-encoder 比向量准，但必须实时算，所以只对 top-20 做 | 延迟预算更紧时换更小的 reranker |
| **切分按标题层级 + 长度兜底** | 笔记天然带 `##` 层级，按标题切语义完整；超长再按长度切 | 语料换成没有结构的（PDF / 聊天记录） |
| **豆包 API** 生成 | 便宜、快、已开通；本地 vLLM 作为备选 | 数据敏感或成本敏感时切本地 |

### 3.1 被否方案与为什么否

| 被否方案 | 为什么否 | 什么条件下重新考虑 |
| :--- | :--- | :--- |
| 只用 numpy，不上向量库 | 这是**工程结论**：6000 块 × 1024 维 ≈ 24MB，CPU 毫秒级；但没做过 pgvector 就答不出「HNSW 和 IVFFlat 怎么选」，而这是 JD 的硬要求 | 纯生产场景，且块数超过 10 万时按数据量选 |
| 全库跑 cross-encoder 精排 | cross-encoder 要把 query 与每个 doc 拼成一个输入过模型，6000 块是 O(n) 次推理、几十秒，在线不可接受 | 语料缩到几百块，或改成离线批处理 |
| 纯 BM25 / 关键词检索 | 痛点恰恰是字面不重合（「rerank 为什么对 top-20 做」vs「精排只处理粗排前 N 条」） | 作为**混合检索的一路补充**，不是替代向量 |
| 把整个文件当一个 section 切 | baseline 实测的两个毛病：代码块 / 表格被拦腰切、末尾产生十几字碎片块 | 语料没有结构时退回长度切分 + 长度兜底 |
| 给 bge-m3 加 query instruction | 那是 `bge-large-zh-v1.5` 的用法；bge-m3 不需要，加错了会掉点 | 换模型时先读模型卡再决定，不照搬网上的写法 |
| 拿 `recall@5` 当「答案正确率」 | 评测旁路不经过生成层，回答对不对、有没有编、该拒答拒没拒都不知道 | 补上生成层评测（§5.4）之后 |
| 为 RAG 顺手做 Agent 编排 | Agent 是另一条能力线，塞进来两边都讲不深 | 不重新考虑：另开 PassUp Agent |

> 决策维护方式：新增「被否方案」直接补进上表；实测结论记进 `learning/实验台账.md`，
> 别另开一份「决策记录」文档 —— 单开一份必然烂尾。

### 3.2 工程结论 ≠ 学习结论

「数据量小不需要向量库」是**工程结论**，不是**学习结论**。
生产上它是对的；但在学习场景里，没亲手建过 HNSW / IVFFlat，就只能背「一个快一个省内存」，
答不出「建索引耗时差多少、ef_search 调大付出什么代价」。
**两个都做，才有对比数据** —— 这是整个项目最核心的一条设计取舍。

## 4. 数据与契约

| 契约 | 唯一权威 | 方案层面的约束 |
| :--- | :--- | :--- |
| `Chunk` 字段 | `src/notes_rag/chunker.py` 的 dataclass | `source` 必须是相对 `CORPUS_DIR` 的 posix 路径 |
| 评估集 schema / 命中判定 | `scripts/evaluate.py` 模块 docstring | 命中 = 返回结果的 `source` 落在 `expected` 里 |
| 检索返回形状 | `src/notes_rag/store.py` 的 `search()` | 两种后端同接口，见 §2.2 |
| 相似度口径 | `store.py` / `store_pg.py` | 向量已归一化 → 点积即余弦；pg 用 `1 - 距离`，两边必须一致 |
| 索引构建参数 | `data/index/manifest.json`（numpy 侧） | 参数从 `.env` 读，让「跑过什么参数」在 git 历史里说得清 |

**为什么 `source` 用相对路径而不是文件 ID / 数据库主键**：
评估集是人工按笔记路径标注的，索引可以从 numpy 换到 pg、切分可以重跑，
只要路径不变，同一份 `queries.jsonl` 就一直有效。改它的格式会让整份评估集静默失效。

> 🔴 本仓 `docs/` 是项目文档；`CORPUS_DIR` 指向的是 `note/docs/`。两个 `docs/` 别混。

## 5. 评测方案

### 5.1 三层指标

| 层 | 指标 | 现状 |
| :--- | :--- | :--- |
| 检索质量 | `recall@k`、`MRR` | ✅ 已实现（`evaluate.py`） |
| 系统性能 | 建索引 / 写入耗时、查询 P95、端到端响应 | ✅ 已实现（含冷启动分段的耗时打印） |
| 生成质量 | 正确性、幻觉、该拒答时拒答 | ☐ **待补**，见 §5.4 |

口径定义与边界见 [`evaluation.md`](evaluation.md) §2，🔴 这里不复制公式。

### 5.2 评估集设计

50 条人工标注，`query` **按「你会怎么问」写，不按文档标题写** —— 后者会让数字虚高；
`expected` 是相对语料根的路径，一个问题在多个文件都有答案就写多个。
`queries.example.jsonl` 里两条是占位示例，标之前先删。

这 1 小时是后面所有优化对比的前提：**先标评估集 → 量 baseline → 改一处 → 再量**。

### 5.3 对照实验矩阵

把「每次只改一处」落到具体矩阵。每张表的**固定项列是硬约束**，不是建议。

| 实验 | 唯一变量 | 固定项 | 观测指标 | 卡片 |
| :--- | :--- | :--- | :--- | :--- |
| 切分粒度 256 / 512 / 1024 | `CHUNK_SIZE` | 同一份 queries、同后端、同语料 | 块数、平均块长、recall@5 | `learning/cards/01-rag/02-切分策略.md` |
| 固定长度 vs 标题感知切分 | `chunker.py` 策略 | 同上 | recall@5、碎片块数 | 同上 |
| numpy vs pg HNSW vs pg IVFFlat | 后端 / 索引类型 | 同一份 queries、同一切分 | 建索引耗时、查询 P95、recall@5 | `learning/cards/01-rag/04-向量检索.md` |
| `hnsw.ef_search` 40 / 100 / 200 | 查询期参数 | HNSW、同一切分、同一份 queries | recall@5、查询 P95 | 同上 |
| 纯向量 vs 向量 + rerank | `retriever.py` | 同一份 queries、同后端 | recall@5、端到端延迟 | `learning/cards/01-rag/06-Rerank.md` |
| 豆包 vs 本地 vLLM（Qwen） | 生成模型 | 同一批检索结果 | 准确率 / 成本 / 延迟 | `learning/能力清单.md` |

命令与四条对照纪律见 [`evaluation.md`](evaluation.md) §4；
切分或换模型后必须重建两个后端的索引，见 [`rag-pipeline.md`](rag-pipeline.md) §4、§5。

### 5.4 生成层评测（待补）

来源：`learning/能力清单.md` 的覆盖矩阵与时间账。
设计：**同一批 query**，用 LLM-as-judge 判「回答是否正确 / 有没有编 / 该拒答时是否拒答」，
抽样子集人工复核，报 **judge 与人工的一致率**。
它是「评测体系」这项 JD 要求的另一半，也是 `SYSTEM_PROMPT` 里那条拒答约束唯一的验证方式。

🔴 在它落地之前，不许把 `recall@5` 说成答案正确率，也不许在简历里写「评测体系已覆盖」。
JD 覆盖与排期见 [`roadmap.md`](roadmap.md) §1、§2。

### 5.5 数字从哪来

所有实测数字唯一落点是 `learning/实验台账.md`；召回失败案例按「切分切断 / 表述差异 / 关键词漏召」
归类记在同一处。本仓文档只放指针，不复述数字 —— 简历上每个数字都要能在台账里找到「怎么来的」。

## 7. 风险与边界

| 风险 | 表现 | 对策 |
| :--- | :--- | :--- |
| 索引陈旧 | 改了切分 / 参数 / 模型却量到旧数据，且 `cli.py` 只在 numpy 后端比 `chunk_size` 告警 | 任何影响向量的改动都重跑 `ingest.py`（两个后端），见 `rag-pipeline.md` §4 |
| 换模型维度变化 | pg 的 `vector(dim)` 表结构不匹配 | 整表重建；🔴 `store_pg.reset()` 是 `DROP TABLE`，`DATABASE_URL` 只许指向本地 5433 实验库 |
| 评估集标注偏差 | query 照着文档标题写 → recall 虚高，优化方向被带偏 | 按「你会怎么问」标；同批 query 贯穿所有实验 |
| 冷启动混入延迟 | 模型初始化耗时被算进检索 P95 | `cli.py` 分段打印「加载 / 检索 / 生成」，只看检索段 |
| 切分破坏结构 | 表格 / 代码块被拦腰切，末尾产生碎片块 | 标题感知 + 长度兜底；碎片是否丢弃用前后数字决定，别凭感觉 |
| 把检索指标当端到端结论 | 只报 recall@5，被追问「答案编没编」答不上 | §5.4 落地前明确说「生成层评测待补」 |
| 能力范围蔓延 | 把 Agent 编排塞进本项目 | 不做，见 §1.2；另开 PassUp Agent |

## 8. 怎么讲这个项目

**一句话**：给 632 篇个人笔记做语义问答，标题感知切分 + bge-m3 召回 + rerank 精排，
用 50 条人工标注评估集做改前 / 改后对比，并把 numpy 与 pgvector 的索引代价量出来。

三个必答问题（答案骨架，细节在上面的对应章节）：

1. **「为什么两种后端都做？」** → 工程结论 ≠ 学习结论（§3.2），要的是 HNSW / IVFFlat 的对比数据，不是「不需要」这句话。
2. **「为什么两段式召回？」** → bi-encoder 快但粗、cross-encoder 准但 O(n) 推理（§3.1），所以只对 top-20 精排。
3. **「怎么证明改完变好了？」** → 先标评估集、每次只改一处、固定项不动（§5.3）、数字进台账（§5.5）。

- 数字溯源：`learning/实验台账.md`；简历那行是**待填模板**（`evaluation.md` §3），`x` 不是实测值。
- 按 JD 逐条自检「我拿什么证明」：`learning/能力清单.md`。
- 🔴 别背结论。**「我先用了什么、因为什么、什么情况下会换」** 才是这个项目要练的答法。
