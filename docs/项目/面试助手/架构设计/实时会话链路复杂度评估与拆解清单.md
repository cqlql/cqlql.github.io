## 1. 结论

1. **复杂度是真的，但不是「写坏了」，而是「新能力持续落在同两个类上」。**
   领域事件解耦时 `AudioStreamSession` 约 730 行，现在是 **812 行** —— 拆过一次又长回来了。
   暂停恢复、独立心跳、ASR 自愈、错误归一这些后续能力，全都默认落在它身上。
2. **「容易出错」的准确口径**：单点改动有测试兜着（本模块约 62 个用例），
   **长尾组合场景没有防线**（暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出 + 顶号并发）。
3. **病根不是行数**，而是三类可复现的东西：职责叠加、隐式不变量、跨模块隐式耦合。
4. **处方**：先补测试接缝（P0-0）→ 三次抽取（ASR 运行期 / 回合编排 / 连接判据接口）→ ID 语义区分 →
   cleanup 收敛与不变量结构化。全部是行为等价的机械重构，不新增能力。
   **V2 的 `input=text` 与 `/ws/asr` 应该在这些之后加**（见 §7）。
   > **测试不是最后一步，而是第一步**：P0-0 是 P0-1 / P0-2 的前置条件（§4.5 的三个盲区正好是要动的块）。
5. **完成标准不是"行数下降"**，而是**变化边界**：`AudioStreamSession` 不再认识 ASR 运行机制、
   LLM 客户端与上下文裁剪；且满足 §8 的四条约束（新增输入源不改 runner、新增通道不复制 runner、
   新增回合输入不复制 turn runner、新增退出路径只能进统一 cleanup）。

## 3. 职责清单：这两个类现在到底在干什么

### 3.1 `AudioStreamSession`（10 个角色）

WebSocket 持有者（含发送队列 + `sendLoop`）｜ASR 运行器（`consumeLoop`、重连退避、`pumpAudio`、残留帧丢弃、`lastAsrId` 轮换、`asrUnavailable`）｜上行协议适配（binary / text / heartbeat / PAUSE）｜**回合编排**（`triggerLlmReply`、`triggerInitialQuestion`）｜对话上下文管理（`context`、`trimContext`、`buildMessages`、`MAX_CONTEXT`）｜落库协调（`conversationService`）｜领域事件发布（Started / Paused / Resumed / Ended）｜连接存活状态（两套时间戳 + `heartbeatCapable` + `isAlive`）｜暂停与结束语义（`paused`、`markPaused`、`onClose` 分支）｜ASR 消息 id 轮换与去重语义

### 3.2 `AudioStreamingService`（8 个角色）

握手准备与失败回滚｜两张注册表的所有者（`streamSessions` / `logicalSessions`）｜恢复与跨进程重建协调｜心跳扫描与踢出｜三种回收（暂停 / 悬挂 / pending）｜**连接存活的唯一判据来源**｜顶号与强制关闭｜主动 / 被动关闭的仲裁

> 这不是"作者没拆"，而是**新能力没有落脚点**：加一个"文字作答"要动它、加一个"识别通道"也要动它。
> 上一轮讨论 V2 时"专门写一套会不会更好"的直觉，正是被这个类逼出来的（结论见 V2 方案 §10.2：新写一套更贵）。

## 4. 真正的病根

### 4.1 隐式不变量只能靠注释维持

编译器管不了、只能靠人记住的规则：

| # | 不变量 | 出处 | 忘了会怎样 |
| :--- | :--- | :--- | :--- |
| 1 | 构造器有副作用（`markActive` + `bindConnection` + 起 2 个线程 + 发事件），失败必须**调用方手工回滚** | `AudioStreamingService#onOpen` 的 `catch (RuntimeException)` 里手工 `resumeState.markPaused()` / `endInterview()` | 留下"无物理连接的 ACTIVE"僵尸，两条回收路径都扫不到（历史上真实发生过，见前一篇 P0.1） |
| 2 | 顶号时**只请求关闭，不能抢先摘注册表** | `onOpen` 内注释 | 心跳扫描再也扫不到该连接，逻辑会话永久残留 |
| 3 | `streamSessions.remove()` 的返回值同时承担「移除」与「幂等守卫」 | 前一篇 §4 原则一 | "移除"与"清理"变成两件事，静默出错 |
| 4 | ASR 重连前必须 `dropStaleAudio()` + 轮换 `lastAsrId` | `consumeLoop` | 旧帧喂给新连接（过期转写）、新旧句子在前端串成一条 |
| 5 | 不要无脑 `forceClose()` | `DoubaoAsrClient` 注释 | `abort` + `shutdownNow` 以异常回调，日志出现误导性故障栈 |
| 6 | 计费起算必须由 `startedPublished` 守卫 | `onAsrReady` | 重连重复 `startBilling`，**覆盖起算点、已用时长归零** |
| 7 | ASR 故障必须走 `onAsrSessionError` 而非 `onAsrSessionEnd` | `consumeLoop` finally + `asrUnavailable` | 结束原因误记为 `USER_ENDED`，统计与客诉都失真 |

前一篇（心跳与暂停恢复）已经修过一批同类问题，但**新写法仍在重复同一模式**：
横向关注点默认寄生在业务回调里 —— 这次 V2 要拆的 ASR→LLM 耦合，就是它的第二次发作。

### 4.2 跨模块的隐式耦合：谁在依赖注册表

4 处「按物理连接定位会话」的调用点直接依赖 `AudioStreamingService` 的 `streamSessions`：

```java
// InterviewBillingScheduler#validateSessionState（每 10 秒跑一次）
String activeConnectionId = streamingService.resolveActiveConnectionId(sessionId);
if (activeConnectionId == null || !streamingService.hasActiveStreamSession(activeConnectionId)) {
    billingService.stopBilling(userId, sessionId);   // ← 找不到就视为孤儿，停计费
    return false;
}
```

| 调用点 | 依赖 | 漏改后果 |
| :--- | :--- | :--- |
| `InterviewBillingScheduler#validateSessionState` | `isConnectionLost` / `resolveActiveConnectionId` / `hasActiveStreamSession` | 新链路的会话若不在注册表里 → **静默停止扣费**，`TIME_UPDATE` 停发 |
| `InterviewBillingScheduler#terminateSession` | 同上 + `forceCloseSession` | 余额耗尽时关不掉会话 |
| `WsHeartbeatScheduler` → `evictDeadSessions` | 只遍历 `streamSessions` | 死连接不回收 |
| `AudioStreamingService#onOpen`（顶号） | `forceTerminateActiveSession` → `resolveActiveConnectionId` → `streamSessions.get` | 顶号失效，同用户两条会话并行计费 |

这就是 V2「识别通道」方案里建议**不碰注册表**的原因，也是 §6 P0-3 要接口化的动机。

### 4.3 命名与语义漂移

| 漂移 | 具体表现 | 危害 |
| :--- | :--- | :--- |
| 两个 `sessionId` | `InterviewContext#sessionId` 是**物理连接 ID**，`InterviewSessionState#sessionId` 是**逻辑会话 ID**，后者靠 `getLogicalSessionId()` 别名纠偏 | `InterviewAsyncService#runSafely` 的告警日志打的是 `context.getSessionId()`（物理 ID），排查时极易看错 |
| `stopBilling` 参数名与注释不符 | 形参 `currentSessionId`，javadoc 写"当前正在关闭的 **WebSocket 会话 ID**"；但三处调用方全部传**逻辑会话 ID**，内部也是拿它比 `sessionInfo.getSessionId()`（`startBilling` 用逻辑 ID 写入） | 按注释传物理连接 ID，会静默走"跳过清理"分支 → **计费不结算、Redis key 残留** |
| `Audio*` 前缀 | `AudioStreamSession` / `AudioWebSocketHandler` 现在还要承载文本（V2 之后更明显） | 误导阅读者以为只处理音频 |
| 文档与代码相反 | `AGENTS.md` §6.5.4 末尾称 `PausedMessage` 经 `sendQueue` 异步入队"若需强一致可改为同步发送"，代码早已是 `sendMessageNow`；§8.6 把"补实时会话单测"列为待做，实际已有约 62 个用例 | 下一个人按文档改代码 |
| 错误码两端未登记 | 后端下发 `ASR_UNAVAILABLE` + 关闭码 4003，PC 的 `protocol.ts` 与小程序 `ws.ts` 白名单里**都没有这个码** | PC 端把消息整条丢弃（用户看不到原因），小程序兜底归为 `BILLING_ERROR` |

### 4.4 已定原则与代码结构的落差

前一篇 §4 定了三条原则，其中**原则一（任何物理连接退出路径最终都必须进入统一 cleanup）在结构上还没收敛**：

> **状态**：这条已在 **P1-1** 收敛（连接退出的「通知/关闭」与「收尾」各成一个入口，见 §6 P1-1 进度）。
> 下面保留问题描述作为改造动机；未进 `cleanup` 的两条逻辑终结路径（暂停超时 / DB 兜底）见 P1-1 说明。

- **触发收尾的入口有 7 处**：Spring `afterConnectionClosed`（间接承接 `handleAsrSessionEnd` / `handleAsrSessionError` /
  `handlePauseRequested` / `handleTransportError` / `forceCloseSession` 五个主动 `close()` 路径）
  \+ 心跳踢出 `evictDeadSessions` 里**自己拼的**「发 ERROR → `onError` → 虚拟线程 sleep 1500ms → `onClose`」。
  后者的时序（发错误通知 + 宽限 1.5 秒）是心跳踢出独有的，与其他路径不一致。
- **「发结束事件」没有单一入口**：`AudioStreamSession#onClose` 发 `InterviewEndedEvent`；
  `evictExpiredPausedSessions` 自己 `logicalSessions.remove()` + 发事件；
  `evictExpiredPausedInterviews`（DB 兜底）**刻意不发事件**（有理由，但正是"每个路径各自决定"的体现）。
- **登记与移除不对称**：逻辑会话登记有 3 个分支（新会话/重建态/不登记），移除有 2 处，各有条件。

结论：原则写在文档里，代码里仍是"每条退出路径各自拼一遍收尾"。新增输入源或新端点时，这里最容易漏。

### 4.5 测试覆盖的不对称（最需要正视的一点）

本模块测试其实是全仓最厚的：`AudioStreamingServiceTest`（32 个用例）、`LogicalSessionRebuilderTest`（14）、
`AudioStreamSessionHeartbeatTest`（6）、`AudioStreamingWebSocketIntegrationTest`（6）、`RealtimePropertiesTest`（4），合计约 62 个。

但盲区恰好落在**最常改、最该动**的地方：

| 块 | 覆盖 |
| :--- | :--- |
| 注册表 / 恢复 / 心跳判据 / 暂停回收 | ✅ 覆盖较好 |
| **ASR 消费循环与重连预算** | ❌ 无（依赖豆包客户端） |
| **回合流水线（LLM 交互、上下文裁剪、落库顺序）** | ❌ 无 |
| **计费调度器的三条判据** | ❌ 无 |

→ 含义：§6 的 P0-1 / P0-2 正好落进盲区，**所以 P0-0（测试接缝与行为基线）是它们的前置条件** ——
先给 `DoubaoAsrClient` 与 LLM 客户端做注入点 + fake，把两组不变量测试按**现状**跑绿，再开始抽取；
否则拆完只是"看起来没坏"。

## 6. 拆解清单

原则：**每项都是行为等价的机械重构，独立提交、独立可回滚、不夹带新功能。**

> **完成定义（每项都适用）：代码抽取完成 + 行为基线测试通过 + 原链路集成测试通过。**
> 没有测试就不算完成 —— 机械抽取不等于低风险：`ASR 回调 → 会话状态 → 回合 → 计费 → WebSocket 推送`
> 之间存在**隐式时序**，只有测试能证明它没变。

### P0-0 测试接缝与行为基线（先做，是 P0-1 / P0-2 的前置条件）

> **进度：已落地（2026-09-22）。** 注入点用两个工厂接口实现（`AsrClientFactory` / `LlmClientFactory`，
> 默认走豆包实现，放在 `AudioStreamSessionDependencies` 上），测试脚手架为
> `AudioStreamSessionTestHarness`，两组基线共 7 个用例（`AudioStreamSessionAsrBaselineTest` 3 个、
> `AudioStreamSessionTurnBaselineTest` 4 个）。
>
> **验证结果：71 个测试全绿** = realtime 单元测试 63（含新增 7）+ WebSocket 端到端集成 5 + 计费集成 3。
> 端到端集成测试需要本地存在 `pass_up_test` 库（`application-test.yml` 指向它；库不存在会以
> 「上下文加载失败」的形式报错，表现为 5 个 Error，与本类改动无关）：
> `docker exec postgres psql -U postgres -c "CREATE DATABASE pass_up_test ENCODING 'UTF8' TEMPLATE template0"`。

不是"补覆盖率"，而是**先把现状钉住**：

1. **注入点**：`DoubaoAsrClient`（工厂或接口）、LLM 客户端（现在每轮 `new DoubaoLlmClient`，加一个 `LlmClientFactory` 即可 fake）。
2. **不变量测试**（两组，分别对应 P0-1 / P0-2 的抽取对象）：

   ```text
   ASR     ready × reconnect → startBilling 只能一次
           reconnect         → 残留音频 = 0
           new ASR           → asrId != 旧 asrId

   回合     final text → 恰好一轮 LLM
           非 final   → 零轮
           空 final   → 零轮
   ```

3. 这两组测试**先在现有实现上跑绿**（即把现状钉住），再开始抽取。

> **cleanup 的基线不在这一步**：它对应 P1-1 的收敛对象，放在 P1-1 一起做（见该节「行为基线」）。
> 这样划分是为了让"测试接缝"只服务于它真正要保护的那两次抽取，不提前把 P1 的对象拉进来。

### P0-1 抽 `AsrStreamRunner`：ASR Runtime

> **进度：已落地（2026-09-22）。** 产出 `AsrStreamRunner` + `AsrEvent`（sealed：`Ready` / `Transcript` / `Ended` / `Unavailable`）
> + `AsrEventHandler`；会话侧改为 `onAsrEvent(...)` 消费事件，`stop()` 由 `markPaused()` / `onClose()` 显式调用
> （不再让运行期去读会话的 paused / WebSocket 状态）。
> **判据已核验**：会话里不再出现重连 / 退避 / `asrId` / 残留帧（812 → 676 行）；
> 验收 = P0-0 的 7 个基线 + 64 个既有单元/集成测试，共 **71 个全绿**。

- **职责一句话**：从「收到音频字节」到「产出 ASR 事件」，含连接重建。
- **对外只有三个动作 + 一个事件入口**：

  ```java
  interface AsrEventHandler { void onEvent(AsrEvent event); }
  // AsrReady / AsrFinalText / AsrSessionEnded / AsrSessionError

  class AsrStreamRunner {
      void start();
      void submitAudio(byte[] chunk);
      void stop();
  }
  ```

  > **修订**（原方案留了 `onReady` / `onText` / `onEnd` / `onError` 四个回调）：**统一成一个事件入口**。
  > 四个回调在第二个使用点（`/ws/asr`）就会立刻分叉 —— 换 API 比换一个 handler 实现贵得多。

### P1-1 关闭路径收敛：`cleanup(reason)` 的边界

> **进度：已落地（2026-09-22）。** 落法不是"抽一个新类"，而是**把收尾抽成两个函数**：
>
> | 入口 | 职责 | 调用方 |
> | :--- | :--- | :--- |
> | `cleanup(session, reason)` | **唯一收尾入口（幂等）**：摘除物理连接（幂等的锚点）→ `AudioStreamSession#onClose()` → 已结束则摘除逻辑会话 | Spring 关闭回调；心跳踢出 / 主动关闭后的兜底 |
> | `requestClose(session, reason, status, notice)` | **唯一退出出口**：按需同步发通知 → 关闭传输层。**不做收尾**（收尾统一走回调） | 7 条路径全部改调它 |
>
> 7 条路径改写后各自只剩一行：顶号 / 传输层错误 / 计费终止 / 心跳踢出 / ASR 自然结束 / ASR 不可用 / 用户暂停。
> 新退出路径只需给出 `CleanupReason` + 关闭码 +（可选）通知。新增 `CleanupReason`（`lifecycle` 包），
> **与 `InterviewEndReason` 刻意分开**：连接退出 ≠ 面试结束（暂停、顶号、心跳踢出都只退出连接）。
>
> **幂等的锚点是「注册表摘除成功者唯一」**：`cleanup` 里 `removeConnection` 返回 `null` 即直接返回，
> 于是 `session.onClose()` 至多执行一次 → `InterviewEndedEvent` 至多一条 → 停计费至多一次（§10 第 8 条）。
> 心跳踢出的「兜底补一刀」因此天然安全，不必再自己防重。
>
> **刻意保持现状项（累计，都已写进代码注释）**：
> 1. 心跳踢出的宽限期仍是「先关连接、等 1.5 秒再兜底收尾」—— 于是"给前端留时间把残存数据发完"这个初衷
>    其实没落到实处（连接那时已经关了）。改成「先等宽限、再关闭」是行为变更，需单独决策。
> 2. 通知的发送方式按路径区分：ASR 不可用走**同步写**（保证"先收到原因、再收到关闭帧"，与握手错误一致）；
>    心跳踢出走**会话发送队列**（扫描线程与发送线程并发写同一 socket 会交错）。
> 3. **结束原因的映射口径**（P1-2）：现在只有 ASR 故障记 `ASR_ERROR`，心跳超时 / 计费终止 / 顶号都记 `USER_ENDED`。
>    有了 `CleanupReason` 之后，把 `BILLING_TERMINATED` → 更准确的结束原因（余额耗尽/计费异常）在代码上是
>    一行的事，但它会**改变已落库的统计口径**，要与产品确认后再动。
>
> **测试（§10 第 8 条基线落地）**：
> - `cleanup`：重复调用只收尾一次；逻辑会话未结束 → **保留**（暂停可重连）、已结束 → 摘除；未知连接静默跳过。
> - 心跳踢出 3 个用例：失联 → 通知（走队列）+ 请求关闭 + 宽限后兜底收尾（用 Mockito `timeout(3000)` 等异步结果）；
>   存活不踢；已标记踢出不重复踢。**这条路径冒烟脚本覆盖不到**（脚本一直发心跳、永远不会被判失联），只能靠单测锁住。
> - 合计 **89 个**用例全绿（82 → 89），真实端到端冒烟仍 **11/11**（本次主代码改动后未复跑的必要性见 §10）。
>
> **本阶段只收敛「物理连接退出」**：`evictExpiredPausedSessions`（暂停超时 → 终结逻辑会话）与
> `evictExpiredPausedInterviews`（DB 兜底）**刻意不进 `cleanup`** —— 它们没有物理连接要收，
> 属于"面试为什么结束"的判定（各有其既有理由，见 §4.4）。
> 这正是上面那句"定义收窄"的含义：`cleanup` 不被拉成万能方法。
>
> 定义收窄为：**物理连接退出的唯一收尾入口**，而**不是**"所有会话结束都要调它"。

```text
7 个物理连接退出入口
        ↓
cleanup(connection, reason)     ← 连接资源收敛 + 注册表移除（幂等）
        ↓
   逻辑会话是否结束？
     ├─ 否 → pause（保留 TTL 待重连）
     └─ 是 → ended（发 Ended 事件）
```

- `cleanup` **不做**"面试是否结束"的判断 —— 那是逻辑生命周期（pause / resume / end）的事。
  两者一旦混在一起，`cleanup` 就会变成万能方法，把"连接关闭"和"面试结束"再次搅在一起。
- 心跳踢出的"发错误 + 宽限期"变成 cleanup 的参数（如 `gracefulNotice(code, message, graceMillis)`），
  而不是每条退出路径各写一遍 —— 这正是 §4.4 里 7 个入口时序不一致的根因。
- **验收**：前一篇原则一在结构上成立；新增一条退出路径不再复制收尾代码。
- **行为基线（本阶段落地为测试）**：

  ```text
  cleanup() × N    → remove 只一次
                   → Ended 事件只一次
                   → 停计费只一次

  非当前连接的事件  → 不影响活跃连接与逻辑会话（见 P1-3 的"迟到事件"场景）
  ```

  > 这组基线归 P1-1 而不归 P0-0：P0-0 只保护 P0-1 / P0-2 那两次抽取，
  > 而 cleanup 是本阶段才收敛的对象，测试与重构同批交付更清晰。

### P1-2 生命周期不变量结构化

> **进度：已落地（2026-09-22）。** 四项逐条：
>
> | 项 | 落地 |
> | :--- | :--- |
> | ① 构造器无副作用 | `new AudioStreamSession(...)` 只赋字段 + 建两个 runner；不再 `markActive` / `bindConnection` / `submit(sendLoop)` / `asrRunner.start()` / `publishResumed()` |
> | ② `start()` 是启动事务边界 | `start()`：重连 → `markActive` + `bindConnection` → `submit(sendLoop)` → `asrRunner.start()` → `publishResumed()`；任一步失败 → `rollbackStart()` → 继续抛 |
> | ③ 退出原因统一 | 删掉 `asrUnavailable` 布尔，改为会话上的 `exitReason`（`CleanupReason`）：`requestClose` 时记录、收尾时由 `onClose(reason)` 消费 |
> | ④ 两类原因不混用 | `CleanupReason`（连接为什么退出）经 `toEndReason(reason)` **唯一一次**映射为 `InterviewEndReason`（面试为什么结束） |
>
> **③ 的关键点**：退出原因必须在**请求关闭时**记到会话上。因为收尾走的是容器关闭回调，
> 回调只带"连接断了"（`CONNECTION_CLOSED`），真实原因（ASR 故障 / 暂停 / 顶号 / 计费终止）会丢 ——
> 原先那个 `asrUnavailable` 布尔正是为了跨过这次回调。现在换成通用的 `exitReason`，**任何**退出路径都能带上原因。
>
> **③ 与 ④ 的口径冲突（已按 ④ 处理）**：任务描述里"`InterviewEndReason` 扩展为 `CleanupReason`"与
> "两类原因不混用"互相矛盾。落地为**两个枚举都保留**：`CleanupReason` 是入参（连接维度），
> `InterviewEndReason` 是出参（面试维度），中间只在一处映射。
> 映射现状**刻意不变**：只有 ASR 故障记 `ASR_ERROR`，心跳超时 / 计费终止 / 顶号仍记 `USER_ENDED`
> （改它会动到已落库的统计口径）—— 见待确认项。
>
> **回滚责任转移**：`rollbackStart()` 就地把逻辑会话恢复成"未启动"的样子（重连 → PAUSED 并解绑连接；
> 新会话 → 标记 ENDED），因为不这么做就会留下「无物理连接的 ACTIVE」僵尸（心跳扫描扫不到、暂停回收又不认它）。
> `AudioStreamingService` 因此不再手工 `resumeState.markPaused()`，只保留新会话失败时的 `endInterview`（DB 不归会话管）。
> 另外**「面试开始」事件仍在 ASR 就绪时发**（`handleAsrReady`），本次没动 —— 计费起算点必须与"识别真的可用"对齐。
>
> **测试**：
> - 新增 `AudioStreamSessionLifecycleTest`（4 个用例，真实会话 + fake ASR）：构造不启动 ASR / 不发事件；
>   `start()` 启动 ASR；重连成功迁 ACTIVE + 绑定新连接 + 恢复事件只发一次；
>   **重连中途失败就地回滚为 PAUSED 且解绑连接**。
> - `AudioStreamingServiceTest`：原「重连失败退回 PAUSED」用例改为断言服务侧剩余责任（不登记连接、不结束 DB 记录）；
>   新增「新会话启动失败 → 结束 DB 记录」。
> - 合计 **94 个**用例全绿（89 → 94），真实端到端冒烟 **11/11**。
>
> **顺带修掉一个长期假绿的集成测试用例（值得记一笔）**：`AudioStreamingWebSocketIntegrationTest` 的
> SessionFactory 桩挂在**三参**重载上，而服务调用的是**四参**重载 → 服务拿到 `null` 会话 →
> `onOpen` 里 NPE → 连接被 1011 关掉。于是「相同用户重复连接时后续连接被拒绝」这条用例把
> "任何关闭"当成了"被拒绝"而假绿，那 5 个用例其实都没走到建连/收尾逻辑。

> 四个点属于同一件事（"生命周期状态只能由一处写，且写的时候是原子的"），因此**是一个任务，不拆成四个**：

1. **构造器无副作用**：`new AudioStreamSession(...)` 只创建对象 —— 不 `markActive`、不绑连接、不起线程、不发事件。
2. **`start()` 是启动事务边界**：markActive → bindConnection → start runner → publish started，
   任一步失败就地回滚（不再让 `AudioStreamingService` 手工补偿 —— 那正是 §4.1 第 1 条不变量的来源）。
3. **退出原因统一**：`InterviewEndReason` 扩展为 `CleanupReason`，替代布尔 + 多处 if 判断。
4. **两类原因的边界写清**：`CleanupReason`（连接为什么退出：用户断开 / 心跳超时 / ASR 故障 / 计费终止 / 暂停）
   与 `InterviewEndReason`（面试为什么结束：用户结束 / 暂停超时 / 余额耗尽）**不混用** ——
   连接退出 ≠ 面试结束（见 P1-1 的时序图）。

### P1-3 组合场景测试（长尾）

> **进度：已落地（2026-09-22），并且这一步抓到了真 bug。**
>
> 场景 2（旧连接迟到事件）**不是"补个测试就好"** —— 写出来立刻暴露出：
> `AudioStreamSession#onClose` 对**共享的逻辑会话**是无条件写状态的，于是
> 「A 掉线（无 PAUSE）→ 客户端带 resume 重连成 B → A 的收尾才到达」这条时序下，
> A 的收尾会把 B 正在进行的面试**结束掉**：状态标记 `ENDED` → 发 `InterviewEndedEvent`
> （→ 停计费 + 结束面试记录），上层随后还把逻辑会话摘出注册表 ——
> 计费扫描从此找不到它，表现为**"面试还在跑、时长却不扣了"**。这是既有 bug，与本次重构无关。
>
> **防护（已落地）**：`onClose(reason)` 先 `releaseResources()`（只收敛本连接资源），然后两道早退：
> 1. 逻辑会话已 `ENDED` → 直接返回（不重复发结束事件，§10.8 的第二道防线）；
> 2. `state.getCurrentConnectionId()` 非空且 ≠ 本连接 → **迟到收尾**，只清自己的资源，绝不碰逻辑会话。
>    （暂停态 `currentConnectionId` 为 `null`，因此正常暂停收尾不会被误判成迟到 ✓ 冒烟已实测。）
>
> **测试**（新增 `AudioStreamSessionLongTailTest`，真实会话 + fake ASR）：
> - `重复收尾_Ended事件只发一次`：端点重复回调 / 兜底补刀也不能重复发事件（否则重复停计费、重复结束记录）；
> - `迟到收尾_已被新连接接替_不影响逻辑会话`：不得结束面试、不得改暂停、不得解绑新连接、不得发结束事件；
> - `暂停收尾_保留逻辑会话并发暂停事件`：暂停的正例（反向保证第 2 条不会误伤暂停路径）。
>
> 合计 **97 个**用例全绿（94 → 97），真实端到端冒烟 **11/11**。
>
> **尚未覆盖（留作后续）**：
> - 场景 1 的"真并发"（暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出同刻发生）目前只覆盖了**确定性交错**
>   （迟到收尾 / 重复收尾），没有多线程随机交错压测 —— 随机交错容易产出偶发红灯，价值不如确定性用例；
>   如需补，建议用 `AudioStreamSessionTestHarness#blockAsrClientClose` 构造确定性窗口，而不是加 sleep。
> - 场景 3（异步落库丢失窗口）未做：`InterviewAsyncService` 的 `@PreDestroy` 有 30 秒排空等待，
>   可以补一条"shutdown 会等待在途落库任务"的用例，但那是"进程优雅退出"的语义，与本次长尾关系较远。
>
> P0-0 / P1-1 锁的是单点不变量，这里补组合：

1. 暂停中重连 + ASR 重连 + 计费扫描 + 心跳踢出并发。
2. **旧连接迟到事件不得影响新连接**（前一篇 §4 原则三的强化版，比"旧 `onClose` 晚于新连接建立"更具体）：

   ```text
   旧连接 A 断开 → 新连接 B 建立并成为 active → A 的 onClose / ASR error / cleanup 才到达
        ↓
   允许：只清理 A 自身（A 的资源、A 在注册表中的条目）
   禁止：移除 B / 结束逻辑会话 / 停掉 B 的计费 / 清掉 B 的注册表条目
   ```

   这是最容易"看起来修好了、实际偶发踩中"的一类竞态，必须用测试钉住。
3. 异步落库丢失窗口（前一篇 §7 假设 5）。

## 8. 拆解完成的结构性验收（不看行数）

### `AudioStreamSession` 的目标形态

- 只应出现：WebSocket 输入输出、**连接生命周期协调**、`InterviewSessionState` 引用、少量编排。
  > 措辞用「协调」而不是「连接生命周期」：P1-1 之后真正的 close / cleanup / 注册表移除应收敛到统一入口，
  > 会话本身只负责"触发并协调"，不负责自己再实现一遍收尾。
- **不应出现**：`DoubaoAsrClient`、重连 / 退避 / 残留帧、LLM 客户端、上下文裁剪、计费调度、清理细节。

### `AudioStreamingService` 的目标形态

- 只应出现：连接建立、连接注册、恢复协调、生命周期协调。
- **不应出现**：ASR runtime、回合执行、心跳判据细节。

### 拆解的目标是「变化边界」，不是「代码变短」

这份方案的核心不是把 812 行拆成几个小类，而是把实时链路后续演进的**变化方向固定下来**：

> **拆解不是为了减少代码行数，而是为了建立稳定的变化边界：**
>
> | 变化 | 约束 |
> | :--- | :--- |
> | 输入源变化（新增一种"用户输入"） | 不修改 `AsrStreamRunner` |
> | 识别通道变化（`/ws/audio` ↔ `/ws/asr`） | 不复制 `AsrStreamRunner` |
> | 回合输入变化（ASR final / TEXT answer / 首问 / 未来的"重新生成"） | 不复制 `ConversationTurnRunner` |
> | 连接退出路径变化（新增一种断开原因） | 只能进入统一 `cleanup`，不再新增收尾入口 |

落到日常开发，就是一句可操作的对照：

```text
新输入      → 找输入适配点
新识别通道  → 复用 ASR Runner
新回合输入  → 复用 Turn Runner
新退出路径  → 进入统一 cleanup
新连接状态  → 不直接碰外围注册表
```

行数只是副产品（预计 `AudioStreamSession` 回落到 300~400 行），**不是目标本身**。

## 9. 明确不做的事

- 不重写实时链路、不引入 Actor / 响应式框架：现有约 62 个用例是资产，重写等于清零。
- **不把实时热路径事件化**：沿用前一篇 §3 的边界 —— 实时流处理（音频 / ASR token / LLM token）直接调用，
  只有业务生命周期（Started / Paused / Resumed / Ended）才走领域事件。**本次不扩大领域事件的范围。**
- 不为 V2 新写一套会话实现（代价见 V2 方案 §10.2）。
- 不做一次性大重构：每项独立提交、独立回滚，P0 与 P1 之间不留长分支。
- 不在这些类上继续叠"顺手写的"新能力：新能力先找落脚点（runner / handler），找不到就先设计。
- **不再新增 Runner / Manager / Context / Projection 这类抽象**：本清单写明的抽取对象就是全部，
  实施过程中不得临时"顺手再抽一个" —— 这是本次重构最大的风险（换文件名 ≠ 降复杂度）。

> **本次实施要守住的一句话：**
> **先把已经存在的变化边界拆出来，而不是提前为未来所有可能的变化设计架构。**
> 与项目整体"实用主义 DDD、不过度设计"的方向一致。
