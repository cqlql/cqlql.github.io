# 面试体验模板：预置场景与快照固化方案

> 定稿方案（2026-09-16 设计；2026-09-17 调整为「建连即准备」并已落地）。
> 目的：让新用户**零上传、零等待**直接进入一场有质量的 AI 模拟面试。
>
> 独立准备接口（`POST /interviews/prepare`）的版本保留在第 17 节作为演进方向，后期再推进。

## 1. 要解决的问题

新用户进入模拟面试的现状链路是：

```text
上传简历 → MinIO → Python AI 解析（10~30s）→ resume_parse_result
```

而模拟面试能否"有质量"，取决于建连时后端能取到多少上下文——只有两个输入：

| 输入 | 来源 | 缺失后果 |
| :--- | :--- | :--- |
| 简历 JSON | `resume_parse_result.raw_json` | 面试官无料可问，只能泛泛提问 |
| 岗位 JD | `app_user.current_target_position_id` → `target_position` | 提问方向与用户预期不匹配 |

所以冷启动有三个硬伤：**慢**（10~30s）、**贵**（每次调用 AI）、**不稳**（依赖外部解析服务）。

**结论：模板的本质不是"一份简历样本"，而是一条绕过 AI 解析、直接产出面试上下文的种子数据通道。**

---

## 2. 核心原则（定死）

> **体验模板不属于用户、不进入 `resume`、不参与 onboarding、不产生用户简历数据；它只是 PassUp 内置的 AI 面试输入。开始面试时把模板内容固化为 Interview 快照，之后整个面试生命周期只依赖快照。**

三条由此推出的硬约束：

1. **模板是"可变配置"，快照是"不可变事实"。** 这是整个方案的基石。
2. **前端只能传资源标识（`templateUid` / `resumeId` / `targetPositionUid`），绝不能传 `resumeJson` / `jobContextJson`。** 与「角色由后端配置、前端只传枚举」的反提示词注入原则一致。
3. **模板只作用于面试链路**（`/ws/audio`）。`QnaService#buildSystemPrompt` 同样读取默认简历，但模板不落库，因此 QnA 场景下用户仍是"无简历"状态——这是**有意为之**，不是缺陷。

## 3. 架构总览

```text
                    ┌──────────────────────┐
                    │ experience_template  │
                    │    DB / 后台维护      │
                    └──────────┬───────────┘
                               │
                        PUBLISHED 模板
                               │
                               ▼
                    ┌──────────────────────┐
                    │ ExperienceTemplate   │
                    │      Service         │
                    └──────────┬───────────┘
                               │
                               ▼
                  InterviewPrepareService
                  （建连时：解析 → 裁剪 → 固化）
                               │
                               ▼
                    ┌─────────────────────┐
                    │      Interview      │
                    │  resume_snapshot    │
                    │  job_snapshot       │
                    └────────┬────────────┘
                             │
                       pending → active
                             │
                             ▼
                    AudioStreamSession
                     （只读快照构建提示词）
                             │
                             ▼
                        AI Interview
```

三层关系：

```text
ExperienceTemplate   ← 可变配置（后台可改、可下架、可归档）
        │ 选择
        ▼
InterviewContext     ← 本次面试的输入
        │ 固化
        ▼
Interview Snapshot   ← 不可变事实（历史可重现）
```

**关键结论：模板的变更不影响任何已创建的 Interview。**

## 4. 关键设计决策

| 决策 | 采纳 | 理由 |
| :--- | :--- | :--- |
| 模板不落 `resume` 表 | ✅ | 面试链路对简历的唯一消费点是两个字符串；`interview` 表不引用简历任何字段；面试历史不展示简历 |
| 模板存储用 DB | ✅ | 需后台可编辑 |
| 服务层隔离模板来源 | ✅ | 模板只被 `InterviewPrepareService` 消费，前台/后台各自只看到自己需要的视图 |
| **面试在 WebSocket 建连时创建** | ✅ | 前端只需「取凭证 → 建连」一步，不存在两次请求之间的状态变化窗口 |
| **上下文参数经 URL 查询串传入** | ✅ | 新旧客户端走同一条代码路径（旧客户端只是不传 `templateUid`），无需任何兼容开关 |
| 模板读取的瞬间即固化快照 | ✅ | 模板后续变更/下架都不影响已创建的面试 |
| 模板版本表 / 变更日志 | ❌ | 快照已解决"历史可重现"，无需为追溯建版本体系 |
| 物理删除模板 | ❌ | 改为归档，避免历史引用悬空 |
| 模板缓存（Redis/TTL） | ❌ | 模板数量 5~20，每次查一次主键即可，缓存只会引入一致性问题 |
| 审计做到 `created_by`/`updated_by` | ✅ | 第一阶段够用，完整审计待运营需求明确后再加 |
| 独立准备接口（prepare） | ⏸️ | 方案保留，后期再推进（见第 17 节） |

### 4.1 关于"快照与版本管理"的精确表述

> **快照不是模板版本管理的替代品，而是"面试历史可重现"的解决方案。**

| 机制 | 回答的问题 |
| :--- | :--- |
| Snapshot | 这场面试当时 AI 到底看到了什么？ |
| Template Version / Audit | 这个模板历史上改过什么？谁改的？能不能回滚？ |

当前阶段前者明显更重要。快照的作用是**让"是否需要版本管理"不再紧急**，而不是取代它。后台运营将来真的需要回滚时，再加 `experience_template_change_log` 即可。

## 5. 数据模型

### 5.1 `experience_template`（新建）

```sql
CREATE TABLE experience_template (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uid              VARCHAR(64)  NOT NULL UNIQUE,   -- 对外标识（种子数据用可读固定值，便于排查）
    name             VARCHAR(100) NOT NULL,
    tag              VARCHAR(50),
    direction        VARCHAR(50),                    -- BACKEND / FRONTEND / ALGORITHM ...
    experience_years INTEGER,
    description      VARCHAR(500),                   -- 前台卡片展示文案
    resume_json      JSONB        NOT NULL,          -- 与 ResumeInfo 同构
    job_context_json JSONB        NOT NULL,          -- 与 InterviewContext.jobContextJson 同构
    status           VARCHAR(20)  NOT NULL,          -- DRAFT / PUBLISHED / ARCHIVED
    sort_order       INTEGER      NOT NULL DEFAULT 0,
    created_by       BIGINT,
    updated_by       BIGINT,
    created_at       TIMESTAMPTZ  NOT NULL,
    updated_at       TIMESTAMPTZ  NOT NULL,

    CONSTRAINT chk_experience_template_status
        CHECK (status IN ('DRAFT', 'PUBLISHED', 'ARCHIVED'))
);

CREATE INDEX idx_experience_template_status_sort
    ON experience_template (status, sort_order);
```

**为什么用 `job_context_json` 而不是 `position_title` + `position_jd` 两列：**

- 与 `InterviewContext.jobContextJson` 结构统一，避免"表结构"和"上下文结构"两套；
- 岗位未来若扩展 `company` / `requirements` / `responsibilities`，不需要改表。

### 5.2 `interview`（扩展）

```sql
-- 快照（本次核心）
ALTER TABLE interview ADD COLUMN resume_snapshot_json JSONB;
ALTER TABLE interview ADD COLUMN job_snapshot_json    JSONB;
ALTER TABLE interview ADD COLUMN created_at           TIMESTAMPTZ;

-- 面试参数：从建连 URL 读取后随面试一起落库，供历史复盘与重连使用
ALTER TABLE interview ADD COLUMN language        VARCHAR(10);
ALTER TABLE interview ADD COLUMN detail_level    VARCHAR(20);
ALTER TABLE interview ADD COLUMN interview_style VARCHAR(20);

-- 体验场景归因（业务统计用，不是历史恢复）：真实简历路径为 NULL
ALTER TABLE interview ADD COLUMN template_uid    VARCHAR(64);

COMMENT ON COLUMN interview.resume_snapshot_json
    IS '面试创建时固化的简历上下文（裁剪后，即 AI 实际看到的输入）';
COMMENT ON COLUMN interview.job_snapshot_json
    IS '面试创建时固化的岗位上下文';
COMMENT ON COLUMN interview.created_at
    IS '创建（建连准备）时间，用于清理超时未建连的 pending 记录';
COMMENT ON COLUMN interview.language
    IS '面试语言：zh / en';
COMMENT ON COLUMN interview.detail_level
    IS '提问详细程度：short / medium / detailed';
COMMENT ON COLUMN interview.interview_style
    IS '面试风格，与 InterviewStyle 枚举对齐（STANDARD / PRESSURE）';
COMMENT ON COLUMN interview.template_uid
    IS '体验场景 uid（真实简历路径为 NULL），用于业务归因统计';

ALTER TABLE interview DROP CONSTRAINT IF EXISTS chk_interview_status;
ALTER TABLE interview ADD CONSTRAINT chk_interview_status
    CHECK (status IN ('pending', 'active', 'paused', 'ended'));

COMMENT ON COLUMN interview.status
    IS '会话状态 (pending/active/paused/ended)';
```

**以下几点必须注意：**

1. **`created_at` 是必需的，不是锦上添花。** V5 建表时 `interview` 只有 `start_time` / `end_time`，而新建的 PENDING 记录 `start_time` 为空，**没有 `created_at` 就无法按时间清理孤儿记录**。
2. **`chk_interview_status` 必须 DROP 后重建。** V15 已定义 `('active','paused','ended')`，直接插入 `pending` 会被约束拒绝。
3. **`language` / `detail_level` / `interview_style` 必须落库。** 这三项虽然从 URL 读取，但落库后才能支撑历史复盘与重连（重连时复用内存中的 `InterviewContext`，而内存态丢失时 DB 是唯一的重建依据）。
4. **`mode` 无需新增**——它是 V5 建表时就有的字段（`mode VARCHAR(20) NOT NULL`，带 `chk_interview_mode` 约束，取值 `ASSIST` / `MOCK`）。因此"`InterviewContext` 的全部输入都在 `interview` 表中"这句话成立：快照 + 上面三列参数 + 原有 `mode`。
5. **`template_uid` 是业务归因列，不是历史恢复手段。** 历史内容已由快照完整固化；这一列只回答"哪个模板被选得多、完成率高、转化好"——这类信息**无法从快照可靠反推**（同名模板可能被改过）。存 uid 而非自增 id：跨表可读、无需 join。**要加就现在加**：后加会导致此前所有面试永远无法归因。

### 5.3 快照存"裁剪后的内容"而非解析原文

`InterviewContext.resumeJson` 存放的**不是** `resume_parse_result.raw_json`，而是已经过裁剪管线的内容：

```text
rawResumeJson ──→ ResumeContextBuilder#buildBoundedJson ──→ InterviewContext.resumeJson
                   （按 realtime.resume-context.* 裁剪）
```

所以快照必须固化**裁剪后**的内容，理由：

- AI 从未看到过完整原文，它看到的就是裁剪后的有限上下文——这才符合"事实快照"的语义；
- 天然有界（受 `ResumeContextPolicy` 约束），不会让 `interview` 表无界膨胀；
- 完整性不丢：真实简历的 `rawJson` 本身就在 `resume_parse_result` 里；
- `job_snapshot_json` 的 JD 来自 `target_position.description`（`TEXT`，无长度约束），写入时需做一次长度兜底截断。

**一句话原则：快照是「AI 输入事实」，不是原始业务数据的替代品。**

```text
resume_parse_result.raw_json      原始业务数据（解析产物）
        ↓ ResumeContextBuilder
interview.resume_snapshot_json    本次 AI 实际看到的内容
        ↓
AI
```

三段数据的职责因此是分开的：

| 数据 | 定位 |
| :--- | :--- |
| `resume_parse_result.raw_json` | 原始数据 |
| `interview.resume_snapshot_json` | 本次 AI 实际看到的数据 |
| `interview` 记录行 | 历史事实 |

这也解释了为什么裁剪算法变更**不应该回填历史快照**：

```text
2026-09-17 的面试 → 使用当时的裁剪结果
2026-10-01 的面试 → 使用新的裁剪结果
```

两次面试各自忠实记录「当时 AI 看到了什么」，这正是快照的价值；若回填，历史就变成了「AI 现在会看到什么」的假象。

## 6. 建连链路与凭证

### 6.1 面试在 WebSocket 建连时创建

前端**不需要任何准备接口**，一条链路完成：

```text
GET /api/ws/ticket                          -> 取凭证（只证明身份，TTL 30 秒）

/ws/audio?ticket=xxx
          &templateUid=exp-java-backend-3y   // 可选：体验场景
          &resumeId=12                       // 可选：指定简历（不传用默认简历）
          &targetPositionUid=01j...          // 可选：指定岗位（不传用当前主目标岗位）
          &mode=MOCK&language=zh&detailLevel=medium&interviewStyle=STANDARD
          &resume=<逻辑会话ID>                // 可选：暂停后重连
   -> 解析上下文 -> ResumeContextBuilder 裁剪
   -> 建 Interview(pending) + 固化快照
   -> pending 转 active，开始音频流
```

内部流程（`InterviewPrepareService#prepareForConnection`）：

```text
1. 解析上下文来源
   ├── templateUid 存在? → 取 PUBLISHED 模板（不存在 / 未发布 → 直接失败）
   └── 否则            → 真实简历路径
                          ├── resumeId 指定? 否则默认简历
                          ├── targetPositionUid 指定? 否则当前主目标岗位
                          └── 两者皆空 → 允许（退化为通用求职者提示词）

2. ResumeContextBuilder 统一裁剪（模板与真实简历走同一条管线）
3. 清理该用户旧的 pending 记录（重复建连不产生孤儿）
4. 创建 Interview(status = pending)：写入快照、面试参数与 template_uid（场景归因）
5. onOpen 校验 pending → 条件更新转 active → 回填 start_time / session_id
6. 用快照构建 InterviewContext，AudioStreamSession 据此生成系统提示词
```

### 6.2 为什么用 URL 参数而不是独立准备接口

**收益**：前端只需「取凭证 → 建连」一步，不存在"凭证签发与建连之间状态发生变化"的时间窗口；也不需要为新旧客户端维护两条入口——旧客户端只是不传 `templateUid`，走的是**同一条代码路径**（因此不需要任何兼容开关）。

**代价**：针对上下文参数的失败只能在建连后以 WebSocket 错误消息返回（HTTP 错误更易处理）。但凭证缺失/无效、余额不足仍由握手层拦截。

**安全约束**：URL 只允许携带**资源标识**：

| 参数 | 服务端校验 |
| :--- | :--- |
| `templateUid` | 必须存在且为 `PUBLISHED` |
| `resumeId` | 必须存在且属于当前用户（`findByIdAndUserId`） |
| `targetPositionUid` | 必须存在且属于当前用户 |

**绝不接受** `resumeJson` / `jobContextJson` 等上下文正文。

**校验策略：「未传」与「传了无效」严格区分**

| 参数 | 未传 | 传了但无效（不存在 / 不属于当前用户 / 未发布） |
| :--- | :--- | :--- |
| `templateUid` | 走真实简历路径 | **直接失败**（`INTERVIEW_PREPARE_FAILED`） |
| `resumeId` | 回退默认简历 | **直接失败**（`INTERVIEW_PREPARE_FAILED`） |
| `targetPositionUid` | 回退当前主目标岗位 | **直接失败**（`INTERVIEW_PREPARE_FAILED`） |

**绝不静默降级**：用户明确选了某个资源后，后端偷偷换成别的（或退化成空上下文），会让他以为 AI 正在看那份简历 / 岗位，实际却不是：

```text
用户明确选择 A 简历
        ↓
A 不存在 / 无权限
        ↓
后端偷偷使用默认简历（或根本没有简历）
        ↓
用户以为 AI 正在看 A
```

这与"上下文必须一次确定并固化"是同一个原则——既然要固化，就必须固化的**是用户要的那份**。

**唯一的宽容之处**：真实简历路径下，如果参数**什么都没传**且用户也确实没有简历 / 岗位，则允许退化为通用求职者提示词——保持历史行为，不能因为新增校验把老用户从"能用"变成"不能用"。

### 6.3 凭证（ticket）

`GET /api/ws/ticket` 是**唯一凭证入口**，Redis value 直接存 `userId`：

```text
auth:ws:ticket:{ticket} = 1001        TTL 30s
```

凭证的职责收敛为：

> **证明"你是谁"。**

它不承载任何面试上下文——"进入哪场面试"由建连时的 URL 参数决定，面试记录也由服务端在建连时创建。因此凭证永远不会与面试状态不一致，也**不需要"载荷对象"这类封装**（单字段的封装只会增加一层无意义的跳转）。

> ⚠️ 实现细节：value 经 Jackson 反序列化到 `Object` 时，数字可能是 `Integer` 也可能是 `Long`（取决于数值范围），因此统一走 `value.toString()` 再做 `Long.valueOf` 解析，避免直接强转踩类型坑。

### 6.4 重连

重连**必须复用原 Interview 与会话，绝不创建新记录**：

```text
GET /api/ws/ticket → /ws/audio?ticket=xxx&resume=<逻辑会话ID>
   -> 从 logicalSessions（JVM 内存注册表）按逻辑会话 ID 恢复
   -> 校验归属 → paused 转 active → 复用原 systemPrompt / context / interviewId
```

URL 上的上下文参数在重连时不会被使用（会话状态已存在内存中）。

> 已知限制（既有，非本次引入）：`logicalSessions` 是 JVM 内存注册表，重连需落到同一实例。由于 `InterviewContext` 的全部输入已可从 `interview` 表（快照 + 参数列）重建，将来做无粘性重连有了基础，但本次不改。

### 6.5 顺带修掉的一个既有缺陷

改造前，「用哪份简历」被决定了两次且互不知情：

```text
GET /api/resumes/interview-prepare    ← 前端据此让用户选择简历（BOUND / DEFAULT / candidates）
        ↓ 用户选 A 简历
WebSocket 建连
        ↓
AudioStreamingService#onOpen
        ↓
resumeService.getDefaultResumeJson(userId)   ← 又独立取了一次「默认简历」
```

即 **HTTP 侧用户选的简历与 WebSocket 实际使用的简历可能不是同一份**。

现在简历在建连时由 URL 的 `resumeId` 一次性确定（不传才回退默认简历）并与快照一起固化，缺陷消除。`GET /api/resumes/interview-prepare` 保留为"简历推荐"查询，其结果作为前端传 `resumeId` 的依据。

### 6.6 前台 / 后台接口

| 侧 | 接口 | 说明 |
| :--- | :--- | :--- |
| 前台 | `GET /api/experience-templates` | 仅返回 `PUBLISHED`，卡片列表（不含简历正文） |
| 前台 | `GET /api/ws/ticket` | 唯一凭证入口（payload 仅 `userId`） |
| 前台 | `GET /api/resumes/interview-prepare` | 简历推荐查询，结果作为建连参数 |
| 后台 | `GET/POST/PUT /api/admin/experience-templates` | CRUD |
| 后台 | `POST /api/admin/experience-templates/{uid}/publish` | 发布 |
| 后台 | `POST /api/admin/experience-templates/{uid}/archive` | 归档（**不提供物理删除**） |
| 后台 | `GET /api/admin/experience-templates/{uid}/preview` | 返回**裁剪后**内容，供运营确认"AI 实际会看到什么" |

## 7. 实例隔离 Demo

**10:00 用户 A 点击体验：**

```text
ExperienceTemplate（当时内容）
        ↓ 建连时生成
Interview A
  resume_snapshot_json = 10:00 的内容
  job_snapshot_json    = 10:00 的内容
```

**10:01 运营修改模板。**

→ **Interview A 完全不受影响。** 内容已注入 `InterviewContext` 并进内存逻辑会话（暂停/重连复用内存中的上下文），后台改动动不了它。

**10:02 用户 B 点击体验：**

```text
ExperienceTemplate（新内容）→ Interview B
```

## 8. 错误处理

### 8.1 握手阶段（连接建立前拦截）

```text
MISSING_TICKET          未携带凭证
INVALID_TICKET          凭证无效或已过期
INSUFFICIENT_BALANCE    面试时长余额不足
```

这些通过 HTTP 握手拦截，前端拿到明确的错误码与提示。

### 8.2 建连后（WebSocket 错误消息）

```text
INTERVIEW_PREPARE_FAILED   上下文准备失败（如体验场景已下架）
RESUME_EXPIRED             重连时逻辑会话不存在或已过期
RESUME_FORBIDDEN           重连时逻辑会话归属不匹配
INTERVIEW_NOT_FOUND        面试记录不存在
INTERVIEW_NOT_PENDING      面试已开始或已结束（并发建连时只有一个能成功）
```

统一通过 `ErrorMessage` 消息下发，随后关闭连接（4002）。

> 注意：这是 URL 传参方案的固有特征——**上下文参数的问题只能在建连后反馈**。如果将来对"参数错误的即时反馈"要求变高，就是推进第 17 节 prepare 方案的理由之一。

## 9. Interview 生命周期

### 9.1 状态机

```text
(建连) pending ──(转 active)──→ active ──→ paused ──→ active
                                  │           │           │
                                  ▼           ▼           ▼
                                 ended      ended       ended
   │
   └─ 超过 3 分钟未完成初始化 → 回收删除
```

| 时机 | 状态迁移 | 同时写入 |
| :--- | :--- | :--- |
| 建连准备 | — → `pending` | `created_at`、快照、mode/language/detailLevel/interviewStyle |
| 建连（onOpen） | `pending` → `active` | `start_time`、`session_id`（物理连接 ID） |
| 暂停 | `active` → `paused` | — |
| 重连 | `paused` → `active` | `session_id` 刷新为新连接 ID |
| 结束 / 暂停超时 | → `ended` | `end_time` |

### 9.2 为什么仍然保留 pending 这一态

即使面试是在建连时创建（`pending` 只存活毫秒级），保留它仍有价值：

1. `pending → active` 用**条件更新**（`activateInterview ... where status = 'pending'`）保证**并发建连的原子性**——返回 0 即代表已被其它连接消费，直接拒绝，避免两条连接共用一场面试；
2. 建连后初始化失败（如 ASR 建立失败）时，记录停在 `pending`，可被定时任务回收，或被显式结束，不会留下"僵尸 active"；
3. 重连场景有明确的终态校验（只有 `paused` 能恢复）。

### 9.3 派生的 4 个问题与对策

| # | 问题 | 对策 |
| :--- | :--- | :--- |
| 1 | 孤儿 pending 堆积（建连中断、初始化失败） | 补 `created_at` 列 + 复用 `WsHeartbeatScheduler` 定时清理（保留 3 分钟） |
| 2 | `start_time` 语义错位（列注释是"面试开始时间"，历史按它排序） | 创建时留空，转 `active` 时回填 |
| 3 | 创建时 `session_id` 还不存在 | 创建时为空，建连后回填物理连接 ID |
| 4 | 同一用户重复建连 | 每次准备先**删除该用户所有 pending 记录**（无消息、无副作用），再创建新的 |

**好消息：** 孤儿 pending 不会污染历史列表——`findNonEmptyByUserIdOrderByStartTimeDesc` 用 `exists(interview_message)` 过滤，无消息的 pending 天然不出现在前端。

### 9.4 附带收益：上下文可从 DB 完整重建

`InterviewContext` 的全部输入（快照 + 参数列 + mode）都在 `interview` 表中。这意味着逻辑会话的上下文**不再唯一依赖 JVM 内存**，为将来做无粘性重连、多实例水平扩展留出了空间（本次不改，`logicalSessions` 仍是内存注册表）。

## 10. 模板内容规范

模板是**面试官提问的燃料**，不是占位符。

1. **结构必须填满**：`basic`（含 `jobTitle` / `experienceYears`）、`summary`、`skills`、`workExperiences`、`projectExperiences`、`educations` 全非空。
2. **每个项目要有"可追问的抓手"**：具体技术选型 + 量化成果 + 个人职责（如"QPS 从 800 提升到 5000，P99 从 320ms 降到 90ms"），面试官才有得追。
3. **按 `ResumeContextPolicy` 上限内书写**：单条描述 ≤300 字、项目描述 ≤500 字、技能 ≤30 项。写到上限外会被静默截断，不如一开始就写紧凑。
4. **规模控制**：2 段工作经历 + 2~3 个项目 + 8~12 项技能，撑起 15~20 分钟面试，再长只增 token 成本。
5. **严禁真实隐私与真实公司**：虚构姓名、示例邮箱（`*.example.com`）、"某电商平台"式公司名。
6. **简历技能栈必须与 JD 呼应**：形成"JD 要求 X → 简历有 X → 面试官深挖 X"的正循环。
7. **一个模板 = 一份简历 + 配套 JD 的完整场景**：不要让前端自由组合简历与岗位——"Java 后端简历 × 算法岗 JD"会让提问非常怪异。
8. **数量控制在 3~6 份**：按方向 × 经验层级（`java-backend-3y` / `frontend-2y` / `software-fresh`）。
9. **不要用模板区分"压力程度"或"语言"**：二者已由 `interviewStyle`（`STANDARD`/`PRESSURE`）和 `language` 控制。模板管**内容**，风格管**打法**。

## 11. 校验与安全

### 11.1 保存期校验（后台化后的新安全边界）

模板在 classpath 时可以启动期校验、写错就启动失败。改为后台可编辑后，**校验必须前移到 Admin 保存时**，否则脏数据会直接流进正在等待的用户面试。

| 校验项 | 说明 |
| :--- | :--- |
| 反序列化 | 必须能解析为 `ResumeInfo` |
| 必填结构 | `basic.name` 非空、至少 1 段工作经历、至少 1 个项目、`jobContext.title` / `jd` 非空 |
| 长度上限 | 与 `ResumeContextPolicy` 对齐（超限直接拒绝，而非静默截断） |
| 发布门槛 | 未通过校验不允许 `PUBLISHED`；发布前会再校验一次 |

后台表单还做了两道辅助防线：JSON 合法性前端预校验 + 「格式化」按钮，以及**裁剪后内容预览**（让运营看到 AI 实际会看到什么）。

### 11.2 PII 检测（定位为"检测"，不是"保证"）

> ⚠️ 不要承诺"保证模板不含真实个人信息"。正则能拦 `138xxxx8888` / 非示例域邮箱，拦不住"某某互联网公司 张经理"。

做法：

- 服务端做**常见 PII 模式检测**（手机号、非 `example.com` 等保留域的邮箱），命中即阻断；
- 后台 UI 明确提示：**模板仅允许使用虚构人物、虚构公司及脱敏数据**；
- 二者结合，比单纯依赖正则可靠。

### 11.3 反提示词注入

- 前端只传资源标识（`templateUid` / `resumeId` / `targetPositionUid`），**绝不接受** `resumeJson` / `jobContextJson`；
- 模板内容由后端受控数据源提供，前端无法注入任意 system prompt；
- 所有标识在服务端校验存在性与归属。

## 12. Seeder：classpath → DB

```text
classpath JSON ──→ Seeder ──→ DB ──→ 服务层 ──→ InterviewContext
```

**不是**：

```text
classpath JSON ──┐
                 ├──→ 服务层     ← ❌ 会出现"到底谁是真相"
DB ──────────────┘
```

规则：

1. Flyway 只建表；模板 JSON 留在 classpath **仅作为 seed 数据源**；
2. Seeder **只插不覆盖**（按 `uid` 判存在）——否则发版会冲掉运营修改，且极难排查；
3. 上线后 **classpath JSON 不再参与运行时读取**，这一点必须写进代码注释；
4. 多实例并发执行 Seeder 由 `UNIQUE(uid)` 兜底，**第一期不做分布式锁**；
5. 种子模板直接以 `PUBLISHED` 导入（否则新环境前台为空）；运营后续编辑会自动退回草稿。

## 13. 风险与对策

| 风险 | 对策 |
| :--- | :--- |
| 孤儿 pending 记录堆积 | `created_at` + 定时清理（复用 `WsHeartbeatScheduler`） |
| `chk_interview_status` 未更新导致插入失败 | V24 中 DROP 后重建，加入 `pending` |
| ticket value 反序列化成 `LinkedHashMap` | 显式 JSON 字符串读写，不依赖 RedisTemplate 对象序列化 |
| **非法 `resumeId` / `targetPositionUid`（传了但不存在 / 无权限）** | **直接失败**（`INTERVIEW_PREPARE_FAILED`），不静默降级；仅「未传」才回退默认 |
| 上下文参数错误只能在建连后反馈 | 接受；若成为痛点则推进第 17 节 prepare 方案 |
| 并发建连消费同一场面试 | `pending → active` 条件更新，失败即拒绝（`INTERVIEW_NOT_PENDING`） |
| 建连后初始化失败留下活动态记录 | 显式结束（无消息记录会被 `endInterview` 直接删除），并在创建失败时兜底回滚 |
| 前端取凭证后超过 30 秒才建连 | 凭证过期 → 重新取凭证即可（不再有第二条链路的窗口问题） |
| 模板内容写坏直接影响新用户 | 保存期强校验 + DRAFT 草稿态 + 预览接口 |
| 运营误传真实隐私数据 | PII 检测 + UI 提示 + 明确"仅虚构数据" |
| 发版覆盖运营修改 | Seeder 只插不覆盖 |

## 17. 演进方向：独立准备接口（暂不实施）

**当前没有实现，不作为现有系统行为的依据。** 本节只记录「何时该重新评估」。

设想：把「解析上下文 + 建面试 + 固化快照」提前为一次 HTTP 调用（`POST /interviews/prepare`），
凭证随之绑定 `interviewId`；建连时只凭凭证取用已就绪的面试。

**仅当出现以下需求之一时重新评估：**

1. 前端必须在建立 WebSocket **之前**拿到参数校验结果（当前参数错误只能在建连后反馈）；
2. 需要在 HTTP 阶段完成**计费预检**（当前只在握手层校验）；
3. 建连前需要展示「准备中」状态；
4. 上下文准备耗时明显增加（当前解析与建连在同一流程内完成，耗时可控）。

### 17.1 若推进，必须守住的一条铁律

> **重连分支不得查询 `logicalSessions`（JVM 内存注册表）。**

原因有二：

1. **多实例漂移**：HTTP 请求经负载均衡可能落到另一个实例，「会话可恢复」会被误判成「会话已过期」；WebSocket 长连接至少有粘性，HTTP 没有；
2. **循环依赖**：`AudioStreamingService` 已依赖准备服务，反向依赖会成环。

所以重连凭证只能证明身份，可恢复性判断必须留在 `onOpen`（那里才真正持有注册表）。

### 17.2 代价

前端多一次调用；凭证出现两种形态；握手需要额外的互斥校验；且需要为新旧客户端维护兼容层（旧客户端不调 prepare，得由服务端代为准备）。

**判断标准**：只有本节开头那 4 个需求真的出现时才做，否则当前的「建连即准备」更简单。
