# 虚拟支付充值 / 价格配置方案

微信虚拟支付、代币充值时长场景下，**单价到底放配置文件还是数据库**，以及配套的订单快照、命名解耦、审计日志等设计。

> 本篇是 [虚拟支付充值-资产发放方案](./虚拟支付充值-资产发放方案.md) 的配套篇：那篇讲资产怎么**发**，本篇讲价格怎么**管**。底层共用 `recharge_order` + `asset_batch` 体系。

------

## 一、核心原则

> **业务定价放数据库；YAML 只做兜底；充值订单保存价格快照；`TOPUP` 不参与价格命名；当前不需要过度抽象成通用配置中心。**

------

## 二、`application.yml` 最终调整

原来：

```yaml
recharge:
  grant:
    max-retry: 10
  topup-unit-price: 0.20
```

建议改成：

```yaml
recharge:
  grant:
    max-retry: 10
  # 数据库无充值价格配置时的兜底默认值
  default-interview-minute-price: 0.20
```

- `grant.max-retry` 属于**技术运行参数**，继续放 YAML。
- `default-interview-minute-price` 只是**数据库没有配置时的兜底默认值**，不是生产环境的最终业务价格。

### 配置优先级

```text
Redis / 本地缓存
        ↓
数据库 recharge_setting
        ↓
application.yml 默认值
```

> 初期不建议做复杂的三级缓存，见后文「缓存不要过度设计」。

### YAML fallback 的意义

保留兜底默认值，但一定要明确：**它不是生产环境的最终业务价格，只是数据库配置不存在时的默认值。**

```java
BigDecimal price = rechargeSettingService
        .getInterviewMinutePrice()
        .orElse(properties.getDefaultInterviewMinutePrice());
```

正常生产环境 DB 一定存在配置；如果走到兜底分支，说明配置丢失，属于异常，**应触发告警**，不能静默使用默认价格跑订单。

------

## 三、价格不要再叫 `topup-unit-price`

这是比较重要的一项命名修改。

不推荐：

```text
topup-unit-price
topup_unit_price
```

原因：`TOPUP` 是**充值方式 / 订单类型**，而不是被定价的资产。

当前已有：

```text
asset_type
├── INTERVIEW_SECONDS
├── AI_CHAT_COUNT
└── VIP_DAYS

order_type
├── PACKAGE
└── TOPUP
```

所以应该把两个概念分开：

```text
TOPUP（充值方式）
  ↓
购买
  ↓
INTERVIEW_SECONDS（资产类型）
  ↓
按 MINUTE 计价
  ↓
0.20 元
```

而不是：

```text
TOPUP = 0.20 元
```

这样以后增加其他充值类型（AI 问答次数、VIP 天数）也不会导致命名混乱。

------

## 四、`sys_config` vs `recharge_setting`

最终建议：**选择 `recharge_setting`**。

不建议现在直接搞一个全局 `sys_config`，因为目前这个价格明显属于**充值领域业务配置**，而不是系统级技术配置。

如果使用 `sys_config`，以后很容易变成大杂烩：

```text
sys_config
-------------------------------
jwt.expire
upload.max-size
email.smtp-host
recharge.topup_unit_price
interview.max-duration
...
```

而 `recharge_setting` 能够保持充值领域边界。

------

## 五、`recharge_setting` 怎么设计

考虑当前实际业务，**不要为了未来可能出现的各种资产立即做成万能价格规则表**。

目前可以简单设计：

```text
recharge_setting
--------------------------------
id
interview_minute_price
status
updated_by
updated_at
```

例如：

```text
id: 1
interview_minute_price: 0.20
status: 1
```

- `status`：预留状态字段，1 启用 / 0 停用，方便运营后台临时关闭时长充值入口，不用删价格。

### 为什么暂时不建议通用价格表

虽然这种设计理论上更通用：

```text
asset_type      | price_unit | unit_price
INTERVIEW_SECONDS | MINUTE   | 0.20
AI_CHAT_COUNT    | COUNT     | 0.10
VIP_DAYS         | DAY       | 1.00
```

但目前业务还没有真正需要这么做。**不要为了"未来可能增加"提前把简单需求抽象成通用价格引擎。**

等未来真的出现 AI 问答次数单独充值、VIP 天数单独充值时，再升级成 `recharge_price` 通用价格表即可。

------

## 六、价格变更日志不要塞进 `recharge_setting`

之前提到的 `old_value` 字段建议取消。

例如不要：

```sql
recharge_setting
----------------
interview_minute_price
old_value
```

因为多次变更后只能知道当前值和上一次值，更早的历史丢失：

```text
0.20 → 0.25 → 0.30 → 0.18
最终只能知道：当前 = 0.18，上一次 = 0.30
```

如果需要后台审计，建议独立建表：

```text
recharge_setting
--------------------------------
id
interview_minute_price
status
updated_by
updated_at

recharge_setting_log
--------------------------------
id
setting_id
old_price
new_price
updated_by
created_at
```

完整记录每一次价格调整：

```text
0.20 → 0.25
0.25 → 0.30
0.30 → 0.18
```

------

## 七、金额字段使用 `BigDecimal`

Java 中：

```java
BigDecimal
```

不要用 `double` / `float`，虚拟支付场景精度不能出错。

数据库使用：

```sql
NUMERIC(12, 4)
```

或者更高精度。例如 `interview_minute_price = 0.2000`，如果未来出现更细的价格，也不会因为 `NUMERIC(10,2)` 被限制。

------

## 八、最重要：订单必须保存价格快照

这是必须落地的，也是米大师对账、退款最关键的保障。

例如当前价格 `0.20 元/分钟`，用户充值 100 分钟，创建订单：

```text
recharge_order
--------------------------------
order_type       = TOPUP
quantity         = 100
unit_price       = 0.20
total_amount     = 20.00
```

随后管理员把价格改成 `0.25 元/分钟`，**这个订单仍然必须按照 `0.20 × 100 = 20.00` 处理**。

不能在支付回调时重新查询 `recharge_setting.interview_minute_price` 然后重新计算订单金额。

### 订单业务字段

`recharge_order` 至少明确以下字段：

| 字段 | 含义 |
| ---- | ---- |
| `order_type` | 怎么充值（PACKAGE / TOPUP） |
| `asset_type` | 充值什么资产（INTERVIEW_SECONDS 等） |
| `quantity` | 买多少 |
| `price_unit` | 怎么计价（MINUTE / COUNT / DAY） |
| `unit_price` | 单位价格 |
| `total_amount` | 最终订单金额 |

示例：

```text
order_type   = TOPUP
asset_type   = INTERVIEW_SECONDS
quantity     = 100
price_unit   = MINUTE
unit_price   = 0.20
total_amount = 20.00
```

### `TOPUP` 和资产类型彻底解耦

最终模型理解：

```text
订单类型 TOPUP
    │
    ▼
充值资产 INTERVIEW_SECONDS
    │
    ▼
计价单位 MINUTE
    │
    ▼
单价 0.20 元
    │
    ▼
数量 100 分钟
    │
    ▼
订单金额 20.00 元
```

资产发放后：

```text
asset_batch
----------------------------
asset_type   = INTERVIEW_SECONDS
source       = TOPUP
total_amount = 6000 seconds
```

> 订单中的 `TOPUP` 表示来源/充值方式；`asset_batch.source = TOPUP` 表示资产来源，两者语义保持一致。

------

## 九、微信虚拟支付注意事项

**业务后台修改价格 ≠ 已创建订单价格修改。**

正确流程：

```text
后台价格 0.20
    ↓
用户创建充值订单
    ↓
读取 0.20，写入 recharge_order
    ↓
unit_price = 0.20，total_amount = 20.00
    ↓
调用微信虚拟支付（米大师）
```

之后管理员 `0.20 → 0.25`，只影响**新订单**，老订单 `unit_price = 0.20` 保持不变。

### 米大师下单传参对齐

下单时传给米大师的金额，**必须和订单快照 `total_amount` 完全一致**。

> 订单快照是唯一可信源；不要动态实时计算传给米大师，防止代码逻辑不一致导致平台侧和米大师侧金额不匹配，对账翻车。

这也是后续支付回调、对账、退款等逻辑保持一致的基础。

------

## 十、缓存不要一开始过度设计

之前方案中提到的「本地缓存 + Redis + 定时 5 分钟刷新」，建议删掉"必须三层"的要求。

目前只有一个 `interview_minute_price`，而且价格读取只发生在**创建充值订单时**，没必要为了这个配置搞复杂缓存体系。

### 第一阶段

```text
创建订单
    ↓
RechargeSettingService
    ↓
本地缓存
    ↓
DB
```

后台修改：

```text
修改 DB → 清除本地缓存
```

就够了。

### 多实例后再升级

```text
后台修改
    ↓
DB
    ↓
Redis Pub/Sub
    ↓
通知所有实例
    ↓
清除本地缓存
```

或者直接使用 Redis 作为共享缓存。**没必要现在就做。**

------

## 十一、后台价格修改需要业务校验

后台不能让管理员随便输入，至少：

- 价格 `> 0`
- 限制合理精度：最多 4 位小数
- 根据业务增加最大允许单价，避免误操作

例如 `0.20` 误填成 `20.00` 甚至 `200.00`，会造成严重支付问题。

### 高风险变更保护

价格修改属于高风险操作，建议：

- 单价变动幅度超过阈值（如 ±20%）时，需要**二次确认或双人审批**
- 记录操作人、修改时间、旧价格、新价格（写入 `recharge_setting_log`）

## 十三、最终定稿

### `application.yml`

```yaml
recharge:
  grant:
    max-retry: 10
  # 数据库无充值价格配置时的默认值
  default-interview-minute-price: 0.20
```

### 数据库表

```text
recharge_setting
----------------------------
id
interview_minute_price
status
updated_by
updated_at

recharge_setting_log
----------------------------
id
setting_id
old_price
new_price
updated_by
created_at

recharge_order
----------------------------
order_type
asset_type
quantity
price_unit
unit_price
total_amount
...
```

### 核心规则

| 规则 | 说明 |
| ---- | ---- |
| 业务价格 | DB > YAML fallback |
| 订单价格 | 创建订单时快照 |
| 订单创建后 | 永远使用订单快照 |
| 价格修改 | 只影响新订单 |
| TOPUP | 表示充值方式/订单类型，不参与价格字段命名 |
| 充值价格 | 属于 recharge 领域，不放通用 sys_config |
| 缓存 | 初期本地缓存即可，多实例后再引入 Redis 失效通知 |
| 审计 | 当前配置和修改历史分表 |
| 金额类型 | Java `BigDecimal`，DB `NUMERIC(12,4)` |

这一版既不会把业务设计得过于简单，也没有为了"以后可能扩展"提前造一个通用配置/价格引擎，适合当前规模。
