# 虚拟支付充值 / 资产发放方案

小程序售卖**问答次数**与**语音时长**，支持固定套餐 + 用户自定义充值时长。

> 本篇是 [AI问答计费-资产扣减方案](./AI问答计费-资产扣减方案.md) 的**对偶篇**：那篇讲资产怎么**消耗**（`CONSUME`），本篇讲资产怎么**进来**（`RECHARGE`）。底层共用同一套 `user_asset` + `user_asset_log` 体系，不要另起炉灶建新的余额表。
>
> 协议细节、签名算法、错误码见 [微信小程序虚拟支付](../../../后端/java/微信小程序虚拟支付.md)。本篇只讲**业务建模与选型**。

------

## 一、为什么 iOS 必须走虚拟支付

iOS 线上售卖虚拟服务（次数、时长）**严禁**使用普通微信支付 `wx.requestPayment`，否则苹果 IAP 审核驳回。虚拟支付在 iOS 上会自动路由到 Apple 支付。

违规后果见错误码 `-15017`（商家涉嫌违规，收款功能被限制）、`-15019`（商户受限）。

------

## 二、两种模式选型

### 1. 道具直购（Offer 商品）

- **无后端统一下单 API**：后端只生成签名，前端调 `wx.requestVirtualPayment` 唤起支付，下单动作在客户端完成。
- 每个道具对应**固定售价、固定套餐**，价格由微信后台锁定，下单时不可动态改价。
- 微信只负责收钱，**发放什么权益完全由后端控制**。
- 适合：固定套餐包。

### 2. 代币模式

- 用户现金充值代币，余额由**微信托管**。
- 后续服务端调扣币接口，兑换成时长 / 次数。
- 适合：**用户自定义输入任意语音分钟数**、零散按次扣费。

### 3. 对照表

| 方案 | 自定义任意分钟 | 需要代币钱包 | 上新档位要审核 | 适用场景 |
| ---- | -------------- | ------------ | -------------- | -------- |
| 道具直购-固定套餐 | ❌ 否 | 不需要 | ✅ 需要 | 档位少的问答包、语音包、组合礼包 |
| 代币模式 | ✅ 可以 | 需要 | ❌ 不需要 | 用户自由输入充值时长、高频零散扣费 |

> ❗ 普通微信支付商户号**不能复用**：虚拟支付需单独开通，有独立的二级商户号与 `appKey`。

### 4. 本项目建议：组合使用

| 场景 | 模式 |
| ---- | ---- |
| 固定套餐（50 次包 / 30 分钟包 / 组合包） | 道具直购 |
| 用户自定义分钟数（17 分钟、125 分钟…） | 代币模式 |

理由：套餐档位是营销抓手，需要用户一眼看到的明码标价 → 道具；自定义时长是长尾需求 → 代币，新增档位无需微信审核。

## 三、前置开通清单

1. 小程序后台开启【虚拟支付】能力（企业 / 事业单位 / 个体工商户主体）。
2. 道具直购：创建道具商品，每个套餐一个 `offerId` / `productId`。
3. 代币模式：配置代币兑换比例——**一旦保存永久不可修改**，上线前必须核算清楚。
4. 获取密钥：`appKey`（虚拟支付密钥，**仅服务端持有**）、小程序 `AppSecret`（换 `access_token`）。
5. 配置回调通知 URL（HTTPS 外网可访问）接收异步推送。
6. 微信侧配置 **IP 白名单**（调 `/xpay/*` 服务端接口必需）。

> `appKey` 有**沙箱 / 现网两套**，按 `env` 取用：现网 `env=0`，沙箱 `env=1`。
>
> **概念澄清：沙箱 vs 现网**（本篇多处引用，先统一认知再往下读）：
>
> | 环境 | `env` | 是什么 | 特征 |
> | ---- | ---- | ------ | ---- |
> | 沙箱 | `1` | 微信隔离测试环境 | 模拟真实「下单 → 回调 → 发货」全流程，**不产生真实资金交易、不碰真实用户数据**；联调、异常分支、压测都在这边做，随便造数、反复重试都不影响线上 |
> | 现网 | `0` | 真实生产环境 | 跑真实用户、真实资金、真实订单，任何疏漏都是真金白银 |
>
> - 两套 `appKey` 与订单数据**必须物理隔离**：收到沙箱推送（`Env=1`）一律不得发放到现网资产表，否则测试单会污染真实账本（见第八节「回调真实性校验」）。
> - ⚠️ **Apple 支付不支持沙箱**，iOS 只能在现网小流量实测，且会产生技术服务费——这是 iOS 链路要格外小心的原因之一（见避坑清单第 10 条）。

## 四、方案 A：道具直购（固定套餐）

### 1. 业务流程

```
① 前端 wx.login 拿 code 传给后端
   ↓
② 后端 auth.code2Session 换 openid + session_key
   ↓
③ 后端生成唯一商户订单号 outTradeNo
   ↓
④ 构造 signData（紧凑 JSON 字符串，字段按字典序）
   ↓
⑤ 后端生成两个签名（禁止前端算签）
     paySig    = HMAC-SHA256(appKey,      "requestVirtualPayment" + "&" + signData)
     signature = HMAC-SHA256(session_key, signData)
   ↓
⑥ 返回 signData / paySig / signature / mode 给前端
   ↓
⑦ 前端 wx.requestVirtualPayment 唤起支付（内部完成下单 + 拉起）
   ↓
⑧ 微信异步推送 xpay_goods_deliver_notify → 校验 → 发放资产
   ↓
⑨ 返回 {"ErrCode":0,"ErrMsg":"success"}
```

> 接口名是 `code2Session`（`auth.code2Session`），不是 `jscode2session`。

### 2. signData 字段

以**官方文档现行版**为准：

```json
{
  "offerId": "12345678",
  "buyQuantity": 1,
  "currencyType": "CNY",
  "env": 0,
  "productId": "pkg_chat_50",
  "goodsPrice": 9900,
  "outTradeNo": "R20260828XXXX",
  "attach": "{\"packageId\":1}"
}
```

| 字段 | 必填 | 说明 |
| ---- | ---- | ---- |
| `offerId` | ✅ | MP 基础配置中的 offerId，**字符串类型** |
| `buyQuantity` | ✅ | 购买数量 |
| `currencyType` | ✅ | 目前只能填 `CNY` |
| `env` | ❌ | `0` 现网（默认）、`1` 沙箱 |
| `productId` | 道具直购必填 | 道具 ID，需已发布到现网 |
| `goodsPrice` | 道具直购必填 | 单价（**分**），与后台发布价不一致报 `-15013` |
| `activitySellingPrice` | ❌ | 优惠价（分），需与 `goodsPrice` 一起传 |
| `outTradeNo` | ✅ | 8–32 字符，仅数字/大小写字母/`_-|*@`，**不能以下划线开头** |
| `attach` | ✅ | 透传 JSON，回调时原样返回 |

> ⚠️ **字段版本提醒**：网上流传的资料里有时会出现 `timestamp` / `nonceStr` / `totalFee` 这类 signData 字段，**它们是米大师旧版（`/cgi-bin/midas/*`）的字段，不在现行 `wx.requestVirtualPayment` 文档中**。接入时以官方文档为准，否则会报 `-15016 signData 格式有问题`。
>
> ⚠️ **逐字节一致**：签名用的字符串与最终传给前端的 `signData` 必须完全一致，前端**禁止 `JSON.parse` 后再 `stringify`**（字段顺序变了就报 `-15006`）。

### 3. 多套餐配置方案

一个道具可以一次性发放**多项权益**（问答次数 + 语音时长）。

⚠️ **一次下单只能购买单个道具**，不支持购物车 / 一次支付买多个商品。想要「组合礼包」就单独建一个组合道具。

**本地商品权益配置表**（`recharge_package`）：

| product_id | 名称 | 售价 | 权益 |
| ---------- | ---- | ---- | ---- |
| `pkg_chat_50` | 问答 50 次包 | ¥9.9 | `AI_CHAT_COUNT +50` |
| `pkg_voice_30` | 语音 30 分钟包 | ¥29.9 | `INTERVIEW_MINUTES +30` |
| `pkg_bundle` | 尊享组合包 | ¥59.9 | `AI_CHAT_COUNT +100`、`INTERVIEW_MINUTES +60` |

```sql
CREATE TABLE recharge_package (
  id              BIGINT PRIMARY KEY,
  product_id      VARCHAR(64) NOT NULL UNIQUE COMMENT '微信侧道具ID',
  name            VARCHAR(128) NOT NULL,
  price_fen       INT NOT NULL COMMENT '售价(分)，需与微信后台一致',
  asset_rules     JSON NOT NULL COMMENT '[{"assetType":"AI_CHAT_COUNT","amount":50}]',
  status          TINYINT NOT NULL DEFAULT 1 COMMENT '1上架 0下架',
  created_at      DATETIME NOT NULL,
  updated_at      DATETIME NOT NULL
);
```

好处：**一份回调代码兼容全部套餐**，新增档位只改配置表 + 微信后台建道具，不改发放逻辑。

### 4. 道具直购的局限

- 无法实现用户自由输入任意语音分钟数，价格固定。
- 新增档位需要后台新建道具 + **提交微信审核**，发布后约 10 分钟生效（`-15014`）。
- 适合档位数量少的固定套餐。

## 五、方案 B：代币模式（自定义时长必选）

### 1. 整体链路

```
① 现金充值代币（固定充值档位，走虚拟支付道具）→ 微信托管代币余额
   ↓
② 用户输入自定义语音时长 N 分钟
   ↓
③ 后端查兑换配置表 → 计算所需代币 = N × 每分钟代币（向上取整）
   ↓
④ 调 /xpay/currency_pay 扣减代币
   ↓
⑤ 扣费成功 → 本地 user_asset 增加时长/次数 → 写 user_asset_log
   扣费失败 → 提示余额不足，不发放
```

### 2. 两套账本必须分开

| 账本 | 存储方 | 内容 |
| ---- | ------ | ---- |
| **微信账本** | 微信托管 | 代币余额（现金价值） |
| **本地账本** | 业务库 `user_asset` | 语音剩余分钟 `INTERVIEW_MINUTES`、问答剩余次数 `AI_CHAT_COUNT` |

> 代币余额 ≠ 语音分钟。代币是「钱」，分钟是「权益」，两者通过兑换配置表关联。

### 3. 代币充值档位配置建议

- 兑换比例建议 **1 元 = 100 代币**（精度到分，**上线后永不修改**）。
- 充值档位只需少量固定档（如 ¥6 / ¥30 / ¥98）。
- **后期新增时长档位无需微信审核**，只改后端兑换配置表。

### 4. 兑换自定义时长

```
用户输入 N = 17 分钟
  ↓
查配置表：语音 1 分钟 = 8 代币
  ↓
所需代币 = ceil(17 × 8) = 136
  ↓
查用户代币余额：/xpay/query_user_balance
  ↓
余额充足 → 调扣费接口
```

扣减代币接口（**参数以官方文档为准**）：

```http
POST https://api.weixin.qq.com/xpay/currency_pay
     ?access_token=ACCESS_TOKEN
     &signature=SIGNATURE
     &pay_sig=PAY_SIG

{
  "openid": "oXXXX",
  "env": 0,
  "user_ip": "1.2.3.4",
  "amount": 136,
  "order_id": "CP20260828XXXX",
  "payitem": "[{\"productid\":\"voice_minute\",\"unit_price\":8,\"quantity\":17}]",
  "remark": "兑换语音17分钟"
}
```

| 参数 | 说明 |
| ---- | ---- |
| `amount` | 扣减的代币数量（**不是 `coin_cnt`**） |
| `order_id` | 扣费流水号（**不是 `out_trade_no`**） |
| `user_ip` | 用户 IP |
| `payitem` | 物品信息，记录到账户流水，JSON 字符串 |
| `remark` | 备注 |

> ⚠️ 三个凭证都要传：`access_token`（接口凭证）+ `signature`（用户态签名，`HMAC-SHA256(session_key, body)`）+ `pay_sig`（支付签名，`HMAC-SHA256(appKey, "/xpay/currency_pay" + "&" + body)`）。
>
> 返回 `errcode`：`0` 成功；`268490004` 重复操作（表示之前已成功，按成功处理）；`268490006` 余额不足；`268490009` `session_key` 过期。

返回值含 `balance`（总余额）与 `used_present_amount`（使用赠送代币的数量）。

### 5. 代币相关回调

| Event | 官方定义 |
| ----- | -------- |
| `xpay_goods_deliver_notify` | 道具发货推送（现金购买道具并支付成功） |
| `xpay_coin_pay_notify` | 代币支付推送，**用户代币扣减成功后** |
| `xpay_refund_notify` | 退款完成 |
| `xpay_complaint_notify` | 用户投诉 |

> ⚠️ 注意区分：`xpay_coin_pay_notify` 官方定义是「**代币扣减**成功」，不是「现金充值代币到账」。它的报文里同时含 `WeChatPayInfo`（MchOrderNo / TransactionId / PaidTime）和 `CoinInfo`（Quantity / OrigPrice / ActualPrice / Attach），具体在现金充值链路中的触发时机**建议用沙箱实测确认**，不要仅凭资料推断。

### 6. 扣费失败回滚

扣代币成功后必须保证本地时长入库成功。若本地写库失败：

1. 重试本地写入；
2. 仍失败则调 `/xpay/cancel_currency_pay` **撤销扣费**，回滚代币余额，避免用户「钱扣了没拿到时长」。

> 用 `coin_pay_record` 表记录每次扣费流水，`order_id` 唯一，作为回滚与对账依据。

## 六、关键决策：代币能不能直接当作语音分钟？

### 结论：业务上可以「1 代币 = 1 分钟」，但**底层账本绝不能合并**。

### 风险

代币兑换比例**上线后不可修改**。若把代币直接当分钟用，后期调价（如改成 2 代币 = 1 分钟）会让已充值用户的老资产全部错乱——因为你无法区分用户手上的代币是哪一版比例充的。

### 推荐方案

| 项 | 做法 |
| -- | ---- |
| 代币定位 | 永远代表**现金价值**，1 元 = 100 代币，**固定不变** |
| 兑换比率 | 每分钟语音 / 每次问答消耗多少代币，放**后端本地配置表，随时可调** |
| 用户感知 | 代币余额对前端隐藏，只展示「剩余语音时长 / 问答次数」 |

兑换配置表（`coin_exchange_rule`）：

| 权益类型 | 消耗代币 |
| -------- | -------- |
| 语音 1 分钟 | 8 |
| 问答 1 次 | 5 |

```sql
CREATE TABLE coin_exchange_rule (
  id            BIGINT PRIMARY KEY,
  asset_type    VARCHAR(32)  NOT NULL COMMENT 'INTERVIEW_MINUTES / AI_CHAT_COUNT',
  coin_per_unit INT          NOT NULL COMMENT '每单位消耗代币数',
  round_mode    VARCHAR(16)  NOT NULL DEFAULT 'CEIL' COMMENT '取整方式',
  status        TINYINT      NOT NULL DEFAULT 1,
  updated_at    DATETIME     NOT NULL
);
```

调价时只改这张表，用户已充值的代币价值不受影响。

### 缺陷

语音通话会产生非整数时长（3 分 20 秒），而代币只支持整数扣费，需要**向上取整**。多扣的部分在下次通话时通过「剩余秒数」抵扣，或被取整规则吃掉——需在产品上明确说明（如「不足 1 分钟按 1 分钟计」）。

## 七、数据库设计

### 1. 复用现有资产体系（不新建余额表）

项目已有（见 [AI问答计费-资产扣减方案](./AI问答计费-资产扣减方案.md)）：

```sql
user_asset        -- 用户资产余额（asset_type + balance + version）
user_asset_log    -- 资产变动流水（change_type: CONSUME / RECHARGE / GIVE）
```

资产类型：`AI_CHAT_COUNT`、`INTERVIEW_MINUTES`、`VIP_DAYS`。

> ⚠️ **不要**再建 `user_quota`（`chat_remain` / `voice_minute_remain`）这类单表——它与 `user_asset` 重复，会导致两处余额不一致。新增权益类型时直接加 `asset_type` 即可。

### 2. 充值订单表 `recharge_order`

```sql
CREATE TABLE recharge_order (
  id             BIGINT PRIMARY KEY,
  out_trade_no   VARCHAR(64)  NOT NULL UNIQUE COMMENT '商户订单号',
  user_uid       VARCHAR(64)  NOT NULL,
  openid         VARCHAR(64)  NOT NULL,
  product_id     VARCHAR(64)  NOT NULL COMMENT '微信侧道具ID',
  offer_id       VARCHAR(32)  NOT NULL,
  total_fee      INT          NOT NULL COMMENT '金额(分)',
  channel        VARCHAR(32)  NOT NULL COMMENT 'WECHAT_VIRTUAL / WECHAT',
  pay_status     TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已退款 3已过期',
  asset_granted  TINYINT      NOT NULL DEFAULT 0 COMMENT '资产是否已发放(幂等标记)',
  attach         VARCHAR(512) COMMENT '透传权益JSON快照',
  wx_transaction_id VARCHAR(64) COMMENT '微信支付订单号',
  env            TINYINT      NOT NULL DEFAULT 0 COMMENT '0现网 1沙箱',
  paid_at        DATETIME,
  created_at     DATETIME NOT NULL,
  updated_at     DATETIME NOT NULL,
  INDEX idx_user (user_uid),
  INDEX idx_status (pay_status, asset_granted)
);
```

> `asset_rules` 建议**快照进 `attach`**，避免套餐后续改权益导致历史订单发放错误——与 JSAPI 笔记里「礼包快照」同理。

### 3. 代币扣费流水表 `coin_pay_record`

```sql
CREATE TABLE coin_pay_record (
  id             BIGINT PRIMARY KEY,
  order_id       VARCHAR(64) NOT NULL UNIQUE COMMENT '扣费流水号',
  user_uid       VARCHAR(64) NOT NULL,
  openid         VARCHAR(64) NOT NULL,
  coin_cnt       INT         NOT NULL COMMENT '消耗代币数',
  exchange_type  VARCHAR(32) NOT NULL COMMENT 'voice / chat',
  exchange_num   INT         NOT NULL COMMENT '兑换时长(分钟)或次数',
  status         TINYINT     NOT NULL DEFAULT 0 COMMENT '0处理中 1成功 2已撤销',
  wx_balance     INT         COMMENT '扣费后微信侧代币余额',
  created_at     DATETIME NOT NULL,
  updated_at     DATETIME NOT NULL,
  INDEX idx_user (user_uid)
);
```

### 4. 补充：配置表

- `recharge_package`：道具套餐 → 权益规则（第四节）
- `coin_exchange_rule`：代币兑换比率（第六节）

### 5. 发放流程落地到资产表

```
回调 xpay_goods_deliver_notify
   ↓
校验订单真实性（见第八节）
   ↓
CAS 抢占：update recharge_order set asset_granted=1 where out_trade_no=? and asset_granted=0
   ↓ 影响行数=0 → 已发放，直接返回成功
解析 attach 里的权益快照
   ↓
逐项：update user_asset set balance=balance+? where user_uid=? and asset_type=?
   ↓
写 user_asset_log（change_type=RECHARGE, biz_type=RECHARGE, biz_id=order_no）
```

与扣减侧共用 `user_asset_log`，一条流水链完整可追溯。

## 八、兜底与可靠性（必须实现）

### 1. 支付结果不能依赖前端回调

前端 `wx.requestVirtualPayment` 的 `success` **不等于付款成功**，且该回调**可能丢失**（微信异常退出）。

### 2. 双链路校验

| 链路 | 方式 |
| ---- | ---- |
| 主链路 | 微信异步推送 `xpay_goods_deliver_notify` |
| 兜底链路 | 定时任务主动调 `/xpay/query_order`，扫描「已下单未确认」的订单 |

两者缺一不可，否则会出现**用户付了钱但不到账**。

### 3. 幂等

所有发货、扣代币业务必须幂等：

- 发放：`recharge_order.asset_granted` 原子更新抢占（CAS）。
- 扣币：`coin_pay_record.order_id` 唯一约束 + 状态机；微信侧返回 `268490004`（重复操作）按成功处理。

> 微信明确说明 `outTradeNo` 极端情况下不保证唯一，**幂等必须靠自己的标记位**。

### 4. 回调真实性校验

虚拟支付的消息推送走小程序消息通道，**没有 APIv3 那样的 RSA 验签**。可用的防护手段：

1. 校验 `ToUserName` 等于自己的小程序原始 ID；
2. 校验 `FromUserName`——道具发货场景固定为微信官方 openid；
3. 校验 `Env`：沙箱（`1`）的推送不得发放到现网；
4. **最可靠**：收到推送后调 `/xpay/query_order` 反向确认订单真实存在且已支付，再发货。这一步同时兜住了伪造与数据不一致。

### 5. 刷新计费缓存

若语音计时扣费走 Redis 实时余额（见 [websocket计时扣费](./websocket计时扣费.md)），发放资产后必须**同步刷新 Redis 缓存**，否则用户刚充完值、通话中仍提示余额不足。

## 九、避坑清单

1. iOS 线上虚拟服务**严禁**走普通微信支付，必须 XPay 虚拟支付，否则苹果 IAP 审核被拒。
2. `session_key`、`appKey` **严禁下发前端**；签名全部后端生成。
3. `signData` 用于签名的 JSON 字符串**不能带多余空格换行**，且必须与前端传入的**逐字节一致**。
4. 回调必须返回微信要求的 JSON（`{"ErrCode":0,"ErrMsg":"success"}`），**不能返回 HTML**，否则重推 15 次。
5. 代币兑换比例**一旦保存永久不可修改**，上线前仔细核算。
6. 用户时长、次数**严禁只放前端缓存**，以后端数据库为准。
7. 扣代币成功后必须保证本地时长入库成功；失败要 `cancel_currency_pay` 回滚。
8. `outTradeNo` 规则：8–32 位、限定字符集、**不能以 `_` 开头**。
9. 新增套餐档位需微信审核，发布后约 10 分钟才生效（`-15014`）。
10. Apple 支付**不支持沙箱**，现网测试会产生技术服务费。
11. iOS 退款问询需 **3 秒内**应答，否则退款决定权交给苹果（详见协议篇第九节）。
