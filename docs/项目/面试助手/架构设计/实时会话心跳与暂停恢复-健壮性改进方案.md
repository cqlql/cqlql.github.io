# 实时会话心跳与暂停恢复：健壮性改进方案

> **文档定位：待办 / 风险记录。**
> 记录当前 `pass-up.backend` 实时会话链路中**已识别、但尚未实施**的健壮性改进项，供后续排期取用。
> 所有"现状"均以当前代码为准；"建议方向"为设想，未落地。

## 1. 背景与范围

实时面试会话（`/ws/audio`）当前具备两项自愈能力：

1. **ASR 内层重连**：豆包 ASR 连接中断后由 `AudioStreamSession#consumeLoop` 自动重建，对前端无感。
2. **暂停 / 逻辑会话重连**：用户主动暂停或断线后，逻辑会话（`InterviewSessionState`）保留 15 分钟，前端凭 `resume=<逻辑会话ID>` 重连复用。

本文档聚焦上述机制在 **超时设置、进程容灾、内存态一致性** 三方面的不足。

## 2. 现状速览

| 机制 | 代码位置 | 当前值 | 可配置 |
| :--- | :--- | :--- | :--- |
| 活跃连接心跳超时 | `WsHeartbeatScheduler#HEARTBEAT_TIMEOUT_MS` | 5 分钟 | 否（硬编码） |
| 心跳扫描周期 | `WsHeartbeatScheduler` `@Scheduled(fixedDelay)` | 30 秒 | 否 |
| 暂停会话保留时长 | `AudioStreamingService#PAUSED_TTL_MS` | 15 分钟 | 否（硬编码） |
| pending 面试回收时长 | `AudioStreamingService#PENDING_TTL_MS` | 3 分钟 | 否（硬编码） |
| ASR 重连参数 | `AudioStreamSession` | 3 次 / 500ms~3s 退避 | 否 |

关键事实：

- 心跳**不是独立 ping/pong**，而是"寄生"在业务消息上：仅 `onOpen` / `receiveAudio` / `receiveText` 刷新 `AudioStreamSession#lastHeartbeatTime`（`AudioStreamingService` 中调用 `refreshHeartbeat`）。
- 逻辑会话 `logicalSessions` 是 `AudioStreamingService` 内的 `ConcurrentHashMap`，**纯 JVM 内存**，不落库。

---

## 3. 待改进项

### P1｜暂停会话为纯内存态，进程重启即不可恢复

**现状**

- 逻辑会话（含 `systemPrompt`、对话 `context`、`interviewId`）只存在于 `AudioStreamingService#logicalSessions`（内存）。
- 暂停落库的只有 `Interview.status='paused'`（`InterviewRepository#pauseInterview`），**不含上下文**。

**问题 / 影响**

1. 进程重启 / 发版后内存清空 → 用户 15 分钟内重连也会 `RESUME_EXPIRED`（`AudioStreamingService` 重连分支 `logicalSessions.get(resumeSessionId) == null`），恢复失败。
2. 数据库 `paused` 记录可能**永久悬挂**：回收逻辑 `evictExpiredPausedSessions()` 是遍历内存 map 触发 `InterviewEndedEvent`；重启后 map 为空，无人再把该记录置为 `ended`。

**建议方向**

- 将逻辑会话（至少 `systemPrompt` + 上下文摘要 + `interviewId`）持久化到 Redis（可复用计费侧 `interview:session:user:{userId}` 的成熟范式），重连时优先从持久化层重建。
- 增加"DB 悬挂 `paused` 记录"兜底回收任务（按超时时间分批置为 `ended` + `SESSION_EXPIRED`）。
- 可与 [实时面试会话重构-领域事件解耦](实时面试会话重构-领域事件解耦.md) 第 8 节"计费状态与逻辑会话状态机统一快照"合并设计。

**涉及文件**：`AudioStreamingService`、`InterviewSessionState`、`InterviewRepository`、`InterviewBillingService`

---

### P2｜心跳超时 5 分钟偏长，存在死连接计费泄漏

**现状**

- `HEARTBEAT_TIMEOUT_MS = 5 分钟`，叠加 30 秒扫描周期 → 最坏约 5.5 分钟才踢出。
- 心跳仅由业务消息刷新，无独立 ping。

**问题 1：依赖前端持续推帧（需先验证）**

- 若前端持续推流（含静音帧；AGENTS.md §4.2 记载空闲 3 秒补发静音帧），心跳始终新鲜，5 分钟不会误杀。
- 若前端为 VAD / 按键说话（仅说话时推帧），用户静默思考 >5 分钟会被误判失联、踢掉健康会话。
- **行动项：先确认前端音频推流策略，再定阈值。**

**问题 2：半开连接计费泄漏（已核实）**

- 优雅关闭（收到关闭帧）会立即触发 `onClose` → 停止计费，**无泄漏**。
- 半开连接（移动网络掉线、进程被杀等无关闭帧）下，后端内存中会话仍为 `ACTIVE`，计费侧两道防线均无法拦截：
  - `InterviewBillingScheduler#SILENCE_TIMEOUT_MS`（30 秒"幽灵会话"检查）**不起作用**——它比较的 Redis `lastHeartbeatTime` 实为"扣费基准"，由计费任务自身每次 `doBilling` 刷新（约每 10 秒），并非连接活跃度。
  - `AudioStreamingService#hasActiveStreamSession` 依赖 `WebSocketSession#isOpen()`，半开连接仍返回 `true`。
- **结果：直到 5 分钟心跳踢出前持续计费，最多约 5 分钟时长被误扣。**

**建议方向**

- 优选：引入**应用层独立心跳**（前端定时发轻量文本 ping，或利用 WebSocket 原生 ping frame），超时设 **30~60 秒**。与音频解耦，既能秒级发现死连接、及时停止计费，又不会因"用户安静思考"误杀。
- 退选（不引入 ping）：将超时缩短至 **60~120 秒**，并在注释标明"依赖前端持续推帧"。
- 修正计费侧 `SILENCE_TIMEOUT_MS` 语义：应基于真实连接活跃度（或让 WebSocket 消息刷新的基准参与判定），而非自刷新的扣费基准。

**涉及文件**：`WsHeartbeatScheduler`、`AudioStreamSession`、`AudioStreamingService`、`InterviewBillingScheduler`、`InterviewBillingService`

---

### P3｜超时参数硬编码，不可按环境调整

**现状**：`HEARTBEAT_TIMEOUT_MS`、`PAUSED_TTL_MS`、`PENDING_TTL_MS`、ASR 重连参数均为 private static 常量；项目无 `RealtimeProperties`（当前配置仅 `realtime.resume-context.*`）。

**建议方向**：抽取 `@ConfigurationProperties(prefix = "realtime")`，外置为 `realtime.heartbeat-timeout-ms`、`realtime.paused-ttl-ms`、`realtime.pending-ttl-ms` 等，提供安全默认值并加校验注释（如 `paused-ttl` 必须大于前端"暂停 → 重连"的预期最大间隔）。

**涉及文件**：新增 `RealtimeProperties`；改造 `WsHeartbeatScheduler`、`AudioStreamingService`

---

## 4. 优先级建议

| 优先级 | 项 | 理由 | 预估工作量 |
| :--- | :--- | :--- | :--- |
| P1 | 暂停会话持久化 | 架构级，影响容灾与数据一致性 | 中（持久化 + 重建 + 兜底任务） |
| P2 | 独立心跳 + 缩短超时 | 直接影响计费准确性与用户体验 | 中（前端需配合） |
| P3 | 超时配置外置 | 运维可调性，低风险 | 低 |

## 5. 待验证假设

1. 前端音频推流策略：持续推帧 还是 仅说话时推帧？（决定 P2 阈值与误杀风险）
2. 生产日志是否出现 `RESUME_EXPIRED` / `重连失败：逻辑会话不存在或已过期`？出现即证实 P1 已造成真实恢复失败。
3. 是否发生过"用户被多扣费"且时间点与网络掉线吻合？（印证 P2 计费泄漏）
