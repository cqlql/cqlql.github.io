# 实时会话心跳与暂停恢复：健壮性改进方案

> **文档定位：问题记录 + 目标架构 + 落地记录。**
> 记录 `pass-up.backend` 实时会话链路中识别到的健壮性改进项，给出最终架构边界，并保留每一项的**落地情况与验证证据**。
> 所有"现状"均以当时代码为准；每项都标注了「已实施 / 已证伪」，便于回溯当时的判断依据。
>
> **文档状态：本文记录的全部事项已闭环**（P0 / P0.1 / P1 / P2 含前端 / P2.1 / P3 / 测试与 CI）。
> 其中 P0 经历过一次修正 —— 本文早期版本把它判为「当前正在发生的缺陷」，**已用 curl 端到端实测证伪**
> （正常路径 cleanup 是收敛的）；它现在记录的是「判断错在哪、以及剩下哪个真实边界」，并已修复。

## 1. 背景与范围

实时面试会话（`/ws/audio`）当前具备两项自愈能力：

1. **ASR 内层重连**：豆包 ASR 连接中断后由 `AudioStreamSession#consumeLoop` 自动重建，对前端无感。
2. **暂停 / 逻辑会话重连**：用户主动暂停或断线后，逻辑会话（`InterviewSessionState`）保留 15 分钟，前端凭 `resume=<逻辑会话ID>` 重连复用。

本文档的核心不是"把某个超时从 5 分钟改成几分钟"，而是要把下面**四件目前被耦合在一起的事情彻底解耦**：

| 关注点 | 回答的问题 | 改造前载体 | 现状 |
| :--- | :--- | :--- | :--- |
| **连接存活检测** | 客户端还活着吗？ | 寄生在业务消息上的 `lastHeartbeatTime` | ✅ 独立心跳 + 音频兜底，自适应（P2） |
| **逻辑会话生命周期** | 这场面试（逻辑上）还在进行吗？ | JVM `logicalSessions` | ✅ 内存优先 + DB 兜底重建（P1） |
| **AI 上下文恢复** | 重连后 AI 还能接着上一句说吗？ | JVM `InterviewSessionState#context` | ✅ 内存优先 + 从 `interview_message` 恢复（P1） |
| **计费时间轴** | 该扣多少秒？ | Redis `lastHeartbeatTime`（扣费基准） | ✅ 与连接活跃度彻底分开（P2 / P2.1） |

四者混用同一套时间戳/内存结构，是本文多数问题的根源；P2 / P2.1 已把「连接存活」与「计费」拆开，P1 负责剩下的「逻辑会话生命周期」与「AI 上下文恢复」。

## 2. 现状速览

> 下表为**改造前**的取值，便于对照；改造后的取值见各 P 项。

| 机制 | 代码位置 | 改造前 | 现状 |
| :--- | :--- | :--- | :--- |
| 连接失联阈值（老客户端 / 音频判据） | `AudioStreamSession#AUDIO_IDLE_TIMEOUT_MS` | 5 分钟 | 5 分钟（不变，见 P2） |
| 连接失联阈值（声明心跳的客户端） | `AudioStreamSession#HEARTBEAT_TIMEOUT_MS` | — | **60 秒**（P2 新增） |
| 心跳扫描周期 | `WsHeartbeatScheduler` `@Scheduled(fixedDelay)` | 30 秒 | **10 秒**（P2） |
| 暂停会话保留时长 | `AudioStreamingService#PAUSED_TTL_MS` | 15 分钟 | 15 分钟 |
| pending 面试回收时长 | `AudioStreamingService#PENDING_TTL_MS` | 3 分钟 | 3 分钟 |
| ASR 重连参数 | `AudioStreamSession` | 3 次 / 500ms~3s 退避 | 不变 |
| 计费"失联"阈值 | `InterviewBillingScheduler#SILENCE_TIMEOUT_MS` | 30 秒（语义错误） | **已删除**，改用 `isConnectionLost()`（P2） |

关键事实（改造前）：

- 心跳**不是独立 ping/pong**，而是"寄生"在业务消息上：仅 `onOpen` / `receiveAudio` / `receiveText` 刷新 `AudioStreamSession#lastHeartbeatTime`（`AudioStreamingService` 中统一调用 `refreshHeartbeat`）。
- 逻辑会话 `logicalSessions` 是 `AudioStreamingService` 内的 `ConcurrentHashMap`，**纯 JVM 内存**，不落库。
- 但**对话内容本身是落库的**：`interview_message` 表按轮次全量记录 user/assistant 消息（异步写入），只是当前没有任何代码路径用它重建 AI 上下文。详见 P1「DB 现有的可重建原料」。
- 逻辑会话与物理连接**已经是两个对象**：`InterviewSessionState`（逻辑，跨暂停存活）与 `AudioStreamSession`（物理，一次连接一个），二者通过 `InterviewSessionState#currentConnectionId` 关联。这为后续拆分提供了现成基础。

## 3. 待改进项

> 排序说明：P0 与 P0.1 是「排查中发现的缺陷」（P0 经实测证伪）；P1 / P2 是架构级健壮性改造；P3 是工程治理。**均已完成。**

### P0｜强踢旧连接可能绕过统一 cleanup —— **实测证伪，仅剩边界场景**

> **结论先行：本文早期版本把这条判为"当前正在发生的 bug"，curl 端到端实测后已证伪。** 正常路径下 cleanup 是收敛的。剩下的只是一个窄边界场景，且已修复。

**曾经的判断（错误）**

`AudioStreamingService#onOpen` 强踢旧连接时，`close()` 之后紧跟 `streamSessions.remove(oldConnectionId)`：

```java
close(oldStreamSession.getSession(), CloseStatus.POLICY_VIOLATION);
streamSessions.remove(oldConnectionId);   // 原判断：这一行会让后续回调拿不到对象
```

推理依据是 `AudioStreamingService#onClose` 依赖 `streamSessions.remove()` 的返回值做守卫：

```java
AudioStreamSession streamingService = streamSessions.remove(session.getId());
if (streamingService != null) {
    streamingService.onClose();          // 只有 remove 拿到对象时才做业务清理
}
```

于是推出：先 remove → 回调拿到 `null` → `AudioStreamSession#onClose()` 永不执行 → 不发 `InterviewEndedEvent` → `interview` 悬挂 `active`。

**实测结果：不成立**

用 curl 建立两条 WebSocket 连接（A 活跃 + 手动写入 Redis 计费会话，再用 B 触发强踢）实测日志：

```text
12:05:20.550 [mcat-handler-5] 正在强踢旧会话 logicalSessionId=e3717fdd..., connectionId=e3717fdd...
12:05:20.550 [mcat-handler-5] 主动关闭: sessionId=e3717fdd..., status=CloseStatus[code=1008]
12:05:20.555 [mcat-handler-5] [音频会话] 会话关闭: connectionId=e3717fdd...   ← onClose 执行了
12:05:20.556 [mcat-handler-5] 已关闭: sessionId=e3717fdd...
```

**同一个线程（`mcat-handler-5`）**、`close()` 之后 5ms 内，`AudioStreamSession#onClose()` 就已经跑完了。原因是：**Tomcat 会在 `session.close(status)` 内部同步回调 `afterConnectionClosed`**，也就是回调发生在 `streamSessions.remove(oldConnectionId)` 这一行**之前**。等 onOpen 执行到那行时，条目早已被回调摘掉，`remove` 是个 no-op。

**因此**：`streamSessions.remove(oldConnectionId)` 在正常路径下是冗余代码，而不是"抢先摘除"。原判断把「异步回调」当成了前提，实际是同步的。

**残留的真实边界（这才是该修的部分）**

`close()` 有两种情况不会触发回调，此时那行 `remove` 就真的变成了"抢先摘除"：

| 情况 | 代码路径 | 后果 |
| :--- | :--- | :--- |
| `session.close()` 抛异常 | `close()` 内 catch 掉，继续执行 `remove` | 条目被摘掉，回调即使稍后到达也拿不到对象 |
| `session.isOpen()` 为 false | `close()` 直接 no-op，继续执行 `remove` | 同上 |

一旦条目被摘掉，**心跳扫描（`evictDeadSessions` 遍历 `streamSessions`）也再也扫不到它**，于是：

1. `logicalSessions` 永久残留一条 **ACTIVE** 记录（`evictExpiredPausedSessions()` 只回收 `PAUSED`），直到进程重启；
2. `interview` 停在 `active`（`forceTerminateActiveSession` 只结计费 + 删 Redis key，**不发布 `InterviewEndedEvent`**，所以 `endInterview()` 不会被调用）。

**已实施的修复（1 行）**

删除那行 `remove`，只保留"请求关闭"：

```java
// 只「请求关闭」，不在此处摘除 streamSessions：
// 容器会在 close() 内部同步回调 afterConnectionClosed → onClose()，由它统一完成
// 「摘除注册表 + 业务清理」。若在此抢先 remove，一旦 close 抛异常 / 连接已关闭导致
// 回调不到达，条目已被摘掉，心跳扫描就再也扫不到它。
close(oldStreamSession.getSession(), CloseStatus.POLICY_VIOLATION);
```

修复后语义：**onOpen 只负责请求关闭；摘除与业务清理统一交给关闭回调；回调没来就由心跳扫描兜底。** 这正是 §4 原则一要的形态，且不依赖"回调是同步的"这个实现细节。

**验证**

- 新增单测 `onOpen_踢出旧会话时close失败_旧会话必须留在注册表以便心跳兜底回收`：把该行加回去 → 用例失败；删除 → 用例通过（已实测双向验证）。
- 端到端重跑：修复前后正常路径行为一致（A 的 `onClose()` 均执行，`interview` 均被正确清理），无回归。

**P0.1｜重连失败会留下「无物理连接的 ACTIVE」逻辑会话（已修）**

原判断里「`logicalSessions` 的 ACTIVE 僵尸没有任何回收路径」这半句是对的，顺着它往下追，找到了确切触发路径：

```java
// onOpen 重连分支
try {
    streamSession = sessionFactory.create(session, listener, interviewContext, resumeState);
} catch (RuntimeException e) {
    if (resumeState == null && ...) { endInterview(...); }   // ← 重连路径不回滚
    throw e;
}
```

失败点在 `AudioStreamSession` 构造函数**内部**，此时它已经执行过 `state.markActive()` + `state.bindConnection(新连接 ID)`，但该连接从未 `put` 进 `streamSessions`。触发条件不是臆想：构造函数里的 `publishResumed()` → `resumeBilling()` 要打 Redis，**Redis 抖动 / 连接池耗尽**即抛异常；executor 已关闭时 `submit()` 也会被拒。

一旦发生，逻辑会话停在 **ACTIVE** 且 `currentConnectionId` 指向一个不存在的连接：

| 回收路径 | 为什么扫不到 |
| :--- | :--- |
| `evictDeadSessions()` | 遍历 `streamSessions`，而它不在里面 |
| `evictExpiredPausedSessions()` | 要求 `isPaused()`，它是 ACTIVE |

→ 永久残留到进程重启（前端若用同一个 `resume=` 再连一次可以自愈，但用户不回来就一直占着）。

**修复**：`catch` 块里对重连路径补回滚 —— `resumeState.markPaused()`。`markPaused()` 只允许 `ACTIVE → PAUSED`，同时解绑悬空连接并重置计时，于是回到暂停 TTL 的回收范围内。

**验证**：新增单测 `onOpen_重连时物理会话创建失败_逻辑会话必须退回PAUSED待TTL回收`，桩件里复现构造函数已做的 `markActive()` + `bindConnection()` 再抛异常；**不加修复 → 断言失败（`expected: <true> but was: <false>`）；加上 → 通过**（双向实测）。

**另外一点仍成立**：`forceTerminateActiveSession` 不发布 `InterviewEndedEvent` —— 它只做「最后一次扣费 + 删 Redis key」。这正是上面边界场景会导致 `interview` 悬挂的原因。

**可复用的既有资产（留给 P1 / §4 原则三）**

`connectionId` 守卫这个模式**项目里已经写过了** —— `InterviewBillingService#stopBilling`：

```java
if (!currentSessionId.equals(sessionInfo.getSessionId())) {
    log.info("[面试计费] 跳过清理: 检测到新会话已覆盖，旧会话不予错杀...");
    return;
}
```

会话层若要做同类守卫（例如防旧连接 `onClose` 误杀 resume 后的新连接），照搬即可，不需要新设计。

**涉及文件**：`AudioStreamingService#onOpen`（已改）、`AudioStreamingServiceTest`（已修）

### P1｜逻辑会话仅存在 JVM 内存，进程重启后无法恢复

> 原标题为"暂停会话为纯内存态"，不够准确。真正的问题不是"暂停"这个动作，而是 `logicalSessions = ConcurrentHashMap` —— **只要 `InterviewSessionState` 在 JVM 内，无论 ACTIVE 还是 PAUSED，它本质都是运行态。**

**现状**

- 逻辑会话（含 `systemPrompt`、对话 `context`、`interviewId`、`resume/job` 快照引用）只存在于 `AudioStreamingService#logicalSessions`（内存）。
- 暂停只落状态：`InterviewRepository#pauseInterview` 仅把 `interview.status` 置为 `paused`，**不写任何上下文**。
- 但**对话内容本身在 DB 里是全的**。这一点必须先说清楚，否则容易误判为"只有靠 Redis 才能恢复"。

**DB 现有的可重建原料（已核实）**

| 数据 | 位置 | 说明 |
| :--- | :--- | :--- |
| 对话历史 | `interview_message`（V5 建表） | 每轮 user/assistant 全量落库，**不做裁剪**；字段 `role` / `content` / `created_at` |
| 逻辑会话 ID | `interview.session_id` | `activateInterview` 写入首次建连的 WebSocket sessionId，重连不更新 → 实际就是 logicalSessionId |
| 业务状态 | `interview.status` | pending / active / paused / ended |
| 面试快照 | `interview.resume_snapshot_json` / `job_snapshot_json` | 建连时固化的**裁剪后**简历与岗位，即 AI 实际看到的输入 |
| 面试参数 | `interview.mode` / `language` / `detail_level` / `interview_style` | 重连复用所需 |
| 读取接口 | `GET /api/interviews/{id}/messages` | 已用于历史详情展示；**目前没有任何代码路径用它重建 AI 上下文** |

消息写入链路：`AudioStreamSession#handleUserMessage / handleAssistantMessage` → `InterviewAsyncService#saveUserMessage / saveAssistantMessage` → `InterviewMessageService#saveMessage`（**线程池异步**）。

**问题 / 影响**

1. 进程重启 / 发版后内存清空 → 用户 15 分钟内重连也会 `RESUME_EXPIRED`（`AudioStreamingService` 重连分支 `logicalSessions.get(resumeSessionId) == null`），恢复失败。
2. 数据库 `paused` 记录可能**永久悬挂**：回收逻辑 `evictExpiredPausedSessions()` 是遍历内存 map 触发 `InterviewEndedEvent`；重启后 map 为空，无人再把该记录置为 `ended`。
3. **旧连接回调误杀新会话**（重启之外的真实风险，见 §4 原则三）：重连时新旧 `AudioStreamSession` **共享同一个 `InterviewSessionState` 对象**（`resumeState` 直接赋值给 `this.state`）。若旧连接的 `onClose()` 延迟到达且其 `paused` 标志未被置位，会执行 `state.markClosed()` → 迁入 `ENDED` + 发布 `InterviewEndedEvent`，**把新连接正在进行的面试直接终结**；随后 `AudioStreamingService#onClose` 因 `isEnded()` 为真，还会把 `logicalSessions` 中的条目一并删除。

**建议方向**

**（1）先纠正概念：不要把"Redis 持久化"等同于"会话持久化"。**

Redis 更准确的定位是 **逻辑会话运行态的持久化/恢复载体**；DB 中的 `Interview` 仍然是业务生命周期的**最终事实来源**。三层职责应明确分开：

```text
DB      = 面试业务事实（Interview）
Redis   = 可恢复的逻辑会话运行态（realtime:session:{sessionId}）
JVM Map = 当前进程的快速缓存（logicalSessions）
```

**（2）持久化对象是「最小可恢复运行态」，不是完整聊天历史。**

> 将 `InterviewSessionState` 的**最小可恢复运行态**持久化到 Redis，并设置与暂停生命周期一致的 TTL。Redis 不作为完整聊天历史存储，仅保存恢复 AI 会话所需的 `interviewId`、必要的 prompt/context 摘要及有限数量的最近消息；完整业务快照仍以 DB 为准。

这一定位有三个直接约束：

- **TTL 与暂停生命周期一致**：Redis key 的过期时间应等于 `PAUSED_TTL_MS`（当前 15 分钟），两者不可各写一套，否则会出现"逻辑会话已过期但 Redis 还在"或反之的中间态。
- **上下文有界**：Redis 只承载"够 AI 接着聊"的最小信息，不是消息归档。
- **但"最小"不等于"过度压缩"**：摘要压缩得太狠，恢复后同样会失忆：

```text
用户暂停 → JVM 重启 → Redis 恢复 → 重建 AI 会话
        → 上下文不完整 → AI「失忆」或前后逻辑不一致
```

因此 Redis 中的结构应至少覆盖：

```text
realtime:session:{sessionId}
├── interviewId
├── sessionId / logicalSessionId
├── systemPrompt
├── context              （有界，见下）
├── resume / job snapshot 引用
├── status               （ACTIVE / PAUSED）
├── createdAt
├── pausedAt
└── expireAt
```

```json
{
  "interviewId": "...",
  "status": "PAUSED",
  "systemPrompt": "...",
  "context": [],
  "pausedAt": "...",
  "expireAt": "..."
}
```

`context` 只保存**有限数量的最近消息**，沿用现有裁剪语义（`AudioStreamSession#MAX_CONTEXT = 50`，即最多保留 `MAX_CONTEXT * 2` 条消息）后落盘，更早的对话不回填。注意这里的有界是**刻意设计**，不是数据缺失：内存有上限，而 DB 的 `interview_message` 是**全量不裁剪**的，真要更早的内容，DB 才是唯一来源。`expireAt` 由 `PAUSED_TTL_MS` 统一推导，不单独配置。

> 更正：本文早前版本与 `AGENTS.md` §3.5 都写 `MAX_CONTEXT = 10`，实际代码是 **50**。

**（3）恢复链路必须是多级回退，而不是"Redis miss 即失败"。**

Redis 也不是永久数据源，必须显式定义降级：

```text
resumeSession(sessionId)
        │
        ├── JVM logicalSessions
        │       ↓ miss
        ├── DB interview + system_prompt + interview_message
        │       ↓ 尝试重建
        └── 无法恢复 → RESUME_EXPIRED
```

> **注**：这是设计初稿，当时以为还需要一层 Redis。实现时砍掉了 —— 理由见下文「P1 已完成」小节。

这比"Redis miss → RESUME_EXPIRED"健壮得多。关键前提是：**DB 是否真有足够的数据重建逻辑会话？** 结论是"基本够，但有三个缺口"，必须分能力说清楚，不能笼统地讲"DB 不够"：

| 能力 | 依赖数据 | DB 是否足够 |
| :--- | :--- | :--- |
| **业务会话可恢复** | `interview.status` + 快照 + 面试参数 | **是**，DB 完全够 |
| **AI 对话上下文可恢复** | 最近 N 轮 user/assistant | **是**，`interview_message` 全量在库 |
| **AI 会话精确复现** | 渲染后的 `systemPrompt` + 内存态标志位 | **否**，见下三个缺口 |

**DB 重建的三个真实缺口**

1. **异步落库的丢失窗口**：消息经 `InterviewAsyncService` 线程池异步写库，进程被 kill（非优雅关闭）时，队列中未落库的最后一两轮会丢。`@PreDestroy` 只在优雅关闭时等 30 秒，`kill -9` 完全兜不住。
2. **渲染后的 `systemPrompt` 不可复现**：DB 存的是快照**输入**（简历 / 岗位 JSON），不是 `buildSystemPrompt()` 的**输出**。提示词模板一改版，重建出的 systemPrompt 就与当时不同 → 恢复后 AI 的人设与规则可能漂移。
3. **内存态独有字段**：`initialQuestionSent`（MOCK 首问防重发）、`startedPublished`（计费起算幂等）、精确的 `lastActiveTime`。部分可由"有无消息"推断，但不显式、不可靠。

> 因此 Redis 的价值不是"唯一上下文来源"，而是 **保住不可由 DB 复现的运行态 + 免去重建成本**。也正因为 DB 重建是一条真能跑通的路径，§5.5 的多级回退才有意义，而不是纸面兜底。

**（4）兜底回收**：增加"DB 悬挂 `paused` 记录"清理任务（按超时时间分批置为 `ended` + `SESSION_EXPIRED`），不再依赖内存 map 遍历。

**（5）** 可与 [实时面试会话重构-领域事件解耦](实时面试会话重构-领域事件解耦.md) 第 8 节"计费状态与逻辑会话状态机统一快照"合并设计。

**恢复链路：实际只需要两级**

```text
resumeSession(sessionId)
  → JVM logicalSessions        （同进程，命中即用）
  → LogicalSessionRebuilder    （从 DB 重建）
  → RESUME_EXPIRED
```

原方案设计的是四级（JVM → Redis → DB → 失败），**最终砍掉了 Redis 那一级**：DB 已经具备重建一个完整 AI 会话的全部事实（V25 的 `system_prompt`、全量 `interview_message`、V24 的面试参数与快照），resume 又是低频操作（用户显式暂停后回来），多一次 DB 读完全可接受；再插一层 Redis 只会多一处不一致的可能。

**重建的关键判定**

| 判定 | 依据 | 失败码 |
| :--- | :--- | :--- |
| 记录是否存在 | `interview.session_id = 逻辑会话ID` | `RESUME_EXPIRED` |
| 归属是否匹配 | `interview.user_id` | `RESUME_FORBIDDEN` |
| 状态是否可恢复 | `paused` / `active`（`pending` / `ended` 不可） | `RESUME_EXPIRED` |
| 暂停是否超时 | **`interview.paused_at` + `PAUSED_TTL_MS`**（不依赖内存 `lastActiveTime`） | `RESUME_EXPIRED` |

> 老数据 `paused_at` 为 NULL 时按**不可恢复**处理：无法判定就不放行。

**重建时按需推导的两个内存态标志**

- `initialQuestionSent`（MOCK 首问防重发）：按"历史消息里有没有 assistant 消息"推导 —— 有就说明 AI 面试官已经开过场。
- `startedPublished`（计费起算幂等）：**不从 DB 推导**，由 `startBilling` 的幂等守卫兜住（见上文坑 2）。

**两个刻意的设计选择**

1. **按需重建，不做启动预热**：预热要为所有暂停会话常驻内存，还要处理"预热期间又来连接"的竞态，而收益只在用户真的回来时才体现。
2. **建连成功后才登记注册表**：重建态在 `sessionFactory.create()` 成功之后才 `logicalSessions.put()`。若建连失败就不登记 —— 否则会留下「无物理连接的 ACTIVE」僵尸（P0.1 那类问题）。

**涉及文件**：`LogicalSessionRebuilder`（新增）、`InterviewSessionState`（新增 `restoreContext` / `markInitialQuestionSent`）、`InterviewMessageRepository`（新增倒序分页查询）、`AudioStreamingService#onOpen`

上面缺口 2 的解法**不是**"把 systemPrompt 塞进 Redis"，而是**在 `interview` 表新增一列**：

```sql
ALTER TABLE interview ADD COLUMN system_prompt TEXT;
COMMENT ON COLUMN interview.system_prompt IS
  '建连时渲染后的系统提示词快照（AI 实际看到的完整 prompt）。写一次、永不更新；'
  '提示词模板改版也不回填历史行，否则历史复盘会漂移';
```

**为什么落 DB 而不是 Redis**

1. 它是**一次生成、永不改变的事实**，不是运行态。Redis 是缓存 —— 把不可变事实放缓存里，事实就可能丢。
2. 这是 V24 既有决策的同一原则往下推一格：V24 存的是 AI 实际看到的**输入**（裁剪后简历/岗位），而 systemPrompt 是 AI 实际看到的**东西本身**。既然"输入"都冻结了，"输出"更没有理由靠重算（重算依赖模板版本，一改版就漂移）。
3. **它让 DB 单独就能重建完整 AI 会话** —— 多级回退的第三级从"近似兜底"变成**完整路径**，Redis 随之从"必需持久化层"降级为"可选加速缓存"。P1 的形状因此显著简化。

**具体约束**

- **独立列**，不要塞进 `resume_snapshot_json`（那是"输入"，混进去破坏该列语义）。
- 建连时**一次写入，永不更新**；模板改版**不回填**历史行。
- 老行该列为 `NULL` → 恢复时回退到"用快照重算"（接受漂移）。天然渐进，无需数据迁移。
- Redis 里**先不放**：少一处不一致的可能；resume 频率低，多一次 DB 读完全可接受，等有性能问题再加缓存。
- 体积：实测模板输入 `resume_json` 3176B + `job_context_json` 349B，裁剪后快照约 2964 字符 → 渲染后 prompt 约 **3.5~4 KB**，与现有快照列同量级（`interview_message` 才是大头）。

**代价：写入时机需要一次重构（纯搬家，不改行为）**

`buildSystemPrompt()` 目前在 `AudioStreamSession` **构造函数**里执行，而面试记录在那之前就已创建。要落库需二选一：

- **(a) 推荐**：把提示词构建提到 `InterviewPrepareService`（建连准备阶段），随快照一起落库，再经 `InterviewContext` 传给会话。顺带把"纯函数式的提示词构建"从会话类挪到准备阶段，职责更合理。
- (b) 会话构造完再回写 DB：多一次 UPDATE，且有"构造成功但回写失败"的窗口。

**另外两个必须先解决的坑（否则会返工）—— 均已修**

1. **`interview` 表没有 `paused_at` 列**（V15 只改了 status 约束）。所以上面的"兜底回收 DB 悬挂 paused 记录"光有任务不够 —— 没有 `paused_at` 就无法按 TTL 判定，只能拿 `created_at` / `start_time` 猜。
   **已修**：V25 加列；`pauseInterview` 写入、`resumeInterview` 清空；新增 `InterviewRepository#endExpiredPaused` + `AudioStreamingService#evictExpiredPausedInterviews`，由 `WsHeartbeatScheduler` 每轮调用。
   与内存路径互不冲突（已被内存路径结束的记录 status 已是 ended，不会命中条件），且刻意**不发布** `InterviewEndedEvent` —— 这些记录本就没有活跃连接，计费侧由连接失联判断兜底结算。
2. **`startedPublished`（计费起算幂等）无法从 DB 推导**。重启后逻辑会话从 DB 重建，该标志默认 `false`；用户 resume 时 ASR ready 会再次 `publishStarted()` → `startBilling()` → **用新的起算点覆盖 Redis 计费会话，用户已用时长被清零**。这是真会踩的坑。
   **已修**：`InterviewBillingService#startBilling` 加幂等守卫 —— Redis 中已有计费会话时直接跳过并告警，绝不覆盖。
   正常"新面试顶替旧面试"不受影响（`onOpen` 已先 `forceTerminateActiveSession` 删掉旧 key）；残留 key 会被计费调度器的连接失联判断在约 10 秒内清掉。

**涉及文件**：`AudioStreamingService`、`InterviewSessionState`、`InterviewRepository`、`InterviewBillingService`、`InterviewPrepareService`、`AudioStreamSession`、新增 Flyway 迁移（`system_prompt` + `paused_at`）

### P2｜物理连接缺少独立存活检测，存在死连接计费泄漏 —— **已实施**

> 结论：**引入独立心跳，而不是继续压缩业务心跳阈值。** 把"心跳"绑在音频/业务消息上，无论阈值调到多少都是错的解法。

**原状**

- `HEARTBEAT_TIMEOUT_MS = 5 分钟`，叠加 30 秒扫描周期 → 最坏约 5.5 分钟才踢出。
- 心跳仅由业务消息刷新，无独立 ping。

**关键事实澄清（原判断里有一处是错的）**

原文写"若前端持续推流（含静音帧），5 分钟不会误杀；若前端改为 VAD，静默 >5 分钟会被误判"。**前半句把静音帧的来源搞错了**：

- 静音帧是**后端**发的 —— `DoubaoAsrClient#scheduleKeepAlive()` 每空闲 3 秒向**豆包**补一帧 200ms 静音 PCM，用于维持**后端↔豆包**的 ASR 长连接（AGENTS.md §4.2 里的"客户端"指 `DoubaoAsrClient` 这个 HTTP 客户端，不是浏览器）。
- 前端**本来就是 VAD**：AGENTS.md §6.7.2 明确写着"前端本地 VAD 不上传静音"，静默期**没有任何音频帧**。

这个澄清改变了结论：**60 秒的音频判据会误杀健康会话**（用户思考一分钟是常态），因此"退选方案：把超时缩短到 60~120 秒、依赖前端持续推帧"是不可行的 —— 前端并不持续推帧。**缩短超时必须以应用层心跳为前提。**

**问题 2：两条时间轴被混为一谈（已核实）**

- `InterviewBillingScheduler#SILENCE_TIMEOUT_MS`（30 秒"幽灵会话"检查）比较的 Redis `lastHeartbeatTime` **实为"扣费基准"**，由计费任务自身每次 `doBilling` 刷新（约每 10 秒），**恒不会超时** —— 这道防线实际上从未生效。
- `AudioStreamingService#hasActiveStreamSession` 依赖 `WebSocketSession#isOpen()`，半开连接仍返回 `true`。
- 优雅关闭（收到关闭帧）会立即触发 `onClose` → 停止计费，**无泄漏**；半开连接（移动网络掉线、进程被杀等无关闭帧）则两道防线全部失效。
- **结果：直到 5 分钟心跳踢出前持续计费，最多约 5 分钟时长被误扣。**

**已实施的方案**

**（1）新增应用层心跳协议**：上行文本控制消息 `{"type":"heartbeat"}`（`ControlMessage#TYPE_HEARTBEAT`），前端 20~30 秒发一次。
不用 WebSocket 原生 ping frame —— 容器会自动回 pong，但 **ping 不会透传到应用层**，后端无从据此刷新活跃度。

**（2）时间戳拆分 + 音频不再是心跳**：

```java
// 改前：语义错误
receiveAudio() -> refreshHeartbeat();

// 改后
receiveAudio()  -> updateAudioActivity();          // 只更新音频活跃度
heartbeatMsg()  -> refreshConnectionHeartbeat();   // 唯一刷新连接活跃度的入口
```

**（3）判据随客户端能力自适应** —— 这是让后端**可以先于前端上线**的关键：

| 客户端 | 判据 | 阈值 |
| :--- | :--- | :--- |
| 未发过心跳（老前端） | 音频活跃度 | **5 分钟**（与改造前一致，不会误杀） |
| 发过一个心跳（新前端） | 只看连接心跳 | **60 秒**（音频再旧也不影响，死连接 1 分钟内被发现） |

发过一个心跳即永久切到严格判据，无需开关、无需前后端同时发布。

**（4）单一判据来源**：`AudioStreamingService#isConnectionLost(逻辑会话ID)` 是连接存活的唯一判定入口，
心跳扫描（`WsHeartbeatScheduler`，扫描周期 30 秒 → **10 秒**）与计费兜底（`InterviewBillingScheduler`）共用它。
计费侧那段自刷新基准的"幽灵会话"检查被替换为真实连接活跃度判断，`SILENCE_TIMEOUT_MS` 常量删除。

```text
客户端
  │ {"type":"heartbeat"} 每 20~30s
  ▼
AudioStreamSession#lastConnectionHeartbeatTime
  │
  ├── WsHeartbeatScheduler（每 10s）→ isConnectionLost() → 踢出 → onClose → 停止计费
  └── InterviewBillingScheduler（每 10s）→ isConnectionLost() → 兜底结算
```

**验证**

- 新增 `AudioStreamSessionHeartbeatTest`（6 用例）：老客户端静默 4 分钟仍存活 / 6 分钟判失联；已声明心跳的客户端**音频停滞 10 分钟也不判失联**；心跳超 60 秒判失联；**音频帧不刷新连接心跳**；`heartbeat` 消息刷新并声明支持；`PAUSE` 消息不刷新。
- `AudioStreamingServiceTest` 新增 4 个 `isConnectionLost` 用例（逻辑会话不存在 / 已暂停 → `null`；存活 → `false`；失联 → `true`）。
- 全量 `mvn test`：**95 用例 / 0 失败 / 0 错误**。

**前端心跳也已在真实浏览器里验证**（这是最后一块空白）。难点与破法：

1. `useRealtimeVoice#start()` 的顺序是**先 `startCapture()`（`getDisplayMedia`）再 `connect()`** ——
   屏幕采集被拒就不会建连，也就没有心跳，而自动化浏览器弹不出选择器。
   破法：把 `getDisplayMedia` / `getUserMedia` 替换成返回「静音音轨的合成 MediaStream」，
   **只替换音频源，被测的心跳代码一行没动**。
2. `onHeartbeatReceived()` 没有日志，无法直接断言"收到心跳"。破法（决定性）：先让浏览器正常发一会儿心跳，
   再把 `WebSocket.prototype.send` 打补丁**丢弃 `heartbeat` 帧**（连接保持打开 = 模拟客户端静默）。
   于是前端计数器证明**定时器在按 25 秒触发**，服务端若在 60 秒后以 `heartbeatCapable=true` 踢出，
   就证明**之前确实收到过心跳**（该标志只在收到心跳时翻转；从未收到则会走 5 分钟音频判据、不会在 60 秒踢）。

实测：前端 `__droppedHeartbeats=2`（75 秒内触发 2 次 → 25 秒节奏）；服务端
`[心跳超时] heartbeatCapable=true, idleMs=61129, timeoutMs=60000`；UI 由「实时监听中」转为「未开始」。
`idleMs=61129` 与「建连时那一次立即心跳 + 补丁丢掉了 25s/50s 两次」完全对得上。

心跳语义另有**单测级覆盖**（含边界），WS 传输层由既有 `AudioStreamingWebSocketIntegrationTest` 覆盖。

**设计取舍：为什么静音保活留在后端，而不是让前端发静音帧（避免重复讨论）**

链路上有**两个跳**，各自有独立的保活需求，不要混为一谈：

```text
浏览器 ──(上行音频 / 心跳)──► 后端 ──(PCM + 静音保活)──► 豆包 ASR
          ▲                            ▲
  客户端↔后端 存活                     后端↔豆包 存活（豆包 8 秒硬超时）
  → 心跳 20 B / 25 s                   → 静音帧 6400 B / 3 s
```

曾考虑过"让前端发静音帧"，好处是能同时保护两跳、把两套保活合并成一套。**结论是不采用**，理由：

| 维度 | 前端发静音帧 | 后端保活 + 前端心跳（当前） |
| :--- | :--- | :--- |
| 上行带宽 | ~7.7 MB/小时（6400 B / 3 s，走**用户移动上行**） | ~2.9 KB/小时（20 B / 25 s，走已建好的 socket） |
| 电量 | 麦克风 / 编码 / 射频持续工作 | 无额外开销 |
| 与音频管线解耦 | ❌ 重新耦合 —— 前端换更严 VAD、用户静音、iOS 挂起 AudioContext 都会让"存活信号"消失 | ✅ 独立信号，这些场景下仍有效 |
| 后端能否独立维持 ASR | ❌ 依赖前端；前端一抖动 ASR 就断 | ✅ 后端自持保活与重连（`consumeLoop`） |
| 前端改动量 | 需在静默期维持采集+编码+上传 | 在已有 socket 上发 20 字节文本帧 |

带宽差约 **2600 倍**，且是用户侧移动流量；把存活判据绑回音频管线又正好抵消 P2 的收益。

**已知缺口（唯一真正偏向"前端发静音"的场景）**：后端保活会让"连接活着、但前端音频管线已死"伪装成"用户很安静"。
覆盖它的正确做法不是持续上传静音，而是加**音频管线看门狗**：心跳正常但连续 N 分钟无音频帧（且非暂停态）时向前端下发告警，让前端自检音频链路。目前未实现。

**涉及文件**：`ControlMessage`、`AudioStreamSession`、`AudioStreamingService`、`WsHeartbeatScheduler`、`InterviewBillingScheduler`、`AGENTS.md`（§3.6 协议 + 新增 §3.7 存活判据）

### P2.1｜计费秒数的取整方式与基准推进 —— **已修**

**原状**

```java
int actualSeconds = Math.round(durationMs / 1000.0f);
...
sessionInfo.setLastHeartbeatTime(now);   // ← 基准直接跳到 now
```

**为什么这是个问题**：计费是**周期性结算**的（`InterviewBillingScheduler` 每 10 秒一次，另有暂停/结束时的结算），
而每轮结算的间隔几乎不可能是整数秒。基准跳到 `now` 会把这一轮的零头**永久丢弃**，于是：

| 取整方式 | 每轮误差 | 累计效果 |
| :--- | :--- | :--- |
| `Math.round` + 基准跳到 now | ±0.5 秒，但零头被丢弃 | 期望无偏；**若结算周期稳定地偏大**（如恒定 10.6 秒），会稳定进位 → **系统性多扣** |
| `floor`（截断）+ 基准跳到 now | 恒为 −0.5 秒 | **系统性少扣约 0.5 秒/轮 ≈ 5%** |

也就是说：**单独把四舍五入改成截断会更糟**（每小时面试少扣约 3 分钟）。

**修法：截断 + 零头结转**

```java
int actualSeconds = (int) (durationMs / 1000);          // 截断：不足 1 秒不计
if (actualSeconds <= 0) return 0;                        // 不动基准，零头留到下一轮
sessionInfo.setUsedSeconds(used + actualSeconds);
// 关键：基准按「已计费秒数」前进，而不是跳到 now
sessionInfo.setLastHeartbeatTime(base + actualSeconds * 1000L);
```

基准只前进「已计费的整秒」，不足 1 秒的零头自然结转到下一轮。效果：

- **不超扣**：任意时刻累计计费 ≤ 真实时长（误差恒 < 1 秒，且只发生在会话结束时）；
- **不系统性少扣**：零头不被丢弃，长期无漂移；
- 语义上真正实现了「不足 1 秒不计费」。

> 暂停 / 恢复会重置基准（`resumeBilling` 设 `lastHeartbeatTime = now`），每轮丢弃 < 1 秒 —— 这是**有意的**：暂停期间本就不该计费。

**验证**：`InterviewBillingServiceTest` 两条用例把语义钉住 ——
`updateStatus_不足1秒_不扣费且不推进基准`（断言基准不变）、
`updateStatus_基准按已计费秒数前进_零头结转到下一轮`（1500ms → 只扣 1 秒，且基准恰前进 1000ms 而非跳到 now）。

**涉及文件**：`InterviewBillingService#doBilling`

## 4. 健壮性原则

在动 P1/P2 之前，先把下面三条定为不可违背的原则，否则改完仍是补丁叠补丁。

**原则一：任何物理连接退出路径最终都必须进入统一 cleanup。**

物理连接的销毁**不能**直接决定逻辑面试生命周期。`afterConnectionClosed` 不能被视为唯一清理入口，需要心跳扫描、异常路径、计费耗尽、用户主动结束共同兜底。

> **曾经的疑似反例（见 P0，已证伪）**：`onOpen` 强踢旧连接时 `close()` 之后紧跟 `streamSessions.remove(oldConnectionId)`。原判断认为这会让回调拿不到对象、`onClose()` 被 `if (streamingService != null)` 挡掉。实测表明 Tomcat 在 `close()` 内部**同步**回调 `afterConnectionClosed`，因此回调先于那行执行，正常路径没有问题；真正出问题的是 `close()` 抛异常 / 连接已关闭这两种回调不到达的情况。该行已删除。
>
> 由此得到一条更稳的规则：**不要让"从 map 里删掉"和"做业务清理"成为两件事。** `streamSessions.remove()` 的返回值同时承担了「移除」和「幂等守卫」两个职责，一旦有路径只想移除不想清理（或反之），就会静默出错。正确形态是：`cleanup()` 内部自己完成移除，并对重复调用幂等。

**原则二：物理连接与逻辑会话严格分层。**

```text
物理连接断开  →  逻辑会话仍然存在  →  重新建立 WebSocket
             →  重新绑定逻辑会话  →  恢复 AI 上下文继续面试
```

**原则三：所有 connection cleanup 必须带 `connectionId` 守卫。**

```text
连接 A → resume → 连接 B 建立 → A 的 afterConnectionClosed() 延迟到达
```

若 A 的关闭回调无条件执行 `pauseInterview()` / `stopBilling()` / `removeLogicalSession()`，就会把 B 正在运行的逻辑会话错误关掉。因此回调内必须先判断：

```text
当前连接是不是我？
  是 → cleanup
  否 → stale callback，忽略
```

`InterviewSessionState` 已具备 `currentConnectionId` + `bindConnection` / `unbindConnection`，守卫所需的元数据**已经存在**，只是清理路径尚未使用它。

## 5. 目标架构

实时面试会话最终分为三个层次，外加一条独立的计费时间轴：

### 5.1 业务生命周期

`Interview`

- DB 持久化
- `RUNNING / PAUSED / ENDED / EXPIRED`
- 业务事实来源

### 5.2 逻辑会话

`InterviewSessionState`

- `interviewId`
- `systemPrompt`
- AI context
- session metadata
- 可跨 WebSocket 连接继续
- Redis 持久化运行态
- JVM Map 作为本地缓存

### 5.3 物理连接

`AudioStreamSession`

- WebSocket
- PCM queue
- Doubao ASR connection
- heartbeat（独立于业务音频）
- connection lifecycle

### 5.4 分层关系

```text
DB
业务事实
  │
  └── Interview

Redis
可恢复运行态
  │
  └── InterviewSessionState

JVM
本地缓存
  │
  └── logicalSessions

WebSocket
物理连接
  │
  └── AudioStreamSession

Billing
独立计费时间轴
  │
  └── lastBillingTime（≠ lastConnectionHeartbeat）
```

### 5.5 目标恢复链路

```text
resumeSession(sessionId)
  → JVM logicalSessions                     （最快，同进程）
  → Redis realtime:session:{id}             （跨进程，含渲染后 systemPrompt）
  → DB interview + snapshot + interview_message
                                            （兜底重建：快照重建 systemPrompt，
                                              最近 N 条消息重建 context）
  → RESUME_EXPIRED
```

第三级是**真能跑通的路径**，不是纸面兜底：`interview_message` 全量在库，快照在库，面试参数在库。它的已知局限是异步落库的丢失窗口与 `systemPrompt` 的版本漂移（见 P1 三个缺口）。
