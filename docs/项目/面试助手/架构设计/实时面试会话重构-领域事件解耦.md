# 实时面试会话重构：领域事件解耦

针对 `AudioStreamSession` 承担职责过多（计费、持久化等横切关注点侵入实时链路）的问题，进行的一次结构化重构。

## 1. 问题诊断

`AudioStreamSession` 是一个「上帝类」（约 730 行），混杂了 6 类职责：

```text
AudioStreamSession
│
├── WebSocket 收发
├── 音频队列
├── ASR 生命周期
├── LLM 调用
├── Prompt 构建
├── 消息持久化
├── 面试生命周期
└── 计费
```

其中 `billingService.startBilling` / `pauseBilling` / `stopBilling` 与 `conversationService` 是典型的**横向关注点**，被硬编码进会话生命周期，导致：

- 每加一个业务（评估、分析）就要往里塞依赖
- 无法单独测试 ASR/LLM 链路
- 计费逻辑散落在 `onAsrReady`、`onClose` 等多处

### 更深层的结构性问题

```text
WebSocket 断开
      ↓
AudioStreamSession.onClose()
      ↓
结束 ASR
      ↓
停止计费
      ↓
结束面试
```

这意味着：**物理连接生命周期 = 面试生命周期**。

而这正是后续要支持「暂停 / 断线重连 / 切后台 / 多次继续面试」时最大的结构障碍。

---

## 2. 设计决策：为什么选「领域事件」而非 Listener / Facade

### 2.1 否决方案 A：`List<SessionLifecycleListener>` 手动遍历

```java
private final List<SessionLifecycleListener> lifecycleListeners;

for (var listener : lifecycleListeners) {
    listener.onReady(...);
}
```

问题：生命周期一旦复杂，接口会膨胀成「另一个上帝接口」：

```java
onReady() onStarted() onPaused() onResumed() onDisconnected()
onReconnected() onClosed() onExpired() onLlmStarted() onLlmCompleted() ...
```

### 2.2 否决方案 B：大 Facade（`InterviewSessionLifecycleHandler`）

```text
AudioStreamSession → LifecycleHandler → BillingService / ConversationService
```

本质上只是把依赖搬家，没有真正的扩展性。

### 2.3 采纳方案：领域事件 + `@EventListener` 独立处理器

```text
                    ┌──────────────────────┐
                    │  InterviewSession    │
                    │  interviewId / userId │
                    │  status / context     │
                    │  billing state        │
                    └──────────┬───────────┘
                               │ Session Lifecycle
                               ▼
                    ┌──────────────────────┐
                    │   Domain Events      │
                    │ SessionStarted       │
                    │ SessionPaused        │
                    │ SessionResumed       │
                    │ SessionEnded         │
                    └──────────┬───────────┘
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        BillingHandler   PersistenceHandler  AnalyticsHandler
```

新增一个功能（如面试质量分析），只需新增一个处理器类，**无需改动** `AudioStreamSession`、`InterviewBillingService` 等任何现有类。

---

## 3. 核心边界原则（最重要）

**不是所有逻辑都事件化。**

| 类别 | 处理方式 | 示例 |
|---|---|---|
| 实时流处理链路 | **直接调用** | `receiveAudio → ASR → LLM → 推送`、`saveUserMessage` |
| 业务生命周期 | **领域事件** | Started / Paused / Resumed / Ended / Expired |

原因：实时链路（音频、ASR token、LLM token）一旦事件化会变得极难调试，且属于高频热路径，不应引入事件广播的开销与间接性。

---

## 4. 最终结构

```text
modules/realtime/
├── session/
│   ├── InterviewSessionState.java   # 逻辑会话状态（跨暂停/重连存活）
│   ├── AudioStreamSession.java      # 物理流连接：收音频/ASR/LLM/推送
│   └── ...
├── lifecycle/                        # 领域事件（纯 record，语义明确）
│   ├── InterviewSessionEvent.java    # 基接口
│   ├── InterviewStartedEvent.java
│   ├── InterviewPausedEvent.java
│   ├── InterviewResumedEvent.java
│   ├── InterviewEndedEvent.java      # 携带 EndReason
│   └── InterviewEndReason.java       # USER_ENDED / SESSION_EXPIRED / BILLING_EXHAUSTED / SYSTEM_ERROR
├── billing/
│   └── InterviewBillingEventHandler.java      # @EventListener 监听 4 个事件
└── conversation/
    └── InterviewConversationEventHandler.java # 监听 Paused/Resumed/Ended
```

事件定义为**业务化语义**（而非模糊的 `onReady`）：

```java
public record InterviewEndedEvent(
    Long userId,
    Long interviewId,
    String sessionId,
    InterviewEndReason reason
) implements InterviewSessionEvent {}
```

结束原因一开始就枚举化，后续业务判断会简单很多：

```java
public enum InterviewEndReason {
    USER_ENDED,        // 用户正常结束
    SESSION_EXPIRED,   // 暂停超时回收
    BILLING_EXHAUSTED, // 余额耗尽
    SYSTEM_ERROR
}
```

## 5. 事件发布关键点

`AudioStreamSession` 注入 `ApplicationEventPublisher`（通过依赖聚合对象 `AudioStreamSessionDependencies` 传递）：

```java
eventPublisher.publishEvent(new InterviewStartedEvent(
    userId, interviewContext.getInterviewId(), state.getSessionId()));
```

- **Started 必须在 `startConversation` 同步回填 interviewId 之后发布**（否则事件的 interviewId 为空）。
- 发布时统一用 `state.getSessionId()`（逻辑会话 ID），而非 `this.sessionId`（物理连接 ID）。

---

## 6. 遗留的同步调用（有意保留）

| 位置 | 调用 | 保留原因 |
|---|---|---|
| `AudioStreamSession.startConversation` | `conversationService.startConversation` | 必须同步回填 interviewId，否则后续消息保存拿不到 ID |
| `AudioStreamSession.saveUserMessage/AssistantMessage` | `conversationService.save*Message` | 实时链路热路径，直接调用 |
| `AudioStreamingService.onOpen` | `billingService.forceTerminateActiveSession` | 同步强踢，需返回 oldSessionId 去断开旧连接（请求-响应语义，非通知） |

---

## 7. 后续演进方向

1. **`InterviewSession` 作为一等公民**：当前 `InterviewSessionState` 已承载 systemPrompt/context/interviewId，接近「逻辑会话」。可再补充 status 状态机（ACTIVE/PAUSED/ENDED）+ 计费状态快照，彻底实现「物理连接生命周期 ≠ 面试生命周期」。
2. **`forceTerminateActiveSession` 事件化**：需同步返回 oldSessionId，属请求-响应而非通知，需引入同步事件/回调机制后再评估。
3. **新增横切能力零侵入**：后续「面试质量分析」「埋点统计」只需新增 `@EventListener` 处理器监听 `InterviewEndedEvent`。
