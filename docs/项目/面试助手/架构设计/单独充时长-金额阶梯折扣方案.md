# 单独充时长 / 金额阶梯折扣方案

「自定义充值面试时长」如何做折扣定价：**判档依据、表结构、计算精度、订单价格快照、三端落地**。

> 前置阅读：[虚拟支付充值-价格配置方案](./虚拟支付充值-价格配置方案.md)（基础单价为什么放数据库、订单快照与审计日志的约定）。
> 本篇在其基础上引入折扣，两者的核心约定（DB 为准 / YAML 兜底 / 订单快照 / `BigDecimal`）完全一致，不冲突。

------

## 一、问题：单一定价无法体现「充得多更划算」

改造前，单独充时长的价格只有一条公式：

```text
金额 = 分钟数 × 基础单价
```

所有档位一个价（当时是 0.20 元/分钟），用户没有任何「多充」的动力，也不利于提升客单价。

于是需要引入折扣，但「折扣阶梯」有两种截然不同的设计思路，必须先选型。

------

## 二、两种阶梯方案对比

以基础售价 `0.50 元/分钟` 为例。

### 方案 A：时长阶梯 —— 用户输入分钟数，按分钟数定价

| 充值时长 | 单价 |
| -------- | ---- |
| 1~30 分钟 | 0.50 |
| 31~60 分钟 | 0.45 |
| 61~120 分钟 | 0.40 |
| 121~300 分钟 | 0.35 |
| 301~600 分钟 | 0.30 |

充 100 分钟：`100 × 0.40 = 40 元`。

### 方案 B：金额阶梯 —— 用户输入金额，反推分钟数

先定金额档位，再算能买多少分钟：

| 充值金额 | 单价 |
| -------- | ---- |
| ¥1~9.99 | 0.50 |
| ¥10~29.99 | 0.45 |
| ¥30~59.99 | 0.40 |
| ¥60~99.99 | 0.35 |
| ¥100~199.99 | 0.30 |
| ¥200+ | 0.25 |

充 10 元 → `floor(10 / 0.45) = 22 分钟` → 剩余 `0.10 元` 无法用完。

**方案 B 的致命问题**：用户充 10 元却不能正好花完，必须引入「余额」「最低充值」「金额必须是单价整数倍」等一堆补丁，支付订单金额与实际获得资产也无法精确对齐。

### 最终选型：方案 C —— 用户输入分钟数，按「原价金额」判档

融合两者优点：**用户仍然只输入分钟数（订单金额精确、无余额残留），但折扣力度由原价金额决定（充得越多越便宜）**。

```text
充值分钟数
    ↓
原价金额 = 基础单价 × 分钟数
    ↓
按原价金额匹配金额阶梯 → 折扣率
    ↓
优惠金额 = 原价金额 × 折扣率
    ↓
实付金额 = 原价金额 - 优惠金额
```

严格说，它应该叫「**按订单原价金额计算折扣的阶梯定价**」，而不是狭义的「充值金额阶梯」。

------

## 三、核心公式与示例

### 定价模型

```text
基础单价（recharge_setting.interview_minute_price）
        ↓
原价金额 = 基础单价 × 充值分钟数
        ↓
折扣率（recharge_price_rule 中命中的档位）
        ↓
优惠金额 = 原价金额 × 折扣率
        ↓
实付金额 = 原价金额 - 优惠金额
        ↓
折后单价 = 实付金额 ÷ 充值分钟数
```

### 默认阶梯（基础单价 0.50 元/分钟）

| 原价金额档（含） | 折扣率 | 折后单价 | 对应分钟数 | 优惠文案 |
| ---------------- | ------ | -------- | ---------- | -------- |
| ¥0 ~ ¥29.99 | 0% | 0.50 | 1 ~ 59 | — |
| ¥30 ~ ¥59.99 | 10% | 0.45 | 60 ~ 119 | 9 折 |
| ¥60 ~ ¥99.99 | 20% | 0.40 | 120 ~ 199 | 8 折 |
| ¥100 ~ ¥199.99 | 30% | 0.35 | 200 ~ 399 | 7 折 |
| ¥200 以上 | 40% | 0.30 | 400+ | 6 折 |

### 计算结果

| 充值分钟 | 原价 | 命中档 | 折扣率 | 优惠 | 实付 | 折后单价 |
| -------- | ---- | ------ | ------ | ---- | ---- | -------- |
| 30 | 15.00 | — | 0% | 0.00 | 15.00 | 0.5000 |
| 60 | 30.00 | ¥30 | 10% | 3.00 | 27.00 | 0.4500 |
| 120 | 60.00 | ¥60 | 20% | 12.00 | 48.00 | 0.4000 |
| 200 | 100.00 | ¥100 | 30% | 30.00 | 70.00 | 0.3500 |
| 300 | 150.00 | ¥100 | 30% | 45.00 | 105.00 | 0.3500 |
| 400 | 200.00 | ¥200 | 40% | 80.00 | 120.00 | 0.3000 |

### 毛利测算

```text
成本价     0.20 元/分钟
基础售价   0.50 元/分钟
最大折扣   40%
最低售价   0.30 元/分钟
最低毛利   0.10 元/分钟（50% 毛利率）
```

## 四、关键设计决策

### 1. 判档依据必须是「原价金额」，不能是实付金额

如果按实付金额判档，会出现循环依赖：

```text
支付金额决定折扣 → 折扣决定支付金额
```

永远解不出来。所以链路必须单向：**分钟数 → 原价 → 档位 → 实付**。

### 2. 阶梯只存 `discount_rate`，不存 `unit_price`

基础单价统一来自 `recharge_setting`，因此：

```text
折后单价 = 基础单价 × (1 - 折扣率)
```

如果阶梯里存死单价，把基础单价从 `0.50` 调到 `0.55` 时就要逐档改数据，容易漏改、改出不一致。只存折扣率，**改基础单价即可整体抬降所有档位**。

### 3. 阶梯放独立表，不塞进 `sys_config`

单值配置（`recharge.base-price`）放配置表合适；但阶梯本质是**一组结构化数据**（一堆 min/max/discount），塞进 `sys_config` 的一段 JSON 之后，后台列表、编辑、校验、排序都会变得很难做。

所以：**`recharge_setting` 管基础单价，`recharge_price_rule` 管阶梯**。

### 4. 订单必须保存完整价格快照

支付系统铁律：**订单创建后，价格永远以订单快照为准，绝不在支付回调时重新计算**。

否则运营改价后，历史订单金额会「漂移」，与微信侧（米大师）对账必然翻车。

快照至少覆盖：

```text
基础单价 / 原价金额 / 折扣率 / 优惠金额 / 实付金额 / 折后单价
```

### 5. 金额一律 `BigDecimal`

`double` 在支付场景不可接受。Java 用 `BigDecimal`，数据库用 `NUMERIC`：

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| 基础单价 | `NUMERIC(12,4)` | 允许 4 位小数 |
| 原价 / 优惠 / 实付 | `NUMERIC(12,2)` | 金额到分 |
| 折扣率 | `NUMERIC(5,4)` | `[0,1)` |

实付金额最终 `setScale(2, HALF_UP)`；折后单价保留 4 位，仅用于展示。

### 6. 档位不要设置太密，4~5 档足够

阶梯定价天然存在「跳价」：门槛前后单价会出现断层。例如默认阶梯下：

```text
119 分钟 → 原价 59.50 → 10% → 实付 53.55
120 分钟 → 原价 60.00 → 20% → 实付 48.00
```

多充 **1 分钟，反而少付 5.55 元**。这是阶梯定价的固有特性，不是 bug，但档位越密、断层越多、被用户发现的概率越高。

**结论：4~5 档、门槛间隔拉开**即可；不要做成「满 10 减 1、满 20 减 2」这种密集阶梯。

> 后续可选优化（未实现）：前端在门槛附近提示「再充 N 分钟可省 X 元」，或后端改成**分段累进（边际）计价**——即每一段按各自单价累加，从根上消除跳价。当前采用「整单按命中档计价」，简单、可解释、后台易配置。

### 7. 自定义充值的价格不能逼近礼包

礼包本身已有较大组合优惠（如「60 分钟 + 300 次 AI 问答 ¥49」）。如果自定义充值能做到和礼包同价，礼包就失去意义，用户会全部转向自定义。

三种购买方式的定位要分层：

```text
新用户         → 新人礼包（拉新，最便宜）
要 AI + 时长   → 固定礼包（组合优惠，提客单价）
只要时长 / 自控数量 → 自定义充值（灵活，但不追求最低价）
```

这也是最大折扣只做到 40%（0.30 元/分钟）、而不是压到成本线的原因。

## 五、数据库设计

### 5.1 阶梯规则表

```sql
CREATE TABLE recharge_price_rule (
    id            BIGSERIAL     PRIMARY KEY,
    asset_type    VARCHAR(32)   NOT NULL,
    min_amount    NUMERIC(12,2) NOT NULL,                   -- 原价金额下限（含）
    max_amount    NUMERIC(12,2),                            -- 原价金额上限（含）；NULL = 无上限
    discount_rate NUMERIC(5,4)  NOT NULL,                   -- [0,1)，0.1000 = 优惠 10%
    status        VARCHAR(20)   NOT NULL DEFAULT 'ENABLED',
    sort_order    INTEGER       NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ   NOT NULL,
    updated_at    TIMESTAMPTZ   NOT NULL,

    CONSTRAINT chk_recharge_price_rule_min_amount CHECK (min_amount >= 0),
    CONSTRAINT chk_recharge_price_rule_max_amount CHECK (max_amount IS NULL OR max_amount > min_amount),
    CONSTRAINT chk_recharge_price_rule_discount   CHECK (discount_rate >= 0 AND discount_rate < 1),
    CONSTRAINT chk_recharge_price_rule_status     CHECK (status IN ('ENABLED', 'DISABLED'))
);

CREATE INDEX idx_recharge_price_rule_match
    ON recharge_price_rule (asset_type, status, min_amount);
```

`asset_type` 复用资产枚举（当前只有 `INTERVIEW_SECONDS`），以后 AI 问答次数、VIP 天数各自充值时可共用此表。

### 5.2 种子阶梯

```sql
INSERT INTO recharge_price_rule
    (asset_type, min_amount, max_amount, discount_rate, status, sort_order, created_at, updated_at)
VALUES
    ('INTERVIEW_SECONDS',   0.00,  29.99, 0.0000, 'ENABLED', 10, NOW(), NOW()),
    ('INTERVIEW_SECONDS',  30.00,  59.99, 0.1000, 'ENABLED', 20, NOW(), NOW()),
    ('INTERVIEW_SECONDS',  60.00,  99.99, 0.2000, 'ENABLED', 30, NOW(), NOW()),
    ('INTERVIEW_SECONDS', 100.00, 199.99, 0.3000, 'ENABLED', 40, NOW(), NOW()),
    ('INTERVIEW_SECONDS', 200.00,   NULL, 0.4000, 'ENABLED', 50, NOW(), NOW());
```

### 5.3 订单表补齐折扣率快照

```sql
ALTER TABLE recharge_order ADD COLUMN discount_rate NUMERIC(5,4);
```

加上已有的 `original_amount` / `discount_amount` / `amount` / `unit_price`，`TOPUP` 订单的价格快照就完整了：

```text
order_type      = TOPUP
asset_type      = INTERVIEW_SECONDS
quantity        = 300
price_unit      = MINUTE
unit_price      = 0.5000     -- 基础单价快照
discount_rate   = 0.3000     -- 折扣率快照
original_amount = 150.00     -- 原价
discount_amount = 45.00      -- 优惠
amount          = 105.00     -- 实付
```

### 5.4 基础单价基准调整

阶梯阈值是按「基础单价 0.50」设计的，而 V18 迁移的种子值是 `0.20`，因此 V23 里把基准一并调整：

```sql
-- 仅当仍是 V18 种子值时才调整，避免覆盖运营已手工改过的价格
INSERT INTO recharge_setting_log (setting_id, old_price, new_price, updated_by, created_at)
SELECT id, interview_minute_price, 0.5000, NULL, NOW()
FROM recharge_setting WHERE interview_minute_price = 0.2000;

UPDATE recharge_setting
SET interview_minute_price = 0.5000, updated_at = NOW()
WHERE interview_minute_price = 0.2000;
```

同时把 YAML 兜底与 `RechargePriceProperties` 的默认值改为 `0.50`。

> 用 `WHERE interview_minute_price = 0.2000` 限定，是为了**只在值仍是种子默认值时调整**；如果生产环境已经人工调过价，不会被这条迁移覆盖。

## 六、后端实现

### 6.1 类结构

```text
modules/recharge
├── entity
│   ├── RechargePriceRule.java            阶梯规则实体
│   └── RechargePriceRuleStatus.java      状态枚举（ENABLED / DISABLED）
├── repository
│   └── RechargePriceRuleRepository.java  按 asset_type + status + min_amount 升序取档
├── model
│   └── RechargePrice.java                价格计算结果 record（唯一的价格快照来源）
└── service
    ├── RechargePricingService.java       定价核心 + 阶梯维护与校验 + 本地缓存
    └── RechargeOrderService.java         下单时调用定价服务并落库
```

`RechargePrice` 把一次计算的全部结果打包，避免在 Service 里到处传零散字段：

```java
public record RechargePrice(
        int minutes,
        BigDecimal baseUnitPrice,
        BigDecimal originalAmount,
        BigDecimal discountRate,
        BigDecimal discountAmount,
        BigDecimal payableAmount,
        BigDecimal actualUnitPrice) {
}
```

### 6.2 核心计算

```java
public RechargePrice calculateInterviewPrice(Integer minutes) {
    int validMinutes = validateMinutes(minutes);
    BigDecimal baseUnitPrice = rechargeSettingService.getInterviewMinutePrice();

    // 1. 原价金额 = 基础单价 × 分钟数
    BigDecimal originalAmount = baseUnitPrice
            .multiply(BigDecimal.valueOf(validMinutes))
            .setScale(2, RoundingMode.HALF_UP);

    // 2. 按原价金额匹配折扣档位（取下限不超过原价的最高档）
    BigDecimal discountRate = matchDiscountRate(originalAmount);

    // 3. 优惠金额与实付金额
    BigDecimal discountAmount = originalAmount.multiply(discountRate)
            .setScale(2, RoundingMode.HALF_UP);
    BigDecimal payableAmount = originalAmount.subtract(discountAmount);

    // 4. 折后实际单价（仅展示用，保留 4 位小数）
    BigDecimal actualUnitPrice = payableAmount
            .divide(BigDecimal.valueOf(validMinutes), 4, RoundingMode.HALF_UP);

    return new RechargePrice(validMinutes, baseUnitPrice, originalAmount,
            discountRate, discountAmount, payableAmount, actualUnitPrice);
}
```

两个容易漏掉的兜底：

- **最低实付金额**：实付低于 `0.01` 元时直接抛业务异常（无法拉起支付），避免出现 0 元订单；
- **分钟数上限**：单次充值不超过 `100000` 分钟，防止异常输入构造超大订单。

### 6.3 档位匹配

规则条目极少，因此**不逐单查库**，而是整体载入后在内存里匹配（同时供「档位提示」接口复用）：

```java
private BigDecimal matchDiscountRate(BigDecimal originalAmount) {
    RechargePriceRule matched = null;
    for (RechargePriceRule rule : loadEnabledRules()) {   // 已按 minAmount 升序
        if (rule.getMinAmount().compareTo(originalAmount) <= 0) {
            matched = rule;
        } else {
            break;
        }
    }
    return matched == null ? NO_DISCOUNT : matched.getDiscountRate();
}
```

「取下限不超过原价的最高档」这个写法顺带解决了**档位出现空洞时不至于算错**：即使运营误停用了中间某档，也会自然回落到前一档，而不是无折扣。

### 6.4 后台保存时的强校验

后台只提交「最低原价金额 + 折扣率」，**每档上限由下一档推导**，从源头消灭人工填错：

```text
上一档 max_amount = 下一档 min_amount - 0.01
最后一档 max_amount = NULL（无上限）
```

服务端在整表覆盖前强校验：

| 校验 | 目的 |
| ---- | ---- |
| 第一档最低原价金额必须为 0 | 否则低于该值的订单匹配不到任何档位 |
| 相邻档位至少相差 0.02 元 | 避免重叠，也避免 `max <= min` 违反数据库约束 |
| 折扣率位于 `[0, 1)` | 防止 100% 折扣或负价 |
| 折扣率随金额递增（非递减） | 不允许「充得越多反而更贵」 |

保存采用**整表覆盖（先删后插，同事务）**。规则不被订单外键引用——订单只保存价格快照——因此覆盖是安全的。

### 6.5 缓存

档位数量少、改动低频，沿用 `RechargeSettingService` 的同款策略：

```text
创建订单 → RechargePricingService → 本地缓存（volatile） → DB
后台改档位 → 清空本地缓存
```

**已知限制**：本地缓存是**单实例**的。多实例部署时，A 实例改档位，B 实例的缓存不会失效，最长会一直用旧档位直到重启。

单实例 / 灰度期可接受；多实例时需升级为 Redis 共享缓存或 Redis Pub/Sub 广播失效（与 `recharge_setting` 基础单价面临同样的问题，属于同一批待办）。

### 6.6 一个真实的坑：资产发放侧会解析失败

下单快照（`recharge_order.package_snapshot`，JSONB）是**礼包**和**单独充时长**共用的结构，`RechargeAssetGrantService` 发放资产时会把它反序列化成自己的视图类。

而 Jackson 的 `ObjectMapper` **默认对未知字段严格失败**（`FAIL_ON_UNKNOWN_PROPERTIES = true`）。往快照里新增价格字段后，发放侧会直接抛 `UnrecognizedPropertyException`，被 catch 后变成「礼包快照数据异常，无法发放资产」——**订单付了钱却发不出资产**。

修法是在发放侧的视图类上声明忽略未知字段：

```java
@com.fasterxml.jackson.annotation.JsonIgnoreProperties(ignoreUnknown = true)
private static class PackageSnapshot { ... }
```

同时给写入侧的 `PackageSnapshot` 加 `@JsonInclude(NON_NULL)`，避免礼包快照里多出一堆 `null` 价格字段。

> 教训：**共用的 JSONB 快照结构演进时，读写两侧都要检查反序列化策略**。快照是「只增字段」的演进型结构，解析侧必须宽容。

| `PUT` | `/api/admin/recharge-setting/price` | `operation:recharge-setting:update` | 改基础单价（影响所有档位折后单价） |
| `GET` | `/api/admin/recharge-setting/price-rules` | `operation:recharge-setting:query` | 阶梯列表 |
| `PUT` | `/api/admin/recharge-setting/price-rules` | `operation:recharge-setting:update` | 整表覆盖阶梯 |

后台阶梯只提交下限与折扣率：

```json
{
  "rules": [
    { "minAmount": 0,   "discountRate": 0 },
    { "minAmount": 30,  "discountRate": 0.1 },
    { "minAmount": 60,  "discountRate": 0.2 },
    { "minAmount": 100, "discountRate": 0.3 },
    { "minAmount": 200, "discountRate": 0.4 }
  ]
}
```

## 八、前端实现

### 8.1 小程序（充时长页）

关键点：**即时试算 + 服务端校准，两者都做**。

```text
进入页面
  ├── GET /unit-price        → 基础单价（失败回退 0.5）
  └── GET /topup/tiers       → 档位列表（失败回退「无折扣」）
        ↓
预设档位 / 自定义分钟数 → 本地按阶梯即时试算（与后端同一套公式）
        ↓
自定义分钟数额外防抖 350ms 调 /topup/preview 校准
（返回的 minutes 与当前输入一致才采用，避免旧响应覆盖新输入）
```

为什么本地也算一遍：预设档位点击、自定义步进器每 +10 都要立刻出价，走接口会有明显延迟；而档位数据（`minAmount` / `discountRate`）已经完整下发，本地算出的结果与服务端一致。

为什么还要调 preview：服务端才是唯一权威，若基础单价刚被改动、本地档位还是旧的，preview 能把价格纠回来。**下单时后端会重新计算**，所以即便 preview 失败也不会下错价。

页面展示：

- 档位卡片：实付价 + 「省 ¥x」（固定高度的占位，保证有无折扣的卡片等高）；
- 阶梯提示条：`满 ¥30 9折 · 满 ¥60 8折 · 满 ¥100 7折 · 满 ¥200 6折`；
- 底部合计：命中折扣时同时显示划线原价与「已优惠 ¥x」。

预设档位也从 `10/30/60/90/120` 调整为 `30/60/120/200/400`，让每一档都正好落在折扣门槛上（否则「热门」标签贴在无折扣的档位上，转化会很差）。

### 8.2 管理后台（充值设置页）

一页三个区块：

1. **基础单价**：保留原有的改价表单，文案调整为「原价基准」，并说明改动会整体抬降各档折后单价；
2. **金额阶梯折扣规则**：`Form.List` 行内编辑，每行只填「最低原价金额 + 优惠比例（%）」，右侧实时显示**推导出的上限**与**折后单价**；支持新增/删除档位、填入默认阶梯；
3. **价格试算**：输入分钟数 → 调 `/topup/preview` 展示原价/优惠/实付，上架前核对用。

后台的优惠比例按「%」填写（运营习惯），提交时才换算成折扣率，规避 `0.1 * 100 = 10.000000000000002` 这类浮点误差：

```ts
const toPercent = (rate: number) => Math.round(rate * 10000) / 100;
const toDiscountRate = (percent: number) => Math.round(percent * 100) / 10000;
```

前端也做一遍与后端一致的校验（首档为 0、间距 ≥ 0.02、折扣递增），减少无效请求；真正的兜底仍在服务端。

## 九、不变的链路

折扣只改变了「**创建订单**」这一步的金额来源，后面的链路完全复用：

```text
创建订单
    ↓
recharge_order（含完整价格快照）
    ↓
微信支付 / 虚拟支付代币充值
    ↓
PAY_SUCCESS
    ↓
RechargeAssetGrantService
    ↓
TOPUP → user_asset 聚合余额（PACKAGE → asset_batch 批次）
    ↓
user_asset_log
```

特别注意：**代币充值的 `buyQuantity` 取自订单 `amount`（实付金额 × 100 代币）**，因此折扣天然生效，无需额外改动——这也是「订单快照是唯一可信源」的价值。

## 十、已知限制与后续演进

| 项 | 现状 | 后续 |
| -- | ---- | ---- |
| 计价方式 | 整单按命中档计价（存在门槛跳价） | 可改分段累进计价，或前端提示「再充 N 分钟更省」 |
| 多实例缓存 | 本地缓存，改档后其他实例不失效 | Redis 共享缓存 / Pub/Sub 广播失效 |
| 档位生效时间 | 立即生效（只影响新订单） | 如需定时生效，加 `effective_at` 字段 |
| 多资产类型 | 表已支持 `asset_type`，业务只做 `INTERVIEW_SECONDS` | AI 问答次数 / VIP 天数充值时可复用 |
| 档位审计 | 仅日志，无独立变更表 | 可参照 `recharge_setting_log` 建 `recharge_price_rule_log` |
| 成本价 | 不参与定价计算 | 保持为经营数据，不进入价格公式 |

> 「成本价不参与实时售价计算」这点很重要：成本是经营数据，价格公式只应关心 `基础单价 × (1 - 折扣率)`。成本涨到 0.23 时，由人决定是否调基础单价，而不是让用户价格自动变化。

## 十一、核心规则速查

| 规则 | 说明 |
| ---- | ---- |
| 判档依据 | 订单**原价金额**，不是实付金额 |
| 原价金额 | 基础单价 × 充值分钟数 |
| 取档 | 取下限不超过原价金额的最高档；未命中则无折扣 |
| 阶梯存储 | 只存 `min_amount` + `discount_rate`，不存单价 |
| 上限推导 | 上一档上限 = 下一档下限 - 0.01，最后一档无上限 |
| 档位约束 | 首档为 0、连续不重叠、折扣随金额递增 |
| 基础单价 | 放 `recharge_setting`；改它整体抬降所有档位 |
| 档位配置 | 放 `recharge_price_rule`，不塞 `sys_config` |
| 订单 | 保存完整价格快照，支付成功后绝不重算 |
| 精度 | Java `BigDecimal`；金额 `NUMERIC(12,2)`、折扣率 `NUMERIC(5,4)` |
| 缓存 | 本地缓存 + 改配置失效；多实例后再上 Redis |
| 快照演进 | JSONB 快照只增字段，解析侧必须 `ignoreUnknown = true` |
