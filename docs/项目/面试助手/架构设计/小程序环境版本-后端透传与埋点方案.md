# 小程序环境版本（envVersion）：后端透传与埋点方案

> 方案定稿（2026-09-30，**已实施**）。
> 一句话：**让后端自己发的事件也带上「这条数据来自哪个小程序包」（开发版 / 体验版 / 线上版），
> 且不引入任何存储、不影响老客户端、不改分析平台。**

## 实施结果（2026-09-30）

后端 `mvnw -o test` **全绿**（297 → 301 用例，0 失败 0 错误），小程序 `tsc --noEmit` 对改动文件零报错。
落地与本文一致，另有两条实测得到的补充：

1. **`RequestUtils.getQueryParam` 不做百分号解码**（它走 `UriComponentsBuilder.fromUri(...).build()`，
   把入参当成未编码再编码一次）。所以 WS 侧 `envVersion` 的**值只能是简单 token** ——
   我们只发 `release` / `trial` / `develop`，无影响；但别指望从这里读到带空格或中文的值，
   白名单会把它挡成「没带」（安全方向，不是 bug）。实测：断言 `%20RELEASE%20` 会被解成
   `release` 并不成立，测试已改成只钉大小写容错。
2. 新增三个测试类钉住契约：`ClientEnvVersionContextTest`（白名单 / 默认值 / **不跨线程传播**）、
   `AnalyticsTrackerEnvTest`（优先级链 + payload 键名必须是 `env_version`）、
   `TicketHandshakeInterceptorTest`（**握手参数名 `envVersion` 是前后端字符串契约**，
   任何一侧改名都会静默退回默认环境，报表上看不出来）。

## 0. 范围（先看这段，避免实现走偏）

- **只做一件事**：把客户端的环境版本传进后端，落到后端埋点事件上。
- **不改分析平台**：它的 `events.env_version` 列、`event_daily` 的 `(event, date, env_version)`
  排序键、`/collect` 的逐条与整批 `env_version` 入参**全都已经就绪**（见 §6.3）。
  「平台是否按环境展示/过滤」是**另一个决定**，本文不涉及。
- **不动登录会话 `UserSession`**（理由见 §7.1）。
- **不解决 `recharge_pay_succeeded`**（微信回调天生没有客户端头，理由见 §7.2）。
- 第一版**不引入任何新的存储**（无 DB 迁移、无 Redis 新键、无新配置项）。

---

## 1. 要解决的问题

现状：小程序把事件**直连**分析平台的 `/collect`，每条事件都带顶层 `env_version`
（`pass-up.frontend-mp/src/features/analytics/service.ts#readEnvVersion`，取值来自
`wx.getAccountInfoSync().miniProgram.envVersion`）。

但**后端自己发的事件（`source=backend`）没有环境**：

- 后端拿不到小程序那个值（它只在 `/collect` 的 body 里，而事件是服务端自己发的）；
- 分析平台的 `_parse_env` 对缺失值按 `DEFAULT_ENV = release` 入库。

后果：**体验版/开发版的测试期间，前端事件被环境挡住，后端事件却全部按「线上」入库** ——
面试开始/结束、支付成功这些恰恰是最关键的口径，会带着测试流量混进线上报表。

当前的兜底是「内部人员名单」（`configs/internal_users.json`）：把测试的人从指标里剔掉。
这能挡住**自己人**，但挡不住「用体验版拉来的外部种子用户」，而且它要求名单被及时维护。

> 目标：**让每条后端事件都能自报「我来自哪个包」，且老客户端不受影响。**

---

## 2. 关键约束（决定了方案形状）

1. **envVersion 是「客户端包」的属性，不是「人」的属性。**
   同一个人可能同时开着 web + 线上版小程序 + 体验版小程序；开发者工具里切环境版本
   **不需要重新登录**（storage 不清，access 15min / refresh 7d 仍然有效）。
   → 不能做成 `user.envVersion`；放进登录会话会**陈旧**。
2. **一半后端事件不在请求线程里产生**（§5 的清单）—— 这是「必须让会话携带」的唯一真实理由。
3. **埋点是旁路，不能给业务加风险**：取不到值一律降级，绝不抛异常、绝不阻塞、绝不影响业务结果。
4. **老客户端零影响**：不带这个信息的请求，行为必须与今天逐字节一致。
5. **客户端自报的值不可信**：只能用于统计与排查（§7.3）。

## 3. 命名

「env」这个词在本项目里已经被占用（`application-dev.yml` 的 profile、`SPRING_PROFILES_ACTIVE`、
`.env` 文件都是「环境」），单独用 `env` 确实抽象、且会与「服务端运行环境」混淆。
统一采用**微信自己的叫法 `envVersion`**（`miniProgram.envVersion`），它在语义上正好把
「环境版本」与「版本号 `version`」区分开 —— 而这两者我们都有。

| 位置 | 名字 | 理由 |
| :--- | :--- | :--- |
| 微信 API | `miniProgram.envVersion` | 上游叫法，不解释 |
| 小程序 TS | `envVersion` | 与微信一致；导出函数 `getClientEnvVersion()` |
| HTTP 请求头 | `X-Client-Env-Version` | 带 `Client` 才不会与「服务端环境」混淆；`Env-Version` 与微信字段一一对应 |
| WebSocket query | `envVersion` | 与同处既有的 `detailLevel` / `interviewStyle` / `templateUid` 同风格（camelCase） |
| Java 字段 / 上下文 | `envVersion` / `ClientEnvVersionContext` | 一眼知道是「客户端环境版本」 |
| 埋点 payload | `env_version` | **不可改**：分析平台的列名就是它 |
| 取值 | `release` / `trial` / `develop` | 与 `__wxConfig.envVersion` 对齐；缺省 `release` |

被否掉的候选：`X-Env-Version`（像服务端环境）、`X-Mini-Env`（把名字绑死在小程序上，
将来 web/app 想带同类信息就得再发明一个）、`X-Client-Channel`（「渠道」在本项目里
指 scene / 来源，语义冲突）。

## 4. 方案：三层

### 4.1 客户端统一带（小程序，2 个文件）

**HTTP**：在 `src/utils/request.ts` 的 **`doRequest()`**（L64）里统一注入请求头。

> ⚠️ **不要加在 `withAuthHeader()`（L81）**：401 之后的重试分支是自己拼 header 的
> （L177-184 的 `header: { ...header, Authorization: ... }`），加在那里会让**重试请求丢掉这个头**。
> `doRequest` 是所有请求（含重试）的唯一出口，加在这里才闭环。
> 这也符合 AGENTS.md 的既有约定（后端业务请求一律经 `utils/request`）。

**WebSocket**：在 `src/features/interview/ws.ts:252` 的建连 URL 上追加 `&envVersion=`，
与既有的 `mode` / `input` / `language` / `detailLevel` 等参数同一写法；
`/ws/asr` 若也需要，同法（它的建连 URL 在同文件另有分支）。

**取值**：把 `features/analytics/service.ts` 里私有的 `readEnvVersion()`（L132-145）
提到 **`src/utils/client-env.ts`**，由 analytics 与 request 共用。

> 为什么必须共用：两处各读一次会出现「埋点里是 trial、请求头里是 release」这种
> 无法解释的偏差（同一份判断逻辑写两遍，迟早漂移）。`utils/` 正是放这种跨切面工具的地方。

**不用动的出口**：简历直传的 `Taro.request`（`features/resume/api.ts:162`）打的是**对象存储**，
不是我们的后端；分析平台的 `/collect`（`features/analytics/api.ts`）body 里**已经带了** env。

### 4.2 后端落点（按事件的产生线程分）

| 事件产生的位置 | env 从哪来 | 落点 |
| :--- | :--- | :--- |
| HTTP 请求线程内 | 请求头 | `ClientEnvVersionContext`（ThreadLocal） |
| WebSocket 会话内 | 握手 query | `InterviewContext` / `InterviewSessionState` |
| 异步 / 事件监听器 | 事件载荷 | 事件对象自带字段 |

**① HTTP 侧：`ClientEnvVersionContext`**

- 新增 `infrastructure/web/ClientEnvVersionContext`（`ThreadLocal<String>`，`get/set/clear`）。
- `TokenAuthenticationFilter`（`infrastructure/security/filter/`）在读 `Authorization` 之后
  顺手读 `X-Client-Env-Version` 写入上下文，`finally` 里 clear。
- 好处：**`@TrackEvent` 切面不用改**（它读上下文即可），请求线程内的手工埋点（如
  `AuthService.loginByWechatMiniAppCode` 的 `user_login_succeeded`）也自动拿到。

> 放在 filter 里而不是每个 controller：这是既有的「读 header → 落到请求上下文」的
> 唯一入口（对照 `WebAuthHelper#detectPlatformType` 读 `Sec-CH-UA-Platform` / `User-Agent`
> 的写法）；放 controller 层必然漏。
> 另一个必须在 filter 里做的理由：**登录 / 注册是公开端点**，会被 `shouldSkip` 跳过 Token 解析，
> 而 `user_login_succeeded` / `user_registered` 恰恰产生在那里 —— 所以读头必须在 `shouldSkip` 之前。

**② WebSocket 侧：握手 → 会话 → 事件**

- `TicketHandshakeInterceptor` 里 `putIfPresent(attributes, ATTR_ENV_VERSION, RequestUtils.getQueryParam(request, "envVersion"))`
  —— 与 L92-104 那一串 `putIfPresent` 完全同构，**一行**。
- 建会话时写进 `InterviewContext`（`AudioStreamingService` 装配处：新建读握手参数、重连复用原值）；
  `InterviewSessionState` 不单独存字段，直接委托上下文取（与 `getInputMode()` 同一套理由）。
- `InterviewStartedEvent` / `InterviewEndedEvent` 两个 record **各加一个 `envVersion` 分量**
  —— 直接照抄它们现在携带 `mode` / `inputMode` 的做法，这是仓库里现成的先例。
- 事件基接口 `InterviewSessionEvent` **不加**该分量：只有这两个事件用于埋点，
  `Paused` / `Resumed` 不需要，加在接口上等于强迫它们也带一个恒为 null 的字段。

**③ 异步侧：`UserRegisteredEvent` 加字段**

`AuthAnalyticsEventListener#onUserRegistered` 是 `@Async` + `AFTER_COMMIT`
（`modules/auth/event/AuthAnalyticsEventListener.java:28-40`），拿不到请求上下文。
发布该事件的登录流程在请求线程里，把 env 塞进事件对象即可。

### 4.3 埋点出口兜底（唯一改口径的地方）

`AnalyticsTracker#buildEvent` 增加一个顶层字段：

```java
body.put("env_version", resolveEnvVersion(explicitEnvVersion));
```

取值优先级：**显式传入（事件载荷）> 当前请求上下文 > 默认 `release`**。

- `track(...)` / `trackNow(...)` 增加一个 `envVersion` 形参（现有 `deviceId` 形参就是同类透传，
  后端事件一律传 `null`，两者风格一致）；为不改动全部调用点，保留旧签名的重载。
- 兜底默认值必须与平台一致（`release`），这样「后端不知道环境」时行为与今天完全相同。
- `resolveEnvVersion` / `buildEvent` 声明为包级可见：单测要直接钉住优先级链与字段名
  （尤其是 `env_version` 这个必须与平台列名一致的键），不依赖真实 HTTP 请求。

## 6. 兼容性、迁移与回滚

### 6.1 老客户端

不带 `X-Client-Env-Version` / `envVersion` 的请求：上下文为空 → 埋点走默认 `release`
→ **与今天的行为完全一致**。前后端可任意顺序发布（客户端先发只是开始带上值；
服务端先发只是暂时收不到值）。

### 6.2 跨进程重建的面试会话

面试逻辑会话支持跨进程重建（`LogicalSessionRebuilder`）。该重建路径没有握手上下文，
env 会丢 —— 这与既有的 `mode` / `inputMode` 是**同一类问题**：它们是靠 DB 里的面试记录
（`interview` 表）恢复的。若重建后要保住 env，两条路：

1. 与 `mode` 一致：从 `interview` 表的既有字段推导（**本版不新增列**）；
2. 或接受重建后的会话 env 为空 → 埋点落 `release`（**本版选择**，见 §10 待办）。

### 6.3 分析平台侧

**零改动**。它的 `ingest.py` 已经是：

```python
env = _parse_env(e.get("env_version") or batch_env)   # 逐条优先，支持整批
```

`db.py` 的 `ENVS = ("release", "trial", "develop")` / `DEFAULT_ENV = "release"`
与我们取值域一致；`events.env_version` 与 `event_daily` 的排序键都已包含它。

### 6.4 回滚

删掉客户端注入的头、后端忽略该字段即可，**没有需要清理的持久化状态**
（这正是「本版不引入任何存储」的价值）。

## 7. 明确不做的事（以及为什么）

### 7.1 不放登录会话 `UserSession`

`UserSession`（Redis，`auth:session:meta:*`）看起来是"放一次、处处可读"的好地方，
但它解决不了本方案的主要矛盾，还带来两个新问题：

- **语义错位**：一个用户可能同时有 web / 线上版小程序 / 体验版小程序三个会话，
  「这个用户的环境」本身不成立；
- **时效性**：开发者工具切环境版本不重登，会话里的值会陈旧；而「请求头」天然是最新的。
- **额外的兼容成本**：Redis 用的是 `JacksonJsonRedisSerializer`（`RedisConfig:47-50`，
  默认 ObjectMapper）。给 `UserSession` 加字段前，必须先补
  `@JsonIgnoreProperties(ignoreUnknown = true)`，否则**滚动发布/回滚期间新旧实例互读会话
  可能直接反序列化失败**，表现为大面积 401 —— 为了一个埋点字段不值得引入这个风险。

> 结论：**不用它**。将来真出现「只有 userId、没有请求也没有会话」的场景（例如 §7.2 的
> 支付回调），再单独设计（更准的是把 env 落在订单上），而不是现在为它铺一层存储。

### 7.2 不管 `recharge_pay_succeeded`

它的两条路径都拿不到客户端环境：微信回调是**微信服务器**发的请求（没有客户端头），
定时补偿只有订单号。要修就得二选一：

- **把 env 落在订单上**（`recharge_order` 加列，回调按订单读）—— 最准，代价是一次迁移；
- 或 Redis 记「用户最近一次客户端环境」—— 最轻，但多端并存时不准。

用户已确认：**目前只是为了埋点统计，这一条先不管**（恒 `release`）。
代价要说清楚：体验版测试的下单事件有 env、支付成功事件没有，**同一笔订单两个事件的环境会不一致**；
因为测试流量主要是自己人，内部名单能兜住，暂时可接受。

### 7.3 不把 envVersion 用于业务逻辑 / 权限 / 计费

它是**客户端自报的请求头**，可以伪造。唯一允许的用途是**统计与排查**（埋点、日志）。

### 7.4 不做「用户级环境」

见 §2.1。任何 `user.envVersion` 形态的设计都不采纳。

### 7.5 不为了埋点改业务表

不加列、不加索引、不改事务（§7.2 的订单落列是**下一版**的选项，不是本版）。

## 9. 验收方式

1. **单测**：`ClientEnvVersionContext` 的取值解析（合法三值 / 空 / 非法值 / 大小写 / 线程隔离）；
   `AnalyticsTracker` 的优先级链（显式 > 上下文 > release）与 payload 键名。
2. **本地端到端**：起后端 → 用带 `X-Client-Env-Version: trial` 的请求打一个会产生事件的接口
   （如登录）→ 看分析平台 `events.env_version` 是否为 `trial`；不带该头 → `release`。
3. **真机**：开发者工具（`develop`）/ 体验版（`trial`）/ 线上版（`release`）各跑一次
   面试开始+结束，确认 `interview_session_*` 的环境正确。
4. **回归**：老版本小程序（不带该头）跑一遍核心链路，确认事件仍按 `release` 入库、
   业务行为无变化。
