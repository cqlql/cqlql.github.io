# 无限额度资产 / 资格方案（「无限」不是数量，是资格）

针对 PassUp「礼包可赠送**无限额度**资产（如**永久会员**礼包中的 AI 问答次数无限）」的方案选型与最终实现。

> 关联笔记：
> - [面试时长充值-礼包批次FIFO方案](./面试时长充值-礼包批次FIFO方案.md)：礼包有限资产的批次账本（`asset_batch`）
> - [AI问答计费-资产扣减方案](./AI问答计费-资产扣减方案.md)：资产怎么**消耗**（`CONSUME`）
> - [虚拟支付充值-资产发放方案](./虚拟支付充值-资产发放方案.md)：资产怎么**进来**（订单 / 支付 / 发放）
>
> **🔑 账本定位（最重要）**：本项目资产体系有**三个互不重叠的事实来源**——
> `asset_batch`（有限礼包批次库存）、`user_asset`（无批次需求的聚合余额）、
> `user_asset_entitlement`（无限资格）。**「无限」进的是第三个，不是前两个。**

---

## 一、背景与需求

### 1.1 需求

礼包可以赠送「AI 问答次数无限」的资产（典型形态：**永久会员**礼包，`asset_package.valid_days = NULL` 即永久）。需要在**不破坏现有批次 FIFO 体系**的前提下支持。

### 1.2 为什么不能塞进 `asset_batch`

`asset_batch` 的语义是「**有限**库存 + FIFO + 临期优先 + 过期作废」，「无限」没有其中任何一个属性：

| 环节 | 现有实现 | 把「无限」塞进去的后果 |
|---|---|---|
| 剩余量 | `remaining_amount BIGINT NOT NULL` | 无限无剩余量可言，只能填大数 → 语义谎话 |
| 排序 | `sortBatches` 临期优先 → FIFO | 无限批次不需要排序，也不该被排到前面白白扣 |
| 求和 | `getBalance` = 聚合余额 + `SUM(remaining)` | 大数求和溢出、前端展示难看 |
| 过期 | `expireExpiredBatches` 清零 + 写 EXPIRE 流水 | 永久会员永远不该进这个任务 |
| 扣减 | `Math.min(remaining, need)` | 永远扣不完，必须特判，逻辑分叉 |
| 撤销 | `revokeAssets` 按余额扣回 | 「应扣 / 实扣 / 差额追缴」对无限毫无意义 |

一句话：`asset_batch` 要同时承担两种语义，之后每个改动都要写 `if`。

### 1.3 也不能用「极大数」模拟

`amount = 999999999` / `-1` 这类做法会污染余额展示、`SUM` 求和、溢出判断，并且无法表达「会员到期」与「已消耗量」，直接排除。

## 二、方案选型（结论：独立资格表）

| 维度 | **A. 独立资格表（采用）** | B. `asset_batch` 加 `is_unlimited` | C. `user_asset` 加 `is_unlimited` | D. 极大数模拟 |
|---|---|---|---|---|
| 语义清晰 | ✅ 无限 = 资格，与账本解耦 | ❌ 两种语义混一表 | ❌ 混进余额行 | ❌ 语义谎话 |
| 对现有 FIFO 体系影响 | ✅ 零侵入 | ❌ 排序/求和/过期/扣减全要特判 | ❌ 余额语义被污染 | ❌ 溢出风险 |
| 有效期 / 永久 | ✅ `expires_at`，NULL = 永久 | ⚠️ 需复用但语义别扭 | ❌ 无位置 | ❌ |
| 撤销 / 退款 | ✅ `ref_order_id` + `REVOKED` | ⚠️ | ❌ | ❌ |
| 审计（谁、何时、为何） | ✅ 独立行可追溯 | ⚠️ | ❌ | ❌ |
| 改动量 | 小（1 建表 + 1 改列） | 中（多处特判） | 小但后患大 | 小但错误 |

**结论**：采用「**独立资格表 `user_asset_entitlement` + 判定/消费短路**」。

> **边界（重要）**：资格表只放「某用户在某个 `AssetType` 上无限」，**不放**等级 / 权益包 / 价格 / 续费。
> 只有当「会员」本身需要被查询 / 展示 / 续费时，才另外引入 `user_membership` 聚合层，其下挂多条 entitlement。当前不提前建。

## 三、模型定位：三个事实来源（核心）

```text
无批次需求充值（单独充时长 TOPUP / 赠送 / 调整 / 历史存量）
  user_asset.balance                    → 聚合余额，唯一权威

礼包有限资产（PACKAGE：时长 + 次数，需批次 + 临期优先 + 有效期）
  asset_batch.remaining_amount          → 批次库存，唯一权威

无限额度（如永久会员的 AI 问答次数）
  user_asset_entitlement.status         → 资格，唯一权威（不是余额）
```

**三条规则：**

1. **可消费总量 = 聚合余额 + 有效礼包批次 SUM**（`getBalance` 语义**不变**，无限资格不参与求和）。
2. **能不能用 = 无限资格 OR 有限余额 > 0**，统一收敛到 `BillingService.canConsume()`。
3. **三者天然不重叠、不要求实时强一致**：同一笔资产永远只落一个账本，不存在双写漂移。

**一句话收敛：**

> `asset_batch` 管有限礼包批次的库存，`user_asset` 管非批次聚合余额，`user_asset_entitlement` 管无上限资格；消费先看资格（无限直接放行），再看账本。

## 四、数据模型（V19）

### 4.1 礼包明细支持「无限」

约定：**`is_unlimited = true` → `amount` 必须为 NULL**（无限 = 没有数量概念）；否则 `amount` 必须 > 0。

```sql
ALTER TABLE asset_package_item ALTER COLUMN amount DROP NOT NULL;
ALTER TABLE asset_package_item ADD COLUMN is_unlimited BOOLEAN NOT NULL DEFAULT FALSE;

ALTER TABLE asset_package_item DROP CONSTRAINT IF EXISTS asset_package_item_amount_check;
ALTER TABLE asset_package_item ADD CONSTRAINT chk_package_item_amount
    CHECK ((is_unlimited AND amount IS NULL)
        OR (NOT is_unlimited AND amount IS NOT NULL AND amount > 0));
```

> 用 `DROP CONSTRAINT IF EXISTS` 而非硬编码约束名：V8 里 `amount` 是内联 CHECK（自动名 `asset_package_item_amount_check`），不同环境可能有差异。
> 不使用「`amount = 0` 表示无限」的魔法值；NULL 更诚实。

### 4.2 用户无限资格表

```sql
CREATE TABLE user_asset_entitlement (
    id            BIGSERIAL    PRIMARY KEY,
    user_id       BIGINT       NOT NULL,
    asset_type    VARCHAR(32)  NOT NULL,
    entitlement   VARCHAR(32)  NOT NULL DEFAULT 'UNLIMITED',
    source        VARCHAR(32)  NOT NULL,        -- PACKAGE / ADMIN_ADJUST / ACTIVITY
    ref_order_id  BIGINT,                       -- 礼包订单（发放幂等 + 撤销定位）
    expires_at    TIMESTAMPTZ,                  -- NULL = 永久
    status        VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE',
    revoked_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ  NOT NULL,
    updated_at    TIMESTAMPTZ  NOT NULL,
    CONSTRAINT chk_uae_asset_type CHECK (asset_type IN ('AI_CHAT_COUNT', 'INTERVIEW_SECONDS')),
    CONSTRAINT chk_uae_status     CHECK (status IN ('ACTIVE', 'REVOKED', 'EXPIRED'))
);

CREATE UNIQUE INDEX uk_uae_active ON user_asset_entitlement (user_id, asset_type) WHERE status = 'ACTIVE';
CREATE UNIQUE INDEX uk_uae_order  ON user_asset_entitlement (ref_order_id, asset_type) WHERE ref_order_id IS NOT NULL;
CREATE INDEX idx_uae_lookup ON user_asset_entitlement (user_id, asset_type, status);
```

**字段取舍（刻意的轻量）：**

| 字段 | 保留理由 |
|---|---|
| `entitlement` | 成本 0 的预留；当前只有 `UNLIMITED` 一种，代码里硬编码不做策略分发 |
| `ref_order_id` | **不可砍**：同时承担发放幂等（`uk_uae_order`，对齐 `uk_asset_batch_order`）+ 撤销定位 |
| `expires_at` | **不可砍**：判定硬条件；永久 = NULL |
| `status` | **不可砍**：撤销需要 `REVOKED`，否则退款/误发只能删行 |
| `effective_at` | 已砍：发放即生效，`created_at` 替代 |

**`status` 三态：** `ACTIVE`（生效中）/ `REVOKED`（被撤销）/ `EXPIRED`（到期）。

> ⚠️ **判定硬条件是 `status = 'ACTIVE' AND (expires_at IS NULL OR expires_at > NOW())`，不是只看 `status`。**
> 与 `asset_batch` 的「扣减硬条件是 remaining + 未过期」同一纪律：即使过期任务没跑，也不会误判为无限。

### 4.3 不新增任何流水表 / 枚举 / 唯一索引

延续「无限不是资产」的定位，**`user_asset_log` 完全不改**：不加 `biz_type`、不改 `chk_user_asset_log_biz`、不重建 `uk_asset_log_noconsume`。详见第八节。

## 五、发放侧

`RechargeAssetGrantService.grantAssets` 从「两路」变「三路」分流：

```text
无限额度（isUnlimited）  → grantUnlimited()  落 user_asset_entitlement（不进任何资产账本）
TOPUP（单独充时长）      → grantAsset()     累加 user_asset.balance + RECHARGE 流水
PACKAGE 有限额度（时长/次数）→ grantBatch()   落 asset_batch + 带 batch_id 的 GRANT 流水
```

- **有效期在发放时物化**：`expires_at = 支付成功时间(payment_success_at) + asset_package.valid_days`，NULL = 永久。
  与批次共用同一个 `calcExpiresAt()`，**资格表只回答「当时授了什么、有效到何时」**，查询时不再回关联礼包。
- **顺序无关**：失败时重推 / 补偿任务沿用订单级 `markAssetGranted` 抢占，数据库层由 `uk_uae_order` + `uk_uae_active` 兜底。
- **一个礼包可同时含两种**：例如「AI 无限 + 面试 3600 秒」，逐 item 分流天然支持。

## 六、消耗侧（含一个关键的边界划分）

### 6.1 三个方法，两种意图

`consumeAsset` 被两种**性质完全不同**的意图共用，必须分开：

| 方法 | 语义 | 谁调用 | 是否被无限资格豁免 |
|---|---|---|---|
| `canConsume()` | 「还能不能用」= 无限 OR 余额 > 0 | 所有**余额检查点** | — |
| `tryConsume()` | **用户使用**资产 | AI 问答扣次数、面试按秒扣费 | ✅ 豁免（直接放行，不做任何扣减） |
| `consumeAsset()` | **扣账本**原语 | 管理员扣回 / 撤销（`revokeAssets`） | ❌ 绝不豁免，一定要真扣 |

> ⚠️ **踩坑记录**：最初设想把短路直接写在 `consumeAsset` 里。这会让
> `RechargeAssetGrantService.revokeAssets`（它调用 `consumeAsset` 扣回错误发货的资产）
> 在用户有无限资格时**静默不扣但返回 true**，且 `RevokeItem` 会上报「已扣回 N」——订单被标记撤销、
> 资产却还在用户账上，**静默资损且无报错**。
> 根因是 `consumeAsset` 同时服务「用户使用」与「管理员扣回」两种意图，而无限资格只应豁免前者。
> 修正即拆出 `tryConsume`（用户使用入口），`consumeAsset` 保持纯账本语义。

### 6.2 判定与消费

```text
tryConsume()
   │
   ▼
isUnlimited() ?
   │         │
  YES        NO
   │          │
   ▼          ▼
直接成功    consumeByFifo()（礼包批次优先 → 聚合余额垫底）
不扣资产
不写流水
```

**余额检查点必须统一走 `canConsume()`**，否则无限用户会因有限余额为 0 被误判为余额不足（0 次 / 无法建连）。已统一的三处：

- `TicketHandshakeInterceptor`（建连前的面试时长预检）
- `QnaAssetService.hasEnoughChatCount`（AI 问答预检，避免无效 LLM 调用）
- `InterviewBillingService.doBilling`（心跳结算）

> 💡 `canConsume` 只能回答「能不能用」，回答不了「还剩多少」。需要展示剩余量的地方
> （如 `doBilling` 回写 `currentBalance`）仍需 `getBalance()` 配一个 `unlimited` 标志，
> 不要试图让 `getBalance()` 返回魔数。

### 6.3 无限的用户消费不写 `user_asset_log`

```java
if (isUnlimited(userId, assetType)) {
    return true;   // 不做任何扣减，也不写流水
}
```

理由：`user_asset_log` 的定义是「资产**变动**流水」，`change_value = 0` 的行违反表自身不变量，
而且会被当成账务记录被对账逻辑扫到。无限用户的消费由**业务记录**承载（如 AI 问答的会话 / 消息）。

**连带收益**：省掉 3 项高风险改动——`chk_user_asset_log_biz` 加白名单、重建 `uk_asset_log_noconsume`、
`AssetChangeSource` 加枚举。其中 `uk_asset_log_noconsume` 的 `WHERE biz_type <> 'CONSUME'`
若忘记排除新类型，会让面试心跳（同一 `interviewId` 多条流水）撞唯一索引并**回滚整笔扣费**
（V6 注释里记载过这个已踩的坑）。

**资格生命周期同样不写流水**：授予不写、使用不写、过期 / 撤销也不写。
（批次过期要写 EXPIRE，是因为有量化损失需要留痕；资格失效没有量化损失。）

## 七、有效期与过期任务

- 发放时物化 `expires_at`；**永久 = NULL**（与 `asset_package.valid_days = NULL` 语义一致）。
- 过期任务（复用 `AssetBatchExpireJob`，每 5 分钟）把 `expires_at <= NOW() AND status = 'ACTIVE'`
  的资格置为 `EXPIRED`。**纯状态维护，不写流水**。
- 该任务缺失也不影响正确性——判定侧已带 `expires_at` 硬过滤（双保险）。

---

## 八、撤销与退款

`RechargeAssetGrantService.revokeAssets` 对无限项改为 `revokeUnlimited()`：把资格置 `REVOKED`（保留行，便于审计与后续重发判重），
`RevokeItem` 的 `expect/deducted/shortfall` 均为 0，另以 `unlimited = true` 标记。

> 无限资格**没有「已消耗量」概念**，撤销不涉及资产扣回，因此不适用那套「差额需人工追缴」的逻辑。

## 十、关键决策与取舍

| 决策点 | 结论 | 理由 |
|---|---|---|
| 「无限」的表达 | 独立资格表，**不进** `asset_batch` / `user_asset` | 无限没有有限库存的任何属性；塞进去等于两套语义混一表 |
| 是否用极大数模拟 | ❌ 禁止 | 污染展示 / 求和 / 溢出判断，无法表达到期与用量 |
| 判定入口 | 统一 `canConsume()` | 实时面试已有多个余额检查点，各自拼 `isUnlimited \|\| getBalance > 0` 必漏 |
| 消费与扣账本 | 拆 `tryConsume`（用户使用）/ `consumeAsset`（管理员扣回） | 否则撤销会静默不扣但返回成功 → 静默资损 |
| 无限期间扣哪个 | **无限优先**：无限生效时不消耗有限额度 | ① 用户友好：会员到期后有限额度仍可用；② 撤销干净：误发资格被撤销时用户资产分文未动，无需追缴差额 |
| 是否写消费流水 | ❌ 不写 | `user_asset_log` 是资产**变动**流水，`change_value = 0` 违反表不变量；用量统计应由业务记录承载 |
| 有效期基准 | 支付成功时间 + `valid_days`，发放时物化 | 支付回调延迟不影响用户买到的有效期；资格表自解释，查询不回关联礼包 |
| 撤销方式 | 置 `REVOKED` 保留行 | 审计 + 重发判重；不删行 |
| 表结构范围 | 只放「某用户某资产无限」 | 不提前扩成完整会员权益系统；需要时再加 `user_membership` 聚合层 |

### 10.1 已知代价：有限批次可能在无限期间白作废

若有限批次的 `expires_at` **早于**无限资格 `expires_at`，在「无限优先」期间该批次会一路不消耗而**过期作废**，用户付过钱的额度白丢。

**当前接受，不为它加复杂度**（动态排序「有限剩余有效期 < 无限剩余有效期时切回有限优先」收益极小、分支成本高）。
低成本缓解：复用已有的临期提醒提示用户，客服口径统一为「无限权益期间不消耗有限额度，到期后自动恢复」。

### 10.2 已知缺口：无限用量统计

- `GET /qna/quota/used` 目前统计的是「**已消耗的有限额度**次数」（`user_asset_log` 的 `CONSUME` 计数），**不含无限额度用量**，接口描述已同步澄清。
- ❌ **不要**简单改成「统计 `qa_message` 的 assistant 条数」：`QnaService.deleteConversation` 会
  **物理删除**消息（`messageRepository.deleteByConversationId`），用户删会话即让「已使用」回退，与「已使用是历史事实」矛盾。
- 若后续确需统计无限用户的实际提问量，建议二选一：
  1. 在资格表加 `used_amount BIGINT DEFAULT 0`，无限放行时原子 `+1`（无逐次流水，且不受会话删除影响）；
  2. 独立的用量表 / 只增不减的事件表，由业务侧写入。

## 十一、未来扩展：若某天面试时长也要「无限」

表结构与 `BillingService` 已按 `asset_type` 粒度支持（多插一行资格即可），但**时长链路还有两处必须一起改**：

1. `InterviewSessionInfo` 加 `unlimited` 标志（`startBilling` 时写入）；
2. `InterviewBillingService.doBilling` 在 `unlimited` 时**跳过** `remaining <= 0 → balanceExhausted`
   判断（否则 `tryConsume` 已放行，但 `getBalance` 返回的有限余额 0 会把面试掐断），并让前端展示「无限」。

当前因「无限只针对 `AI_CHAT_COUNT`」，这两处未改动。为避免误配置出故障，已加两道闸门：

1. **后端**：`AssetPackageService#UNLIMITED_SUPPORTED_TYPES` 只放行 `AI_CHAT_COUNT`，
   配置其他资产的无限额度会被直接拒绝（放开新类型前必须先补齐对应消费链路的无限判定）；
2. **管理后台**：明细的「无限」开关带 tooltip 说明，且切换资产类型时自动重置为「按量」。

---

## 十二、最终决策（2026-09-11 已落地）

- ✅ 「无限」建模为**资格**，落 `user_asset_entitlement`，与 `asset_batch` / `user_asset` 并列，互不重叠。
- ✅ 礼包明细用 `is_unlimited` + `amount IS NULL` 表达无限，DB 层 CHECK 保证互斥。
- ✅ 判定统一 `canConsume()`；用户消费走 `tryConsume()`（无限放行、不扣减、不写流水）；管理员扣回继续用 `consumeAsset()`。
- ✅ 无限优先：资格生效期间不消耗有限额度。
- ✅ 有效期发放时物化（支付成功时间 + `valid_days`，NULL = 永久）；过期任务只改状态、不写流水。
- ✅ 撤销 = `REVOKED` 保留行，无「差额追缴」语义。
- ⚠️ 遗留项：无限用量统计（见 10.2）、面试时长无限的两处配套（见第十一节）。
