# 限量礼包 / 名额占用与限购方案（前 N 名 + 每人限购）

针对 PassUp「永久礼包只允许**前 1000 名用户**购买」的方案选型与实现要点。

> 关联笔记：
> - [无限额度资产-资格方案](./无限额度资产-资格方案.md)：永久礼包送的「无限 AI 次数」怎么建模
> - [虚拟支付充值-资产发放方案](./虚拟支付充值-资产发放方案.md)：订单 / 支付 / 发放链路
> - [虚拟支付充值-价格配置方案](./虚拟支付充值-价格配置方案.md)：订单快照与价格配置
>
> **🔑 一句话方案**：名额用 `package_stock` **单行原子 CAS** 抢，限购用 `(package_id, user_id)` **唯一约束**兜底，
> 下单即**预占**、订单过期**归还**，**不引入 Redis**。

---

## 一、需求与语义

「前 1000 名用户可购买永久礼包」拆成**两个独立约束**，二者不可互相替代：

| 约束 | 语义 | 缺了它会怎样 |
|---|---|---|
| 总名额 ≤ 1000 | 限量库存 | 限量意义消失 |
| 每人限购 1 次 | 1000 **名**用户 | 1 个脚本用户可包圆 1000 单，「1000 名用户」落空 |

### 1.1 决策：1000 个用户，不是 1000 单

| # | 理由 |
|---|---|
| 1 | **语义**：需求说的是「1000 **名**用户」，「名」修饰人而非订单 |
| 2 | **重复购买对用户零价值**：第二份永久会员不产生任何增量（AI 次数已无限），理性用户不会买 → 限购**几乎不损失流水**，却挡住全部套利者 |
| 3 | **黄牛风险**：限量稀缺品必有套利动机，不限购会被脚本包圆 → 钱收到、营销目标（1000 个付费用户）落空 |
| 4 | **KPI 是人头**：限量活动冲的是「1000 个高价值用户 + 稀缺感 + 口碑」，不是这一单收入 |
| 5 | **成本几乎一样**：多一张限购表 + 一次 INSERT；名额计数表两种方案都要 |

> 何时才该选「1000 单」（不限购）：商品**可叠加消耗**（时长包 / 次数包），或活动目标纯冲流水。永久礼包两条都不成立。

### 1.2 「前 1000 名」的判定基准

按「第 1000 个**下单**的用户」（**预占制**）：

| 基准 | 结果 | 评价 |
|---|---|---|
| 第 1000 个**下单**的用户（采用） | 严格 1000 个不同用户；名额会被"下单不付款"短暂占用（2h 后释放） | 符合先到先得预期 |
| 第 1000 个**支付成功**的用户 | 发放数严格 ≤1000；但会出现"付完钱被告知没名额" | ❌ 体验差，退款链路成本远高于多送一个 |

**配套文案要求**：必须写明「锁定名额后需在 2 小时内完成支付，超时名额释放」。

## 二、方案选型

| 维度 | **A. DB 单行 CAS + 唯一约束（采用）** | B. Redis DECR 预扣 | C. `COUNT(*)` 判断后插入 |
|---|---|---|---|
| 并发正确性 | ✅ 行锁串行化，天然无超卖 | ⚠️ 快，但需回补，易与 DB 漂移 | ❌ COUNT 与 INSERT 非原子，**必超卖** |
| 账实权威 | ✅ DB 唯一权威 | ❌ Redis 不是账本 | ✅ 但结果错误 |
| 1000 名额量级 | ✅ 单行热点绰绰有余 | 过度设计 | — |
| 复杂度 | 低（2 张小表） | 高（双写一致性） | 低但错 |

**结论**：**不引入 Redis**。
- 1000 名额远非瓶颈（PG 单行 CAS 可到数千 TPS）；
- 名额是钱相关，必须 DB 权威；Redis 只适合当「挡板」（允许极少数误拒），真到几十万并发再引入；
- 削峰靠**前置**：前端售罄置灰 + 轻量查剩余接口（快速失败，减少进事务的量）+ 网关限流。

## 三、数据模型（V20）

**配置与运行态分开存**，避免同一个数字两处维护：

```sql
-- 配置：总名额（NULL = 不限量）。放在礼包配置表，不参与热点更新
ALTER TABLE asset_package ADD COLUMN stock_limit INTEGER;
ALTER TABLE asset_package ADD CONSTRAINT chk_asset_package_stock
    CHECK (stock_limit IS NULL OR stock_limit > 0);

-- 运行态：已占用计数（含待支付 + 已支付），单行热点
CREATE TABLE package_stock (
    package_id  BIGINT      PRIMARY KEY REFERENCES asset_package(id) ON DELETE CASCADE,
    used_quota  INTEGER     NOT NULL DEFAULT 0,
    created_at  TIMESTAMPTZ NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT chk_package_stock_used CHECK (used_quota >= 0)
);

-- 限购闸门：谁「正占着」名额（不是"谁买过"的账本，买过的由订单/资产侧可查）
CREATE TABLE package_purchase_quota (
    id          BIGSERIAL   PRIMARY KEY,
    package_id  BIGINT      NOT NULL REFERENCES asset_package(id) ON DELETE CASCADE,
    user_id     BIGINT      NOT NULL,
    order_id    BIGINT,
    status      VARCHAR(16) NOT NULL DEFAULT 'RESERVED',  -- RESERVED / CONFIRMED
    created_at  TIMESTAMPTZ NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT chk_ppq_status CHECK (status IN ('RESERVED', 'CONFIRMED'))
);

CREATE UNIQUE INDEX uk_ppq_package_user ON package_purchase_quota (package_id, user_id);
CREATE UNIQUE INDEX uk_ppq_order ON package_purchase_quota (order_id) WHERE order_id IS NOT NULL;
CREATE INDEX idx_ppq_package_status ON package_purchase_quota (package_id, status);
```

> **实现细节（与最初草稿的差异）**：`package_purchase_quota` 用**代理主键 + `(package_id, user_id)` 唯一索引**
> 表达限购，而不是复合主键。二者对限购的约束力完全等价（唯一索引就是唯一约束），
> 但代理主键对 JPA / 调试 / 未来扩展更友好。
> 另外两表都挂 `REFERENCES asset_package(id) ON DELETE CASCADE`：删除礼包时自动清理名额与占用记录。

### 3.1 名额 CAS：总量读配置、计数读运行态

```sql
UPDATE package_stock s
   SET used_quota = s.used_quota + 1, updated_at = NOW()
  FROM asset_package p
 WHERE s.package_id = p.id
   AND p.id = :packageId
   AND p.stock_limit IS NOT NULL
   AND s.used_quota < p.stock_limit
RETURNING s.used_quota
```

返回空行 = 名额已抢完。**优点是单一数据源**（`stock_limit` 只在 `asset_package`，`used_quota` 只在 `package_stock`），
且**后台把 `stock_limit` 调小到低于 `used_quota` 时，CAS 自然失败**（等价"已售完"），不会负数、不会误放行。

> `stock_limit IS NULL` 表示不限量：下单时直接跳过名额校验，`package_stock` 行也不必有。

### 3.2 限购：用唯一约束，不用「先查后插」

「先查有没有买过再插入」在并发下必错（两个请求同时查到"没买过"）。用 PK 兜底：

```sql
INSERT INTO package_purchase_quota (package_id, user_id, status, expires_at, created_at, updated_at)
VALUES (?, ?, 'RESERVED', ?, NOW(), NOW())
-- PK (package_id, user_id) 冲突 → 已有待支付订单或已购买 → 拒绝
```

### 3.3 `status` 与行的生命周期（关键设计）

| 状态 | 含义 | 是否占名额 |
|---|---|---|
| `RESERVED` | 已下单待支付 | ✅ |
| `CONFIRMED` | 已支付，永久限购 | ✅ |
| 无行 | 可以购买 | — |

- 支付成功 → `RESERVED → CONFIRMED`（**保留行** = 永久限购）；
- 订单过期 / 退款 → **DELETE 行**（+ 归还名额）。

> **为什么过期用 DELETE 而不是置 `RELEASED`**：PK 是 `(package_id, user_id)`，置 RELEASED 后用户重新下单会撞 PK，
> 还得写 `ON CONFLICT DO UPDATE` 补丁。DELETE 让「可重新购买」自然成立，而「已买过」由不删的 `CONFIRMED` 行继续挡住。

## 四、下单预占流程

插入点是 `RechargeOrderService#createOrder`（单一 `@Transactional`，天然「要么都成功、要么都回滚」）：

```text
1. 校验礼包（存在 / ENABLED）                       ← 现有逻辑
2. 建订单并 save（拿到 orderId，PENDING，expire_time = now + 2h）
3. packageStockService.reserve(pkg, userId, orderId)
     3.1 礼包未配置 stock_limit → 直接返回（不限量、不限购）
     3.2 INSERT package_purchase_quota(status=RESERVED) ON CONFLICT DO NOTHING
         → 受影响 0 行 = 已有待支付订单/已购买 → 拒绝
     3.3 CAS 扣 package_stock.used_quota
         → 受影响 0 行 = 名额已抢完 → 拒绝
```

**顺序很重要**：先插 quota（唯一索引冲突早失败，不浪费名额），再 CAS 扣名额。
任一步失败 → 抛业务异常 → 整个事务回滚，订单与 quota 行一并消失。

> ⚠️ **安全阀（必须保留）**：**无论额不占、不限购的前提是「礼包配置了 `stock_limit`」**。
> 如果无条件插入 quota 行，会把**所有存量礼包意外变成「每人限购一次」**——
> 这是本功能最容易造成的线上事故，因此 `reserve` 第一行就判断 `stockLimit == null → return`。

**为什么不在支付成功时才扣名额**：用户付完钱才发现没名额，只能退款，微信退款链路 + 客诉成本远高于「下单即锁定」。
**为什么不能下单扣了不释放**：恶意用户下 1000 单不付款就能锁死活动。

## 五、订单过期与超发（决策：接受少量超发）

### 5.1 冲突根源：现有「订单过期后仍可支付成功」

```42:46:src/main/java/com/xiaodingtie/passup/modules/recharge/repository/RechargeOrderRepository.java
    @Query("UPDATE RechargeOrder o SET o.payStatus = 'SUCCESS', o.payTime = :payTime, " +
            "o.payChannel = :payChannel, o.thirdTradeNo = :thirdTradeNo, o.payCallbackTime = :payTime " +
            "WHERE o.orderNo = :orderNo AND o.payStatus IN ('PENDING', 'EXPIRED')")
    int updateStatusToSuccess(...);
```

`IN ('PENDING', 'EXPIRED')` 是**故意的**：微信侧可能已支付但回调丢失/延迟，本地过期后仍允许支付成功，避免「付了钱拿不到资产」。

它与名额归还天生冲突：

```text
订单超时 → 归还名额（名额被别人抢走）
        → 用户稍后支付成功（现有语义允许！）
        → 该用户拿到资产，但名额已给别人
        → 最终发放数 > 1000（超发 ε）
```

### 5.2 决策：方案 A —— 接受少量超发

| 选项 | 做法 | 结论 |
|---|---|---|
| **A. 过期即归还，接受 ε 超发** | 最终发放 ≤ 1000 + ε | ✅ **采用**：ε 只来自「过期后仍支付成功」的极少数单；营销活动多送 1~2 个的边际成本，远低于退款链路 + 客诉 |
| B. 关单成功才归还 | 过期后名额先冻结，确认微信已关单才归还 | ❌ 现有代码**没有关单能力**（`markOrderExpired` 只改本地状态），需接入微信关单接口，工作量明显更大 |
| C. 过期不归还 | 名额一旦占用永久消耗 | ❌ 恶意用户下 1000 单不付款即锁死活动 |

### 5.3 消掉大部分竞态：过期走原子抢占

```text
逐单：UPDATE recharge_order SET payStatus='EXPIRED'
       WHERE id = ? AND payStatus = 'PENDING'      -- 原子抢占
  返回 0 → 这单刚被支付成功 → 跳过，不释放名额
  返回 1 → DELETE quota 行 + used_quota - 1
```

这样只剩「先过期成功、后支付成功」的**极窄窗口**会产生 ε。

### 5.4 落点：`expirePendingOrders` 必须改造

它现在是批量 UPDATE，只返回条数（拿不到 `packageId` / `orderId`，无法释放）：

```484:490:src/main/java/com/xiaodingtie/passup/modules/recharge/service/RechargeOrderService.java
    @Transactional(rollbackFor = Exception.class)
    public void expirePendingOrders() {
        int updated = rechargeOrderRepository.expirePendingOrders(Instant.now());
```

改为「查列表 → 逐单原子过期 → 释放」，挂现有 `RechargeOrderExpireJob`（每分钟）即可，无需新调度器。

### 5.5 对账兜底

`countByPackageIdAndPayStatus(packageId, "SUCCESS")` 已存在，可直接做「实际发放 / 名额」对比，超发一眼可见。

## 六、退款 / 撤销归还名额（决策：归还）

### 6.1 现状：真实的"退还"入口只有一处

| 入口 | 现状 |
|---|---|
| admin `POST /admin/recharge-orders/{id}/revoke`（撤销错误发货） | ✅ 有实现（`RechargeAssetGrantService#revokeAssets`） |
| 虚拟支付 `xpay_refund_notify`（退款通知） | ⚠️ **只打日志，无业务处理**（预留） |
| iOS 退款问询 `xpay_subscribe_ios_refund_query_notify` | 策略是「已发货 → 拦截退款」，即 iOS 虚拟支付默认不退款 |

### 6.2 用「DELETE 的受影响行数」做「归还 + 幂等闸门」

归还名额必须**幂等**（退款回调会重推），否则重复归还会把 `used_quota` 扣成负数 → 多放名额。

```java
// 1. 先取 packageId（查不到 = 未占用 / 已归还 → 直接返回）
SELECT package_id FROM package_purchase_quota WHERE order_id = :orderId

// 2. DELETE 的受影响行数即幂等闸门：删到才归还，没删到说明已被其它线程归还
int deleted = DELETE FROM package_purchase_quota WHERE order_id = :orderId

// 3. 仅 deleted > 0 时执行（GREATEST 兜底防负数）
UPDATE package_stock SET used_quota = GREATEST(used_quota - 1, 0) WHERE package_id = :packageId
```

> 实现上不需要 `RETURNING`——`executeUpdate()` 返回的受影响行数已经能表达「本次是否真的归还」，
> 也比 `INSERT/UPDATE ... RETURNING` 绑定参数更稳妥（避免原生查询的 `Instant` 类型推断问题，
> 时间戳统一用 SQL 的 `CURRENT_TIMESTAMP`）。

**两个好处**：
1. **一次 SQL 同时完成"归还动作"与"幂等判断"**，不需要额外的状态列或去重表；
2. **天然兼容第五节接受的超发边界**：

```text
超发的那个用户，名额早在他订单过期时就被归还、quota 行已被 DELETE
→ 他后续退款时 DELETE 无行可删 → 不重复归还 → used_quota 不会被少算
```

即「超发 ε 单」在退款环节**自动不归还**，账不会乱。

### 6.3 收敛为单一入口

把归还封装成 `PackageStockService#releaseByOrder(orderId)`（幂等），由各终态入口调用：

```text
订单过期（RechargeOrderExpireJob）        → releaseByOrder(orderId)
虚拟支付查单「微信侧不存在该订单」         → releaseByOrder(orderId)   ← 见下方「易漏点」
撤销错误发货（admin revokeAssets）        → releaseByOrder(orderId)
未来真实退款回调                          → releaseByOrder(orderId)   ← 接上同一方法，不用改两处
```

> ⚠️ **易漏点（已踩）**：`RechargeOrderService#markOrderExpired`（虚拟支付查单返回「订单不存在」时把订单
> 标为终态未支付、停止轮询）**同样是「终态未支付」**，也必须归还名额。若漏掉，由于订单已变 EXPIRED、
> 再也不会被过期任务捞起，该用户占用的名额会**永久泄漏**。修复方式：`expireOrderByOrderNo` 返回 >0 后
> 查出订单再调一次 `releaseByOrder`。

> 归还后 quota 行被删除 → 用户**可以重新购买**（占一个新名额）。语义 = 「退掉了就等于没买过」，符合预期。

## 七、展示与后台

- **前端**：礼包详情返回 `stockLimit` / `remainingQuota` / `soldOut`；剩余为 0 时按钮置灰，避免无效下单；
  文案提示「锁定名额后需在 2 小时内完成支付」。
- **轻量查询**：`GET /packages/{id}/quota` 只读剩余数，作为下单前的快速失败挡板（不查则不返回 500 人同时进事务）。
- **后台**：占用 / 应发 / 实发（`SUCCESS` 订单数）三者对比；手动调整名额。
- **调整名额的校验**：`stock_limit` 调小到低于 `used_quota` 时，CAS 自然失败（等价售罄），前端应提示「当前设置下已无可售名额」。

## 九、决策记录

| 决策点 | 结论 | 理由 |
|---|---|---|
| 1000 名用户 vs 1000 单 | **1000 名用户**（每人限购 1 次） | 需求语义是"名用户"；重复购买对用户零价值；防黄牛包圆；实现成本几乎一样 |
| 「前 1000 名」判定基准 | 第 1000 个**下单**的用户（预占） | 符合先到先得；避免"付了钱没名额"；代价是需配文案说明 2h 内支付 |
| 并发控制 | DB 单行 CAS + 唯一约束，**不用 Redis** | 1000 量级单行热点足够；名额是钱相关须 DB 权威；Redis 只适合当挡板 |
| 扣名额时机 | **下单预占** | 支付成功才扣会让用户"付完钱没名额"，退款链路成本更高 |
| 超发 | **接受 ε**（方案 A） | ε 只来自"过期后仍支付成功"的极少数单；远低于接入微信关单的成本 |
| 减少竞态 | 过期走**原子抢占**（`WHERE payStatus='PENDING'`），抢占失败不释放 | 把 ε 压缩到极窄窗口 |
| 过期归还方式 | **DELETE quota 行**（非置 RELEASED） | PK 冲突问题自然消解；`CONFIRMED` 行不删 → 永久限购仍生效 |
| 退款/撤销 | **归还名额**，用 `DELETE ... RETURNING` 做幂等闸门 | 一次 SQL 同时完成归还与幂等；且超发单自动不重复归还 |
| 归还入口 | 收敛为 `releaseByOrder(orderId)` 单一幂等方法 | 过期 / 撤销 / 未来退款回调共用，避免一处漏改 |

## 十一、附：营销展示口径（虚标已售）——P2 方案

### 11.1 需求

限量礼包刚上线真实销量为 0，需要对外显示「已售 300」营造人气，即希望用户看到
「已售 300 / 共 1000 / 仅剩 700」。

### 11.2 核心结论：「不可能三角」

设总数 `T`、想要的初始虚标 `N`，以下三条**不可兼得**：

1. 初始即显示「已售 N」（`f(0) = N`）
2. 每次真实购买后展示数字都变化（展示值严格递增）
3. 展示售罄不早于真实售罄（`f(real) <= T - 1` 当 `real < T`）

**证明**：真实卖完共发生 `T` 次购买；展示值需从 `N` 涨到 `T`，净增 `T - N`。
由 2 要求每次至少 +1，则 `T` 次购买后展示值至少为 `N + T > T`，与 3 矛盾。∎

推论：**「剩余 700」与「卖满 1000」互斥** —— 想让展示剩余变小只能靠真实成交。
若真需要「已售 300 / 仅剩 700」，等价于只卖 700 个，那就应该直接把 `stock_limit` 配成 700
（后端硬拦），而不是让展示口径提前售罄（前端置灰挡不住直接调 API 的人）。

### 11.3 采用方案 P2：虚标量同时加到「总数」与「已售」

```text
展示总数 = stock_limit + display_sold_base
展示已售 = display_sold_base + 真实已售
展示剩余 = 展示总数 - 展示已售 ≡ 真实剩余        ← 恒等
售罄判定 = 真实已售 >= stock_limit              ← 红线
```

- `T=1000, N=300` 实际效果：**共 1300 份 · 已售 300 · 仅剩 1000**（不是「仅剩 700」）
- 推导出来的恒等式让 11.2 的第 3 条**自动成立**，不需要任何校验规则
- `display_total` **不落库、不配置**，返回时算出来即可

| 玩法 | 真实库存 | 展示总数 | 初始已售 | 初始展示剩余 | 用户买 1 个 | 代价 |
|---|---|---|---|---|---|---|
| P1 `max(真实, 基数)` | 1000 | 1000 | 300 | 700 | 仍 300 ❌ 冻结 | 数字不动，像坏了 |
| **P2 总数+已售一起抬（采用）** | 1000 | **1300** | 300 | 1000 | 301 / 剩 999 ✅ | 「仅剩」紧迫感弱 |
| P3 只虚标已售、接受提前售罄 | 1000 | 1000 | 300 | 700 | 301 / 剩 699 ✅ | 真实 700 时展示售罄 → 少卖 300 |
| P4 真相少卖（=B 方案） | **700** | 1000 | 300 | 700 | ✅ | 宣传 1000 实卖 700，货不对板、少卖 30% |
| P5 只说「已有 300+ 人抢购」 | 1000 | — | 300 | — | 301 ✅ | 用「300+」化解 300+1000≠1300 的算术矛盾 |

> P3 与 P4 **业务结果完全相同**（可卖数 = 700），但 P3 只是前端软拦，直接调 API 就能买满。
> 所以若要少卖，就该像 P4 一样改 `stock_limit`，别用展示口径间接实现。

### 11.4 数据模型与红线

```sql
ALTER TABLE asset_package ADD COLUMN display_sold_base INTEGER NOT NULL DEFAULT 0;  -- 0 = 不虚标
CHECK (display_sold_base >= 0)
```

**三条红线（实现时最易踩）：**

1. **`soldOut`、下单校验、名额 CAS 全部只看真实剩余**。营销基数绝不能进任何业务判断，
   否则要么假售罄（白丢单），要么真超卖。
2. **展示剩余不得小于 0、也不得早于真实剩余归零**（P2 的恒等式已保证）。
3. **展示值只能涨不能跌**。因此 `display_sold_base` 在**已有真实成交后只允许调大**
   （`AssetPackageService#updatePackage` 已加此校验）；未开张时允许自由调整，方便修配置。

### 11.5 字段与落点

| 层 | 字段 / 行为 |
|---|---|
| 配置 | `asset_package.display_sold_base`（后台表单「展示已售基数」） |
| App 接口（`AssetPackageResponse`） | `stockLimit`(真实) / `displaySoldBase`(配置) / `displayTotal`(展示总数) / `soldQuota`(展示已售) / `remainingQuota`(展示剩余＝真实剩余) / `soldOut`(真实) |
| 后台列表（`AssetPackageListResponse`） | 保持**真实口径**（`remainingQuota`/`stockLimit`），另带 `displaySoldBase` 供列表打「已售基数」标签 |
| 小程序 | `resolvePromoLimit` 只取 `displayTotal` 与 `remainingQuota`（进度条用 `(total - remain) / total`），**不做任何加减与兜底**；售罄直接用 `pkg.soldOut` |
| 文案 | 「前 {displayTotal} 名专享优惠，仅剩 {remainingQuota} 个名额」（售罄时改为「名额已抢完」） |

> **关键收益**：展示口径全部由后端算好，前端零魔法数字。这就是 11.6 里 B 方案被否掉的核心原因。
>
> **前端为什么不需要 `soldQuota`**：P2 下 `展示已售 ≡ 展示总数 - 剩余`，需要时前端减一下即可，
> 所以小程序端的 `PromoLimit` 只有 `{ total, remain, progress }` 三个字段。
> `soldQuota` 保留在后端 DTO 里，给**后台管理端**做「对外展示」对照用。
>
> **售罄必须用 `pkg.soldOut`（后端按真实剩余判定）**，不要在前端用 `remain <= 0` 推导——
> 展示口径不参与售罄判断这条红线，要在前端也守住；即使当前二者等价，也不给未来留隐患。

### 11.6 为什么不选「前端 +300」（上一版讨论的 B 方案）

- 前端又回到硬编码（本轮刚清掉的历史包袱），且小程序/后台/H5 各写一份，口径必然漂移
- 前端算出的「剩余」与后端真实的 `soldOut` 两套账，真实销量涨上来后关系越来越乱
- 若同时把后端 `stock_limit` 调小到 700 来"凑"出「仅剩 700」，则**宣传 1000 实卖 700**，
  从"虚标销量"升级为"货不对板/虚假宣传"，风险等级完全不同，且**少卖 30%**（与刺激消费的初衷相反）

### 11.7 合规提示

「虚标已售」在《电子商务法》《广告法》口径下属于「虚构交易」的灰色地带，风险主要在**被截图举证**时。
若只需要紧迫感，更稳的写法是 P5（用「已有 300+ 人抢购」这类不可证伪的表述），
或保留 `display_sold_base` 可随时改为 0 的开关（P2 天然支持）。
