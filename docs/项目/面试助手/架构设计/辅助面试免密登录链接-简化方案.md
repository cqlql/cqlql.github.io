# 辅助面试免密登录链接（简化方案：Magic Login Ticket）

> 推荐方案（2026-07-23 复盘后）。若需要第三方授权、多角色（面试官 / 企业管理员 / 分享访客）等场景的设计，见 [辅助面试免密登录链接（原 Helper Session 方案）](./辅助面试免密登录链接.md)。

## 为什么从 Helper Session 转向 Magic Login

之前设计的 `ROLE_INTERVIEW_HELPER + 独立 Cookie + scope + helper session` 是偏 SaaS 多租户、多人协作场景的设计，对 PassUp 当前阶段偏重。

### 真实业务场景

```text
手机端
用户 A 已登录

点击：
辅助面试

↓

生成链接

↓

PC打开

↓

继续操作自己的面试
```

这里没有：

- 面试官邀请别人
- 候选人授权第三方
- 多人协作
- 外部分享

本质：

> 用户 A 给自己的另一个设备授权。

这和以下场景更像：

- 微信网页版登录
- 飞书扫码登录
- ChatGPT 登录新设备

---

## 简化方案：直接以用户身份登录（Magic Login Ticket）

### 手机端：生成一次性授权码

```
ticket
{
 userId
}
```

Redis：

```
login:ticket:xxx

{
 userId:1001
}

TTL 10分钟
```

### PC 端：兑换为普通用户登录态

```
/helper?t=xxx
```

exchange：

- 消费 ticket（GET+DEL）
- 创建 `PASSUP_SESSION`
- 普通 JWT：

```json
{
 "sub": 1001,
 "roles": ["ROLE_USER"]
}
```

流程：

```text
手机(已登录)
  |
  | 生成一次性授权码
  ↓
Redis

PC
  | 输入链接
  ↓ 兑换
普通用户登录态
  ↓
辅助面试
```

## 安全考虑

### Ticket 泄露风险

泄露：

```text
https://passup.ai/helper?t=xxx
```

别人打开即可获得用户登录态。

但注意，这个风险与以下同类：

- 微信网页版扫码登录
- 邮箱 Magic Link
- 密码重置链接

### 缓解措施

1. **Ticket 短时间**：10 分钟，足够手机 → 复制 → 切电脑 → 打开。
2. **一次消费**：GET+DEL，兑换后立即销毁。
3. **生成的普通 JWT 不要太长**：access token 2 小时，refresh token 走正常流程。

## 之前的 Helper Session 适用于什么场景？

| 场景 | 需要身份 | 说明 |
| --- | --- | --- |
| 第三方授权（邀请面试官 B） | `ROLE_INTERVIEWER` | B 不应成为 A |
| 候选人分享 | `ROLE_GUEST` | 访问者不是用户 |
| 企业版（HR 查看候选人） | 独立身份 | 需要独立权限 |

但「自己手机授权自己的 PC」不需要。

---

## 对 PassUp MVP 的建议

采用 **Magic Login Ticket** 而非 Helper Session。

### Redis 结构

```
interview:login-ticket:{token}

{
 userId
}

TTL 10min
```

### 兑换

```text
token
 ↓
用户身份
 ↓
正常登录
```

### 接口

```
POST /api/auth/magic-ticket
```

而不是：

```
/interview/helper-ticket
```

因为它本质不是面试授权。

### 辅助面试权限

正常走业务校验即可：

```text
GET /api/interview/current
```

检查：

```text
currentUser == interview.owner
```

## 何时再升级？

以后若出现以下需求，再引入 `AccessToken + Scope + Resource Permission`：

- 面试官：`ROLE_INTERVIEWER`
- 企业管理员：`ROLE_COMPANY_ADMIN`
- 分享链接：`ROLE_GUEST`

## 方案对比

| 方案 | 复杂度 | 适合 |
| --- | --- | --- |
| Helper Session | 高 | 第三方访问、多角色 |
| 普通用户 Magic Login | 低 | 当前 PassUp |
| 直接传 userId | 低但不安全 | 不要 |

> 不要为了未来可能出现的需求，把今天的核心流程复杂化。

PassUp 当前：

> **Magic Link 登录用户 + 正常权限控制**

是最合适的。不是说原来方案错，只是它解决了一个目前不存在的问题。你已有 Spring Security、JWT、Redis，实现成本非常低。

## 仍可复用的工程细节（来自原方案）

即便身份模型简化，以下"工程防护"仍然适用，建议保留：

1. **防社交软件预抓取**：`GET /helper?t=xxx` 只渲染页面，真正的兑换放在 `POST /api/auth/magic-ticket`，避免微信 / 飞书 / 钉钉的预览爬虫提前消费 ticket。
2. **防 URL / 日志泄露**：兑换成功后前端用 `history.replaceState` 擦除 `?t=`，避免残留在浏览器历史 / Referral。
3. **token 不可预测**：用 `SecureRandom` 生成 32 字符随机串（MVP 足够，无需 48）。
4. **一次性消费**：兑换用 Lua `GET+DEL` 原子操作，杜绝并发重复兑换。
5. **极简存储**：Ticket 直接存 Redis（不建表），TTL 10 分钟。
