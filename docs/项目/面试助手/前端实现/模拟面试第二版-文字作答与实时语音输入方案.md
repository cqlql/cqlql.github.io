## 1. 背景与目标

### 1.1 要解决的问题

V1 的整场音频上行（`/ws/audio` 二进制 PCM 帧）有三个连带成本：

| 问题 | 说明 |
| :--- | :--- |
| 网络与稳定性 | 每分钟约 60KB/s 的持续上行，网络抖动直接表现为卡顿、断连 |
| 用户表达成本 | 必须「说完」才能被识别，思考型用户（面试做题思路）被迫在语音里组织语言 |
| 环境限制 | 开会、办公室、图书馆等场景无法开口说话 |

V2 的目标：**默认用文字作答**，让「不愿/不便开口」的用户能完成整场模拟面试；语音只作为想偷懒时的快捷输入。

### 1.2 目标形态

- 交互形态对齐 `pages/ai-qa`：气泡对话 + 底部输入区，用户发一条、AI 面试官回一条（流式）。
- 输入框右侧一个**话筒按钮**：点击开始实时语音识别，识别文本实时写入输入框。
- V1 的会话语义（一场面试、时长计费、面试记录、暂停恢复）**不因形态变化而消失**，接入时需继续满足（见 6.3）。

## 4. 页面设计

### 4.1 路由与入口

```text
面试助手首页「步骤一：模拟面试」
  └─ /pages/mock-interview-setting/index            → 开始面试 → /pages/mock-interview/index     （V1，默认，行为不变）
  └─ /pages/mock-interview-setting/index?mode=text  → 开始面试 → /pages/mock-interview-v2/index  （V2）
```

- 设置页用 `useRouter().params.mode` 判定形态，**不传即 V1**，因此现有入口完全不受影响。
- V2 下不校验麦克风授权、也不显示「请先授权麦克风权限」的拦截提示：文字作答不需要麦克风，语音输入是可选项，权限在点话筒时才申请。
- 入口是否切到 V2（甚至砍掉 V1）属产品决策，留待接口接入后再定，见第 9 节。

> ⚠️ **`?mode=text` 不是后端的 `input=text` —— 两者不能互相透传**（接线时最容易踩的一处）：
>
> | | 含义 | 取值 | 归属 |
> | :--- | :--- | :--- | :--- |
> | 页面参数 `?mode=text`（设置页 → 页面） | 选**页面形态**（V1 语音版 / V2 文字版） | `text` / 不传 | 前端路由 |
> | WS 建连参数 `input=text` | 选**作答方式**（起不起 ASR、收不收 `ANSWER`） | `audio` / `text` | 后端会话 |
> | WS 建连参数 `mode=mock` | 选**面试模式**（AI 是面试官还是求职者） | `assist` / `mock` | 后端会话 |
>
> V2 建连是 `mode=mock` + `input=text`。若把页面的 `mode=text` 直接透传：
> 后端 `InterviewMode.from('text')` 会**静默回退成 `ASSIST`**，随后被 `assist + text` 组合校验拒掉 ——
> 表现为"建连就失败"，但根因是页面参数被当成了会话参数。

### 4.2 页面结构

```text
┌──────────────────────────────────────────┐
│ 模拟面试            剩余 12:34 [暂停][结束] │  ← 顶栏：左＝标题 + 状态提示；右＝剩余时长 + 操作
│ 面试进行中                                 │
├──────────────────────────────────────────┤
│  ● 面试官开场白（AI 气泡，左）             │  ← ChatList（复用）
│                       用户回答 ●（右）    │
├──────────────────────────────────────────┤
│ （暂停态才出现）面试已暂停…      [继续面试]  │  ← 暂停条
├──────────────────────────────────────────┤
│ （识别中才出现）● 正在聆听，说话内容会实时…  │  ← 语音识别状态条
├──────────────────────────────────────────┤
│ [ 输入你的回答…        ] (话筒) (发送)     │  ← 输入区
├──────────────────────────────────────────┤
│            内容由AI生成，仅供参考          │  ← 免责声明（与 V1 一致）
└──────────────────────────────────────────┘
```

- 尺寸单位统一 `px`（`designWidth: 375`，与 `mock-interview-setting`、`formal-interview-assistant` 等新页面一致）。
- 底部预留 `env(safe-area-inset-bottom)`，避免全面屏机型压住免责声明。
- **操作集中在顶栏**（2026-09-23 调整）：剩余时长 / 暂停（暂停态为「继续」）/ 结束都在头部右侧，
  做成竖向圆角胶囊（`align-self: stretch` + 上下 10px 边距，随头部高度自适应）；
  底部只留输入区与免责声明。**没有「文字作答」形态标签**（入口已经区分形态，标签是冗余信息）。
- 输入胶囊（`input-wrapper`）**外层不留 padding**：留白一律下沉到子元素（文本缩进给原生 `input` 的 padding，
  按钮的视觉圆形留给内层 `*-inner`，外层 42px 只作热区），否则外层留白是"看起来有边距、点上去没反应"的死区。

### 4.3 交互

| 操作 | 行为 |
| :--- | :--- |
| 输入后点发送（或键盘回车） | 追加用户气泡 → 清空输入框 → 上传 `ANSWER`，AI 追问以 `loading` 气泡占位并逐字填充 |
| 发送后（AI 未回复完） | **输入框与发送按钮禁用**（这是 `TURN_BUSY` 的语义要求，见 §6.1）；收到 `LLM_REPLY.final` 或 `ERROR` 后恢复 |
| 点话筒（空闲） | 申请麦克风权限 → 开始识别 → 按钮变红并出现状态条 |
| 点话筒（识别中） | 结束识别（`stop`），保留已识别文本；识别连接由 transport 在**空闲 ~8 秒后自动释放** |
| 点发送（识别中） | **先停识别再发送**（`useSpeechInput` 的 `stop()`）：输入框马上要清空，识别结果再写回来会变成"幽灵文字"（用户没说的话出现在空输入框里） |
| 录音达到单次上限（**180 秒**，`MAX_RECORDING_MS`） | 录音由微信自动停止，**明确提示「已到单次语音上限，可再点话筒继续说」**，不能静默停止（否则用户会以为识别坏了）。**界面上不显示已用时长**（2026-09-24 决定：提示条只写"正在聆听…"，不拿数字分散注意力） |
| 输入为空 | 发送按钮置灰不可点；同时前端做长度拦截（上限 2000 字，后端会拒） |
| 点「暂停」（进行中时出现在头部） | 先弹确认（暂停会取消在途回复、超 15 分钟面试就结束，值得挡一下）→ **同时立即停止语音输入**（只停录音与推帧；识别通道由 transport 在空闲 ~8 秒后自行释放）→ 发 `PAUSE` → 收 `PAUSED` 后进入暂停态：输入区禁用、底部出现暂停条 + 「继续面试」，**头部同一位置也由「暂停」变为「继续」**；暂停**不往对话流里补记录**（暂停是状态，不是对话内容，状态栏已有提示） |
| 点「继续面试」/ 头部「继续」（暂停态） | 两处等价，都是 `handleResume`；用 `resume=<逻辑会话ID>` 重连：**复用原上下文与计费，不重发首问**；超时或记录不可恢复 → `RESUME_EXPIRED` / `RESUME_FORBIDDEN` → 提示"暂停会话已失效，请重新开始面试" |
| 点头部「结束」（红胶囊，与「暂停 / 继续」并列） | 断开连接 → 提示「面试已结束」→ 600ms 后跳转：**用了通用模板进「体验完成」引导页**，否则返回上一页（细节见 §6.3.3）；**语音输入通道随之释放**（`terminated` → `dispose()`，页面不手工调用） |

## 5. 实时语音识别方案

### 5.1 分层

```text
页面（mock-interview-v2）
  └─ useSpeechInput（features/speech/hooks）      ← 权限申请、识别文本与输入框的合并规则、卸载释放
       └─ SpeechRecognizer（features/speech）      ← 平台判定、录音采集、生命周期收尾、错误归一
            └─ AsrTransport（features/speech）     ← 【唯一待接入点】把 PCM 帧送出去、把文本收回来
```

**接入识别服务只需要实现 `AsrTransport` 并在 `createAsrTransport()` 里换掉返回值**，页面与 Hook 无需改动。

### 5.2 路线取舍（方案 A 已定稿，B 仅作历史备选）

| 维度 | 方案 A：服务端流式 ASR（推荐） | 方案 B：微信同声传译插件 WechatSI |
| :--- | :--- | :--- |
| 文本来源 | 后端 ASR，前端推 PCM 帧、收识别文本 | 插件内置识别，零后端 |
| 前端改动 | 实现 `AsrTransport`（新通道，如 `/ws/asr`） | 页面配置声明插件 + 换 Hook 内部实现，`AsrTransport` 不再需要 |
| 跨端 | 采集能力本来就仅微信端，与 A 相同 | 仅微信端 |
| 额外成本 | 后端需提供识别通道 | **需在小程序后台添加插件**、需用户授权该插件 |
| 与面试链路 | **通道独立、资格挂靠**：不产生面试计费、不触发 AI 回复；但必须有进行中的面试才能建连（后端方案 §4.2.5） | 完全独立 |
| 风险 | 需要后端配合 | 插件不可用/未授权时无法自愈，构建与运行都依赖后台配置 |

> **已定稿：正式方案是 A（服务端流式 ASR）。** 方案 B（微信同声传译插件）**不进入实现范围**，仅作为历史备选保留上表：
> 它引入的是插件声明 + 后台配置 + 用户授权三层外部依赖，且会与既有 ASR 能力形成两套语音输入链路；
> 而后端方案 §3 已经做了同样的取舍（A / B / C 三选一，结论 A），并明确"识别不依赖任何第三方插件"。
>
> **A 的落地节奏**：前端已经把通道抽象出来（`AsrTransport` 留桩）；**后端 `/ws/asr` 也已交付**
> （2026-09-22，后端 Step 2：路由 + 轻量鉴权 + 并发/时长上限，复用 `AsrStreamRunner`）。
> 因此现在唯一缺的就是**前端把 `AsrTransport` 的占位实现换成真实传输**（协议见 §6.2）。

还有一条**不推荐**的取巧路线：复用现有 `/ws/audio` 的音频上行，只取回包的 `ASR_RESULT` 而忽略 `LLM_REPLY`。它会让每次语音输入都额外产生一场面试会话与时长消耗，且 AI 会同时抢答，仅在「后端支持纯识别模式」时才值得考虑。

### 5.3 识别文本写入输入框的规则

以「基准 + 草稿」两段式合并，保证**边说边改**不覆盖用户已输入的文字：

```text
点话筒那一刻：base = 输入框当前内容，draft = ''
收到 final=false（流式中间态）：draft = 该片段        → 输入框 = base + draft
收到 final=true （定稿）      ：base = base + 片段，draft = '' → 输入框 = base
```

- 中间态是**覆盖**而非追加，否则会出现「我我我想想」这类叠字。
- 定稿后 `base` 才前进，因此连续说多句会依次追加，标点随服务端结果带回。
- 用户手动输入的内容作为 `base` 起点保留，不会被识别结果清空。
- `value/onChange/onError` 通过 ref 读取最新值，避免识别过程中每次结果触发重渲染而拿到旧闭包。

**边界：识别过程中用户手动改字（补一条，否则会覆盖用户刚改的内容）**

```text
ASR 识别中 → 用户手动改了输入框 → 后续 ASR 中间结果到达
```

- 规则：**用户一旦手动编辑，就视为"用户接管输入"** —— 把 `base` 重置为"用户编辑后的输入框内容"、
  `draft` 清空；之后 ASR 结果继续按"中间态覆盖 `draft` / 定稿追加 `base`"处理，
  **不再回滚用户改过的内容**。
- 实现：`onChange` 里区分"程序写入"与"用户输入"（程序写入时置一次性标记），
  非程序触发的 `onChange` ⇒ `base = 最新值; draft = ''`。
- 为什么必须定义：两段式只解决"边说边改"，没解决"人机同时改" ——
  用户把 `Redis` 改成 `Redis Cluster`，下一个中间态会把改动吃掉。

### 5.4 跨端与降级

- 实时帧回调（`RecorderManager.onFrameRecorded`）**是小程序专属能力**，H5/其他端无等价实现。
- 识别器构造时即判定 `process.env.TARO_ENV === 'weapp'`，非微信端点话筒直接返回 `UNSUPPORTED_PLATFORM`，页面提示「当前端暂不支持实时语音识别，请手动输入」——**输入框与发送链路不受影响**。
- 因此 V2 页面在 H5 端可用（只是不能语音输入），不违反跨端规范。

### 5.5 权限与错误处理

| 时机 | 处理 |
| :--- | :--- |
| 首次点话筒 | `Taro.getSetting` 查 `scope.record` → 未授权则 `Taro.authorize` |
| 用户此前拒绝过 | `authorize` 不再弹窗，弹 `showModal` 引导「去设置」→ `Taro.openSetting()` |
| 录音失败 | `onError` 归一为 `RECORD_FAILED`，页面 Toast 提示，同时清理通道（不留下挂着麦克风的空会话） |
| 识别通道不可用 | `transport.start()` **返回 Promise，失败即 reject**（凭证失效 / **没有进行中的面试** / 并发超限 / 配额用完都走这条），**不启动录音**（不开一个没有出口的麦克风） |
| 面试**暂停** / AI 正在回复 | `enabled=false` → `stop()`：停录音与推帧、`listening` 归位；连接由 transport 在**空闲 ~8 秒后自行释放**（恢复后再点话筒会新建一条 —— `start()` 本来也会先释放旧的） |
| 面试**结束**（主动结束 / 掉线 / 余额耗尽 / 暂停超时） | `terminated=true` → `dispose()`：真正关闭 `/ws/asr`，并把 `listening` 归位；此后到达的识别结果 / 错误 / 超时提示**一律丢弃** |
| 离开页面 | `dispose()`：停录音、释放通道；`dispose` 后忽略一切异步回调 |
| 单次时长上限 | 录音 `duration: MAX_RECORDING_MS`（**2026-09-24 由 60 → 120 → 180 秒**），到点由微信自动停止，与手动停止走同一套收尾（用户想继续再点一次话筒）；**它是"单次回答允许说多久"的产品口径**，与后端"物理连接绝对上限 300 秒"是两个概念（见 §5.6 末尾） |
| 到达单次上限 | ✅ **已实现（2026-09-23）**：由 `SpeechHandlers.onTimeout` 给显式提示（「本次语音输入已结束，可再次点话筒继续」）：静默停止会被当成"识别坏了" |

> **录音参数的官方依据**（2026-09-24 核对微信开放文档 `RecorderManager.start`）：
> - `duration` 官方默认 **60000**、**上限 600000（10 分钟）** —— 原来的 60000 就是"官方默认值"，
>   现在的 **180000** 是产品口径（= 官方额度的 3/10），两者都不是"规则上限"；
> - `frameSize`（单位 KB）官方注明**传入才会有帧回调**，且**暂仅支持 mp3 / pcm**
>   —— 所以 `format: 'PCM'` + `frameSize: 4` 不是可选优化，而是"实时识别"这条链路的**硬前提**；
> - `sampleRate: 16000` 配 `encodeBitRate: 48000` 落在官方「采样率 × 编码码率」合法区间
>   （16000 → 24000~96000）内；官方原文明确**不合法的组合会导致录音失败** —— 改参数前先对表；
> - 两处端/版本限制留意：`sampleRate` **PC 不支持**（微信 PC 版跑小程序时录音参数未必完整支持）；
>   官方另有 `audioMode: 'voiceRecognition'`（基础库 3.17.3+，噪声抑制 + 自动增益）**尚未启用**，
>   若嘈杂环境识别率不理想可作为候选（需真机对比后再定）。

> 停止识别时**不立即释放通道**：流式识别常在停止后才吐出最后一段定稿文本，因此留一个约 **8 秒**的空闲窗口
> （`WsAsrTransport#stop()` 的 `IDLE_RELEASE_DELAY_MS`）再断开，避免最后一句丢失。
> **但不能无限期保留**（2026-09-24 更正）：后端 `DoubaoAsrClient` 有静音保活，挂着的豆包会话会继续按
> 音频时长计费 —— 原注释里"这条通道不计费、多留一会儿没有成本"是**错的**；后端另有 25 秒上游空闲兜底
> （见后端方案 §4.2.4）。
>
> Hook 对外是 `{ listening, toggle, stop }`：`toggle` 给话筒按钮做"开 / 关"，
> `stop` 给「发送作答」这类**必须停**的场景调用 —— 它不做状态反转，
> 免得在竞态（刚点话筒、还在建连）时反而把识别开起来。
>
> **入参 `enabled` / `terminated` 是资源生命周期的唯一开关**（2026-09-24 加，见 §6.2 的「生命周期收口」）：
> 页面只回答"现在还能不能录音"，**不直接操作 WebSocket** —— "什么时候真的断开连接"只由 hook 决定。

### 6.1 会话与消息（本页面的核心缺口）

| 能力 | 建议形态 | 说明 |
| :--- | :--- | :--- |
| 开场白 | 会话创建时后端下发第一题 | ✅ **已落地（2026-09-23）**：删掉了固定文案 `GREETING` —— 建连成功即起算，首问由后端下发（首条下行是 `THINKING`） |
| 提交回答 + 收追问 | **走 `/ws/audio` 的 WS 上行**：建连带 `input=text`（且 `mode=mock`），上行 `{"type":"ANSWER","text":"..."}`（**不是流式 HTTP**）。**后端已可用**（Step 1），协议已登记 | 下行沿用既有协议：先 `THINKING`、再 `LLM_REPLY` 流式分片（`final` 标记收尾，`replyId` **由后端生成**）。UI 侧仍是「用户气泡落地 → `loading` 占位 → 首字到达取消 → `error` 还原输入」 |
| 历史记录 | 复用 `/api/interviews/history` 与详情 | 文本版是否与语音版混在同一列表，需产品确认 |

> **为什么不是流式 HTTP（2026-09-22 与后端方案对齐后修订）**：会话计时、心跳、暂停恢复、顶号、余额下发
> **全在 WS 连接上**，且逻辑会话与计费状态由 `InterviewSessionState` + `InterviewBillingService` 持有。
> 走 HTTP 等于把这三套在服务端再实现一遍；更关键的是 HTTP 无连接后"连接失活判据"直接失效
> （后端方案原文见《模拟面试第二版-语音识别与LLM回合解耦方案》§4.1.3）。
>
> 因此：**`QnaChat.tsx` 只能借鉴它的 UI 侧模板**（`loading` 占位 / 逐字填充 / 错误还原输入），
> 传输层必须换成 WS 消息（`THINKING` / `LLM_REPLY`），**不要照搬 `streamPost` 那套 `onMeta/onDelta/onDone/onError`**。

**接线契约（引后端方案，别在这里另抄一份协议）**：

- **建连**：`input=text` 且 `mode=mock`。`assist + text` 不是合法组合，后端在建连阶段直接失败
  （握手错误 `INTERVIEW_PREPARE_FAILED`）；页面入口的 `?mode=text` 不要透传（见 §4.1 的对照表）。
- **上行**：`{"type":"ANSWER","text":"…"}`。**不做幂等、不要加 `answerId` / `clientMsgId`** ——
  后端上行解析是严格的（`Jsons.parse` 默认遇到未知字段即失败），多一个字段会让**整条作答被丢弃**。
  将来若要做"失败重试"，两端同版本一起加 `clientMsgId` 并由后端去重。
- **前端先拦**：非空 + 长度上限 **2000 字**（输入框 `maxLength`）。
  否则后端会回 `INVALID_ANSWER` / `ANSWER_TOO_LONG` —— 白跑一次往返。
- **`TURN_BUSY` 是"发送后禁用输入框"的实现依据**：首问或上一轮还在流式输出时，后端会拒绝本次作答。
  页面应保持禁用 + 提示「AI 正在回复中」，等 `LLM_REPLY(final=true)` 再恢复输入。
  > **`final` 分片就是流式响应的末分片，它带最后一段正文**：收尾时仍按**追加**处理（`prev + text`），
  > **不要**改成"用 final 的文本整段替换"；一轮回复只应有一条 final 分片。
  > 另注意字段名以实际 JSON 为准（是 `final`，不是 Java 侧的 `isFinal`）——
  > 判错会得出"结束信号没来"的假结论（后端方案 §12.6.1 记了这个坑）。
- **`replyId` 由后端生成**（文本作答没有 ASR id）：前端按 `onThinking(replyId)` 建占位气泡、
  按 `LLM_REPLY.replyId` 填充，**不要自己造 ID、也不依赖其格式**。
- **错误码已登记**在 `features/interview/ws.ts`：`INVALID_INPUT_MODE` / `TURN_BUSY` / `INVALID_ANSWER` /
  `ANSWER_TOO_LONG`（均**非终止性**，不进 `FATAL_CODES`；`TURN_BUSY` 只是"稍后再发"）。
- **就绪点**：text 模式**建连成功即起算**，并且 MOCK 首问由后端**立刻下发**（首条下行是 `THINKING`）——
  所以页面不需要"先发一句才激活"，也不要用固定文案兜底开场白（接入后删掉 `GREETING`）。

**落地记录（2026-09-23，`pages/mock-interview-v2/index.tsx`）**：

| 要点 | 实现 |
| :--- | :--- |
| 建连 | `connect({ mode: 'mock', input: 'text', wsBaseUrl, language / detailLevel / interviewStyle（沿用设置页）, templateUid: getSelectedTemplate()?.uid })` |
| 首问 | **已删除固定开场白**：建连成功即起算，首条下行就是后端下发的 `THINKING` + 追问（不再用 `GREETING` 兜底） |
| 作答 | 乐观渲染用户气泡 → `sendAnswer(text)`；输入框 `maxLength=2000`，非空 / 超长在前端先拦 |
| 输入框禁用 | `canAnswer = status==='active' && !replying`；发送时置 `replying`，`onLlmDone` / 非终止性错误 / 会话结束时恢复（话筒按钮同样受它约束） |
| 发送即结束语音输入 | `handleSend` 校验通过后先调 `useSpeechInput` 的 `stop()` 再发送：输入框紧接着会被清空，识别结果再写回来就成了"幽灵文字"（细节见 §6.2 落地记录） |
| 流式渲染 | `onThinking(replyId)` 建占位气泡（typing 指示器）→ `onLlmDelta` 追加 → `onLlmDone` **追加末分片正文**并恢复输入（final 分片带正文，是追加语义） |
| `TURN_BUSY` | **收回**那条未被接受的作答（删气泡 + 把文字还回输入框）**并保持禁用**，等当前这轮的 `final` 到了再让用户重发 —— 既守"忙时不放行"，也不让用户白写一段话 |
| 其他非终止性错误 | `INVALID_ANSWER` / `ANSWER_TOO_LONG` 同样收回并还回输入框；`INVALID_INPUT_MODE` 属客户端配置错误，按结束处理 |
| 终止性错误 | `AUTH_FAILED` / 余额类 / `HEARTBEAT_TIMEOUT` / `SESSION_REPLACED` → 收尾 + 在对话流里补一条**错误气泡**（用户回看时知道发生过什么）；余额类跳充值页（沿用 V1） |
| 剩余时长 | `onTimeUpdate` → 头部显示「剩余 mm:ss」（会话按时长计费，用户需要随时能看到）。服务端 `TIME_UPDATE` 只是**间隔快照**，照抄下来会一跳一跳，因此前端以「快照秒数 + 收到时刻」为基准（`timeSyncRef`）**本地每秒递减**，每条新快照重新对齐、避免误差累积；只在 `active` 时走秒（暂停即停表），离开进行中时把当前剩余**定格**为新基准，恢复时从定格值接着数，等新快照到了再按服务端口径对齐 |
| 看门狗（前端自加） | 后端在 LLM 流式失败时**不下发 ERROR**（只落日志），前端会永久停在"回复中" → **90 秒内一条下行消息都没有**即恢复输入框。误判代价小（提前发送会被 `TURN_BUSY` 拒并回到禁用），漏判代价大（输入框卡死） |

> 看门狗这条其实指向一个**后端语义缺口**：LLM 失败本该有一条明确的错误码，而不是让客户端靠静默超时猜。
> 本轮先在前端兜住，是否在后端补 `ERROR`（如 `LLM_FAILED`）尚未定 —— 记在**待议**，不在本方案强制范围。

### 6.2 语音识别通道（第 5 节的 `AsrTransport` 实现）

无论走哪条路线（现在是 A），`AsrTransport` 对外都只产出 `SpeechResult{ text, final }`：

- 方案 A：`start` 建连（带鉴权）→ `pushFrame` 推 16k/16bit/单声道 PCM → 回包按「中间态/定稿」分别 `onResult`。
- 方案 B：`start` 调插件开录 → 插件回调直接是文本。

**方案 A 的落地状态（2026-09-22 第二次修订）**：

> ✅ **`/ws/asr` 后端侧已交付**（后端方案 Step 2）：端点注册 / handler / 识别会话 / 轻量鉴权拦截器都齐了，
> 识别运行本体复用 `AsrStreamRunner`（P0-1 产物：重连预算、退避、残留帧丢弃、`asrId` 轮换）。
> 所以前端现在**可以开始实现 `AsrTransport`**（不再是"等接口"）。

实现时的三步 + 协议要点（**事实以后端方案 §4.2.2 为准**）：

1. **点话筒才建连**（带 ticket，走同一个 `GET /api/ws/ticket`）；停止识别后不必立刻断开
   （等最后一次定稿文本），`dispose` 时释放 —— 与 5.3 一致；
2. 推 PCM 帧（16kHz/16bit/单声道，与 `recorder.ts` 参数一致），按 `ASR_RESULT` 的 **`final`** 字段
   分流中间态/定稿（**`final` 是 Step 2 新增的字段**，两条通道都会带）；
3. 记住这条通道**物理上与面试会话无关**：不计费、不触发 AI 回合、识别失败**不会**影响面试
   （与 `/ws/audio` 的 `ASR_UNAVAILABLE` 杀会话完全不同）。但它的**使用资格来自面试**
   （后端方案 §4.2.5，✅ 已实现）：必须有进行中的面试才能建连，面试结束会被服务端**静默回收**。

**实现 `AsrTransport` 时要一并做的两件事**：

- **登记错误码**（这条通道自己的语义空间，**不要塞进 `ws.ts` 的面试错误码**）：
  `AUTH_FAILED`(4001) / `ASR_LIMIT_EXCEEDED`(4004，先关掉自己那条旧识别连接再重试) /
  `ASR_QUOTA_EXCEEDED`(4006，今日次数已用完，**重试无用**、不要自动重连，提示改用打字) /
  `ASR_UNAVAILABLE`(4003，提示改用打字) / `ASR_TIMEOUT`(4005，当作"本次语音输入已结束")；
  ✅ **`ASR_NO_ACTIVE_SESSION`(4007，2026-09-24 已登记)**：没有进行中的面试，提示「请先开始面试」，
  **不要自动重连**（除非用户重新开始了一场面试）；
  正常结束是 1000（含"面试结束被服务端回收"），静默收尾即可。
  > 四道闸门顺序：凭证 → **资格** → 并发 → 日配额（后端已写死）。三者的引导各不相同：
  > 资格是"去开始面试"、并发是"先关掉旧连接"（可即时自救）、配额是"改用打字"（重试无用）——
  > **别合成一句提示**。
  > 4007 已进 `transport.ts` 的白名单与关闭码映射 —— **不登记的话**它会落进"未知码 → `ASR_UNAVAILABLE`"
  > 兜底，把「去开始面试」说成「改用打字」（同一份代码里那个兜底是从第一版就有的）。
- **上行只发音频**：这条通道没有心跳、没有控制指令（后端收到文本只记日志）；
  连接存活由后端**物理连接绝对上限**兜底（`session-max-duration-ms`，**300 秒**，绝对墙钟、不重置）。
⚠️ **两个概念别混**（2026-09-24 明确）：**单次回答允许说多久** = 前端录音上限（`duration: MAX_RECORDING_MS`，**180 秒**）；
**连接能活多久** = 后端那个 300 秒（**关系固定为「后端 = 前端 + 120 秒余量」**）。后者只兜"客户端该关没关 / 连接悬挂"，正常路径由前端的 8 秒空闲释放先收掉。

> 后端侧对这条通道的禁区是**硬约束**（后端方案 §4.2.1）：`/ws/asr` 不接 `SessionRegistry`、
> 不走 `requestClose` / `cleanup`、不创建/修改 `Interview`、不计费、不落库、不触发 LLM；
> 自检句是「**识别失败时会不会有人想动面试状态？**」—— 答案是"不会"才没跑偏。
> 前端侧同构的一条：**识别失败只提示"改用打字"，不要因此去动面试连接**。

**落地记录（2026-09-23，`features/speech/transport.ts` + `recognizer.ts`）**：

| 要点 | 实现 |
| :--- | :--- |
| 建连 | `start()` 取 ticket（`GET /api/ws/ticket`，**各自取各自的**：一次性消费）→ 连 `/ws/asr?ticket=` → 等 `onOpen` 才算成功 |
| 接口签名 | `AsrTransport.start()` 从"同步抛错"改为**返回 Promise**（建连本就是异步的，只有它能表达"通道没建起来"）；`SpeechRecognizer.start()` 随之改异步 |
| **先建连、后开录音** | 凭证失效 / 并发超限 / 配额用完时**根本不打开麦克风** —— 否则会出现"录音在跑、识别通道没有出口"（麦克风常亮，用户以为在识别） |
| 下行结果 | `ASR_RESULT{ text, final }` → `SpeechResult`（**`final` 与 `isFinal` 两种字段名都认**，见后端方案 §12.6.1） |
| 错误码 | 按通道语义空间映射为用户文案（`AUTH_FAILED` / `ASR_LIMIT_EXCEEDED` / `ASR_QUOTA_EXCEEDED` / `ASR_UNAVAILABLE` / `ASR_TIMEOUT`），**没有塞进 `ws.ts` 的面试错误码**；并发与配额**分开提示**（一个能自救、一个重试无用） |
| 关闭码 | `1000` 静默收尾；**`4005`（时长上限）在已停止推帧时按正常结束处理**（用户早就说完了，不该弹"出错了"）；其余按原因提示 |
| `stop()` 不立即断开 | 流式识别可能在停止后才吐最后一段定稿文本 → **空闲 ~8 秒后自动断开**（`IDLE_RELEASE_DELAY_MS`；`start()`/`dispose()` 都会清掉那个定时器）。原来说"这条通道不计费、多留一会儿没有成本"是错的：后端静音保活会让挂着的豆包会话继续按时长计费 |
| `stop()` 的两种时机 | ① **识别中**（`active`）→ 停录音 + 通知页面；② **建连中**（`starting`，麦克风还没打开）→ 只置 `canceled`，建连完成即释放通道、**不打开麦克风**（此时没触发过 `onStart`，因此不回调 `onStop`）。②是"点话筒后立刻点发送"的兜底：没有它，那次识别会先建连、后开麦，用户明明已经发出去了 |
| 服务端主动结束 | 识别器**先把录音管理器停掉**再通知页面：避免"识别通道已经没了、麦克风还在采集"（既是隐私问题也白耗电） |

**生命周期收口（2026-09-24，`useSpeechInput` + 页面只多传一个判据）**：

起因是一个**前端资源生命周期 bug**（与后端无关）：`transport.stop()` 的语义是"停推帧、**保留连接**"，
而页面在会话结束时没有任何地方去 `dispose()`，于是：

| 现象 | 之前 | 现在 |
| :--- | :--- | :--- |
| 面试结束（掉线 / 余额耗尽 / 主动结束） | 识别连接残留到后端 300 秒上限；话筒按钮已被禁用，**用户关不掉**；"正在聆听…"还挂在已结束的页面上 | `terminated=true` → `dispose()` 立即关闭；`listening` 归位 |
| 暂停 / 恢复 | `listening` 卡在 `true`，恢复后点话筒**反而把识别停掉**（要点两次才真的开始） | `enabled=false` → `stop()` + `listening=false`；恢复后点话筒正常开始 |
| 发送后迟到的定稿片段 | 写回刚清空的输入框（幽灵文字） | 生命周期闸门丢弃 |
| 结束后迟到的失败通知 / 超时提示 | 在已结束的页面上弹 toast | 丢弃 |
| **停止说话后连接一直挂着**（2026-09-24 补） | `stop()` 只停推帧，连接留到下一次点话筒 / 页面卸载 —— 期间豆包会话靠静音保活一直活着（**静音帧同样按时长计费**），最长到后端 300 秒 | `WsAsrTransport#stop()` 起 **8 秒空闲定时器**：到点仍没再 `start()` 就 `dispose()`（尾包照样落地） |
| **客户端该关却没关**（崩溃 / 老版本 / 小程序切后台定时器不跑） | 连接挂到 300 秒上限，豆包侧一直在喂静音；并发闸门也被占着 | 后端 **25 秒**上游空闲兜底（**只对 `/ws/asr`**，见后端方案 §4.2.4）：静默关闭（1000、无 ERROR），指标 tag `input_idle` |

实现要点（三条，改代码前先看）：

1. **两个入参的语义**：`enabled` = "现在能不能录音"（暂停 / AI 生成中 / 未就绪都是 `false`），
   `terminated` = "是否彻底不需要识别通道"（**只有面试结束才为 `true`**）。页面传的是
   `enabled: canAnswer`、`terminated: status === 'ended'` —— 与输入框 / 话筒 / 发送按钮**共用同一个判据**，
   避免"按钮说不能用、hook 却还活着"这类漂移。
2. **闸门在渲染期同步赋值**（`enabledRef.current = enabled`），不走 effect：
   识别回调可能在任意时刻到达，用 effect 会留下"状态已变、effect 还没跑"的一帧窗口。
3. **`stop()` 里也要显式 `setListening(false)`**：识别器在"建连中被要求停止"那条分支不会回调 `onStop`。

> `enabled` 用的是 `canAnswer`（= `status === 'active' && !replying`）而不是单纯的 `status === 'active'` ——
> 多排除"AI 正在回复"这一档，顺带把上表第 3 行（发送后迟到定稿写回输入框）也一起堵住。
>
> ✅ **已接（2026-09-24）**：`ASR_NO_ACTIVE_SESSION`(4007) 已登记进 `features/speech/transport.ts`
> （错误码白名单 + 关闭码映射 + 文案「请先开始面试」），不会落进 `ASR_UNAVAILABLE` 的兜底。
>
> 另外前端这套收口与后端 Step 4 是**互补**的、不是替代关系：前端负责"面试结束就自己释放"，
> 后端负责"面试结束就把服务端这条连接收掉" —— 两边幂等，谁先到都不会报错。

### 6.3 会话生命周期（接入时必须一起解决，不能只接"发消息"）

V2 只是把上行从音频换成文本，**产品语义仍是一场有时长的面试**。
下表区分"后端已实现（直接消费）"与"仍待产品定"：

| 机制 | 状态与做法 |
| :--- | :--- |
| 建会话与结束 | ✅ 已实现（后端 + 前端）：**建连成功即起算**（text 模式不再等 ASR 就绪），MOCK 首问由后端立刻下发；结束时生成面试记录。前端收尾见 §6.3.3：头部「结束」→ 用通用模板进「体验完成」，否则返回上一页 |
| 计时与计费 | ✅ 后端已实现：**文本模式同样按会话时长计费**（思考时间算面试时间），且**不做"无操作自动暂停"**（已定稿）。「文本模式单价是否与语音一致」仍属商业决策（见 §9-3） |
| 心跳 | ⚠️ **硬要求**：建连后立即发一次 `{"type":"heartbeat"}`，之后**每 25 秒一次**，随连接启停。文本模式下「思考 1 分钟再回」是常态，心跳比语音模式更关键（小程序 V1 的 `InterviewSocket` 已内置，V2 复用它即可，页面**不要自己 setInterval**）。**失联阈值**：语音 60 秒 / 文字作答 **180 秒**（`realtime.text-heartbeat-timeout-ms`，见 §6.3.1） |
| 暂停 / 恢复 | ✅ 后端已实现：显式 `PAUSE` → `PAUSED`，用 `resume=<逻辑会话ID>` 重连，重连后**仍是 text**（`input_mode` 已落库还原）。<br>✅ **前端入口已实现（2026-09-23）**：头部「暂停」（带确认弹窗）→ 暂停条 + 「继续面试」，**头部同一位置也变为「继续」**（两处等价，都是 `handleResume`）；时序与守卫见 §6.3.2 |
| 多端顶号 | ✅ 沿用 V1：同一用户新建连接会踢掉旧连接 |
| 计费活跃度判据 | ✅ **不沿用"无音频即静默"**：只看心跳。后端**不做「收到 `ANSWER` 就当心跳」的特例**（那样"正在思考"与"已掉线"无法区分）—— 这正是心跳是硬要求的原因 |
| 失联 vs 暂停 | ⚠️ **失联 = 结束，显式 `PAUSE` = 暂停** —— 见 §6.3.1，这条最容易被当成 bug |

#### 6.3.1 两条状态机（分开写，别合并）+ 三条容易混的语义

**① 后端权威的会话状态**（前端只消费，不定义）：

```text
pending ──(WebSocket 建连)──→ active ──(显式 PAUSE)──→ paused ──(resume=逻辑会话ID)──→ active
                                │                        │
                                └──── 结束 / 失联 / 余额耗尽 / 暂停超时 ────→ ended
```

> （这是 `interview.status` 的取值；内存里的逻辑会话只有 `ACTIVE` / `PAUSED` / `ENDED` 三态，
> `pending` 只存在于"准备好了但还没建连"这个短暂窗口。）

**② 前端回答气泡的 UI 状态**（与上面的会话状态**无关**）：

```text
sending ──→ thinking ──→ streaming ──→ done
                 │             │
                 └─────────────┴──→ error（还原输入框 / 提示）
```

- 由后端事件驱动：`THINKING` → `thinking`；`LLM_REPLY(final=false)` → `streaming` 并追加文本；
  `LLM_REPLY(final=true)` → `done`（**末分片带最后一段正文，仍按追加处理**）；`ERROR` 或本地失败 → `error`。
- **不要把 `thinking` / `streaming` 画进会话状态机** —— 它们只是"这一个气泡"的状态，
  期间会话一直是 `active`（回合执行状态由后端 `ConversationTurnRunner` 自持，前端不参与）。

**三条容易混的语义（写死）**：

| 事件 | 会话状态 | 说明 |
| :--- | :--- | :--- |
| 用户在思考，长时间不发 `ANSWER` | 仍 `active` | **思考 ≠ 暂停**；思考时间算面试时间（按整场时长计费） |
| 发 `{"type":"heartbeat"}` | 仍 `active` | 心跳只证明**连接活着**，不代表"用户正在操作"，也不刷新计费活跃度 |
| 超过失联阈值没收到心跳（语音 60 秒 / **文字作答 180 秒**） | `ended` | **失联 = 结束，不是暂停**（后端踢出 + 停计费 + 落库收尾）；只有显式 `PAUSE` 才进 `paused`。文字模式阈值放宽的理由见下 |
| 显式 `PAUSE` 后 | `paused` | 保留 15 分钟等 `resume` 重连，超时 `SESSION_EXPIRED` 结束 |

> **已定稿（2026-09-22，产品方向）：失联仍沿用「结束」，不改「暂停」；但文字作答的失联阈值放宽到 180 秒。**
> 这样两套语义都保持干净：
>
> | 事件 | 含义 | 处置 |
> | :--- | :--- | :--- |
> | 显式 `PAUSE` | **用户明确表示"我暂时不面了"** | `paused`，15 分钟内可 `resume` |
> | 失联（心跳丢失） | **系统无法确认用户还在** | 短暂等待后仍然 `ended`（停计费 + 落库收尾） |
>
> **为什么不能把失联也映射成 `paused`**：那样 `paused` 会同时表示"用户主动暂停 / 锁屏 / 断网 /
> 杀进程 / 故意断网"五种情况，而「用户主动暂停」这条最有产品价值的信号会被冲掉 ——
> 一旦 `paused` 变成万能状态，它就不再能回答"用户是不是自己要停"。
>
> **180 秒这个数的边界**：失联判定期间会话仍是 `active`、**仍在计时计费**（心跳丢失 ≠ 暂停，
> 见 §6.3 表格），所以阈值 = "真的一去不回时最多多扣多少秒余额"；上限由它约束，不能随意放大。
>
> **为什么不新增 `DISCONNECTED` 状态 / "短暂重连窗口"**：小程序切后台时**TCP 连接通常还在**
> （被挂起的是 JS，心跳随之停），因此**只放宽阈值**就能让用户回来自动续上，**零前端改动**；
> 而连接真的断了（进程被杀 / 网络断开）时，前端**没有自动重连**（当前唯一的恢复路径是
> "显式 `PAUSE` → 手动 `resume`"），后端留多久都不会有人来接 —— 要做真正的"失联可恢复"，
> 得引入新状态 + DB 语义 + 前端自动 resume，属独立议题，收益远小于成本。
> **结论：本轮只放宽阈值，不新增状态。**
>
> 联调提醒仍适用：若用户切后台**超过 180 秒**，回来时面试**已经结束**（不是暂停），
> 这是既定行为，不要当 bug 报。
>
> **已定稿（2026-09-23，后端已落地）**：失联结束不再记 `USER_ENDED` —— 新增
> `InterviewEndReason.DISCONNECTED`（心跳超时 / 顶号 / 传输错误），埋点 `end_reason` 从此能区分
> 「用户主动结束」与「连接层失联」；**历史数据不回溯**，报表按发布日分界。
> 映射与理由见后端方案 §8 P0-2 与 §8.1。

#### 6.3.2 暂停 / 恢复的时序与守卫（实现里最容易写错的一处）

```text
点「暂停」
   ├─ 确认弹窗（取消则什么都不做）
   ├─ pausing = true  ←── 先立标志，再发指令
   └─ 上行 PAUSE
        ↓
   服务端：回 PAUSED{sessionId}  → 页面：paused = true、存 sessionId、进入暂停态
        ↓
   服务端：**正常关闭**物理连接（1000）→ onClose 一样会触发
        ↓
   点「继续面试」（或头部「继续」，两处等价）→ connect({ ...原建连参数, resume: sessionId })
        ↓
   恢复成功（onOpen）→ pausing / paused 复位 → 回到进行中（**不重发首问**）
```

三条"不这么写就会出 bug"的实现要点：

1. **必须用 `pausing` / `paused` 标志区分「预期的关闭」与掉线**：服务端确认暂停后会正常关闭连接，
   `onClose` 照样触发。没有标志，页面会立刻弹"连接已断开"，用户以为暂停失败了。
   - 已确认暂停（`paused`）→ 连接关闭**静默处理**；
   - 发过 `PAUSE` 但没等到 `PAUSED` → 拿不到逻辑会话 ID，**恢复不了** →
     按「暂停失败，请重新进入」收尾（**不假装成功**，否则用户点"继续"必然失败）。
2. **恢复要用同一套建连参数**（模式 / 作答方式 / 模板 / 语言…）+ 多一个 `resume`：
   少任何一项，恢复出来的都是"另一场面试"（例如 `input` 丢了就退回 audio 会话）。
   实现里存了一份建连参数（`wsConfigRef`）供恢复复用。
3. **暂停要 5 秒兜底**：`PAUSED` 没来（发送时连接已关 / 网络断）时回滚标志并提示，
   否则页面会永久停在"正在暂停…"。

> **暂停会取消在途回复**：如果在"刚发完作答、AI 正在生成"时暂停，那一轮回答会被服务端取消且不落库。
> 当前实现**不阻止**这种暂停（用户可能正是因为来电话才急着暂停），但没有把它做成"无损暂停" ——
> 真要无损，需要后端先把已生成的部分落库，属独立议题。
>
> **参数名陷阱**：恢复用的 query 参数是 `resume`（= **逻辑会话 ID**）；协议里另有一个 `resumeId`
> 是**简历 ID**。两者只差两个字母，混用会得到"用错简历（或直接失败）的一场面试"。

#### 6.3.3 结束与收尾跳转（对齐 V1）

入口在**头部右侧**（2026-09-23 由底部上移，红胶囊，与「暂停 / 继续」并列）：红胶囊按钮 →
断开连接（服务端据此收尾落库）→ 提示「面试已结束」→ **600ms 后**跳转：

> 为什么从底部移到头部：底部只留输入区，操作入口集中在一处（V1 的底部按钮是当时的形态，
> 上移后与「暂停 / 继续」同一视线高度，不会在长对话里被滑走的输入区挤走）。
> 跳转规则、`usedTemplateRef` 定格、无二次确认这些都不随位置变化。

| 本场面试 | 跳转 | 为什么 |
| :--- | :--- | :--- |
| 用了**通用模板** | `redirectTo('/pages/experience-complete/index')` | 体验用户还没填自己的岗位/简历，收尾正是引导补齐的最佳时机 |
| 没用模板 | 有上一页 → `navigateBack()`；否则 → `redirectTo('/pages/index/index')` | 回到设置页 / 首页即可 |

三条要点：

1. **模板分支用 `redirectTo` 而不是 `navigateBack`**：面试页要被顶掉 —— 返回它只会看到一张过期的对话。
2. **「是否用了模板」在建连成功时定格**（`usedTemplateRef`）：面试结束后用户可能已经清掉选中态，
   那时再读 storage 就判断不出这场面试到底用的什么（V1 同款处理）。
3. **不做二次确认、也不依赖网络往返**：断连即结束，离线也点得动（与 V1 一致）。

> **暂停态也能结束，但这条路径靠后端兜底**：暂停时没有物理连接可断，服务端无从立刻得知"用户结束了"，
> 该记录由**暂停保留时长**（默认 15 分钟）到期后自动收尾 —— 也就是说这条路径的 `end_reason`
> 会是超时口径，而不是 `USER_ENDED`。要做到"暂停态结束也立即落库、归因准确"，需要一个显式的结束指令
> （控制消息或 REST 接口），属独立议题（当前把它当已知限制）。

## 8. 验证方式

1. 微信开发者工具打开 demo 页（开发环境下自动登录）→ 点「模拟面试V2（文字作答）」，或走「模拟面试设置（V2 入口）」→ 自动建连。
2. **首问**：建连成功后**无需任何操作**，AI 面试官主动发出第一题（先出现打字指示器气泡，再逐字填充）。
   **不应出现前端写的固定开场白**（`GREETING` 已删）。
3. **作答**：输入文字 → 发送 → 用户气泡立刻出现、输入框清空并**禁用**（话筒按钮同时禁用）→ AI 追问逐字填充 → 收到结束信号后输入框恢复。
4. **发送前拦截**：空文本时发送按钮置灰；超过 2000 字被输入框 `maxLength` 拦住（后端仍会兜底拒绝）。
5. **重复发送**：AI 生成期间输入框是禁用的（这是 `TURN_BUSY` 的语义要求）。若通过看门狗恢复后提前发送而被后端拒绝，
   应看到「AI 正在回复中」提示，且**刚才那段文字回到输入框**（不会被丢掉）。
6. **语音输入**：点话筒 → 首次弹麦克风授权 → 授权后话筒变红 + 出现「正在聆听」提示条 → 说话内容实时填入输入框
   （中间态覆盖草稿、定稿追加）→ 再点一次结束。**识别不会触发 AI 回答**（这是本方案的核心解耦）。
   **识别中点发送**：识别随发送一起停止（话筒恢复蓝色、状态条消失），发送后**不应**再有识别文字写回刚被清空的输入框。
7. **语音输入边界**：说到 **180 秒**被自动停止 → 提示「已到单次语音上限，可再点话筒继续说」；
   配额用完 → 「今日语音识别次数已用完，请改用打字输入」；已有识别在进行 → 「已有一条语音识别在进行，请稍后再试」。
8. **暂停 / 继续**：点头部「暂停」→ 确认 → 输入区禁用、底部出现「面试已暂停，15 分钟内可继续」+「继续面试」，
   且**头部同一位置的按钮由「暂停」变为「继续」**（两处都能恢复）；
   **不应**出现"连接已断开"之类的提示（服务端此时会正常关闭连接，页面已按预期关闭处理），
   也**不应**在对话流里多出一条"面试已暂停"的消息（暂停是状态，不是对话内容）。
   点「继续面试」或头部「继续」→ 回到进行中，**对话不丢、且不会重发首问**。
   暂停期间**剩余时长停表**（数字不再变化），恢复后接着走。
9. **暂停的边界**：确认弹窗点取消 → 什么都不该发生（仍可正常作答）；
   暂停超过 15 分钟（或后端把该记录结束掉）后再点「继续面试」→ 提示「暂停会话已失效，请重新开始面试」，
   页面进入结束态（**不能**停在"正在恢复面试…"）。
10. **剩余时长**：头部「剩余 mm:ss」**按秒连续变化**（不是几秒一跳），与服务端下发的快照误差不超过 1 秒。
11. **结束与收尾跳转**：点头部「结束」→ 提示「面试已结束」→ 用通用模板的面试进入「体验完成」页
   （没用模板则返回上一页）；模板分支用的是 `redirectTo`，所以**返回键不该再回到面试页**。
11. **H5 端**（`pnpm dev:h5`）：点话筒提示「当前端暂不支持实时语音识别」，文字作答链路正常。
12. **构建**：`pnpm build:weapp` 通过。
13. **V1 回归**：V1 页面 `pages/mock-interview/index` 建连、心跳、暂停/恢复照旧（协议登记是纯增量，不改 V1 行为）。
14. **端到端**：后端冒烟脚本 `pass-up.backend/scripts/smoke-v2.mjs` 全绿（协议层），与本页人工验收互为补充
    （清单见《模拟面试第二版-联调与冒烟清单》）。
15. **输入区热区**（改动后回归）：点输入胶囊最左侧留白 → **输入框获得焦点**；
    点话筒 / 发送圆形的边缘与外围留白 → 仍然触发对应按钮（视觉圆形与热区不是同一层）。
16. **识别通道的生命周期收口**（2026-09-24 新增）：
    - 说话中直接点「结束」→ 识别连接立即关闭（"正在聆听"提示消失、麦克风释放），
      且**已结束的页面上不再出现任何识别 / 超时 Toast**；
    - 说话中「暂停」→ 录音停止、话筒恢复蓝色；「继续」后再点话筒能正常开始
      （不能出现"点了没反应"或"点了反而停"）；
    - 识别中点「发送」→ 发送后**不应**再有识别文字写回刚被清空的输入框。
17. **资格闸门**（2026-09-24 可测）：未开始 / 已结束 / 暂停中的页面上点话筒 → 提示「请先开始面试」，
    且**不会**打开麦克风、不会自动重连；面试结束（含掉线 / 余额耗尽）时服务端会**回收**识别连接，
    前端不应对这次关闭弹任何错误（此时本就在结束态）。
18. **停止后的空闲释放**（2026-09-24 新增）：
    - 说一段话 → 点话筒停止 → 之后什么也不做：**约 8 秒后**连接自动关闭（开发者工具 Network 能看到 WS 关闭），
      再次点话筒能正常建立新连接；
    - 「发送」后再点话筒仍然正常（发送那次 `stop()` 起的定时器**不能**把新连接关掉）；
    - 把前端窗口临时调大（或用老版本客户端）以触发后端兜底：应看到 `[识别通道] 上游输入空闲已达上限`
      与指标 `end="input_idle"`，且页面**不弹任何错误**。
19. **单次上限 180 秒**（2026-09-24 新增，配合上限 60 → 120 → 180 秒）：
    - 说到 180 秒 → 微信自动停录音 + toast「已到单次语音上限，可再点话筒继续说」，
      **已识别的文字留在输入框里**（不能因为自动停止而丢掉）；
    - 随后再点话筒 → 能正常开始新的一次（新连接、新的 180 秒窗口）；
    - 界面**不显示**已用时长（2026-09-24 决定，见 §5.6 的权限/边界表）。
