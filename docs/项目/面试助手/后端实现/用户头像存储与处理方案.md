# 用户头像存储与处理方案

用户自定义头像通常涉及图片处理，是否「压缩 + 多尺寸存储」取决于业务规模。

针对 PassUp 这类 AI 面试产品，建议采用**轻量但规范**的处理策略：不直接保存用户原图，而是在上传链路中完成裁剪、转码与多尺寸生成。

## 推荐流程

```text
用户上传头像
      ↓
对象存储（MinIO）临时文件
      ↓
图片处理服务（裁剪 / 转码 / 缩放）
      ↓
生成多个尺寸
      ↓
保存头像记录
      ↓
返回头像地址
```

## 为什么需要多尺寸？

头像的使用场景很多，不同场景对分辨率的要求差异很大：

| 场景       | 推荐尺寸  |
| ---------- | --------- |
| 列表小头像 | 40 × 40   |
| 评论 / 聊天 | 64 × 64   |
| 个人主页   | 128 × 128 |
| 设置页面   | 256 × 256 |

如果所有场景都加载同一张原图（假设 5MB），代价会被放大：

```text
头像列表显示 20 个人：
20 × 5MB = 100MB
```

带宽与解码开销都会被成倍浪费。多尺寸的核心目的就是**按场景下发最小够用的图**。

## 推荐存储结构

### 对象存储（MinIO）

按 `年 / 月 / uid` 分层，避免单目录下文件过多，也便于按时间维度做生命周期清理：

```text
bucket: passup-public

avatar/
  2026/
    08/
      uid123/
        original.webp
        40.webp
        128.webp
        256.webp
```

### 数据库

**方案 1：字段冗余在用户表**（简单场景）

```sql
user_profile
  avatar_url        -- 主头像（大图）
  avatar_thumb_url  -- 缩略图（小图）
```

**方案 2：独立头像表**（便于扩展更多尺寸 / 历史记录）

```sql
user_avatar
  id
  user_id
  original_url
  small_url
  medium_url
  large_url
  created_at
```

## 图片格式

不要保存原始上传格式（如 `.jpg` / `.png`），应统一转码为 **WebP**：

- 体积小（相比 jpg/png 通常可再压缩 25%~35%）
- 现代浏览器支持良好
- 支持透明背景

> 注意：JDK 原生 `ImageIO` 不支持 WebP，服务端转码需额外引入 `webp-imageio`（见下方「依赖」），否则 `ImageIO.write()` 会因找不到 WebP Writer 而报错。

典型体积对比：

| 资源          | 大小   |
| ------------- | ------ |
| 原图（jpg）   | 3.5MB  |
| 40.webp       | 2KB    |
| 128.webp      | 10KB   |
| 256.webp      | 30KB   |

## 上传限制

### 上传前限制（前端）

```text
最大 5MB
支持类型：jpg / jpeg / png / webp
```

### 后端再次校验（不要信任前端）

前端限制只是体验优化，**不能**作为安全边界**。后端必须独立校验：

- **MIME 类型**：`Content-Type`
- **文件头（魔术字节）**：防止改后缀绕过
- **图片尺寸**：宽高是否合理
- **解码是否成功**：用图片库实际读取一次，确认不是损坏 / 伪造文件

## 是否保存 original？

存在两种方案，需要权衡「空间」与「可重处理」：

### 方案 A（推荐 SaaS）

只保存处理后的尺寸：

```text
40.webp
128.webp
256.webp
```

- **优点**：节省存储、更安全（不留存用户原图）
- **缺点**：以后无法用新算法重新裁剪 / 生成新尺寸

### 方案 B

同时保存原图与各尺寸：

```text
original.webp
40.webp
128.webp
256.webp
```

- **优点**：可随时更换裁剪算法、补生成新尺寸
- **缺点**：占用更多空间

### 对 PassUp 的建议

用户量预计在**几万以内**时，建议采用折中：

```text
保存 original.webp
+ 128.webp
+ 256.webp
```

不要一次性保存几十个尺寸——按需即可，后续增长再补尺寸成本也很低。

## Spring Boot 实现

技术栈为 **Spring Boot + MinIO**，图片处理使用 **Thumbnailator + webp-imageio**。

### 依赖

```xml
<!-- 图片缩略图处理：裁剪、缩放 -->
<dependency>
    <groupId>net.coobird</groupId>
    <artifactId>thumbnailator</artifactId>
    <version>0.4.21</version>
</dependency>
<!-- ImageIO 的 WebP 读写插件（社区活跃维护，支持 arm64/多架构） -->
<dependency>
    <groupId>com.github.usefulness</groupId>
    <artifactId>webp-imageio</artifactId>
    <version>0.11.0</version>
    <scope>compile</scope>
</dependency>
```

> 说明：JDK 自带的 `ImageIO` 原生不支持 WebP 格式，`webp-imageio` 通过 SPI 机制为其补充 WebP 的读写能力。引入后 `ImageIO.read()` / `ImageIO.write()` 即可直接读写 `.webp`，无需额外改代码；Thumbnailator 底层也是基于 `ImageIO`，因此二者可以无缝配合。

### 处理流程

```text
MultipartFile
  ↓
ImageIO 读取（校验可解码）
  ↓
裁剪为正方形（居中或按裁剪框）
  ↓
生成 128 / 256 两个尺寸
  ↓
转 WebP / 上传 MinIO
```

核心思路：先用 `ImageIO.read()` 验证文件是合法图片，再用 Thumbnailator 做尺寸缩放与格式转换（WebP 编码依赖 `webp-imageio` 提供的能力），最后通过 MinIO SDK 上传。

### 核心代码

```java
@PostMapping("/api/files/upload/avatar")
public String uploadAvatar(@RequestParam("file") MultipartFile file) {
    // 1. 校验大小与类型
    if (file.getSize() > 5 * 1024 * 1024) {
        throw new IllegalArgumentException("头像不能超过 5MB");
    }

    // 2. ImageIO 读取，验证是合法图片
    BufferedImage source;
    try (InputStream in = file.getInputStream()) {
        source = ImageIO.read(in);
    }
    if (source == null) {
        throw new IllegalArgumentException("文件不是合法图片");
    }

    // 3. 裁剪为正方形（居中）
    int size = Math.min(source.getWidth(), source.getHeight());
    int x = (source.getWidth() - size) / 2;
    int y = (source.getHeight() - size) / 2;
    BufferedImage square = Thumbnails.of(source)
            .sourceRegion(x, y, size, size)
            .asBufferedImage();

    // 4. 生成 128 / 256 两个尺寸并转 WebP
    BufferedImage small = Thumbnails.of(square)
            .size(128, 128)
            .outputFormat("webp")
            .asBufferedImage();
    BufferedImage large = Thumbnails.of(square)
            .size(256, 256)
            .outputFormat("webp")
            .asBufferedImage();

    // 5. 上传 MinIO 并返回地址
    uploadToMinIO("avatar/" + uid + "/128.webp", small);
    uploadToMinIO("avatar/" + uid + "/256.webp", large);

    return "avatar/" + uid + "/256.webp";
}
```

> 说明：`Thumbnails.of()` 的 `outputFormat("webp")` 依赖 JDK 内置的 WebP 支持，JDK 9+ 才提供原生 WebP ImageIO 插件；若在 JDK 8 上运行，需额外引入 `org.sejda.imageio:webp-imageio`。

## 一个细节：头像裁剪

很多 App（如微信头像）并非直接缩放整图，而是让用户**拖动裁剪框**选定区域后再生成正方形头像。

前端可选用：

- Web：`cropper.js`
- 小程序：`image-cropper`

前端先产出裁剪区域，后端按区域处理：

```json
{
  "x": 120,
  "y": 50,
  "width": 800,
  "height": 800
}
```

## 结合 PassUp 的最终设计

综合上述权衡，PassUp 采用「轻量、可扩展」的方案：

```text
POST /api/files/upload/avatar
  限制:
    - <= 5MB
    - jpg / png / webp
  处理:
    - 裁剪正方形
    - 转 WebP
    - 生成: 128 / 256
  MinIO:
    avatar/{uid}/128.webp
    avatar/{uid}/256.webp

PATCH /api/profile
  {
    "avatar": "avatar/{uid}/256.webp"
  }
```

该方案复杂度适中：既规范了存储与转码，又为后续用户量增长预留了扩展空间（补尺寸、改算法都不需要推倒重来）。
