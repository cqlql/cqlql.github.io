# 用户头像存储与处理方案

用户自定义头像通常涉及图片处理，是否「压缩 + 多尺寸存储」取决于业务规模。

针对 PassUp 这类 AI 面试产品，建议采用**轻量但规范**的处理策略：不直接保存用户原图，而是在上传链路中完成裁剪与转码。

> **当前定稿（结论先行）**：PassUp 现阶段采用**仅 `256.webp` 作为头像唯一资源**——不保存原图、不预生成多尺寸；优先把「文件生命周期 + 清理」做扎实，多尺寸（`variants`）作为演进储备，详见文末「现状与改进」。

> 本文档前半部分（为什么需要多尺寸 / 存储结构 / 是否保存 original / Spring Boot 实现）为方案调研与权衡背景，供后续扩展多尺寸时参考；**最终口径以文末「现状与改进」为准**。

## 推荐流程

```text
用户上传头像
      ↓
图片校验
      ↓
图片裁剪 / 转码 / 缩放
      ↓
生成 256.webp
      ↓
保存 file / attachment
      ↓
激活头像
      ↓
返回头像地址
```

## 为什么需要多尺寸？（背景与权衡）

头像的使用场景很多，不同场景对分辨率的要求差异很大：

| 场景       | 推荐尺寸  |
| ---------- | --------- |
| 列表小头像 | 40 × 40   |
| 评论 / 聊天 | 64 × 64   |
| 个人主页   | 128 × 128 |
| 设置页面   | 256 × 256 |

如果所有场景都加载同一张原图（假设 5MB），代价会被放大：

```text
头像列表显示 20 个人：
20 × 5MB = 100MB
```

带宽与解码开销都会被成倍浪费。多尺寸的核心目的就是**按场景下发最小够用的图**。

## 推荐存储结构（背景）

### 对象存储（MinIO）

按 `年 / 月 / uid` 分层，避免单目录下文件过多，也便于按时间维度做生命周期清理：

```text
bucket: passup-public

avatar/
  2026/
    08/
      uid123/
        original.webp
        40.webp
        128.webp
        256.webp
```

### 数据库

**方案 1：字段冗余在用户表**（简单场景）

```sql
user_profile
  avatar_url        -- 主头像（大图）
  avatar_thumb_url  -- 缩略图（小图）
```

**方案 2：独立头像表**（便于扩展更多尺寸 / 历史记录）

```sql
user_avatar
  id
  user_id
  original_url
  small_url
  medium_url
  large_url
  created_at
```

## 图片格式

不要保存原始上传格式（如 `.jpg` / `.png`），应统一转码为 **WebP**：

- 相近视觉质量下通常能拿到更小体积（实际压缩比例取决于图片内容与编码参数）
- 现代浏览器支持良好
- 支持透明背景

> 注意：JDK 原生 `ImageIO` 不支持 WebP，服务端转码需额外引入 `webp-imageio`（见下方「依赖」），否则 `ImageIO.write()` 会因找不到 WebP Writer 而报错。

典型体积对比：

| 资源          | 大小   |
| ------------- | ------ |
| 原图（jpg）   | 3.5MB  |
| 40.webp       | 2KB    |
| 128.webp      | 10KB   |
| 256.webp      | 30KB   |

## 上传限制

### 上传前限制（前端）

```text
最大 5MB
支持类型：jpg / jpeg / png / webp
```

### 后端再次校验（不要信任前端）

前端限制只是体验优化，**不能**作为安全边界**。后端必须独立校验：

- **MIME 类型**：`Content-Type`
- **文件头（魔术字节）**：防止改后缀绕过
- **图片尺寸**：宽高是否合理
- **解码是否成功**：用图片库实际读取一次，确认不是损坏 / 伪造文件

## 是否保存 original？（背景与权衡）

存在两种方案，需要权衡「空间」与「可重处理」：

### 方案 A（推荐 SaaS）

只保存处理后的尺寸：

```text
40.webp
128.webp
256.webp
```

- **优点**：节省存储、更安全（不留存用户原图）
- **缺点**：以后无法用新算法重新裁剪 / 生成新尺寸

### 方案 B

同时保存原图与各尺寸：

```text
original.webp
40.webp
128.webp
256.webp
```

- **优点**：可随时更换裁剪算法、补生成新尺寸
- **缺点**：占用更多空间

### 对 PassUp 的建议

用户量预计在**几万以内**，且当前头像无多尺寸消费场景，最终结论是**不保存 original、不预生成多尺寸，仅保留 `256.webp`**：

```text
256.webp
```

不要为「以后可能用到」提前制造存储与清理复杂度；待真实出现多尺寸需求（小头像列表、简历预览、封面图等），再按文末「若引入 variants」升级。

## Spring Boot 实现

技术栈为 **Spring Boot + MinIO**，图片处理使用 **Thumbnailator + webp-imageio**。

### 依赖

```xml
<!-- 图片缩略图处理：裁剪、缩放 -->
<dependency>
    <groupId>net.coobird</groupId>
    <artifactId>thumbnailator</artifactId>
    <version>0.4.21</version>
</dependency>
<!-- ImageIO 的 WebP 读写插件（社区活跃维护，支持 arm64/多架构） -->
<dependency>
    <groupId>com.github.usefulness</groupId>
    <artifactId>webp-imageio</artifactId>
    <version>0.11.0</version>
    <scope>compile</scope>
</dependency>
```

> 说明：JDK 自带的 `ImageIO` 原生不支持 WebP 格式，`webp-imageio` 通过 SPI 机制为其补充 WebP 的读写能力。引入后 `ImageIO.read()` / `ImageIO.write()` 即可直接读写 `.webp`，无需额外改代码；Thumbnailator 底层也是基于 `ImageIO`，因此二者可以无缝配合。

### 处理流程

```text
MultipartFile
  ↓
ImageIO 读取（校验可解码）
  ↓
裁剪为正方形（居中或按裁剪框）
  ↓
生成 256（当前仅此一档）
  ↓
转 WebP / 上传 MinIO
```

核心思路：先用 `ImageIO.read()` 验证文件是合法图片，再用 Thumbnailator 做尺寸缩放与格式转换（WebP 编码依赖 `webp-imageio` 提供的能力），最后通过 MinIO SDK 上传。

### 核心代码

```java
@PostMapping("/api/files/upload/avatar")
public String uploadAvatar(@RequestParam("file") MultipartFile file) {
    // 1. 校验大小与类型
    if (file.getSize() > 5 * 1024 * 1024) {
        throw new IllegalArgumentException("头像不能超过 5MB");
    }

    // 2. ImageIO 读取，验证是合法图片
    BufferedImage source;
    try (InputStream in = file.getInputStream()) {
        source = ImageIO.read(in);
    }
    if (source == null) {
        throw new IllegalArgumentException("文件不是合法图片");
    }

    // 3. 裁剪为正方形（居中）
    int size = Math.min(source.getWidth(), source.getHeight());
    int x = (source.getWidth() - size) / 2;
    int y = (source.getHeight() - size) / 2;
    BufferedImage square = Thumbnails.of(source)
            .sourceRegion(x, y, size, size)
            .asBufferedImage();

    // 4. 生成 256 并转 WebP（当前仅此一档，多尺寸为演进储备）
    BufferedImage avatar = Thumbnails.of(square)
            .size(256, 256)
            .outputFormat("webp")
            .asBufferedImage();

    // 5. 上传 MinIO 并返回地址（用唯一 key，如 ULID/UUID，避免二次上传覆盖旧头像）
    String objectKey = "avatar/" + uid + "/" + uniqueId() + "/256.webp";
    uploadToMinIO(objectKey, avatar);

    return objectKey;
}
```

> 说明：JDK 标准 `ImageIO` 并不提供可靠的 WebP 编解码能力（不应以「JDK 原生支持 WebP」作为依据），项目显式引入 `webp-imageio` 插件提供 WebP 读写能力；`Thumbnails` 底层同样基于 `ImageIO`，二者可无缝配合。

## 一个细节：头像裁剪

很多 App（如微信头像）并非直接缩放整图，而是让用户**拖动裁剪框**选定区域后再生成正方形头像。

前端可选用：

- Web：`cropper.js`
- 小程序：`image-cropper`

前端先产出裁剪区域，后端按区域处理：

```json
{
  "x": 120,
  "y": 50,
  "width": 800,
  "height": 800
}
```

## 结合 PassUp 的最终设计

综合上述权衡，PassUp **当前定稿**采用「最简、可扩展」的方案：

```text
POST /api/files/upload/avatar
  限制:
    - <= 5MB
    - jpg / png / webp
  处理:
    - 裁剪正方形
    - 转 WebP
    - 生成: 256（当前仅此一档）
  MinIO:
    avatar/{uid}/{yyyy}/{MM}/{dd}/{ulid}.webp

PATCH /api/profile
  {
    "avatarFileId": "01K..."
  }
```

要点：

- **唯一 storage key（ULID）**：每次上传都生成新 key，二次上传不覆盖旧对象；换头像时旧对象走「引用解除 → 待删除 → MinIO 删除」生命周期，不依赖覆盖写。
- **前端只提交 `avatarFileId`**：上传完成后返回 fileId，前端 `PATCH /api/profile` 提交 `avatarFileId`，由后端校验归属、建立 `attachment` 并更新 `app_user.avatar`；前端无需理解 MinIO storage key。
- 一条 `file` 记录 + 一个 256 对象，清理链路简单可审计；待真实多尺寸需求出现，再按文末「若引入 variants」升级。

## 现状与改进：文件生命周期与多尺寸落盘（方案 C 已落地）

> 记录于代码实现落地后。基于当前 `AvatarImageProcessor` / `AttachmentService` / `FileCleanupService` 的实际实现，梳理隐患与改进方向（已吸收多轮评审意见）。方案 C 已按「仅 `256.webp`」落地并通过编译，下文保留落地前隐患分析与演进储备说明。

### 问题本质：是「文件生命周期」，不是「多尺寸」

当前问题的根不在「多尺寸该放 JSON 还是拆表」，而在于生命周期链未闭环：

```text
上传临时文件 → 生成多个对象 → 业务引用哪个？
→ 删除头像时删哪些？ → 换头像时旧图何时删？ → 处理中途失败怎么办？
```

### 落地前隐患（已消除）

方案 C 落地前，链路曾实现为「生成 3 档 WebP，但只有 256 进数据库」，存在如下隐患：

1. `AvatarImageProcessor.process()` 曾生成 `{base}-original.webp`、`{base}-128.webp`、`{base}-256.webp`。
2. `AttachmentService.activateAvatar()` 只把 `256.webp` 覆盖写回 `file.storage_key`，`original` / `128` 的 key 与 size 被直接丢弃，无任何落盘。
3. `file` 表只有单个 `storage_key`（且唯一），`app_user.avatar` 也只存 `256` 的 URL；`attachment` 表仅关联一条（256）。
4. `FileCleanupService.deleteWithDerivatives()` 靠识别 `-256.webp` 后缀**反推** `-original.webp` / `-128.webp` 一并删除。

上述隐患导致 `original.webp` 与 `128.webp` 游离为「幽灵对象」，可回收性完全依赖「命名后缀」隐性契约；且它们**无任何消费端**（profile 仅返回 256），属于「生成了却没人用」。

### 落地后改动（方案 C）

已按「仅 `256.webp`」落地，改动如下：

1. `AvatarImageProcessor.process()` 只生成单个 `{base}.webp`（256×256），移除 original / 128 两档；`AvatarProcessResult` 只保留 `key` 与 `size`。
2. `AttachmentService.activateAvatar()` 改用单尺寸结果覆盖激活：下载原始图 → 缩放转码为 256 WebP → 删除原始对象 → 以该 WebP 作为最终文件记录。
3. `FileCleanupService` 移除 `deleteWithDerivatives()`（不再靠命名后缀反推衍生对象），清理统一走按 `storageKey` 通用的 `deleteByStorageKey`。

由此头像只保留单个 `256.webp` 资源，每个对象都可由 `file` 表（`storage_key`）完整追踪，清理与审计不再依赖隐性命名契约。

### 结论：已直接采用「仅 256」

PassUp 当前已直接采用 **方案 C（仅 `256.webp` 作为头像唯一资源）**，而非搭建完整的图片变体系统：

- 前端目前所有头像展示都可用 256 覆盖（profile 已只返回 256）。
- `original` 其实已非原始格式（是转码后的 WebP），头像重新上传成本极低，无需为「以后重新生成」留存。若确需留存原始文件，应保留原格式（如 `source.jpg`），而不是 `original.webp`。
- 128 若无小头像列表场景，同样不必提前生成。
- 先把「文件生命周期 + 清理」做扎实，比提前做「多尺寸」更有价值。

```text
attachment → file → 256.webp
```

### 生命周期闭环（已补齐）

头像对象已有一条可执行、可审计的完整生命周期：

```text
上传临时文件 → 图片处理（转码 256 WebP）→ 上传 WebP → 删除原对象 → 激活 file
→ 旧头像进入删除流程 → 对象存储删除
```

- **DB 与 MinIO 不是同一事务**：跨资源操作不具备原子性，不应理解为「事务回滚」，而是「失败可补偿」。
  - DB 成功、MinIO 删除失败 → 对象残留，进入删除重试。
  - MinIO 上传成功、DB 落库失败 → 产生无记录孤儿对象，由 `FileCleanupService` 后台扫描兜底（`cleanOrphanActiveFiles` / `cleanUploadingFiles`）。
  - 删除范围由 DB `file.storage_key` 明确给出，清理统一按 `storageKey` 删除，不再靠命名反推。

```text
FileCleanupService
    ↓
删除任务 / 孤儿扫描
    ↓
失败重试
    ↓
最终一致
```

### 若引入 variants：设计要点（演进储备）

待多尺寸扩展到头像之外（小头像列表、简历预览、封面图等）时，再落 `variants`，遵循：

1. **`storage_key` 永远代表主资源**（头像即 `256.webp`），`variants` 只存**衍生**资源，不重复存主资源。

```sql
ALTER TABLE file ADD COLUMN variants jsonb;
```

```json
{
  "s128": { "key": "avatar/uid/2026/09/xx-128.webp", "size": 10240, "width": 128, "height": 128 }
}
```

2. **`variants` 只存 key / size / width / height，不存 url**：URL 是派生信息（endpoint / CDN / 域名会变），应由 API 层按 key 生成，避免 DB 存历史 URL。

3. **当前规模用 `jsonb` 即可，勿急着抽表**：当多尺寸从「头像专属」扩展到多种资源时，再抽象为通用 `file_variant` 表（`file_id` / `variant` / `storage_key` / `size` / `width` / `height`）。

4. **无需为每个尺寸各建 attachment 记录**：attachment 语义是「业务实体 ↔ 文件」，一个用户一个头像是**一个业务引用**，多尺寸是同一头像的渲染变体，属 file 级衍生元数据。

### 备选方向对比

| 方案 | 说明 | 适用 |
| ---- | ---- | ---- |
| C（仅 256） | 头像唯一资源，最简 | **当前采用** |
| A（`file.variants` jsonb） | 主资源 + 衍生变体，一条记录承载 | 多尺寸仍以头像为主、种类少 |
| B（独立 `file_variant` 表） | 通用多尺寸/多衍生资源模型 | 多资源、多种衍生规模化扩展 |

> 建议：先落地 C 并补齐生命周期闭环；当多尺寸资源从头像扩展到其他业务资源、或同一 file 出现多个稳定消费尺寸时，升级为 A；规模再大升级为 B。
