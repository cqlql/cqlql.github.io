# 后台系统账号互通 — 免密直连落地方案

> **系统定义（以本机实际仓库为准）**
>
> - **A = 自研产品分析平台**
>   - 后端：`D:\_work\analytics-platform\backend`（**Python FastAPI** + ClickHouse，`uv` 管依赖）
>   - 前端：`D:\_work\analytics-platform\frontend`（Vite + React 18 + TS + AntD + ECharts，构建产物 `dist` 由 backend 托管）
>   - 登录：账号来自环境变量 `AUTH_USERS`（**一人一号**，无用户表），会话是 **HMAC-SHA256 签名的无状态 Cookie**（`analytics_session`，httponly，`SameSite=Lax`），前端 JS **读不到**
>   - **没有 Redis**（只有 ClickHouse），所以 A 侧不能存一次性票据
>   - 部署：宝塔 + Nginx 反代到 `127.0.0.1:8010`（backend 同端口托管前端）
> - **B = PassUp 管理端**
>   - 后端：`D:\_work\pass-up\pass-up.backend`（Java 25 / Spring Boot 4 / **PostgreSQL** + Redis）
>   - 用户表：`app_user`（内部 `id` BIGINT + 对外 `uid` ULID）
>   - 登录态：JWT access token（15 分钟）+ Redis 会话（`auth:session:meta:*`）；`TokenAuthenticationFilter` **只认 `Authorization: Bearer <access JWT>`**，不依赖 Cookie
>   - **前端（`pass-up.frontend/apps/admin`）本方案一行不改**
>
> **版本说明（v4.2，2026-09-30）**
> 本文件原名「后台系统账号互通-签名跳转落地方案」（v1 签名跳转 → v2 服务端换 code → v3 A 前端跨域换 code）。
> v4 按最终确认的形态重写：**B 不需要任何前端改动；A 新增前端页面，直接调用 B 的接口。**
> 于是"跳转 / 落地页 / 一次性 code / token 落地"这一整套全部消失 —— 认证收敛成一句话：
> **A 的页面用 A 后端签的一组短时参数，向 B 换一个 B 的 access token，之后拿它当 `Authorization` 调 B 的接口。**
> v4.1 起，兑换出来的会话用**新增的 `ClientType.EXTERNAL`**（不借位 `DESKTOP`），两个易踩的坑见 **附 C**。
> v4.2 起，**不再新建 `EXTERNAL_OPERATOR` 角色**：`required-role-code` 直接指向 `ADMIN`，
> 每个 A 账号 **1:1 绑到各自已有的 B 管理端账号**。理由、被否掉的做法与已知代价见 **§5.3**。
> 历史评审意见的落点见 **附 A**。

## 0. 一句话结论

```text
A 页面（新增）                          B 后端
   │ ① POST /api/sso/passup/sign            （同源，A 后端只签名，不碰 B）
   │ ② POST https://<B>/api/sso/exchange    （跨域，带签名 → 换 B 的 access token）
   │ ③ Authorization: Bearer <accessToken>  （跨域，调 B 的现有管理接口）
   ▼
B 侧：TokenAuthenticationFilter 照常解析 → @PreAuthorize 照常校验权限
      （B 的 controller / 前端 一行不改）
```

- **A 后端**：只加一个签名接口（密钥不出后端），不持有 B 的地址、不调 B；
- **B 后端**：只加一个兑换接口（验签 → 查映射 → 发 access token）+ 一张映射表 + CORS 白名单；
- **B 前端**：**不动**（没有落地页、没有新路由）；
- **A 前端**：新增页面 + 一个 `passupFetch` 封装（自动带 token、401 自动重换）。

## 1. 目标与边界

### 1.1 目标

1. 运营/开发在分析平台（A）看完数据后，**在 A 的页面里就能完成对 PassUp（B）的操作**，不必再登录 B 的管理端；
2. 两侧各自保留账号与权限体系，**不做统一用户中心**；
3. B 侧只做"加接口"，不改认证链路、不改前端、不改任何现有业务代码。

### 1.2 明确不做

- ❌ **不改 B 的前端**（`apps/admin` 一行不动）；
- ❌ 不做"跳转 / 落地页 / 一次性 code"（v1~v3 的形态，本版整体废弃）；
- ❌ 不把 B 的 access token 放进 URL（没有 URL 传参这件事了）；
- ❌ 不建统一用户中心 / 不合并账号体系 / 不做账号数据同步；
- ❌ 不把 A 的会话 Cookie、A 的账号当 B 的登录凭证（A 的账号只是**映射索引**）；
- ❌ 不在兑换时自动创建 B 用户（影子账号）；
- ❌ 不接受 A 传来的任意接口路径或任意跳转地址；
- ❌ v4.2 不为 v1 新建最小权限角色、也不建专门的承载账号（直接绑各自的 ADMIN 账号，代价见 §5.3）；
- ❌ 不为一个 A→B 的互通引入 Keycloak / CAS。

### 1.3 信任边界

```text
┌───────────────────────────┐
│   A 控制台登录态           │  证明：这个人是 A 的某个账号（AUTH_USERS）
│  （analytics_session）     │  前端 JS 读不到这个 Cookie
└─────────────┬─────────────┘
              │ ① A 后端用共享密钥签名（密钥不出后端）
              ▼
   ┌────────────────────────────┐
   │ 一组短时签名参数            │  ts / nonce / sign（A 前端只负责搬运）
   └─────────────┬──────────────┘
                 │ ② 跨域 POST（body，不进 URL）
                 ▼
   ┌────────────────────────────┐
   │ B 验签 → 查映射 → 发 token  │  A 账号 → B 用户（角色决定它能做什么）
   └─────────────┬──────────────┘
                 │ ③ 之后每个请求带 Bearer token
                 ▼
   ┌────────────────────────────┐
   │ B 现有鉴权链路（filter + @PreAuthorize）│  ← 完全复用，零改动
   └────────────────────────────┘
```

> 关键点：**B 不新增任何"认证方式"**。A 换到的就是一张普通的 B access token，
> 后续请求与"用户在 B 管理端自己点"走的是**同一条**鉴权与权限链路。
> 因此 A 页面能做什么，完全由**映射到的 B 用户的角色与权限点**决定 —— A 说了不算。

## 2. 选型：为什么是「换 B 的 token」而不是「每个请求带签名」

三条候选（本版只在这三条里选）：

| 维度 | ① **换 B 的 access token（本版主线）** | ② 每个请求带一次性签名 | ③ A 前端换 code + B 落地页（v3） |
| :--- | :--- | :--- | :--- |
| B 的 controller / 前端改动 | **零**（复用现有 filter + `@PreAuthorize`） | 零，但要在 filter 里**新增一种凭证解析分支** | 零 controller，但**要加 B 前端落地页** |
| A 前端每个请求的额外往返 | 无（token 缓存，15 分钟换一次） | **每个请求都要先找 A 后端签名** | 无 |
| 签名需要绑定"具体资源"吗 | 不需要（token 决定身份，权限决定范围） | **需要**（否则凭证可被改成访问别的资源） | 不需要 |
| 是否引入"登录态"概念 | 是（一张 15 分钟的 token） | 否 | 是 |
| 泄漏面 | A 页面持有 B token（15 分钟，XSS 可窃取） | **最小**（凭证一次性、短时） | 中（URL 里有过 code） |
| 复杂度 | 低 | 中（逐请求签名 + 资源绑定 + filter 新分支） | 中（code + 落地页） |

**选 ①**：B 侧改动最小（只加一个兑换接口），且**不引入任何新的认证概念** ——
A 换到的 token 就是 B 自己的 token，后续链路 100% 复用。
② 看起来更"安全"，但代价是 B 的 filter 要新增一种凭证类型，且签名必须绑定 method + path + query
（否则一个"读用户 A"的凭证能被改成"读用户 B"），实现细节反而更多、更易出错。
③ 是上一版，被"B 不需要前端"这条直接否掉。

> 结论：**能用"发一张自己的 token"解决的事，就不要新造一种认证凭证。**

## 3. 整体流程

### 3.1 流程表

| 步骤 | 角色 | 动作 |
| :--- | :--- | :--- |
| 1 | B 管理员 | 在 PassUp 管理端「外部账号绑定」页，把 `A 账号名 → B 用户` 写入 `external_user_map` |
| 2 | 用户 | 登录 A 分析平台（`AUTH_USERS` 里的账号） |
| 3 | 用户 | 打开 A 新增的页面（如「PassUp 用户」），页面初始化时换 token |
| 4 | A 前端 | `POST /api/sso/passup/sign`（同源，带 A 的会话 Cookie） |
| 5 | A 后端 | 取当前账号名 → 生成 `ts` / `nonce` / `sign` → 返回（**不接触 B**） |
| 6 | A 前端 | 跨域 `POST https://<B>/api/sso/exchange`，body 带上这组参数 |
| 7 | B 后端 | 参数校验 → 时间窗 → 验签（constant-time）→ 消费 nonce → 查映射（`status=1`）→ 校验 B 用户存在且持所需角色 → `AuthService.createTokens` 建会话 |
| 8 | B 后端 | 返回 `{ "accessToken": "...", "expiresIn": 900 }` |
| 9 | A 前端 | token 存**内存**（不落 localStorage），后续请求带 `Authorization: Bearer <token>` |
| 10 | A 前端 | 正常调用 B 的现有管理接口（如 `GET /api/admin/users/page`） |
| 11 | B 后端 | 现有链路照常：`TokenAuthenticationFilter` 解析 → `@PreAuthorize` 校验权限点 |
| 12 | A 前端 | 收到 401（token 过期/被踢）→ **静默重换一次并重试**（用户无感） |

> 未绑定 / 映射被禁用 / 目标用户角色不足：**第 7 步就失败**，A 前端提示
> 「该账号未授权访问 PassUp 后台」，不产生任何 B 会话。

### 3.2 时序图

```text
A 浏览器                    A 后端              B 后端
   │                         │                    │
   │ 打开「PassUp 用户」页    │                    │
   │ POST /api/sso/passup/sign                    │
   ├────────────────────────►│                    │
   │◄────────────────────────┤ {ts,nonce,sign,sourceUserId}
   │                                              │
   │ 跨域 POST /api/sso/exchange（签名在 body）     │
   ├─────────────────────────────────────────────►│
   │                         │  校验→验签→nonce     │
   │                         │  查映射→校验角色     │
   │                         │  createTokens()     │
   │◄─────────────────────────────────────────────┤ { accessToken, expiresIn }
   │                                              │
   │ GET /api/admin/users/page                    │
   │ Authorization: Bearer <accessToken>          │
   ├─────────────────────────────────────────────►│
   │                         │  TokenAuthenticationFilter（照常）
   │                         │  @PreAuthorize（照常）
```

## 4. 接口契约

### 4.1 A 侧：签发参数（同源，需登录）

```http
POST /api/sso/passup/sign
Cookie: analytics_session=<签名会话>      # 同源自动携带
```

**响应**

```json
{
  "sourceSystem": "A",
  "sourceUserId": "zhangsan",
  "ts": 1769490000,
  "nonce": "3f9a2c7e5b1d4e8f9a0b1c2d3e4f5a6b",
  "sign": "8c1f...e9"
}
```

**A 后端实现要点**（`backend/app/sso.py`，在 `main.py` 里 `app.include_router(sso.router)`）：

```python
import hashlib, hmac, secrets, time

CANONICAL_PATH = "/api/sso/exchange"   # 签名绑定的目标接口（B 侧）

def _sign(account: str, ts: str, nonce: str) -> str:
    canonical = "\n".join(["POST", CANONICAL_PATH, "A", account, ts, nonce])
    return hmac.new(
        PASSUP_SSO_SECRET.encode(), canonical.encode(), hashlib.sha256
    ).hexdigest()

@router.post("/api/sso/passup/sign")
def sign(request: Request, principal: Principal = Depends(require_session)):
    ts = str(int(time.time()))
    nonce = secrets.token_urlsafe(32)          # 256bit，不用 UUID 截断
    return {
        "sourceSystem": PASSUP_SSO_SOURCE,     # 当前为 "A"，B 按它取密钥、查映射
        "sourceUserId": principal.user,
        "ts": ts, "nonce": nonce,
        "sign": _sign(principal.user, ts, nonce),
    }
```

- **只认登录会话，不认 `X-API-Key`**：`require_console` 同时接受会话与读 Key，
  但读 Key 是给脚本/CI 拉数据用的机器凭据，**不应该能换取 B 的后台登录态**。
  故在 `security.py` 里加一个只认会话的依赖 `require_session`
  （`current_user(request) is None` 就 401），本接口用它。
- 新配置项：`PASSUP_SSO_SECRET`（**必须与会话密钥 `AUTH_SECRET` 分开**：一个是 A 自己的会话签名，
  一个是 A↔B 的信任密钥，混用会让泄露面互相牵连）。缺省时该接口直接 503，避免"没配密钥却以为能用"。
- 路由命名不冲突：A 的业务路由是 `/api/{pid}/{action}`（`overview` / `trend` / …），
  `/api/sso/passup/sign` 不会命中任何已有模板；注册顺序上放在业务 router 之前更直观。
- 建议落一条审计日志（A 已有 `request.state.actor` + 结构化日志模式）：
  `sso_sign actor=<account> ip=<ip>`。

> **签名里为什么不带"要操作哪个用户/哪个接口"**：这张签名只用来**换 token**，
> 换到 token 之后"能操作什么"由 B 的角色与权限点决定。签名不承担资源级授权，
> 也就不会出现"凭证被改一个 uid 就越权"的问题（对比 §2 的方案 ②）。

### 4.2 B 侧：兑换 token（跨域公开接口）

```http
POST /api/sso/exchange
Origin: https://<A 的域>
Content-Type: application/json

{ "sourceSystem": "A", "sourceUserId": "zhangsan", "ts": "1769490000",
  "nonce": "3f9a...", "sign": "8c1f...e9" }
```

**canonical string（B 侧按同一份规范重算）**

```text
POST
/api/sso/exchange
A
zhangsan
1769490000
3f9a2c7e5b1d4e8f9a0b1c2d3e4f5a6b
```

- 第 1、2 行绑定**方法与目标接口**（这份签名只能用于 A→B 的这个接口）；
- 第 3 行绑定**来源系统**（将来加 C 时不会串用）；
- 第 4~6 行绑定**身份与时效**。

> body 就是这几个参数本身，**不需要再单独签 body 的 hash** —— 少一层"双方拼串不一致"的风险。

**B 侧处理顺序（评审第 1 条"先验签再消费 nonce"的落点）**

```text
① 参数格式校验（source 白名单 / ts 可解析 / nonce 长度 / sign 非空）
② 时间窗校验：|now - ts| <= 60s
③ 按 source 取密钥（未配置该来源 → 401，不做后续任何动作）
④ 计算 HMAC 并 constant-time 比较（MessageDigest.isEqual，不用 equals）
⑤ 消费 nonce：SET NX auth:sso:nonce:A:{nonce} TTL 120s（失败 → 401，判定为重放）
⑥ 查映射 external_user_map(source_system='A', source_user_id)，要求 status=1
⑦ 校验目标 B 用户：仍存在（未被软删）且持有要求的角色（见 §5.3）
⑧ AuthService.createTokens(新 UserSession) → 建会话、发 access token
⑨ 返回 access token（不返回任何 B 用户信息）
```

**响应**

```json
{ "accessToken": "<JWT>", "expiresIn": 900 }
```

> ⚠️ **错误响应契约（实现时踩过一次，调用方必须知道）**
> B 侧所有业务/鉴权错误都是 **HTTP 200 + body `{code, message, data}`**
> ——`ResponseUtils.writeJson` 不设 HTTP 状态码（`JsonAuthenticationEntryPoint` /
> `JsonAccessDeniedHandler` / `GlobalExceptionHandler` 走的是同一条路）。
> 所以 A 的前端**必须按 `body.code` 判断成败**，不能看 `res.ok`：
> 兑换被拒是 `code=403`（未授权）、`code=401`（签名/时间窗/nonce 问题），
> 而**后续调 B 的接口时 token 失效也表现为 `code=401` 而不是 HTTP 401** ——
> 「401 就静默重换一次」这条重试逻辑必须挂在 `body.code` 上，否则永远不会触发。

**发放实现（复用现有组件，不新造认证路径）**

```java
// 1) 验签、nonce、映射、角色校验见上（失败一律 Result.failed(...)，不建任何会话）

// 2) 建一个"外部系统代持"的会话
UserSession session = UserSession.builder()
        .userId(map.getLocalUserId())
        .clientType(ClientType.EXTERNAL)     // 新增枚举值，见附 C（不要借位 DESKTOP）
        .platform(PlatformType.UNKNOWN)
        .ipAddress(request.getRemoteAddr())  // 用户浏览器的真实 IP（请求由浏览器发出）
        .loginTime(System.currentTimeMillis())
        .build();

// 3) 复用现有签发逻辑：会新建 sessionId、填充 roles/permissions/status、存 Redis、限会话数
AuthTokens tokens = authService.createTokens(session);

// 4) 只返回 access token
return Result.ok(new SsoTokenResponse(tokens.getAccessToken(), 900));
```

- **不要用 `WebAuthHelper#createWebTokens`**：它会额外写 refresh token 的 HttpOnly Cookie
  （`Path=/api/web/auth/refresh`），而 A 的页面跨域调 B 根本用不上那个 Cookie
  （跨站 `Set-Cookie` 会被浏览器拒绝），直接调 `AuthService.createTokens` 更干净；
- **不发 refresh token**：A 的页面只拿 15 分钟的 access token，过期就重新走签名换一次
  （签名是自动的、用户无感），这样**不需要把 7 天的长期凭证交给 A 的页面**；
- 会话里的 `roles` / `permissions` 由 `createTokens` **查库填充**，
  所以 A 页面拿到的权限 = 映射到的 B 用户的真实权限，且与用户在 B 管理端登录时完全一致。

> 失败响应沿用 B 现有 `Result` / `ResultCode` 约定，例如
> `{ "code": 40030, "message": "该账号未授权访问 PassUp 后台" }`。

### 4.3 A 侧：前端请求封装（token 缓存 + 401 单飞重换）

并发语义**集中在一个不依赖浏览器的模块**里（`frontend/src/api/passupToken.ts`），
这样它可以脱离浏览器验证 —— 竞态是这条链路里最难靠手测发现的部分。

```ts
// frontend/src/api/passupToken.ts —— 并发语义只在这里定义
export function createTokenCoordinator(exchange: () => Promise<string>) {
  let cached: string | null = null;
  let inFlight: Promise<string> | null = null;

  // 单飞：`if (!inFlight)` 与赋值之间**没有 await**，JS 单线程下这一步是原子的，
  // 所以并发调用不会各起一次 exchange。这是"单飞"成立的全部依据。
  function start(): Promise<string> {
    if (!inFlight) {
      inFlight = exchange()
        .then((t) => { cached = t; return t; })
        .finally(() => { inFlight = null; });
    }
    return inFlight;
  }

  return {
    async get(force = false) {
      if (!force && cached) return cached;
      return start();               // force 也走单飞，不是"绕过单飞"
    },
    current: () => cached,
    async invalidateIfCurrent(usedToken: string) {
      if (cached !== usedToken) return;   // 别人刚刷新过 → 直接用新 token 重试
      cached = null;
      await start();                      // 置空与 start 必须在同一同步块内
    },
    reset() { cached = null; },
  };
}
```

```ts
// frontend/src/api/passup.ts
const tokens = createTokenCoordinator(fetchToken);   // fetchToken 见下方说明

export async function passupFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const first = await send(path, init, await tokens.get());
  if (first.body?.code !== 401) return unwrap<T>(first);

  await tokens.invalidateIfCurrent(first.token);     // 只在"我用的 token 已过时"时才真换
  return unwrap<T>(await send(path, init, await tokens.get()));
}
```

`fetchToken` 本身是两步：① 同源 `POST /api/sso/passup/sign` 拿签名参数；
② 跨域 `POST <B>/api/sso/exchange` 换 token。**必须看 `body.code` 而不是 `res.ok`**
（B 用 HTTP 200 承载所有业务/鉴权错误，见 §4.2 的契约说明）。

要点：

- **token 只放内存**（模块变量），不写 `localStorage`：A 的页面刷新后自动重新换一次，
  代价是一次同源 + 一次跨域请求，换来"B 的凭证不落盘"；
- **单飞覆盖"首次获取"和"401 后的重换"两种情况**：N 个并发请求（含同时收到 401 的）
  最多产生一次 exchange，不会在 B 侧堆出 N 个会话（B 的 `external` 上限只有 5，超出还会踢最旧）；
- **`force` 不绕过单飞**：`get(true)` 只是跳过缓存读取，仍然复用在途请求；
- **不误伤新 token**：一个用**旧 token** 发出的请求，其 401 可能在别人刷新成功之后才回来 ——
  这时 `cached !== usedToken`，直接跳过刷新并用新 token 重试。
  少了这一步，刚换好的 token 会被清掉、随后再多发一次 exchange（旧实现就是这样）；
- **用 token 本身当版本号**：每次 exchange 拿到的都是全新随机串，"换过就一定不相等"，
  与额外的 `tokenVersion` 计数器等价，但少一份需要同步的状态；
- **按 `body.code` 重试一次**（不是按 HTTP 状态码）：token 15 分钟过期后用户不会看到报错；
  连续两次 401 说明问题不在 token（多半是映射被禁用 / 角色被回收），不再重试；
- `VITE_PASSUP_ORIGIN` 走构建期注入（与 A 现有 `VITE_DEV_PAGES` 同一套模式）；
  改这个值需要**重新构建前端**（A 的前端是构建产物，不是运行时配置）。

**并发校验**（零依赖，不需要装 `node_modules`）：

```bash
node frontend/scripts/check-passup-token.mjs
```

覆盖 6 项不变量：并发首次只换一次 / 并发 401 只多换一次 / **迟到的 401 不误伤新 token** /
exchange 失败不缓存且可重试 / 刷新在途时后续请求复用在途 / reset 后重新获取。
（已实测：把"迟到的 401"这条的判据去掉后，该脚本以 `AssertionError` 退出并指出
「又发起了一次 exchange（应为 2 次，实际 3 次）」—— 说明它确实在测这件事，不是空跑。）

### 4.4 B 侧：CORS（本版新增，B 原本没有任何 CORS 配置）

```java
@Bean
CorsConfigurationSource corsConfigurationSource(SsoProperties props) {
    CorsConfiguration cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(props.getAllowedOrigins());        // ["https://<A 的域>"]，不用 "*"
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));  // 关键：要允许 Authorization
    cfg.setAllowCredentials(false);                          // 不用 Cookie
    cfg.setMaxAge(600L);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    // 路径来自配置 sso.cors-paths，默认只有 /api/sso/**；A 页面还要调哪些接口就显式加进去
    props.getCorsPaths().forEach(path -> source.registerCorsConfiguration(path, cfg));
    return source;
}
```

- 配置项：`sso.allowed-origins`（env `SSO_ALLOWED_ORIGINS`，**精确来源、含 scheme 与端口、不带尾斜杠**）
  与 `sso.cors-paths`（env `SSO_CORS_PATHS`，默认 `/api/sso/**`）；
  配了 `*` 会被忽略并告警 —— 避免"以为收窄了其实全放开"；
- `SecurityConfig` 里加 `http.cors(cors -> cors.configurationSource(corsConfigurationSource))`
  （Spring Security 会自行放行预检 `OPTIONS`）；
- `/api/sso/exchange` 要加进 `PublicEndpoints.PERMIT_ALL`（那是"哪些路径免认证"的**唯一权威来源**，
  `SecurityConfig` 与 `TokenAuthenticationFilter` 都引用它）—— 它的认证就是签名本身；
- **`/api/admin/**` 不要整段放开 CORS**，只放 A 页面真正用到的那几个前缀，把暴露面压到最小；
- **白名单外的来源会被服务端拦掉**（冒烟实测）：Spring 的 `CorsFilter` 对"带了 `Origin` 但不在白名单"
  的请求直接返回 **403 + 空响应体**，所以这条护栏确实在服务端生效，不只是浏览器行为；
- **但它仍然不是安全边界**：它拦的是"带 `Origin` 头的请求"，**不带 `Origin` 头**（`curl`、服务端调用）
  照样放行 —— 它拦的是浏览器，不是攻击者。真正的防护是签名 + 时间窗 + nonce（见 §8.3）。

## 5. 数据模型

### 5.1 映射表（PostgreSQL，Flyway `V28__external_user_map.sql`）

```sql
CREATE TABLE external_user_map
(
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source_system  VARCHAR(32)  NOT NULL,               -- 来源系统标识，当前仅 'A'
    source_user_id VARCHAR(64)  NOT NULL,               -- A 控制台账号名（AUTH_USERS 的 username）
    local_user_id  BIGINT       NOT NULL,               -- B 本地用户 ID，关联 app_user.id
    status         SMALLINT     NOT NULL DEFAULT 1,     -- 1 可用 / 0 禁用（临时关权限，不删数据）
    remark         VARCHAR(255),
    created_at     TIMESTAMPTZ  NOT NULL,
    updated_at     TIMESTAMPTZ  NOT NULL
);

CREATE UNIQUE INDEX uk_external_user_map_source
    ON external_user_map (source_system, source_user_id);

CREATE INDEX idx_external_user_map_local ON external_user_map (local_user_id);

COMMENT ON TABLE external_user_map IS '外部系统用户映射表（跨系统免密直连）';
COMMENT ON COLUMN external_user_map.source_system IS '来源系统标识，如 A（产品分析平台）';
COMMENT ON COLUMN external_user_map.source_user_id IS
    '来源系统稳定账号标识，不要求与本系统用户 ID 一致；当前为 A 控制台账号名（AUTH_USERS 的 username）';
COMMENT ON COLUMN external_user_map.local_user_id IS 'B 本地用户 ID，关联 app_user.id';
COMMENT ON COLUMN external_user_map.status IS '状态：1 可用，0 禁用';
```

**映射键的选择（按 A 的实际账号模型）**

- A 的账号来自环境变量 `AUTH_USERS`（**没有用户表**），所以 `source_user_id` 取**账号名**（如 `zhangsan`），一人一号；
- 用账号名而不是"某个数字 id"，是因为账号名是 A 侧**唯一稳定**的标识；
- 将来 A 若接入真正的用户表并拿到稳定的用户 ID，**只换值、不换结构**（`VARCHAR(64)` 足够容纳 ULID/UUID）；
- 语义上它不是"A 的数据库主键"，而是"A 对外稳定的账号标识"（评审第 3、10 条）。

### 5.2 与仓库既有约定的对齐

| 原模板写法 | 本版写法 | 原因 |
| :--- | :--- | :--- |
| MySQL：`AUTO_INCREMENT` / `ENGINE=InnoDB` / `ON UPDATE CURRENT_TIMESTAMP` | PostgreSQL：`GENERATED BY DEFAULT AS IDENTITY` / `TIMESTAMPTZ`，时间由 JPA 审计维护 | B 是 PostgreSQL + Flyway；`updated_at` 由 `BaseEntity` 的 `@LastModifiedDate` 负责 |
| 表名 `sys_external_user_map` | `external_user_map` | 仓库里没有 `sys_` 前缀约定（`app_user` / `asset_package` / `experience_template`） |
| `COMMENT '...'` 内联 | `COMMENT ON TABLE/COLUMN` | PostgreSQL 语法 |
| 解绑走 `DELETE`（未说明语义） | **硬删** | 配置类表（`asset_package`、`experience_template`）都是硬删 + `status` 软禁用；只有 `app_user` / `user_auth` 用 `@SoftDelete`。映射表属配置类，跟随后者 |

### 5.3 目标 B 用户的角色（**v4.2：直接绑 ADMIN，不建新角色**）

A 页面拿到的权限 = 映射到的 B 用户的权限。所以映射目标的选择直接决定"A 页面能干什么"。

**v4.2 的决定**：**不新建 `EXTERNAL_OPERATOR` 角色、也不建专门的承载账号**，
`required-role-code` 直接配 `ADMIN`，每个 A 账号 **1:1 绑到各自已有的 B 管理端账号**。

| 做法 | 结果 | 采用 |
| :--- | :--- | :--- |
| **1:1 绑到各自的 ADMIN 账号** | A 页面 = 该人的全权 B 管理端 | ⭐ **v4.2 采用**，代价见下方"已知代价" |
| 多个 A 账号共用一个专用账号（如 `sso_operator`） | 省事，但**审计被毁**：B 侧日志里 `localUserId` 全是同一个人，分不出谁做的 | ❌ **明确否决**，理由见下 |
| 新建最小权限角色 `EXTERNAL_OPERATOR` | 越权风险被结构性消除 | ⏸️ **推迟**，触发条件见下 |
| 绑到普通 `USER` 用户 | 不可用 | ❌ `USER` 角色自带 `system:user:query`，但没有任何管理端业务权限；且判据会误放行 C 端用户 |

**为什么否决"共用一个专用账号"（这是本版最容易搞反的一点）**

"审计只要追踪来源就行"这个理由，恰恰**反对**共用账号：

- 共用账号下，B 自己的审计日志（`clientType=EXTERNAL` 的会话、业务操作日志）里
  `localUserId` 恒为同一个值，**你分不出是张三还是李四干的**；
- 只能回头翻 `sso_exchange_ok source=A sourceUserId=zhangsan localUserId=<sso_operator>`，
  按时间/会话去对 —— 两个人同时在用的 15 分钟窗口里根本对不上；
- 1:1 映射则让 B 侧审计**直接落到本人**，来源只用来解释"这次操作是从 A 页面发起的"。

> 一句话：**来源追踪是"补充信息"，不是"身份替代品"。**

**为什么保留角色校验（而不是删掉）**

`required-role-code` 不是给审计用的，它管的是**爆炸半径**，同时兼任绑定时的**误操作护栏**：

- A 页面拿到的是 B 的**完整 access token**，放在浏览器内存里 ——
  页面上画了哪些按钮不重要，打开 devtools 就能拿它调**任意** B 管理接口；
- 所以绑 ADMIN = A 页面 = 全权 B 管理端；
- 而校验本身能拦住"误绑到 C 端 `USER` 账号"这种操作（`USER` 角色自带 `system:user:query`，
  这正是**不能用权限点当判据**的原因）。

**已知代价（必须正视）**

> A 页面 = 全权 B 管理端。**任何能登录 A 的人，都能通过 A 页面（甚至绕过 A 的 UI）执行 B 的任何管理操作。**
> 这个代价成立的前提是：**能登 A 的人 ⊆ 你愿意给 B 管理端权限的人**。
> 按现状（`AUTH_USERS` 手工配置、内部少数几个人）该前提成立，故接受。

**将来补最小权限角色的触发条件**（出现任一即回头做）：

1. A 的受众扩大到**非 B 管理员**（例如只做数据查看的运营同学）；
2. A 页面开始做"用户查询 / 老师备注"之外的事（发资产、撤销订单、改配置…）；
3. A 侧出现多租户 / 外包 / 临时账号。

**绑定校验的判据**（写成配置项，不写死）：

```yaml
sso:
  clients:
    A:
      secret: ${PASSUP_SSO_SECRET}
      required-role-code: ADMIN   # v4.2：不新建角色；见上方"已知代价"
```

> ⚠️ **代码默认值是 `EXTERNAL_OPERATOR`，而种子角色里没有这个角色**
> （`role_permissions.json` 只有 `ADMIN` / `USER`）。所以**必须显式覆盖成 `ADMIN`**，
> 否则表现为：绑定被拒（`ExternalUserMapService#bind`）、兑换一律
> `reason=role_missing` → `code=403`（`SsoExchangeService` 第 ⑦ 步）。
> 保留这个"默认值指向一个不存在的角色"是刻意的 fail-closed —— 忘配就整体不可用，
> 而不是悄悄放行全权。

## 7. 映射关系的建立时机

> 结论：**兑换链路只读映射，绝不建号**。创建/修改映射走独立管理接口，需管理员权限。

| 方案 | 说明 | 采用 |
| :--- | :--- | :--- |
| ① 管理员预绑定 | B 后台「外部账号绑定」页填写 `A 账号名 + B 用户`，写入映射表 | ⭐ **推荐** |
| ② 首次兑换时自动绑定 | 拿 A 账号名去 B 查同名用户，存在则自动建映射 | ❌ 账号名错位会绑错人 |
| ③ 自动建影子账号 | 无映射时在 `app_user` 插新用户 | ❌ 会堆影子账号、权限失控 |
| ④ 前端引导手动绑定 | 无映射时引导用户输 B 账号密码验证后写映射 | ⭕ 折中，管理员不想逐个配置时用 |

> A 侧账号是"内部少数几个人"（`AUTH_USERS` 手配），映射行数很少，① 的运维成本几乎为零。

## 8. 安全要点

### 8.1 必须做到

1. **HTTPS**：A 与 B 都必须走 TLS（签名与 token 都在公网传输）；
2. **共享密钥只放 A 后端**（B 持有同一把用于验签），绝不进前端代码与仓库（环境变量 / k8s Secret）；
3. **A 的会话密钥与 SSO 密钥分开**（`AUTH_SECRET` ≠ `PASSUP_SSO_SECRET`）；
4. **B 的 access token 不进 URL**（它只在请求头里），且 **A 侧只放内存、不落 localStorage**；
5. **A 页面能做什么 = 映射到的 B 用户的权限**。v4.2 绑的是 ADMIN 账号，这条代价必须被正视并记录（§5.3）；
6. **映射只经管理员接口增删改**，兑换链路只读；
7. **兑换接口必须验签**（见 §8.3）。

### 8.2 密钥粒度（评审第 6 条）

```text
现在：   A ──── A_B_SECRET ──── B
将来：   A ── A_B_SECRET ── B
        A ── A_C_SECRET ── C
```

配置结构按"每个信任关系一把密钥"设计（B 侧 `sso.clients[source].secret`；A 侧一个
`PASSUP_SSO_SECRET` 对应它），当前只配一条。**不要**用一个全局 `SHARED_SECRET` 覆盖所有来源。

### 8.3 兑换接口是公网可达的

这个接口必须能被**任意位置的浏览器**（运营同学在哪都能开分析平台）跨域调用，来源 IP 不可预测：

| 层 | 手段 |
| :--- | :--- |
| 主防护 | HMAC 签名（密钥不出后端）+ 60s 时间窗 + nonce 一次性 |
| 浏览器侧护栏 | CORS 精确白名单（带 `Origin` 且不在白名单 → 服务端 403 空响应；但**不带 `Origin` 即绕过**，所以它拦的是浏览器不是攻击者） |
| 抗爆破/抗刷 | 按来源 IP + `sourceUserId` 限流（复用 B 侧现有 Redis；阈值宽松，只防脚本狂刷） |
| 可观测 | **验签失败 / 时间窗超时 / nonce 重复一律 WARNING + 告警** |
| 信息最小化 | 失败响应不区分"未绑定"和"用户不存在"，统一文案，避免枚举 B 用户 |

### 8.4 token 在 A 的页面里 —— 真实的残余风险

- B 的 access token 由 A 的页面持有（内存），**A 域上一旦有 XSS，token 会被偷**，
  攻击者可在 15 分钟内以该 B 用户的身份操作 B；
- 缓解：① token 只存内存、不落 localStorage；② 有效期 15 分钟、无 refresh token；
  ③ A 页面用最小权限角色（§5.3），把"被偷了能干什么"压到最小；
  ④ A 是内网工具、无 UGC 内容，XSS 面本身很小；
- **这是本方案与"每请求签名"方案的本质差别**（§2），接受它换来的是 B 侧零认证改动。

### 8.5 时间参数统一（评审第 12 条）

| 参数 | v1 | v4 | 说明 |
| :--- | :--- | :--- | :--- |
| 签名有效期 | 文档 60~120s / 代码 ±5min | **时间窗 ±60s** | 签名只在这一刻有效 |
| nonce TTL | 300s | **120s** | 时间窗的 2 倍，留一点容错 |
| B access token | — | **15 分钟**（B 全局配置） | 过期由 A 前端静默重换（§4.3） |

> 若 A、B 两台机器都做了 NTP 同步，可把时间窗收紧到 ±30s。

### 8.6 审计的锚点

- **兑换事件**是一条完整日志：`sso_exchange source=A account=zhangsan localUserId=<id> ip=<用户 IP> 结果` ——
  它把"A 的哪个账号"与"B 的哪个用户"在某一刻绑定起来，是排查"这个操作是谁做的"的起点；
- 后续每个请求的审计由 **B 现有链路**负责（会话里带 `clientType`，可与用户自己登录的会话区分）；
- **不要**为"每个请求都记一条来源系统"再改造 B 的日志体系 —— 收益低、侵入大。

## 9. 边界与已知代价

| 问题 | 处理 | 代价 / 备注 |
| :--- | :--- | :--- |
| **A 页面 = 全权 B 管理端**（v4.2 已接受的代价） | 映射目标是 ADMIN 账号，A 页面（乃至任何能登 A 的人）持有的是全权 token；范围靠 A 页面自己克制 | 前提：**能登 A 的人 ⊆ 愿意给 B 管理端权限的人**。受众扩大、或 A 页面开始做用户查询/备注之外的事时，必须回头补最小权限角色（§5.3） |
| **会话名额** | 新增 `ClientType.EXTERNAL`，兑换时用它建会话（实施注意见**附 C**），把"A 页面换来的临时会话"与"用户自己在管理端的登录"**分开计名额** | 若复用 `WEB`，A 页面多次换 token 会累积到 `max-sessions-per-device.web = 5`，超出会**踢最旧会话** —— 可能把用户自己的管理端会话踢掉（体验隐蔽、难排查）。**不借位 `DESKTOP`**：那会让后来人问"为什么 A 系统登录的用户算桌面端"，审计、踢会话、统计口径都会含糊 |
| **A 页面反复换 token 堆积会话** | 前端缓存 token（内存）+ 单飞重换（§4.3）；一个标签页 15 分钟只换一次 | 观测点：`auth:user:sessions:{userId}:EXTERNAL`。若发现堆积，把 `external` 上限调大或改为"同 A 账号复用会话" |
| **B 用户已注销** | `User` 带 `@SoftDelete(deleted_at)`，兑换时 `getUserById` 自动过滤为 `null` → 拒绝换 token | 提示管理员修映射；`status=0` 亦可临时断掉 |
| **B 用户角色被回收** | 已发出的 token 仍带旧权限，最长 15 分钟后自然失效 | 15 分钟窗口内不拦（可接受）；要更严就把 access token TTL 调短，或在 B 侧权限校验时每次查库（`TokenAuthenticationFilter` 已有"会话里没有权限则回查数据库"的兜底，但正常情况走缓存） |
| **A 账号被停用** | 从 `AUTH_USERS` 移除该账号 → A 登录态失效 → 签不出参数 | **残余风险：已发出的 token 最长 15 分钟内仍可用**。若不可接受：把 access token TTL 调短，或在 B 绑定页禁用该映射（`status=0`，立即生效） |
| **A 前端跨域被浏览器拦** | 表现为"页面数据加载失败"或 CORS 报错 | 排查顺序：① B 的 `CorsConfigurationSource` 是否含 A 的**精确**域（含 scheme 与端口，不带尾斜杠）② 是否允许了 `Authorization` 头 ③ 预检 `OPTIONS` 是否被放行 ④ A 是否用 HTTPS 访问 |
| **A 后端没配密钥** | 签名接口返回 503 | 明确报错，不要静默降级 |
| **一个 A 账号绑多个 B 账号** | 禁止，唯一索引拦截 | — |
| **换绑** | 管理端解绑（硬删）+ 重新绑定 | 操作留痕靠 `remark` / 后续接审计 |
| **未绑定 / 映射被禁用 / 角色不足** | 兑换阶段就失败，**不建会话、不产生任何 B 侧登录态** | 用户看到明确提示 |
| **B 后端不可用** | A 页面请求失败，提示"稍后重试" | 不影响 A 平台其他功能 |
| **双向互通 / 统一登出 / 三系统接入** | 再评估标准 SSO | 见 §12 |

### 9.1 失败场景与用户可见提示

| 失败场景 | 判定位置 | 用户提示 | 附加动作 |
| :--- | :--- | :--- | :--- |
| A 未登录 / 会话过期 | A 后端签名接口 | 前端跳 A 的登录页（A 现有 401 处理） | — |
| A 后端未配密钥 | A 后端签名接口 | 「跨系统跳转未配置，请联系管理员」 | 记 ERROR |
| 未绑定 / 映射被禁用 / 角色不足 | B 兑换接口 | 「该账号未授权访问 PassUp 后台」 | B 记审计日志；不建会话 |
| 验签失败 / 时间窗超时 / nonce 重复 | B 兑换接口 | 「无法访问 PassUp 后台，请稍后重试」 | **记审计日志并告警** |
| CORS 被拒 | 浏览器（请求根本没到 B） | 同上 | 排查配置（§9 表） |
| token 过期 | B 侧 401 | **无感**（A 前端静默重换一次并重试） | — |
| 重换也失败（映射被禁用等） | B 兑换接口 | 显示具体原因，页面给出空态 | 记审计日志 |

## 10. 验收清单

- [ ] A 页面打开即拿到 B 的 token（用户无感），能列出 PassUp 用户
- [ ] A 页面能读/写老师备注，操作结果与在 B 管理端操作一致
- [ ] **B 前端代码零改动**（`pass-up.frontend` 除了可选的绑定管理页，没有其他 diff）
- [ ] 未绑定的 A 账号：页面明确提示未授权，B 侧**不建会话**
- [ ] 映射 `status=0` 时立即失效（已发出的 token 最多 15 分钟后自然失效）
- [ ] 篡改 `sign` / 任一参数 → 验签失败
- [ ] 复用同一 `nonce`（重放）→ 拒绝
- [ ] 超过时间窗（±60s）→ 拒绝
- [ ] 白名单外的 `Origin` → 服务端 403 空响应（CorsFilter 拦掉）
- [ ] **不带** `Origin` 头 → 仍按签名校验（说明 CORS 不是安全边界，别把它当防线）
- [ ] 用错误签名 + 伪造 `Origin` → 依然被拒（签名才是真正的防线）
- [ ] token 过期后页面**无感恢复**（不出现报错弹窗）
- [ ] token 不在 `localStorage` / 地址栏 / 浏览器历史里（只在内存与请求头）
- [ ] 目标 B 用户换成"角色不足的账号" → 绑定接口拒绝
- [ ] A 页面调一个它**没有权限**的 B 接口 → B 返回 403（证明权限由 B 决定，不由 A 决定）
- [ ] A、B 原有登录、权限逻辑未受影响（两侧回归）
- [ ] 生产 HTTPS + CORS 白名单为 A 的精确域名

## 附 C：实施时的两个坑（`ClientType.EXTERNAL`）

> 为什么不借位 `DESKTOP`：见 §9「会话名额」那行。完整改动点（枚举、record、yml、switch、踢会话）
> 动手时看代码即可，这里只留两处**症状隐蔽、删了会踩**的。

1. **`max-sessions-per-device.external` 必须显式配上。** `JwtProperties.MaxSessionsPerDevice` 是 record，
   `application.yml` 漏配会**绑成 0**；而 `AuthService#enforceSessionLimit` 的逻辑是"超出上限就踢最旧"，
   `limit = 0` 会把**刚建好的那个会话立刻撤销** —— 症状是"兑换拿到了 token，但所有请求都 401"，
   且日志里看不到报错（是正常的超限逻辑在干活，不是异常）。可选加一道代码保险：
   `case EXTERNAL -> Math.max(1, maxSessionsPerDevice.external());`
2. **`AuthService#kickUserSessions(userId)` 要补 `EXTERNAL`。** 它的"全类型踢"是**逐个枚举硬编码**的
   （`WEB`/`APP`/`MINIAPP`/`DESKTOP`/`UNKNOWN` 五行相加），漏了会导致"封禁/注销用户时踢不掉这类会话"，
   对方还能继续用 15 分钟。
