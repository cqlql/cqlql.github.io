        设计注记 · 与 docs/backup-restore.md 的对照
        
    
          
  • 本页钉死 §5.2 三段式：候选清单（A 只读）→ 预演（A 只读）→ 执行（B 写）。
              命令 ops restore list/plan/run 已注册、已实现；真实参数与门禁见
              ops restore help 与分册 §7。原型仍是静态速览，不执行任何动作。
    • 
          
  • 门禁照抄六道门并加码：confirm=yes、name 只认清单、候选路径只认备份根目录、
              目标库名人工输入两次并逐字比对、默认 restore_test、覆盖生产要额外勾选、
              服务端先跑 --dry-run、任务脱离 HTTP、单任务锁、日志脱敏。详见分册 §5.3。
    • 
          
  • 弹窗没有 sudo 密码输入：恢复以清单 user 在备份机跑，不需要提权；
              这与「备份能力部署」的安装弹窗不同。
    • 
          
  • 评审 R1：工具不读 crontab。安全条的「停定时备份」是人在前置清单里的
              显式声明（未确认 / 已人工确认），不是采集事实；cron-running 场景的
              语义是「未确认」，阻塞来自缺这项确认。停定时备份是独立显式动作，原型里点它只给提示，
              不真改 crontab（现行标签还有前缀误删问题，见分册 §4 第 4 条）。
    • 
          
  • 评审 R2：--server 只认备份机（候选来源 / 采集地 / 脚本执行地），
              数据写到主服务器，后者由该机 backup.env 决定、不由清单另选。
              预演计划首行必须回显恢复目标供人核对。
    • 
          
  • 评审 R3：阻塞分全局与候选行两级，都由服务端下发；原型 planFor()
              只是把多份服务端响应投成静态对象，换选中行 = 重新取一次计划，
              实现时不能照抄成前端重算 available。
    • 
          
  • 评审 R4 / R5：界面预演只是给人看的只读动作，不是执行凭证，服务端每次
              写动作前自己跑 --dry-run；报告只报脚本结果，失败不重跑 / 不自动清场，
              PG 成功也只说「数据已恢复」，Flyway 兼容性必须人工确认，不许假装应用已恢复。
    • 
          
  • 落地同步清单已逐项完成（2026-11-08）：main.go 注册表 + 菜单、
              internal/restore/、web/src/features/restore/、
              ui.md §16、AGENTS.md 状态 / 硬约束 33 / 命令表 / 速查表、
              本页与分册状态行；没有新增配置键。判据见分册 §5.6 / §7。
              🔴 原型留作交互回归基线，六场景仍是 §5.7 的验收用例集（真机未跑）。
