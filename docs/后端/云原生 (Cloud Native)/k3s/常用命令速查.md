日常运维 K3s 集群时的高频命令，按用途分类整理。

> K3s 的 `kubectl`、`crictl`、`ctr` 都通过 `sudo k3s` 前缀调用，因为它们内嵌在 K3s 二进制中，不依赖外部安装。

---

## 一、Pod / 工作负载

### 查看所有命名空间的 Pod

```bash
sudo k3s kubectl get pod -A
```

最常用的命令，一眼看清整个集群在跑什么。

### 查看特定命名空间的资源

```bash
# 同时列出 DaemonSet、Deployment、Pod
sudo k3s kubectl get daemonset,deployment,pod -n kube-system
```

一次性看多种资源类型，适合快速排查某个命名空间里所有关键组件。

### 查看 DaemonSet 详细信息

```bash
sudo k3s kubectl describe -n kube-system ds kube-vip-ds
```

`describe` 输出 DaemonSet 的完整事件、状态、Pod 模板等，排查"Pod 为什么没起来"时的第一选择。

### 重启 Deployment

```bash
# 触发滚动重启
sudo k3s kubectl rollout restart deployment traefik -n kube-system

# 查看滚动更新进度
sudo k3s kubectl rollout status deployment traefik -n kube-system
```

`rollout restart` 会逐个重建 Pod（滚动更新），不影响流量。`rollout status` 实时显示更新进度，确认是否全部就绪。

### 删除指定 Pod

```bash
sudo k3s kubectl delete -n kube-system pod svclb-traefik-958c134b-zzk45
```

> Pod 属于更高层控制器（DaemonSet / Deployment）时，删除后会自动重建——这是正常行为，不是 bug。

## 二、镜像管理

K3s 内置 containerd 作为容器运行时，镜像管理通过 `crictl` 和 `ctr` 两个工具。

### `crictl` vs `ctr` 的区别

| 工具 | 定位 | 适用场景 |
| --- | --- | --- |
| `crictl` | CRI（容器运行时接口）标准客户端，与 K8s 的 Pod/容器概念对齐 | 日常查看容器状态、日志、镜像 |
| `ctr` | containerd 原生客户端，操作底层 containerd namespace | 导入/导出镜像、直接操作底层镜像存储 |

> 简单记：`crictl` 是"K8s 视角"，`ctr` 是"containerd 视角"。看镜像列表用 `crictl`，导入导出镜像用 `ctr`。

### 查看镜像列表

```bash
# 方式一：crictl（推荐，K8s 视角）
sudo k3s crictl images

# 方式二：ctr（containerd 原生，需指定 namespace）
sudo k3s ctr i ls
```

> `ctr` 操作的是 containerd 的默认 namespace（`default`），而 K3s 的 Pod 镜像存在 `k8s.io` namespace 下。所以 `ctr i ls` 看到的镜像可能和 `crictl images` 不一致——日常建议用 `crictl`。

### 导入离线镜像

```bash
sudo k3s ctr image import ./local-path-provisioner.tar
```

离线环境或内网部署时，先把镜像打成 tar 包传到节点，再用此命令导入 containerd。导入后即可被 K3s 正常调度使用。

## 三、常用组合场景

### 排查 Pod 启动失败

```bash
# 1. 看全局 Pod 状态
sudo k3s kubectl get pod -A

# 2. 看具体资源详情
sudo k3s kubectl describe -n <namespace> pod <pod-name>

# 3. 看日志
sudo k3s kubectl logs -n <namespace> <pod-name>
```

### 更新镜像后重启

```bash
# 1. 导入新镜像
sudo k3s ctr image import ./my-app.tar

# 2. 滚动重启
sudo k3s kubectl rollout restart deployment my-app -n default

# 3. 确认完成
sudo k3s kubectl rollout status deployment my-app -n default
```

### 网络组件异常

```bash
# 看 kube-system 下所有关键组件
sudo k3s kubectl get daemonset,deployment,pod -n kube-system

# 如果 svclb-traefik Pod 异常，可以删除让它重建
sudo k3s kubectl delete -n kube-system pod <svclb-traefik-xxxxx>
```
