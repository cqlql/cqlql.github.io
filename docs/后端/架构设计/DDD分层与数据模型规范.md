# DDD 分层与数据模型规范

> **实用主义 DDD = 用 DDD 的思想解决复杂度，而不是照搬 DDD 的全部理论。**
>
> 本文融合正统 DDD 四层架构与实践中的实用主义落地经验，兼顾理论完整性和工程可操作性。

## 一、核心架构层级职责（四层架构体系）

DDD 将传统"三层"演进为"四层"，核心思想是**依赖倒置**：领域层处于最中心，绝不依赖任何外部框架和底层数据库。

| **层级**                        | **对应组件**                            | **核心作用**                                         | **处理的数据模型**                                           | **核心原则**                                                 |
| ------------------------------- | --------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **用户接口层 (Interfaces)**     | `Controller`, `Consumer`                | **网关与适配器**：协议转换与路由分发                 | 接收外部请求，封装为 `Command/Query` 传给应用层；将结果组装为 `Response/VO`。 | 处理 HTTP/MQ 协议、基础参数校验、鉴权。**绝对不包含任何业务逻辑**。 |
| **应用层 (Application)**        | `ApplicationService`                    | **业务编排与用例调度**：系统的"用例（Use Case）"入口 | 接收 `Command/Query`，调用领域层和基础设施层，返回 `DTO`。   | 负责事务控制、权限校验、发布领域事件。**非常薄，不包含核心业务规则**，只负责调度。 |
| **领域层 (Domain)**             | `Aggregate`, `Entity`, `Domain Service` | **业务大脑**：表达最纯粹的业务规则与状态流转         | 处理 `Domain Entity`、`Value Object`。                       | 纯净对象，**无视任何数据库与外部框架技术**。这是 DDD 的绝对核心。 |
| **基础设施层 (Infrastructure)** | `RepositoryImpl`, `RPC Client`          | **技术落地**：持久化、外部调用、消息发送             | 操作 `PO (Persistent Object)`、调用外部 `DTO`。              | 提供底层技术实现。实现领域层定义的接口（依赖倒置），只关心技术细节。 |

### 传统三层对比

| **组件**       | **所在层级**       | **核心作用**                             | **处理的数据模型**                                           | **核心原则**                                                 |
| -------------- | ------------------ | ---------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Controller** | 接口层 (Web 层)    | **交通警察**：路由转发与输入输出控制     | 接收外部 `Request`，转换为 `Command` 传给底层；接收底层 `DTO`，封装为 `Response/VO` 返回。 | 处理 HTTP 请求、参数基础校验、身份解析。**绝对不包含业务逻辑**。 |
| **Service**    | 业务层 (Domain 层) | **业务大脑**：执行核心业务逻辑与规则     | 处理领域模型，调用 `Repository` 或其他 Service               | 负责事务控制、业务规则校验、状态流转。**不关心外部协议**（无视 HTTP/JSON），是系统最核心的层级。 |
| **Repository** | 持久层 (Data 层)   | **数据搬运工**：与数据库进行交互         | 操作 `PO`，查询返回 `Projection`                             | 只负责数据的 CRUD 和 SQL 组装。**不包含业务逻辑**。          |

## 二、核心领域层（系统的业务基石）

在 DDD 中，业务逻辑不再塞进臃肿的 `Service` 里，而是下沉到拥有数据和行为的**富领域模型（充血模型）**中。

| **对象**                              | **核心作用**                                             | **特点**                                                     | **示例**                              |
| ------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------- |
| **聚合根 (Aggregate Root)**           | **保证业务一致性的边界**，是外部访问领域模型的唯一入口。 | 包含实体和值对象。必须通过聚合根才能修改内部实体的数据。     | `Order` (包含多个 OrderItem)          |
| **领域实体 (Domain Entity)**          | **具有唯一标识**，且生命周期内状态会发生变化的业务对象。 | 拥有丰富的业务方法（充血模型）。不包含持久化注解，完全脱离数据库。 | `User` (包含 `changePassword()` 动作) |
| **值对象 (Value Object)**             | **描述实体的特征或属性**，没有唯一标识，一旦创建不可变。 | 往往用来代替基本数据类型，内聚了校验逻辑。                   | `Address` (包含省市区), `Money`       |
| **领域事件 (Domain Event)**           | **解耦业务流程**，表示领域内发生的一个重要既定事实。     | 命名通常是过去时。用于触发其他聚合或外部系统的响应。         | `UserRegisteredEvent`                 |
| **领域服务 (Domain Service)**         | **协调跨实体的业务逻辑**。                               | 当一个业务规则不适合放在单一实体/聚合根中时（例如转账），才放入领域服务。它是无状态的。 | `TransferService`                     |

> **Model 层的核心价值**：核心业务逻辑只依赖纯净的 Model，不依赖底层的数据库结构（PO），实现了真正的**"业务与技术解耦"**。

## 三、数据模型职责说明

为了保证领域层的绝对纯净，数据在跨层时必须进行转换。针对不同的场景需要使用特定的数据载体。

| **对象类别**   | **具体命名**               | **所在层级**       | **作用与特点**                                               | **示例**                               |
| -------------- | -------------------------- | ------------------ | ------------------------------------------------------------ | -------------------------------------- |
| **指令/查询**  | **Command / Query**        | 应用层 (入参)      | 封装调用者意图（写用 Command，读用 Query）。包含基础注解校验。 | `CreateOrderCommand`, `OrderListQuery` |
| **输入模型**   | **Request**                | 接口层 (入参)      | 接收外部（前端/第三方）请求参数。可校验、与接口强绑定。       | `CreateUserRequest`                    |
| **输出模型**   | **Response / VO**          | 接口层 (出参)      | 封装并返回给前端的数据载体。控制字段暴露、可包含脱敏逻辑。   | `UserProfileResponse`                  |
| **数据传输**   | **DTO**                    | 应用层 (出参/跨界) | 内部服务间或跨进程的数据传输。解耦内部结构，适配远程调用。   | `WechatUserInfoDTO`                    |
| **领域对象**   | **Entity / Aggregate**     | 领域层             | **真正的业务核心**。充血模型，包含状态和行为。无任何框架注解。 | `Order` (包含 `pay()` 等业务方法)      |
| **持久化对象** | **PO (Persistent Object)** | 基础设施层         | 数据库表结构的一一映射。与 ORM 强绑定。**贫血模型，只有 getter/setter**。 | `OrderPO` (映射 `t_order` 表)          |
| **读模型**     | **Projection**             | 基础设施/应用层    | 查询结果的精简或聚合视图。绝对只读、字段子集、与 SQL 强绑定。 | `UserPermissionProjection`             |

### 命名风格约定

针对输入和输出，团队需统一选择**其中一种**命名风格，切勿混用：

1. **RESTful 标准风格（最常见）**
   - **输入**统一叫 `xxxRequest`（例如 `CreateUserRequest`）。
   - **输出**统一叫 `xxxResponse`（例如 `UserDetailResponse`）。
   - *(注：`Form` 属于遗留 MVC 时代叫法，现代前后端分离架构中建议淘汰。)*

2. **CQRS / DDD 风格（适合复杂业务）**
   - **输入 (写)** 叫 `xxxCommand`（例如 `CreateUserCommand`，代表改变状态的命令）。
   - **输入 (读)** 叫 `xxxQuery`（例如 `UserDetailQuery`，代表查询参数）。
   - **输出** 叫 `xxxDTO` 或保留 `xxxResponse`。

### 核心红线规范

- `PO` 绝不能进入领域层（Domain）和接口层（Controller）。PO 是底层实现细节。
- `Projection` 绝不能进入 `save` 或 `update` 的写操作流程。
- Controller 不能直接调用领域层（Aggregate/Entity），必须通过应用层（Application Service）作为门面。
- 接口的返回值**必须**是 `Response` 或 `VO`，绝对不能直接返回底层 `PO` 或领域对象。
- 不要用 `DTO` 作为 Controller 的入参（Request）或出参（Response），DTO 专职于 RPC 或服务间内部流转。

### DTO 核心理解

> **DTO = 用在"跨边界"的地方，而不是"所有地方"**

DTO 的适用场景：

1. **调第三方接口**：`WechatUserInfoDTO` —— 微信返回的数据结构 ≠ 你系统的结构
2. **微服务 / RPC / Feign**：`UserServiceClient.getUser() → UserDTO` —— 服务 A ≠ 服务 B，必须用 DTO 作为契约防止内部模型泄漏

**正确的数据流**：

```
Controller → Request / Response
Service → Domain Model
Repository → PO / Projection
外部 → DTO
```

### Request vs DTO（最易踩坑）

| **维度**     | **Request / Command (输入)**             | **DTO (传输)**                       |
| ------------ | ---------------------------------------- | ------------------------------------ |
| **方向**     | 纯输入（Input）                          | 双向传输（内部/跨进程）              |
| **面向对象** | 外部调用方（前端 / OpenAPI 客户端）      | 内部微服务 / 第三方 API 适配         |
| **参数校验** | ✅ 必须严格校验                          | ❌ 通常不负责基础校验（信任内部流转） |
| **复用性**   | ❌ 极低（与特定接口强绑定）               | ✅ 较高（可在多个内部方法间复用）     |

### Response vs VO（输出视角的细微差异）

- **Response**：更侧重于 **"接口级别的回应"**。例如 `ApiResponse<UserProfileResponse>`，包含了状态码、提示信息等外壳。
- **VO (View Object)**：更侧重于 **"视图层的数据聚合"**。如果后端只为特定 UI 服务，VO 的结构会严格贴合前端的 UI 组件树。
- **结论**：在绝大多数前后端分离项目中，`Response` 的 payload 本质上就是 `VO`，两者选其一作为包名统一即可（推荐统一使用 `Response` 降低认知负担）。

## 四、数据流转全景视图（CQRS 读写分离视角）

DDD 极力推崇 CQRS（命令查询职责分离），因为写操作需要复杂的业务规则保证一致性，而读操作通常只需要快速返回数据。

### 写操作数据流（Command - 意图改变系统状态）

1. **前端** 发起请求 → **接口层** `Controller` 接收请求，将 HTTP 参数转化为 `Command`。
2. **应用层** `ApplicationService` 接收 `Command`，开启数据库事务。
3. `ApplicationService` 调用 `Repository` 接口，从数据库查出 `PO`，并转换为 **领域层**的 `Aggregate / Entity`。
4. `ApplicationService` 调用聚合根的业务方法执行核心逻辑（例如：`order.pay(amount)`）。
5. `ApplicationService` 将修改后的聚合根交还给 `Repository` 进行 `save()`。
6. **基础设施层**的 `RepositoryImpl` 将聚合根转换为 `PO`，生成 SQL 落库，并发布领域事件。

### 读操作数据流（Query - 仅查询数据，无副作用）

1. **前端** 发起请求 → **接口层** `Controller` 将参数转化为 `Query`。
2. **应用层** `QueryService` 接收请求。**（注意：这里可以绕过领域模型！）**
3. 由于查询不需要业务规则校验，直接调用 **基础设施层** 的 DAO/Mapper。
4. 执行复杂 SQL，直接将结果映射为 `Projection` 或 `DTO`。
5. 返回给 `Controller` 封装为 `ViewObject` 响应给前端。

> **核心洞察**：写流程必须经过充血的领域模型（保证业务安全）；读流程直接走 SQL 查询到 DTO（保证性能）。这就是 DDD 落地的最佳实践。

### Command 与 Request 的分工

当参数简单时：

```
Request → Service（拆字段传）
```

参数变得复杂再引入 Command：

```
Request → Command → Service
```

| **环节** | **对象名称** | **主要职责**                                                 |
| -------- | ------------ | ------------------------------------------------------------ |
| **入口** | **Request**  | 适配 HTTP 协议。处理序列化、Swagger 注解、基础非空校验。     |
| **指令** | **Command**  | **封装意图**。它是 Service 方法的唯一参数，代表一个明确的业务动作。 |
| **模型** | **Entity**   | **处理规则**。Command 里的数据会填充到领域模型中进行运算。    |

**为什么要把 Command 和领域模型分开？**

1. **动作 vs. 状态**：`LoginCommand` 只需要 `code`；但 `User` 可能包含几十个字段。用 `User` 做登录参数，方法签名会变得极度模糊。
2. **幂等与溯源**：Command 是可以被记录和重放的。你可以记录"用户在 A 时间点发出了一个 LoginCommand"。
3. **多来源支持**：Service 方法只依赖 `Command`。如果明天要加一个 MQ 消费者来触发登录，它只需构建 `Command` 即可，完全不需要碰 `Request`。

## 五、推荐工程目录结构

### 标准 DDD 四层目录

```
├── interfaces/                   // 1. 用户接口层 (防腐、路由)
│   ├── controller/
│   ├── mq/consumer/
│   └── assembler/                // DTO <-> VO 转换
├── application/                  // 2. 应用层 (编排、事务、CQRS)
│   ├── command/                  // 写操作入参
│   ├── query/                    // 读操作入参
│   ├── dto/                      // 应用层输出载体
│   └── service/
│       ├── OrderAppService.java  // 处理 Command
│       └── OrderQueryService.java // 处理 Query (可选直连 DAO)
├── domain/                       // 3. 核心领域层 (纯业务、无依赖)
│   ├── model/                    // 聚合根、实体、值对象
│   ├── event/                    // 领域事件定义
│   ├── service/                  // 领域服务
│   └── repository/               // 仓储接口定义 (依赖倒置)
└── infrastructure/               // 4. 基础设施层 (底层实现)
    ├── persistence/
    │   ├── po/                   // 贫血持久化对象 (OrderPO)
    │   ├── mapper/               // MyBatis Mapper / JPA DAO
    │   └── repository_impl/      // 实现领域层的仓储接口
    ├── rpc/                      // 第三方 API 调用实现
    └── config/                   // 技术框架配置
```

### 实用主义按模块目录（适合中小项目）

```
modules/
├── user/                         // 用户域
│   ├── controller/
│   ├── request/                  // 明确的输入模型
│   ├── response/                 // 明确的输出模型
│   ├── service/                  // 应用服务（用例编排）
│   ├── domain/                   // 领域核心
│   │   ├── model/                // 实体 / 值对象（有行为）
│   │   ├── service/              // 领域服务（可选）
│   │   └── event/                // 领域事件（复杂时再加）
│   ├── repository/               // 数据操作
│   ├── entity/                   // 持久化模型 (PO)
│   ├── projection/               // 只读查询结果切面
│   └── dto/                      // RPC/第三方调用载体
└── permission/                   // 权限域
    └── ...
```

> **modules ≠ domain 层**：`modules/user` = domain + application + interfaces 的混合体。这是一种实用主义折中，适合不想过早拆分的项目。

## 六、一句话总纲

> - **Interfaces (接口层)** 负责把守外部边界，完成协议解析与视图组装。
> - **Application (应用层)** 负责用例编排、事务管理与权限控制，是系统的指挥官。
> - **Domain (领域层)** 负责纯粹的业务状态转移与规则约束，是系统的核心业务大脑（充血模型）。
> - **Infrastructure (基础设施层)** 负责提供底层能力（DB/MQ/RPC），并实现领域层定义的仓储接口。
> - **Command / Query** 分离了写意图与读诉求，杜绝了参数的混用。
> - **Entity / Aggregate** 告别贫血，真正承担起业务计算的职责。
> - **PO** 退回到它应有的位置：只做纯粹的数据库映射。
