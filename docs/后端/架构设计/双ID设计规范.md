# 双 ID 设计规范

## 一、设计目标

- **唯一性**：全局不重复
- **可扩展性**：支持分布式环境
- **数据库友好**：适合作为主键、索引高效
- **对外安全**：防枚举、防遍历

## 二、常见方案对比

### 自增 ID

| 优点 | 缺点 |
|------|------|
| 简单，无需额外依赖 | 不适合分布式（多节点冲突） |
| 数据库天然支持，B+ 树索引友好 | 可被枚举，暴露业务规模 |
| 数字型，占用空间小 | 迁移合并困难 |

### 雪花 ID（Snowflake）

| 优点 | 缺点 |
|------|------|
| 分布式友好，高性能 | 需要 workerId 管理（需引入协调组件） |
| 数字型，适合数据库主键 | 依赖时钟，时钟回拨有风险 |
| 趋势递增，索引友好 | 生成的 ID 可能被猜测 |

### UUID v4

| 优点 | 缺点 |
|------|------|
| 无中心，随处生成 | 字符串型，占用空间大 |
| 实现简单 | 完全无序，B+ 树索引性能差（页分裂） |

### ULID

| 优点 | 缺点 |
|------|------|
| 无中心，随处生成 | 字符串型，不适合作为主键 |
| 时间有序，索引友好 | 生成性能略低于雪花 ID |
| 26 字符可读性好，适合对外暴露 | - |

## 三、最终方案：双 ID 设计

```text
id  → BIGINT（内部主键，自增或雪花 ID）
uid → ULID（对外标识，API 层暴露）
```

**核心思想**：把"可变的内部实现（id）"和"稳定的外部契约（uid）"分离。

### 为什么采用双 ID？

| 维度 | 内部 ID (id) | 对外 ID (uid) |
|------|-------------|--------------|
| **类型** | BIGINT（数字） | ULID（字符串，26 字符） |
| **用途** | 数据库主键、外键关联、索引 | API 请求/响应、URL 参数、日志追踪 |
| **变更** | 可随数据库迁移改变（如从自增切换雪花） | 永远不变 |
| **安全** | 不对外暴露 | 不可枚举，无法推测数据规模 |

### 双 ID 的优势

- **无痛升级**：当需要从单机迁移到分布式时，只需改变内部 `id` 生成策略，对外 `uid` 保持不变，调用方无感知。
- **安全隔离**：即使内部 `id` 被意外泄露，攻击者也无法遍历数据。
- **索引性能**：内部 `id` 保持数字型，B+ 树性能最优；外部 `uid` 仅在对外接口中使用，不影响存储层。

### 使用示例

```text
API 请求:
  GET /api/users/01ARZ3NDEKTSV4RRFFQ69G5FAV     ← 使用 uid

数据库:
  SELECT * FROM users WHERE uid = '01ARZ3NDEKTSV4RRFFQ69G5FAV'

内部关联:
  orders.user_id = 123456                        ← 使用内部 id
```
