# 基于 DDD 的后端分层架构与数据模型规范

Domain-Driven Design (DDD)

## 一、 核心架构层级职责（四层架构体系）

在 DDD 架构中，系统从传统的“三层”演进为“四层”（或六边形架构），核心思想是**依赖倒置**：领域层处于最中心，绝不依赖任何外部框架和底层数据库。

| **层级**                        | **对应组件**                            | **核心作用**                                         | **处理的数据模型**                                           | **核心原则与特点**                                           |
| ------------------------------- | --------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **用户接口层 (Interfaces)**     | `Controller`, `Consumer`                | **网关与适配器**：负责协议转换与路由分发             | 接收外部请求，封装为 `Command/Query` 传给应用层；将结果组装为 `Response/ViewObject`。 | 处理 HTTP/MQ 协议、基础参数校验、鉴权。**绝对不包含任何业务逻辑**。 |
| **应用层 (Application)**        | `ApplicationService`                    | **业务编排与用例调度**：系统的“用例（Use Case）”入口 | 接收 `Command/Query`，调用领域层和基础设施层，返回 `DTO`。   | 负责事务控制、权限校验、发布领域事件。**非常薄，不包含核心业务规则**，只负责调度。 |
| **领域层 (Domain)**             | `Aggregate`, `Entity`, `Domain Service` | **业务大脑**：表达最纯粹的业务规则与状态流转         | 处理 `Domain Entity`、`Value Object`。                       | 纯净的 Java/业务对象，**无视任何数据库与外部框架技术**。这是 DDD 的绝对核心。 |
| **基础设施层 (Infrastructure)** | `RepositoryImpl`, `RPC Client`          | **技术落地**：持久化、外部调用、消息发送             | 操作 `PO (Persistent Object)`、调用外部 `DTO`。              | 提供底层技术实现。实现领域层定义的接口（依赖倒置），只关心技术细节。 |

## 二、 核心领域层（系统的业务基石）

在 DDD 中，业务逻辑不再塞进臃肿的 `Service` 里，而是下沉到拥有数据和行为的**富领域模型（充血模型）**中。`BO` 这个模糊的概念被更精确的领域对象替代。

| **对象**                              | **核心作用**                                             | **特点**                                                     | **示例**                              |
| ------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------- |
| **聚合根 (Aggregate Root)**           | **保证业务一致性的边界**，是外部访问领域模型的唯一入口。 | 包含实体和值对象。必须通过聚合根才能修改内部实体的数据，以此保证强一致性。 | `Order` (包含多个 OrderItem)          |
| **领域实体 (Domain Entity)**          | **具有唯一标识**，且生命周期内状态会发生变化的业务对象。 | 拥有丰富的业务方法（充血模型）。不包含持久化注解，完全脱离数据库。 | `User` (包含 `changePassword()` 动作) |
| **值对象 (Value Object / Domain VO)** | **描述实体的特征或属性**，没有唯一标识，一旦创建不可变。 | 往往用来代替基本数据类型，内聚了校验逻辑。                   | `Address` (包含省市区), `Money`       |
| **领域事件 (Domain Event)**           | **解耦业务流程**，表示领域内发生的一个重要既定事实。     | 命名通常是过去时。用于触发其他聚合或外部系统的响应。         | `UserRegisteredEvent`                 |
| **领域服务 (Domain Service)**         | **协调跨实体的业务逻辑**。                               | 当一个业务规则不适合放在单一实体/聚合根中时（例如转账），才放入领域服务。它是无状态的。 | `TransferService`                     |

## 三、 数据模型职责说明（严格防腐与隔离）

为了保证领域层的绝对纯净，数据在跨层时必须进行转换。此时，`Entity` 的概念被一分为二：业务核心的 `Domain Entity` 和数据库视角的 `PO`。

| **对象类别**   | **具体命名**               | **所在层级**       | **作用与特点**                                               | **示例**                               |
| -------------- | -------------------------- | ------------------ | ------------------------------------------------------------ | -------------------------------------- |
| **指令/查询**  | **Command / Query**        | 应用层 (入参)      | 封装了调用者的意图（写用 Command，读用 Query）。包含基础注解校验。 | `CreateOrderCommand`, `OrderListQuery` |
| **视图对象**   | **ViewObject (API VO)**    | 接口层 (出参)      | 面向前端展示的数据聚合，可以包含枚举翻译、脱敏逻辑。         | `OrderDetailVO`                        |
| **数据传输**   | **DTO**                    | 应用层 (出参/跨界) | 面向应用层外部的粗粒度数据载体，屏蔽内部领域模型细节。       | `OrderDTO`, `WechatUserDTO`            |
| **领域对象**   | **Entity / Aggregate**     | 领域层             | **真正的业务核心**。充血模型，包含状态和行为。无任何框架注解。 | `Order` (包含 `pay()` 等业务方法)      |
| **持久化对象** | **PO (Persistent Object)** | 基础设施层         | 数据库表结构的一一映射。与 ORM (MyBatis/JPA) 强绑定。**贫血模型，只有 getter/setter**。 | `OrderPO` (映射 `t_order` 表)          |
| **读模型**     | **Projection**             | 基础设施/应用层    | CQRS 架构下，针对复杂列表查询优化的扁平化读模型，直连 SQL，不经过领域层。 | `OrderSummaryProjection`               |

> 💡 **DDD 核心红线规范**：
>
> 1. **数据库对象（PO）绝不能进入领域层（Domain）和接口层（Controller）**。PO 是底层实现细节。
> 2. **Controller 不能直接调用领域层（Aggregate/Entity）**，必须通过应用层（Application Service）作为门面。
> 3. **应用服务（Application Service）不能包含核心业务规则**，它的职责是：加载聚合根 -> 调用聚合根的业务方法 -> 保存聚合根（俗称“搬砖层”）。

## 四、 数据流转全景视图（CQRS 读写分离视角）

DDD 极力推崇 CQRS（命令查询职责分离），因为写操作需要复杂的业务规则保证一致性，而读操作通常只需要快速返回数据。

### 1. 写操作数据流（Command - 意图改变系统状态）

1. **前端** 发起请求 -> **接口层** `Controller` 接收请求，将 HTTP 参数转化为 `Command`。
2. **应用层** `ApplicationService` 接收 `Command`，开启数据库事务。
3. `ApplicationService` 调用 `Repository` 接口，根据 ID 从数据库查出 `PO`，并转换为 **领域层**的 `Aggregate / Entity`。
4. `ApplicationService` 调用聚合根的业务方法执行核心逻辑（例如：`order.pay(amount)`）。
5. `ApplicationService` 将修改后的聚合根交还给 `Repository` 进行 `save()`。
6. **基础设施层**的 `RepositoryImpl` 将聚合根转换为 `PO`，生成 SQL 落库，并发布领域事件。

### 2. 读操作数据流（Query - 仅查询数据，无副作用）

1. **前端** 发起请求 -> **接口层** `Controller` 将参数转化为 `Query`。
2. **应用层** `QueryService` 接收请求。**（注意：这里可以绕过领域模型！）**
3. 由于查询不需要业务规则校验，直接调用 **基础设施层** 的 DAO/Mapper。
4. 执行复杂 SQL，直接将结果映射为 `Projection` 或 `DTO`。
5. 返回给 `Controller` 封装为 `ViewObject` 响应给前端。

> 💡 **核心洞察**：写流程必须经过充血的领域模型（保证业务安全）；读流程直接走 SQL 查询到 DTO（保证性能）。这就是 DDD 落地的最佳实践。

## 五、 推荐工程目录结构 (标准包驱动)

根据 DDD 的四层架构，工程通常会按 Maven Module 进行拆分，或者在单体项目中按顶级包进行分层：

```
├── my-project-interfaces        // 1. 用户接口层 (防腐、路由)
│   ├── controller
│   ├── mq/consumer
│   └── assembler                // 负责 DTO <-> VO 的转换
├── my-project-application       // 2. 应用层 (编排、事务、CQRS)
│   ├── command                  // 写操作入参
│   ├── query                    // 读操作入参
│   ├── dto                      // 应用层输出载体
│   ├── service
│   │   ├── OrderAppService.java // 处理 Command
│   │   └── OrderQueryService.java// 处理 Query (可选直连Dao)
├── my-project-domain            // 3. 核心领域层 (纯业务、无依赖)
│   ├── model                    // 聚合根、实体、值对象
│   │   ├── Order.java           // 充血模型，包含核心业务逻辑
│   │   └── Address.java         // 领域值对象 (Domain VO)
│   ├── event                    // 领域事件定义
│   ├── service                  // 领域服务 (处理跨实体的复杂逻辑)
│   └── repository               // 仓储接口定义 (防腐层接口，依赖倒置)
│       └── OrderRepository.java // Interface
└── my-project-infrastructure    // 4. 基础设施层 (底层实现)
    ├── persistence              // 数据库持久化
    │   ├── po                   // 贫血持久化对象 (OrderPO)
    │   ├── mapper               // MyBatis Mapper / JPA DAO
    │   └── repository_impl      // 实现领域层的仓储接口
    ├── rpc                      // 第三方 API 调用实现
    └── config                   // 各种技术框架配置
```

## 六、 一句话总纲总结（DDD 版）

> - **Interfaces (接口层)** 负责把守外部边界，完成协议解析与视图组装。
> - **Application (应用层)** 负责用例编排、事务管理与权限控制，是系统的指挥官。
> - **Domain (领域层)** 负责纯粹的业务状态转移与规则约束，是系统的核心业务大脑（充血模型）。
> - **Infrastructure (基础设施层)** 负责提供底层能力（DB/MQ/RPC），并实现领域层定义的仓储接口。
> - **Command / Query** 分离了写意图与读诉求，杜绝了参数的混用。
> - **Entity / Aggregate** 告别贫血，真正承担起业务计算的职责。
> - **PO** 退回到它应有的位置：只做纯粹的数据库映射。
