# 主流架构分层对比

> 目的：把几种常见的后端/软件架构分层记下来，方便选型时快速回忆。
> 适用场景与推荐指数来自经验性总结，具体项目需结合团队与业务权衡。

## 一、总览表

| 架构                                     | 适用场景               | 推荐指数     |
| ---------------------------------------- | ---------------------- | ------------ |
| MVC                                      | 小项目 / 简单 CRUD 页面 | ⭐            |
| 三层（Controller-Service-Repository）    | 标准 CRUD 业务         | ⭐⭐           |
| DDD（领域驱动设计）                       | 业务复杂、规则多变     | ⭐⭐⭐⭐         |
| FDD（Feature First / 按功能组织）        | 大多数中大型项目       | ⭐⭐⭐⭐⭐        |
| Clean Architecture（整洁架构）           | 长期维护、技术栈易变   | ⭐⭐⭐⭐⭐        |
| Hexagonal（Ports & Adapters / 六边形）   | 多外部依赖 / 多 Provider | ⭐⭐⭐⭐⭐        |
| AI Capability Architecture（能力中心）   | AI Agent / RAG 类系统  | ⭐⭐⭐⭐⭐         |

> 注：推荐指数越高不代表越"高级"，而是**越贴合现代项目的演进趋势**（易维护、易测试、易替换外部依赖）。小项目上 DDD 反而过度设计。

## 二、MVC（Model-View-Controller）

最经典的分层，适合简单页面/小项目。

- **Model**：数据模型与简单业务逻辑
- **View**：展示层（页面/模板）
- **Controller**：接收请求、调度 Model、选 View

特点：层与层容易耦合，业务逻辑容易堆积在 Controller 或 Model 里；项目变大后难维护。

## 三、三层架构（Controller-Service-Repository）

在 MVC 基础上把"业务逻辑"与"数据访问"显式拆开，是大多数 CRUD 项目的默认选择。

| 层级              | 职责                                         |
| ----------------- | -------------------------------------------- |
| Controller        | 接收请求、参数校验、返回响应（不含业务规则） |
| Service           | 核心业务逻辑、事务控制                       |
| Repository / DAO  | 数据持久化与查询（屏蔽数据库细节）           |

特点：简单清晰、上手快；缺点是 Service 容易变成"上帝类"，业务复杂后分层边界模糊。

## 四、DDD（领域驱动设计）

把业务规则下沉到"充血模型"，以领域为核心。详见 [DDD 分层与数据模型规范](./DDD分层与数据模型规范.md)。

四层核心：
- **用户接口层（Interfaces）**：协议转换、路由
- **应用层（Application）**：用例编排、事务、轻量
- **领域层（Domain）**：业务大脑（聚合根、实体、值对象、领域服务）
- **基础设施层（Infrastructure）**：持久化、外部调用（依赖倒置实现领域层接口）

适用：业务复杂、规则多变、需要长期演进的系统。成本高、学习曲线陡。

## 五、FDD（Feature First / 按功能组织）

不按"技术角色"分层，而按"业务功能"组织代码。常与三层/DDD 结合使用。

目录示例：

```
src/
├── features/
│   ├── order/
│   │   ├── controller.py
│   │   ├── service.py
│   │   ├── repository.py
│   │   └── model.py
│   └── user/
│       ├── controller.py
│       └── ...
└── shared/        # 跨功能的公共能力
```

特点：功能内聚、改动影响面小、易拆分微服务；适合大多数中大型项目（尤其 Python 生态常见）。

## 六、Clean Architecture（整洁架构）

Robert C. Martin 提出，核心是**依赖规则：外层依赖内层，内层不依赖任何外层框架**。

同心圆（由内到外）：
1. **Entities（企业业务规则）**
2. **Use Cases（应用业务规则）**
3. **Interface Adapters（接口适配：Controller/Presenter/Repository 接口）**
4. **Frameworks & Drivers（最外层：DB、Web 框架、UI）**

特点：业务核心与技术框架彻底解耦，极易测试、易替换框架；代价是样板代码多、目录偏重。

## 七、Hexagonal（Ports & Adapters / 六边形架构）

与 Clean Architecture 思想高度一致，强调"应用核心 + 端口 + 适配器"。

- **Domain / Application Core**：业务核心
- **Ports（端口）**：核心对外暴露的接口（入站/出站）
- **Adapters（适配器）**：把具体技术（REST、DB、MQ、第三方 API）接到端口上

特点：非常适合"多 Provider / 多外部依赖"场景（如同时接多家支付、多家 LLM）。可替换适配器而不动核心逻辑。

## 八、AI Capability Architecture（能力中心架构）

面向 AI Agent / RAG 类系统的组织方式，把"AI 能力"当作一等公民沉淀。

核心思想：
- **能力中心（Capability Hub）**：把检索、生成、工具调用、记忆等封装成可复用能力
- **编排层（Orchestration）**：Agent 流程编排、Prompt/RAG 管线
- **适配层**：对接不同模型 Provider、向量库、工具

适用：AI Agent、RAG、多模型切换场景。是六边形/整洁架构在 AI 领域的实例化。

## 九、选型口诀

- 小项目 / 页面多 → **MVC**
- 标准 CRUD → **三层**
- 业务规则复杂 → **DDD**
- 想让代码好找、好拆 → **FDD（按功能）**
- 怕框架绑死、要长期维护 → **Clean / Hexagonal**
- 多外部依赖 / 多 Provider → **Hexagonal**
- AI Agent / RAG → **能力中心**
