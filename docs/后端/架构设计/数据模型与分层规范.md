# 后端分层架构与数据模型规范

## 一、 核心执行层职责说明

在后端架构中，Controller、Service 和 Repository 是处理业务逻辑和数据流转的核心“器官”，它们各司其职，有着严格的边界。

| **组件**       | **所在层级**       | **核心作用**                             | **处理的数据模型**                          | **核心原则与特点**                                           |
| -------------- | ------------------ | ---------------------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| **Controller** | 接口层 (Web 层)    | **交通警察**：负责路由转发与输入输出控制 | 接收 `Form`，返回 `DTO` 或 `VO`             | 处理 HTTP 请求、参数基础校验、身份解析。**绝对不包含业务逻辑**，不关心底层数据库。 |
| **Service**    | 业务层 (Domain 层) | **业务大脑**：执行核心业务逻辑与规则     | 处理 `BO`，调用 `Repository` 或其他 Service | 负责事务控制、业务规则校验、状态流转。**不关心外部协议**（无视 HTTP/JSON），是系统最核心的层级。 |
| **Repository** | 持久层 (Data 层)   | **数据搬运工**：与数据库进行交互         | 操作 `Entity`，查询返回 `Projection`        | 只负责数据的 CRUD 和 SQL 组装。**不包含业务逻辑**，只关心“怎么查/存”，不关心“为什么查/存”。 |

## 二、 核心领域层（业务的基石）

在融入了领域驱动思想（DDD）的架构中，`Model` 是剥离了技术细节后，最纯粹的业务表达。

| **对象**  | **所在层级** | **核心作用**               | **特点**                                                     | **示例**                                    |
| --------- | ------------ | -------------------------- | ------------------------------------------------------------ | ------------------------------------------- |
| **Model** | 核心领域层   | **业务概念与规则的具象化** | 纯净对象，无框架依赖（无 Spring/JPA 注解）。包含核心枚举、值对象、核心业务实体。 | `UserAuthType` (枚举) `UserStatus` (状态机) |

> 💡 **Model 层的核心价值**：
>
> 核心业务逻辑只依赖纯净的 Model，不依赖底层的数据库结构（Entity），实现了真正的**“业务与技术解耦”**。

## 三、 数据模型职责说明

数据模型是系统中流淌的“血液”，为了保证各层之间的解耦和安全，针对不同的场景需要使用特定的数据载体。

| **对象**       | **层级**       | **作用**         | **特点**                     | **示例**                   |
| -------------- | -------------- | ---------------- | ---------------------------- | -------------------------- |
| **Form**       | 接口层（输入） | 接收前端请求参数 | 可校验、可缺省、与前端强绑定 | `CreateUserForm`           |
| **Entity**     | 持久层         | 数据库表映射     | 全字段、JPA/ORM 注解强绑定   | `User`                     |
| **Projection** | Repository 层  | 精简查询结果     | 只读、字段子集、SQL 强绑定   | `UserPermissionProjection` |
| **BO**         | 业务层         | 业务语义封装     | 聚合、规则、状态机载体       | `UserPermissionBO`         |
| **DTO**        | 接口层（输出） | 接口返回         | 控制暴露字段、序列化友好     | `UserPermissionDTO`        |
| **VO**         | 展示层         | 前端展示         | 格式化、组合、可计算         | `UserPermissionVO`         |

> 💡 **核心规范**：
>
> - `Entity` 绝不能进入 `Controller`。
> - `Projection` 绝不能进入 `save` 或 `update` 操作。
> - 纯正的业务逻辑**只**存在于 `BO`（或 `Service` 处理 `BO` 的过程中）。
> - 如果是 BFF 或前后端分离项目，`VO` 可以只存在于前端，后端直接返回 `DTO` 即可。

## 四、 数据流转全景视图

### 1. 正向数据流（查询 / 读）

`Entity` → `Repository` → `Projection` → `BO` → `DTO` → `VO` → **前端**

### 2. 反向数据流（提交 / 写）

**前端** → `VO` / `Form` → `Controller` → `DTO` / `BO` → `Service` → `Entity` → `Repository` → **数据库**

### 3. 数据流转说明（步骤拆解）

1. **Form → Controller**：接收不可信的外部输入，执行基础校验。
2. **Controller → Service**：剥离 HTTP 属性，转化为 `BO`（或直接使用基本类型/Model）进入业务大脑。
3. **Service → Repository**：结合 `Model` 的业务规则，指挥 Repository 获取 `Entity` 或 `Projection`。
4. **Repository → Service**：拿到底层数据，映射回业务对象继续处理。
5. **Service → Controller**：业务执行完毕，将结果安全打包成 `DTO` 交还。
6. **Controller → 前端 (VO)**：输出 `DTO`，前端根据需要转为 `VO` 进行页面渲染。

## 五、 易混淆概念辨析

### 1. Form vs DTO （最易踩坑）

| **维度**         | **Form**                       | **DTO**                     |
| ---------------- | ------------------------------ | --------------------------- |
| **方向**         | 输入 (Input)                   | 输出 (Output)               |
| **面向对象**     | 前端请求                       | 前端响应                    |
| **是否校验**     | ✅（必须严格校验）              | ❌（通常不需校验）           |
| **是否可缺字段** | ✅（如 PATCH 更新只传部分字段） | ❌（尽量保证结构完整）       |
| **含业务语义**   | ❌                              | ❌                           |
| **是否可复用**   | ❌（紧贴具体接口，不建议复用）  | ✅（可在多个查询接口间复用） |

> 🚨 **红线警告**：
>
> **绝对不要用 DTO 去接收请求！**
>
> **绝对不要用 Form 去做接口返回！**

### 2. Model vs Entity

| **维度**     | **Model (领域模型)**                 | **Entity (持久化实体)**            |
| ------------ | ------------------------------------ | ---------------------------------- |
| **关注点**   | **“是什么”**（纯粹的业务概念与规则） | **“怎么存”**（数据库表结构的映射） |
| **技术依赖** | 无（纯 Java/面向对象概念）           | 强（贴满 `@Table`, `@Id` 等注解）  |
| **生命周期** | 贯穿整个业务核心生命周期             | 仅在与数据库交互时作为映射介质     |

### 3. Projection vs BO

| **维度**        | **Projection**           | **BO**                              |
| --------------- | ------------------------ | ----------------------------------- |
| **所在层**      | Repository               | Service                             |
| **角色扮演**    | 数据库查询结果的精简切面 | 承载业务规则的充血/贫血模型         |
| **是否可变**    | 否（绝对只读）           | 视设计而定（通常在 Service 中演进） |
| **是否含逻辑**  | ❌                        | ✅                                   |
| **与 SQL 绑定** | 强绑定                   | 弱绑定（完全解耦数据库）            |
| **生命周期**    | 短（离开持久层即应转换） | 长（贯穿整个业务处理流程）          |

#### 📌 Projection 的典型使用场景：

- 原生 SQL 查询（`nativeQuery = true`）。
- 多表 JOIN 后的聚合结果。
- 只需要查询极少数表字段（`SELECT` 字段远少于 `Entity` 字段），为了极致的性能优化。
- 临时拼装的数据视图。

## 六、 推荐工程目录结构

为了配合上述规范，推荐在模块内采用以下包结构：

```
permission
├─ controller
│   ├─ PermissionController.java
│   └─ form
│       ├─ AssignPermissionForm.java
│       └─ RevokePermissionForm.java
├─ service
│   └─ PermissionService.java
├─ entity        （表结构）
│   └─ Permission.java
├─ model          领域模型（核心规则与业务基石）
│   └─ PermissionCode.java
├─ repository    （数据操作与查询）
│   └─ PermissionRepository.java
├─ projection    （查询结果切面）
│   └─ UserPermissionProjection.java
├─ bo            （业务领域模型）
│   └─ UserPermissionBO.java
├─ dto           （接口输出模型）
│   └─ UserPermissionDTO.java
└─ vo            （可选：展示模型）
    └─ UserPermissionVO.java
```

## 七、 一句话总纲总结

> - **Controller** 负责拆解输入，**Service** 负责核心大脑，**Repository** 负责搬运数据。
> - **Form** 负责“接收世界不可信的输入”。
> - **Model** 负责“定义系统最纯粹的业务基石”。
> - **BO** 负责“承载系统真实的业务规则”。
> - **DTO** 负责“对外提供安全的输出”。
> - **Projection** 负责“还原 SQL 世界的真实形态”。
