## 一、什么是 K3s

K3s 是 [CNCF 毕业项目](https://www.cncf.io/projects/k3s/)，一个**轻量级的 Kubernetes 发行版**，由 Rancher Labs（现 SUSE）创建与维护。

- 整个集群由**单个二进制文件**（约 50~100MB）提供，去除了 K8s 中大量非必需组件（如旧的、Alpha 功能、in-tree 云厂商驱动等）。
- 名字来源：`k8s` 里 `k` 和 `s` 之间有 5 个字母，所以简写为 `k3s`（3 = 5 个被去掉的字母的谐音玩笑）。
- 适合**边缘计算、IoT、ARM 设备、CI 流水线、本地开发、资源受限环境**。

可以看作是「把 K8s 减肥到极致」的版本：**API、概念、工具链（kubectl）100% 兼容标准 Kubernetes**，只是更轻、更快、更易安装。

---

## 二、与标准 K8s 的区别

| 维度 | 标准 Kubernetes | K3s |
| --- | --- | --- |
| **部署形态** | 多组件、多二进制、配置复杂 | 单二进制，一键安装 |
| **资源占用** | 高（建议控制节点 2C4G 起） | 低（512M 内存即可跑） |
| **容器运行时** | 需自行安装 containerd/CRI-O | 内置 containerd |
| **网络** | 需自选 CNI | 内置 Flannel（可替换） |
| **存储** | 需自选 | 内置 Local-Path 本地存储 Provisioner |
| **Ingress/负载均衡** | 需自选 | 内置 Traefik、Klipper-LB |
| **DNS** | 需自选 | 内置 CoreDNS |
| **数据存储** | 必须 etcd | 默认 SQLite，可选 etcd / 外部 DB |

> 结论：K3s 把「Kubernetes 周边配套」打包好了，开箱即用；代价是定制灵活度不如原生 K8s，但绝大多数中小场景完全够用。

## 三、核心架构

K3s 节点分两类角色：

### Server 节点（控制平面）

运行 K8s 控制平面组件：`kube-apiserver`、`kube-scheduler`、`kube-controller-manager`，并内置数据存储。

- 负责集群的「大脑」：调度、状态、鉴权。
- 生产环境推荐 **3 个 Server**（奇数，满足 etcd 多数派）。

### Agent 节点（Worker / 工作节点）

- 只运行 `kubelet` + `kube-proxy` + 容器运行时，**负责运行业务 Pod**。
- 可以横向扩展，加多少台都行。

```text
        ┌─────────────────────────────────────────┐
        │            K3s Server (控制平面)          │
        │  kube-apiserver / scheduler / controller  │
        │  + 数据存储 (SQLite / etcd / 外部DB)       │
        └───────────────┬─────────────────────────┘
                        │  6443 (Kubernetes API)
        ┌───────────────┼─────────────────────────┐
        ▼               ▼                          ▼
   K3s Agent       K3s Agent                  K3s Agent
   (业务 Pod)      (业务 Pod)                 (业务 Pod)
```

### 数据存储（Datastore）

K3s 的数据存储决定了高可用能力：

| 存储方式 | 适用场景 | 高可用 |
| --- | --- | --- |
| **SQLite**（默认） | 单节点开发/测试 | 否（单点） |
| **Embedded etcd** | 生产 HA（推荐） | 是，3 Server 组成 etcd 多数派 |
| **外部数据库** | 已有 MySQL/PostgreSQL/etcd 基础设施 | 是，依赖外部 DB 高可用 |

> **etcd 是什么？** etcd 是整个集群的数据库，存储了所有节点、Pod、配置的状态。
> 它不是 PostgreSQL 这类关系型数据库——etcd 是一个**键值（KV）存储**，专为存储集群状态和配置设计，强调一致性与高可用（Raft 协议）。K3s 高可用模式下，3 个 Server 各自运行 etcd 副本，通过 Raft 保持数据一致。

## 四、关键概念

### 节点角色与「打 Taint（污点）」

`打 taint` 的意思是：**给节点打上污点（Taint），阻止普通业务 Pod 调度到这个节点。**

Kubernetes 中，**Taint（污点）** 和 **Toleration（容忍）** 是一对机制：

- **Taint**：节点说「普通 Pod 不要来我这里」。
- **Toleration**：Pod 说「虽然你有污点，但我允许运行在这里」。

典型用法：

- **只有 3 台 Server（无独立 Agent）**：推荐**不加** taint，让 Server 也能跑业务 Pod（资源充分利用）。
- **3 台 Server + 多台 Agent**：推荐给 Server **加 taint**，把控制平面和业务 Pod 隔离，避免业务把控制节点资源吃满导致集群不稳定。

### 业务 Pod

真正运行业务逻辑的容器（如你的微服务、数据库 Deployment 等）。在「Server + Agent」架构中，业务 Pod 通常只调度到 Agent 节点（被 taint 隔离的 Server 不会接收它们，除非 Pod 显式声明 Toleration）。

## 五、安装

### 单节点快速体验

官方默认方式（需要能访问 `get.k3s.io`）：

```bash
curl -sfL https://get.k3s.io | sh -
```

安装完成后，kubeconfig 已自动写到 `/etc/rancher/k3s/k3s.yaml`，可直接用：

```bash
kubectl get nodes
# NAME      STATUS   ROLES           AGE   VERSION
# k3s-01    Ready    control-plane   1m    v1.xx
```

**大陆环境（推荐国内镜像源）**：直接拉 `get.k3s.io` 通常很慢，且容易因代理导致本地 IP 被劫持、TLS 证书报错。改用 Rancher 国内镜像源，通过 `INSTALL_K3S_MIRROR=cn` 让安装脚本从 `rancher-mirror.rancher.cn` 拉取：

```bash
curl -sfL https://rancher-mirror.rancher.cn/k3s/k3s-install.sh | INSTALL_K3S_MIRROR=cn sh -
```

> 国内源会直接从国内节点拉取安装脚本和 K3s 二进制包，速度极快，且避开代理引发的 IP 劫持与 TLS 报错。

### 高可用（HA）部署

生产环境建议 **3 台 Server + 若干 Agent**，使用 Embedded etcd 实现控制平面高可用。

完整步骤（服务器规划、关闭 swap/ufw、逐台安装、加入 token、本地 kubeconfig）见 👉 [Ubuntu 高可用部署 (HA)](./Ubuntu高可用部署.md)

### 卸载

```bash
# 卸载 Agent
/usr/local/bin/k3s-agent-uninstall.sh

# 卸载 Server
/usr/local/bin/k3s-uninstall.sh
```

## 六、高可用访问入口（VIP）

HA 集群有 3 个 Server，但外部访问 API Server（6443）需要一个**统一的固定入口 IP**，即 VIP（虚拟 IP）。常用方案：

- **kube-vip**（K3s 官方推荐）：云原生设计，兼顾 Control Plane 高可用与 Service 负载均衡，以 Static Pod 运行在集群内，极简。
- **Keepalived + HAProxy**：传统成熟组合，LB 跑在集群外，隔离性高。

详细选型对比与适用场景见 👉 [VIP 方案选型 (Kube-vip vs Keepalived+HAProxy)](./VIP方案选型.md)

## 八、Auto-Deploy 机制（manifest 自动部署）

K3s 原生集成了对静态 YAML、Kustomize、Helm 的自动化部署支持，无需手动逐个 `kubectl apply`：

- **内置 Auto-Deploy 目录**：K3s 默认监听 `/var/lib/rancher/k3s/server/manifests/`，把 YAML 文件或含 `kustomization.yaml` 的目录丢进去，K3s 会自动将其 `kubectl apply` 到集群。
- **内置 Helm Controller**：K3s 默认集成了 Helm 控制器，可编写自定义 `HelmChart` CRD 放进 manifests 目录，K3s 会自动下载 Chart 并完成安装。

> 这正体现了 K3s 与配置管理工具的关系：K3s 是「运行平台」，而 YAML / Kustomize / Helm 是「在平台上装应用的工具」，K3s 把后者的执行自动化了。

## 九、管理界面与工具链

### 是否有必要装管理界面？

前期**没必要**。K3s 自带 `kubectl`，命令行很多时候更快；维护一套 Web 管理界面本身也要占用额外资源和精力。等人多、集群变复杂再考虑。

折中方案：先用**本地客户端**看集群状态，避免常驻服务：

- **Lens / OpenLens**：强大的本地桌面 K8s 客户端，可视化查看 Pod、日志、资源。
- **k9s**：终端里的 K8s 仪表盘，键盘操作极快。

需要 Web 可视化时，优先级建议：

1. **Headlamp**（轻量 Web UI）先做基础可视化；
2. 如果发展为**多集群、多团队协作**，再升级到 **Rancher**。

### 前期推荐组合

```text
Ubuntu
    │
K3s
    │
kubectl          # 命令行管理
    │
k9s              # 终端仪表盘（可选）
    │
Grafana          # 监控可视化
Prometheus       # 指标采集
Loki             # 日志聚合
```

> 上面这一套覆盖了「集群管理 + 资源监控 + 日志」三件大事，且全部云原生、资源占用可控，适合从零起步。
