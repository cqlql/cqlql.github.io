这里为你梳理 Kubernetes (K8s/K3s) 中最核心的几类**工作负载控制器（Workload Resources）**。它们各自扮演着不同的角色，用来满足从普通 Web 服务到数据库、后台定时任务等各种不同的应用场景。

## 1. Pod（基本运行单元）

- **核心定义**：Kubernetes 中**最小的部署与调度单元**。
- **工作机制**：Pod 就像是容器的"外壳"或"胶囊"，一个 Pod 内可以包含一个或多个共享网络（IP）和存储卷（Volume）的容器（如主应用容器 + Sidecar 辅助容器）。
- **使用场景**：所有高级控制器（Deployment、DaemonSet 等）最终都是通过创建和管理 Pod 来运行实际业务的。
- **注意**：通常**不建议直接创建孤立的 Pod**。因为单副本 Pod 一旦崩溃或所在节点宕机，没有任何机制会自动恢复它。

## 2. Deployment（无状态应用控制器）

- **核心定义**：最常用的无状态应用（Stateless Application）管理工具。
- **工作机制**：
  - **关注副本数量**：你可以声明"需要 3 个副本"，Deployment 会确保集群中始终有 3 个相同的 Pod 在运行。
  - **位置不敏感**：Pod 被随机调度到集群中的各个可用节点上，并不限制必须落在特定节点。
  - **版本管理**：支持平滑的**滚动更新（Rolling Update）**和**一键回滚**。
- **典型场景**：Web 服务、微服务 API（如 Spring Boot、Go、Node.js）、前端 Nginx 等。

## 3. DaemonSet（节点守护进程控制器）

- **核心定义**：确保在集群的**每一个（或指定的）节点上，且仅运行一个 Pod 副本**。
- **工作机制**：
  - 自动跟随集群节点的扩缩容。新增节点时，DaemonSet 会自动在该节点拉起 Pod；节点被移除时，Pod 也会随之销毁。
- **典型场景**：
  - **日志收集**：如 Fluentd、Filebeat（收集每台机器上的日志）。
  - **节点监控**：如 Prometheus Node Exporter（监控每台机器的 CPU/内存）。
  - **网络/基础设施**：如 Flannel、Calico、kube-vip 等网络插件。

## 4. StatefulSet（有状态应用控制器）

- **核心定义**：专门用于管理有状态应用（Stateful Applications）的控制器。
- **工作机制**：
  - **固定身份**：每个 Pod 都有唯一且固定的网络标识/主机名（如 `web-0`, `web-1`），即使 Pod 漂移到其他节点，名称和网络标识也不会改变。
  - **稳定存储**：每个 Pod 可以绑定专属的持久化存储（PVC/PV），Pod 重建后依然能重新挂载原来的数据卷。
  - **有序增删**：Pod 的创建、更新和销毁是严格按照顺序进行（如 `0 -> 1 -> 2`）。
- **典型场景**：数据库（MySQL 主从、PostgreSQL）、分布式中间件与存储（Redis 集群、Kafka、ZooKeeper、Elasticsearch）。

## 5. Job & CronJob（任务类控制器）

这两个控制器用于处理**非持续运行**的任务，任务执行完毕即退出。

### Job（一次性任务）

- **工作机制**：启动一个或多个 Pod 来执行特定任务。任务成功完成后（容器退出码为 0），Pod 状态变为 `Completed` 并停止运行，不会无限重启。
- **典型场景**：数据库 Migration 脚本、一次性数据计算/导出、源码打包编译。

### CronJob（定时任务）

- **工作机制**：类似于 Linux 中的 `crontab`，基于时间表（Cron 表达式，如 `0 2 * * *`）**周期性地触发并创建 Job**。
- **典型场景**：每日凌晨数据库自动备份、定时清理日志/临时文件、定时发送对账邮件等。

## 总结归纳

- **Pod** 是容器运行的**基本单元**。
- **Deployment** 适合**普通的 Web/微服务**（随意拉起多个副本，不在乎落在哪个节点）。
- **DaemonSet** 适合**节点守护服务**（每台机器必须留一个，比如网络/日志/监控）。
- **StatefulSet** 适合**数据库/中间件**（需要固定身份和固定存储）。
- **Job / CronJob** 适合**一次性或定时任务**。
