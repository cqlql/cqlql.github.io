# PC Web 微信扫码登录

基于**微信开放平台「网站应用」网页授权（qrconnect）**实现 PC 浏览器扫码登录。用户手机扫码确认后，微信通过 OAuth2 授权码（`code`）回调到后端，后端落地登录态并跳回前端兑换 accessToken。

> 项目背景：PassUp 面试助手（Java Spring Boot 后端 + React 前端）。相关代码位于后端 `modules/auth/`、`infrastructure/integration/wechat/` 与前端 `features/auth/pages/`。

------

## 一、整体流程

```
① PC 端点击「微信扫码登录」 → 进入 /login/wechat
   ↓
② 前端调 GET /api/web/auth/wechat/scan/url 拿 { state, url }
   ↓
③ 后端生成随机 state 写 Redis（state → "PENDING"，TTL 5 分钟），拼 qrconnect 授权 URL
   ↓
④ 前端用 <iframe> 内嵌微信官方 qrconnect 授权页（官方二维码）
   ↓
⑤ 用户手机扫码、点确认 → 微信顶层跳转到回调地址（redirect_uri）
   GET /api/web/auth/wechat/callback?code=xxx&state=xxx
   ↓
⑥ 后端校验 state → 用 code 换 openid/unionid → 创建/复用用户
   → 生成 Web 登录态（写 refreshToken HttpOnly Cookie）
   ↓
⑦ 后端返回一段 HTML，用 JS 将浏览器跳回前端回调页 /login/wechat/callback
   ↓
⑧ 前端回调页用 Cookie 调 POST /api/web/auth/refresh 兑换 accessToken
   → 存 localStorage → 跳转首页
```

关键点：**扫码确认由微信顶层跳转驱动，前端无需轮询扫码状态**。

------

## 二、后端实现

### 1. 获取扫码 URL

`WechatScanLoginController#getScanUrl` → `WechatScanLoginService#buildAuthorizationUrl`：

```java
public ScanUrlResult buildAuthorizationUrl() {
    String state = SecurityUtil.generateOpaqueToken(); // 32 字节随机不透明 token

    // state 写 Redis，状态 PENDING，TTL 5 分钟
    redisTemplate.opsForValue().set(stateKey(state), "PENDING",
            Duration.ofSeconds(openPlatformProperties.getStateTtlSeconds()));

    String url = "https://open.weixin.qq.com/connect/qrconnect"
            + "?appid=" + openPlatformProperties.getAppId()
            + "&redirect_uri=" + URLEncoder.encode(openPlatformProperties.getRedirectUri(), UTF_8)
            + "&response_type=code"
            + "&scope=snsapi_login"   // 网页扫码登录专用 scope
            + "&state=" + state
            + "#wechat_redirect";

    return new ScanUrlResult(state, url);
}
```

要点：

- `state` 用于**防 CSRF**：授权 URL 与回调一一对应，回调时校验 state 在 Redis 中存在才算合法。
- `scope=snsapi_login`（开放平台网页扫码专用，区别于公众号的 `snsapi_base`/`snsapi_userinfo`）。
- Redis Key 前缀：`auth:wechat:scan:state:{state}`，值 `PENDING`。

### 2. 处理微信回调

`WechatScanLoginController#callback` → `WechatScanLoginService#handleCallback`：

```java
@Transactional
public String handleCallback(String code, String state, HttpServletRequest request,
        HttpServletResponse response) {
    // 1. 校验 state：不存在即二维码过期或被篡改
    Object existing = redisTemplate.opsForValue().get(stateKey(state));
    if (existing == null) {
        return buildCallbackHtml("二维码已过期，请刷新页面重试");
    }

    // 2. code 换 access_token + openid + unionid
    WechatOauthTokenDTO tokenDTO = wechatAuthService.getOauthAccessToken(code);
    String openid = tokenDTO.getOpenid();
    String unionid = tokenDTO.getUnionid();

    // 3. 创建或复用用户
    User user = getOrCreateUserByOpenPlatformId(openid, unionid);

    // 4. 落地 Web 登录态（写 refreshToken HttpOnly Cookie）
    webAuthHelper.createWebTokens(request, response, user.getId());

    // 5. 消费 state，删除避免残留
    redisTemplate.delete(stateKey);

    // 6. 返回 JS 跳转 HTML，跳回前端回调页
    return buildRedirectHtml();
}
```

回调接口返回**一段 HTML**（而非 JSON），因为它由微信服务器**顶层跳转**触发，浏览器需要展示一个「登录成功，正在跳转」页面并用 `window.location.replace()` 跳回前端。

### 3. code 换 token

`WechatAuthService#getOauthAccessToken`，调用开放平台接口：

```
GET https://api.weixin.qq.com/sns/oauth2/access_token
    ?appid={appId}&secret={appSecret}&code={code}&grant_type=authorization_code
```

返回 `WechatOauthTokenDTO`：`access_token`、`openid`、`unionid`（开放平台账号与公众号绑定后才返回 unionid）、`errcode`/`errmsg`。

### 4. 用户创建 / 复用（核心业务）

`getOrCreateUserByOpenPlatformId` 按三级优先级查找：

```java
// 1. 按 PC 扫码 openid 查（PC 端老用户）
findByAuthTypeAndIdentifier(WECHAT_OPEN_PLATFORM, openid) → 命中即返回

// 2. 按 unionid 跨登录类型查（打通小程序与 PC）
findUserByUnionIdOnly(unionid) → 命中则绑定 openid 后复用该用户

// 3. 完全新用户 → 新建 User + 绑定 openid
```

`unionid` 机制是**打通 PC 扫码与小程序账号**的关键：同一微信用户在小程序和开放平台拥有不同 `openid`，但共享同一 `unionid`。因此用户先用小程序注册，再用 PC 扫码时，能通过 unionid 识别为同一人，复用账号。

`UserAuth` 实体以 `authType + identifier` 定位认证记录，`UserAuthType` 枚举含 `WECHAT_OPEN_PLATFORM("wechat_open_platform")` 与 `WECHAT_MINIAPP("wechat_miniapp")` 两种微信登录类型。

### 5. 落地登录态

`WebAuthHelper#createWebTokens`：构建 `ClientType.WEB` 会话 → 生成 accessToken + refreshToken → 将 refreshToken 写入 **HttpOnly + Secure + Path 限定** Cookie：

```java
cookie.setHttpOnly(true);
cookie.setSecure(cookieSecure);
cookie.setPath("/api/web/auth/refresh"); // 仅刷新接口发送，防 CSRF
cookie.setMaxAge(7 * 24 * 60 * 60);      // 7 天
```

accessToken 不写入 Cookie，由前端从 refresh 接口的响应体拿取后自行管理。

## 三、前端实现

### 1. 登录入口

`LoginPage.tsx` 中「微信扫码登录」按钮跳转 `/login/wechat`：

```tsx
<Button icon={<WechatOutlined />} onClick={() => navigate('/login/wechat')}>
  微信扫码登录
</Button>
```

### 2. 扫码页

`WechatScanLoginPage.tsx` 挂载时调 `getWechatScanUrl()` 拿 URL，用 `<iframe>` 直接内嵌微信官方 qrconnect 授权页：

```tsx
const result = await getWechatScanUrl(); // GET /api/web/auth/wechat/scan/url
setQrCodeUrl(result.url);

<iframe src={qrCodeUrl} className="block w-[300px] h-[400px]" frameBorder="0" />
```

**为什么用 iframe 而不是自己生成二维码**：微信官方推荐直接内嵌 qrconnect 授权页，由微信渲染官方二维码；若用第三方二维码服务二次编码该 URL，扫出来的码只会跳转到微信二维码页，无法完成登录。

页面提供「刷新二维码」「返回密码登录」，无需轮询——确认后由微信顶层跳转驱动后续流程。

### 3. 回调页兑换 token

`WechatScanCallbackPage.tsx` 被后端 HTML 跳转进入后，用 Cookie 调 refresh 接口兑换 accessToken：

```tsx
useEffect(() => {
  if (exchangedRef.current) return;
  exchangedRef.current = true; // 防止 React StrictMode 下重复兑换
  (async () => {
    const accessToken = await webRefreshToken(); // POST /api/web/auth/refresh（withCredentials）
    setToken(accessToken);                        // 存 localStorage
    navigate('/', { replace: true });             // replace 避免回退再次进入回调页
  })();
}, [navigate]);
```

`webRefreshToken` 使用裸 axios + `withCredentials: true` 携带 Cookie，绕过 `http` 拦截器的自动刷新与错误弹窗逻辑。

### 4. 路由

```tsx
{ path: '/login', element: <LoginPage /> },
{ path: '/login/wechat', element: <WechatScanLoginPage /> },
{ path: '/login/wechat/callback', element: <WechatScanCallbackPage /> },
```

三条路由均挂在 `GuestLayout`（未登录布局）下。回调页路径 `/login/wechat/callback` 与后端 `WechatScanLoginService#buildRedirectHtml` 中拼的跳转地址一致。

## 四、配置项

`application.yml` 中 `wechat.open-platform`：

```yaml
wechat:
  open-platform:
    app-id: your-open-app-id          # 开放平台「网站应用」AppID
    app-secret: your-open-app-secret  # 对应 AppSecret
    redirect-uri: https://<your-domain>/api/web/auth/wechat/callback  # 回调地址（需在开放平台配置为授权回调域）
    frontend-base-url: https://<your-frontend-domain>  # 扫码成功后跳回的前端站点
    state-ttl-seconds: 300            # state 有效期（秒）
```

对应 `WechatOpenPlatformProperties`，注意：

- `redirect-uri` 必须与开放平台「网站应用」里配置的**授权回调域**一致。
- `frontend-base-url` 用于回调成功后 `buildRedirectHtml` 拼跳转地址（`{frontendBaseUrl}/login/wechat/callback`）。

## 五、关键设计点

1. **state 防 CSRF + 防过期**：随机 state 写 Redis（TTL 5 分钟），回调时校验存在才继续，成功后删除防重放。
2. **顶层跳转驱动，前端零轮询**：扫码确认由微信跳转后端回调，后端返回跳转 HTML，无需前端定时轮询扫码状态。
3. **unionid 打通多端账号**：PC 扫码（openid A）与小程序（openid B）通过 unionid 归并为同一用户，避免重复注册。
4. **refreshToken 放 HttpOnly Cookie + Path 限定**：`Path=/api/web/auth/refresh`，仅刷新接口携带，降低 XSS 窃取与 CSRF 风险；accessToken 仍由前端 JS 管理。
5. **回调返回 HTML 而非 JSON**：因为由微信浏览器顶层跳转触发，需承载「登录成功」提示页并 JS 跳回前端。
6. **StrictMode 防重复兑换**：回调页用 `useRef` 标记，避免 React 18 严格模式下 effect 二次执行导致重复调 refresh。

## 六、state 参数为什么不能省

`state` 是这套流程里最容易被当成「可选项」的参数，但它实际承担了**两个**职责，核心是安全而非过期控制。

### 1. state 的两个作用

| 作用 | 说明 |
| ---- | ---- |
| 防登录 CSRF | OAuth2 规范要求 `state` 的原生目的，**必须保留** |
| 二维码时效控制 | 顺带实现「二维码 5 分钟过期」，属体验与可控性增强 |

代码里对 `state` 只做了一件事：**校验回调是否由「本服务端刚发出去的二维码」触发**。

### 2. 去掉 state 后的最大风险：登录 CSRF（账号劫持）

OAuth 回调是**不可预测**的——后端无法从 `code` 反推出「是谁发起的授权」。若没有 state 绑定，攻击者可实施经典的 OAuth 登录 CSRF：

```
① 攻击者自己用微信走一遍授权流程，拿到一个「已授权但尚未消费」的 code
② 把回调链接发给受害者：
   https://your-domain/api/web/auth/wechat/callback?code=攻击者的code
③ 受害者点开 → 后端用攻击者的 code 换取 openid → 落地成攻击者身份的登录态
④ 受害者浏览器（写入攻击者的 refreshToken Cookie）现在登录成了攻击者的账号
```

后果：受害者在自己浏览器里登录进了**攻击者的账号**，攻击者随后可窃取受害者在该账号下的敏感操作（绑定手机号、充值、提交简历等）。

> 补充：这套代码里 `redirect_uri` 是后端写死的（不接收前端传入），所以 OAuth 另一类「回调地址篡改」风险天然不存在，剩下的登录 CSRF 只能靠 `state` 防。

### 3. 其他次要影响

- **二维码无法过期**：去掉 state 后，过期完全交由微信 `code` 自身有效期（约 5 分钟）决定，失去自定义过期时间（`state-ttl-seconds`）与「回调前感知失效并提示」的能力。不构成直接安全漏洞，但体验与可控性变差。
- **无法防重放**：现在 state 校验通过即删除（一次性消费），去掉后失去这层保险。不过微信 `code` 本身也是一次性的，风险较低。

### 4. 结论

| 作用 | 必要性 | 去掉后的风险 |
| ---- | ------ | ------------ |
| 防登录 CSRF | **必须保留** | 攻击者可让受害者登录攻击者账号（账号劫持） |
| 二维码时效控制 | 建议保留 | 失去自定义过期与友好提示，不构成直接漏洞 |
| 防重放 | 锦上添花 | 微信 code 本身一次性，风险较低 |

**state 校验不能去掉**，它的核心价值不是「过期控制」，而是 **OAuth 登录 CSRF 防护**。当前实现（随机不透明 token + Redis 存储 + 一次性消费）是标准且正确的做法。

> 一个可选的加固点：当前只判断「state 是否存在于 Redis」，未校验其值是否为当初发的那一个。因为 state 是随机不可猜测的，能命中 Redis 基本等价于合法。若想更严谨，可把 Redis value 从固定串 `"PENDING"` 换成「发起时的上下文信息」（如来源平台、客户端标识），回调时比对，防止 state 被跨上下文复用。对当前场景，随机 token + 存在性校验已足够安全。

## 七、接口清单

| 方法 | 路径 | 说明 | 触发方 |
| ---- | ---- | ---- | ------ |
| GET  | `/api/web/auth/wechat/scan/url` | 获取扫码 URL（返回 state + url） | 前端扫码页 |
| GET  | `/api/web/auth/wechat/callback` | 微信 OAuth 回调（code + state） | 微信服务器 |
| POST | `/api/web/auth/refresh` | 用 Cookie 兑换 accessToken | 前端回调页 |

## 八、与其他登录方式对比

| 维度 | 微信小程序登录 | PC 微信扫码登录 |
| ---- | -------------- | --------------- |
| 微信接口 | `jscode2session` | `sns/oauth2/access_token` |
| scope | 无（小程序天然绑定） | `snsapi_login` |
| 授权 URL | 无（小程序端 `wx.login`） | `open.weixin.qq.com/connect/qrconnect` |
| 回调方式 | 前端拿 code 传给后端 | 微信顶层跳转后端 callback |
| 用户标识 | openid（小程序） | openid（开放平台）+ unionid 打通 |
| 登录态落地 | 返回 token 对 | 写 Cookie + 前端跳转兑换 |
