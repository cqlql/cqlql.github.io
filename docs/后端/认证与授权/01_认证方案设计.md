# 认证方案设计

核心方案：**JWT + sid + jti + Redis** 混合管理 token —— JWT 作为无状态载体，Redis 作为有状态管控中心。

> 阅读顺序建议：本文讲「整体方案与 Key 设计」→ `02_Token刷新策略.md` 讲「刷新与失效」→ `03_Token生成方案对比.md` 讲「token 怎么生成才安全」→ `04_App防冒充方案.md` 讲「客户端防伪造」。

------

## 一、术语表

| 缩写 | 全称            | 含义                                   |
| ---- | --------------- | -------------------------------------- |
| sid  | Session ID      | 一次登录会话的唯一标识，绑定所有 token |
| jti  | JWT ID          | 单个 JWT 的唯一标识，用于单独撤销某张 token |
| sub  | Subject         | JWT 中的用户 ID                        |
| exp  | Expiration      | JWT 过期时间（epoch 秒）               |

**sid 与 jti 的本质区别**：

- `sid` 管「这一整个登录会话」——删除 session 即让该会话下全部 token 失效。
- `jti` 管「这一张 token」——可单独撤销某张 token，而不影响同会话其他 token。

> 结论：**jti 是补丁，sid 是体系**。设计刷新/风控时优先用 sid。

------

## 二、方案选型

### JWT vs Redis Token

| 维度     | JWT Token（无状态）       | Redis Token（有状态）       |
| -------- | ------------------------- | --------------------------- |
| 状态     | 无状态，自包含用户信息    | 有状态，服务端存储          |
| 可撤销   | ❌ 天然不可撤销            | ✅ 删 Key 即失效             |
| 安全性   | 依赖密钥签名，泄露即伪造  | Token 只是标识，信息在服务端 |
| 风控能力 | 弱，无法实时控制          | 强，可随时踢人/下线         |
| 适用场景 | 简单场景、无需风控        | 企业级、需要风控            |

> **结论**：需要登录风控选 Redis Token。Redis Token + Refresh Token 可兼顾长期会话体验与安全性。

### 微服务中的 Redis Token 方案

单点登录 + Redis Token + 网关，是企业级微服务最安全、最可控、最易风控的登录方案。

```
Client → API Gateway → Auth Server (Redis token)
                    → Service A
                    → Service B
                    → Service C
```

**职责划分：**

- **Auth Server（单点登录中心）**：登录认证、Redis token 管理、风控、统一失效控制
- **API Gateway / 网关**：统一鉴权入口，token 校验只在这里做一次
- **微服务**：不再关心登录态，只关注业务逻辑

## 三、核心理念

1. 结合 **JWT（载体）+ Redis（管控）** 管理 token。
2. JWT 只存必要标识，**真实权限与状态由 Redis 管控**。
3. 🔥 **关键点**：只要 `session` 被删，该会话下所有 token 同时失效。

------

## 四、Redis Key 设计（重点）

```
# access token（可选，用于单独撤销某张 access）
auth:access:{jti}        -> sid
TTL: 30 min

# refresh token（hash 存储，脱敏）
auth:refresh:{hash}      -> sid
TTL: 7 days

# session 信息（核心管控对象）
auth:session:{sid}       -> { userId, roles, jti, version, loginTime }
TTL: 7 days

# sid -> refreshToken（用于刷新时轮换/失效）
auth:session:refresh:{sid} -> hash
TTL: 7 days

# 用户多端会话（限制同时在线设备数）
auth:user:sessions:{userId}:{clientType} -> ZSET(sid), score = 过期时间
TTL: 7 days
```

**设计要点：**

- **refreshToken 用 hash 存储**：令牌脱敏，泄露后也无法被直接重放；hash 计算方式见 `03_Token生成方案对比.md`。
- **accessToken 可选**：即使不维护 `auth:access:{jti}`，仅靠删除 `auth:session:{sid}` 也能实现踢人。
- 🔥 **session 被删 → 所有 token 失效**，这是整套方案的核心失效机制。

## 五、JWT Payload 设计

```json
{
  "sub": "1001",
  "sid": "sid-uuid",
  "jti": "access-jti-uuid",
  "exp": 1700000000
}
```

- `sub`：用户 ID
- `sid`：会话 ID（本次登录唯一标识）
- `jti`：access token 的 ID，用于在 Redis 中单独定位/撤销该 token
- `exp`：过期时间（epoch 秒）

> RefreshToken **不强制用 JWT**，随机字符串 + Redis 即可（详见 `02_Token刷新策略.md` 与 `03_Token生成方案对比.md`）。

## 六、登录流程

```
账号密码正确
   ↓
生成 sid
   ↓
生成 accessToken（15 min）  /  生成 refreshToken（7 d）
   ↓
写 Redis（session + token 映射）
   ↓
返回前端
```

- AccessToken 与 refreshToken 都关联到同一个 `sid`。
- Redis 记录 session 与 token 的映射关系。

------

## 七、校验逻辑

```
Header 带 accessToken
   ↓
解析 JWT 拿 sid / jti
   ↓
Redis 查 auth:session:{sid} 是否存在
   ↓
存在 & 未过期 → 放行
```

> JWT 只是载体，**真实权限通过 Redis 校验**。单点登出只需删除 `auth:session:{sid}` → 该会话 token 全部失效。

## 八、多端会话控制

限制同一用户同时在线设备数，依赖 `auth:user:sessions:{userId}:{clientType}` 这个 ZSET。

### 方案一：登录时懒清理（⭐⭐⭐）

遍历 ZSET，对 `auth:session:{sid}` 已不存在的成员执行 `ZREM`：

```
for (sid in zset) {
    if (!exists("auth:session:" + sid)) {
        ZREM(sid);
    }
}
```

✔ 优点：实现简单，无额外机制，大厂也采用。

### 方案二：用 score 表示过期时间（⭐⭐⭐⭐，推荐）

```
ZADD key score=(now + 7days) member=sid
# 登录时先清理已过期成员：
ZREMRANGEBYSCORE key 0 now
```

✔ 优点：无需逐个 `exists`，O(logN) 性能，优雅高效。

⚠️ **隐藏坑**：refresh 时 session TTL 被延长（7 天 → 再 7 天），但 ZSET 的 score 仍是旧时间，会被误删。
✅ **解决办法**：refresh 时同步 `ZADD key newExpireTime sid`。

## 九、FAQ

### 1. refreshToken 需要是 JWT 吗？

不需要。企业级常见做法：AccessToken = JWT + Redis，RefreshToken = 随机字符串 + Redis。

### 2. 为什么 accessToken 还要放 `jti`？

用于在 Redis 中快速定位具体 token，可单独撤销某张 token，而不是整段 session。

### 3. 删除 session 会让 token 失效吗？

✅ 会。Redis 统一管控 session，删除 `auth:session:{sid}` 即撤销该会话下所有 token。

### 4. 前端 token 存哪里？

- `access_token` → **放内存 / 前端变量**（少数情况用 localStorage）
- `refresh_token` → **放 HttpOnly + Secure Cookie（强烈推荐）**，仅刷新接口携带
