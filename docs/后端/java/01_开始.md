## jar war 如何选择？

对于 **Spring Boot Web API** 项目，绝大多数情况下的标准答案是：**JAR**。

虽然 Spring Boot 同时也支持 WAR，但除非你的运维环境有极特殊的限制（比如公司强制要求必须把所有应用塞进一个统一管理的外部 Tomcat 容器），否则 JAR 永远是第一选择。

以下是为什么 **JAR** 在 Web API 开发中统治地位的原因：

------

### 1. “自带干粮” (内嵌服务器)

使用 JAR 包时，Spring Boot 会把 Web 服务器（默认是 Tomcat）直接打包进 JAR 文件里。

- **JAR 模式：** 运行 `java -jar app.jar`，它自己启动 Tomcat，直接对外提供 API 服务。
- **WAR 模式：** 你需要先安装 Tomcat，配置环境变量，然后把 WAR 丢进 `webapps` 文件夹，等待 Tomcat 解压并启动。

### 2. 开发与运维的一致性

这是 JAR 最大的优势。你在本地 IDE（IntelliJ IDEA）点击运行时的逻辑，与你在服务器上运行 JAR 包的逻辑完全一致。这种“**自包含**”的特性极大减少了“我电脑上能跑，服务器上不行”的玄学问题。

### 3. 微服务与容器化（Docker）的绝配

现代 Web API 通常配合 Docker 部署。

- **JAR + Docker：** 你的 `Dockerfile` 只需要一行 `ENTRYPOINT ["java", "-jar", "app.jar"]`。
- **WAR + Docker：** 你需要基于 Tomcat 镜像构建，处理复杂的目录挂载和权限。

### 4. 性能与掌控力

JAR 模式允许你通过代码或配置文件（`application.yml`）直接调优 Tomcat 参数（如最大连接数、线程池）。而在 WAR 模式下，这些配置往往受限于外部 Tomcat 的全局设置。

------

### 核心对比表

| **维度**          | **JAR (推荐)**                | **WAR (传统)**                 |
| ----------------- | ----------------------------- | ------------------------------ |
| **部署难度**      | 极低（单文件，一行命令）      | 中（需预装服务器软件）         |
| **启动速度**      | 快                            | 较慢（涉及解压过程）           |
| **云原生/Docker** | 完美适配                      | 兼容，但显得笨重               |
| **适合场景**      | **Web API**、微服务、独立应用 | 必须共享旧版 Tomcat 的传统环境 |

------

### 如何在 Spring Boot 中确认？

在你的 `pom.xml` 文件中，检查 `<packaging>` 标签。如果你没有写这个标签，它**默认就是 JAR**。

XML

```
<groupId>com.example</groupId>
<artifactId>demo-api</artifactId>
<version>0.0.1-SNAPSHOT</version>
<packaging>jar</packaging> 
```

------

### 什么时候必须用 WAR？

只有一种情况：你的甲方或运维部门指着一个已经运行了 5 年的旧 **Tomcat 独立集群**说：“我们的所有 API 必须统一扔到这个容器里跑，不准自己带服务器。”

### 💡 核心建议

1. **不管用哪种，先做 CI/CD：** 永远不要手动 `scp` 一个 Jar 包去覆盖生产环境。哪怕是用 GitHub Actions 写一个简单的脚本，也能减少 90% 的低级错误。
2. **关注 Java 版本：** 2026 年，请确保你的生产环境至少在 **Java 21 (LTS)** 以上，利用虚拟线程（Virtual Threads）可以显著提升 Web 服务的并发能力，而无需修改部署架构。
3. **可观测性：** 部署时记得集成 **Prometheus** 和 **Grafana**（或者使用云厂商自带的监控），看不见内部运行状态的部署是不及格的。

## 本地依赖 mvn install

把当前项目的打包结果（Jar/War）放到你电脑的“本地仓库”里，供其他项目引用。

### 引用本地仓库

项目中使用本地依赖与线上依赖一致，Maven 会先找本地仓库，找不到才会找线上。如果远程也找不到，就会抛出经典的 `Dependency resolution failed`。

```
<dependencies>
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>my-utils</artifactId>
        <version>1.0-SNAPSHOT</version>
    </dependency>
</dependencies>
```



## 快照版 (Snapshot)

如果你的版本号后面带着 `-SNAPSHOT`（如 `1.0-SNAPSHOT`），这是一个非常实用的特性：

1. **自动更新**：当你在 A 项目里修改了代码并再次执行 `mvn install` 时，B 项目**不需要**改版本号。
2. **强制刷新**：如果 B 项目没感应到变化，你可以执行 `mvn clean compile -U`。这里的 `-U` 会强制 Maven 检查本地和远程仓库的最新快照。

### Maven找寻核心区别：SNAPSHOT vs RELEASE

Maven 对这两种版本的“找寻态度”完全不同，这决定了它会不会“自动”去远程找：

#### **情况 A：正式版 (Release)**

- **版本号示例**：`1.0.0`, `2.1.4`
- **逻辑**：Maven 认为正式版是**不可变的**。只要本地仓库里有了这个版本，它**永远不会**再去远程仓库检查更新。如果你在远程改了代码但没改版本号，本地是感应不到的。

#### **情况 B：快照版 (Snapshot)**

- **版本号示例**：`1.0-SNAPSHOT`
- **逻辑**：Maven 认为快照版是**正在开发中**的。即使本地有了，它也会**定期**（默认每天一次，或者当你使用 `-U` 参数时）去远程仓库检查有没有更新的时间戳。如果有更新，它会自动下载覆盖本地。
