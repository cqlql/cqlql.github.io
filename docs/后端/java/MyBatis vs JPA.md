

# MyBatis（@Mapper）vs JPA（ORM）使用边界与选型

> [!TIP]
>
> `@Mapper` 是主流做法之一， 在复杂业务和权限系统中， 它往往比 JPA 更主流、更可靠。

## 一、背景

在 Java 后端开发中，数据访问层常用两种主要技术：

1. **JPA / Hibernate（ORM）**
   - 面向对象，实体映射到数据库表
   - 自动管理对象关系、级联操作和懒加载
2. **MyBatis / @Mapper（SQL 映射）**
   - 通过 SQL 显式操作数据库
   - 关系由 SQL 决定，不依赖 ORM 注解

> 本文结合 RBAC（角色权限）系统的实践，总结两者的**使用边界、优缺点及选型原则**。

## 二、核心概念对比

| 维度             | JPA / ORM        | MyBatis / @Mapper                    |
| ---------------- | ---------------- | ------------------------------------ |
| 数据访问方式     | 对象关系映射     | SQL 映射                             |
| 是否自动管理关系 | ✅ 是             | ❌ 否，手写 SQL                       |
| 懒加载 / 级联    | ✅ 支持           | ❌ 不支持，需要自己 join              |
| SQL 可控性       | ❌ 生成 SQL 难读  | ✅ 完全可控，可调优                   |
| 学习曲线         | 中等             | 中等偏低                             |
| 使用场景         | 简单 CRUD / 单表 | 复杂 join / 权限 / 报表 / 高性能要求 |

## 三、使用场景对比

### 1️⃣ JPA 适合场景

- 单表或极简单表关系
- CRUD 操作频繁，但关系简单
- 表结构稳定，不常改动
- 不涉及复杂权限计算或多表 join

**优点：**

- 开发快速，减少手写 SQL
- 对象模型直观

**缺点：**

- 性能不可完全预测
- 多表关系复杂时容易触发 N+1 查询
- SQL 优化困难

------

### 2️⃣ MyBatis / @Mapper 适合场景

- 权限系统（RBAC）
- 复杂业务逻辑 / 多表 join
- 报表、BI、统计分析
- 性能关键路径

**优点：**

- SQL 完全可控，可 explain 和优化
- 关系清晰、可追踪
- 高并发场景更稳定

**缺点：**

- CRUD 需要手写 SQL
- 对象关系需手动维护
