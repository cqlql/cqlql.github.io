# 微信小程序虚拟支付（xpay / 米大师）

小程序内售卖**虚拟商品**（虚拟货币、解锁功能、订阅内容、付费功能、打赏、虚拟礼物等），购买和支付必须接入虚拟支付，不能再用普通 JSAPI 支付。

> **与 [微信小程序支付（JSAPI）](./微信小程序支付.md) 是两套完全不同的体系**：商户主体、下单方式、签名算法、回调协议、退款接口全部不同。那篇笔记里的「三把钥匙 + 两次签名 + APIv3 回调解密」在这里**一个都用不上**。

> 项目背景：PassUp 面试助手（卖面试时长礼包 = 虚拟商品）。改造思路：新增 `VirtualPayService`（签名 + `/xpay/*` 服务端接口 + 回调分派），保留 `WechatPayService` 走双轨，业务层抽象 `PaymentChannel`，订单 / 快照 / 幂等发放 / 补偿任务全部复用。

------

## 一、为什么必须改

在 iOS 上用普通 JSAPI 收虚拟商品的钱属于违规，微信有明确的处罚路径（见错误码 `-15017` 商家违规收款被限制、`-15019` 商户受限）。只要业务在 iOS 端合规收款，就必须切虚拟支付。

强制范围包括：虚拟货币、解锁功能、订阅内容、付费功能、打赏、购买虚拟礼物等——**面试时长、积分、会员、课程**这些都在范围内。

------

## 二、JSAPI vs 虚拟支付 对照

| 环节 | JSAPI 普通支付 | 虚拟支付 |
| ---- | -------------- | -------- |
| 商户主体 | 微信支付商户号 `mchid` | 小程序后台开通的**独立二级商户号**（`offerId`），T+3 结算 |
| 下单 | 后端 `POST /v3/pay/transactions/jsapi` 拿 `prepay_id` | **后端不下单**，只签出 `signData` + `paySig`，客户端 `wx.requestVirtualPayment` 内部自带下单 + 拉起 |
| 签名 | 商户私钥 `SHA256withRSA`，两次签名 | HMAC-SHA256：`paySig = hex(hmac_sha256(appKey, "requestVirtualPayment" + "&" + signData))` |
| 用户态签名 | 无 | `signature = hex(hmac_sha256(session_key, signData))` |
| 回调 | `Wechatpay-*` 头验签 + AES-256-GCM 解密 | MP 消息推送（XML/JSON），`Event` 区分类型 |
| 回调响应 | `{"code":"SUCCESS","message":"成功"}` | `{"ErrCode":0,"ErrMsg":"success"}`，最多重试 15 次 |
| 查单 | `/v3/pay/transactions/out-trade-no/{no}` | `/xpay/query_order?access_token=xxx` |
| 退款 | `/v3/refund/domestic/refunds` | `/xpay/refund_order` 启动任务，再 `query_order` 轮询结果 |
| 凭证 | 商户私钥 / 平台公钥 / APIv3 密钥 | `offerId` / `appKey`（沙箱+现网各一套）/ `session_key` / `access_token` |
| 商品 | 自家 DB 里一行 | 必须先在 MP 后台上传并**发布**道具 / 代币 |

## 三、开通与配置

### 1. 开通条件与入口

- 条件：**已认证**小程序，主体为**企业 / 事业单位 / 个体工商户**，主体信息完备。
- 入口：MP 左侧栏【虚拟支付】→ 提交营业执照、提现账户、支付管理员 → 账户验证 → 扫码签约。审核约 1–7 个工作日，签约后再等 1–2 个工作日。
- 开通后拿到的是**新的二级商户号**，与原微信支付商户号是两套资金账户。

### 2. 基础配置（拿三样东西）

MP → 虚拟支付 → 基础配置：

| 项 | 说明 |
| -- | ---- |
| `appid` | 小程序 AppID |
| `offerId` | 商户号（**signData 里必须传字符串**，传数字会验签失败） |
| `AppKey` | **沙箱 AppKey 和现网 AppKey 各一套**，按 `env` 取值 |
| 发货订阅 | 配置消息推送地址（见第七节） |

### 3. 道具 / 代币配置

MP → 虚拟支付 → 道具管理 / 代币配置：

- **道具**：上传到「开发版本」，测试通过后「发布至现网版本」。名称需符合法规要求，**发布后约 10 分钟才生效**（未生效下单报 `-15014`）。
- **代币**：配置代币名称 + 兑换比例，**一旦发布不可修改**。

### 4. 选型：道具直购 还是 代币充值

| 模式 | `mode` | 适用 | 说明 |
| ---- | ------ | ---- | ---- |
| **道具直购** | `short_series_goods` | 固定金额买固定权益（**面试时长礼包推荐这个**） | 一个礼包 = 一个 `productId`，`goodsPrice`（分）做价格校验 |
| 代币充值 | `short_series_coin` | 先充成余额，再按次扣减 | 充值后业务侧用 `/xpay/currency_pay` 扣币 |
| 会员订阅 | 见独立文档 | 连续包月 | 安卓/鸿蒙 与 iOS 各有单独文档 |

> 判断依据：用户付一次钱拿到「一个确定的东西」用道具直购；用户先把钱充进账户、后续按用量慢慢扣，用代币。
> 组合方案与业务建模（问答次数 / 语音时长、自定义时长充值、双账本设计、表结构）见 [虚拟支付充值-资产发放方案](../../../项目/面试助手/架构设计/虚拟支付充值-资产发放方案.md)。

## 四、整体流程

### 1. 道具直购（推荐）

```
① 小程序端选择礼包 → POST /api/recharge-orders 创建订单
   ↓
② 后端：校验礼包 → 生成 outTradeNo（8-32 位规则）→ 查 session_key
   ↓
③ 后端：构造 signData（字典序）→ 算 paySig + signature
   ↓
④ 返回 { signData, paySig, signature, mode } 给小程序端
   ↓
⑤ 小程序端 wx.requestVirtualPayment(...)  ← 内部完成下单 + 拉起收银台
   ↓
⑥ 用户支付成功
   ├─ 分支 A：微信 MP 消息推送 xpay_goods_deliver_notify → 后端发货
   └─ 分支 B：后端定时 /xpay/query_order 轮询补单（**必须做**，success 回调可能丢失）
   ↓
⑦ 发货：解析 Attach → 发放资产（幂等）→ 响应 {"ErrCode":0}
```

### 2. 代币充值

比道具直购多一步消费：用户先买代币（`short_series_coin`），业务侧实际消费时调 `/xpay/currency_pay` 扣减，扣减成功后触发 `xpay_coin_pay_notify`。

### 3. 关键差异：下单不在后端

普通支付是「后端下单 → 前端拉起」，虚拟支付是「**后端只出签名 → 前端内部完成下单和拉起**」。所以后端**没有 `prepay_id`**，也无法感知「用户是否已打开收银台」——只能靠推送或轮询确认结果。

## 五、后端：签名与出参

### 1. signData 构造（最容易踩坑）

`signData` 是一个 **JSON 字符串**，字段必须**按 key 字典序排列**：

```java
// 顺序：attach < buyQuantity < currencyType < env < goodsPrice < offerId < outTradeNo < productId
String signData = "{"
        + "\"attach\":\""      + jsonEscape(attach)      + "\","
        + "\"buyQuantity\":"   + quantity                + ","
        + "\"currencyType\":\"CNY\","
        + "\"env\":"           + env                     + ","
        + "\"goodsPrice\":"    + goodsPriceFen           + ","
        + "\"offerId\":\""     + offerId                 + "\","   // 字符串！
        + "\"outTradeNo\":\""  + outTradeNo              + "\","
        + "\"productId\":\""   + productId               + "\""
        + "}";
```

| 字段 | 必填 | 说明 |
| ---- | ---- | ---- |
| `offerId` | ✅ | MP 基础配置中的 offerId，**字符串类型** |
| `buyQuantity` | ✅ | 购买数量 |
| `currencyType` | ✅ | 币种，目前只能填 `CNY` |
| `env` | ❌ | `0` 现网（默认）、`1` 沙箱。**现网版本只能填 0**（`-15011`） |
| `productId` | 道具直购必填 | 道具 ID，必须已发布到现网 |
| `goodsPrice` | 道具直购必填 | 道具单价（**分**），用于校验与后台价格一致，不一致报 `-15013` |
| `activitySellingPrice` | ❌ | 优惠价（分），需与 `goodsPrice` 一起传，传了即为实际下单价 |
| `outTradeNo` | ✅ | 业务订单号，**8–32 字符**，仅数字/大小写字母/`_-|*@`，**不能以下划线开头** |
| `attach` | ✅ | 透传数据，发货通知时原样回传（放订单号 / 礼包 ID） |

> ⚠️ **逐字节一致原则**：微信会按字典序重组 `signData` 后验签。签名用的字符串和最终传给 `wx.requestVirtualPayment` 的 `signData` 必须**完全一致**，前端**绝不能 `JSON.parse` 后再 `stringify`**（字段顺序/空格变了就报 `-15006`）。后端直接返回签名用的那个原始字符串最安全。

### 2. 两个签名

```java
// 支付签名：uri 固定为 "requestVirtualPayment"（基础库调用场景）
String paySig = hmacSha256Hex(appKey, "requestVirtualPayment" + "&" + signData);

// 用户态签名：用 code2Session 拿到的 session_key
String signature = hmacSha256Hex(sessionKey, signData);
```

HMAC-SHA256 实现：

```java
private static String hmacSha256Hex(String key, String data) {
    try {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(key.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        byte[] raw = mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        StringBuilder sb = new StringBuilder(raw.length * 2);
        for (byte b : raw) {
            sb.append(Character.forDigit((b >> 4) & 0xF, 16))
              .append(Character.forDigit(b & 0xF, 16));
        }
        return sb.toString();   // 小写 hex
    } catch (Exception e) {
        throw new IllegalStateException("HMAC-SHA256 计算失败", e);
    }
}

private static String jsonEscape(String s) {
    if (s == null) return "";
    return s.replace("\\", "\\\\").replace("\"", "\\\"")
            .replace("\n", "\\n").replace("\r", "\\r").replace("\t", "\\t");
}
```

### 3. Service 实现

```java
@Service
public class VirtualPayService {

    private final WechatVirtualPayProperties props;   // offerId / appKey / env
    private final SessionKeyStore sessionKeyStore;    // 自己维护的 openid → session_key

    public VirtualPayParams createGoodsOrder(RechargeOrder order, String openId) {
        int env = props.getEnv();                          // 0 现网 / 1 沙箱
        String appKey = env == 0 ? props.getAppKeyProd() : props.getAppKeySandbox();

        // 1. session_key（过期会导致 -15007，需重新 code2Session 刷新）
        String sessionKey = sessionKeyStore.get(openId)
                .orElseThrow(() -> new BusinessException("登录态已失效，请重新进入小程序"));

        // 2. 价格（分），必须与 MP 后台该道具的发布价一致
        int goodsPriceFen = order.getAmount().multiply(BigDecimal.valueOf(100)).intValue();

        // 3. signData（字典序，见上）
        String signData = buildSignData(order, goodsPriceFen, env);

        // 4. 两个签名
        String paySig    = hmacSha256Hex(appKey, "requestVirtualPayment" + "&" + signData);
        String signature = hmacSha256Hex(sessionKey, signData);

        return VirtualPayParams.builder()
                .signData(signData)                    // 原样返回，前端不要二次序列化
                .paySig(paySig)
                .signature(signature)
                .mode("short_series_goods")
                .env(env)
                .build();
    }
}
```

### 4. 订单号规则

`R + 时间戳 + 4 位随机`（沿用 JSAPI 笔记的 `generateOrderNo()`）需要校验：

```java
// outTradeNo：8-32 字符，[0-9A-Za-z_\-|*@]，且不能以 _ 开头
if (!orderNo.matches("[0-9A-Za-z|*@][0-9A-Za-z_\\-|*@]{7,31}")) {
    throw new IllegalStateException("订单号不符合虚拟支付规则: " + orderNo);
}
```

> `outTradeNo` 重复使用会报 `-15002`，且官方说明「极端情况不保证唯一，不建议业务强依赖唯一性」——**幂等仍要靠自己的 `markAssetGranted`**。

## 六、小程序端调用

```ts
// 基础库 >= 2.19.2（Android / 鸿蒙 / Windows）
const res = await createVirtualOrder(packageId);   // 后端返回 signData/paySig/signature/mode

wx.requestVirtualPayment({
  signData: res.signData,      // 字符串，原样传，勿 JSON.parse
  paySig: res.paySig,
  signature: res.signature,
  mode: res.mode,              // 'short_series_goods' | 'short_series_coin'
  success: () => { /* 仅表示收银台流程结束，不代表发货成功 */ },
  fail: ({ errMsg, errCode }) => { /* 见错误码表 */ },
});
```

兼容性判断（低版本基础库）：

```ts
if (compareVersion(SDKVersion, '2.19.2') >= 0 || wx.canIUse('requestVirtualPayment')) {
  wx.requestVirtualPayment({ ... });
} else {
  // 提示用户升级微信
}
```

> Taro 若未封装该 API，直接走 `wx.requestVirtualPayment`（Taro 项目可通过 `wx` 全局命名空间调用）。
> Windows 端需额外适配：`platform === 'android' || platform === 'windows'` 才走虚拟支付。

**与 JSAPI 的字段对比（全变了）**：

| JSAPI `wx.requestPayment` | 虚拟支付 `wx.requestVirtualPayment` |
| ------------------------- | ----------------------------------- |
| `appId` / `timeStamp` / `nonceStr` / `package` / `paySign` / `signType` | ❌ 全部作废 |
| — | ✅ `signData` / `paySig` / `signature` / `mode` |

## 七、回调：MP 消息推送

### 0. 配置回调 URL 的 GET 验证（接入第一步）

> ⚠️ **保存即验证**：在 MP 后台「发货推送配置」里**点「保存」的那一刻**，微信会立刻向回调 URL 发一个 **GET 请求**做验证——不是保存后才异步触发。这一步之前，你的后端 GET 接口必须已经部署、可公网访问、且 `token` 配置与后台填写值一致。验证通过后台「测试状态」显示「已通过」，之后才开始推送业务消息；验证失败后台直接报 **「Token校验失败，请检查确认」**，这一步没做对，后面 POST 推送根本进不来。

> 「Token校验失败」这个报错**几乎都跟 token 字符串本身无关**（随机字符串不会格式不合法），而是微信拿着你填的 token 去回调 URL 做 SHA1 验签没通过，常见原因：后端 `token` 没改成真实值（还留着占位符）、回调 URL 少写了 `/api` 前缀、后端未部署/未重启、或地址非公网 HTTPS。

**请求参数**（微信 GET 到你的回调地址）：

| 参数 | 说明 |
| ---- | ---- |
| `signature` | 微信加密签名，`sha1(字典序排序[token, timestamp, nonce] 拼接)` |
| `timestamp` | 时间戳 |
| `nonce` | 随机数 |
| `echostr` | 随机字符串，验证通过后需**原样回显** |

示例：

```
https://your-domain.com/api/webhook/wechat/virtual-pay
  ?signature=6298f2b139f33959c59d69da33f5c4215d9df26a
  &timestamp=1700735027
  &nonce=50328042
  &echostr=Mzi3wDcVa5uI
```

**验签算法**：`token` 是你在后台「发货推送配置」里自定义填写的令牌（≤32 字符，与后端配置保持一致）：

```java
String[] arr = {token, timestamp, nonce};
Arrays.sort(arr);                                   // 字典序排序
String expected = sha1(String.join("", arr));       // 拼接后 SHA1，小写 hex
boolean ok = MessageDigest.isEqual(expected.getBytes(UTF_8),
                                   signature.getBytes(UTF_8));
return ok ? echostr : "";                           // 通过则原样返回 echostr
```

**响应格式（与 POST 完全不同）**：

| 阶段 | 请求方式 | 响应格式 |
| ---- | -------- | -------- |
| URL 验证 | GET | **纯文本 `echostr`**（原样回显，**不是** JSON） |
| 业务推送 | POST | JSON `{"ErrCode":0,"ErrMsg":"success"}` |

> ⚠️ 踩坑点：
> - **GET 回显 `echostr`、POST 回 JSON**，两个响应格式别搞反——GET 回 JSON 会导致后台「测试状态」不通过。
> - `token` 必须与后台填写值**逐字节一致**，否则 `expected` 永远对不上、验证失败。
> - 回调路径若加了 `/api` 前缀（Spring 全局前缀），后台填的 URL 也要带 `/api`，并在 `SecurityConfig` 放行 `/api/webhook/**`。
> - 建议额外校验 `timestamp` 时效（如 ±5 分钟）防重放。

> 说明：这一步是「小程序消息推送通道」的 URL 接入验证，SHA1 只用于确认请求来自微信服务器，与 JSAPI 的 APIv3 RSA 请求头验签是两码事。业务推送（POST）的真实性校验仍要靠第八节第 4 点的 `query_order` 反查，不要误以为过了 GET 验证就能信任推送体。

### 1. 事件类型

| Event | 触发时机 |
| ----- | -------- |
| `xpay_goods_deliver_notify` | 现金购买道具并支付成功（**主要处理这个**） |
| `xpay_coin_pay_notify` | 代币支付推送，用户代币**扣减**成功后（报文含 `WeChatPayInfo` + `CoinInfo`） |
| `xpay_refund_notify` | 退款完成 |
| `xpay_complaint_notify` | 用户发起投诉 |
| `xpay_wxpay_callback_notify` | 风控事件（尽职调查 / 管控流水） |
| `xpay_subscribe_ios_refund_query_notify` | **iOS 退款问询**（见第九节） |

### 2. 回调真实性校验（没有 APIv3 那样的验签）

虚拟支付的消息推送走**小程序消息推送通道**，**不存在** APIv3 那套 RSA 请求头验签 + AES-GCM 解密。可用的防护手段：

1. 校验 `ToUserName` 等于自己的小程序原始 ID；
2. 校验 `FromUserName`——道具发货场景固定为微信官方 openid；
3. 校验 `Env`：沙箱（`1`）的推送不得发放到现网业务库；
4. **最可靠**：收到推送后主动调 `/xpay/query_order` 反向确认订单真实存在且已支付，再发货。这一步同时兜住了伪造回调与数据不一致。

> 不要照搬 JSAPI 那篇的 `Wechatpay-Signature` 头验签逻辑，这里根本没有这些请求头。

### 3. 道具发货推送结构

```json
{
  "ToUserName": "gh_xxxxxxxx",
  "FromUserName": "oXXXX",
  "CreateTime": 1756000000,
  "MsgType": "event",
  "Event": "xpay_goods_deliver_notify",
  "OpenId": "oXXXX",
  "OutTradeNo": "R2026082812345678",
  "Env": 0,
  "WeChatPayInfo": {
    "MchOrderNo": "商户单号",
    "TransactionId": "微信支付订单号",
    "PaidTime": 1756000000
  },
  "GoodsInfo": {
    "ProductId": "pkg_interview_60min",
    "Quantity": 1,
    "OrigPrice": 9900,
    "ActualPrice": 9900,
    "Attach": "透传数据"
  }
}
```

> `Env` 字段必须校验：沙箱（`1`）的推送不要往现网业务库发货。

### 4. 响应格式（写错会被重推）

三种都算成功，推荐第一种：

```json
{"ErrCode":0,"ErrMsg":"success"}
```

```xml
<xml><ErrCode>0</ErrCode><ErrMsg><![CDATA[success]]></ErrMsg></xml>
```

> **响应格式不对会重推，最多 15 次**（间隔 2、4、8、16… 秒）。XML 推送就用 XML 响应，JSON 推送就用 JSON 响应。

### 5. Controller 实现

```java
@RestController
@RequestMapping("/api/callback/wechat-virtual-pay")
public class VirtualPayCallbackController {

    @PostMapping
    public Map<String, Object> handle(@RequestBody Map<String, Object> msg) {
        String event = (String) msg.get("Event");
        try {
            switch (event) {
                case "xpay_goods_deliver_notify" -> handleDeliver(msg);
                case "xpay_coin_pay_notify"      -> handleCoinPay(msg);
                case "xpay_refund_notify"        -> handleRefund(msg);
                case "xpay_subscribe_ios_refund_query_notify" -> handleIosRefundQuery(msg);
                default -> log.info("忽略的虚拟支付事件: {}", event);
            }
            return Map.of("ErrCode", 0, "ErrMsg", "success");
        } catch (Exception e) {
            log.error("处理虚拟支付回调失败 event={}", event, e);
            return Map.of("ErrCode", 1, "ErrMsg", "处理失败");  // 触发微信重推
        }
    }

    private void handleDeliver(Map<String, Object> msg) {
        if (!Integer.valueOf(0).equals(msg.get("Env"))) {
            log.info("沙箱推送，跳过发货");
            return;
        }
        String outTradeNo = (String) msg.get("OutTradeNo");
        String transactionId = (String) ((Map<?, ?>) msg.get("WeChatPayInfo")).get("TransactionId");

        rechargeOrderService.handlePaymentSuccess(outTradeNo, "WECHAT_VIRTUAL", transactionId);

        try {
            RechargeOrder order = rechargeOrderService.getOrderByOrderNo(outTradeNo);
            rechargeAssetGrantService.grantAssets(order.getId());   // 内部 markAssetGranted 幂等
        } catch (Exception e) {
            log.error("发放资产失败，等待补偿任务", e);
        }
    }
}
```

> 正常通过推送返回成功即可**不需要**再调 `/xpay/notify_provide_goods`——那个接口是推送处理失败后的补救手段。

### 6. 幂等与补偿（比 JSAPI 更重要）

官方文档明确：**「发货推送分支」与「发货轮询分支」至少实现一个，两者结合使用体验更可靠**。原因是 `wx.requestVirtualPayment` 的 `success` 回调**可能丢失**（微信异常退出），推送也可能失败。

所以在 JSAPI 笔记的补偿任务之外，还要加一条**主动查单**通道：

```java
// 定时扫描「已发起支付但未确认」的订单，主动向微信确认
public void confirmPendingOrders() {
    List<RechargeOrder> orders = rechargeOrderRepository.findUnconfirmedOrders();
    for (RechargeOrder order : orders) {
        VirtualOrderQueryResult r = virtualPayService.queryOrder(order.getOrderNo());
        if (r.isPaid()) {
            rechargeOrderService.handlePaymentSuccess(
                    order.getOrderNo(), "WECHAT_VIRTUAL", r.getTransactionId());
            rechargeAssetGrantService.grantAssets(order.getId());  // 幂等
        } else if (order.isExpired()) {
            rechargeOrderService.markExpired(order.getOrderNo());
        }
    }
}
```

原有的 `markAssetGranted` 原子更新 + 补偿任务**完全保留**，这两条路径共用同一套幂等保护。

## 八、服务端 API 清单

网关：`https://api.weixin.qq.com`，接口路径均为 `/xpay/*`。

### 签名与鉴权

```java
// uri：不含 query string，如 "/xpay/query_order"
// postBody：本次请求的 POST body（逐字节一致）
String paySig    = hmacSha256Hex(appKey,     uri + "&" + postBody);   // 支付签名
String signature = hmacSha256Hex(sessionKey, postBody);               // 用户态签名
```

三个凭证都通过 **query 参数**传递：

```
POST https://api.weixin.qq.com/xpay/query_order
     ?access_token=ACCESS_TOKEN&signature=SIGNATURE&pay_sig=PAY_SIG
```

- `access_token` 用 `stable_token` 接口获取并缓存（提前 300 秒刷新），**需要在微信侧配置 IP 白名单**（否则报 `40164`）。
- `signature` 依赖 `session_key`，过期会报 `268490009`，与前端 `wx.requestVirtualPayment` 的 `-15007` 同理。
- 注意：**客户端调用时 uri 固定为 `requestVirtualPayment`**，服务端接口则用各自的路径。
- 具体每个接口的参数以官方服务端 API 文档为准。

### 常用接口

| 用途 | 路径 | 要点 |
| ---- | ---- | ---- |
| 查订单 | `/xpay/query_order` | `order_id`（商户单号）或 `wx_order_id` 二选一；**退款也靠它轮询结果** |
| 启动退款任务 | `/xpay/refund_order` | 只表示「任务启动成功」，要继续 `query_order` 直到状态为退款完成 |
| 通知已发货 | `/xpay/notify_provide_goods` | 仅现金单；推送已返回成功时不必调 |
| 查询代币余额 | `/xpay/query_user_balance` | 代币模式用 |
| 扣减代币 | `/xpay/currency_pay` | body：`openid` / `env` / `user_ip` / **`amount`（代币数）** / **`order_id`（流水号）** / `payitem` / `remark`；成功后触发 `xpay_coin_pay_notify` |
| 撤销代币扣减 | `/xpay/cancel_currency_pay` | `currency_pay` 的逆操作 |
| 赠送代币 | `/xpay/present_currency` | 不支持按单号查询，重试至返回 `0` 或 `268490004` |
| 批量上传/发布道具 | `/xpay/start_upload_goods`、`/xpay/query_upload_goods`、`/xpay/start_publish_goods`、`/xpay/query_publish_goods` | 一次只能处理一个道具，异步任务需轮询结果 |
| 下载账单 | `/xpay/download_bill`、`/xpay/query_download_order` | 对账用 |

> 退款时限：支付 **180 天内**退款平台退还手续费，超过 180 天不退。

## 九、iOS 端差异（新增工作量）

`wx.requestVirtualPayment` 会按设备类型自动路由：

| 设备 | 对接支付系统 |
| ---- | ------------ |
| Android / 鸿蒙 / Windows | 微信支付 |
| iOS | **Apple 支付** |

### 1. 门槛

- 用户：iPhone/iPad + **iOS 15+**，微信 **8.0.68+**，**最低支付 1 元**，仅中国大陆 App Store 账户。
- 小程序：需先配置**小程序简称**（Apple 要求展示 display name）。
- **Apple 支付不支持沙箱环境**，只能现网测（现网会产生技术服务费，注意成本）。
- 道具 / 代币是**双端互通**的，已配置的无需重复配。

### 2. 开发者不能主动退款

Apple 支付下，用户需到 App Store 自行申请退款。苹果会向开发者发起**最多 3 次退款问询**，后端需应答 `xpay_subscribe_ios_refund_query_notify`：

```json
{
  "Event": "xpay_subscribe_ios_refund_query_notify",
  "refund_time": "1756000000",
  "order_time": "1755000000",
  "channel_bill": "Apple 支付票据号",
  "bundleid": "应用的 Apple bundleid",
  "product_id": "道具 id",
  "p_count": "数量",
  "refund_request_reason": "用户请求退款的原因",
  "provide_status": "0 未发货 / 1 已发货 / 2 发货中",
  "pay_order_id": "退款对应支付订单号"
}
```

应答：

```json
{
  "result_code": 0,          // 0 = 放过，建议退款；1 = 拦截，拒绝退款
  "result_info": "结果描述",
  "evidence": "决策凭据（必填），本次判断的依据，用于退款审计"
}
```

> ⚠️ **若连续 3 次、3 秒内均未应答**，微信会向 Apple 返回「不确定」，退款决定权完全交给苹果。所以这个接口要**同步快速返回**，不能走耗时业务。
> 策略建议：查订单发货状态 → 已消费/已发货用 `result_code=1` 拦截（附消费凭据），未发货则用 `0` 放过。

### 3. 结算与费率

- **结算**：iOS 订单由苹果结算，自然月结束后 **45～60 天**汇款给腾讯，再划转到你的虚拟支付账户。
- **费率**（iOS 端）：

| 科目 | 收取方 | 标准费率 | 2026 年 |
| ---- | ------ | -------- | ------- |
| Apple 服务费 | 苹果 | 12% | 以苹果佣金政策为准，当前 12% |
| 腾讯技术服务费 | 腾讯 | 5% | 限时减免，0% |
| 合计 | — | 17% | **12%** |

- Android 端结算为 **T+3**，费率参见官方「技术服务费」文档。

### application.yml

```yaml
wechat:
  # 原普通支付（保留，非虚拟商品继续用）
  pay:
    mch-id: your-mch-id
    api-v3-key: your-api-v3-key
    serial-number: your-serial-number
    private-key-path: /secrets/apiclient_key.pem
    public-key-path: /secrets/pub_key.pem
    notify-url: https://your-domain.com/api/callback/wechat-pay
  # 新增：虚拟支付
  virtual-pay:
    app-id: wxXXXXXXXX
    app-secret: your-app-secret        # 用于换取 access_token
    offer-id: "12345678"               # 字符串！
    app-key-sandbox: sandbox-appkey
    app-key-prod: prod-appkey
    env: 0                             # 0 现网 / 1 沙箱，按环境注入
    callback-path: /api/callback/wechat-virtual-pay
```

### 密钥用途对比

| 凭证 | JSAPI | 虚拟支付 |
| ---- | ----- | -------- |
| 商户私钥 / 平台公钥 / APIv3 密钥 | 签名 + 验签 + 解密 | ❌ 完全不用 |
| `offerId` | — | 商户标识，进 `signData` |
| `AppKey`（沙箱/现网两套） | — | 算 `paySig`、`pay_sig` |
| `session_key`（`code2Session`） | — | 算 `signature`（会过期） |
| `access_token`（`stable_token`） | — | 调 `/xpay/*` 服务端接口 |

### session_key 维护

`signature` 依赖 `session_key`，而它会过期（`-15007`）。需要：

1. 登录时 `code2Session` 拿 `session_key` 存起来（Redis，key 为 openid，过期时间与微信侧对齐）。
2. 前端遇到 `-15007` → 重新 `wx.login` → 后端刷新 `session_key` → 前端重试下单。

## 十一、错误码速查

| 错误码 | 含义 | 处理 |
| ------ | ---- | ---- |
| `-1` | 支付失败 | 提示重试 |
| `-2` | 支付取消 | **正常场景**，不要当错误提示 |
| `-4` | 风控拦截 | 提示用户联系客服 |
| `1001` / `-15001` | 参数错误 | 检查 `signData` 字段 |
| `-15002` | `outTradeNo` 重复 | 换新单号重试 |
| `-15004` | `currencyType` 错误 | 只能填 `CNY` |
| `-15005` | 用户态签名 `signature` 错误 | `session_key` 不对或 `signData` 不一致 |
| `-15006` | 支付签名 `paySig` 错误 | AppKey 与 `env` 不匹配、或 `signData` 被二次序列化 |
| `-15007` | `session_key` 过期 | 重新 `wx.login` 刷新 |
| `-15009` / `-15010` | 代币未发布 / 道具未发布 | MP 后台发布 |
| `-15011` | 现网 `env` 只能是 0 | 环境配置错 |
| `-15013` | `goodsPrice` 与后台价格不一致 | 同步价格 |
| `-15014` | 道具/代币发布未生效 | 等约 10 分钟 |
| `-15016` | `signData` 格式有问题 | 检查 JSON 与字段顺序 |
| `-15017` / `-15019` | 商家违规 / 商户受限，收款被限制 | 登录商户平台查看原因（**这就是不接虚拟支付的下场**） |
| `-15018` | 道具/代币审核不通过 | MP 后台处理 |
| `-15020` | 操作过快 | 稍后重试 |
| `-15021` | 小程序被限频交易 | 联系平台 |

## 十三、易错点总结

1. **`signData` 逐字节一致**：字段按字典序、不重排、不重新序列化，否则 `-15006`。
2. **`offerId` 必须是字符串**，传数字验签失败。
3. **`env` 与 AppKey 必须配套**：`env=0` 用现网 AppKey，`env=1` 用沙箱 AppKey。
4. **后端没有 `prepay_id`**：下单在客户端完成，后端只能靠推送或轮询确认。
5. **回调响应是 `ErrCode/ErrMsg`**，不是 APIv3 的 `code/message`。
6. **`success` 回调会丢失**：必须做轮询补单，不能只靠前端回调。
7. **`outTradeNo` 规则**：8–32 位、限定字符集、不能以 `_` 开头。
8. **`session_key` 会过期**：`-15007` 时刷新后重试。
9. **Apple 支付不支持沙箱**，现网测试会产生技术服务费。
10. **iOS 退款问询 3 秒内必须应答**，否则退款决定权交给苹果。
