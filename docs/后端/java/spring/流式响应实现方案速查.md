# 流式响应实现方案速查

**分类：** `#SpringBoot` `#StreamingResponseBody` `#SseEmitter` `#WebFlux` `#NDJSON` `#Java` `#Backend`

**核心问题：** 在 Spring 生态中实现流式响应（如 AI 对话打字机效果）有哪些主流方案？各自的适用场景和优劣是什么？

------

## 1. 方案总览

| 方案 | 适用栈 | 格式灵活度 | 复杂度 | 推荐场景 |
|------|--------|-----------|--------|---------|
| `StreamingResponseBody` + NDJSON | Spring MVC (Servlet) | 高（自定义 MIME type） | 中 | 需要自定义事件格式的流式接口 |
| `SseEmitter` | Spring MVC (Servlet) | 低（固定 SSE 格式） | 低 | 标准 SSE 推送场景 |
| `Flux<ServerSentEvent>` | WebFlux (Reactive) | 低（固定 SSE 格式） | 中 | 响应式栈的流式接口 |

```text
主流程度对比：

StreamingResponseBody + NDJSON   ──────  ████████░░  成熟但偏手工
SseEmitter (Spring MVC)          ──────  ██████████  纯 SSE 场景首选
WebFlux Flux<ServerSentEvent>    ──────  █████████░  响应式栈首选
```

## 2. 方案一：`StreamingResponseBody` + NDJSON（推荐自定义场景）

### 核心写法

```java
@GetMapping("/chat")
public ResponseEntity<StreamingResponseBody> chat() {
    // 提前 resolve 用户身份，避免异步线程丢失 SecurityContext
    String userId = getCurrentUserId();

    StreamingResponseBody stream = outputStream -> {
        try {
            Writer writer = new OutputStreamWriter(outputStream, StandardCharsets.UTF_8);
            PrintWriter out = new PrintWriter(writer);

            for (String chunk : chunks) {
                writeEvent(out, "delta", Map.of("content", chunk));
            }
            writeEvent(out, "done", Map.of());

        } catch (IOException e) {
            throw new StreamWriteException("流式写入失败", e);
        } finally {
            out.close();
        }
    };

    return ResponseEntity.ok()
            .contentType(MediaType.valueOf("application/x-ndjson"))
            .body(stream);
}

private void writeEvent(PrintWriter out, String type, Object data) throws IOException {
    String json = objectMapper.writeValueAsString(Map.of("type", type, "data", data));
    out.write(json);
    out.write("\n");
    out.flush();
    response.flushBuffer(); // 绕过 Servlet 容器缓冲，直接触发网络写
}
```

### 关键点

| 点 | 说明 |
|----|------|
| `response.setBufferSize(0)` | 关键操作，禁用 Servlet 容器缓冲，确保增量推送 |
| `response.flushBuffer()` | 绕过 OutputStream 装饰器层，直接触发网络写 |
| `out.flush()` + `response.flushBuffer()` | 双重 flush，缺一个都可能导致某些容器下缓冲 |
| NDJSON 格式 (`application/x-ndjson`) | 每行一个 JSON，前端逐行解析，比 SSE 更灵活 |
| 提前 resolve 用户身份 | 异步线程丢失 SecurityContext 的标准解法 |
| `StreamWriteException` (RuntimeException) | 解决 lambda 无法抛 checked exception 的问题 |

### NDJSON vs SSE

| 维度 | NDJSON | SSE |
|------|--------|-----|
| MIME type | `application/x-ndjson` | `text/event-stream` |
| 事件结构 | 完全自定义 JSON | 固定 `event:` / `data:` 字段 |
| 前端解析 | `response.body.getReader()` 逐行读 | `EventSource` API 自动解析 |
| 断线重连 | 需手动实现 | 浏览器自动重连（可能重复请求） |
| 灵活性 | 高 | 低 |

### 优化建议

- `response.flushBuffer()` 不必每次 `writeEvent` 都调用，可改为每隔 N 个 chunk 或每隔一定时间 flush 一次，减少系统调用开销
- 客户端断开后不抛异常（`writeEventQuietly`），避免日志噪音

## 3. 方案二：`SseEmitter`（Spring MVC 原生 SSE）

Spring MVC 对 SSE 的官方封装，框架帮你管理 flush、超时、异常关闭。

```java
@GetMapping(value = "/chat-sse", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter chat() {
    SseEmitter emitter = new SseEmitter(0L); // 0 = 无超时

    executor.execute(() -> {
        try {
            emitter.send(SseEmitter.event()
                    .name("delta")
                    .data("Hello"));

            emitter.send(SseEmitter.event()
                    .name("done")
                    .data("完整内容"));

            emitter.complete();
        } catch (IOException e) {
            emitter.completeWithError(e);
        }
    });

    return emitter;
}
```

### 优劣分析

| 优势 | 劣势 |
|------|------|
| 框架管理 flush、超时、异常关闭 | 格式固定为 SSE，不能自定义 MIME type |
| 代码量少，框架处理边缘情况 | 浏览器 `EventSource` 断线自动重连，可能导致重复请求 |
| Spring MVC 原生支持 | 无法自定义事件结构，受限于 `event:`/`data:` 模型 |

### 适用场景

- 简单的服务端推送（通知、进度条）
- 不需要自定义事件格式
- 前端使用 `EventSource` 即可接入

## 4. 方案三：`Flux<ServerSentEvent>`（WebFlux 响应式栈）

```java
@GetMapping(value = "/chat-flux", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> chat() {
    return Flux.create(sink -> {
        sink.next(ServerSentEvent.<String>builder()
                .event("delta")
                .data("Hello")
                .build());

        sink.next(ServerSentEvent.<String>builder()
                .event("done")
                .data("完整内容")
                .build());

        sink.complete();
    });
}
```

### 优劣分析

| 优势 | 劣势 |
|------|------|
| 声明式编程，代码简洁 | 需要切换到 WebFlux 技术栈（Netty 代替 Tomcat） |
| 原生支持背压（Backpressure） | 生态兼容性（部分 Servlet Filter 不可用） |
| 天然响应式，线程模型高效 | 学习曲线较高 |

### 适用场景

- 项目已是 WebFlux 技术栈
- 需要背压控制的高并发流式场景
- 团队熟悉响应式编程

## 5. 方案选择决策

```text
需要自定义事件格式（如 NDJSON）？
├── 是 → StreamingResponseBody + NDJSON
└── 否 → 标准 SSE 场景
         ├── Spring MVC 栈 → SseEmitter
         └── WebFlux 栈    → Flux<ServerSentEvent>
```

## 6. 常见踩坑

### ContentCachingResponseWrapper 导致流式响应空 Body

当 Filter 使用 `ContentCachingResponseWrapper` 包装响应时，流式接口返回空 Body。原因是 Filter 在主线程返回时认为响应已结束，写入 `Content-Length: 0` 并提交响应，导致后续异步写入被丢弃。

**修复：** 在 Filter 中排除流式端点的 Response 包装，只包装 Request。

```java
if (requestURI.contains("/chat")) {
    filterChain.doFilter(requestWrapper, response); // 传原生 response
    return;
}
```

> 详见：[ContentCachingResponseWrapper-流式响应空Body问题](./ContentCachingResponseWrapper-流式响应空Body问题.md)

### 异步线程丢失 SecurityContext

`StreamingResponseBody` 在异步线程中执行，SecurityContext 不会自动传递。

**修复：** 在主线程中提前 resolve 用户信息，作为参数传入异步逻辑。

```java
String userId = SecurityContextHolder.getContext().getAuthentication().getName();
StreamingResponseBody stream = out -> {
    // 直接使用已 resolve 的 userId，不依赖 SecurityContextHolder
};
```

------

## 7. 总结

| 结论 | 说明 |
|------|------|
| **Spring MVC + 自定义格式 → `StreamingResponseBody` + NDJSON** | 最灵活，完全控制事件结构和 MIME type |
| **Spring MVC + 标准 SSE → `SseEmitter`** | 框架封装，代码量最少 |
| **WebFlux 栈 → `Flux<ServerSentEvent>`** | 声明式 + 背压，但需切技术栈 |
| **`StreamingResponseBody` 不是"偏门"** | 它是 Spring MVC 实现自定义流式响应最正确的写法之一 |
