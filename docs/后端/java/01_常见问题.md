# 常见问题速查

## 日志显示 debug 去不掉？

有两处控制：

```yaml
debug: true # 改成 false
logging:
  level:
    root: debug # 改成 info
```

## JAR vs WAR 如何选择？

对于 **Spring Boot Web API** 项目，绝大多数情况下的标准答案是：**JAR**。

| 维度 | JAR (推荐) | WAR (传统) |
| ---- | ---------- | ---------- |
| 部署难度 | 极低（单文件，一行命令） | 中（需预装服务器软件） |
| 启动速度 | 快 | 较慢（涉及解压过程） |
| 云原生/Docker | 完美适配 | 兼容，但显得笨重 |
| 适合场景 | **Web API**、微服务、独立应用 | 必须共享旧版 Tomcat 的传统环境 |

### JAR 的优势

1. **内嵌服务器**：运行 `java -jar app.jar` 即可，自带 Tomcat
2. **开发与运维一致**：本地和服务器逻辑完全一致
3. **微服务与容器化绝配**：Dockerfile 只需一行 `ENTRYPOINT ["java", "-jar", "app.jar"]`

### 什么时候必须用 WAR？

只有一种情况：甲方或运维要求所有 API 必须统一扔到外部 Tomcat 容器里跑。

## 部署方式推荐

| 特性 | 传统 JAR (Systemd) | Docker 容器 | GraalVM 原生镜像 |
| ---- | ------------------ | ----------- | ---------------- |
| 部署难度 | 简单 | 中等 | 较高 (编译慢) |
| 启动速度 | 较慢 | 中等 | **极快** |
| 内存开销 | 高 | 高 | **低** |
| 隔离性 | 弱 | **强** | **强** |
| 推荐等级 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ (特定场景) |

## 打包命令

```bash
mvn clean package
```

## 本地依赖 mvn install

把当前项目的打包结果放到本地仓库里，供其他项目引用。

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>my-utils</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>
```

### SNAPSHOT vs RELEASE

| 类型 | 版本号示例 | 行为 |
| ---- | ---------- | ---- |
| Release | `1.0.0` | 本地有了就**永远不更新** |
| Snapshot | `1.0-SNAPSHOT` | 定期检查更新，`-U` 强制刷新 |

## application.yml 与 pom.xml 区别

| 特性 | Maven (pom.xml) | Spring Boot (application.yml) |
| ---- | --------------- | ----------------------------- |
| 身份 | **构建工具** | **应用框架** |
| 职责 | 管理依赖、编译代码、打包 | 管理业务逻辑、数据库连接、Web 请求 |
| 生效时间 | **打包时** | **运行时** |

## CI/CD 工具格局

| 工具 | 份额特征 | 核心标签 |
| ---- | -------- | -------- |
| Jenkins | 34% (缓慢下降) | 老大哥 / 万能 / 复杂 |
| GitHub Actions | ~28% (快速上升) | 生态丰富 / 零维护 |
| GitLab CI | ~18% (稳步增长) | 安全 / K8s 原生 |
| 云厂商 (Azure/AWS/GCP) | ~12% | 厂商集成 / 合规 |

### 核心建议

1. 不管用哪种，先做 CI/CD：永远不要手动 `scp` 一个 Jar 包覆盖生产
2. 关注 Java 版本：生产环境至少 **Java 21 (LTS)**，利用虚拟线程提升并发能力
3. 可观测性：集成 Prometheus 和 Grafana
