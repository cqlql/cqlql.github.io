# **`BlockingQueue`**（阻塞队列）

## put offer add 对比

如果你不想让程序死等，Java 提供了几种不同的处理方式，你可以根据业务逻辑选择：

| **方法**                   | **队列满时的行为**                       | **推荐场景**                             |
| -------------------------- | ---------------------------------------- | ---------------------------------------- |
| **`put(e)`**               | **死等**，直到有空位。                   | 决不允许丢数据，且能接受处理速度受限。   |
| **`offer(e)`**             | **直接返回 `false`**，不等待。           | 宁可丢弃这次数据，也要保证程序流程顺畅。 |
| **`offer(e, time, unit)`** | **等一会**，超时了就返回 `false`。       | 兼顾成功率和响应时间。                   |
| **`add(e)`**               | **抛出异常** (`IllegalStateException`)。 | 队列满了说明逻辑出错，需要报错处理。     |

## queue.poll 对比 queue.take

在 Java 的并发编程中（通常指 `BlockingQueue` 接口），`poll` 和 `take` 的核心区别在于**“面对空队列时的耐心程度”**。

我们可以把队列想象成一个**自动售货机**，而你是消费者：

### 1. 核心区别对比

| **方法**               | **行为模式**     | **如果队列是空的（Empty）**                             | **适用场景**                       |
| ---------------------- | ---------------- | ------------------------------------------------------- | ---------------------------------- |
| **`poll()`**           | **非阻塞**       | **立即返回 `null`**。                                   | 哪怕没货也要立刻回来，不能耽误事。 |
| **`poll(time, unit)`** | **有限等待**     | **等够时间**，期间有货立刻拿，过期还没货才返回 `null`。 | 愿意等一会儿，但不想等一辈子。     |
| **`take()`**           | **死等（阻塞）** | **一直阻塞**，直到队列里有了新数据。                    | 必须拿到货，否则就地“冬眠”。       |

------

### 2. 深度拆解

#### `queue.take()` —— “执着型”

这是最常用的生产-消费模式。如果没有数据，当前线程会进入 **WAITING** 状态，完全不消耗 CPU 资源，直到被其他线程唤醒（`put` 了一个数据）。

- **优点**：代码逻辑最简单，不需要处理 `null`。
- **缺点**：如果生产者挂了，消费者会永远卡在那里。
- **异常**：必须处理 `InterruptedException`。

#### `queue.poll(long timeout, TimeUnit unit)` —— “理性型”

它兼顾了响应速度和稳定性。

- **优点**：可以防止线程死锁。如果一直没数据，它可以跳出来检查一下标志位（比如你代码里的 `session.isOpen()`）。
- **缺点**：需要额外处理返回值为 `null` 的情况。

------

### 3. 如何选择？

- **用 `take()` 的场景**：

  你的程序是一个纯粹的任务处理器，任务不来我就不干活，且没有复杂的退出逻辑。

- **用 `poll(time, unit)` 的场景**：

  你需要**优雅停机**。比如你需要在等待数据的间隙，顺便看看“老板是不是让我下班了”（检查 `stopFlag` 或 `session` 状态）。

- **用 `poll()` (无参) 的场景**：

  你需要极高的吞吐量，且能容忍空转。比如在一个死循环里不断扫多个队列，哪个有货处理哪个。

------

### 代码直观对比

```java
// 场景 A：必须拿到数据，拿不到就原地踏步
byte[] data = queue.take(); 
outputStream.write(data);

// 场景 B：拿不到就先干点别的（比如你之前的代码）
byte[] data = queue.poll(1, TimeUnit.SECONDS);
if (data != null) {
    outputStream.write(data);
} else {
    // 队列是空的，这一秒我等完了，刚好可以检查一下 session 是否关闭
    System.out.println("等了一秒还是没数据，看看 session 关没关...");
}
```

## 如何优雅地让消费线程退出

### 方案一：发送“结束信号”（推荐 👍）

这是最优雅、最常用、最可控的方式。

------

#### 🔹 原理

当连接关闭时：

```
向队列放入一个特殊数据（结束标记）
```

消费者收到后退出。

------

#### 🔹 实现方式

##### 1️⃣ 定义结束标记

```
private static final byte[] END_SIGNAL = new byte[0];
```

------

##### 2️⃣ 消费线程

```java
private void consumeAudio(WebSocketSession session,
                          BlockingQueue<byte[]> queue) {

    try (FileOutputStream outputStream =
                 new FileOutputStream("audio-" + session.getId() + ".pcm")) {

        while (true) {

            byte[] data = queue.take();  // 仍然可以用 take()

            // 收到结束信号
            if (data == END_SIGNAL) {
                break;
            }

            outputStream.write(data);
        }

    } catch (Exception e) {
        e.printStackTrace();
    }
}
```

------

##### 3️⃣ 连接关闭时发送结束信号

```java
@Override
public void afterConnectionClosed(WebSocketSession session,
                                  CloseStatus status) {

    BlockingQueue<byte[]> queue =
            queueMap.get(session.getId());

    if (queue != null) {
        queue.offer(END_SIGNAL);  // 唤醒 take()
    }

    queueMap.remove(session.getId());
}
```

------

#### 优点

- 不需要 poll
- 不需要 sleep
- 线程立即退出
- 不浪费 CPU
- 最干净

### 方案二：使用 poll 超时（简单但次优）

```java
while (true) {

    if (!session.isOpen() && queue.isEmpty()) {
        break;
    }

    byte[] data = queue.poll(1, TimeUnit.SECONDS);

    if (data != null) {
        outputStream.write(data);
    }
}
```

#### 优点

- 简单
- 不需要额外信号

#### 缺点

- 每秒醒一次
- 多线程时浪费资源
- 不够优雅
