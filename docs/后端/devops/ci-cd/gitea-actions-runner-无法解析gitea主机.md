# Gitea Actions Runner 任务容器无法解析 gitea 主机

> docker-compose 部署 Gitea + act_runner 时，CI 任务的 `checkout` 步骤报 `Could not resolve host: gitea` 的原因与几种解决方式。

## 问题现象

Gitea Actions 流水线在 `Checkout` 步骤失败：

```
/usr/bin/git -c protocol.version=2 fetch ... origin +<sha>:refs/tags/v5
fatal: unable to access 'http://gitea:3000/***/pass-up.backend.dev/';: Could not resolve host: gitea
The process '/usr/bin/git' failed with exit code 128
```

clone 地址是 `http://gitea:3000/...`，但执行 `checkout` 的容器里解析不了 `gitea` 这个主机名。

## 根本原因

- `gitea` 和 `gitea-runner`（act_runner）两个容器都在同一个自定义网络 `gitea-net` 上，**runner 容器自己能解析 `gitea`**，所以它能正常从 Gitea 拉取任务。
- 但真正执行 `checkout` 的不是 runner 容器，而是 act_runner 为每个任务**临时启动的任务容器**（如 `ubuntu-latest` 镜像）。
- 任务容器默认挂在 Docker 的 `bridge` 网络，**不在 `gitea-net` 上**，因此里面没有 `gitea` 这条 DNS 记录，自然解析不到。
- `checkout` 用的地址来自 runner 注册时记录的 `address`（写入 `/data/.runner`），act_runner 会把它作为 `GITEA_INSTANCE_URL` 注入到任务容器里，于是任务容器去访问 `http://gitea:3000`，解析失败。

一句话：**runner 能连通 gitea，但 runner 拉起来的任务容器连不通 gitea。**

## 解决方案对比

| 方案 | 做法 | 推荐度 |
| --- | --- | --- |
| A. 让任务容器加入 gitea-net | `config.yaml` 设 `container.network: gitea-net` | ⭐ 推荐 |
| B. 重新注册 runner 用可达地址 | 删 `.runner` 后用 `http://宿主机IP:3000` 注册 | 可用 |
| C. 手动改 `.runner` 的 address | 直接编辑 `/data/.runner` | 临时/不推荐 |
| D. 改 Gitea `ROOT_URL` | 设为宿主机可达地址 | 改动面大 |

### 方案 A（推荐）：任务容器使用 gitea-net 网络

让 act_runner 启动的任务容器直接挂到 `gitea-net`，就能像 runner 一样解析 `gitea` 主机名，内部流量也走 Docker 网络、不绕宿主机。

编辑 runner 挂载的 `config.yaml`（compose 里是 `./config.yaml:/config.yaml`），加入 `container.network`：

```yaml
log:
  level: info
runner:
  file: .runner
  capacity: 1
container:
  # 关键：任务容器使用与 gitea 相同的网络，才能解析 gitea 主机名
  network: "gitea-net"
  options:
    - --cpus=1
  volumes:
    - /var/run/docker.sock:/var/run/docker.sock
```

然后重启 runner 使配置生效：

```bash
docker compose restart runner
# 或
docker restart gitea-runner
```

> 前提：`gitea` 服务也在这个 `gitea-net` 网络上（你的 compose 已经满足）。

### 方案 B：用宿主机可达地址重新注册 runner

让注册地址使用宿主机 IP（如 `http://192.168.1.221:3000`），任务容器通过宿主机 IP 访问 Gitea（bridge 网络能访问宿主机 IP）。

注意：**只改环境变量 `GITEA_INSTANCE_URL` 不会更新已注册的 runner**，因为地址已经固化在 `/data/.runner` 里。需要删掉 `.runner` 重新注册：

```bash
# 确认 compose 中 GITEA_INSTANCE_URL 已是可达地址
#   GITEA_INSTANCE_URL: http://192.168.1.221:3000
docker compose down runner
docker volume rm <gitea_runner_data>   # 或直接删容器内的 /data/.runner
# 重新启动，runner 会用新的 GITEA_INSTANCE_URL 注册，address 变为 http://192.168.1.221:3000
docker compose up -d runner
```

### 方案 C（你用的临时方案）：手动编辑 `.runner`

直接改 runner 容器里的 `/data/.runner`：

```json
{
  "WARNING": "This file is automatically generated by act-runner. Do not edit it manually ...",
  "address": "http://gitea:3000",   // 改成 http://192.168.1.221:3000
  ...
}
```

改完重启 runner 即可生效。

**为什么不推荐**：文件顶部明确警告"自动生成，不要手动改"；runner 重新注册（删 `.runner` / 升级）后会覆盖此文件，改动丢失。仅适合临时验证。

### 方案 D：修改 Gitea 的 ROOT_URL

在 `gitea` 的 `app.ini` 中把 `ROOT_URL` 设为宿主机可达地址：

```ini
[server]
ROOT_URL = http://192.168.1.221:3000/
```

这样 Gitea 下发的 clone 地址就是 IP，任务容器能直接访问。但会影响所有 clone 地址和页面访问基址，改动面较大。

## 推荐做法

优先用 **方案 A**：只需在 `config.yaml` 加一行 `container.network: "gitea-net"`，不动地址、不绕宿主机，最干净也最稳。

若 runner 与 gitea 不在同一台宿主机，则改用 **方案 B**，用可达地址重新注册 runner。

## 验证

重新触发一次流水线，观察 `Checkout` 步骤：

```bash
# 进入任务容器确认能解析 gitea（方案 A）
docker exec -it <job_container> getent hosts gitea

# 或直接在 runner 容器内确认地址
docker exec -it gitea-runner cat /data/.runner | grep address
```

## 相关命令

```bash
# 查看 gitea-net 上有哪些容器（确认 gitea / runner 都在）
docker network inspect gitea-net

# 查看某个任务容器的网络（默认应是 bridge，方案 A 后应是 gitea-net）
docker inspect <container_id> | grep -A5 Networks

# 进入 runner 容器看 .runner 当前 address
docker exec -it gitea-runner sh -c "cat /data/.runner"
```
