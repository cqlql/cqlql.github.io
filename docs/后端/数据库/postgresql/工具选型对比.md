# 备份工具选型对比：pgBackRest vs WAL-G

这两个工具在 PostgreSQL 社区里都是**顶级（Tier 1）的生产级备份恢复利器**，但它们的**设计哲学和最佳适用场景**有很大不同。

用一句话概括：

> 如果是传统的物理机/虚拟机部署，选 `pgBackRest`；如果是 K8s / K3s 云原生环境，选 `WAL-G`。

---

## 核心维度对比

| 维度 | `pgBackRest` | `WAL-G` |
| --- | --- | --- |
| **开发语言** | C 语言（早期是 Perl） | Go 语言（Golang） |
| **主打优势** | **功能极其强悍、极致的控制力与稳定性** | **云原生契合度高、并发性能极强、轻量** |
| **增量备份** | 支持 **BLOCK 级增量与差异备份** | 支持增量备份（但依赖日志重放） |
| **资源消耗** | 内存占用极低，C 语言高效运行 | 依赖 Go 协程，高并发时 CPU/内存消耗比 C 稍高 |
| **S3 / MinIO 支持** | 支持（可直接流式写入对象存储） | 原生极佳（Go 内置 S3 SDK，上传速度极快） |
| **生态/工具链** | Crunchy Data 主导，物理机部署的标准答案 | CitusData / Zalando 主导，云原生环境的首选 |

---

> 增量备份的间隔机制、Block 级增量特例与生产避坑，见姊妹篇：[增量备份机制与避坑](./增量备份机制与避坑.md)。
> `pgBackRest` 默认其实是文件级增量、如何开启真正的 Block 级，见：[pgBackRest 备份策略：增量粒度、定期全量与滚动轮转](./pgBackRest备份策略.md)。

## 详细优缺点分析

### 1. pgBackRest（传统物理/虚机环境的霸主）

`pgBackRest` 专门为了解决大规模 PostgreSQL 数据库的备份难题而生。

- **优势**：
  - **真正的 Block 级增量备份**：它能够检测 PostgreSQL 数据页的变化，只备份修改过的块（Block），极大地节省存储空间和备份时间。
  - **异步 WAL 传输**：WAL 归档可以异步并行处理，即使写入吞吐量极高，也不会阻塞 PG 自身的事务提交。
  - **极强的安全性与容错**：支持完整性校验（Hash）、加密、自动重试和损坏检测。
- **劣势**：
  - 配置相对复杂（需要配置服务端/客户端、ssh 密钥或配置文件）。

### 2. WAL-G（Kubernetes / 云原生的宠儿）

`WAL-G` 是前代工具 `WAL-E` 的 Go 语言重写版，它的核心目标就是**极致的传输速度与云原生集成**。

- **优势**：
  - **云原生 / S3 性能优异**：利用 Go 语言的高并发协程，WAL-G 在将 WAL 日志和全量文件并发上传到 **MinIO / AWS S3** 时，速度非常惊人。
  - **单文件/无依赖**：编译后就是一个独立的 Go 二进制文件，非常适合打包进 Docker 镜像或 Pod 中运行。
  - **K8s 生态集成度高**：大部分主流 Kubernetes PostgreSQL Operator（如 CloudNativePG、Zalando Operator）默认或推荐使用 WAL-G 作为底层 WAL 传输引擎。
- **劣势**：
  - 相比 `pgBackRest`，某些高级物理控制功能（如特定的块级增量粒度控制）略逊一筹。

## 选型建议

```
                             你的部署环境？
                                   │
                   ┌───────────────┴───────────────┐
                   ▼                               ▼
            【物理机 / 虚拟机】                 【K3s / K8s / 容器】
                   │                               │
                   ▼                               ▼
             推荐 pgBackRest                   推荐 WAL-G
          (功能最全、稳定老牌)              (搭配 Operator 运维极佳)
```

1. **选 `WAL-G` 的场景**：
   - 运行在 **K3s / K8s** 环境中。
   - 备份目标是 **MinIO / S3 对象存储**。
   - 使用了 **CloudNativePG** 或 **Zalando Postgres Operator**。

2. **选 `pgBackRest` 的场景**：
   - 部署在**传统 Linux 物理机或虚拟机**上。
   - 数据库体积非常大（TB 级），需要极致的 **块级增量备份** 节约空间。
   - 对备份数据的加密、严格的完整性校验有很高要求。
