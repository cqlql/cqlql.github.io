# 大库全量备份性能优化

当数据库很大（例如几百 GB 到几 TB）时，全量备份确实会变慢，而且如果不加限制，非常可能会拖垮服务器性能（耗尽 CPU、磁盘 I/O 和网络带宽）。

这也是为什么在生产环境中，**绝对不能"硬干"全量备份**，必须配合一系列优化手段。

---

## 1. 为什么全量备份会拖垮性能？

全量备份本质上是做三件事：

1. **磁盘 I/O 暴增**：需要把整个数据目录里的几万/几百万个数据块（Page）**全部从磁盘读取一遍**。
2. **CPU 飙升**：如果开启了备份压缩（如 gzip/lz4），CPU 会高负载进行数据压缩。
3. **网络/存储打满**：备份数据在传输到 MinIO / S3 时会挤占网络带宽；如果直接存本地，则会引发磁盘写入竞争。

---

## 2. 生产环境如何防止"拖垮服务器"？

像 `pgBackRest` 这种专业的物理备份工具，本身就设计了完善的**限速与资源隔离机制**：

### ① 限制 I/O / 磁盘读写带宽 (Bandwidth Throttling)

最直接防止 I/O 打满的方法就是**给备份限制最大传输速率**。

- **`pgBackRest` 参数**：配置 `band-max-bytes` 参数（例如限制最大带宽为 `50MB/s`）。
- **效果**：哪怕服务器磁盘能读 1GB/s，备份工具也只会用 50MB/s 慢慢读取，把绝大多数 I/O 资源留给 PG 数据库响应业务请求。

### ② 控制并发线程数 (Process Max)

- `pgBackRest` 支持多线程并行备份（`process-max` 参数）。
- **优化策略**：如果服务器有 16 核 CPU，在业务高峰期备份时，可以把并发线程数限制在 **2 ~ 4 个**，避免 CPU 核心被压缩任务占满。

### ③ 业务低峰期执行（如凌晨 2 点）

- 配合 Cron 定时任务，将耗时较长的全量备份安排在**业务访问量最低的时间段**（如每周日凌晨 2:00 ~ 4:00）。

---

## 3. 大库（TB 级）的极限优化：磁盘快照备份 (Storage Snapshot)

如果你的数据库到了几 TB，用传统的 `pgBackRest` 读取全量文件可能需要跑好几个小时，此时业内会采用**物理云盘快照**方案：

```
1. pgBackRest / PG 命令  ──>  发出 pg_backup_start()（进入备份模式，标记一致性点）
2. 云厂商 / 存储阵列      ──>  触发磁盘快照 (Snapshot) —— 【仅需几秒钟即可完成！】
3. pgBackRest / PG 命令  ──>  发出 pg_backup_stop()（结束备份模式）
4. 后续处理              ──>  后台慢慢把这个快照异步挂载并推送到 MinIO，对原库完全无感
```

这种方案把全量备份对主库的影响降到了**秒级**，完全解决了大库全量备份耗时久、拖垮性能的问题。

---

## 总结

| 数据库规模 | 推荐的全量备份应对策略 |
| --- | --- |
| **小库 (< 100GB)** | 正常使用 `pgBackRest` 在业务低峰期（深夜）跑全量，基本无感。 |
| **中/大库 (100GB ~ 1TB)** | 使用 `pgBackRest`，同时设置 **`band-max-bytes` 限速** + **限制 CPU 线程数**，避免影响业务。 |
| **超大库 (> 1TB)** | 结合 **LVM / 云盘磁盘快照（Snapshot）**，秒级完成全量基线创建，彻底避免拖垮性能。 |
