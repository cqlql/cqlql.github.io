# 数据库备份与恢复策略 (v2.0 生产级规范)

## 1️⃣ 备份策略类型及区别

### 全量 + 增量（生产环境推荐）

- **形式**：`全量A + 增量B + 增量C + 增量D`
- **特点**：
  - 每次增量备份只保存自上次备份以来的变化。
  - 恢复时需要 **全量 + 所有增量链条**。
- **优点**：
  - 占用存储空间最小。
  - **关键点**：能配合 Binlog/WAL 日志实现精确到秒的 **时间点恢复（PITR）**。

### 全量 + 差异

- **形式**：`全量A + 差异D`
- **特点**：
  - 每次差异备份保存自上次 _全量_ 备份以来的变化。
  - 恢复仅需两份数据（全量 + 最新差异）。
- **缺点**：
  - 差异备份随时间增长会越来越大，占用空间较多。

## 2️⃣ 备份周期与保留策略

### 2.1 常规策略 (适用于 < 500GB 数据量)

- **每日全量备份**
  - 时间：业务低峰期（如 02:00）。
  - 保留周期：30 天。
- **每小时增量备份**（日志备份）
  - 备份 MySQL binlog / PostgreSQL WAL。
  - 保留周期：30 天。

### 2.2 大数据量优化策略 (适用于 TB 级数据量)

> _针对大数据量，每日全量会导致 I/O 压力过大，建议采用以下组合：_

- **每周全量**：周日 02:00。
- **每日差异**：周一至周六 02:00 (只备份自周日以来的变化)。
- **实时/每 10 分钟**：日志备份 (降低数据丢失风险)。

### 2.3 异地容灾 (3-2-1 原则)

- **3** 份数据副本（生产数据 + 本地备份 + 异地备份）。
- **2** 种存储介质（磁盘 + 对象存储/磁带）。
- **1** 个异地存储（云端 OSS/S3 或 异地机房）。

---

## 3️⃣ 日志的核心作用

- **本质**：增量备份通常就是日志备份 (MySQL Binlog / PG WAL)。
- **原则**：
  - **实时产生**：日志记录了所有修改操作。
  - **必须归档**：恢复时必须使用“已归档/备份”的日志文件。
  - **切勿直接使用运行日志**：恢复时应将日志文件复制出来，经过校验后再使用，避免破坏正在运行的现场。

## 🛡️ 4️⃣ 备份安全与防勒索 (新增核心)

仅有备份是不够的，必须确保备份文件 **不可篡改** 且 **不泄密**。

### 4.1 加密策略

- **传输加密**：备份上传至云端（OSS/S3）时，必须强制走 HTTPS/TLS 通道。
- **静态加密**：
  - **敏感数据**：包含用户信息、财务数据的备份，必须在本地打包时使用 `GPG` 或 `AES-256` 进行加密。
  - **密钥隔离**：解密密钥严禁与备份文件放在同一服务器，建议存储在密码管理工具 (1Password/Vault) 中。

### 4.2 防勒索机制 (WORM)

黑客攻入服务器后，通常会尝试删除所有本地和挂载的云端备份。

- **启用“对象锁定” (Object Lock)**：
  - 在云存储桶（AWS S3 / 阿里云 OSS）开启 **WORM (Write Once, Read Many)** 功能。
  - 设置锁定周期（如 30 天）。
  - **效果**：在锁定周期内，即使拥有最高管理员权限，也 **无法删除或修改** 备份文件。这是防御勒索病毒的最后一道防线。
- **版本控制**：开启云存储的版本控制，防止同名文件覆盖攻击。

## 🔄 5️⃣ 恢复策略 (修订版)

### 5.1 恢复黄金法则

> ⚠️ **严禁直接在生产库 (Master) 执行全量恢复！**
> 任何恢复操作必须先在 **隔离环境**（测试库或新建的临时实例）进行验证。

### 5.2 场景一：整库灾难恢复 (实例崩溃)

1. **准备环境**：启动一台新的空数据库实例（版本需一致）。
2. **全量恢复**：导入最近一次全量备份。
3. **日志回放**：应用增量日志（Binlog/WAL）至故障前一刻。
4. **业务切换**：
   - 验证数据无误后，修改应用连接字符串指向新实例。
   - 原实例保留现场用于后续排查。

### 5.3 场景二：误删数据/误操作恢复 (旁路恢复法)

_场景：某个用户误删了一张表，或更新错了字段，其他业务正常运行。_

- **❌ 错误做法**：直接在生产库回放日志或生成反向 SQL。
  - _风险：极易引发主键冲突、外键报错，导致二次故障。_
- **✅ 正确步骤 (旁路恢复)**：
  1. **搭建临时库**：利用备份，在另外一台机器/端口搭建一个 **临时实例**。
  2. **恢复至时间点**：将临时实例恢复到“误操作发生前”的状态。
  3. **导出所需数据**：
     - 确认临时库中的数据正确。
     - 仅导出误删的那张表或特定数据行（`mysqldump ... --tables table_name`）。
  4. **导入生产库**：
     - 将导出的 SQL 文件导入回生产环境。
     - 若涉及外键，需在事务中临时关闭外键检查。

### 5.4 场景三：业务级精准恢复 (审计表/快照)

_场景：仅需撤销特定用户的误操作，且不希望滚动整个数据库或搭建临时库。_

这是对底层备份的有力补充，通常需要在 **应用开发阶段** 提前设计：

- **实现方式**：
  - **审计表 (Audit Log)**：记录 `WHO, WHEN, DO WHAT, BEFORE, AFTER`。
  - **数据快照**：在执行关键变更前，应用逻辑自动将该行数据的 JSON 快照存入历史表。
- **恢复优势**：
  - **极速回滚**：直接通过业务后台或 SQL 脚本，根据快照执行反向更新（Undo）。
  - **零停机**：对其他用户和表完全无感知。
- **局限性**：
  - 会增加额外的存储开销和开发成本。
  - 无法应对“物理删库”或“表结构变更”级别的灾难。

> 🔹 **核心提醒**：请务必记住，数据库原生备份（全量+日志）仅能实现“时间点恢复”；若要实现“按用户/按单条记录”的秒级回滚，必须依赖此类**应用层审计方案**。

### 5.5 RTO 与 RPO 指标 (业务承诺)

- **RPO (允许丢多少数据)**：
  - 建议：$\le 1$ 小时（取决于增量备份频率，金融级建议缩短至 5-10 分钟）。
- **RTO (允许停机多久)**：
  - 误操作恢复：$\approx 2$ 小时（取决于搭建临时库的速度）。
  - 灾难全量恢复：取决于数据总量（TB 级数据可能需 4-6 小时以上）。

## 6️⃣ 总结与执行清单

1. **策略核心**：生产环境首选 **全量 + 增量 (Binlog)**，配合 **异地对象锁定存储**。
2. **安全底线**：备份必须 **加密** 且 **防删除 (WORM)**。
3. **恢复原则**：永远使用 **旁路恢复法** (Sidecar Restore)，禁止在生产库直接回滚。
4. **定期演练**：
   - **频率**：每月/每季度一次。
   - **内容**：不仅验证备份文件是否损坏，还要记录从下载到恢复完成的真实耗时 (RTO)，看是否符合业务预期。

## 💡 常见问答（FAQ）

**Q：使用云服务还需要备份吗？**
A：需要。云服务通常保障硬件可用性，但用户误删、应用层错误、配置错误或云端的逻辑错误/区域级灾难都需要备份与异地副本来应对。

**Q：增量备份就是日志吗？**
A：不是。增量备份是指数据块/文件的变化快照；事务日志是按事务记录的变更。两者可能同时使用但概念不同。

**Q：能仅靠 binlog/WAL 做恢复吗？**
A：原则上要实现 PITR 必须有基准备份（base backup）+ 完整的归档日志。仅靠日志若无 base backup 是不可行的。
