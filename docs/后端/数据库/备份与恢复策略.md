# 数据库备份与恢复策略

## 1️⃣ 备份策略类型及区别

### 全量 + 增量（推荐）

- 形式：`全量A + 增量B + 增量C + 增量D`
- 特点：
  - 每次增量备份只保存自上次备份以来的变化
  - 恢复时需要 **全量 + 所有增量**
- 优点：
  - 占用存储空间较小
  - 能配合日志实现时间点恢复（PITR）

### 全量 + 差异

- 形式：`全量A + 差异D`
- 特点：
  - 每次差异备份保存自上次全量备份以来的变化
  - 只有两份数据（全量 + 差异）
- 缺点：
  - 差异备份随时间增长可能会变大
  - 恢复速度较快，但存储效率不如增量备份

------

## 2️⃣ 备份策略示例

- **每日全量备份**
  - 时间：02:00
  - 保留周期：30 天
- **每小时增量备份**（日志备份）
  - 备份 MySQL binlog / PostgreSQL WAL
  - 保留周期：30 天
- **异地存储**
  - 每日备份上传到云端
  - 建议至少保留两地备份（本地 + 异地）
- **定期恢复演练**
  - 每月演练一次
  - 确保备份可用

### 💡 注意事项

- 即使使用云服务器，也需要备份数据
  - 云服务器仅保证硬件安全
  - 用户误删除 / 错误操作无法恢复时，需要依赖备份

------

## 3️⃣ 日志的作用

- **增量备份通常就是日志备份**
  - MySQL：binlog
  - PostgreSQL：WAL
- **实时产生，但必须归档 / 备份**
  - 写到本地和异地只是降低风险
  - 恢复时必须用“备份日志”（冻结 + 校验 + 可验证），不能直接用运行中的日志

------

## 4️⃣ 恢复策略

### 4.1 恢复到时间点（PITR）

- **步骤**：
  1. 恢复最近的全量备份
  2. 回放备份日志（增量 / Binlog / WAL）到目标时间点
- **注意**：
  - 日志必须完整且连续
  - 时间点稍微提前一点更安全
  - 恢复到最新状态理论上没问题，但要注意误操作可能被重演

### 4.2 恢复某个用户的某个操作点

#### 方式1：日志解析

1. 从 Binlog / WAL 定位该用户操作的 SQL
2. 生成反向 SQL（回滚操作）
3. 手工或脚本执行恢复

#### 方式2：操作日志 / 审计表

- 需提前设计
- 保存操作前后数据快照
- 恢复时直接回写或执行反向操作

> 🔹 注意：数据库原生备份和日志恢复 **只能做到时间点恢复，无法直接按用户或单条操作恢复**，必须依赖日志解析或审计表。

------

## 5️⃣ 总结

- **全量 + 增量** 是生产环境推荐方案，适合配合日志实现时间点恢复
- **备份日志必须归档 / 冻结 / 校验**，运行中的日志不能直接作为恢复依据
- **至少两地备份**（本地 + 异地）保证硬件和自然灾害安全
- **定期演练恢复**，确保备份可用
- **针对单用户操作恢复**，必须依赖日志解析或审计表
