        设计注记 · 为什么是「目录 + 详情」、实现时要守的红线（点开）
        
    
          
  • 本页的用处：把「一个组件目录 + 选中详情」的交互讲清楚，比读文档快；
            但它是交互速览（静态数据、不连远端），与 docs/components.md /
            docs/ui.md §13 同步维护，冲突时以文档判据为准。
            2026-11-07 起四个写动词全部已接入，状态补齐为
            missing / ok / update / degraded / unknown（外加 planned 占位），
            本页按实现口径写。
    • 
          
  • 为什么是目录 + 详情：以后还会加别的安装项，全塞一页会装不下；
            拆成 N 个导航页同样不解决 —— 窄屏横向 Menu 先撑不住，每个新页还得重复一套任务轮询。
            目录天然可增长，每屏只展开一个组件，导航项与页面数永远不变。
    • 
          
  • 注册表在 Go 侧，只有一份（已实现）：internal/component/registry.go
            的有序表声明 {ID, Name, Kind, Depends, Phase, OfflineImage, Verbs}；
            目录、依赖链、检查项与按钮顺序由它推导，写动词走 RunnableVerb
            （不声明 Verbs 的组件只给 install）、导入 tar 走 SupportsImage
            第二道白名单。
            本页 COMPONENTS 只是演示镜像；组件专属区块（离线镜像）按
            offline_image 条件渲染，不污染其它组件。
    • 
          
  • 依赖由拓扑推导（已实现）：上游未就绪时下游安装禁用；
            update / degraded 都算「已装」（ready = ok || update || degraded），
            unknown 一律禁用、不冒充「未安装」。卸上游 Docker 会连带停
            下游 MinIO，弹窗强警示且必须额外勾选（ack_downstream 必填，
            服务端 ValidateActionFlags 再验一次，见
            docs/components.md §8.3）。
    • 
          
  • 零跨页共享状态：目录 / 详情 / 依赖链 / 任务日志 / 配置摘要都在同一页；
            后台任务单实例互斥（并发 409），GET /api/components/task?after=
            增量日志全局一份，且与备份部署共用同一把任务锁。符合 docs/ui.md §7。
    • 
          
  • 六道门（已实现，四个写动词各一套）：POST +
            confirm=="yes" + 页面输 yes → 服务端先跑
            --dry-run → name 只认 servers.json（未知 404）、
            动词只认注册表白名单 + 附加参数门 → 密码只经 stdin（界面单次请求内存，
            弹窗里留空即走免密 sudo）→ 单任务 409 / 脱敏日志 →
            🔴 界面不开放 --force，删数据独立勾选且默认不勾。
            预检与正式动作带同一组附加参数（--proxy / --image-ref /
            --purge-data / --ack-downstream），
            否则「预检过了」不代表「正式动作会这么跑」。
            🔴 影响清单、能否执行、阻塞原因由 Go 侧 BuildActions 算，
            随 actions[id][] 下发，前端只渲染；本页 CONFIRM
            里的文案是演示用的静态数据（已按 Go 侧 impacts 抄平），不是实现。
    • 
          
  • 凭证绝不进二进制：deploy/component/** 整目录 //go:embed 编进 exe；
            root 凭证只从本机 backup/minio.env 的 DEST_KEY /
            DEST_SECRET 读，运行时注入远端脚本头部、用完 rm -f，
            不落脚本、不回显、不进日志（TestComponentScriptsHaveNoCredentials 挡回归）。
    • 
          
  • 更新 / 卸载已落地（2026-11-07）：CLI 有
            update / uninstall，界面按钮按后端动作计划启用。
            判据见 docs/components.md §8：更新只动一个组件、MinIO 换镜像保留
            /data/minio、失败回滚到原镜像标签 + 原容器配置且数据卷不参与；
            卸载默认只移除容器 / 包，数据 / 镜像 / 引擎一律保留，删数据独立勾选默认不勾
            （COMPONENT_PURGE_DATA=yes 分支才 rm -rf /data/minio）、
            卸引擎必勾连带影响；卸载后备份失败是预期结果，不许顺手改 crontab。
            update 态只由只读体检推导：Docker 看 apt 候选版本、
            MinIO 看已导入镜像里有没有与当前容器不同的标签，绝不在线查版本。
            「有新版本」是更新的独立门：两者正常时更新按钮禁用、只留卸载；
            MinIO 更新还要在弹窗里显式选目标镜像（actions[id].update.images
            白名单下拉，选中值作 --image-ref 回传，不悄悄挑一个）；
            degraded（已装但服务 / 容器不健康）算 ready，更新 / 卸载可当修复手段，
            unknown 仍一律禁用（docs/components.md §8.6）。
    • 
          
  • 现行 CLI（不是草案）：

    ops component list --server <name> [--json]                    # 只读体检 + 写动作计划
ops component install docker --server <name> [--proxy <http://host:port>] [--dry-run] [--password-stdin]
ops component install minio  --server <name> [--dry-run] [--password-stdin]
ops component update docker --server <name> [--proxy <http://host:port>] [--dry-run] [--password-stdin]
ops component update minio  --server <name> [--image-ref <已导入镜像:标签>] [--dry-run] [--password-stdin]
ops component uninstall docker --server <name> --ack-downstream [--dry-run] [--password-stdin]
ops component uninstall minio  --server <name> [--purge-data] [--dry-run] [--password-stdin]
ops component image-load minio --server <name> --image-tar <本机 .tar> [--dry-run]
    
            --server 只认清单里的 name；--proxy 只给
            install docker / update docker 用（两者都跑 apt），
            格式严格校验、只本次生效；MinIO 与卸载动作传了直接 400；
            --image-ref 只用于 update minio、且必须在体检采到的
            已导入镜像白名单里（省略时取第一个候选）；
            --purge-data 默认关、--ack-downstream 是卸引擎必填；
            --dry-run 绝不改远端。装 MinIO 时 /data 不存在会
            mkdir -p 并警告根分区（k4）。
    • 
          
  • 现行接口（不是草案）：GET /api/components/status?name=
            （含 actions 动作计划）、
            POST /api/components/run（{verb:"install"|"update"|"uninstall",
            component, name, confirm:"yes", password?, proxy?, image_ref?, purge_data?,
            ack_downstream?}，附加参数由服务端 ValidateActionFlags 再验）、
            POST /api/components/image（multipart，verb=image-load + image，
            服务端 os.CreateTemp、不接收本机路径）、
            GET /api/components/task?after=。全部要 token，写操作校验 Origin。
    • 
          
  • 构建顺序：改了 web/ 或 deploy/component/** 都要
            npm test && npm run typecheck && npm run build →
            go vet ./... && go test ./... && go build -o ops.exe .；
            或点界面「重启」勾「先重建」。改了脚本必须重建 exe，否则部署出去的还是旧脚本。
