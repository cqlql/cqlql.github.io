i 交互回归基线，不是运行中的界面：静态数据、不连真实远端、不发网络请求、不执行任何动作。 页面演示的是「只读预演 → 显式确认 → 执行 → 如实报告」，动作计划（能否执行 / 阻塞原因 / 影响清单 / 将执行的命令）由服务端下发、前端只渲染，原型里用静态对象投影。 ops backup once 与 mode=once 已注册并落地；实现与真机前置见 docs/backup-once.md §7，脚本本体见 docs/backup-scripts.md。 工具不读 crontab，手动成功会刷新心跳但不代表定时任务正常； 与恢复原型相反，这里的数据方向是「生产端 → 备份端」。

  • 为什么独立页（§2.2）：监控页纯只读，手动成功会改心跳，读与写混屏最易误读；
              部署页是一次性装机动作。本页复用 features/backup/ 的任务锁 / 六道门 /

  • 门禁照抄硬约束 21 并加码：confirm=yes、name 只认清单、组件白名单、
              不收 sudo 密码（root=false，弹窗没有密码框）、服务端预检门、
              单任务锁（并发 409）、任务脱离 HTTP、日志脱敏。详见分册 §3。
    • 
          
  • 预演不是执行凭证：点「预演」只给只读结果；服务端每次写动作前自己再跑一次

    • 
          
  • 撞锁 / 失败 / 超时都不是预演能挡住的（§4.1 / §4.4）：因此 locked、
              failed、timeout 三个场景的计划仍是 available=true，
              差异体现在运行期的日志与报告，不是前端重算按钮门。
    • 
          
  • 报告只报脚本结果：不写「备份体系正常 / 定时任务正常」，不把 status 的心跳当成功凭证；
              失败不自动重试、不自动清场、不改心跳；超时只能写「远端可能仍在执行」，不写「已取消」。
    • 
          
  • 影响清单逐条列出：PG 会新建 dump + globals + .sha256、按日期进分级目录、
              find -mtime -delete 清理旧备份；MinIO 会写 ~/.mc、
              必要时 mc mb、mc mirror --overwrite 覆盖同名对象（§4.3）。
