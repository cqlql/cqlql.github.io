网页面板重启自己（通用实现手册）

网页面板重启自己（通用实现手册）

状态：母本 · 现行（2026-11-06，从 pass-up.ops 与 infra/wsl-manager 两次实战提炼）

这份文档的用法：新项目要做「界面上一个按钮 → 一键重建 + 重启服务 → 页面自己回来」时， 把这一篇整份丢给 AI，让它按 §4–§8 施工、按 §10 落文件、按 §12 验收、按 §11 换常量。 不需要再去读那两个项目的源码。施工中报错先查 §9（坑）与 §13（症状速查）。

⚠️ 本文修订《桌面启动器与本地网页面板（通用实现手册）》§8 / §15 里 「不做自重建」的结论。那条结论的前提是「重建失败发生在隐藏进程里、无人看见」—— 本文用 §2 的三条硬约定解决它。不满足 §1.3 的前提时，仍应照母本「不做」， 并把「为什么不做」写进项目文档，别让后来的人以为点了重启会生效。

本文只写通用判据与可复制规格；项目常量（exe 名、端口、配置目录、构建命令）见 §11。

0. 一页速用

目标形态，五段交接，顺序不能换：

页面「重启」按钮 → POST /api/restart（confirm + rebuild）
  → [1] 服务端可选重建，产物落到 <tool>.next.exe（失败就地停，服务照旧在跑）
  → [2] 先回 200（显式 Content-Length）→ 拉起 __restart 接手进程（detached，输出进日志）
  → [3] 旧进程 shutdown（让出端口）→ exit 0（原守护随之结束）
  → [4] 接手：等端口空 → 把 next.exe 换到正式 exe → __takeover 同端口同 token 起服务
  → [5] 前端轮询 /api/health，boot_id 变了才 location.reload()

三句红线，先记住：

  1. 🔴 重建失败就地停。构建可能产出一个起不来的二进制，而交接之后没有回头路。
  2. 🔴 不换 token。前端 token 通常只在内存 + 地址栏；换掉之后轮询 health 会一直 401， boot_id 永远拿不到，界面会把一次成功的重启误报成失败。
  3. 🔴 判据只有 boot_id。交接失败时旧进程会刻意原地活着，那时「服务还在」与 「重启成功」在界面上完全一样；传输层失败也不是失败。

1. 适用与不适用

1.1 适用

  • 本机单二进制工具（Go / Rust / Node 打包均可），已有或想要一个 127.0.0.1 的 Web 面板。
  • 开发时反复改代码，需要「重建 → 重启」这条循环不再靠手工四步。
  • 平台是 Windows（本文的交接机制是 Windows 专属，见 §3）。

1.2 不适用（别硬套）

场景为什么该怎么做
服务端 / 多实例 / 有负载均衡没有「单个本机进程」可换走正常的滚动发布
前端产物由别的进程托管（独立 dev server）二进制里没有需要重建的嵌入产物只重启后端，构建交给前端工具链
无法写本机日志文件detached 进程没有控制台，启动失败原因会静默丢掉先补日志落点，见 §1.3
Linux / macOS那边有 syscall.Exec，同 PID 换映像更干净用 exec，不要照抄本文的接手进程

1.3 🔴 开工前必须满足的四个前提

缺任何一个，就别做，照母本 §8 保留「不做自重建」并在文档里写明理由。

前提缺了会怎样
构建输出能同时回 HTTP 响应并落日志重建失败在隐藏进程里无人看见 —— 这正是母本当初否决它的正当理由
有一个本机日志文件作为 detached 进程的输出落点新进程启动失败时只剩「连不上」，原因查不到
单实例凭据可复用（端口 + token 落盘，如 ui.json 0600）页面回来后 401，或新进程绑到别的端口
前端能读到「进程实例标识」（boot_id）只能按「服务还在」判，交接失败会被报成成功

2. 三条硬约定：当初「不做」的理由怎么被解决

母本 §8 的顾虑本文的对策不做会怎样
重建链路长、失败面大先重建、成功才交接；失败回 500 + 构建输出进响应构建出一个起不来的二进制，服务彻底没了
失败发生在隐藏进程、无人看见新进程 stdout/stderr 重定向到日志；确认弹窗显示日志路径启动失败原因静默丢掉，人只能对着「连不上」猜
链路长，人会懒得点、干脆不重启过期检测自动勾「先重建」；前端产物新鲜时跳过耗时的前端构建忘了勾 = 用旧二进制起来，症状是「我明明改了，界面怎么没变」

这三条互为前提：只做第一条（失败就地停）而不做第二条（日志落点）， 等于把「失败得看得见」换成了「失败得见得着、但成功失败都查不到」。

3. 机制选型：Windows 上没有 exec

机制平台评价
syscall.Exec（同 PID 换映像）Linux / macOS同终端、同 cwd/env，失败原因就在原终端里；但 Windows 没有
退出码 75 + exe.new 换身 + 启动器循环重拉Windows复用守护；代价是要改启动器（CRLF / ASCII 注释 / 隐藏窗口 pause 规则），多一处状态机
detached 接手进程 + 内部子命令（本文选它）Windows启动器一行不改；失败面收敛到「旧进程 / 接手进程」两处，日志同一份

为什么不用守护循环：启动器是这类工具里最脆的一层（批处理解析、代码页、隐藏窗口）， 让它承担「退出码 → 换文件 → 重拉」的状态机会把风险放到最不该放的地方。 独立接手进程只认三个参数，行为可单测。

Windows 上必须显式补 exec 免费给的两件事：

缺什么判据 / 做法漏了的症状
监听地址要先被让出来WaitPortFree(addr, 60s)：反复尝试 net.Listen(addr)，能绑上就是「可以接手」；不查 PID（会复用、会因权限查不到）新进程绑不上端口，界面「重启完连不上了」
新进程不能共享原控制台DETACHED_PROCESS + CREATE_NEW_PROCESS_GROUP；stdout/stderr 接日志文件关掉原窗口会把新服务一起带走；或输出静默丢掉

4. 代码分层与依赖方向

以 Go 为例（其它语言照搬职责划分）。依赖只许单向：

main → ui → restart → shared
模块职责不能做
internal/restart/纯机制：WaitPortFree / ReplaceBinary / Spawn / Rebuild / Check（过期判定）不反向 import ui；不含 HTTP、不含业务状态
internal/ui/restart.go三个接口、确认令牌、六道门、交接编排不自己实现重建命令
根包 restartchild.go接手子进程的入口（它要调 ui.CmdUI）放根包是为了不成环：restart 不能反向依赖 ui
web/src/features/system/确认弹窗 + restartFlow 判定纯函数判定逻辑不依赖 DOM / React，必须能脱离浏览器单测
internal/ui/ui.go内部标记 __takeover：同端口、复用 token、单例重试、不新开浏览器不生成新 token

平台差异用 build tag 拆：spawn_windows.go 实现 detached；spawn_other.go 明确报错 （「该能力只在 Windows 可用」），而不是用一套没验证过的 POSIX detach 假装能用。

内部标记不进注册表：__restart / __takeover 用下划线开头，不出现在 --help、 README、菜单的能力探测里；参数传错只能退出（它必须以服务身份起来，否则没人绑端口）。

5. 接口契约

三个接口，全部走现有 token 校验；写操作 POST 且校验 Origin。 字段名可按项目信封调整（本文用 {ok, data, error}），语义不能改。

5.1 GET /api/health

{ ok: true, data: { ok: true, boot_id: "<这个进程实例>" } }

boot_id 是进程级随机值（8 字节随机数，取不到退化成时间戳，绝不返回空串）。 不用 PID 代替：PID 会变，但「服务还在」与「重启成功」必须能分开。

5.2 GET /api/restart（确认视图）

字段类型用途
confirm_tokenstring绑「进程实例 + 端口 + token」；页面是上一个进程打开的就得 409
impactstring[]影响面原文，弹窗里逐条摊开。不用 Markdown 加粗：JSX 纯文本渲染会原样显示星号
build_commandstring[]「会跑：…」给人看，不是给人执行
binary_stale / stale_reasonbool / string前端据此自动勾「先重建」
log_pathstring启动失败原因只在这里
port / exe / exe_exists当前事实；exe 不在时没什么可重启
task_runningbool有长任务在跑时弹窗提前提示（真正的拦截在 POST）
notestring非空 = 现在不能重启（凭据读不到 / exe 不在），前端不给按钮

5.3 POST /api/restart

请求：{ "rebuild": true|false, "confirm": "sha256:…" }   // 只认这两个字段，多余的直接拒
200： { ok:true, data:{ restarting:true, rebuild, build_output, boot_id } }  // 显式 Content-Length
409： confirm 过期 / 长任务在跑 / 接手凭据读不到
500： 重建失败（服务照旧在跑）/ 拼响应失败（不交接）

请求体要读干净再往下走：socket 上还有未读数据时关闭会发 RST，可能让浏览器把 已经完整收到的响应也丢掉；而这次不会正常返回 handler。

5.4 六道门（服务端 enforce，前端只是交互）

#门理由
①confirm_token 绑「进程实例 + 端口 + token」，不一致 409页面是上一个实例打开时，刚才看到的那份对照已不成立
②会写外部状态的长任务在跑时 409 拒绝远端/数据库正在写，拦腰截断会留半状态（只提示「会中断」不够）
③重建按固定顺序执行，失败就地停、服务照旧在跑交接之后没有回头路
④接手进程复用 ui.json 的 port + token；令牌不进命令行换 token → 前端 401 → 成功被误报成失败；命令行参数在任务管理器里看得见
⑤响应必须显式 Content-Length；先回 200 再 Shutdown + 退出；拉起失败就不退出退出而新进程没起来 = 服务彻底没了，界面只会显示「连不上」
⑥判据只有 boot_id 变了；传输层失败不是失败；同路径换二进制必须拒绝见 §0 红线 3 与 §9 坑 5

不要求输 yes：重启是本机动作（不碰远端），二次确认弹窗已把影响面逐条摊开。 给主路径多加一次输入，只会让人更少用它。远端的写操作才需要 yes + 服务端预检。

6. 交接链路（顺序与判据）

[HTTP handler]
  1. 校验 confirm / 任务门 / 凭据可读性
  2. 可选 Rebuild（context.Background()，禁用 r.Context()：请求会断，构建要 30~40 秒）
  3. 留痕（交接之后这个进程就没了，日志必须写在前面）
  4. 自己 json.Marshal + 显式 Content-Length + WriteHeader(200) + Write + Flush
  5. sleep ~500ms（让浏览器开始轮询 health）
  6. Spawn(接手进程)  ← 失败：只记日志、return，**不退出**、不写第二个响应体
  7. srv.Shutdown(ctx, 3s)（关监听，把端口让给接手进程）
  8. exit(0)

[接手进程 __restart <addr> <targetExe> <newExe|->]
  1. WaitPortFree(addr, 60s)
  2. newExe != "-" → ReplaceBinary(newExe, targetExe)
     ⚠️ 换不上**不是致命**：如实记日志，继续用现有二进制起服务
  3. 以 __takeover --port <addr 的端口> 启动服务（从 ui.json 读 token）

接手进程的三个参数含义（混填是最隐蔽的一类 bug）：

参数含义
<addr>等它空出来 = 旧进程已让位的唯一信号
<targetExe>ReplaceBinary 的目标（正式 exe），不是「从哪个文件起来」
<newExe｜->重建产物；- 表示没重建（此时不跑 ReplaceBinary）

「从哪个文件起来」是第四个隐含值：重建过就从 next.exe 起，否则从正式 exe 起。 把两者混填会让 ReplaceBinary 变成 next.exe → next.exe 的空操作， 表面成功、正式 exe 永远停在旧版本，而日志照样写着「新二进制已就位」。

为什么响应必须显式 Content-Length：Go 在 handler 返回之前 Flush 会退化成 chunked， 而结束块（0\r\n\r\n）要等 handler 返回才写 —— 可下一步就退出进程了，那个结束块 永远发不出去。客户端收到的是截断报文（Failed to fetch）， 于是「重启明明成功了，界面上却报失败」。

为什么先拉起再 Shutdown：反过来接手进程要干等，而这段时间端口还占着。 __takeover 里还要带重试拿单实例锁（见 §9 坑 2）。

7. 重建：顺序、超时、产物命名、过期判定

7.1 顺序（前端 → 后端，因为产物被 embed 进二进制）

步命令说明
1npm install（仅依赖缺失时）冷启动兜底
2npm test测试目录常故意不在 tsconfig.include 里，类型错误只能靠跑一遍发现
3npm run typecheck同上
4npm run build生成前端产物
5go build -o <tool>.next.exe .把新产物 embed 进去
  • 每步都有超时上界（300s）：一次卡住的构建会把「正在重建」状态锁死，界面上连按钮都点不动。
  • npm 只在前端真的过期或依赖缺失时跑：写死每次都跑会白等 30~40 秒，代价会让人干脆不点重启。
  • 产物落在 <tool>.next.exe：正在运行的 exe 被 Windows 锁着，直接 build -o <tool>.exe 只会拿到一句毫无信息量的 sharing violation。旧进程退出后由接手进程改名换上去。
  • 回读确认产物存在：「命令没报错」≠「真的产出了新二进制」。
  • 源码不在 exe 同目录时明确失败：在一个只有 exe 的目录里「构建成功」是最坏的假话。

7.2 命令拼装（踩过两次的坑）

规则原因
name 与 args 分开传，绝不自己拼命令行字符串Go 的 exec 在 Windows 按 CommandLineToArgvW 组装/转义，而 cmd.exe 不按那套解析；含空格的 go.exe 路径（默认就在 C:\Program Files\Go\）必然坏掉，症状是 'C:\Program' 不是内部或外部命令，看起来像「go 没装」
后端构建命令直接 exec，不经 cmd.exe同上，加多少引号都救不回来
只有 npm（.cmd）需要 cmd.exe /d /cWindows 上直接 exec 一个 .cmd 在各版本 Go 上行为不稳；/d 是不要执行 AutoRun
构建窗口隐藏（CREATE_NO_WINDOW）构建那几十秒里不该一直有个黑框
输出合并、只回传末尾 60 行失败原因总在最后；几百行进 HTTP 响应没意义

7.3 过期检测（Check）只有一份实现

两条判据：前端源码比前端产物新（或产物不存在）→ 需要前端重建； 后端源码或前端产物比 exe 新 → 需要后端重编。

🔴 前端产物本身也算后端输入：它被 embed 进二进制。漏掉它就会出现 「前端重建了但没重编 Go，界面看着变了、其实跑的是旧后端」。 🔴 所有 embed 输入目录都要算（例：备份脚本、模板、静态资源目录）， 漏一个就是「脚本改了、部署出去还是旧的」。

运行态文件一律排除（*.exe / *.exe~ / *.log / *.env / servers.json / ui.json / node_modules / .git / IDE 目录）：否则「先重建」会永远勾着 —— 一个永远为真的告警等于没有告警。

基线文件拿不到 = 过期，不是「不知道」：没有产物可谈，谈不上新鲜；理由里写明 是哪个文件不存在，界面才说得清要重建什么。

8. 前端：判定纯函数与确认弹窗

8.1 判定必须与渲染分离

把下面三个函数放进不依赖 DOM / React 的模块（例：restartFlow.ts）， 这样 node --test 之类能直接跑，不用起浏览器。它们守的是「两种失败长得很像」：

交接成功交接失败
响应可能丢掉，boot_id 会变响应同样可能丢掉，boot_id 永远不变
函数规则
defaultRebuild(info)info.binary_stale === true。写死 true 白等几十秒；写死 false 会用旧二进制起来
judgeHandover(before, after)after === before → unchanged；after 非空且不同 → restarted；before 为空、after 为空/null → unknown
timeoutMessage(info, seconds)必须带上日志路径：失败原因只在那里
shouldRefreshView(status)409 / 500 后重新拉一次视图，否则下次点「执行」还拿旧 confirm_token

🔴 unknown 不许显示成成功或失败：拿不到重启前的 boot_id 只能说「没法确认」； 重启期间连接断几秒是「还没到」，不是结论。

8.2 请求与轮询

1. before = (await health()).boot_id        // 读不到 → ''，如实退化成「没法确认」
2. POST /api/restart
   - 只有 ApiError（服务端明确回 JSON 错误）才说明它没动手 → 提示 + 刷新视图
   - 传输层异常（Failed to fetch / 连接被重置）→ 忽略，转去等 boot_id
3. 每 1s 轮询 health，直到 boot_id 变了 → location.reload()
4. 上界 120s；超时报「看起来没重启成功」+ 日志路径，构建输出打到 console

8.3 弹窗与按钮

元素要求
标题「重启 <工具名>？」/「重建并重启 <工具名>？」
顶部一句说清「重启后沿用当前端口与访问令牌，页面自动回来」
影响面impact 逐条 <li> 摊开：会中断什么、重建失败会怎样、Windows 没有 exec、日志在哪、按 boot_id 判断
「先重建」复选框默认值来自 defaultRebuild；只在第一次拿到事实时设一次，之后别覆盖用户的手动选择
过期提示binary_stale 时警告「不重建的话跑的还是旧代码」，并给出 stale_reason
会跑什么build_command 逐条列出
日志路径log_path 明写出来
执行按钮危险色（danger），文案「执行」；点完就关弹窗，让全局 loading 与消息承担等待，别让弹窗挂 120 秒

按钮放全局工具栏（不是某一页的头部）：它是对服务本身的动作，与当前看哪一页无关； 改完前端就该在当前页直接重启。工具栏不随页面卸载，轮询不会被切页打断。

⚠️ 弹窗必须走 App 上下文（App.useApp() 的 modal / message），不要用静态方法： antd v6 + React 19 下静态方法渲染到独立 React root、拿不到主题，真机表现为 「点了按钮，什么都没发生」。

9. 十二个坑（都是实测踩过的）

#症状根因修法
1重启后页面一直转圈，最后报「没重启成功」，但服务是新的新进程换了 token，前端轮询 health 一直 401__takeover 从 ui.json 复用 port + token；GET /api/restart 先校验凭据可读且与当前一致
2重启后「服务还在」，其实是旧进程；日志里接手进程只开了个浏览器命名互斥体要等旧进程 exit 才由内核释放，而 WaitPortFree 只看端口（关监听在 exit 之前），两者差几毫秒接手进程带重试拿锁（8s 上界）；拿不到就如实失败，不要走「已有实例 → 只开浏览器」那条路
3重启成功了，界面却报 Failed to fetchhandler 返回前 Flush 退化成 chunked，结束块随进程退出永远发不出去自己序列化 + 显式 Content-Length
4'C:\Program' 不是内部或外部命令，看起来像 go 没装把含空格的 go 路径拼进 cmd.exe /c 字符串；加引号也没用（转义规则不同）name 与 args 分开传；后端构建直接 exec，只有 npm.cmd 走 cmd.exe /d /c
5日志写着「新二进制已就位」，正式 exe 却永远是旧的ReplaceBinary(new, target) 里 new == target，os.Rename 做了空操作却报成功同路径必须拒绝；「从哪个文件起来」与「换到哪个文件」分开两个值传
6第一次「带重建」成功后，第二次不重建的重启报「文件被删了」Windows 上 os.Executable() 返回进程映像加载时的路径：从 next.exe 起来、改名成正式 exe 后仍返回 next.exeTargetExe() 走按后缀的 NormalizeExePath（.next.exe → .exe）；按文件名判，不靠探测文件在不在
7改了脚本 / 前端，重启后跑的还是旧的过期检测只算了 *.go，漏掉 embed 输入目录与前端产物白名单含所有 embed 输入 + 前端产物/index.html
8「先重建」永远勾着运行态文件（*.exe~ / *.log / ui.json / node_modules）被算成源码白名单 + prune，运行态文件一律排除
9交接后服务彻底没了，日志里什么都没有detached 进程没有控制台可写，启动失败原因静默丢掉Spawn 把 stdout/stderr 接日志文件；界面显示路径
10重启成功两秒后服务又没了新进程共享父进程控制台，关窗口的 CTRL_CLOSE_EVENT 把它一起带走DETACHED_PROCESS + CREATE_NEW_PROCESS_GROUP
11影响面文案里出现字面量 **加粗**文案直接塞进 JSX 当纯文本渲染要强调就换措辞，不写 Markdown
12明明回了 200，浏览器却说响应丢了请求体没读干净就关连接，socket 上残留数据触发 RSTio.Copy(io.Discard, r.Body) 再往下走

11. 换项目只改这些

#常量 / 位置本手册示例换项目时要确认
1正式 exe / 重建产物ops.exe / ops.next.exe名字与后缀；.gitignore 要忽略 *.exe
2内部子命令名__restart / __takeover保持下划线开头，别进注册表
3配置目录与凭据文件%APPDATA%\pass-up\ui.json（0600，port + token）覆盖变量；GET /api/restart 要能校验它
4日志文件ops-ui.log（追加 + 轮转上限）detached 进程与后台守护共用一份打开逻辑
5默认端口 / 递增上限7788 / 20与同机其它工具错开
6单实例名Local\<vendor>-<tool>-ui-<hash>名字带配置目录指纹；接手要重试拿锁
7构建命令npm test / typecheck / build → go build -o …next.exe .换成该项目的真实构建链；test/ 是否在 tsc include 里
8embed 输入deploy/backup/**、web/dist/index.html逐个列全，漏一个就是隐性过期
9长任务判据backupBusy()换成「会写外部状态的任务」的判定函数
10HTTP 信封 / token 头{ok,data,error} / X-Ops-Token前端 request() 与后端 writeAPI 对齐
11影响面文案5 条按项目改「会中断什么」「日志在哪」，别照抄
12等新进程上界120s冷启动慢的机器要放宽

落地顺序：restart 机制 + 过期判定 → 三个接口 + 六道门 → __restart 子进程 + __takeover 复用凭据 → 前端判定纯函数 + 弹窗 + 工具栏 → 文档与红线 → 测试矩阵 → 真机真跑。

🔴 每一步都要能回答「失败了会怎样」。这整条链路最怕的不是报错， 是「看起来正常」：日志写着成功、页面也能连上，但跑的是旧二进制或旧进程。

12. 测试与验收

12.1 自动（CI 能跑，不真起进程、不碰真配置）

测试点断言什么
WaitPortFree端口空了立即返回；被占时超时并说清「仍占着」
ReplaceBinary覆盖目标成功；同路径拒绝；产物不存在时给出可记进日志的原因（非致命）
NormalizeExePath / TargetExe.next.exe → .exe；正式 exe 原样返回；空路径返回空
Check（过期）前端源码过期、后端源码过期、embed 输入过期、前端产物比 exe 新；运行态文件不触发；产物缺失判为过期
Rebuild顺序对（前端四步 → 后端构建）；前端新鲜时跳过 npm；任一步失败立即停、不继续 go build；源码根缺失时明确拒绝
确认令牌同实例稳定；换实例 / 换端口后失效
六道门错 confirm 409、任务在跑 409、凭据读不到 409、重建失败 500 且不交接/不退出
交接参数重建过从 next.exe 起；不重建从正式 exe 起且 newExe == "-"；正式 exe 与「换到哪」是两个值
响应显式 Content-Length；boot_id 是重启前的那个
Spawn 失败200 已写出、进程不退出、不写第二个响应体
单例重试前几次拿不到锁最终成功 → 不判失败；一直拿不到 → 如实失败
前端判定defaultRebuild / judgeHandover 真值表 / 超时文案带日志路径 / 409-500 后刷新视图

12.2 覆盖变量下的真跑（用临时配置目录 + 独立端口，不写真配置、不碰真远端）

  1. 起界面：配置目录覆盖变量指到临时目录，显式 --port 绑一个空闲端口，--no-open。
  2. GET /api/health 记下 before.boot_id；GET /api/restart 核对 note 为空、影响面 5 条、日志路径。
  3. 触发过期：touch 一个前端源文件 → 再取一次视图，应得 binary_stale=true 且 build_command 列出完整前端构建链（这一步同时验证「自动勾先重建」）。
  4. POST /api/restart 带 rebuild=true → 应拿得到完整 200（含 build_output）， 不要因为传输层异常就判失败。
  5. 轮询 health 直到 boot_id 变化；核对正式 exe 的 mtime 变了、next.exe 已不在、 日志里有「等端口让出来 → 新二进制已就位 → 沿用原令牌」。
  6. 再点一次 rebuild=false：只换进程、日志里没有 ReplaceBinary，boot_id 再次变化。
  7. 用错 confirm 发一次 → 409，之后 health 仍 200（服务没被动过）。
  8. 收尾用项目自己的「关闭界面」停掉验证进程，别留后台进程。

12.3 真机人工（Windows，逐条打勾）

  • [ ] 浏览器里点「重启」→ 弹窗逐条列出影响面、复选框、构建命令、日志路径。
  • [ ] 勾「先重建」→ 页面断连几秒后自己回来，不用重新复制地址、不用重新双击启动器。
  • [ ] 不勾「先重建」→ 同样能回来，且 exe 的 mtime 不变。
  • [ ] 故意让构建失败（例如临时改坏一个 .ts）→ 提示「重建失败、服务照旧在跑」，页面仍在。
  • [ ] 备份/部署类长任务在跑时点「重启」→ 被拒绝并说明原因。
  • [ ] 前端产物里确认工具栏样式与弹窗文案；无头浏览器截图核对布局与按钮不是 disabled。
  • [ ] 原标签页的 token 若因重启流程之外的操作换过，重新双击启动器能打开带新 token 的地址。

14. 决策与备选

决策备选为什么选这个
修订母本 §8/§15，做自重建继续「不做，手动 build」当初的顾虑（失败无人看见）被 §2 三条硬约定解决；链路长的问题由自动勾重建 + 前端新鲜跳过 npm 解决。前提不满足时仍不做
detached 接手进程退出码 75 + .new 换身 + 启动器循环启动器是最脆的一层（批处理解析 / 代码页 / 隐藏窗口 pause），不该再塞一个换身状态机；.cmd 一行不改
复用 ui.json 的 token每次进程生成新 token前端 token 没落盘，换了就 401，成功会被误报成失败
令牌从 0600 文件读，不进命令行当 argv 传给子进程命令行参数在任务管理器里看得见
单例互斥体带重试拿不到就判「已有实例」关监听在 exit 之前，锁晚几毫秒释放；误判会只开浏览器、服务却没起来
boot_id 作唯一判据按「服务还在」/「请求成功」交接失败时前者同样成立；后者在响应丢失时必然误报
传输层失败不算失败任何异常都报失败服务端先回 200 再退出，连接切断是预期形态
重建失败就地停失败也重启 / 带旧二进制重启后者会把「构建坏了」变成「服务没了」
备份类长任务在跑时 409 拒绝只提示「会中断」远端/数据库正在写，截断会留半状态
过期检测只有一份实现重启一份、手工构建一份两份会漂移成「重启说要重建、手工说不用」
自动勾「先重建」默认勾 / 默认不勾默认勾每次白等；默认不勾会用旧二进制起来
二次确认但不输 yes沿用远端写操作的 yes重启是本机动作；多一次输入只会让人更少用它
next.exe + 旧进程退出后改名直接 build -o <tool>.exe正在运行的 exe 被 Windows 锁着，覆盖只会拿到 sharing violation
非 Windows 明确报错用 POSIX detach 假装能用没验证过的「看起来能用」比明确失败更坏
全局顶部工具栏某个页面的头部对服务本身的动作，与当前页无关；不随页面卸载，轮询不中断
