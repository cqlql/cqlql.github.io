代码验证规范（母本）

代码验证规范（母本）

状态：母本 · 现行（2026-11-18 起草；同日打通与《代码设计规范》§十、§十一 的双向指针； 同日二次修订：§10.2 / §10.4 按 L1~L4 分档，取消「六步缺一不可」的无条件要求 —— 原写法与 §零 第 2 条冲突， 实际效果是让改 DTO 也走全流程）

AI 执行版：skills/repo-bootstrap/references/code-validation.md（可移植副本）； 本文件仍是母本，改判据先改这里，再同步 skill 与各仓实例。

本文件是通用条款的母本。各仓的 docs/code-validation.md 是实例：通用条款以本文件为准， 实例只允许追加本仓的工具、命令、环境与专项场景（见 §十一）。 改通用条款 → 改这里 → 再逐仓同步实例。不要反向：先改某个仓、再指望别的仓知道。

适用栈：节标题后的 〔后端〕 标明该节只适用后端仓，无标记 = 全栈通用。 本文作为母本保留全部节；建实例时按目标仓裁掉不匹配的节。

本文管什么：改完代码后，用什么手段、验到什么深度、拿什么当证据，才算「这件事做完了」。

本文不管的四件事（各有专文，别在这里重复）：

  • 代码应该怎么设计（职责、状态机、事务、抽象）→
  • 数据访问层怎么验证（EXPLAIN、查询次数、索引前后对比、数据规模、批量档位）→ §六
  • 文件放哪、依赖往哪指 →
  • 本仓怎么跑、跑哪些命令 → 各仓 AGENTS.md 的「构建、冒烟与验证」节 + 实例的工具映射表

起因：一份「禁止 N+1、禁止 SELECT *」的清单被逐条执行完，交付说明写着「已优化」， 但查询次数一次都没统计；另一个仓的「已完成」，事后发现只跑了 compile。

一句话：规范说应该怎么做，测试说实际做得怎么样，验证证据决定能不能认为任务完成。

零、五条元规则（优先级高于下面所有条款）

  1. 结果优先于形式：代码符合规范 ≠ 代码正确；工具没报错 ≠ 没有问题。
  2. 风险决定深度：改 DTO 字段和改退款扣权益，不能用同一套验证标准（§二）。
  3. 先定预期，再选手段：先写清「要证明哪几条行为」，再决定用单测、集成、压测还是人工验证。
  4. 证据优先于自述：读代码、跑静态分析、AI 自我评价，都不算验证；能贴出命令与输出的才算。
  5. 诚实报告：没执行不能说通过；验证不了要说「受阻」并写清卡在哪（§十）。

第 1、2 条的直接推论：本文任何一条都不构成「每次提交都要执行」。 真正「必须验证」的只有一件事——你声称已经正确的那部分行为。

一、验证看什么：六个维度

维度要证明什么主要手段常见假验证
正确性业务行为、边界、异常符合预期单测、集成、回归只断言「没抛异常」
一致性事务、状态、数据在成功与失败后都对真库集成 + 断言最终状态只断言接口返回码
稳定性并发、重放、资源释放、故障恢复可靠并发测试、重复请求、故障注入顺序循环调 100 次当并发
性能耗时、吞吐、内存满足目标benchmark、profiler、压测用平均响应时间下结论
安全性认证、授权、输入、敏感信息可靠越权用例、输入用例、依赖扫描扫一遍工具就当安全
可维护性没有引入多余复杂度与重复规则代码审查用复杂度数字代替审查

维度不能互相顶替：单测全绿证明不了并发安全；压测 P99 达标证明不了权限没漏。 按改动实际触及的维度选验证项，没触及的写「不适用」，不要静默跳过。

二、定级：改什么，验到什么程度

2.1 定级三问

按顺序问，命中越靠后等级越高：

  1. 动了钱、权益、权限、用户数据吗？→ 至少 L3
  2. 动了并发、事务、状态转换、幂等、消息消费吗？→ 至少 L3
  3. 动了高频路径、核心接口、架构或性能关键点吗？→ L3 起步，通常到 L4
  4. 都不沾（DTO、展示字段、纯工具方法）→ L1~L2

补充信号（不单独定级，但往上抬一档）：跨模块改动、外部依赖变更、历史出过故障的代码、影响面说不清。

2.2 四级

等级适用至少要做明确不必做
L1 基础DTO、字段映射、纯函数工具编译 / 类型检查 + 相关单测 + 自审 diff集成、压测
L2 功能一般业务逻辑、参数校验L1 + 正常路径 + 边界 + 异常路径 + 相关回归并发、profiler
L3 关键资金、权益、权限、状态机、事务、幂等、跨模块协作L2 + 真组件集成 + 并发/重复请求 + 事务提交与回滚 + 数据一致性断言全链路压测（除非同时命中 L4）
L4 性能/系统高频接口、性能优化、架构调整L3 适用项 + benchmark 或 profiler + 压测 + 资源分析 +（必要时）故障注入——

等级是下限，不是清单：L3 里的「并发测试」在只读查询上不适用，写「不适用 + 理由」不算降级。 等级不是工具数量：给 L1 改动堆五个工具跑一遍，不叫验证到位。

2.3 定级反例（AI 最容易犯的两头错）

表现为什么错
改了个 DTO，去写微基准、跑压测花掉时间，没有提高任何结论的可信度
改了退款状态机，compile 过就交付编译能过，恰恰说明不了并发下的正确性
「我写了 12 个测试」当成交付证据数量与风险覆盖无关，要说覆盖了哪条行为
只在 mock 环境跑通 →「数据库并发安全」mock 里没有事务、没有唯一约束、没有行锁
把 L4 流程套到所有改动上成本高到没人执行，最后全部被跳过

三、正确性

3.1 单元测试：验证规则，不验证实现

覆盖优先级：正常输入 → 边界与空值 → 非法输入 → 状态转换是否合法 → 异常是否按预期处理 → 计算结果。

  • 断言外部可观察的行为（返回值、业务异常、落库结果），不要断言「内部调了哪个方法、调了几次」—— 这类测试会在合理重构时集体变红，然后被整批删掉。
  • 一条用例一个「失败时能定位」的理由。isEqualTo(expected) 比 assertNotNull(result) 有用一百倍。
  • 一个测试里堆五个断言、失败时不知道断在哪，比拆成五条用例更贵。

3.2 集成测试：多组件协作必须用真组件

场景用什么不能用什么
Service ↔ Repository真库（Testcontainers / 本地实例）mock Repository
事务提交、回滚、隔离级别真库 + 断言事务后的数据内存库（方言与锁行为不同）
唯一约束、外键、CHECK真库 + 故意撞键mock
Redis 与 DB 协作、缓存失效真 Redis假缓存实现
消息生产/消费、重投真 broker 或官方测试容器直接调 listener 方法
序列化/反序列化、外部适配真实报文样本（含异常报文）只测 happy path

🔴 涉及事务、唯一约束、锁、并发行为时，mock 出来的「通过」不算证据。 这条决定了「并发安全」四个字能不能写进交付说明，是本文最硬的一条。

前端仓把上表换成「组件测试 + 真接口 / 真机」两项，判据不变：你要证明的那一层不许 mock。

3.3 回归：先找「谁会受影响」

改之前先回答：这段行为的调用方有谁？共用这张表 / 这个状态的还有谁？前端有没有复制同一份规则？

  • 已有正常流程、异常流程、状态转换是否仍然成立；
  • 对外接口、响应字段、错误码有没有非预期变化；
  • 前后端各写一份的公式 / 枚举是否同步（这类漂移只能靠用例抓，靠读代码抓不住）。

发现关键行为没有任何测试保护时，补一条最小用例比写一句「已人工确认」值钱。

3.4 测试质量的红线

  • 🔴 不许为了让测试变绿去改预期值。预期错了 → 改预期并写明理由；代码错了 → 改代码。
  • 🔴 不许删掉失败的测试。确实不再适用的，说明原因并留下替代用例。
  • 不许「只验证没抛异常」就认定业务正确（assertDoesNotThrow 不是业务断言）。
  • 不许把被测逻辑 mock 掉再断言「它被调用过」——那是测 mock。
  • 用例之间尽量独立；依赖执行顺序的测试最终会随机变红。
  • 测试数据要有代表性：只有 1 条记录的库，证明不了分页和 N+1。

四、并发与一致性（钱 / 权益类最高优先级）〔后端〕

4.1 八项必查

  1. 同一资源被并发操作时，会不会执行两次（重复发放、重复扣减、重复发消息）；
  2. 有没有超扣 / 覆盖写 / 丢更新；
  3. 条件更新是否真的原子（判断影响行数，而不是先查后写）；
  4. 唯一约束能否在数据库层挡住重复（不是只在代码里 if 一下）；
  5. 事务回滚后，数据是否干净（没有半成品、没有残留状态）；
  6. 分段事务中间失败，能否靠重试或补偿收敛；
  7. 幂等在重复、并发、重启后重放三种情况下是否都成立；
  8. 有没有死锁、竞态、连接池耗尽。

4.2 怎么测（可操作，不是「注意并发」）

要证明做法断言什么
原子抢占N 个线程（N ≥ 10）同时推进同一笔单据最终 DB 状态：只有 1 条推进成功，其余拿到可识别的失败
唯一约束兜底并发插入同一业务键1 成功 + N-1 抛约束冲突，且异常被翻译成业务结果
幂等同一请求连发 → 再并发连发 → 重启后重放权益/流水只有一份，返回值一致
事务回滚在事务末尾制造异常业务表、流水表、余额都没变，不只断言异常类型
分段补偿人为让第二段失败重试/补偿后数据收敛，对账能发现中间态
死锁两个线程反向加锁顺序有重试或明确失败语义，不出现长时间挂死

🔴 并发测试必须检查最终数据库状态，不能只看接口返回值—— 返回值一致而库里多了一条，是最典型的资损形态。 🔴 必须用真实数据库。内存库的锁、隔离级别、约束行为与生产不同，测出来的「通过」不可迁移。

4.3 自动化不了的，写人工步骤

故障注入、真实回调重放、跨环境切换这类场景允许人工验证，但必须留下： 操作步骤 + 预期现象 + 实际结果 + 剩余风险。只写「已人工验证」等于没验。

五、性能

边界：数据访问层的性能验证（EXPLAIN、查询次数、索引前后对比、批量档位、数据规模） 在 §六，本文不重复。本节管语言层与系统层。

5.1 三条原则

  1. 不凭代码形态判断性能：循环嵌套、行数、写法都不构成性能结论，只有测量构成。
  2. 先测再优化：没有证据的「提前优化」通常优化错了地方，还额外欠下维护成本。
  3. 同条件对比：优化前后用相同环境、相同数据规模、相同并发；换条件比出来的倍数没有意义。

5.2 三个层次，别混用

手段回答什么不能回答什么
Benchmark（微基准）某个方法/算法的耗时、内存分配、随数据规模的变化接口性能、端到端延迟
Profiler（剖析）CPU 热点、GC、锁竞争、阻塞调用、调用栈耗时「优化后快了多少」（它是定位工具，不是验收工具）
压测（负载测试）目标负载下的 P95/P99、吞吐、错误率、资源水位单个方法为什么慢

🔴 微基准不能等同于接口性能：测的是几十纳秒的方法，接口里大部分时间在 IO 与序列化上。 微基准本身也有陷阱——要预热、要多次迭代、要防死代码消除、要控制 GC 干扰。 用 nanoTime() 随手包一圈得到的数字，不要写进报告。

5.3 压测看什么

指标用途
P50 / P95 / P99用户体验与长尾；只看平均值会掩盖长尾
Throughput单位时间处理量，是否随并发增长到拐点
Error Rate失败率（含超时、5xx、业务失败）
CPU / Memory是否饱和；内存是否随时间单调增长（泄漏信号）
连接池 / 线程池 / 队列是否耗尽、是否积压

结论要能回答：并发到多少、P99 多少、错误率多少、瓶颈在哪一环。「压测通过」不是结论。

5.4 性能结论的证据要求

性能类结论必须带：优化前数字 → 优化后数字 → 环境与数据规模 → 并发与负载 → 是否引入额外复杂度。

🔴 禁止「已优化」「明显变快」「性能大幅提升」这类没有数字的说法 （同 §6.7）。 拿不到对比数据时，写「只做了 X，未做前后对比，依据是 Y」——把推测标成推测，而不是标成结论。

六、安全性

6.1 什么时候必须查

认证与登录态、权限与角色、用户数据读写、文件上传下载、外部输入（含 header / 回调 body）、 第三方回调与验签、反序列化、依赖升级。

6.2 检查清单

  • 水平越权：拿 A 的身份访问 B 的资源 id（列表、详情、导出、下载、修改都要试）；
  • 垂直越权：低权限账号调高权限接口（「前端没入口」不算防护）；
  • 注入：SQL / 命令 / 模板 / 日志注入（拼接字符串、exec、动态表名与排序字段）；
  • 敏感信息：响应体、日志、异常堆栈里有没有手机号、证件号、Token、密钥；
  • 回调真实性：签名、时间戳、重放窗口是否校验，能否重放；
  • 不可信反序列化：外部 JSON 直接映射到带行为的对象、原生反序列化；
  • 文件：路径穿越（../）、类型伪造、大小限制、下载鉴权；
  • 依赖：已知 CVE（升级，或明确记录风险接受）；
  • 错误信息：是否把堆栈、SQL、内部路径返回给调用方。

6.3 手段与红线

按风险选：静态安全扫描 → 依赖漏洞扫描 → 权限边界用例（双侧）→ 针对性渗透。

🔴 工具没报 ≠ 没有漏洞。扫描器不懂你的业务权限模型，越权只能靠用例证明。 🔴 权限用例必须断言「拒绝」：只测「管理员能访问」等于没测权限。

七、静态分析与代码审查

7.1 静态分析能发现什么

不需要运行就能看出的问题：空指针路径、资源未关闭、可疑 catch、未使用代码、复杂度异常、 重复代码、已知不安全 API、部分安全问题。

它发现不了：业务规则错、并发竞态、事务边界错、权限漏、性能瓶颈、需求理解错。 所以它是筛子，不是结论。

7.2 警告怎么处理

  • 新增代码引入的警告 → 本次处理（修，或显式抑制并写理由）。
  • 存量警告 → 不顺手全修（会淹没 diff），只处理与本次改动相关的，其余记录。
  • 🔴 不许用「全量忽略规则」把 CI 变绿。

7.3 指标是信号，不是目标

指标能说明不能说明
覆盖率哪些代码从没被执行过断言是否正确（高覆盖 + 零断言 = 零）
圈复杂度哪段逻辑分支多、难测业务是否复杂（该复杂的地方就该复杂）
重复代码率哪里有复制粘贴该不该抽象（见 §七）

🔴 不许为了指标好看去重构：把 200 行方法拆成 6 个类只为降复杂度，是拿可读性换数字。

八、运行时验证（测试环境的盲区）

测试环境全绿不等于线上没问题。核心链路交付后，应能回答：

  • 接口 P95 与错误率有没有异常；
  • CPU / 内存 / GC 有没有异常（内存是否单调增长）；
  • 数据库连接池、慢查询、锁等待；
  • Redis 命中率与响应时间；
  • 外部依赖的耗时与失败率；
  • 异步任务是否积压、消息是否堆积；
  • 关键业务动作成功率（下单、支付、发放）。

跨服务 / 异步链路要能用业务 ID 或 traceId 串起来，否则出问题只能靠猜。 🔴 观测手段本身不得成为泄露源：日志、埋点、trace 里不许出现密码、Token、密钥、完整证件号。

九、工具与自动化

9.1 母本只定义「工具位」，工具名由实例填

不把 JMH / pprof / JFR 这类名字写死在母本：栈不同、版本不同、CI 环境不同， 写死的结果是要么被无视，要么被机械照抄到不适用的仓。工具映射在实例里维护（§十一 第 1 项）。

工具位回答什么问题本仓工具（实例填）命令（实例填）
编译 / 类型检查有没有明显写错
单元测试规则对不对
集成测试组件协作对不对
静态分析有没有可疑写法
依赖漏洞扫描依赖有没有已知 CVE
基准测试局部快不快
性能剖析时间花在哪
负载 / 压力测试系统扛不扛得住

选型原则：优先语言/框架官方工具 → 优先维护活跃的成熟工具 → 一个工具位一个工具（不叠三个同类）→ 能稳定进 CI 的才值得长期维护。

9.2 哪些进 CI，哪些不进

进每次提交 / PR不进每次提交（专项或定期）
编译、类型检查压力测试
单元测试复杂并发与故障注入
集成测试（可容器化的）全量 profiler
静态分析（新增代码）大规模数据量对比
依赖漏洞扫描安全渗透测试

理由：门禁要快且稳定。把 20 分钟的压测塞进每次 PR，结果是被跳过或被注释掉。

9.3 质量门禁

按风险设，每条都要能说清「为什么它能阻断」：

  • 编译失败、核心业务测试失败 → 阻断；
  • 权限 / 越权用例失败 → 阻断；
  • 并发一致性用例失败 → 阻断；
  • 已确认且有修复方案的严重漏洞 → 按安全策略阻断；
  • 性能未达既定目标 → 需要分析结论，不自动阻断（目标本身可讨论）。

🔴 不设机械覆盖率阈值：覆盖率 ≥ 80% 只会催生没有断言的测试。

十、交付：验证报告怎么写

10.1 五种状态，不许混用

状态含义
已通过实际执行了，结果符合预期（附命令 / 用例名）
未通过执行了，结果不符合预期（说明现状与影响）
未执行本次没跑（说明为什么）
不适用本次改动不涉及（说明为什么）
受阻想跑但跑不了（环境 / 依赖 / 权限，说明卡在哪）

🔴 「未执行」不能写成「通过」，「受阻」不能写成「不适用」。

10.2 报告模板（按等级选，不要一律用完整表）

L1 / L2 —— 一行写完，不建表：

验证：L2（参数校验逻辑）· `./gradlew test --tests OrderValidatorTest` 9 例通过 · `tsc --noEmit` 0 error · 未跑集成（未触及事务 / 状态机）

一行要能回答四件事：等级（含依据）+ 做了什么 + 结果 + 没做什么及原因。 三行是上限，不是配额。

L3 / L4 —— 完整表（直接抄）：

### 验证结果

- 改动范围：<模块 / 文件 / 行为>
- 风险等级：L<N>（依据：命中 §2.1 第 <n> 条）

| 验证项 | 状态 | 证据 |
| :--- | :--- | :--- |
| 编译 / 类型检查 | 已通过 | `tsc --noEmit`，0 error |
| 单元测试 | 已通过 | `<用例文件>` 12 例，覆盖 <行为> |
| 集成测试 | 已通过 | 真库容器，覆盖事务回滚 + 唯一约束撞键 |
| 并发测试 | 未执行 | 本次未改状态机与扣减路径 |
| 压测 | 不适用 | 非高频路径 |

- 未覆盖场景：<...>
- 已知风险：<...>
- 建议后续：<...>

🔴 反向也是错的：给一个 DTO 字段改动交一张七行表，不是更严谨，而是让真正的 L3 报告失去信号—— 两份报告长得一样，读者就无法从形式判断该不该细看。

10.3 七种假验证（自查）

表现为什么是假的
「编译通过」→「功能已完成」编译不验证任何业务行为
只跑 mock 单测 →「数据库并发安全」mock 里没有事务、锁、约束
跑了一遍静态分析 →「没有 Bug」静态分析看不见业务与竞态
覆盖率 90% →「测试充分」可能是 90% 的代码被执行、0 条断言
没有前后数字 →「性能提升明显」无对比即无结论
测试失败 → 改预期 / 删用例 →「全部通过」把问题藏起来了
「已验证」但不说命令、环境、用例无法复核，等于没验

10.4 交付闭环：等级决定走几步

等级走哪几步明确不走
L1② 改 → ⑤ 编译 / 类型检查 → ⑥ 一行证据不写验证设计（③）、不列未覆盖场景、不建报告表
L2① 理解 → ② 改 → ④ 跑相关测试 → ⑥ 一行证据不做基准 / 剖析 / 压测 / 并发
L3 / L4六步全走（下）——

🔴 L1 的「不读规范」≠「不核实事实」。 表里写「必读：无」，指的是不用读设计与验证规范， 不是可以凭印象写。实测反例：改一条配置注释（L1），仍需 grep 两次 —— 一次确认注释引用的配置项真的被使用，一次确认它声称的错误码真的会抛。 少这两步，交付的就是一条骗人的注释，比不改更坏。

六步全貌（L3 / L4 适用）：

① 理解需求   → 业务目标、改动范围、风险在哪
② 设计实现   → 按《代码设计规范》
③ 设计验证   → 要证明哪几条行为（先写预期，再选手段）
④ 执行验证   → 跑测试与静态分析，必要时基准、剖析、压测、并发
⑤ 分析结果   → 失败就修；修不了就记录风险，不许绕过
⑥ 交付报告   → 实际做了什么、通过了什么、还剩什么（§10.2）

🔴 「缺一步就不算完成」只对 L3 / L4 成立。 对 L1 也套六步，等于把 §零 第 2 条（风险决定深度）当场作废； 而 §零 是优先级高于本文所有条款的元规则，冲突时以 §零 为准。

十一、各仓实例怎么建

  1. 复制本文全文到本仓 docs/code-validation.md，状态行改成 实例 · 现行（母本：cqlql-notes/docs/工程/代码验证规范.md）。 🔴 留全文，不要改成「只放指针 + 差异」：AI 在仓内读不到别的仓，规范一旦只存在于别处，等于没写。
  2. 删掉不适用的章节：按节标题的 〔后端〕 标记整节删，不逐句判断（无前端就没有前后端规则同步；无支付就没有回调验签）。
  3. 填七项本仓信息（下表就是填空清单）：
#实例必须补例
1工具位映射（§9.1 表右两列）JUnit5 + Testcontainers + SpotBugs + JMH
2编译 / 测试 / 静态分析的具体命令./gradlew test、./gradlew spotbugsMain
3集成测试的环境与依赖本地 PG 容器、Redis 容器、启动脚本
4核心业务的专项验证场景充值回调重放、退款两段事务、权益冻结
5并发 / 事务 / 一致性要求扣减并发 N=50、幂等重启后重放
6性能目标与测试条件（有明确要求才写）列表接口 P95 < 300ms @ 100 并发
7CI 执行的检查与门禁PR 必跑单测 + lint；夜间压测
  1. AGENTS.md 只放验证命令 + 3~5 条最反直觉的红线，正文不进 （≤220 行 / 16.5KB，见 ）。

十二、与其他母本的分工

文件回答什么体积
AGENTS.md本仓验证命令 + 红线（一句结论 + 一个指针）≤ 220 行 / 16.5KB
代码应该怎么写不限
代码验证规范（本文）怎么证明写对了、验到什么深度、交什么证据不限
数据访问层怎么写 + 它的验证闭环（§六）不限

实例 docs/code-validation.md本仓工具、命令、环境、专项场景不限
